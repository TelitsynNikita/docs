## 1.0 Пролог: два сервиса, которые не выдержали нагрузки

У тебя есть два сервиса. Первый — `order-service` — принимает заказы от пользователей. Второй — `email-service` — отправляет письма: «Ваш заказ принят», «Заказ отправлен», «Заказ доставлен».

Пока заказов было немного, всё работало отлично. `order-service` обрабатывал запрос, а затем **синхронно** вызывал `email-service` по HTTP:

```go
// order-service, упрощённо
func (s *OrderService) CreateOrder(ctx context.Context, order Order) error {
    // 1. Сохраняем заказ в БД
    if err := s.db.Save(ctx, order); err != nil {
        return err
    }

    // 2. Синхронно вызываем email-service
    if err := s.emailClient.SendOrderConfirmation(ctx, order.UserEmail, order.ID); err != nil {
        // Что делать, если письмо не ушло?
        // Заказ уже сохранён. Откатывать?
        return err
    }

    return nil
}
```

Всё было хорошо. Ровно до того момента, как `email-service` начал падать.

### Первый звонок: падение email-service

Однажды ночью `email-service` ушёл в перезагрузку. Пользователи начали оформлять заказы. `order-service` успешно сохранял заказы в БД, а затем пытался вызвать `email-service` — и получал `connection refused`.

**Что произошло:**

```
Пользователь → order-service → [БД: заказ сохранён] → email-service ❌
                                              ↓
                                    HTTP 500 пользователю
                                    «Ошибка оформления заказа»
```

Пользователь видит ошибку. Заказ **на самом деле сохранён** в БД. Но письма нет. Пользователь пытается оформить заказ снова — создаётся **дубликат**.

Это **первая проблема**: синхронный вызов делает **всю операцию** зависимой от **самого медленного и самого хрупкого** звена в цепочке.

### Второй звонок: пиковая нагрузка

Чёрная пятница. Заказов в 100 раз больше обычного. `order-service` справляется — он пишет в БД быстро. А `email-service` — нет. Отправка письма через SMTP занимает 200 миллисекунд. При 1000 заказов в секунду это 200 000 миллисекунд работы, которые нужно распараллелить.

**Что происходит:**

```
order-service держит HTTP-соединения открытыми, ожидая ответа от email-service.
Пул соединений исчерпан.
Новые запросы от пользователей не принимаются.
Вся система встала.
```

Это **вторая проблема**: медленный потребитель **тормозит** быстрого производителя. Синхронный вызов **связывает** их скорости.

### Третий звонок: бизнес хочет новое

Бизнес говорит: «Хотим отправлять push-уведомления», «Хотим аналитику по заказам в реальном времени», «Хотим начислять бонусные баллы».

**Что происходит:**

```
order-service теперь должен:
  1. Сохранить заказ
  2. Вызвать email-service
  3. Вызвать push-service
  4. Отправить данные в analytics
  5. Вызвать loyalty-service

Каждый новый потребитель → правка order-service.
Каждый новый потребитель → риск падения всей цепочки.
```

Это **третья проблема**: синхронная архитектура **жёстко связывает** производителя со всеми потребителями. Добавление нового потребителя требует изменения производителя.

### Что мы имеем

Три проблемы, одна причина: **прямой синхронный вызов**.

1. **Хрупкость.** Падение потребителя ломает операцию производителя.
2. **Связывание скоростей.** Медленный потребитель тормозит быстрого производителя.
3. **Жёсткая связанность.** Новый потребитель = правка производителя.

**Вопрос:** как разорвать эту цепочку?

## 1.1 Проблема: синхронный вызов как хрупкая цепочка

### Три вида связанности

Когда `order-service` синхронно вызывает `email-service`, между ними возникает **три вида связанности**:

**1. Временная связанность (temporal coupling)**

`order-service` и `email-service` должны быть **одновременно доступны**. Если `email-service` упал, `order-service` не может завершить операцию.

```
order-service работает → email-service должен работать
order-service упал → не важно, email-service всё равно не получит данные
email-service упал → order-service не может завершить операцию
```

**2. Пространственная связанность (spatial coupling)**

`order-service` должен **знать адрес** `email-service`. Если `email-service` переехал на другой хост, изменился порт или DNS — `order-service` нужно обновить.

**3. Связанность по скорости (rate coupling)**

`order-service` может обрабатывать 10 000 запросов в секунду. `email-service` — только 100. Синхронный вызов означает, что `order-service` **вынужден** ждать `email-service` и работать на его скорости.

### Почему это не масштабируется

Представь, что к `order-service` добавили ещё пять потребителей: push, SMS, аналитика, лояльность, логистика.

**Синхронная архитектура:**

```
order-service
    ├── HTTP → email-service
    ├── HTTP → push-service
    ├── HTTP → sms-service
    ├── HTTP → analytics-service
    ├── HTTP → loyalty-service
    └── HTTP → logistics-service

Время обработки одного заказа:
  = время(БД) + время(email) + время(push) + время(sms) + ...
  = 5 мс + 200 мс + 150 мс + 180 мс + 50 мс + 300 мс
  = 885 мс

Вероятность успеха:
  = P(email) × P(push) × P(sms) × P(analytics) × P(loyalty) × P(logistics)
  = 0.99 × 0.98 × 0.97 × 0.99 × 0.95 × 0.99
  ≈ 0.87

13% заказов падают из-за проблем с одним из потребителей.
```

**Проблема усугубляется с каждым новым потребителем.**

### Аналогия: телефонный звонок vs голосовое сообщение

Синхронный вызов — это **телефонный звонок**. Ты набираешь номер. Если абонент не берёт трубку — ты не можешь оставить сообщение. Если линия занята — ты ждёшь. Если абонент недоступен — ты не можешь передать информацию.

Асинхронная очередь — это **голосовая почта**. Ты оставляешь сообщение и **продолжаешь заниматься своими делами**. Абонент прослушает его, когда сможет. Тебе не нужно ждать.

**Ключевое отличие:** в синхронной модели **отправитель ждёт получателя**. В асинхронной — **отправитель кладёт сообщение в буфер и забывает**.

### Что нам нужно

Нам нужен **буфер** между производителем и потребителем. Производитель кладёт данные в буфер и **не ждёт**. Потребитель забирает данные из буфера **в своём темпе**.

```
order-service → [БУФЕР] → email-service
              → [БУФЕР] → push-service
              → [БУФЕР] → analytics-service
```

**Требования к буферу:**

1. **Производитель не ждёт потребителя.** Кладёт данные и идёт дальше.
2. **Потребитель может отставать.** Данные ждут в буфере.
3. **Падение потребителя не ломает производителя.** Данные остаются в буфере.
4. **Добавление нового потребителя не требует правки производителя.** Новый потребитель просто читает из буфера.
5. **Данные не теряются.** Буфер должен быть надёжным.

Это и есть **очередь сообщений** (message queue). Или, в случае Kafka, **распределённый лог**.

## 1.2 Идея: буферизация и развязка через очередь

### Как работает очередь сообщений

Очередь сообщений — это **посредник** между производителем и потребителем.

```
БЫЛО (синхронно):
  order-service ────────HTTP───────► email-service
  (ждёт ответа)

СТАЛО (через очередь):
  order-service ──► [ ОЧЕРЕДЬ ] ──► email-service
  (не ждёт)         (буфер)        (читает в своём темпе)
```

**Производитель** (order-service):

1. Формирует сообщение: «Заказ #123 создан для user@mail.com».
2. Кладёт его в очередь.
3. **Сразу получает подтверждение** и идёт дальше.

**Потребитель** (email-service):

1. Читает сообщения из очереди.
2. Отправляет письмо.
3. Подтверждает обработку.

**Что изменилось:**

| Аспект | Синхронно | Через очередь |
|:---|:---|:---|
| **Временная связанность** | Оба должны работать | Могут работать в разное время |
| **Пространственная связанность** | order-service знает адрес email-service | order-service знает только адрес очереди |
| **Связанность по скорости** | order-service ждёт email-service | order-service не ждёт |
| **Падение потребителя** | Ломает order-service | Данные ждут в очереди |
| **Новый потребитель** | Правка order-service | Новый потребитель просто читает |

### Что такое «очередь» в классическом смысле

Классическая очередь сообщений (RabbitMQ, ActiveMQ) работает так:

```
Производитель кладёт сообщение → Очередь
Очередь доставляет сообщение ОДНОМУ потребителю → Потребитель обрабатывает → Сообщение УДАЛЯЕТСЯ
```

**Ключевые свойства:**

- **Одно сообщение — один потребитель.** Если два потребителя читают одну очередь, они **делят** сообщения между собой.
- **Сообщение удаляется после обработки.** Нет «истории».
- **Нет повторного чтения.** Если потребитель обработал сообщение и упал — при перезапуске он **не увидит** это сообщение снова.

Это работает для **задач** (task queue): «отправь письмо», «обработай платёж». Каждая задача выполняется **один раз**.

### Чего не хватает классической очереди

Вернёмся к нашему примеру. Бизнес хочет, чтобы **аналитика** тоже получала данные о заказах. И **loyalty-service**. И **логистика**.

**Классическая очередь:**

```
order-service → [ОЧЕРЕДЬ] → email-service
                           (другие не получают)
```

Чтобы добавить аналитику, нужно **ещё одна очередь**:

```
order-service → [ОЧЕРЕДЬ 1] → email-service
              → [ОЧЕРЕДЬ 2] → analytics-service
              → [ОЧЕРЕДЬ 3] → loyalty-service
```

**Проблема:** производитель должен **знать** обо всех очередях и **писать в каждую**. Это возвращает нас к связанности.

### Что нужно: лог, а не очередь

Нам нужен не «канал, который доставляет сообщение одному потребителю и удаляет его», а **журнал событий**, который:

1. **Хранит все сообщения** (не удаляет после обработки).
2. **Позволяет нескольким потребителям читать независимо.**
3. **Позволяет перечитать** сообщения с начала (replay).
4. **Гарантирует порядок** внутри раздела.

Это **распределённый лог**. И это — Kafka.

## 1.3 Почему Kafka — это не просто очередь

### Определение, а не метафора

Kafka часто называют «очередью сообщений». Это **неточно** и вводит в заблуждение.

**Точное определение:** Kafka — это **распределённый, реплицируемый, append-only лог** (distributed commit log).

Разберём каждое слово:

- **Распределённый** — данные хранятся на нескольких узлах (брокерах).
- **Реплицируемый** — каждая часть данных существует в нескольких копиях для отказоустойчивости.
- **Append-only** — данные только добавляются в конец. Их нельзя изменить или удалить по произвольному смещению.
- **Лог** — упорядоченная последовательность записей.

### Лог vs очередь: принципиальная разница

| Свойство | Классическая очередь | Лог (Kafka) |
|:---|:---|:---|
| **После обработки** | Сообщение удаляется | Сообщение остаётся |
| **Несколько потребителей** | Делят сообщения | Каждый читает все (в своём темпе) |
| **Повторное чтение** | Невозможно | Возможно (replay) |
| **Порядок** | Не гарантируется глобально | Гарантируется внутри раздела |
| **Хранение** | Пока не обработано | Пока не истечёт retention |
| **Семантика** | «Сделай это один раз» | «Вот что произошло, реагируй как хочешь» |

### Лог как в журнале транзакций БД

Вспомни, как работает WAL (Write-Ahead Log) в PostgreSQL.

Когда ты делаешь `UPDATE users SET email = 'new@mail.com'`, PostgreSQL:

1. Записывает в WAL: «Транзакция 100: users.id=42, email изменился с old@mail.com на new@mail.com».
2. WAL — это **append-only лог**. Записи добавляются в конец.
3. Позже фоновые процессы читают WAL и применяют изменения к страницам данных.
4. WAL можно **перечитать** для восстановления после сбоя.

**Kafka работает так же.** Только вместо транзакций БД — **события** («заказ создан», «пользователь зарегистрирован»). А вместо одной машины — **кластер брокеров**.

> **Kafka — это распределённый append-only лог, как журнал транзакций в БД. Только вместо транзакций — сообщения, а вместо одной машины — кластер брокеров.**

### Что это меняет на практике

**Классическая очередь (RabbitMQ):**

```
Задача: отправить письмо.
  → Производитель кладёт задачу.
  → Один из потребителей забирает.
  → После отправки задача УДАЛЯЕТСЯ.
  → Если нужно ещё раз — заново положить.
```

**Лог (Kafka):**

```
Событие: заказ создан.
  → Производитель записывает событие в лог.
  → email-service читает событие и отправляет письмо.
  → push-service читает ТО ЖЕ событие и отправляет push.
  → analytics-service читает ТО ЖЕ событие и обновляет статистику.
  → Событие ОСТАЁТСЯ в логе (до истечения retention).
  → Через месяц можно перечитать все события и пересчитать аналитику.
```

**Ключевое:** в Kafka **один производитель записывает событие один раз**, а **сколько потребителей его прочитают — не его забота**. Каждый потребитель читает в своём темпе и хранит свою позицию (offset).

### Почему это называется «развязкой»

**Синхронно:** order-service **знает** о email-service, push-service, analytics-service. Он **вызывает** каждого.

**Через Kafka:** order-service **не знает** ни о ком. Он **записывает событие в топик**. Кто его прочитает — не его дело.

```
order-service:
  Публикую событие «order.created» в топик «orders».
  Всё. Моя работа сделана.

email-service:
  Подписан на топик «orders». Читаю, отправляю письмо.

push-service:
  Подписан на топик «orders». Читаю, отправляю push.

analytics-service:
  Подписан на топик «orders». Читаю, обновляю статистику.
```

**Добавление нового потребителя:** analytics-service просто подписывается на топик. order-service **не меняется**.

**Падение потребителя:** email-service упал. События остаются в топике. Когда email-service восстановится — он продолжит с того места, где остановился.

## 1.4 Kafka среди других: RabbitMQ, NATS, Pulsar

Kafka — не единственный брокер. Разберём, чем она отличается от конкурентов.

### Сравнительная таблица

| Свойство | Kafka | RabbitMQ | NATS JetStream | Pulsar |
|:---|:---|:---|:---|:---|
| **Модель** | Распределённый лог | Очередь/обменник | Лог + очередь | Лог + очередь |
| **Язык реализации** | Java/Scala | Erlang | Go | Java |
| **Размер бинарника** | JVM + JARs (большой) | Erlang runtime | < 15 МБ | JVM |
| **Пропускная способность** | Миллионы/сек | Десятки тысяч/сек | Миллионы/сек (JetStream) | Миллионы/сек |
| **Задержка** | Миллисекунды | Микросекунды | Микросекунды (core), миллисекунды (JetStream) | Миллисекунды |
| **Хранение после чтения** | Да (retention) | Нет (удаляется) | Да (JetStream) | Да |
| **Replay** | Да | Нет | Да (JetStream) | Да |
| **Порядок** | Внутри раздела | Внутри очереди | Внутри потока | Внутри раздела |
| **Маршрутизация** | Топик + раздел | Обменники (direct, topic, fanout, headers) | Субъекты + wildcards | Топик + SQL-фильтры |
| **Гарантии** | at-least-once, exactly-once | at-least-once, exactly-once | at-most-once (core), at-least-once (JetStream) | at-least-once, exactly-once |
| **Экосистема** | Connect, Streams, Schema Registry | Плагины | Минимальная | Functions, Tiered Storage |
| **Операционная сложность** | Высокая | Средняя | Низкая | Высокая |

### Kafka: распределённый лог

Kafka спроектирована для **максимальной пропускной способности** и **хранения истории**. Её архитектура — append-only лог с разделами.

**Когда выбирать Kafka:**

- Логи, метрики, события (высокий throughput).
- Event sourcing, CQRS.
- Real-time стриминг (Kafka Streams).
- Аналитические пайплайны.

**Цена:** высокая операционная сложность. ZooKeeper/KRaft, управление разделами, мониторинг consumer lag, планирование retention .

### RabbitMQ: гибкая маршрутизация

RabbitMQ — **классический брокер сообщений**. Его сильная сторона — **гибкая маршрутизация** через обменники (exchanges).

```
Producer → Exchange → [правила маршрутизации] → Queue 1
                                              → Queue 2
                                              → Queue 3
```

Exchange может быть:

- **Direct** — точное совпадение routing key.
- **Topic** — wildcard-совпадение (`order.*.created`).
- **Fanout** — во все очереди.
- **Headers** — по атрибутам сообщения.

**Когда выбирать RabbitMQ:**

- Сложная маршрутизация (много очередей, правил).
- Задачи (task queue), где каждое сообщение обрабатывается один раз.
- Низкая задержка критична (микросекунды).
- Не нужен replay или хранение истории.

**Пример:** отправка email. Ты кладёшь задачу «отправить письмо». Один из worker'ов забирает и отправляет. После отправки задача удаляется.

### NATS: лёгкость и гибкость

NATS — **лёгкая, высокопроизводительная система обмена сообщениями**, написанная на Go . Она состоит из двух компонентов:

- **Core NATS** — базовая система без персистентности (at-most-once).
- **NATS JetStream** — добавляет персистентность, гарантии доставки и replay .

**Ключевые преимущества NATS:**

**1. Операционная простота**

NATS — это **один бинарник размером менее 15 МБ**, написанный на Go. Нет JVM, нет ZooKeeper, нет зависимости от внешних координационных сервисов .

> «NATS остаётся гораздо более лёгкой в эксплуатации, чем Kafka. Есть много вещей, которые NATS делает из коробки, для которых с Kafka пришлось бы развернуть Kafka Streams, коннекторы и mirror maker поверх брокеров.» 

**2. Низкая задержка**

NATS спроектирована для **микросекундной задержки** в Core NATS. Это делает её идеальной для микросервисной коммуникации, IoT, real-time приложений .

**3. Гибкость моделей обмена**

NATS поддерживает **Request-Response** из коробки. В Kafka для этого нужно строить логику самостоятельно .

**4. JetStream: персистентность без сложности**

JetStream добавляет к NATS:

- **Streams** — серверное хранилище сообщений, привязанное к субъектам .
- **Consumers** — серверные stateful-представления потоков, отслеживающие позицию клиента .
- **Гарантии доставки** — at-least-once через явные подтверждения .
- **Replay** — возможность перечитать сообщения с начала, с определённого времени или последовательности .

**Ключевое отличие от Kafka:** JetStream **не требует партиционирования** для параллельного потребления. Один поток может читать несколько консьюмеров без разделения на партиции . Это упрощает проектирование, но создаёт сложности для строго упорядоченного потребления (нужны клиентские библиотеки вроде Orbit для эмуляции consumer groups) .

**5. Work-queue семантика**

JetStream поддерживает **WorkQueue retention policy** — сообщения удаляются после подтверждения обработки, что делает его пригодным для task queue .

**Когда выбирать NATS:**

- Микросервисная коммуникация (Core NATS).
- IoT и edge computing (малый размер, низкое потребление ресурсов).
- Real-time приложения (чат, игры).
- Сценарии, где операционная простота важнее максимального throughput.
- Гибридные архитектуры: NATS для messaging + Kafka для стриминга .

**Ограничения NATS:**

- **Меньше экосистема.** Нет аналога Kafka Connect, Kafka Streams, Schema Registry.
- **Меньше throughput в распределённых сценариях.** Исследования показывают, что Kafka достигает лучшей производительности и эффективнее использует ресурсы при тяжёлых распределённых нагрузках .
- **Consumer groups сложнее.** Концепция consumer group в Kafka «чище» и проще для понимания .

### Pulsar: конкурент Kafka

Pulsar — **следующее поколение** после Kafka. Ключевое отличие: **разделение вычислений и хранения**.

```
Kafka:
  Брокер хранит данные на своём диске.

Pulsar:
  Брокер (вычисления) → BookKeeper (хранение)
```

**Преимущества Pulsar:**

- **Масштабирование хранения** независимо от вычислений.
- **Мультитенантность** из коробки.
- **Tiered Storage** — автоматическое перемещение старых данных в S3/GCS.

**Недостатки Pulsar:**

- Меньше экосистема.
- Сложнее в эксплуатации.
- Меньше готовых коннекторов.

### Когда что выбирать

| Задача | Рекомендация | Почему |
|:---|:---|:---|
| **Логи, метрики, события** (высокий throughput) | Kafka | Миллионы/сек, хранение, replay |
| **Task queue** (отправить письмо) | RabbitMQ | Гибкая маршрутизация, низкая задержка |
| **Микросервисная коммуникация** | NATS Core | Микросекундная задержка, простота |
| **Event sourcing, CQRS** | Kafka | Append-only лог, replay |
| **Real-time стриминг** | Kafka | Streams API, Connect |
| **IoT, edge computing** | NATS | Малый размер, низкое потребление ресурсов |
| **Мультитенантность + Tiered Storage** | Pulsar | Разделение вычислений и хранения |
| **Гибрид: messaging + стриминг** | NATS + Kafka | NATS для коммуникации, Kafka для данных  |

### Гибридные архитектуры: NATS + Kafka

Некоторые организации используют **обе системы**:

> «Я видел, как разные компании используют и Kafka, и NATS: Kafka для больших данных, NATS для обмена сообщениями.» 

**Пример гибридной архитектуры:**

```
Микросервисы:
  order-service ↔ NATS (request-response, низкая задержка)

Данные:
  order-service → Kafka (события, хранение, аналитика)
  email-service ← Kafka (подписка на события)
  analytics-service ← Kafka (подписка на события)
```

**Логика выбора:**

- **NATS** — для **коммуникации** между сервисами (команды, запросы, ответы).
- **Kafka** — для **данных** (события, аналитика, хранение).

## 1.5 Что Kafka делает хорошо и что — плохо

### ✅ Kafka делает хорошо

**1. Высокая пропускная способность**

Kafka спроектирована для **миллионов сообщений в секунду** на кластер. Секрет — в **последовательной записи на диск** (append-only) и **батчинге**.

```
Disk throughput (последовательная запись): ~500 МБ/с на SSD
Disk throughput (случайная запись): ~100 МБ/с на SSD

Kafka пишет последовательно → в 5 раз быстрее.
```

Исследования показывают, что Kafka достигает **1.2M сообщений/сек** с p95 latency 18ms в идеальных условиях . Однако реальные нагрузки (переменный размер сообщений, bursty traffic) снижают throughput на 40-70% .

**2. Хранение и replay**

Сообщения хранятся **до истечения retention** (по умолчанию 7 дней, настраивается). Можно **перечитать** с любого момента.

```
Сценарий: аналитика сломалась на 3 дня.
  → Починили.
  → Перечитали все события за 3 дня.
  → Пересчитали статистику.
```

**3. Несколько независимых потребителей**

Одно событие может быть прочитано **неограниченным** числом потребителей. Каждый хранит свою позицию (offset).

```
Топик «orders»:
  → email-service читает (offset = 1000)
  → push-service читает (offset = 1500)
  → analytics-service читает (offset = 800)

Никто никому не мешает.
```

**4. Порядок внутри раздела**

Kafka **гарантирует порядок** сообщений внутри **раздела** (partition). Если все события одного пользователя пишутся в один раздел — порядок гарантирован.

```
user_id = 42 → hash(42) % 3 = раздел 0

Все события пользователя 42:
  → «email изменён на a@mail.com» (раздел 0)
  → «email изменён на b@mail.com» (раздел 0)
  → «email изменён на c@mail.com» (раздел 0)

Порядок гарантирован: a → b → c.
```

**5. Масштабирование**

Добавление брокера → добавление разделов → больше пропускной способности.

### ❌ Kafka делает плохо

**1. Сложность эксплуатации**

Kafka — **распределённая система**. Она требует:

- ZooKeeper (или KRaft) для координации.
- Мониторинга (JMX-метрики, consumer lag).
- Настройки (сотни параметров).
- Понимания внутренних механизмов (ISR, ребалансировка).

> «Kafka операционно насыщена. Разделами нужно управлять. Offset'ы нужно сбрасывать. Consumer groups нужно инспектировать. Топики нужно создавать, изменять, мониторить. Ничего из этого не опционально в продакшене.»

Kafka требует «существенной операционной экспертизы и инвестиций в инфраструктуру» .

**2. Задержка**

Kafka оптимизирована для **пропускной способности**, а не для **задержки**. Батчинг и последовательная запись добавляют миллисекунды.

```
NATS Core: микросекунды
RabbitMQ: микросекунды
Kafka: миллисекунды (батчинг)
```

Для **реального времени** (финансовые транзакции, игры) Kafka может быть **слишком медленной**. NATS здесь выигрывает .

**3. Гибкая маршрутизация**

Kafka не умеет **сложную маршрутизацию**. Нет exchange'ов, нет wildcard-подписок, нет header-based routing.

```
RabbitMQ: можно маршрутизировать по routing key, headers, fanout.
NATS: субъекты + wildcards.
Kafka: только топик + раздел. Всё остальное — логика потребителя.
```

**4. Малые системы**

Для системы с 10 сообщениями в минуту Kafka — **избыточна**. Она требует кластера, мониторинга, эксплуатации. NATS с одним бинарником справится лучше .

**5. Тысячи потребителей**

Kafka **не спроектирована** для десятков тысяч TCP-соединений. Каждый consumer group хранит offset в `__consumer_offsets`. При миллионах потребителей это становится проблемой.

## 1.6 Когда Kafka не нужна

### Decision tree: Kafka или не Kafka

```
Нужен ли replay? (перечитать старые события)
  ├── ДА → Kafka
  └── НЕТ ↓

Нужно ли несколько независимых потребителей на одно событие?
  ├── ДА → Kafka
  └── НЕТ ↓

Нужно ли хранить историю событий?
  ├── ДА → Kafka
  └── НЕТ ↓

Высокий throughput? (миллионы/сек)
  ├── ДА → Kafka
  └── НЕТ ↓

Микросервисная коммуникация с низкой задержкой?
  ├── ДА → NATS Core
  └── НЕТ ↓

Task queue с гибкой маршрутизацией?
  ├── ДА → RabbitMQ
  └── НЕТ ↓

Всё остальное?
  → Redis, REST + background jobs, NATS JetStream
```

### Простые сценарии, где Kafka избыточна

**1. Отправка email**

```
Задача: пользователь зарегистрировался → отправить приветственное письмо.

NATS JetStream (WorkQueue): producer → stream → consumer → отправка → удаление.
RabbitMQ: producer → queue → email worker → отправка → удаление.
Kafka: producer → topic → consumer group → отправка → offset.

NATS/RabbitMQ проще, потому что:
  - Нет нужды в replay.
  - Один потребитель.
  - После отправки задача не нужна.
```

**2. Микросервисная коммуникация**

```
Задача: order-service вызывает inventory-service для проверки наличия.

NATS Core:
  - Request-Response из коробки.
  - Микросекундная задержка.
  - Не нужна персистентность.

Kafka здесь — оверкилл.
```

**3. Фоновые задачи**

```
Задача: обработать изображение (ресайз).

Redis + Sidekiq/Celery:
  - Быстро.
  - Просто.
  - Нет кластера Kafka.

Kafka здесь — оверкилл.
```

**4. Маленькая система**

```
Задача: 100 пользователей, 10 заказов в час.

NATS с одним бинарником < 15 МБ.
Kafka — избыточна.
```

### Признаки, что Kafka НУЖНА

- **Событийная архитектура (EDA).** Система строится вокруг событий.
- **Event sourcing.** Состояние восстанавливается из последовательности событий.
- **CQRS.** Разделение чтения и записи через события.
- **Аналитика в реальном времени.** События стекаются в Kafka, обрабатываются Streams.
- **Интеграция множества систем.** Kafka как «шина данных».
- **Высокий throughput.** Миллионы событий в секунду.

## 1.7 Выводы и типичные ошибки

**Что мы узнали?**

Синхронный вызов между сервисами создаёт три вида связанности: временную, пространственную и по скорости. Это делает систему хрупкой и не масштабируемой. Очередь сообщений разрывает эту связанность, выступая буфером. Kafka — это не просто очередь, а **распределённый append-only лог**: сообщения не удаляются после чтения, несколько потребителей читают независимо, возможен replay.

Kafka отличается от RabbitMQ/ActiveMQ моделью (лог vs очередь), от Pulsar — архитектурой (хранение на брокере vs разделение вычислений и хранения), от NATS — философией (максимальный throughput vs минимальная задержка и операционная простота).

NATS — лёгкая система на Go с одним бинарником, микросекундной задержкой и JetStream для персистентности. Она проще в эксплуатации, но имеет меньшую экосистему и уступает Kafka в распределённых нагрузках. Для микросервисной коммуникации и IoT NATS — отличный выбор. Для стриминга и аналитики — Kafka.

**Типичные ошибки:**

- ❌ **Использовать Kafka как «очередь по умолчанию».** Kafka — для стриминга и событий. Для простых задач — NATS, RabbitMQ или Redis.
- ❌ **Думать, что Kafka «доставляет сообщение».** Kafka **хранит** сообщение. Потребитель **читает** его. Это принципиально другая модель.
- ❌ **Игнорировать операционную сложность.** Kafka требует мониторинга, настройки, понимания ISR и ребалансировки. NATS — проще.
- ❌ **Синхронный вызов + Kafka одновременно.** Если ты вызываешь Kafka-клиент синхронно и ждёшь ответа — ты не используешь её преимуществ.
- ❌ **Выбирать Kafka для низкой задержки.** Kafka оптимизирована для throughput. Для микросекундной задержки — NATS Core.

## 1.8 Для быстрого повторения

- **Синхронный вызов** создаёт временную, пространственную и rate-связанность.
- **Очередь** разрывает связанность: производитель не ждёт потребителя.
- **Kafka — это лог, не очередь.** Сообщения не удаляются после чтения. Несколько потребителей читают независимо. Возможен replay.
- **RabbitMQ** — гибкая маршрутизация, task queue, микросекундная задержка.
- **NATS** — лёгкость (один бинарник < 15 МБ на Go), микросекундная задержка (Core), JetStream для персистентности, низкая операционная сложность.
- **Pulsar** — разделение вычислений и хранения, мультитенантность, Tiered Storage.
- **Kafka хороша для:** событий, стриминга, аналитики, event sourcing, CQRS.
- **NATS хороша для:** микросервисной коммуникации, IoT, real-time, edge computing.
- **Kafka плоха для:** простых task queue, малых систем, микросекундной задержки.
- **Decision tree:** replay? несколько потребителей? история? высокий throughput? → Kafka. Коммуникация с низкой задержкой? → NATS. Task queue? → RabbitMQ.

## 1.10 Ответы

**1.** Синхронный вызов создаёт: (1) временную связанность — оба сервиса должны быть доступны одновременно; (2) пространственную связанность — производитель знает адрес потребителя; (3) связанность по скорости — производитель ждёт потребителя.

**2.** Потому что order-service синхронно вызывает email-service. Если email-service упал, order-service получает ошибку и не может завершить операцию. Заказ уже сохранён в БД, но пользователь видит ошибку. При повторной попытке создаётся дубликат.

**3.** Буферизация — это помещение сообщения в промежуточное хранилище (очередь). Производитель кладёт сообщение и **не ждёт**. Потребитель забирает в своём темпе. Временная, пространственная и rate-связанность разрываются.

**4.** В классической очереди сообщение **удаляется после обработки**. В Kafka сообщение **остаётся** в логе до истечения retention. Это позволяет нескольким потребителям читать одно сообщение и перечитывать его (replay).

**5.** Kafka хранит данные как **append-only лог** — упорядоченную последовательность записей, которые только добавляются в конец. Как WAL в БД. Это позволяет: гарантировать порядок, хранить историю, перечитывать.

**6.** Каждый потребитель хранит свою **позицию** (offset) в разделе. Потребители не мешают друг другу: email-service читает с offset 1000, push-service — с offset 1500, analytics — с offset 800.

**7.** Replay — это **повторное чтение** сообщений с начала или с произвольного offset. Нужен для: восстановления после сбоя обработки, пересчёта аналитики, отладки.

**8.** Ключевое отличие — **философия и операционная сложность**. NATS — лёгкая система на Go (один бинарник < 15 МБ), с микросекундной задержкой в Core NATS. Kafka — JVM-система с высокой пропускной способностью, но сложной эксплуатацией. NATS проще, Kafka мощнее для распределённых нагрузок .

**9.** **Core NATS** — базовая система обмена сообщениями без персистентности, с гарантией at-most-once, микросекундной задержкой. **JetStream** — слой поверх NATS, добавляющий персистентность, at-least-once доставку, replay, streams и consumers .

**10.** NATS выбирать для: (1) микросервисной коммуникации с низкой задержкой; (2) IoT и edge computing (малый размер, низкое потребление ресурсов); (3) real-time приложений (чат, игры). В этих сценариях NATS проще и быстрее .

**11.** Pulsar **разделяет вычисления и хранение**: брокеры обрабатывают, BookKeeper хранит. Kafka хранит данные на брокерах. Это даёт Pulsar гибкость в масштабировании и мультитенантность.

**12.** Kafka избыточна для: (1) простой отправки email (task queue); (2) микросервисной коммуникации (NATS проще); (3) малой системы с 10 заказами в час. В этих случаях NATS или RabbitMQ проще и дешевле.

**13.** Task queue требует **удаления** сообщения после обработки. Kafka **не удаляет** сообщения. Если нужно «сделать один раз и забыть» — Kafka не подходит. NATS JetStream с WorkQueue retention или RabbitMQ — правильный инструмент .

**14.** «Операционно насыщена» означает, что Kafka требует **постоянного управления**: создание топиков, управление разделами, сброс offset'ов, инспекция consumer groups, мониторинг. Это не «поставил и забыл» — это система, требующая внимания .
