## 2.0 Пролог: от одного брокера к кластеру

В Главе 1 мы разобрались, **зачем** нужна Kafka: она разрывает связанность между сервисами, выступая буфером-логом, из которого несколько потребителей читают независимо. Мы поняли, что Kafka — это **распределённый append-only лог**, а не очередь.

Но остались вопросы:

- **Как** Kafka хранит данные? Что такое **раздел** (partition)?
- **Что** такое **брокер** и **кластер**?
- **Как** producer записывает данные, а consumer читает?
- **Что** такое **offset** и **consumer group**?
- **Почему** одного сервера недостаточно для продакшена?

В этой главе мы **запустим Kafka** и напишем **первый producer и consumer** на Go. Ты увидишь все сущности **в работе**, а не в теории. А потом мы разберём, куда идти дальше: каждая сущность получит **детальный разбор** в отдельной главе книги.

## 2.1 Первый запуск: producer, consumer, один брокер

### Что нам нужно

Прежде чем разбирать архитектуру кластера, давай **запустим Kafka** и напишем простейшие producer и consumer на Go. Ты увидишь, как это работает, и **через код** поймёшь, какие сущности существуют.

Нам понадобится:

1. **Docker** — чтобы запустить Kafka локально.
2. **Go** — чтобы написать producer и consumer.
3. **Две библиотеки**: `sarama` (IBM) и `kafka-go` (Segment) — будем изучать обе.

### Шаг 1: Запускаем Kafka через Docker

Создай файл `docker-compose.yml`:

```yaml
version: '3.8'

services:
  kafka:
    image: apache/kafka:3.7.0
    container_name: kafka
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
```

Запусти:

```bash
docker-compose up -d
```

Проверь, что Kafka работает:

```bash
docker logs kafka | tail -20
```

Ты должен увидеть что-то вроде:

```
[2024-01-15 10:00:00,000] INFO [KafkaRaftServer nodeId=1] Kafka Server started (kafka.server.KafkaRaftServer)
```

**Что мы только что сделали:**

Мы запустили **один сервер Kafka** в Docker. В конфигурации есть строка `KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092` — она говорит Kafka, по какому адресу к ней подключаться. Порт `9092` — это стандартный порт для клиентов Kafka.

Внутри этого одного контейнера работает **весь процесс Kafka**: сетевой слой, который принимает подключения, слой хранения, который пишет на диск, слой координации. Это не набор микросервисов — это **один процесс**, который делает всё.

### Шаг 2: Пишем producer на kafka-go

Создай директорию проекта:

```bash
mkdir kafka-go-example
cd kafka-go-example
go mod init kafka-go-example
go get github.com/segmentio/kafka-go
```

Создай файл `producer.go`:

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/segmentio/kafka-go"
)

func main() {
	w := &kafka.Writer{
		Addr:     kafka.TCP("localhost:9092"),
		Topic:    "orders",
		Balancer: &kafka.LeastBytes{},
	}
	defer w.Close()

	for i := 1; i <= 5; i++ {
		msg := kafka.Message{
			Key:   []byte(fmt.Sprintf("user-%d", i)),
			Value: []byte(fmt.Sprintf(`{"order_id": %d, "total": %d}`, i, i*1000)),
		}

		err := w.WriteMessages(context.Background(), msg)
		if err != nil {
			log.Fatalf("Ошибка отправки: %v", err)
		}

		fmt.Printf("Отправлено: key=%s value=%s\n", msg.Key, msg.Value)
		time.Sleep(500 * time.Millisecond)
	}
}
```

Запусти:

```bash
go run producer.go
```

Ты увидишь:

```
Отправлено: key=user-1 value={"order_id": 1, "total": 1000}
Отправлено: key=user-2 value={"order_id": 2, "total": 2000}
...
```

### Шаг 3: Пишем consumer на kafka-go

Создай файл `consumer.go`:

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/segmentio/kafka-go"
)

func main() {
	r := kafka.NewReader(kafka.ReaderConfig{
		Brokers:  []string{"localhost:9092"},
		Topic:    "orders",
		GroupID:  "order-processor",
		MinBytes: 1,
		MaxBytes: 10e6,
	})
	defer r.Close()

	fmt.Println("Ждём сообщения...")

	for {
		msg, err := r.ReadMessage(context.Background())
		if err != nil {
			log.Fatalf("Ошибка чтения: %v", err)
		}

		fmt.Printf("Получено: key=%s value=%s partition=%d offset=%d\n",
			msg.Key, msg.Value, msg.Partition, msg.Offset)
	}
}
```

Запусти **в другом терминале**:

```bash
go run consumer.go
```

Ты увидишь:

```
Ждём сообщения...
Получено: key=user-1 value={"order_id": 1, "total": 1000} partition=0 offset=0
Получено: key=user-2 value={"order_id": 2, "total": 2000} partition=0 offset=1
...
```

### Шаг 5: Разбираем код — что мы только что сделали

Теперь, когда ты видел код в работе, давай **разберём каждую строчку** и поймём, какие сущности Kafka за ней стоят.

#### Брокер — сервер, к которому мы подключаемся

Вот эта строчка в producer'е:

```go
Addr: kafka.TCP("localhost:9092"),
```

Здесь мы задаём **адрес для подключения к серверу Kafka**. `localhost:9092` — это хост и порт, по которому Kafka принимает подключения от клиентов.

А вот эта строчка в consumer'е:

```go
Brokers: []string{"localhost:9092"},
```

Здесь то же самое, только в виде списка (можно указать несколько адресов).

**Что такое брокер?**

Брокер — это **сервер, на котором запущен процесс Kafka**. Это отдельный узел: у него есть свой IP-адрес (или доменное имя), свой порт, свой диск, своя память.

Когда ты пишешь `localhost:9092`, ты говоришь клиенту: «Подключись к серверу Kafka, который работает на localhost и слушает порт 9092».

**Что делает брокер:**

Брокер — это **рабочая лошадка** Kafka. Он:

- **Принимает подключения** от producer'ов и consumer'ов.
- **Принимает сообщения** от producer'ов и **сохраняет их на диск**.
- **Отдаёт сообщения** consumer'ам, когда они запрашивают.
- **Хранит разделы** (partitions) топиков, за которые отвечает.
- **Реплицирует данные** другим брокерам (если их несколько).

**Важно:** брокер — это не «база данных», не «очередь» и не «микросервис». Это **узел кластера**, который хранит данные и обрабатывает запросы. Внутри одного брокера работают все компоненты Kafka: сетевой слой, API, хранилище, координация. Это **один процесс**, а не набор сервисов.

**Сколько брокеров у нас сейчас?**

В нашем `docker-compose.yml` мы запустили **один брокер**. В выводе `kafka-topics.sh --describe` мы видели `Leader: 1` — это значит, что лидером раздела является брокер с ID 1 (мы задали `KAFKA_NODE_ID: 1` в конфиге).

```
┌─────────────────────────────────────────────┐
│  БРОКЕР (ID = 1)                            │
│                                             │
│  Адрес: localhost:9092                      │
│                                             │
│  ┌─────────────────────────────────────┐    │
│  │  Процесс Kafka                      │    │
│  │                                     │    │
│  │  • Принимает сообщения              │    │
│  │  • Сохраняет на диск                │    │
│  │  • Отдаёт потребителям              │    │
│  │  • Участвует в координации          │    │
│  └─────────────────────────────────────┘    │
│                                             │
└─────────────────────────────────────────────┘
```

**Ключевое:** в нашем случае брокер — **один**. Если он упадёт, данные потеряются. Чтобы пережить падение, нужно **несколько брокеров** — это и есть кластер. Но об этом в следующих подглавах.

#### Топик — куда мы пишем и откуда читаем

Вот эта строчка в producer'е:

```go
Topic: "orders",
```

Здесь мы указываем, **в какой топик** писать сообщения. `orders` — это имя топика.

А вот эта строчка в consumer'е:

```go
Topic: "orders",
```

Здесь то же самое: **из какого топика** читать.

**Что такое топик?**

Топик — это **логическая категория сообщений**. Это как «папка» или «канал», в который producer'ы пишут, а consumer'ы читают.

Можно представить топик как **таблицу в базе данных**: у неё есть имя (`orders`), и в неё пишутся строки (сообщения). Только в отличие от таблицы, топик — это **поток**, а не набор строк.

**Важно:** топик — это **логическое имя**, а не физическое хранилище. Физически данные лежат в **разделах** (partitions), из которых состоит топик. Об этом — следующий пункт.

**Что произошло в нашем случае:**

Мы **не создавали топик** `orders` явно. Kafka **автоматически создала** его при первой записи. Это поведение по умолчанию (`auto.create.topics.enable=true`).

Если бы автоматическое создание было отключено, producer получил бы ошибку «топик не существует». В продакшене обычно отключают автосоздание и создают топики явно — чтобы контролировать число разделов и replication factor.

#### Раздел — где физически лежат данные

Вот эта строчка в consumer'е:

```go
fmt.Printf("... partition=%d ...", msg.Partition)
```

Здесь мы выводим **номер раздела**, из которого пришло сообщение. В нашем выводе было `partition=0` — все сообщения пришли из раздела 0.

**Что такое раздел?**

Раздел — это **физическая единица хранения** внутри топика. Один топик состоит из одного или нескольких разделов. Каждый раздел — это **append-only лог**: сообщения добавляются только в конец, их нельзя изменить или удалить.

Раздел можно представить как **одну длинную ленту**, на которую последовательно наклеиваются сообщения. У каждого сообщения есть свой номер — **offset**.

**Почему разделы важны:**

1. **Порядок гарантируется внутри раздела.** Сообщения с offset 0, 1, 2 идут строго в этом порядке.
2. **Раздел — единица параллелизма.** Чем больше разделов, тем больше consumer'ов могут читать параллельно.
3. **Разделы распределяются между брокерами.** Если у тебя 3 брокера и 6 разделов, каждый брокер будет лидером для 2 разделов.

**В нашем случае:**

У топика `orders` **один раздел** (`PartitionCount: 1`), поэтому все сообщения попали в **partition 0**. Если бы разделов было 3, producer распределил бы сообщения между ними по ключу:

```
hash("user-1") % 3 = 0 → partition 0
hash("user-2") % 3 = 1 → partition 1
hash("user-3") % 3 = 2 → partition 2
...
```

#### Offset — номер сообщения в разделе

Вот эта строчка в consumer'е:

```go
fmt.Printf("... offset=%d ...", msg.Offset)
```

Здесь мы выводим **offset** — номер сообщения в разделе. В нашем выводе было `offset=0`, `offset=1`, и так далее.

**Что такое offset?**

Offset — это **уникальный номер сообщения внутри раздела**. Он монотонно возрастает: 0, 1, 2, 3, ... Каждое новое сообщение получает следующий номер.

Offset можно представить как **номер страницы в книге**: страница 0, страница 1, страница 2. Ты всегда знаешь, на какой странице ты находишься, и можешь вернуться к любой.

**Зачем нужен offset:**

Consumer **запоминает свой offset** — до какого места он дочитал. Если consumer перезапустится, он продолжит с того же места. Это позволяет не обрабатывать одни и те же сообщения повторно.

**Кто хранит offset:**

Offset хранится **в Kafka**, в специальном внутреннем топике `__consumer_offsets`. Consumer периодически **коммитит** свой offset — сообщает Kafka: «Я дочитал до offset 42 в partition 0».

#### Producer — кто пишет данные

Вот этот код:

```go
w := &kafka.Writer{
    Addr:     kafka.TCP("localhost:9092"),
    Topic:    "orders",
    Balancer: &kafka.LeastBytes{},
}
```

Здесь мы создаём **producer** — объект для записи в Kafka.

**Что такое producer:**

Producer — это **клиент, который пишет сообщения в топик**. Он:

- Подключается к брокеру (адрес указывается в `Addr: kafka.TCP("localhost:9092")`).
- Формирует сообщение: ключ, значение, заголовки.
- Выбирает раздел (по ключу или round-robin).
- Отправляет сообщение **лидеру** раздела.
- Ждёт подтверждения.

**Ключевое:** producer **не знает** заранее, какой брокер является лидером для нужного раздела. Он:

1. Подключается к **любому брокеру из списка адресов**, который ты указал в `Addr` (в нашем случае — `localhost:9092`).
2. Запрашивает **метаданные**: «Кто лидер для partition 0 топика orders?».
3. Получает ответ: «Лидер — брокер 1».
4. Отправляет сообщение **напрямую** брокеру 1.

**В нашем случае:**

Producer подключился к `localhost:9092`, запросил метаданные, узнал, что лидер для partition 0 — брокер 1 (единственный брокер), и отправил туда все 5 сообщений.

#### Consumer — кто читает данные

Вот этот код:

```go
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers:  []string{"localhost:9092"},
    Topic:    "orders",
    GroupID:  "order-processor",
    MinBytes: 1,
    MaxBytes: 10e6,
})
```

Здесь мы создаём **consumer** — объект для чтения из Kafka.

**Что такое consumer:**

Consumer — это **клиент, который читает сообщения из топика**. Он:

- Подключается к брокеру.
- Подписывается на **топик** (в `kafka-go` — один топик на один `Reader`).
- Читает сообщения из назначенных разделов.
- Обрабатывает сообщения.
- **Коммитит offset** — сообщает Kafka, до какого места дочитал.

**Важно про несколько топиков:**

В `kafka-go` один `Reader` читает **один топик** (поле `Topic` — это строка, а не срез). Если нужно читать несколько топиков — создай несколько `Reader`'ов, по одному на каждый топик.

В других библиотеках (например, `sarama`) можно подписаться на **несколько топиков** одним consumer group.

**В нашем случае:**

Consumer подключился к `localhost:9092`, подписался на топик `orders` как группа `order-processor`, прочитал все 5 сообщений, начиная с offset 0.

#### Consumer group — кто читает параллельно

Вот эта строчка:

```go
GroupID: "order-processor",
```

Здесь мы указываем **ID группы потребителей**. `order-processor` — это имя группы.

**Что такое consumer group:**

Consumer group — это **группа потребителей, которые совместно читают топик**. Внутри одной группы:

- **Один раздел — один потребитель.** Раздел читается только одним consumer'ом в группе.
- **Разные группы читают независимо.** Два consumer'а в разных группах получают все сообщения.

**В нашем случае:**

У нас **один consumer** в группе `order-processor`. Он читает все сообщения из топика `orders` (потому что у топика один раздел).

**Что было бы с несколькими consumer'ами:**

Если бы мы запустили **второй** consumer с тем же `GroupID: "order-processor"`, Kafka попыталась бы распределить разделы между ними. Но у нас **один раздел**, поэтому второй consumer **простаивал** бы.

**Что было бы с разными GroupID:**

Если бы мы запустили consumer с `GroupID: "analytics"`, он **независимо** прочитал бы все те же сообщения. Группы не мешают друг другу — каждая читает свою копию потока.

#### Репликация — как пережить падение брокера

В выводе `kafka-topics.sh --describe` мы видели:

```
ReplicationFactor: 1
```

**Что такое replication factor:**

Replication factor — это **сколько копий раздела хранится в кластере**. В нашем случае RF=1 — **одна копия**, то есть **нет репликации**.

**Что это значит:**

Если брокер, на котором лежит partition 0, упадёт — данные потеряются. Потребители не смогут читать, producer'ы не смогут писать.

**Что было бы с RF=3:**

Каждый раздел хранился бы на **3 брокерах**. Один брокер — **лидер** (обрабатывает запросы), два других — **follower'ы** (копируют данные). Если лидер упадёт, один из follower'ов станет новым лидером, и система продолжит работать.

**Почему RF=1 в нашем случае:**

У нас **один брокер**, поэтому RF=1 — единственный возможный вариант. Для RF=3 нужно **минимум 3 брокера**. Об этом — в подглаве 2.3.

#### ISR — синхронизированные реплики

В выводе `kafka-topics.sh --describe` мы видели:

```
Isr: 1
```

**Что такое ISR:**

ISR (In-Sync Replicas) — это **набор реплик, которые синхронизированы с лидером**. В нашем случае ISR = [1] — только лидер (потому что RF=1).

**Зачем нужен ISR:**

Когда лидер падает, новый лидер выбирается **только из ISR**. Это гарантирует, что новый лидер имеет все закоммиченные данные.

**Что было бы с RF=3:**

ISR мог бы быть `[1, 2, 3]` — все три реплики синхронизированы. Если один follower отстал, он исключается из ISR: `[1, 2]`.

#### Контроллер — кто координирует

В нашем случае брокер с ID 1 выполняет **две роли**: он и **broker** (хранит данные), и **controller** (управляет метаданными). Это потому что мы запустили Kafka в **KRaft mode** с `KAFKA_PROCESS_ROLES: broker,controller`.

**Что такое контроллер:**

Контроллер — это **брокер, который управляет метаданными кластера**:

- Отслеживает состояние брокеров (кто жив, кто упал).
- Назначает лидеров для разделов.
- Управляет списком топиков и их конфигурациями.

**В нашем случае:**

Единственный брокер — он же контроллер. Если бы брокеров было несколько, один из них был бы выбран контроллером (в KRaft mode — через Raft-quorum).

#### KRaft — как договориться о метаданных

В нашем `docker-compose.yml` мы использовали:

```yaml
KAFKA_PROCESS_ROLES: broker,controller
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
```

Это **KRaft mode** — встроенный консенсус-протокол, который заменяет ZooKeeper.

**Что такое KRaft:**

KRaft (Kafka Raft) — это **встроенный Raft-консенсус** для управления метаданными. В KRaft mode:

- Нет внешнего ZooKeeper.
- Контроллеры образуют **quorum** (группу) и договариваются о метаданных через Raft.
- Метаданные хранятся в специальном топике `__cluster_metadata`.

**В нашем случае:**

`KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093` означает: «один контроллер с ID 1 на localhost:9093». Это **quorum из одного узла** — для разработки нормально, для продакшена нужно 3-5 контроллеров.

**С Kafka 4.0 ZooKeeper полностью удалён.** Новые кластеры должны использовать KRaft с самого начала.

### Три ключевые идеи

**1. Kafka — это лог, а не очередь.**

Сообщения не удаляются после прочтения. Они остаются в разделе до истечения retention. Это позволяет нескольким consumer'ам читать одно и то же и перечитывать (replay).

**2. Раздел — единица параллелизма.**

Чем больше разделов, тем больше consumer'ов могут читать параллельно. Внутри одной группы один раздел читает только один consumer.

**3. Репликация — основа отказоустойчивости.**

Каждый раздел хранится на нескольких брокерах. Один — лидер, остальные — follower'ы. Если лидер падает, новый выбирается из ISR.

## 2.3 Кластер: зачем нужно несколько брокеров

В нашем примере мы запустили **один брокер**. Этого достаточно для разработки и обучения. Но в продакшене так делать нельзя.

### Три причины, почему нужен кластер

**1. Отказоустойчивость.**

Один брокер упал — данные недоступны. Если раздел хранится на трёх брокерах, падение одного не останавливает систему.

```
Один брокер:
  Брокер 1 упал → ВСЁ недоступно

Кластер из 3 брокеров:
  Брокер 1 упал → данные доступны на брокерах 2 и 3
```

**2. Масштабирование.**

Один брокер имеет ограничения: диск, CPU, сеть. Чтобы обрабатывать больше данных, нужно больше брокеров.

```
Один брокер: 100 МБ/с
Три брокера: 300 МБ/с (при правильном распределении разделов)
```

**3. Обслуживание без простоя.**

Нужно обновить Kafka или заменить диск. С кластером можно вывести один брокер из строя, обновить его, вернуть, потом взяться за следующий.

```
Один брокер:
  Остановил → система недоступна

Кластер из 3 брокеров:
  Остановил брокер 1 → система работает на 2 и 3
  Обновил → вернул → остановил брокер 2 → ...
```

### Минимальный продакшн-кластер

**3 брокера** — минимальный размер для продакшена. Почему:

- **Replication factor = 3** — каждый раздел хранится на трёх брокерах.
- Падение **одного** брокера не влияет на доступность.
- Можно обслуживать брокеры по одному.

**5 брокеров** — если нужна ещё большая надёжность или нагрузка.

### Что дальше

Детально кластер, репликацию, выборы лидера, ISR, HW, LEO мы разберём в **Главе 4: Топики, партиции и репликация**. Там будет:

## 2.5 Выводы и типичные ошибки

**Что мы узнали?**

Kafka — это кластер брокеров, которые хранят данные в топиках, разделённых на разделы. Producer'ы пишут в топики, consumer'ы читают из них, consumer groups распределяют разделы между потребителями. Каждый раздел имеет лидера и follower'ов (реплики), синхронизированные реплики образуют ISR. Контроллер управляет метаданными, в KRaft mode консенсус встроен в Kafka. Для продакшена нужно минимум 3 брокера и replication factor = 3.

**Типичные ошибки:**

- ❌ **Запускать Kafka на одном брокере в проде.** Один брокер упал — данные потеряны, система недоступна.
- ❌ **Replication factor = 1 в проде.** Нет копий — нет отказоустойчивости.
- ❌ **auto.create.topics.enable = true в проде.** Топики создаются с дефолтными настройками (1 раздел, RF=1). Лучше создавать явно.
- ❌ **Думать, что Kafka — это очередь.** Сообщения не удаляются после чтения. Это лог.
- ❌ **Игнорировать ключ при записи.** Без ключа сообщения распределяются round-robin, порядок для сущности не гарантирован.
- ❌ **Ожидать глобальный порядок.** Kafka гарантирует порядок только внутри раздела.
- ❌ **Забывать про consumer group.** Один consumer без `GroupID` не сможет продолжить с того же offset'а после перезапуска.

## 2.8 Ответы

**1.** Брокер — это узел кластера Kafka, на котором запущен процесс Kafka. Он принимает подключения от клиентов, сохраняет сообщения на диск, отдаёт их consumer'ам, хранит разделы, участвует в репликации.

**2.** Топик — это логическая категория сообщений (аналог таблицы в БД). Он не хранит данные — данные хранятся в разделах, из которых состоит топик. Топик — это просто имя и набор настроек.

**3.** Раздел — это физическая единица хранения внутри топика. Это append-only лог, в который сообщения добавляются только в конец. Раздел — единица параллелизма, потому что consumer'ы распределяются по разделам: один раздел — один consumer в группе.

**4.** Offset — это уникальный номер сообщения внутри раздела. Он монотонно возрастает: 0, 1, 2, ... Consumer запоминает свой offset, чтобы продолжить чтение с того же места после перезапуска.

**5.** Producer — клиент, который пишет сообщения в топик. Он не знает заранее, какой брокер является лидером для нужного раздела. Он подключается к любому брокеру из списка, запрашивает метаданные, получает ответ «лидер — брокер X» и отправляет сообщение напрямую ему.

**6.** Consumer — клиент, который читает сообщения из топика. Он коммитит свой offset в Kafka (в топик `__consumer_offsets`), чтобы при перезапуске продолжить с того же места.

**7.** Consumer group — группа потребителей, которые совместно читают топик. Внутри одной группы один раздел читается только одним consumer'ом. Больше consumer'ов, чем разделов — лишние простаивают.

**8.** Replication factor — сколько копий раздела хранится в кластере. RF ≥ 3 для продакшена, потому что позволяет пережить падение одного брокера без потери доступности.

**9.** ISR (In-Sync Replicas) — набор реплик, синхронизированных с лидером. Новый лидер выбирается только из ISR, чтобы гарантировать, что он имеет все закоммиченные данные.

**10.** Контроллер — брокер, который управляет метаданными кластера: список топиков, разделов, лидеров, конфигураций. KRaft заменяет ZooKeeper, встраивая Raft-консенсус внутрь Kafka. Преимущества: проще операции (одна система), быстрее failover, выше масштабируемость.
