### 11.1 API как контракт: почему стиль API определяет развитие системы

Представь, что у тебя есть сервис, который предоставляет данные о заказах. Клиенты — это мобильное приложение, веб-приложение, партнёрские интеграции. Каждый клиент хочет получать данные по-своему: мобильному нужно минимум полей, веб-приложению нужно больше, партнёрам нужны все поля и фильтры.

Ты проектируешь API. И здесь возникает вопрос: как сделать так, чтобы API удовлетворял всех клиентов, но при этом не превратился в хаос?

Если ты делаешь один endpoint, который возвращает все поля, мобильное приложение будет получать лишние данные и тратить трафик. Если ты делаешь разные endpoints для разных клиентов, ты дублируешь логику и усложняешь поддержку. Если ты делаешь GraphQL, клиенты сами выбирают, какие поля им нужны, но ты добавляешь сложность.

Это и есть выбор стиля API. И он определяет, как система будет развиваться.

**REST** — это стиль, основанный на ресурсах и HTTP-методах. Он простой, понятный, широко поддерживается. Но он может быть неэффективным для сложных запросов (нужно несколько запросов, чтобы получить связанные данные).

**gRPC** — это стиль, основанный на protobuf и HTTP/2. Он быстрый, эффективный, поддерживает streaming. Но он сложнее в настройке и менее дружелюбен для браузеров.

**GraphQL** — это стиль, основанный на схеме и запросах. Клиенты сами выбирают, какие поля им нужны. Но он добавляет сложность (N+1 проблема, кеширование, авторизация).

**WebSocket** — это стиль для real-time коммуникации. Он поддерживает двунаправленную связь. Но он сложнее в масштабировании и не подходит для request-response.

Выбор стиля API — это компромисс между простотой, эффективностью, гибкостью. И он определяет, как клиенты будут взаимодействовать с системой, какие гарантии ты можешь дать, насколько легко будет развивать API.

Клеппман в «Высоконагруженных приложениях» объясняет, что API — это контракт. Он определяет, что клиент может делать и что он ожидает в ответ. И если контракт меняется, клиенты ломаются. Поэтому API должен быть стабильным и версионированным.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как выбор стиля API влияет на архитектуру. Если у тебя простые CRUD-операции, REST. Если у тебя высокопроизводительные межсервисные вызовы, gRPC. Если у тебя гибкие клиентские запросы, GraphQL. Если у тебя real-time, WebSocket.

### 11.2 REST: ресурсы, HTTP-методы, статусы, HATEOAS

REST (Representational State Transfer) — это архитектурный стиль, основанный на ресурсах. Каждый ресурс имеет URI, и клиенты взаимодействуют с ресурсами через HTTP-методы.

Вот основные принципы REST.

**Ресурсы.** Всё, что можно назвать, — это ресурс. Пользователь, заказ, товар — это ресурсы. Каждый ресурс имеет URI: `/users/123`, `/orders/456`, `/products/789`.

**HTTP-методы.** REST использует HTTP-методы для операций над ресурсами. GET — получить ресурс, POST — создать, PUT — обновить полностью, PATCH — обновить частично, DELETE — удалить.

**Статусы.** REST использует HTTP-статусы для ответов. 200 OK — успех, 201 Created — создано, 400 Bad Request — неверный запрос, 404 Not Found — не найдено, 500 Internal Server Error — ошибка сервера.

**Stateless.** Каждый запрос содержит всю информацию, необходимую для его обработки. Сервер не хранит состояние между запросами. Это упрощает масштабирование: любой сервер может обработать любой запрос.

**HATEOAS (Hypermedia as the Engine of Application State).** Ответы содержат ссылки на другие ресурсы и действия. Клиент может навигировать по API, следуя ссылкам. Это делает API самоописываемым.

REST прост и понятен. Он широко поддерживается (браузеры, инструменты, библиотеки). Он хорошо работает для CRUD-операций.

Но у REST есть ограничения.

**Over-fetching и under-fetching.** Клиент получает все поля ресурса, даже если ему нужны только некоторые (over-fetching). Или клиенту нужно несколько запросов, чтобы получить связанные данные (under-fetching).

**Сложные запросы.** REST не очень хорошо подходит для сложных запросов (фильтры, агрегации, joins). Ты можешь добавить query-параметры, но это быстро становится хаосом.

**Версионирование.** REST API нужно версионировать, чтобы не ломать клиентов. Это добавляет сложность.

Клеппман в «Высоконагруженных приложениях» объясняет, что REST — это стиль, который хорошо работает для простых CRUD-операций. Но для сложных запросов он может быть неэффективным. И выбор зависит от того, какие запросы у тебя в системе.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как REST влияет на архитектуру. Если у тебя простые CRUD-операции, REST. Если у тебя сложные запросы, возможно, GraphQL.

### 11.3 gRPC: protobuf, HTTP/2, streaming, codegen

gRPC — это фреймворк для удалённого вызова процедур (RPC), разработанный Google. Он использует protobuf для сериализации данных и HTTP/2 для транспорта.

Вот основные концепции gRPC.

**Protobuf.** Это язык описания интерфейсов (IDL) и формат сериализации. Ты определяешь сервисы и сообщения в `.proto` файлах, и gRPC генерирует код для клиента и сервера на разных языках.

**HTTP/2.** gRPC использует HTTP/2, который поддерживает мультиплексирование (несколько запросов по одному соединению), сжатие заголовков, bidirectional streaming.

**Streaming.** gRPC поддерживает четыре типа вызовов: unary (один запрос — один ответ), server streaming (один запрос — поток ответов), client streaming (поток запросов — один ответ), bidirectional streaming (поток запросов — поток ответов).

**Codegen.** gRPC генерирует код для клиента и сервера, что упрощает разработку и уменьшает количество ошибок.

gRPC быстрый и эффективный. Он использует бинарную сериализацию (protobuf), которая компактнее и быстрее JSON. Он поддерживает streaming, что полезно для real-time и больших данных. Он генерирует код, что упрощает разработку.

Но у gRPC есть ограничения.

**Браузеры.** gRPC не работает напрямую в браузерах (нужен gRPC-web или прокси). Это ограничивает использование gRPC для клиентских приложений.

**Сложность.** gRPC сложнее в настройке и отладке, чем REST. Нужно определять `.proto` файлы, генерировать код, настраивать HTTP/2.

**Читаемость.** Protobuf — бинарный формат, который не читается человеком. Это усложняет отладку.

Клеппман в «Высоконагруженных приложениях» объясняет, что gRPC — это стиль, который хорошо работает для межсервисных вызовов, где важна производительность. Но для клиентских приложений он может быть неудобным. И выбор зависит от того, кто клиенты и какие требования к производительности.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как gRPC влияет на архитектуру. Если у тебя микросервисы с высокими требованиями к производительности, gRPC. Если у тебя клиентские приложения, REST.

### 11.4 GraphQL: schema, resolvers, N+1 проблема

GraphQL — это язык запросов для API, разработанный Facebook. Он позволяет клиентам запрашивать именно те данные, которые им нужны, и ничего лишнего.

Вот основные концепции GraphQL.

**Schema.** Ты определяешь схему, которая описывает типы данных и доступные запросы. Схема — это контракт между клиентом и сервером.

**Resolvers.** Для каждого поля в схеме ты определяешь resolver — функцию, которая возвращает данные для этого поля. Resolvers могут обращаться к базе данных, кешу, другим сервисам.

**Запросы.** Клиент отправляет запрос, который описывает, какие поля ему нужны. Сервер возвращает только эти поля. Это решает проблему over-fetching и under-fetching.

**Мутации.** Клиент может изменять данные через мутации (создать, обновить, удалить).

**Подписки.** Клиент может подписаться на изменения данных через subscriptions.

GraphQL гибкий и эффективный. Клиенты получают именно те данные, которые им нужны. Это уменьшает трафик и упрощает клиентов.

Но у GraphQL есть ограничения.

**N+1 проблема.** Если resolver для каждого элемента списка обращается к базе данных, ты получаешь N+1 запросов. Это может быть медленно. Решение: DataLoader (батчинг и кеширование).

**Кеширование.** GraphQL сложнее кешировать, чем REST, потому что запросы динамические. Нужно использовать persisted queries или другие техники.

**Авторизация.** Авторизация в GraphQL сложнее, потому что клиент может запрашивать любые поля. Нужно проверять права на уровне полей.

**Сложность.** GraphQL сложнее в настройке и отладке, чем REST. Нужно определять схему, resolvers, обрабатывать N+1, кеширование, авторизацию.

Клеппман в «Высоконагруженных приложениях» объясняет, что GraphQL — это стиль, который хорошо работает для клиентов, которым нужна гибкость. Но он добавляет сложность на сервере. И выбор зависит от того, насколько важна гибкость для клиентов.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как GraphQL влияет на архитектуру. Если у тебя много клиентов с разными потребностями, GraphQL. Если у тебя простые CRUD-операции, REST.

### 11.5 WebSocket, SSE, long polling: real-time коммуникация

REST, gRPC, GraphQL — это request-response стили. Клиент отправляет запрос, сервер отвечает. Но что если сервер должен отправить данные клиенту без запроса? Например, уведомления, чат, обновления в реальном времени.

Для этого есть несколько техник.

**Long polling.** Клиент отправляет запрос, сервер держит его открытым, пока не появятся данные. Когда данные появляются, сервер отвечает, и клиент сразу отправляет новый запрос. Это работает, но неэффективно: каждый запрос — это новое соединение, и сервер тратит ресурсы на удержание соединений.

**SSE (Server-Sent Events).** Клиент открывает соединение, сервер отправляет данные в одном направлении (сервер → клиент). Это работает для уведомлений, обновлений, но не для двунаправленной связи.

**WebSocket.** Клиент и сервер открывают двунаправленное соединение. Оба могут отправлять данные в любой момент. Это работает для чата, игр, collaborative editing.

WebSocket эффективнее long polling (одно соединение вместо множества), но сложнее в масштабировании (нужно управлять соединениями, балансировать их, обрабатывать переподключения).

Клеппман в «Высоконагруженных приложениях» объясняет, что real-time коммуникация — это компромисс между эффективностью и сложностью. Long polling проще, но неэффективнее. WebSocket эффективнее, но сложнее. И выбор зависит от того, что важнее для задачи.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как real-time коммуникация влияет на архитектуру. Если у тебя чат, WebSocket. Если у тебя уведомления, SSE или long polling.

### 11.6 Идемпотентность, пагинация, rate limiting

Помимо стиля API, есть несколько аспектов, которые нужно учитывать при проектировании API.

**Идемпотентность.** Идемпотентность — это свойство операции, при котором повторное выполнение даёт тот же результат, что и однократное. GET, PUT, DELETE идемпотентны. POST — нет. Если клиент отправляет POST и не получает ответ (таймаут), он может повторить запрос, и это создаст дубликат. Решение: idempotency keys. Клиент генерирует уникальный ключ для каждого запроса, и сервер дедуплицирует запросы по этому ключу.

**Пагинация.** Когда данных много, нужно возвращать их частями. Есть несколько способов: offset-based (limit/offset), cursor-based (keyset), page-based. Offset-based прост, но может пропускать или дублировать данные при изменениях. Cursor-based стабильнее, но сложнее. Page-based прост, но неэффективен для больших данных.

**Rate limiting.** Ограничение количества запросов от одного клиента. Есть несколько алгоритмов: token bucket, leaky bucket, fixed window, sliding window. Token bucket позволяет bursts, leaky bucket сглаживает, fixed window прост, но имеет проблемы на границах, sliding window точнее, но сложнее.

Клеппман в «Высоконагруженных приложениях» объясняет, что идемпотентность, пагинация, rate limiting — это аспекты API, которые определяют, как клиенты взаимодействуют с системой. Они влияют на надёжность, производительность, безопасность.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как эти аспекты влияют на архитектуру. Если у тебя платежи, идемпотентность обязательна. Если у тебя лента, cursor-based пагинация. Если у тебя публичный API, rate limiting.

### 11.7 Версионирование и документация API

API живёт годами. Клиенты не могут обновиться мгновенно. И когда ты меняешь API, ты должен делать это так, чтобы не ломать клиентов. Для этого есть версионирование.

Есть несколько способов версионирования.

**URL versioning.** Версия в URL: `/v1/users`, `/v2/users`. Это просто и понятно, но URL меняется, и это может быть неудобно.

**Header versioning.** Версия в заголовке: `Accept: application/vnd.api.v2+json`. URL не меняется, но это менее очевидно.

**Query versioning.** Версия в query-параметре: `/users?version=2`. Просто, но не рекомендуется.

**Content negotiation.** Версия в Accept-заголовке с кастомным MIME-типом. Гибко, но сложно.

Выбор способа зависит от задачи. URL versioning самый распространённый, потому что он прост и понятен.

Документация — это второй важный аспект. API должен быть задокументирован, чтобы клиенты знали, как с ним работать. Есть несколько инструментов: OpenAPI (Swagger) для REST, gRPC reflection для gRPC, GraphQL introspection для GraphQL.

Документация должна быть актуальной, полной, с примерами. Она должна генерироваться из кода или из спецификации, чтобы не расходиться с реальностью.

Клеппман в «Высоконагруженных приложениях» объясняет, что версионирование и документация — это аспекты API, которые определяют, насколько легко клиентам работать с системой. Они влияют на развитие API и на удовлетворённость клиентов.

Книга Алекса Сюя «System Design. Подготовка к сложному интервью» показывает, как версионирование и документация влияют на архитектуру. Если у тебя публичный API, версионирование и документация обязательны. Если у тебя внутренний API, можно обойтись без версионирования, но документация всё равно нужна.

## Эталонные ответы

**1. Почему стиль API определяет развитие системы? Какие компромиссы нужно учитывать при выборе?**

API — это контракт между клиентом и сервером. Он определяет, как клиенты взаимодействуют с системой, какие гарантии ты можешь дать, насколько легко будет развивать API. Если контракт меняется, клиенты ломаются. Стиль API определяет компромиссы: REST прост, но неэффективен для сложных запросов; gRPC быстрый, но сложный; GraphQL гибкий, но добавляет N+1 проблему; WebSocket эффективен для real-time, но сложен в масштабировании. Выбор зависит от того, кто клиенты, какие запросы, какие требования к производительности.

**2. Чем REST отличается от gRPC? Когда выбирают каждый?**

REST использует HTTP-методы, JSON, ресурсы. Простой, понятный, широко поддерживается. gRPC использует protobuf, HTTP/2, streaming, codegen. Быстрый, эффективный, поддерживает streaming. REST выбирают для клиентских приложений, простых CRUD-операций, публичных API. gRPC выбирают для межсервисных вызовов, высокопроизводительных систем, streaming. REST проще, но менее эффективен. gRPC эффективнее, но сложнее и менее дружелюбен для браузеров.

**3. Что такое N+1 проблема в GraphQL? Как её решать?**

N+1 проблема — это когда resolver для каждого элемента списка обращается к базе данных, и ты получаешь N+1 запросов (1 запрос для списка + N запросов для каждого элемента). Это может быть медленно. Решение: DataLoader — библиотека, которая батчит и кеширует запросы. DataLoader собирает запросы за один тик, выполняет их одним batch-запросом и распределяет результаты. Это уменьшает количество запросов с N+1 до 1+1.

**4. Чем WebSocket отличается от long polling? Когда выбирают каждый?**

Long polling: клиент отправляет запрос, сервер держит его открытым, пока не появятся данные. Когда данные появляются, сервер отвечает, и клиент сразу отправляет новый запрос. WebSocket: клиент и сервер открывают двунаправленное соединение, оба могут отправлять данные в любой момент. WebSocket эффективнее (одно соединение вместо множества), но сложнее в масштабировании. Long polling проще, но неэффективнее. WebSocket выбирают для чата, игр, collaborative editing. Long polling — для уведомлений, где не нужна двунаправленная связь.

**5. Что такое идемпотентность и почему она важна для API? Как её обеспечить?**

Идемпотентность — свойство операции, при котором повторное выполнение даёт тот же результат, что и однократное. GET, PUT, DELETE идемпотентны. POST — нет. Если клиент отправляет POST и не получает ответ (таймаут), он может повторить запрос, и это создаст дубликат. Идемпотентность важна для надёжности: клиент может безопасно повторять запросы. Обеспечить можно через idempotency keys: клиент генерирует уникальный ключ для каждого запроса, сервер дедуплицирует запросы по этому ключу.
