## 3.0 Пролог: запрос, который положил базу

Ты написал бэкенд для интернет-магазина. Всё работало отлично: 1000 пользователей, таблица `users` на 50 000 строк, запросы летали за миллисекунды.

Потом магазин вырос. Пользователей стало 5 миллионов. И вдруг — беда. Тот же самый запрос, который раньше выполнялся за 2 мс, теперь занимает 15 секунд. База лежит, пользователи жалуются, мониторинг показывает 100% утилизацию диска.

Что произошло?

Ты открываешь `EXPLAIN` и видишь:

```
Seq Scan on users  (cost=0.00..125000.00 rows=1 width=64)
  Filter: (id = 42)
```

**Seq Scan** — последовательное сканирование. PostgreSQL читает **всю** таблицу, страницу за страницей, чтобы найти одну строку с `id = 42`.

Пока таблица была маленькой — это работало. 50 000 строк — это ~3 000 страниц по 8 КБ, читаются за доли секунды. Но 5 миллионов строк — это 62 500 страниц. PostgreSQL читает их **все**, чтобы найти одну.

❓ **Почему так происходит?** Потому что без индекса PostgreSQL **не знает**, на какой странице лежит строка с `id = 42`. У него есть только файл таблицы — последовательность страниц. И чтобы найти нужную, он вынужден читать их все подряд.

💡 **Решение:** создать структуру, которая позволит **по значению `id` быстро найти номер страницы**, где лежит эта строка. Такая структура называется **индекс**.

> **Важный мост к будущим главам:** `Seq Scan` и `Index Scan` — это **способы доступа к данным**, которые выбирает **планировщик**. Когда ты видишь в `EXPLAIN` слово `Seq Scan` — это значит, что планировщик решил читать таблицу целиком. Когда видишь `Index Scan` — решил использовать индекс. **Почему** он принимает такое решение — мы разберём в Главе 7 (Планировщик запросов). Сейчас фокус на том, **как устроен сам индекс**.

## 3.1 Проблема: почему Seq Scan не масштабируется

Прежде чем строить индекс, давай поймём, **насколько плох** Seq Scan на больших таблицах.

### Числа, которые пугают

Допустим, у нас таблица `users` с 5 миллионами строк. Каждая строка — примерно 100 байт. На одной странице (8 КБ) помещается около 80 строк.

```
5 000 000 строк / 80 строк на страницу ≈ 62 500 страниц
62 500 страниц × 8 КБ = 500 МБ данных
```

Чтобы найти одну строку по `id = 42`, Seq Scan должен прочитать **все 62 500 страниц**. Это 500 МБ с диска.

Даже на быстром NVMe-диске (скорость чтения ~2 ГБ/с) это займёт:

```
500 МБ / 2 ГБ/с = 0.25 секунды
```

Кажется, не так уж страшно? Но подожди:

- **Параллельные запросы.** Если таких запросов 100 в секунду (а у интернет-магазина это реально), диск читает 50 ГБ/с — это невозможно. Диск упрётся в пропускную способность.
- **Кэш не помогает.** Если таблица не влезает в `shared_buffers` (а 500 МБ при стандартных 128 МБ `shared_buffers` — не влезает), каждая новая транзакция будет читать страницы с диска заново. Вспомни Главу 1: Buffer Manager загружает страницы в `shared_buffers`, но если кэш мал, старые страницы вытесняются, и каждый новый запрос снова упирается в диск.
- **Рост данных.** Когда пользователей станет 50 миллионов, таблица вырастет до 5 ГБ, и Seq Scan будет занимать 2.5 секунды **на каждый запрос**.

### Сложность Seq Scan: O(N)

Seq Scan имеет **линейную сложность**: время выполнения растёт пропорционально размеру таблицы.

```
10 000 строк    → 1 мс
100 000 строк   → 10 мс
1 000 000 строк → 100 мс
10 000 000 строк → 1 секунда
```

Это не масштабируется. Чтобы обрабатывать 100 запросов в секунду на таблице в 10 миллионов строк, нужен диск, который читает 100 ГБ/с. Таких дисков не существует.

### Что нам нужно

Нам нужна структура, которая отвечает на вопрос: **«На какой странице лежит строка с `id = 42`?»** — за **логарифмическое время O(log N)**, а не за линейное O(N).

Для 5 миллионов строк:

```
O(N)     = 5 000 000 операций  ← Seq Scan
O(log N) = log₂(5 000 000) ≈ 23 операции  ← индекс
```

Разница — в 200 000 раз.

## 3.2 Идея: индекс как оглавление книги

Представь, что таблица `users` — это энциклопедия на 10 000 страниц, где статьи идут в произвольном порядке. Тебе нужно найти статью про «Пингвинов».

**Без оглавления (Seq Scan):** ты открываешь страницу 1, читаешь, не то. Страницу 2, не то. Страницу 3... Через 5 000 страниц ты наконец находишь статью про пингвинов.

**С оглавлением (индекс):** ты открываешь оглавление в конце книги. Находишь букву «П», потом «Пи», потом «Пингвины» — и видишь: «страница 4 321». Открываешь сразу нужную страницу. Время поиска — секунды вместо часов.

**Индекс в PostgreSQL работает так же:**

- Это **отдельная структура данных**, которая хранится в отдельных файлах на диске (вспомни Главу 2: у индекса свой `relfilenode`, свои файлы `_fsm`, `_vm`).
- Она содержит **отсортированные значения** одной или нескольких колонок.
- Для каждого значения хранится **TID** (Tuple ID) — номер страницы и позиция строки на этой странице.
- Когда ты делаешь `WHERE id = 42`, PostgreSQL ищет `42` в индексе, получает TID, и читает **ровно одну страницу** из таблицы.

### Аналогия с телефонным справочником

Телефонный справочник — это отсортированный список фамилий с номерами телефонов. Фамилии отсортированы по алфавиту, поэтому поиск «Смирнов» занимает секунды: открываешь середину, видишь «М», понимаешь, что «С» — дальше, открываешь середину второй половины, видишь «С»... Через несколько шагов находишь нужную фамилию.

Индекс — это тот же телефонный справочник, но для данных таблицы. Значения колонки отсортированы, и для каждого значения указан TID — «адрес» строки в таблице.

## 3.3 B-tree: сбалансированное дерево поиска

Прежде чем разбирать поиск, нужно понять **откуда берётся индекс** и **как он физически устроен**.

### Как создаётся индекс

Индекс может появиться двумя способами:

#### Способ 1: Автоматически, через ограничения

**PRIMARY KEY:**

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,   -- ← здесь неявно создастся индекс
    name TEXT
);
```

PostgreSQL **автоматически** создаёт уникальный индекс для `PRIMARY KEY`. Это нужно для **проверки уникальности**: когда ты вставляешь новую строку, PostgreSQL должен быстро проверить, нет ли уже строки с таким же `id`. Без индекса пришлось бы сканировать всю таблицу при каждой вставке — O(N). С индексом проверка занимает O(log N).

**UNIQUE:**

```sql
CREATE TABLE users (
    id SERIAL,
    email TEXT UNIQUE,       -- ← здесь тоже неявно создастся индекс
    name TEXT
);
```

То же самое происходит при `UNIQUE`-ограничении. Если уникальность по нескольким колонкам (`UNIQUE (a, b)`) — создаётся составной уникальный индекс.

**EXCLUDE:**

```sql
CREATE TABLE reservations (
    room_id INT,
    during TSRANGE,
    EXCLUDE USING GIST (room_id WITH =, during WITH &&)
);
```

`EXCLUDE` — это обобщённая форма уникальности: «нельзя вставить строку, которая конфликтует с существующей по заданному правилу». Для поддержки `EXCLUDE` PostgreSQL создаёт индекс (обычно GiST или GIN).

**ALTER TABLE ... ADD CONSTRAINT:**

```sql
ALTER TABLE users ADD PRIMARY KEY (id);
ALTER TABLE users ADD CONSTRAINT unique_email UNIQUE (email);
ALTER TABLE reservations ADD EXCLUDE USING GIST (...);
```

Если ограничение добавляется позже, индекс создаётся в этот момент.

#### Способ 2: Вручную, через CREATE INDEX

```sql
CREATE INDEX idx_users_name ON users(name);
```

Этот индекс не связан с уникальностью — он просто ускоряет поиск по колонке `name`.

#### Важный нюанс: REFERENCES не создаёт индекс

**Внешний ключ НЕ создаёт индекс автоматически:**

```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id)  -- ← индекса по user_id НЕ будет!
);
```

PostgreSQL создаст индекс для `orders.id` (PRIMARY KEY), но **не создаст** индекс для `orders.user_id`. Это частая проблема: запросы вида `SELECT * FROM orders WHERE user_id = 42` будут делать Seq Scan, если не создать индекс вручную.

**Почему так:** при вставке строки в `orders` PostgreSQL должен проверить, что `user_id` существует в `users`. Для этого нужен индекс **на стороне `users`** (по `users.id`) — а он уже есть благодаря PRIMARY KEY. На стороне `orders` индекс не обязателен: PostgreSQL не проверяет обратное (что никто не ссылается на удаляемую строку) без явного запроса.

### Что происходит при создании индекса

Независимо от того, как индекс создаётся — автоматически (PRIMARY KEY, UNIQUE) или вручную (CREATE INDEX) — **алгоритм одинаковый**.

**Кто выполняет CREATE INDEX:**

`CREATE INDEX` выполняет **твой Backend-процесс** — тот самый, который обрабатывает твоё SQL-подключение. Это **не фоновый процесс** (не Background Writer, не Checkpointer), а **обычный пользовательский процесс**.

Когда ты запускаешь `CREATE INDEX` в `psql`:

1. Твой Backend-процесс проходит обычные этапы: Parse → Plan → Execute.
2. На этапе Execute он выполняет весь алгоритм создания индекса.
3. Всё это время твой `psql`-сеанс «висит» — ждёт завершения.
4. Другие Backend-процессы **не участвуют** в этой работе (если не включён параллелизм).

#### Случай 1: Таблица содержит данные

Когда ты выполняешь `CREATE INDEX` на таблице с данными, **твой Backend-процесс**:

1. **Читает всю таблицу** — каждую страницу, каждый кортеж. Чтение идёт через Buffer Manager: тот же самый механизм, что и при обычном `SELECT` (Глава 1). Если страницы нет в `shared_buffers` — читает с диска.
2. Для каждой строки **извлекает значение индексируемой колонки** (например, `id`) и **TID** (номер страницы + позиция строки).
3. **Сортирует** все пары `(значение, TID)` по значению. Сортировка идёт в памяти (параметр `work_mem`), а при нехватке памяти — с использованием временных файлов на диске.
4. **Упаковывает** отсортированные пары в страницы индекса — это будут **листовые страницы** (level = 0). Страницы создаются в `shared_buffers`.
5. Над листовыми страницами **строит дерево** — внутренние страницы и корень.
6. **Сбрасывает** готовые страницы индекса на диск. Ты не получишь `CommandComplete`, пока индекс не будет физически на диске.

```
ШАГ 1: Backend-процесс читает таблицу users
┌─────────────────────────────────────────────────────────┐
│ Страница 0 таблицы:                                     │
│   Слот 1: id=5,  name='Alice'                           │
│   Слот 2: id=42, name='Bob'                             │
│   Слот 3: id=17, name='Charlie'                         │
│ Страница 1 таблицы:                                     │
│   Слот 1: id=100, name='Diana'                          │
│   Слот 2: id=7,  name='Eve'                             │
│   ...                                                   │
└─────────────────────────────────────────────────────────┘

ШАГ 2: Извлекаем пары (id, TID)
  (5,   (0,1))
  (42,  (0,2))
  (17,  (0,3))
  (100, (1,1))
  (7,   (1,2))
  ...

ШАГ 3: Сортируем по id
  (5,   (0,1))
  (7,   (1,2))
  (17,  (0,3))
  (42,  (0,2))
  (100, (1,1))
  ...

ШАГ 4: Упаковываем в листовые страницы индекса
  Листовая страница 200: (5,(0,1)) (7,(1,2)) (17,(0,3)) ...
  Листовая страница 201: (42,(0,2)) (100,(1,1)) ...
  ...

ШАГ 5: Строим дерево над листьями
  Корень: [42 → страница 200, 100 → страница 201, ...]

ШАГ 6: Сбрасываем страницы индекса на диск
```

Это дорогая операция: O(N log N) для сортировки + O(N) для чтения таблицы. Но она выполняется **однократно**.

**Важно про WAL:** все изменения в процессе `CREATE INDEX` логируются в WAL (как и любые другие изменения). Если сервер упадёт во время создания индекса, WAL позволит либо завершить, либо откатить операцию.

#### Случай 2: Таблица пустая

Если таблица пустая, `CREATE INDEX` создаёт **только метаданные** индекса (записи в `pg_class`, `pg_index`). Физический файл индекса пуст — **B-tree ещё не существует**.

Дерево **растёт по мере вставки**:

```
t=0: Индекс создан, таблица пустая
  Файл индекса: 0 байт (нет B-tree)

t=1: INSERT id=42
  Backend-процесс создаёт первую листовую страницу (level=0)
  Она же является КОРНЕМ (root=да, level=0)
  Содержимое: [key=42, TID=(0,1)]

t=2: INSERT id=17
  Вставка в ту же страницу: [key=17] [key=42]

t=3: INSERT id=100
  [key=17] [key=42] [key=100]

... страница заполняется ...

t=400: Страница заполнена (400 ключей)
  Расщепление:
  - Новая листовая страница
  - Половина ключей переносится
  - Создаётся НОВЫЙ КОРЕНЬ (level=1)
  - В нём указатели на оба листа

  Было:  Одна страница (level=0, root=да)
  Стало: Корень (level=1) + два листа (level=0)
```

**Ключевой момент:** дерево **не пересобирается с нуля** при каждой вставке. Оно **растёт вверх** через расщепления. Каждое расщепление затрагивает O(log N) страниц, а не всё дерево.

#### Сравнение стоимости

| Операция | Стоимость | Когда происходит |
|:---|:---|:---|
| `CREATE INDEX` на таблице с данными | O(N log N) | Однократно при создании |
| `CREATE INDEX` на пустой таблице | O(1) | Мгновенно, дерева ещё нет |
| Вставка в незаполненную страницу | O(log N) | Обычная вставка |
| Вставка с расщеплением листа | O(log N) | Когда лист заполнен |
| Вставка с расщеплением до корня | O(log N) | Редко, когда все уровни заполнены |

### Ключевая идея: индекс — это ОТДЕЛЬНЫЕ файлы

Индекс — это **не часть таблицы**. Это отдельные файлы на диске. Индекс хранит **не копии строк**, а только:

- **Значения индексируемой колонки** (например, `id = 42`).
- **TID** — указатель, где эта строка лежит в таблице.

Таблица хранит сами данные (имя, email, все колонки). Индекс хранит только «оглавление»: `id → TID`.

**Важное уточнение про «оглавление»:**

Когда мы говорим «индекс — это оглавление», мы имеем в виду **листья** (level = 0). Именно в листьях хранятся пары `(значение, TID)` — «`id=42` лежит на странице 500, слот 15».

Уровни выше (внутренние страницы и корень) — это **оглавление оглавления**. Они хранят не TID'ы строк таблицы, а **указатели на другие страницы индекса**:

```
ВНУТРЕННЯЯ СТРАНИЦА (level=1):
┌─────────────────────────────────────┐
│ [key=100, child_page=200]           │
│ [key=500, child_page=201]           │
│ [key=1000, child_page=202]          │
└─────────────────────────────────────┘

«Значения ≤ 100 ищи в странице 200 индекса»
«Значения 101–500 ищи в странице 201 индекса»
«Значения 501–1000 ищи в странице 202 индекса»
```

Зачем это нужно: если бы все записи оглавления лежали **только** в листьях, поиск `id = 42` превратился бы в линейный перебор листьев — O(N) чтений. Уровни выше позволяют «перепрыгнуть» сразу к нужному листу за O(log N) шагов.

**Итог:**
- **Листья (level=0)** — оглавление **строк таблицы**: `значение → TID`.
- **Внутренние страницы и корень (level>0)** — оглавление **страниц индекса**: `ключ → дочерняя страница`.

### 💡 Практика: когда создавать индекс

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **PRIMARY KEY** — создаётся автоматически, не трогай.
2. **UNIQUE** — создаётся автоматически.
3. **Внешний ключ (`REFERENCES`)** — индекс по FK-колонке **нужно создавать вручную**, если по ней часто фильтруют или джойнят:
   ```sql
   CREATE INDEX idx_orders_user_id ON orders(user_id);
   ```

**👍 СТОИТ СДЕЛАТЬ:**

4. **Частые `WHERE` по колонке с высокой избирательностью:**
   ```sql
   SELECT * FROM users WHERE email = ?;  -- email почти уникален
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Колонки с низкой избирательностью** (`status` с 3 значениями) — Seq Scan может быть не хуже.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай индекс на каждую колонку «на всякий случай»** — каждый лишний индекс замедляет вставку и занимает место.

## 3.4 Чем страница индекса отличается от страницы таблицы

Теперь ключевой вопрос: **индекс хранит отсортированные пары (значение, TID). Но как они физически лежат на диске?**

Ответ: точно так же, как и данные таблицы — **в страницах по 8 КБ**. Но внутренняя структура страницы **другая**.

### Страница таблицы (Heap Page)

```
┌──────────────────────────────────────────────────────────┐
│                СТРАНИЦА ТАБЛИЦЫ (8 КБ)                    │
│                                                          │
│  Page Header (24 байта)                                  │
│  ┌────────────────────────────────────────────────────┐  │
│  │ lsn | checksum | flags | lower | upper            │  │
│  │ special = 0  (специальной области НЕТ)             │  │
│  │ pagesize | version | prune_xid                    │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  ItemId Array (указатели на кортежи, растут вниз ↓)     │
│  ┌──────┬──────┬──────┬─────────────────────────────┐   │
│  │ [0]  │ [1]  │ [2]  │ ...                         │   │
│  └──────┴──────┴──────┴─────────────────────────────┘   │
│                                                          │
│  Free Space (свободное место)                            │
│                                                          │
│  Heap Tuples (полные строки, растут вверх ↑)             │
│  ┌────────────────────────────────────────────────────┐  │
│  │ Кортеж: t_xmin=100, t_xmax=0                      │  │
│  │ id=42, name='Bob', email='bob@mail.com', ...      │  │
│  │ (ВСЕ колонки + MVCC-заголовок)                    │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**Что хранит:** полные строки таблицы — все колонки + `t_xmin`/`t_xmax` для MVCC.

### Страница индекса (B-tree Page)

```
┌──────────────────────────────────────────────────────────┐
│                СТРАНИЦА ИНДЕКСА (8 КБ)                    │
│                                                          │
│  Page Header (24 байта)                                  │
│  ┌────────────────────────────────────────────────────┐  │
│  │ lsn | checksum | flags | lower | upper            │  │
│  │ special = 16  (указывает на BTree Special)         │  │
│  │ pagesize | version | prune_xid                    │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  BTree Special (16 байт)  ← специальная область          │
│  ┌────────────────────────────────────────────────────┐  │
│  │ btpo_flags = BT_LEAF (это лист)                    │  │
│  │ btpo_prev = 199 (сосед слева)                      │  │
│  │ btpo_next = 201 (сосед справа)                     │  │
│  │ btpo_level = 0 (0 = лист)                          │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  ItemId Array (указатели на индекс-кортежи, вниз ↓)     │
│  ┌──────┬──────┬──────┬─────────────────────────────┐   │
│  │ [0]  │ [1]  │ [2]  │ ...                         │   │
│  └──────┴──────┴──────┴─────────────────────────────┘   │
│                                                          │
│  Free Space (свободное место)                            │
│                                                          │
│  Index Tuples (ключи + TID'ы, растут вверх ↑)           │
│  ┌────────────────────────────────────────────────────┐  │
│  │ [key=10, TID=(500,3)]                             │  │
│  │ [key=42, TID=(500,15)]  ← только ключ и TID       │  │
│  │ [key=50, TID=(500,7)]                             │  │
│  │ (БЕЗ t_xmin, БЕЗ t_xmax, БЕЗ остальных колонок)   │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**Что хранит:** только ключ (значение индексируемой колонки) + TID (указатель на строку в таблице). Никаких `t_xmin`/`t_xmax`, никаких остальных колонок.

### Три принципиальных отличия

**Отличие 1: `special` область**

Вспомни Главу 2: в Page Header есть поле `special` (2 байта). Оно хранит **смещение** до специальной области страницы.

**В странице таблицы** `special = 0` — специальной области нет. Это поле зарезервировано, но не используется.

**В странице индекса** `special = 16` — специальная область существует. Это **BTree Special**: 16 байт в начале страницы (сразу после Page Header), где хранится метаинформация для навигации по дереву.

| Поле | Размер | Назначение |
|:---|:---|:---|
| `btpo_flags` | 2 байта | Флаги: это корень? это лист? |
| `btpo_prev` | 4 байта | Номер страницы-соседа **слева** |
| `btpo_next` | 4 байта | Номер страницы-соседа **справа** |
| `btpo_level` | 1 байт | Уровень: **0 = лист**, 1 = родитель листьев, 2 = дед... |
| `btpo_cycle` | 1 байт | Для обнаружения циклов (VACUUM) |

**Отличие 2: Содержимое кортежей**

**Кортеж таблицы (Heap Tuple)** содержит:
- Заголовок с `t_xmin`/`t_xmax` (для MVCC)
- **Все колонки строки** (имя, email, bio, все поля)

**Индексный кортеж (Index Tuple)** содержит **только**:
- Значение ключа (например, `id = 42`)
- TID (6 байт — номер страницы + позиция строки)

В индексе **НЕТ** `t_xmin`/`t_xmax` — индекс не хранит информацию о видимости. Это важно: если строка обновилась, в индексе может остаться старый TID, указывающий на старую версию. PostgreSQL обрабатывает это при чтении (через MVCC, Глава 5).

**Отличие 3: Связи между страницами**

**Страницы таблицы не связаны друг с другом.** Единственный способ найти нужную страницу — вычислить смещение по номеру (Глава 2). Страница 0 не знает, где страница 1. Страница 100 не знает, где страница 101.

**Страницы индекса связаны:**
- **Вертикально**: родитель → дочерняя (через указатели в индексных кортежах).
- **Горизонтально**: сосед слева ↔ сосед справа (через `btpo_prev`/`btpo_next` в BTree Special).

Горизонтальные связи есть **только на уровне листьев** (level = 0). Это и есть тот самый «двусвязный список».

### Таблица-сравнение

| Аспект | Страница таблицы | Страница индекса |
|:---|:---|:---|
| **Page Header** | ✅ 24 байта | ✅ 24 байта |
| **`special`** | = 0 (пусто) | = 16 (BTree Special) |
| **Специальная область** | ❌ Нет | ✅ 16 байт: `btpo_prev`, `btpo_next`, `btpo_level`, `btpo_flags` |
| **ItemId Array** | ✅ Есть | ✅ Есть |
| **Кортежи** | Полные строки: все колонки + `t_xmin`/`t_xmax` | Только ключ + TID |
| **MVCC-заголовок** | ✅ Есть (`t_xmin`, `t_xmax`, `t_ctid`) | ❌ Нет |
| **Связи между страницами** | ❌ Нет (каждая сама по себе) | ✅ Вертикальные (родитель → дочерняя) + горизонтальные (листья) |

### Почему страницы индекса устроены иначе

Все три отличия служат одной цели: **быстрый поиск**.

- **BTree Special** (`btpo_level`, `btpo_prev`, `btpo_next`) позволяет навигировать по дереву: спускаться вниз (через `child_page`) и идти по листьям влево-вправо (через `btpo_prev`/`btpo_next`).
- **Короткие индексные кортежи** (только ключ + TID) позволяют уместить **сотни ключей на одной странице**. Если бы индекс хранил полные строки (как таблица), на странице помещалось бы 10-20 записей вместо 400, и высота дерева была бы в 20-40 раз больше.
- **Отсутствие `t_xmin`/`t_xmax`** экономит место: индекс не хранит информацию о видимости, потому что видимость проверяется в таблице (через Visibility Map или чтение кортежа).

**Ключевой вывод:** страница индекса — это **та же 8-КБ страница**, что и страница таблицы (тот же Page Header, ItemId, Free Space), но с тремя отличиями: `special`-область (16 байт метаданных для навигации), короткие кортежи (только ключ + TID вместо полных строк) и связи между страницами (вертикальные и горизонтальные).

## 3.5 Что такое «листья» и зачем нужен двусвязный список

Теперь чётко определим терминологию.

### Три типа страниц в B-tree

B-tree состоит из страниц **трёх ролей**:

| Роль | level | Что хранит | Связи |
|:---|:---|:---|:---|
| **Корень** | максимальный (например, 2) | Указатели на дочерние страницы | Только вертикальные (вниз) |
| **Внутренние** (internal) | промежуточный (например, 1) | Указатели на дочерние страницы | Вертикальные (вверх и вниз) |
| **Листья** (leaf) | **0** | **Значения + TID'ы строк таблицы** | Вертикальные (вверх) + **горизонтальные** (`btpo_prev`/`btpo_next`) |

**Ключевое различие:**

- **Внутренние страницы** (корень и промежуточные) хранят **указатели на другие страницы индекса**. Они нужны только для навигации.
- **Листовые страницы** хранят **значения индексируемой колонки и TID'ы строк таблицы**. Это конечная цель поиска.

Когда говорят «листья связаны в двусвязный список» — имеются в виду **только страницы с level = 0**. У них есть указатели `btpo_prev` и `btpo_next` на соседние листовые страницы. Внутренние страницы **не имеют** горизонтальных связей.

### Визуализация: три уровня B-tree

```
╔═══════════════════════════════════════════════════════════════════╗
║                    КОРЕНЬ (level = 2)                              ║
║                                                                    ║
║  Хранит: УКАЗАТЕЛИ НА ДРУГИЕ СТРАНИЦЫ ИНДЕКСА                     ║
║  НЕ хранит: TID'ы строк таблицы!                                   ║
║                                                                    ║
║  ┌─────────────────────────────────────────────────────────────┐   ║
║  │ [key=1000, child_page=100]                                  │   ║
║  │ [key=5000, child_page=101]                                  │   ║
║  │ [key=10000, child_page=102]                                 │   ║
║  └─────────────────────────────────────────────────────────────┘   ║
║                                                                    ║
║  «Значения ≤ 1000 ищи в странице 100 индекса»                     ║
║  «Значения 1001–5000 ищи в странице 101 индекса»                  ║
║  «Значения 5001–10000 ищи в странице 102 индекса»                 ║
║                                                                    ║
╚══════════════════════════════════════════╦═════════════════════════╝
                                       │
                                       │ Вертикальные указатели
                                       │ (только вниз)
                                       ▼
╔═══════════════════════════════════════════════════════════════════╗
║                ВНУТРЕННЯЯ СТРАНИЦА (level = 1)                     ║
║                                                                    ║
║  Хранит: УКАЗАТЕЛИ НА ДРУГИЕ СТРАНИЦЫ ИНДЕКСА                     ║
║  НЕ хранит: TID'ы строк таблицы!                                   ║
║                                                                    ║
║  ┌─────────────────────────────────────────────────────────────┐   ║
║  │ [key=100, child_page=200]                                   │   ║
║  │ [key=500, child_page=201]                                   │   ║
║  │ [key=1000, child_page=202]                                  │   ║
║  └─────────────────────────────────────────────────────────────┘   ║
║                                                                    ║
║  «Значения ≤ 100 ищи в странице 200 индекса»                      ║
║  «Значения 101–500 ищи в странице 201 индекса»                    ║
║  «Значения 501–1000 ищи в странице 202 индекса»                   ║
║                                                                    ║
╚══════════════════════════════════════════╦═════════════════════════╝
                                       │
                                       │ Вертикальные указатели
                                       │ (только вниз)
                                       ▼
╔═══════════════════════════════════════════════════════════════════╗
║                ЛИСТОВАЯ СТРАНИЦА (level = 0)                       ║
║                                                                    ║
║  Хранит: ЗНАЧЕНИЯ + TID'ы СТРОК ТАБЛИЦЫ                            ║
║  Это конечная цель поиска!                                         ║
║                                                                    ║
║  ┌─────────────────────────────────────────────────────────────┐   ║
║  │ [key=10,  TID=(500,3)]                                      │   ║
║  │ [key=42,  TID=(500,15)]  ← «id=42 лежит в таблице,          │   ║
║  │ [key=50,  TID=(500,7)]      страница 500, слот 15»          │   ║
║  │ [key=100, TID=(500,20)]                                     │   ║
║  └─────────────────────────────────────────────────────────────┘   ║
║                                                                    ║
║  «Значение 42 лежит на странице 500 таблицы, слот 15»             ║

║  Горизонтальные связи: btpo_prev ↔ btpo_next                      ║
║  (соседние листовые страницы)                                      ║
║                                                                    ║

                                       │ TID ведёт в ТАБЛИЦУ
                                       ▼

                              │ ТАБЛИЦА users    │
                              │ Страница 500     │
                              │ Слот 15: id=42   │
                              │ name='Alice'     │
                              └─────────────────┘
```

### Зачем нужен двусвязный список листьев

Представь запрос:

```sql
SELECT * FROM users WHERE id BETWEEN 42 AND 50;
```

Тебе нужно найти не одно значение, а **диапазон**: 42, 43, 44, ..., 50. Все эти значения лежат в листьях **подряд**, потому что листья отсортированы. Но листьев может быть много, и они находятся на разных страницах.

**Без двусвязного списка:**

1. Ищем 42: спуск от корня → промежуточная → лист. (3 чтения)
2. Читаем 42, 43, 44... на этой листовой странице.
3. Страница закончилась. Чтобы найти следующую, нужно **вернуться к корню**, снова спуститься, найти следующую страницу. (ещё 3 чтения)
4. Повторить для каждого листа.

Это O(log N) на **каждый лист** — медленно.

**С двусвязным списком:**

1. Ищем 42: спуск от корня → промежуточная → лист. (3 чтения)
2. Читаем 42, 43, 44... на этой листовой странице.
3. Страница закончилась. Читаем `btpo_next` → получаем номер следующей листовой страницы. (1 чтение)
4. Читаем следующую страницу. Повторяем, пока не достигнем 50.

Это O(log N) **один раз** + O(1) на каждый следующий лист — быстро.

```
Поиск 42 (первый раз):
  Корень (level=2) → Внутренняя (level=1) → Лист 200 (level=0)
  [3 чтения]

Поиск следующего листа:
  Лист 200 (level=0) → btpo_next → Лист 201 (level=0)
  [1 чтение, БЕЗ возврата к корню!]

Поиск следующего:
  Лист 201 (level=0) → btpo_next → Лист 202 (level=0)
  [1 чтение]
```

### Итог подглавы 3.5

- **Листья (level = 0)** — единственное место, где хранятся TID'ы строк таблицы. Это конечная цель поиска.
- **Внутренние страницы и корень (level > 0)** — хранят только указатели на другие страницы индекса. Они нужны для быстрой навигации к нужному листу.
- **Двусвязный список** — горизонтальные связи (`btpo_prev`/`btpo_next`) между **только листьями**. Он позволяет проходить по диапазону значений (`BETWEEN`, `ORDER BY`) без возврата к корню.

## 3.6 Поиск по B-tree: путь от корня к листу

Теперь, когда мы знаем, как устроены страницы индекса и как они связаны, пройдём **весь путь поиска** строки `id = 42`.

### Как страницы индексов попадают в shared_buffers

Прежде чем разбирать поиск по шагам, закроем важный вопрос: **как страницы индексов попадают в `shared_buffers`?**

**Точно так же, как и страницы таблиц.** Buffer Manager не различает их. Для него «страница индекса №200» и «страница таблицы №500» — это одно и то же: «страница с номером X в файле Y».

Вспомни Главу 1: когда Backend-процессу нужна **страница таблицы**, он вызывает `ReadBuffer(relation, block_number)`. Внутри `ReadBuffer`:

1. Смотрит в `shared_buffers` — есть ли там уже эта страница?
2. Если нет — читает с диска и загружает в `shared_buffers`.
3. Возвращает указатель на буфер.

**Когда Backend-процессу нужна страница индекса, он вызывает ту же самую функцию `ReadBuffer`**, но с другим параметром `relation` (это `relfilenode` индекса, а не таблицы) и другим `block_number` (номер страницы **в файле индекса**).

```
Чтение страницы ТАБЛИЦЫ:
  ReadBuffer(relation = relfilenode_таблицы, block_number = 500)
  → Файл: /base/16384/16385 (файл таблицы)
  → Смещение: 500 × 8192 = 4 096 000 байт
  → Читаем 8 КБ → загружаем в shared_buffers

Чтение страницы ИНДЕКСА:
  ReadBuffer(relation = relfilenode_индекса, block_number = 200)
  → Файл: /base/16384/16386 (файл индекса!)
  → Смещение: 200 × 8192 = 1 638 400 байт
  → Читаем 8 КБ → загружаем в shared_buffers
```

**Оба вызова работают одинаково.** Разница только в том, **из какого файла** читать и **какой номер страницы** использовать.

```
┌─────────────────────────────────────────────────────────────────┐
│                    🗂️ shared_buffers (общий кэш)                 │
│                                                                 │
│  Сюда попадают страницы ИЗ ВСЕХ ФАЙЛОВ:                          │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 📄 Страница таблицы №500 (из файла 16385)                 │  │
│  │    Содержит: кортежи (id=42, name='Alice', ...)           │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 📄 Страница индекса №200 (из файла 16386)                 │  │
│  │    Содержит: ключи + TID'ы (key=42, TID=(500,15), ...)    │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                 │
│  Buffer Manager не различает их:                                 │
│  «страница X в файле Y» — и всё.                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Откуда ReadBuffer знает, с какой страницы начать

Когда ты выполняешь `SELECT * FROM users WHERE id = 42`, Backend-процесс **не знает** номер корневой страницы заранее. Он **узнаёт его из метаданных индекса**, которые хранятся в системном каталоге `pg_class`.

Когда создаётся индекс (подглава 3.3), PostgreSQL записывает в системную таблицу `pg_class` (для индекса) номер **корневой страницы** B-tree. Это поле называется `relpages` — но для индекса `relpages` хранит **номер корневой страницы**, а не общее количество страниц (как для таблицы).

```
СИСТЕМНЫЙ КАТАЛОГ pg_class:

┌──────────┬───────────────┬──────────┬─────────────────┐
│ relname  │ relfilenode   │ relkind  │ relpages        │
├──────────┼───────────────┼──────────┼─────────────────┤
│ users    │ 16385         │ 'r'      │ 62500           │ ← таблица: число страниц
│          │               │          │                 │
│ idx_user │ 16386         │ 'i'      │ 3               │ ← индекс: КОРНЕВАЯ страница!
│ _id      │               │          │                 │
└──────────┴───────────────┴──────────┴─────────────────┘

Для таблицы relpages = общее количество страниц (62 500).
Для индекса relpages = номер корневой страницы B-tree (3).
```

Когда ты выполняешь `SELECT * FROM users WHERE id = 42`:

1. **Планировщик** (Глава 7) решает использовать индекс `idx_users_id`.
2. Планировщик находит OID индекса в `pg_class`.
3. Из `pg_class.relpages` планировщик узнаёт **номер корневой страницы** — например, 3.
4. Планировщик создаёт план: «Читай страницу 3 файла индекса 16386».
5. **Backend-процесс** на этапе Execute вызывает `ReadBuffer(relation = 16386, block_number = 3)`.
6. `ReadBuffer` читает страницу №3 из файла `16386` — это корень B-tree.

**Backend-процесс не «помнит» структуру B-tree.** Он каждый раз узнаёт корневую страницу из `pg_class`. Вся навигация после корня идёт по содержимому страниц: корень указывает на внутренние страницы, внутренние — на листья, листья — на таблицу.

### Шаг за шагом

```
ЗАПРОС: SELECT * FROM users WHERE id = 42

ШАГ 1: Чтение корневой страницы индекса
─────────────────────────────────────────

  Backend-процесс (тот, который выполняет твой SELECT) вызывает
  функцию Buffer Manager (ReadBuffer).

  Buffer Manager — это НЕ отдельный процесс. Это код, который
  выполняется В КОНТЕКСТЕ Backend-процесса.

  ReadBuffer внутри себя:
  1. Смотрит в shared_buffers (общая память):
     «Есть ли там страница индекса №3?»
     → Да: возвращает указатель на неё.
     → Нет: читает с диска (pread), загружает в shared_buffers, возвращает указатель.

  Backend-процесс получил страницу и теперь читает её содержимое:

  ┌────────────────────────────────────────────────────────┐
  │ КОРЕНЬ (level = 2)                                     │
  │                                                        │
  │ [key=1000, child_page=100]                             │
  │ [key=5000, child_page=101]                             │
  │ [key=10000, child_page=102]                            │
  └────────────────────────────────────────────────────────┘

  Проверяем: 42 ≤ 1000? Да.
  Идём в дочернюю страницу 100.

ШАГ 2: Чтение промежуточной страницы
─────────────────────────────────────

  Backend-процесс снова вызывает ReadBuffer:
  «Дай страницу индекса №100»

  ReadBuffer снова проверяет shared_buffers, при необходимости
  читает с диска, возвращает страницу.

  ┌────────────────────────────────────────────────────────┐
  │ ВНУТРЕННЯЯ СТРАНИЦА (level = 1)                        │
  │                                                        │
  │ [key=100, child_page=200]                              │
  │ [key=500, child_page=201]                              │
  │ [key=1000, child_page=202]                             │
  └────────────────────────────────────────────────────────┘

  Проверяем: 42 ≤ 100? Да.
  Идём в дочернюю страницу 200.

ШАГ 3: Чтение листовой страницы
────────────────────────────────

  Backend-процесс вызывает ReadBuffer:
  «Дай страницу индекса №200»

  ┌────────────────────────────────────────────────────────┐
  │ ЛИСТОВАЯ СТРАНИЦА (level = 0)                          │
  │                                                        │
  │ [key=10,  TID=(500,3)]                                 │
  │ [key=42,  TID=(500,15)]  ← нашли!                      │
  │ [key=50,  TID=(500,7)]                                 │
  │ [key=100, TID=(500,20)]                                │
  └────────────────────────────────────────────────────────┘

  Бинарный поиск внутри страницы: находим key=42.
  Получаем TID=(500,15) — «страница 500, слот 15».

ШАГ 4: Чтение страницы таблицы
───────────────────────────────

  Backend-процесс вызывает ReadBuffer:
  «Дай страницу таблицы №500»

  ┌────────────────────────────────────────────────────────┐
  │ СТРАНИЦА ТАБЛИЦЫ (500)                                 │
  │                                                        │
  │ Слот 15: t_xmin=100, t_xmax=0                          │
  │          id=42, name='Alice', ...                      │
  └────────────────────────────────────────────────────────┘

  Идём в слот 15, читаем кортеж — это наша строка.
  Проверяем видимость (MVCC) — строка видна?
  Да → возвращаем её клиенту.
```

### Итого: 4 чтения вместо 62 500

**Индексный поиск:** 3 страницы индекса + 1 страница таблицы = **4 чтения с диска**.

**Seq Scan:** 62 500 страниц таблицы = **62 500 чтений с диска**.

Разница — в **15 000 раз**.

### Важное замечание про Buffer Manager

Все четыре чтения прошли через **один и тот же Buffer Manager**. Для него нет разницы, читает он страницу индекса или страницу таблицы — это просто «страница с номером X в файле Y».

Но нюанс в том, что **страницы индекса и страницы таблицы — это разные файлы**:

- Страница индекса №200 лежит в файле индекса (`relfilenode` индекса = 16386).
- Страница таблицы №500 лежит в файле таблицы (`relfilenode` таблицы = 16385).

Buffer Manager знает оба `relfilenode` и работает с обоими файлами одинаково (Глава 2: `shared_buffers` кэширует **все** страницы).

### Что происходит при поиске диапазона

Запрос `SELECT * FROM users WHERE id BETWEEN 42 AND 50`:

1. Идём по дереву к ключу 42 (3 чтения) — так же, как в точечном поиске.
2. На листовой странице находим 42, 45, 47, 50 (все в отсортированном порядке).
3. Если диапазон выходит за пределы страницы — идём по `btpo_next` к следующему листу (1 чтение).
4. Для каждого TID читаем страницу таблицы.

Благодаря двусвязному списку листьев (подглава 3.5), проход по диапазону — это **последовательное чтение** листовых страниц, а не спуск от корня для каждого значения.

```
Поиск BETWEEN 42 AND 200 (диапазон выходит за пределы одного листа):

1. Спуск к ключу 42:    Корень → Внутренняя → Лист 200   [3 чтения]
2. Читаем 42, 45, ... на листе 200
3. Лист 200 закончился → btpo_next → Лист 201             [1 чтение]
4. Читаем 101, 150, ... на листе 201
5. Для каждого TID → читаем страницу таблицы             [по 1 чтению]
```

### Почему это быстро: итоговая картина

| Операция | Чтений с диска |
|:---|:---|
| **Seq Scan** (поиск `id = 42` в 5 млн строк) | 62 500 |
| **Index Scan** (поиск `id = 42` в 5 млн строк) | **4** |
| **Index Scan** (`BETWEEN 42 AND 50`) | 4 + 1 на каждый доп. лист |

### Ключевые выводы подглавы 3.6

- **Поиск по B-tree — это спуск от корня к листу.** На каждом уровне мы сравниваем искомое значение с ключами и выбираем дочернюю страницу.
- **Все чтения идут через Buffer Manager** — тот же самый, что и при чтении таблицы. Индекс не имеет «отдельного» механизма доступа.
- **Номер корневой страницы** хранится в `pg_class.relpages` для индекса — Backend-процесс узнаёт его оттуда при каждом поиске.
- **Точечный поиск** (`id = 42`) требует фиксированное число чтений: высота дерева + 1 (чтение таблицы).
- **Диапазонный поиск** (`BETWEEN`) использует двусвязный список листьев, чтобы не возвращаться к корню для каждого следующего листа.

## 3.7 Вставка в B-tree: расщепление страниц

В подглаве 3.6 мы разобрали, как **читается** B-tree. Но индекс — это живая структура: при каждой вставке строки в таблицу в индекс добавляется новый ключ. Как это работает, если ключи должны оставаться отсортированными?

### Проблема: куда вставить новый ключ

Представь: у нас есть индекс по `id`, и мы вставляем в таблицу новую строку с `id = 43`. Индекс должен пополниться новой парой `(43, TID)`.

Вопрос: **куда именно** её положить?

Ответ: в **ту листовую страницу**, где должны лежать ключи в диапазоне, включающем 43. Мы спускаемся по дереву от корня к нужному листу (как в подглаве 3.6) и вставляем ключ **в правильную позицию**, чтобы порядок сохранился.

### Вставка в лист с местом

Если на листовой странице **есть свободное место**, всё просто:

```
ЛИСТОВАЯ СТРАНИЦА 200 (level = 0)
ДО ВСТАВКИ 43:

  [10] [42] [50] [100] [150] ... [400]
         ↑
    сюда нужно вставить 43 (между 42 и 50)

ПОСЛЕ ВСТАВКИ 43:

  [10] [42] [43] [50] [100] [150] ... [400]
              ↑
      элементы справа сдвинулись на 1 позицию
```

Что произошло:

1. Бинарным поиском нашли позицию для `43` — между `42` и `50`.
2. Сдвинули ключи справа от позиции на одну ячейку вправо.
3. Записали `43` в освободившееся место.
4. Обновили ItemId-массив (указатели на кортежи).

**Это не «пересортировка».** Массив уже был отсортирован. Мы просто вставили новый элемент в правильную позицию. Сложность — O(K), где K — число ключей на странице (обычно сотни). Это микросекунды.

### Что происходит, когда лист заполнен

Но что, если на листовой странице **нет свободного места**? Например, страница уже заполнена 400 ключами (максимум для 8-КБ страницы с целочисленными ключами).

Если мы вставим 401-й ключ, он не влезет. Нужно **расщепление** (split).

### Расщепление листовой страницы: шаг за шагом

```
ДО РАСЩЕПЛЕНИЯ:

  Листовая страница 200 (level = 0, заполнена на 100%)
  ┌───────────────────────────────────────────┐
  │ [1][2][3]...[200][201]...[399][400]       │
  └───────────────────────────────────────────┘
  (400 ключей, места нет)

  Вставляем 401. Места нет. Происходит расщепление.

ШАГ 1: Выделяем НОВУЮ листовую страницу
  Листовая страница 300 (level = 0, пустая)
  ┌───────────────────────────────────────────┐
  │ (пусто)                                   │
  └───────────────────────────────────────────┘

ШАГ 2: Переносим ПОЛОВИНУ ключей на новую страницу
  Листовая 200: [1][2][3]...[200]   (первые 50%)
  Листовая 300: [201][202]...[400]  (вторые 50%)

ШАГ 3: Обновляем горизонтальные связи (btpo_prev/btpo_next)
  Было:  ... ↔ [200] ↔ [201] ↔ ...
  Стало: ... ↔ [200] ↔ [300] ↔ [201] ↔ ...

  Теперь лист 200 указывает на лист 300,
  а лист 300 указывает на следующий (бывший сосед 201).

ШАГ 4: Добавляем указатель в РОДИТЕЛЬСКУЮ страницу
  Внутренняя страница 100 (level = 1) получает новый ключ:

  ДО:
    [key=1, child=200]  [key=?, child=201]  ...

  ПОСЛЕ:
    [key=1, child=200]  [key=201, child=300]  [key=?, child=201]  ...
                             ↑
              минимальный ключ в новой странице 300 — это 201
```

### Важное уточнение: что означает ключ в родителе

Ключ в родительской странице — это **минимальный ключ в правой дочерней странице**, а не «верхняя граница» левой.

```
ВНУТРЕННЯЯ СТРАНИЦА (родитель):
┌──────────────────────────────────────────────────────┐
│ [key=1, child=200]  [key=201, child=300]  [key=?, child=201] │
│                                                      │
│  «child=200: ключи начиная с 1»                      │
│  «child=300: ключи начиная с 201»                    │
│  «child=201: ключи начиная с ?»                      │
│                                                      │
│  Где заканчивается child=200?                        │
│  Смотрим на СЛЕДУЮЩИЙ ключ в родителе: 201           │
│  Значит child=200 содержит ключи < 201               │
│  То есть: 1, 2, 3, ..., 200                          │
└──────────────────────────────────────────────────────┘
```

### Что происходит, если родительская страница тоже заполнена

Родительская страница (внутренняя) получила новый указатель. Но что, если **в ней самой** нет места?

Тогда она **тоже расщепляется** — по тому же принципу:

1. Создаётся новая внутренняя страница.
2. Половина указателей переносится на неё.
3. В родителя (или корень) добавляется указатель на новую внутреннюю страницу.

### Что происходит, если расщепление доходит до корня

Если корневая страница тоже заполнена и должна расщепиться:

1. Создаётся **новая корневая страница** (level = предыдущий + 1).
2. Старый корень становится обычной внутренней страницей.
3. Дерево **растёт вверх** — становится на один уровень выше.

```
ДО РАСЩЕПЛЕНИЯ КОРНЯ:

  Корень (level=1): [key=1, child=200] [key=401, child=201] ... (заполнен)

ПОСЛЕ РАСЩЕПЛЕНИЯ КОРНЯ:

  НОВЫЙ Корень (level=2): [key=1, child=старый_корень_левая] [key=401, child=старый_корень_правая]
                              │                                    │
                              ▼                                    ▼
  Внутренняя (level=1): [key=1, child=200]...   Внутренняя (level=1): [key=401, child=201]...

  Дерево стало на уровень выше!
```

### Почему расщепление эффективно

**Расщепление — локальная операция.** Она затрагивает максимум O(log N) страниц:

- Одну листовую страницу (делим пополам).
- Родительскую страницу (добавляем указатель).
- Возможно, родителя родителя (если он тоже заполнен).
- В худшем случае — до корня.

Для дерева высотой 3 это **максимум 3 страницы**. Не 2.5 миллиона сдвигов, как было бы в отсортированном массиве.

### Почему листья после расщепления заполнены на ~50%

После расщепления обе новые страницы заполнены примерно **наполовину**. Это **намеренно**:

- Оставшееся место используется для **будущих вставок** без новых расщеплений.
- Если бы страницы были заполнены на 100%, следующая вставка сразу потребовала бы нового расщепления.

**Важно не путать:**

- **50% после расщепления** — это результат деления заполненной страницы пополам. Не зависит от `fillfactor`.
- **fillfactor** — это процент заполнения страниц при **создании** или **пересоздании** индекса (`CREATE INDEX`, `REINDEX`). После расщепления fillfactor ни на что не влияет.

### Что такое fillfactor

**`fillfactor`** — это параметр, который задаёт, **на сколько процентов** PostgreSQL заполняет страницы индекса при их **создании** или **пересоздании** (REINDEX).

```sql
CREATE INDEX idx_users_id ON users(id) WITH (fillfactor = 70);
```

Эта команда означает:

> «При создании индекса заполняй каждую страницу на 70%, оставляя 30% свободного места для будущих вставок».

**Дефолтное значение для B-tree индексов — 90.** Если ты не указываешь `fillfactor` явно, страницы при создании заполняются на 90%, а 10% остаётся пустым. Это касается **всех** B-tree индексов: PRIMARY KEY, UNIQUE, обычных CREATE INDEX.

**Как это работает на физическом уровне:**

Вспомни Главу 2: страница — это 8 КБ. Внутри неё есть **Free Space** — свободное место между ItemId-массивом и кортежами.

```
fillfactor = 90 (дефолт для B-tree индекса, 8 КБ):
┌─────────────────────────────────────────────┐
│ PageHeader │ ItemId │ Index Tuples (90%)    │
│            │        │ [1][2][3]...[327]     │
│            │        │ [СВОБОДНО ~10%]       │
└─────────────────────────────────────────────┘

fillfactor = 70 (явно задан, 8 КБ):
┌─────────────────────────────────────────────┐
│ PageHeader │ ItemId │ Index Tuples (70%)    │
│            │        │ [1][2][3]...[254]     │
│            │        │ [СВОБОДНО ~30%]       │
└─────────────────────────────────────────────┘
```

**Зачем оставлять свободное место:**

Чтобы **не расщеплять страницы при каждой вставке**. Когда в страницу с `fillfactor = 70` вставляется новый ключ, он попадает в уже зарезервированное свободное место. Расщепление потребуется только после того, как это свободное место закончится.

**Важное ограничение:**

`fillfactor` **применяется только при создании или пересоздании** индекса. Он **не влияет** на страницы, которые уже существуют и уже заполнены. Если индекс был создан с `fillfactor = 90`, а потом вставки стали интенсивными, страницы заполнятся до 100% — `fillfactor` не «перераспределит» их. Нужен `REINDEX`.

### Какой fillfactor выбирать на практике

**Реальная практика такова:**

- **Дефолт (90)** — используют почти все и почти всегда. Он даёт 10% запаса на случай вставок в середину, и этого достаточно для большинства сценариев.

- **`fillfactor = 70`** — осознанно ставят для индексов со **случайными вставками** (UUID, email, hash). Случайные вставки вызывают расщепления по всему дереву, и запас 30% существенно снижает их число.

- **`fillfactor = 100`** — экзотика. Ставят крайне редко, только для append-only таблиц, где гарантированно не бывает вставок в середину (например, audit log). Выигрыш в размере индекса минимален (около 10% по сравнению с дефолтом 90), поэтому на практике почти никто не заморачивается.

| Сценарий | Рекомендация | Почему |
|:---|:---|:---|
| Обычные таблицы (смешанные вставки) | **90 (дефолт)** | Достаточно для большинства |
| Случайные вставки (UUID, email) | **70** | Меньше расщеплений при вставках в середину |
| Append-only (audit log, events) | 90 (дефолт) | 100 даёт выигрыш ~10%, но риски при неожиданных вставках |

### 💡 Практика: какой fillfactor выбирать

**✅ ОБЯЗАТЕЛЬНО:**

- **Знай дефолт: 90 для B-tree индексов.** Не 100, не 50. Если не указан явно — работает 90.

**👍 СТОИТ СДЕЛАТЬ:**

- **`fillfactor = 70` для случайных вставок (UUID, email):**
  ```sql
  CREATE INDEX idx_sessions_token ON sessions(token) WITH (fillfactor = 70);
  ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

- **`fillfactor = 100` для автоинкремента.** Выигрыш ~10% места, но риски при неожиданных вставках (ручная вставка с меньшим id, восстановление из бэкапа) перевешивают.

**❌ НЕ ДЕЛАЙ:**

- **Не меняй fillfactor без понимания характера вставок.** Если ошибёшься — получишь либо частые расщепления (fillfactor=100 и вставки в середину), либо раздутый индекс (fillfactor=70 и только последовательные вставки).

### 50% заполнение после расщепления — это не всегда благо

Здесь есть **тонкий нюанс**. Свободное место в странице **полезно только тогда, когда новые ключи могут в него попасть**.

#### Случай 1: Случайные вставки — свободное место используется

Индекс по `email`, `UUID` или любому случайному значению. Новые вставки распределяются **по всем страницам**. Свободные 50% постоянно заполняются.

```
Страница 200 (50%): [alice@...] [charlie@...] [dave@...] ... [СВОБОДНО]
Страница 300 (50%): [bob@...] [eve@...] [frank@...] ... [СВОБОДНО]

Вставка 'aaron@...' → страница 200 (есть место)
Вставка 'george@...' → страница 300 (есть место)
```

#### Случай 2: Последовательные вставки — свободное место «застревает»

Индекс по автоинкрементному `id`. Новые ключи **всегда идут в конец** — в самую правую листовую страницу.

```
Страница 200 (50%): [1..200]  ← диапазон закрыт, новые ключи сюда НЕ попадут
Страница 300 (50%): [201..400] ← и сюда не попадут
...
Последняя страница: [40001..40400] ← только сюда идут новые вставки
```

Промежуточные страницы (200, 300, ...) остаются заполненными на 50% **навсегда**. Их свободное место не используется, потому что:

- Новые ключи (401, 402, 403...) **больше** всех ключей в этих страницах.
- Вставить `201` в страницу 200 **нельзя** — её диапазон ограничен ключом `201` в родителе (все ключи `< 201` должны лежать в странице 200, а `201` уже в странице 300).

### Фрагментация индекса: когда 50% заполнение становится проблемой

Ситуация, когда страницы заполнены частично, но **не могут принять новые ключи**, называется **фрагментацией индекса**.

**Симптомы:**

- Индекс занимает **больше места**, чем должен (много недозаполненных страниц).
- Чтение по индексу требует **больше операций ввода-вывода** (больше страниц нужно прочитать).
- Кэш `shared_buffers` используется **менее эффективно** (кэшируются полупустые страницы).

### Как диагностировать фрагментацию

**Способ 1: pgstatindex (расширение pgstattuple)**

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT * FROM pgstatindex('idx_users_id');
```

Вывод:

```
 version | tree_level | index_size | root_block_no | internal_pages | leaf_pages | empty_pages | deleted_pages | avg_leaf_density | leaf_fragmentation
---------+------------+------------+---------------+----------------+------------+-------------+---------------+------------------+--------------------
       4 |          3 |   120 MB   |             3 |            150 |       7500  |          12 |             0 |            52.3  |               31.2
```

Ключевые поля:

| Поле | Что означает | На что смотреть |
|:---|:---|:---|
| `leaf_fragmentation` | Процент «мёртвых» ключей в листьях | > 30% — пора REINDEX |
| `avg_leaf_density` | Средняя заполненность листовых страниц | < 50% — много пустого места |
| `deleted_pages` | Число полностью пустых страниц | > 0 — после массовых DELETE |

**Способ 2: pg_stat_user_indexes**

```sql
SELECT 
    relname AS index_name,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'idx_users_id';
```

Если `idx_tup_read` (прочитано из индекса) **намного больше** `idx_tup_fetch` (реально получено строк из таблицы) — это признак того, что индекс читает много лишнего (в том числе из-за фрагментации).

**Способ 3: сравнение размера индекса с ожидаемым**

```sql
SELECT 
    pg_size_pretty(pg_relation_size('idx_users_id')) AS actual_size,
    pg_size_pretty(pg_relation_size('users') * 0.2) AS expected_size;
```

Если фактический размер **в разы больше** ожидаемого — это фрагментация.

### Когда делать REINDEX

**REINDEX** — это полное пересоздание индекса:

```sql
REINDEX INDEX idx_users_id;
```

Операция **блокирует** запись в таблицу (или требует `CONCURRENTLY`), поэтому её нельзя выполнять «просто так».

**Признаки, что пора:**

| Симптом | Порог | Что делать |
|:---|:---|:---|
| `leaf_fragmentation` > 30% | Много мёртвых ключей после UPDATE/DELETE | `REINDEX INDEX` |
| `avg_leaf_density` < 50% | Страницы полупустые | `REINDEX` |
| Индекс вырос в 2-3 раза от ожидаемого | Недозаполненные страницы | `REINDEX` |
| `idx_tup_read` в 10+ раз больше `idx_tup_fetch` | Чтение лишних страниц | `REINDEX` + анализ запросов |
| После массового DELETE (например, удаление 50% строк) | Мёртвые ключи не убраны VACUUM'ом | `REINDEX` (или `VACUUM FULL`) |

### Какие сценарии заранее указывают на будущую фрагментацию

**Сценарий 1: Частые UPDATE индексируемой колонки**

```sql
-- Колонка status индексирована
CREATE INDEX idx_orders_status ON orders(status);

-- Часто обновляем статус
UPDATE orders SET status = 'shipped' WHERE id = 42;
```

Каждый UPDATE создаёт **новую версию строки** в таблице и **новый ключ** в индексе. Старый ключ остаётся «мёртвым» до VACUUM. Если VACUUM не успевает — фрагментация растёт.

**Сценарий 2: Последовательные вставки (автоинкремент)**

```sql
CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,
    ...
);
```

Новые ключи всегда идут в конец. После первого расщепления промежуточные страницы навсегда остаются заполненными на 50%. На практике дефолтного `fillfactor = 90` достаточно; `REINDEX` может помочь, если индекс разросся после многих расщеплений.

**Сценарий 3: Случайные вставки (UUID, email)**

```sql
CREATE TABLE sessions (
    token UUID PRIMARY KEY,  -- случайные значения
    ...
);
```

Здесь расщепления происходят **по всему дереву**, и свободные 50% **используются**. Для этого случая `fillfactor = 70` — осознанная практика, снижающая число расщеплений.

**Сценарий 4: Массовые DELETE**

```sql
DELETE FROM audit_log WHERE created_at < now() - interval '1 year';
```

После удаления большого числа строк в индексе остаются мёртвые ключи. VACUUM их уберёт, но страницы останутся полупустыми. `REINDEX` вернёт плотность.

### Как вставка в индекс связана с другими механизмами

Когда Backend-процесс вставляет новую строку в таблицу, для **каждого индекса** таблицы он:

1. **Читает** нужную листовую страницу индекса через Buffer Manager (как в подглаве 3.6).
2. **Изменяет** страницу в `shared_buffers` → она становится «грязной».
3. **Записывает** изменение в WAL-буфер (как для таблицы — Глава 1).
4. Если нужно — выполняет **расщепление** (создаёт новую страницу, обновляет родителя).

Позже:

- Background Writer сбросит «грязные» страницы индекса на диск.
- Checkpointer сбросит все «грязные» страницы во время контрольной точки.
- WAL Writer сбросит WAL-записи в файлы `pg_wal/`.

**Для этих механизмов нет разницы между страницей индекса и страницей таблицы.**

### Итог подглавы 3.7

- **Вставка в лист с местом** — бинарный поиск позиции + сдвиг части ключей. Быстро, в пределах одной страницы.
- **Вставка в заполненный лист** — расщепление: новая страница, половина ключей переносится, родитель получает указатель.
- **Расщепление может дойти до корня** — тогда дерево растёт вверх, создаётся новый корень.
- **Расщепление локально** — затрагивает O(log N) страниц, а не всё дерево.
- **Ключ в родителе** — это минимальный ключ правой дочерней страницы, а не «верхняя граница» левой.
- **50% после расщепления** — результат деления заполненной страницы пополам. Не зависит от `fillfactor`.
- **fillfactor** — параметр заполнения страниц при создании/пересоздании индекса. Дефолт для B-tree — **90**.
- **Практика:** дефолт 90 — почти всегда; 70 — для случайных вставок (UUID, email); 100 — экзотика для append-only.
- **Фрагментация диагностируется** через `pgstattuple`, `pg_stat_user_indexes`, сравнение размеров.
- **REINDEX** — пересоздание индекса; выполняется по симптомам: `leaf_fragmentation > 30%`, `avg_leaf_density < 50%`, рост размера в 2-3 раза.

## 3.8 Составной индекс: порядок колонок решает всё

До сих пор мы рассматривали индекс по **одной** колонке. Но реальные запросы часто фильтруют по нескольким:

```sql
SELECT * FROM orders 
WHERE user_id = 42 
  AND created_at >= '2024-01-01' 
  AND created_at < '2024-02-01';
```

Какой индекс нужен? Варианты:

- Индекс по `user_id` — найдёт все заказы пользователя, но придётся фильтровать по дате вручную.
- Индекс по `created_at` — найдёт заказы за период, но придётся фильтровать по пользователю.
- **Составной индекс** `(user_id, created_at)` — найдёт именно то, что нужно.

### Как устроен составной индекс

В составном индексе ключ — это **комбинация значений нескольких колонок**, отсортированных **лексикографически**: сначала по первой колонке, потом по второй, потом по третьей.

```
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);

Содержимое индекса (отсортировано лексикографически):
  (1, '2024-01-05') → TID
  (1, '2024-01-12') → TID
  (1, '2024-01-20') → TID
  (2, '2024-01-03') → TID
  (2, '2024-01-15') → TID
  (3, '2024-01-01') → TID
  ...
  (42, '2024-01-01') → TID  ← пользователь 42, 1 января
  (42, '2024-01-02') → TID
  ...
  (42, '2024-01-31') → TID  ← пользователь 42, 31 января
  (43, '2024-01-01') → TID
```

**Ключевое свойство:** все записи для пользователя 42 лежат **подряд** в индексе. Внутри них записи отсортированы по дате.

### Структура B-tree для составного индекса

Внутренне составной индекс — это **тот же B-tree**, что и одиночный. Разница только в том, что ключ — это не одно значение, а **кортеж значений**.

```
ЛИСТОВАЯ СТРАНИЦА (level = 0):
┌──────────────────────────────────────────────────────────────┐
│ [(1, '2024-01-05') → TID]                                   │
│ [(1, '2024-01-12') → TID]                                   │
│ [(1, '2024-01-20') → TID]                                   │
│ [(2, '2024-01-03') → TID]                                   │
│ [(2, '2024-01-15') → TID]                                   │
│ ...                                                          │
│ [(42, '2024-01-01') → TID]                                  │
│ [(42, '2024-01-02') → TID]                                  │
│ ...                                                          │
│ [(42, '2024-01-31') → TID]                                  │
│ [(43, '2024-01-01') → TID]                                  │
└──────────────────────────────────────────────────────────────┘
```

Сравнение ключей идёт **по порядку колонок**:

1. Сначала сравниваем `user_id`.
2. Если `user_id` равны — сравниваем `created_at`.
3. Если и `created_at` равны — сравниваем TID (для уникальности).

Это ровно тот же принцип, что сортировка строк в телефонном справочнике: сначала по фамилии, потом по имени.

### Почему порядок колонок критичен

Порядок колонок в составном индексе определяет, **какие запросы он может ускорить**. Разберём на примере индекса `(user_id, created_at)`.

#### Правило крайнего левого префикса

Составной индекс `(a, b, c)` может эффективно обслуживать запросы по:

- `a` (первая колонка)
- `a, b` (первые две)
- `a, b, c` (все три)

Но **не может** эффективно обслуживать:

- `b` (вторая без первой)
- `c` (третья без первой и второй)
- `b, c` (вторая и третья без первой)

**Почему:** ключи в B-tree отсортированы сначала по `a`, потом по `b`, потом по `c`. Если в запросе нет условия по `a`, то значения `b` разбросаны по всему дереву — их нельзя прочитать подряд.

#### Аналогия с телефонным справочником

Справочник отсортирован по **фамилии**, потом по **имени**.

- «Найди всех Смирновых» → ✅ Быстро: все Смирновы лежат подряд.
- «Найди всех Смирновых Александров» → ✅ Быстро: внутри Смирновых ищем Александров.
- «Найди всех Александров» → ❌ Медленно: Александры разбросаны по всему справочнику (под разными фамилиями).
- «Найди всех, у кого имя начинается на А» → ❌ Медленно: имена не отсортированы глобально.

### Разбор сценариев запросов

Теперь пройдём по **всем сценариям** для индекса `(user_id, created_at)` и посмотрим, как PostgreSQL будет его использовать (или не использовать).

#### Сценарий 0: Данные

```
Таблица orders (упрощённо):
  id | user_id | created_at  | status
  ---+---------+-------------+--------
  1  | 42      | 2024-01-05  | active
  2  | 42      | 2024-01-12  | shipped
  3  | 42      | 2024-01-20  | done
  4  | 7       | 2024-01-03  | active
  5  | 7       | 2024-01-15  | shipped
  6  | 100     | 2024-01-01  | active
  ...

Индекс idx_orders_user_date(user_id, created_at):
  (7,  '2024-01-03') → TID(0,4)
  (7,  '2024-01-15') → TID(0,5)
  (42, '2024-01-05') → TID(0,1)
  (42, '2024-01-12') → TID(0,2)
  (42, '2024-01-20') → TID(0,3)
  (100,'2024-01-01') → TID(0,6)
  ...
```

#### Сценарий 1: Поиск по всем колонкам индекса (идеальный случай)

```sql
SELECT * FROM orders 
WHERE user_id = 42 
  AND created_at >= '2024-01-01' 
  AND created_at < '2024-02-01';
```

```
ПЛАН: Index Scan по idx_orders_user_date
```

**Как работает:**

```
ШАГ 1: Спуск по дереву к ключу (42, '2024-01-01')

  Корень (level=2):
    [(7, '2024-01-03') → child=100]  [(100, '2024-01-01') → child=101]
    
  Сравниваем (42, '2024-01-01') с (7, '2024-01-03'):
    user_id: 42 > 7 → идём направо
  Сравниваем с (100, '2024-01-01'):
    user_id: 42 < 100 → идём в child=100

ШАГ 2: Во внутренней странице 100 (level=1)

  [(7, '2024-01-03') → child=200]  [(42, '2024-01-05') → child=201]
  
  42 < 100 → идём в child=201

ШАГ 3: В листовой странице 201 (level=0)

  [(42, '2024-01-05') → TID(0,1)]
  [(42, '2024-01-12') → TID(0,2)]
  [(42, '2024-01-20') → TID(0,3)]
  
  Бинарный поиск: находим (42, '2024-01-05') ≥ '2024-01-01'.
  Идём ПОСЛЕДОВАТЕЛЬНО по ключам, пока user_id = 42 и created_at < '2024-02-01'.

ШАГ 4: Для каждого TID читаем страницу таблицы.

ИТОГ: прочитали 3 страницы индекса + 3 страницы таблицы.
      Нашли ровно то, что нужно, без фильтрации лишнего.
```

**Эффективность:** максимальная. Читаем только нужные записи, в правильном порядке.

#### Сценарий 2: Поиск только по первой колонке (крайний левый префикс)

```sql
SELECT * FROM orders WHERE user_id = 42;
```

```
ПЛАН: Index Scan по idx_orders_user_date
```

**Как работает:**

```
ШАГ 1: Спуск к ключу (42, -∞) — то есть к ПЕРВОМУ ключу с user_id = 42

ШАГ 2: В листе находим первую запись с user_id = 42:
  (42, '2024-01-05') → TID(0,1)

ШАГ 3: Идём последовательно по всем ключам с user_id = 42:
  (42, '2024-01-05') → TID(0,1)
  (42, '2024-01-12') → TID(0,2)
  (42, '2024-01-20') → TID(0,3)
  ... пока user_id не сменится

ШАГ 4: Для каждого TID читаем таблицу.

ИТОГ: работаем только с частью индекса, где лежит user_id = 42.
      Записи лежат ПОДРЯД — эффективно.
```

**Эффективность:** высокая. Индекс используется **полностью**: все записи нужного пользователя лежат подряд.

#### Сценарий 3: Поиск только по второй колонке (НЕ крайний левый префикс)

```sql
SELECT * FROM orders 
WHERE created_at >= '2024-01-01' 
  AND created_at < '2024-02-01';
```

```
ПЛАН: Seq Scan (НЕ Index Scan!)
```

**Как работает:**

```
Индекс idx_orders_user_date отсортирован так:
  (7,  '2024-01-03')
  (7,  '2024-01-15')
  (42, '2024-01-05')
  (42, '2024-01-12')
  (42, '2024-01-20')
  (100,'2024-01-01')
  ...

Значения created_at РАЗБРОСАНЫ по всему индексу:
  '2024-01-03' → у user_id = 7
  '2024-01-05' → у user_id = 42
  '2024-01-15' → у user_id = 7
  '2024-01-20' → у user_id = 42

Чтобы найти все created_at в диапазоне, нужно прочитать ВЕСЬ индекс,
а потом ещё и таблицу. Это ДВОЙНАЯ работа.

Поэтому планировщик выбирает Seq Scan — прочитать таблицу целиком
дешевле, чем читать весь индекс + таблицу.
```

**Эффективность:** нулевая. Индекс **не используется**.

**Что делать:** создать **отдельный индекс** по `created_at`:

```sql
CREATE INDEX idx_orders_date ON orders(created_at);
```

#### Сценарий 4: Поиск по первой + третьей колонке (разрыв в префиксе)

```sql
-- Индекс: (a, b, c)
-- Запрос: WHERE a = 1 AND c = 3
```

```sql
-- Конкретно для нашего индекса (user_id, created_at, status):
CREATE INDEX idx_orders_user_date_status ON orders(user_id, created_at, status);

-- Запрос:
SELECT * FROM orders WHERE user_id = 42 AND status = 'active';
```

```
ПЛАН: Index Scan по user_id, затем ФИЛЬТРАЦИЯ по status вручную
```

**Как работает:**

```
ШАГ 1: Спускаемся к ключам с user_id = 42 (как в сценарии 2).

ШАГ 2: Последовательно читаем ВСЕ ключи с user_id = 42:
  (42, '2024-01-05', 'active')
  (42, '2024-01-12', 'shipped')
  (42, '2024-01-20', 'done')
  ...

ШАГ 3: Для каждого ключа ПРОВЕРЯЕМ status = 'active'.
  Подходят только те, где status = 'active'.
  Остальные ОТБРАСЫВАЕМ.

ИТОГ: использовали индекс для user_id (сужение),
      но status отфильтровали вручную.
      Пришлось прочитать ВСЕ заказы пользователя 42,
      даже те, у которых status != 'active'.
```

**Эффективность:** частичная. Индекс сузил поиск до одного пользователя, но не смог отфильтровать по `status` — пришлось читать лишние ключи.

**Что делать:** если такой запрос частый — создать индекс `(user_id, status)`.

#### Сценарий 5: Поиск по средним колонкам без крайнего левого

```sql
-- Индекс: (a, b, c)
-- Запрос: WHERE b = 2 AND c = 3
```

```sql
-- Для нашего индекса (user_id, created_at, status):
SELECT * FROM orders WHERE created_at = '2024-01-12' AND status = 'active';
```

```
ПЛАН: Seq Scan (индекс НЕ используется)
```

**Как работает:**

Индекс отсортирован сначала по `user_id`. Без условия по `user_id` значения `created_at` и `status` **разбросаны** по всему дереву.

```
Индекс:
  (7,  '2024-01-03', 'active')
  (7,  '2024-01-15', 'shipped')
  (42, '2024-01-05', 'active')
  (42, '2024-01-12', 'shipped')
  ...

Ищем created_at = '2024-01-12':
  Есть в ключе (42, '2024-01-12', 'shipped') — но это единственное место.
  Другие '2024-01-12' могут быть у user_id = 7, 100, 200...
  Они разбросаны по разным страницам.

Чтобы найти их все, нужно прочитать ВЕСЬ индекс.
```

**Эффективность:** нулевая. Индекс **не используется**.

#### Сценарий 6: Поиск по крайней правой колонке

```sql
-- Индекс: (user_id, created_at)
-- Запрос: WHERE created_at = '2024-01-12'
```

То же самое, что сценарий 3. Без условия по `user_id` индекс не используется.

### Сводная таблица сценариев

| Сценарий | Запрос | Использует индекс? | Эффективность |
|:---|:---|:---:|:---|
| Все колонки | `WHERE user_id = 42 AND created_at BETWEEN ...` | ✅ Да | Максимальная |
| Первая колонка | `WHERE user_id = 42` | ✅ Да | Высокая |
| Вторая колонка | `WHERE created_at BETWEEN ...` | ❌ Нет | Seq Scan |
| Первая + третья (с разрывом) | `WHERE user_id = 42 AND status = 'active'` | ⚠️ Частично | Index Scan + фильтр |
| Средние без первой | `WHERE created_at = ... AND status = ...` | ❌ Нет | Seq Scan |
| Крайняя правая | `WHERE status = 'active'` | ❌ Нет | Seq Scan |

### Ключевое правило: крайний левый префикс

**Составной индекс работает только если условие в WHERE начинается с крайней левой колонки индекса.**

- `(a, b)` → `WHERE a = ...` ✅
- `(a, b)` → `WHERE a = ... AND b = ...` ✅
- `(a, b)` → `WHERE b = ...` ❌

### Вставка в составной индекс

Механика вставки **та же**, что и для одиночного индекса (подглава 3.7):

1. Спускаемся по дереву, сравнивая **кортежи ключей**.
2. Вставляем в нужную листовую страницу со сдвигом.
3. Если страница заполнена — расщепление.

**Нюанс:** ключ теперь занимает **больше места** (два значения вместо одного), поэтому на страницу помещается **меньше ключей**.

```
Одиночный индекс (user_id):
  Ключ: 8 байт (bigint) + TID 6 байт = ~22 байта на кортеж
  Ключей на страницу: ~363

Составной индекс (user_id, created_at):
  Ключ: 8 байт (bigint) + 8 байт (timestamp) + TID 6 байт = ~30 байт на кортеж
  Ключей на страницу: ~266
```

Больше размер ключа → меньше ключей на страницу → выше дерево → чуть медленнее поиск.

**Это плата за ускорение составных запросов.** Если составной индекс обслуживает только редкий запрос, а одиночный — частый, может быть выгоднее держать два одиночных индекса вместо одного составного.

### 💡 Практика: когда составной индекс оправдан

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Частый запрос фильтрует по двум и более колонкам одновременно:**
   ```sql
   WHERE user_id = ? AND created_at BETWEEN ? AND ?
   ```
   Без составного индекса PostgreSQL прочитает много лишнего.

2. **Запрос фильтрует по первой колонке и сортирует по второй:**
   ```sql
   WHERE user_id = ? ORDER BY created_at DESC
   ```
   Составной индекс `(user_id, created_at)` отдаст данные **уже отсортированными** — сортировка не нужна.

3. **Уникальность по паре колонок:**
   ```sql
   UNIQUE (user_id, email)
   ```

**👍 СТОИТ СДЕЛАТЬ:**

4. **Частый запрос группирует по двум колонкам:**
   ```sql
   GROUP BY user_id, created_at
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Запрос фильтрует по двум колонкам, но редко выполняется** (раз в день) — выгода от индекса не окупает затраты на вставку.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай составной индекс «на всякий случай»** — если нет конкретного запроса, который он ускорит.

7. **Не дублируй составной индекс одиночным:**
   ```sql
   CREATE INDEX idx_a ON t(a);
   CREATE INDEX idx_ab ON t(a, b);  -- idx_a ЛИШНИЙ, idx_ab уже покрывает WHERE a = ...
   ```
   Составной `(a, b)` уже обслуживает запросы по `WHERE a = ...`. Одиночный `(a)` — лишний, он замедляет вставку.

8. **Не ставь редко используемую колонку первой** — индекс `(rarely_used, frequently_used)` бесполезен для запросов по `frequently_used`.

#### Как понять по метрикам, что нужен составной индекс

**Метрика 1: Частота запроса**

```sql
SELECT 
    query,
    calls,
    mean_exec_time,
    total_exec_time
FROM pg_stat_statements
WHERE query LIKE '%user_id%' 
  AND query LIKE '%created_at%'
ORDER BY total_exec_time DESC
LIMIT 5;
```

Если запрос с фильтром по двум колонкам **выполняется часто** (`calls > 1000/день`) и **занимает много времени** (`mean_exec_time > 10 мс`) — это кандидат на составной индекс.

**Метрика 2: Сколько лишнего читает запрос**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders 
WHERE user_id = 42 
  AND created_at >= '2024-01-01' 
  AND created_at < '2024-02-01';
```

Смотрим на план:

- `Seq Scan` → читает **всю таблицу**. Для 5 млн строк — 62 500 страниц.
- `Index Scan по user_id` → читает **все заказы пользователя**, потом фильтрует по дате вручную.

Если `Buffers: shared hit=... read=...` показывает **сотни или тысячи прочитанных страниц** — значит, запрос читает много лишнего. Составной индекс может сократить это до **десятков страниц**.

**Метрика 3: Проверка после создания**

Создали индекс. Запустили тот же `EXPLAIN (ANALYZE, BUFFERS)`. Сравнили:

| Метрика | До индекса | После составного индекса |
|:---|:---|:---|
| План | Seq Scan или Index Scan по 1 колонке | Index Scan по 2 колонкам |
| Страниц прочитано | 62 500 (Seq Scan) | **~10** |
| Время | 250 мс | **< 1 мс** |

Если чтение страниц **сократилось в десятки-сотни раз** — индекс окупился.
Если сократилось **незначительно** (например, с 100 до 90 страниц) — индекс не дал выгоды, а вставка замедлилась.

#### Закономерности: когда составной индекс даст выгоду

**✅ Даст выгоду, если:**

1. **Фильтр по двум колонкам сужает выборку в разы.**
   Запрос `WHERE user_id = 42 AND created_at BETWEEN ...` читает 100 000 строк без индекса и 50 строк с индексом. Разница — 2000 раз.

2. **Сортировка по второй колонке — частая операция.**
   `WHERE user_id = ? ORDER BY created_at` без индекса сортирует каждый раз (Sort в EXPLAIN). С индексом `(user_id, created_at)` данные уже отсортированы — Sort исчезает.

3. **JOIN по двум колонкам.**
   `JOIN orders o ON o.user_id = u.id AND o.created_at = ...` — составной индекс на `orders(user_id, created_at)` ускорит JOIN.

**❌ Не даст выгоды, если:**

4. **Фильтр по второй колонке не сужает выборку.**
   `WHERE user_id = 42 AND status = 'active'` — если у пользователя 90% заказов active, фильтр по status почти не уменьшает число строк. Индекс по `(user_id, status)` не нужен.

5. **Запрос редкий, а вставка частая.**
   Если запрос выполняется раз в день, а вставка — 1000 раз в секунду, замедление вставки не окупится.

#### Чек-лист перед созданием

- [ ] Есть **конкретный** частый запрос с фильтром по 2+ колонкам?
- [ ] `EXPLAIN` показывает много чтений (Seq Scan или Index Scan с большой фильтрацией)?
- [ ] Фильтр по второй колонке **реально сужает** выборку (проверил через `WHERE` с `COUNT`)?
- [ ] Нет **дублирующего** одиночного индекса, который уже покрывает запрос?
- [ ] Замедление вставки **приемлемо**?

Если все пять пунктов — да, создавай.

### Итог подглавы 3.8

- **Составной индекс** хранит ключ как кортеж `(a, b, c)`, отсортированный лексикографически.
- **Правило крайнего левого префикса:** индекс работает только если WHERE начинается с первой колонки индекса.
- **Идеальный случай** — запрос по всем колонкам индекса: читаем только нужные ключи подряд.
- **Запрос по первой колонке** — тоже эффективен: все записи нужного значения лежат подряд.
- **Запрос без первой колонки** — индекс не используется, Seq Scan.
- **Вставка в составной индекс** — та же механика, что и для одиночного, но ключ больше → меньше ключей на страницу.
- **Практика:** обязательно — частые составные WHERE и сортировка по второй колонке; не делай — «на всякий случай», дублирование одиночным, редкая колонка первой.

## 3.9 Покрывающий индекс: Index Only Scan

До сих пор поиск по индексу состоял из двух шагов:

1. Найти ключ в индексе → получить TID.
2. Прочитать страницу таблицы по TID → получить строку.

Но что, если **все нужные колонки уже есть в индексе**? Тогда шаг 2 можно пропустить.

### Пример

```sql
-- Запрос:
SELECT user_id, created_at FROM orders WHERE user_id = 42;

-- Индекс:
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);
```

Индекс содержит `user_id` и `created_at`. Запрос хочет **только эти две колонки**. Значит, PostgreSQL может:

1. Найти ключ `(42, ...)` в индексе.
2. Прочитать `user_id` и `created_at` **прямо из индекса**.
3. **Не читать таблицу вообще.**

Это называется **Index Only Scan** — сканирование только индекса.

### Препятствие: Visibility Map

Но есть нюанс. Индекс не содержит `t_xmin`/`t_xmax` — полей для проверки видимости (MVCC). Индекс хранит только ключ и TID. Как PostgreSQL узнаёт, что строка видна текущей транзакции, не читая таблицу?

Ответ: через **Visibility Map (VM)** — тот самый файл `_vm`, который мы разбирали в Главе 2.

VM хранит для каждой страницы таблицы флаг **all-visible**: все ли строки на этой странице видны всем транзакциям.

- Если страница помечена как all-visible → все строки на ней гарантированно видны → можно не читать таблицу.
- Если страница НЕ помечена → есть хоть одна строка с неопределённой видимостью → нужно прочитать таблицу и проверить `t_xmin`/`t_xmax`.

```
Index Only Scan:

1. Идём по индексу → находим ключ (42, ...) и TID (500, 15).
2. Проверяем VM: страница 500 all-visible? 
   → Да: читаем user_id и created_at из индекса, ИДЁМ ДАЛЬШЕ.
   → Нет: читаем страницу 500 из таблицы, проверяем видимость.
```

### Почему Index Only Scan не всегда работает

VM обновляется **VACUUM'ом**. Если VACUUM давно не работал (или таблица постоянно обновляется), VM устаревает, и Index Only Scan превращается в обычный Index Scan + чтение таблицы.

Это одна из причин, почему **регулярный VACUUM критически важен** — он поддерживает VM в актуальном состоянии. Мы вернёмся к этому в Главе 6 (VACUUM и Autovacuum).

### Включаем покрывающие колонки через INCLUDE

PostgreSQL 11+ поддерживает явные покрывающие индексы:

```sql
CREATE INDEX idx_orders_user_cover ON orders(user_id) 
  INCLUDE (created_at, status);
```

Отличие от обычного составного индекса:

- Колонки в `INCLUDE` **не участвуют в поиске** (по ним нельзя искать).
- Они **хранятся в листовых страницах** индекса.
- Они **не влияют на сортировку** и не увеличивают размер внутренних страниц.

Для чего это: если запрос фильтрует по `user_id`, но выбирает `created_at` и `status` — покрывающий индекс даст Index Only Scan, не раздувая дерево лишними ключами.

### Сравнение: составной индекс vs INCLUDE

| Аспект | Составной `(user_id, created_at)` | INCLUDE `(user_id) INCLUDE (created_at)` |
|:---|:---|:---|
| Поиск по `user_id` | ✅ | ✅ |
| Поиск по `created_at` | ✅ (если после `user_id`) | ❌ |
| Сортировка по `created_at` | ✅ (внутри `user_id`) | ❌ |
| Index Only Scan для `SELECT user_id, created_at` | ✅ | ✅ |
| Размер внутренних страниц | Больше (ключ включает created_at) | Меньше (ключ только user_id) |
| Проверка уникальности | Может быть UNIQUE | Не может |

**Ключевое различие:** в составном индексе `created_at` — часть ключа, влияет на сортировку и поиск. В `INCLUDE` — просто «приложение» к ключу, только для покрытия запроса.

### Как это работает на физическом уровне

Вспомни подглаву 3.4: индексный кортеж в листе хранит **ключ + TID**.

**Обычный индекс** `(user_id)`:

```
ЛИСТОВАЯ СТРАНИЦА:
[user_id=42, TID=(500,15)]
```

**Составной индекс** `(user_id, created_at)`:

```
ЛИСТОВАЯ СТРАНИЦА:
[user_id=42, created_at='2024-01-05', TID=(500,15)]
```

**Покрывающий индекс** `(user_id) INCLUDE (created_at, status)`:

```
ЛИСТОВАЯ СТРАНИЦА:
[user_id=42, TID=(500,15), created_at='2024-01-05', status='active']
                                        ↑
                          Дополнительные колонки, доступные для чтения
                          без обращения к таблице
```

**Важно:** во **внутренних страницах** (level > 0) `INCLUDE`-колонки **не хранятся**. Они есть **только в листьях**. Это экономит место и ускоряет навигацию по дереву.

```
ВНУТРЕННЯЯ СТРАНИЦА (level=1) — только ключ:
  [user_id=100, child=200] [user_id=500, child=201]

ЛИСТОВАЯ СТРАНИЦА (level=0) — ключ + INCLUDE:
  [user_id=42, TID=(500,15), created_at='...', status='...']
```

### Полная схема Index Only Scan

```
ЗАПРОС: SELECT user_id, created_at FROM orders WHERE user_id = 42;

Индекс: (user_id) INCLUDE (created_at)

ШАГ 1: Спуск по дереву к ключу user_id = 42
  Корень → Внутренняя → Лист
  (3 чтения индекса)

ШАГ 2: В листе находим ключи с user_id = 42
  [user_id=42, TID=(500,15), created_at='2024-01-05']
  [user_id=42, TID=(500,16), created_at='2024-01-12']
  ...

ШАГ 3: Для каждого ключа проверяем VM:
  TID (500,15) → страница 500 → VM: all-visible = да
    → Читаем created_at ПРЯМО ИЗ ИНДЕКСА. Таблицу НЕ читаем!

  TID (500,16) → страница 500 → VM: all-visible = да
    → Тоже из индекса.

ШАГ 4: Возвращаем результат клиенту.

ИТОГО: 3 чтения индекса. Таблица НЕ читалась вообще.
```

**Сравнение с обычным Index Scan:**

| Операция | Index Scan | Index Only Scan |
|:---|:---|:---|
| Чтений индекса | 3 | 3 |
| Чтений таблицы | 3 (по одному на TID) | **0** |
| Итого | 6 чтений | **3 чтения** |

### 💡 Практика: когда покрывающий индекс оправдан

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Частый запрос выбирает 2-3 колонки, а фильтрует по одной:**
   ```sql
   SELECT user_id, created_at, status 
   FROM orders 
   WHERE user_id = ?;
   ```
   Если `WHERE` по `user_id`, а `SELECT` выбирает только `user_id`, `created_at`, `status` — покрывающий индекс `(user_id) INCLUDE (created_at, status)` даст Index Only Scan.

2. **Запрос выбирает колонку, по которой НЕ фильтрует:**
   ```sql
   SELECT email FROM users WHERE id = ?;
   ```
   Индекс `(id) INCLUDE (email)` — поиск по `id`, а `email` читается из индекса.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Частый запрос считает или агрегирует по покрытым колонкам:**
   ```sql
   SELECT COUNT(created_at) FROM orders WHERE user_id = ?;
   ```
   Покрывающий индекс позволит посчитать без чтения таблицы.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Запрос выбирает много колонок** (5+). Покрывающий индекс раздуется и станет сравнимым по размеру с таблицей. Выгода от Index Only Scan будет минимальной.

5. **Запрос редкий.** Затраты на дополнительное место и замедление вставки не окупятся.

**❌ НЕ ДЕЛАЙ:**

6. **Не включай в INCLUDE часто обновляемые колонки.** Каждый UPDATE покрытой колонки будет обновлять и индекс. Это замедлит вставку/обновление.

7. **Не используй INCLUDE для колонок, по которым фильтруешь.** Для фильтрации нужна колонка в **ключе** индекса, а не в INCLUDE.

8. **Не путай INCLUDE с составным индексом.** Если запрос фильтрует по двум колонкам — нужен составной `(a, b)`. Если фильтрует по одной, а выбирает несколько — `INCLUDE`.

#### Как понять по метрикам, что нужен покрывающий индекс

**Метрика 1: План показывает чтение таблицы, хотя все колонки могли бы быть в индексе**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, created_at FROM orders WHERE user_id = 42;
```

Если видишь `Index Scan` (не `Index Only Scan`) и `Buffers` показывает чтение страниц таблицы (`heap`) — значит, таблица читается зря.

**Метрика 2: Соотношение Heap Fetches**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

В выводе для Index Only Scan есть строка:

```
Heap Fetches: 150
```

`Heap Fetches` — это число строк, для которых пришлось читать таблицу (потому что VM не подтвердила видимость).

- `Heap Fetches = 0` → идеально, Index Only Scan работает на 100%.
- `Heap Fetches > 0` → VM устарела, нужен VACUUM.

**Метрика 3: Проверка после создания**

Создали покрывающий индекс. Запустили `EXPLAIN (ANALYZE, BUFFERS)`. Проверили:

| Метрика | До | После |
|:---|:---|:---|
| План | Index Scan | **Index Only Scan** |
| Heap Fetches | 150 (читал таблицу) | **0** (таблицу не читает) |
| Время | 15 мс | **5 мс** |

Если `Heap Fetches` упал до 0 и время уменьшилось — индекс окупился.

#### Закономерности: когда покрывающий индекс даст выгоду

**✅ Даст выгоду, если:**

1. **Запрос выбирает мало колонок (2-3), а фильтрует по одной.**
   Чтение таблицы занимает 80% времени запроса. Покрывающий индекс убирает эти 80%.

2. **Таблица большая и редко обновляется.**
   VM почти всегда актуальна → Index Only Scan работает на 100%.

3. **Частые точечные запросы.**
   `WHERE id = ?` → точечный поиск по индексу + чтение из индекса вместо таблицы.

**❌ Не даст выгоды, если:**

4. **Запрос выбирает много колонок.**
   Покрывающий индекс станет огромным. Выгода от пропуска таблицы нивелируется размером индекса.

5. **Таблица часто обновляется.**
   VM быстро устаревает → Index Only Scan превращается в Index Scan с Heap Fetches.

6. **VACUUM не настроен или не успевает.**
   Без актуальной VM покрывающий индекс бесполезен.

#### Чек-лист перед созданием

- [ ] Есть **конкретный** частый запрос, который выбирает 2-3 колонки?
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` показывает `Heap Fetches > 0` или `Index Scan` вместо `Index Only Scan`?
- [ ] Колонки для INCLUDE **не обновляются часто**?
- [ ] Таблица **не слишком часто** обновляется (VM успевает обновляться)?
- [ ] Замедление вставки **приемлемо**?

Если все пять пунктов — да, создавай.

### Итог подглавы 3.9

- **Index Only Scan** — чтение данных прямо из индекса, без обращения к таблице.
- **Условие** — все нужные колонки есть в индексе **и** VM подтверждает видимость.
- **Visibility Map (VM)** — битовая карта all-visible. Обновляется VACUUM'ом.
- **INCLUDE** — способ добавить колонки в листья индекса без включения их в ключ.
- **Составной индекс vs INCLUDE** — составной для фильтрации по нескольким колонкам, INCLUDE для покрытия запроса.
- **Heap Fetches** — метрика: сколько строк пришлось читать из таблицы. 0 = идеальный Index Only Scan.
- **Практика:** обязательно — частые точечные запросы с выбором 2-3 колонок; не делай — INCLUDE часто обновляемых колонок.

## 3.10 Частичный индекс: индекс для подмножества строк

До сих пор мы рассматривали индексы, которые покрывают **всю таблицу**. Но иногда индексировать нужно не все строки, а только **часть**.

### Проблема

```sql
-- Таблица заказов: 10 миллионов строк.
-- Из них активных (status = 'active') — только 100 000.
-- Остальные — archived (архивные).

-- Запрос, который выполняется часто:
SELECT * FROM orders WHERE user_id = 42 AND status = 'active';
```

Если создать индекс по `user_id` — он будет содержать **все 10 миллионов** заказов, включая архивные. Размер индекса — сотни мегабайт. Обновление — при каждой вставке (даже архивных).

### Решение: WHERE в индексе

```sql
CREATE INDEX idx_active_orders_user 
  ON orders(user_id) 
  WHERE status = 'active';
```

Теперь индекс содержит **только активные заказы** — 100 000 строк вместо 10 миллионов. Он в 100 раз меньше, быстрее в поиске и дешевле в обновлении.

### Как это работает

Частичный индекс — это **обычный B-tree**, который строится не по всем строкам таблицы, а только по тем, которые удовлетворяют условию `WHERE`.

**Полный индекс** `(user_id)`:

```
ВСЕ строки таблицы orders (10 млн):

ЛИСТОВАЯ СТРАНИЦА:
[user_id=7, TID=...]    ← status = 'archived'
[user_id=7, TID=...]    ← status = 'active'
[user_id=42, TID=...]   ← status = 'archived'
[user_id=42, TID=...]   ← status = 'active'
...все 10 млн строк...
```

**Частичный индекс** `(user_id) WHERE status = 'active'`:

```
ТОЛЬКО строки с status = 'active' (100 тыс):

ЛИСТОВАЯ СТРАНИЦА:
[user_id=7, TID=...]    ← status = 'active'
[user_id=42, TID=...]   ← status = 'active'
...только 100 тыс строк...
```

### Что происходит при создании

Вспомни подглаву 3.3: `CREATE INDEX` читает **всю таблицу**, извлекает пары `(значение, TID)`, сортирует, строит B-tree.

**Частичный индекс делает то же самое, но с фильтром:**

```
ШАГ 1: Backend-процесс читает ВСЮ таблицу orders (10 млн строк).

ШАГ 2: Для каждой строки проверяет условие WHERE status = 'active':
  → Да: извлекает пару (user_id, TID)
  → Нет: пропускает

ШАГ 3: Получили 100 000 пар (вместо 10 млн).

ШАГ 4: Сортируем, строим B-tree.
       Дерево получилось в 100 раз меньше.
```

### Когда планировщик использует частичный индекс

Планировщик (Глава 7) использует частичный индекс **только если** условие в запросе **гарантирует**, что нужные строки попадают в этот индекс.

```sql
-- ✅ Использует частичный индекс:
SELECT * FROM orders WHERE user_id = 42 AND status = 'active';
-- Условие status='active' совпадает с WHERE индекса → все нужные строки в индексе.

-- ❌ НЕ использует частичный индекс:
SELECT * FROM orders WHERE user_id = 42;
-- В этом запросе могут быть и archived, и active.
-- Частичный индекс не содержит archived → он неполный.
-- Планировщик не может его использовать.
```

### Физика: как это выглядит в файлах

Частичный индекс — это **отдельные файлы** на диске (свой `relfilenode`), как и любой другой индекс (Глава 2). Отличие только в **содержимом**: в нём меньше строк.

```
Полный индекс по user_id:
  Файл: 16386 (размер: 350 МБ для 10 млн строк)

Частичный индекс (user_id) WHERE status='active':
  Файл: 16387 (размер: 3.5 МБ для 100 тыс строк)
```

При этом:

- Страницы частичного индекса **точно так же** живут в `shared_buffers` (Глава 2).
- Изменения **точно так же** логируются в WAL (Глава 1).
- Background Writer и Checkpointer **точно так же** сбрасывают грязные страницы.

### Вставка и обновление в частичный индекс

**Вставка строки с `status = 'active'`:**

1. Backend-процесс вставляет строку в таблицу.
2. Проверяет условие частичного индекса: `status = 'active'`? Да.
3. Вставляет `(user_id, TID)` в частичный индекс.
4. Обычная вставка в B-tree (подглава 3.7).

**Вставка строки с `status = 'archived'`:**

1. Backend-процесс вставляет строку в таблицу.
2. Проверяет условие: `status = 'active'`? Нет.
3. **Ничего не делает с частичным индексом.**

Это **огромная экономия**: вставка архивных строк (90% всех вставок) не трогает индекс вообще.

**Обновление строки с `status = 'active'` на `status = 'archived'`:**

1. Backend-процесс обновляет строку в таблице.
2. Старое значение `status = 'active'` — ключ был в индексе. Нужно **удалить** его.
3. Новое значение `status = 'archived'` — ключа не будет. Индекс обновляется.

### 💡 Практика: когда частичный индекс оправдан

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Большая таблица, но индексируешь малое подмножество:**
   ```sql
   -- 10 млн заказов, из них 100 тыс активных
   CREATE INDEX idx_active_orders_user 
     ON orders(user_id) 
     WHERE status = 'active';
   ```
   Индекс в 100 раз меньше полного.

2. **Частые запросы только по этому подмножеству:**
   ```sql
   SELECT * FROM orders WHERE user_id = ? AND status = 'active';
   ```

3. **Проверка уникальности только в подмножестве:**
   ```sql
   CREATE UNIQUE INDEX idx_unique_active_email 
     ON users(email) 
     WHERE is_deleted = false;
   ```
   Уникальный email только для активных пользователей.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Индекс на колонку с перекосом значений:**
   ```sql
   -- 99% строк имеют status='done', 1% — 'pending'
   CREATE INDEX idx_pending ON tasks(id) WHERE status = 'pending';
   ```
   Индекс только для «редких» строк.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Подмножество > 50% таблицы.** Выгода от размера индекса невелика, а сложность условий растёт.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай частичный индекс на часто меняющееся условие:**
   ```sql
   -- Плохо: status меняется постоянно, индекс будет дёргаться
   CREATE INDEX idx_orders_user_status ON orders(user_id) WHERE status = 'pending';
   ```
   Каждое обновление `status` заставляет добавлять/удалять ключ из индекса.

7. **Не забывай, что планировщик должен видеть условие:**
   ```sql
   -- Частичный индекс: WHERE status = 'active'
   -- Запрос ДОЛЖЕН содержать status = 'active' в WHERE
   SELECT * FROM orders WHERE user_id = 42 AND status = 'active';  -- ✅
   SELECT * FROM orders WHERE user_id = 42;                        -- ❌ не использует
   ```

#### Как понять по метрикам, что нужен частичный индекс

**Метрика 1: Распределение значений**

```sql
SELECT 
    status,
    COUNT(*),
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS percent
FROM orders
GROUP BY status;
```

Вывод:

```
 status   | count   | percent
----------+---------+--------
 active   |  100000 |   1.00
 archived | 9900000 |  99.00
```

Если подмножество **< 10%** — частичный индекс даст выгоду.

**Метрика 2: Размер полного индекса**

```sql
SELECT pg_size_pretty(pg_relation_size('idx_orders_user')) AS full_index_size;
```

Если полный индекс занимает сотни МБ, а подмножество — 1% → частичный индекс будет в 100 раз меньше.

**Метрика 3: Проверка после создания**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 AND status = 'active';
```

| Метрика | Полный индекс | Частичный индекс |
|:---|:---|:---|
| Размер индекса | 350 МБ | **3.5 МБ** |
| Чтений страниц индекса | 5 | **2** |
| Время | 8 мс | **2 мс** |

#### Закономерности: когда частичный индекс даст выгоду

**✅ Даст выгоду, если:**

1. **Подмножество мало (< 10%).**
   Индекс в 10+ раз меньше → меньше чтений, быстрее поиск, лучше попадает в кэш.

2. **Запросы всегда содержат условие индекса.**
   `WHERE status = 'active'` — если это условие есть во всех запросах, планировщик всегда сможет использовать частичный индекс.

3. **Вставки в подмножество редки.**
   Если 99% вставок — это `archived`, частичный индекс не обновляется для них.

**❌ Не даст выгоды, если:**

4. **Подмножество > 50%.**
   Выгода от размера невелика.

5. **Условие часто меняется.**
   Строки постоянно входят и выходят из подмножества → индекс постоянно обновляется.

6. **Запросы не всегда содержат условие.**
   Планировщик не сможет использовать частичный индекс для запросов без `WHERE status = 'active'`.

#### Чек-лист перед созданием

- [ ] Подмножество **< 10%** таблицы (проверил через COUNT)?
- [ ] Запросы **всегда** содержат условие частичного индекса?
- [ ] Условие **редко меняется** (строки редко входят/выходят из подмножества)?
- [ ] Полный индекс **слишком большой** (сотни МБ)?
- [ ] Замедление вставки **приемлемо**?

Если все пять — да, создавай.

### Итог подглавы 3.10

- **Частичный индекс** — B-tree, построенный только для строк, удовлетворяющих `WHERE`.
- **Создание** — читает всю таблицу, но индексирует только подходящие строки.
- **Использование планировщиком** — только если запрос гарантирует, что нужные строки попадают в индекс (WHERE совпадает).
- **Выгода** — меньше размер (в 10-100 раз), быстрее поиск, дешевле вставка для строк вне подмножества.
- **Практика:** обязательно — малое подмножество с частыми запросами; не делай — часто меняющееся условие, подмножество > 50%.

## 3.11 Функциональный индекс: индекс по выражению

До сих пор мы индексировали **колонки** — значения, которые хранятся в таблице. Но что, если запрос фильтрует не по самой колонке, а по **результату функции** от неё?

### Проблема

```sql
-- Запрос ищет пользователей по email в нижнем регистре:
SELECT * FROM users WHERE lower(email) = 'alice@example.com';

-- Обычный индекс по email НЕ поможет:
CREATE INDEX idx_users_email ON users(email);
-- PostgreSQL не может использовать его для lower(email), 
-- потому что в индексе лежит оригинальное значение email.
```

Почему обычный индекс не работает? Вспомни подглаву 3.6: поиск по B-tree сравнивает **искомое значение** с **ключами в индексе**. Если в индексе лежит `email = 'Alice@Example.com'`, а запрос ищет `lower(email) = 'alice@example.com'`, то сравнение невозможно: `'Alice@Example.com' ≠ 'alice@example.com'`.

PostgreSQL не может «догадаться», что `lower('Alice@Example.com') = 'alice@example.com'`. Ему нужен индекс, где ключи **уже** в нижнем регистре.

### Решение: индекс по выражению

```sql
CREATE INDEX idx_users_lower_email ON users(lower(email));
```

Теперь в индексе лежат **результаты `lower(email)`**:

```
ЛИСТОВАЯ СТРАНИЦА индекса idx_users_lower_email:
['alice@example.com' → TID(0,1)]
['bob@example.com'   → TID(0,2)]
['charlie@example.com' → TID(0,3)]
...
```

Поиск `lower(email) = 'alice@example.com'` теперь работает: сравниваем строку `'alice@example.com'` с ключами в индексе, которые **уже** в нижнем регистре.

### Как это работает при создании

Вспомни подглаву 3.3: `CREATE INDEX` читает всю таблицу, извлекает пары `(значение, TID)`, сортирует, строит B-tree.

**Функциональный индекс делает то же самое, но с вычислением функции:**

```
ШАГ 1: Backend-процесс читает ВСЮ таблицу users.

ШАГ 2: Для каждой строки:
  а) Извлекает значение колонки email
  б) Вычисляет lower(email)
  в) Получает пару (lower(email), TID)

ШАГ 3: Сортирует пары по lower(email).

ШАГ 4: Строит B-tree.

ИТОГ: В индексе лежат НЕ оригинальные email,
      а результаты lower(email).
```

### Ключевое правило: выражение должно совпадать

Функциональный индекс работает **только если** выражение в запросе **точно совпадает** с выражением в индексе.

```sql
-- Индекс:
CREATE INDEX idx ON users(lower(email));

-- ✅ Работает: выражение точно совпадает
SELECT * FROM users WHERE lower(email) = 'alice@example.com';

-- ✅ Работает: регистр в SQL-функции не важен
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';

-- ❌ НЕ работает: другое выражение
SELECT * FROM users WHERE lower(trim(email)) = 'alice@example.com';
-- Индекс по lower(email), а в запросе lower(trim(email)) — не совпадает.

-- ❌ НЕ работает: функция с другой стороны
SELECT * FROM users WHERE email = lower('Alice@Example.com');
-- Здесь lower применяется к константе, а не к колонке.
-- Индекс по lower(email) не используется.
```

### Типичные случаи использования

**1. Поиск без учёта регистра:**

```sql
CREATE INDEX idx_users_lower_email ON users(lower(email));

SELECT * FROM users WHERE lower(email) = 'alice@example.com';
```

**2. Поиск по дате из timestamp:**

```sql
CREATE INDEX idx_orders_date ON orders((created_at::date));

SELECT * FROM orders WHERE created_at::date = '2024-01-15';
```

**3. Поиск по части строки:**

```sql
CREATE INDEX idx_users_phone_prefix ON users(substr(phone, 1, 3));

SELECT * FROM users WHERE substr(phone, 1, 3) = '495';
```

**4. Поиск по JSON-полю:**

```sql
CREATE INDEX idx_users_json_email ON users((data->>'email'));

SELECT * FROM users WHERE data->>'email' = 'alice@example.com';
```

**5. Поиск по году из даты:**

```sql
CREATE INDEX idx_orders_year ON orders(EXTRACT(YEAR FROM created_at));

SELECT * FROM orders WHERE EXTRACT(YEAR FROM created_at) = 2024;
```

### Внутреннее устройство

Функциональный индекс — это **обычный B-tree**. Разница только в том, что **ключ** — это результат выражения, а не значение колонки.

Структура та же:

- Листья (level=0) — ключи + TID'ы.
- Внутренние страницы — указатели для навигации.
- Листья связаны в двусвязный список.

Всё, что мы разбирали в подглавах 3.3–3.7, применимо **без изменений**: поиск, вставка, расщепление, fillfactor, фрагментация.

**Физически** функциональный индекс — это отдельные файлы на диске (свой `relfilenode`), живут в `shared_buffers`, логируются в WAL.

### Особенность: null-значения

Если выражение возвращает `NULL` для некоторых строк, эти строки **не попадают** в индекс (как и в обычном B-tree).

```sql
CREATE INDEX idx_users_lower_email ON users(lower(email));

-- Если у какой-то строки email IS NULL:
-- lower(NULL) = NULL
-- NULL не хранится в B-tree индексе
-- Строка НЕ попадёт в индекс idx_users_lower_email
```

Это **полезно**: если в таблице много строк с `NULL` в индексируемой колонке, функциональный индекс автоматически исключает их.

### 💡 Практика: когда функциональный индекс оправдан

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Частый запрос фильтрует по функции от колонки:**
   ```sql
   WHERE lower(email) = ?
   WHERE created_at::date = ?
   WHERE data->>'field' = ?
   ```
   Без функционального индекса — Seq Scan.

2. **Поиск без учёта регистра по email/имени:**
   ```sql
   CREATE INDEX idx_users_lower_email ON users(lower(email));
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Поиск по части строки (префикс телефона):**
   ```sql
   CREATE INDEX idx_phone_prefix ON users(substr(phone, 1, 3));
   ```

4. **Поиск по извлечённому из JSON полю:**
   ```sql
   CREATE INDEX idx_json_email ON users((data->>'email'));
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Запрос редкий.** Замедление вставки не окупится.

6. **Функция дорогая (например, `regexp_replace`).** Вычисление функции при каждой вставке замедлит запись.

**❌ НЕ ДЕЛАЙ:**

7. **Не создавай индекс на мутирующую функцию** (например, `random()`, `now()`). Ключ будет разным при каждой вставке — индекс бесполезен.

8. **Не дублируй обычный индекс функциональным**, если они оба обслуживают один запрос.

#### Как понять по метрикам, что нужен функциональный индекс

**Метрика 1: План показывает Seq Scan**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE lower(email) = 'alice@example.com';
```

Если видишь `Seq Scan` — обычный индекс по `email` не используется (потому что в нём оригинальные значения, а не `lower(email)`).

**Метрика 2: Частота запроса**

```sql
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
WHERE query LIKE '%lower(email)%'
ORDER BY total_exec_time DESC
LIMIT 5;
```

Частый запрос с функцией = кандидат на функциональный индекс.

**Метрика 3: Проверка после создания**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE lower(email) = 'alice@example.com';
```

| Метрика | До | После |
|:---|:---|:---|
| План | Seq Scan | **Index Scan по idx_users_lower_email** |
| Чтений страниц | 62 500 | **4** |
| Время | 250 мс | **< 1 мс** |

#### Закономерности: когда функциональный индекс даст выгоду

**✅ Даст выгоду, если:**

1. **Запрос фильтрует по функции, и эта функция дешёвая.**
   `lower()`, `substr()`, `::date`, `->>` — быстрые операции.

2. **Функция детерминированная.**
   Для одного и того же значения колонки функция всегда возвращает один результат.

3. **Запрос частый.**
   Чем чаще выполняется, тем быстрее окупается.

**❌ Не даст выгоды, если:**

4. **Функция дорогая.**
   `regexp_replace()` при каждой вставке — замедлит запись.

5. **Функция недетерминированная.**
   `random()`, `now()` — ключ меняется, индекс бесполезен.

6. **Выражение в запросе не совпадает с индексом.**
   Индекс по `lower(email)`, а запрос по `lower(trim(email))` — индекс не используется.

#### Чек-лист перед созданием

- [ ] Есть **конкретный** частый запрос с функцией в WHERE?
- [ ] Функция **детерминированная** и **дешёвая**?
- [ ] Обычный индекс по колонке **не может** обслужить запрос (Seq Scan)?
- [ ] Выражение в запросе **точно совпадает** с выражением в индексе?
- [ ] Замедление вставки **приемлемо**?

Если все пять — да, создавай.

### Итог подглавы 3.11

- **Функциональный индекс** — B-tree по результату выражения, а не по значению колонки.
- **Создание** — читает таблицу, вычисляет выражение для каждой строки, строит B-tree по результатам.
- **Главное правило** — выражение в запросе должно **точно совпадать** с выражением в индексе.
- **NULL-значения** — не попадают в индекс (как и в обычном B-tree).
- **Типичные случаи** — `lower(email)`, `::date`, `substr(phone, 1, 3)`, `data->>'field'`.
- **Практика:** обязательно — частый поиск по `lower(email)` или `::date`; не делай — дорогие и недетерминированные функции.

## 3.12 Практика Go: анализ индексов в базе

В предыдущих подглавах мы разобрали, как устроены индексы, как они создаются, как работают и когда их нужно создавать. Теперь напишем **утилиту на Go**, которая анализирует индексы в реальной базе PostgreSQL и находит:

- **Неиспользуемые индексы** — созданы, но ни разу не применялись. Замедляют вставку, занимают место.
- **Дублирующиеся индексы** — составной `(a, b)` и одиночный `(a)` сосуществуют, хотя второй покрывается первым.
- **Индексы с фрагментацией** — после многих UPDATE/DELETE накопились мёртвые ключи (подглава 3.7).
- **Индексы без Index Only Scan** — запрос мог бы читать только индекс, но VM устарела (подглава 3.9).

### Что будет утилита

Утилита `index-analyzer` подключается к базе, собирает статистику из системных представлений PostgreSQL и выводит отчёт:

```
=== НЕИСПОЛЬЗУЕМЫЕ ИНДЕКСЫ ===
  users.idx_users_phone: 156 MB, ни разу не использован
  orders.idx_orders_legacy: 89 MB, ни разу не использован

=== ДУБЛИРУЮЩИЕСЯ ИНДЕКСЫ ===
  orders: ["idx_orders_user", "idx_orders_user_date"]

=== ИНДЕКСЫ С ФРАГМЕНТАЦИЕЙ ===
  events.idx_events_user: 45 MB, фрагментация 32%

=== ИНДЕКСЫ БЕЗ INDEX ONLY SCAN ===
  orders.idx_orders_user_date: Heap Fetches = 150 (VM устарела)
```

### Полный код

```go
package main

import (
	"database/sql"
	"fmt"
	"log"
	"os"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type IndexInfo struct {
	Schema      string
	Table       string
	Index       string
	SizeBytes   int64
	IdxScan     int64
	IdxTupRead  int64
	IdxTupFetch int64
}

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// 1. Неиспользуемые индексы
	fmt.Println("=== НЕИСПОЛЬЗУЕМЫЕ ИНДЕКСЫ ===")
	unused := findUnusedIndexes(db)
	if len(unused) == 0 {
		fmt.Println("  нет")
	}
	for _, idx := range unused {
		fmt.Printf("  %s.%s: %s, ни разу не использован\n",
			idx.Table, idx.Index, formatSize(idx.SizeBytes))
	}

	// 2. Дублирующиеся индексы
	fmt.Println("\n=== ДУБЛИРУЮЩИЕСЯ ИНДЕКСЫ ===")
	dups := findDuplicateIndexes(db)
	if len(dups) == 0 {
		fmt.Println("  нет")
	}
	for _, d := range dups {
		fmt.Printf("  %s\n", d)
	}

	// 3. Индексы с фрагментацией
	fmt.Println("\n=== ИНДЕКСЫ С ФРАГМЕНТАЦИЕЙ ===")
	frag := findFragmentedIndexes(db)
	if len(frag) == 0 {
		fmt.Println("  нет")
	}
	for _, idx := range frag {
		fmt.Printf("  %s.%s: %s, прочитано в %.1f раз больше, чем получено\n",
			idx.Table, idx.Index, formatSize(idx.SizeBytes),
			float64(idx.IdxTupRead)/float64(idx.IdxTupFetch))
	}

	// 4. Индексы без Index Only Scan
	fmt.Println("\n=== ИНДЕКСЫ С HEAP FETCHES (потенциальный Index Only Scan) ===")
	heapFetches := findIndexesWithHeapFetches(db)
	if len(heapFetches) == 0 {
		fmt.Println("  нет")
	}
	for _, idx := range heapFetches {
		fmt.Printf("  %s.%s: Heap Fetches = %d (нужен VACUUM или INCLUDE)\n",
			idx.Table, idx.Index, idx.IdxTupRead-idx.IdxTupFetch)
	}
}

// findUnusedIndexes находит индексы с idx_scan = 0
func findUnusedIndexes(db *sql.DB) []IndexInfo {
	query := `
	SELECT 
		schemaname,
		relname AS table_name,
		indexrelname AS index_name,
		pg_relation_size(indexrelid) AS size_bytes,
		idx_scan,
		idx_tup_read,
		idx_tup_fetch
	FROM pg_stat_user_indexes
	WHERE idx_scan = 0
	  AND schemaname NOT IN ('pg_catalog', 'pg_toast')
	ORDER BY pg_relation_size(indexrelid) DESC
	LIMIT 10;`

	return queryIndexes(db, query)
}

// findDuplicateIndexes находит индексы, где один покрывает другой
func findDuplicateIndexes(db *sql.DB) []string {
	query := `
	SELECT
		a.tablename,
		ARRAY_AGG(a.indexname ORDER BY a.indexname) AS indexes
	FROM pg_indexes a
	JOIN pg_indexes b 
	  ON a.tablename = b.tablename
	 AND a.indexname <> b.indexname
	 AND (
		-- Индекс (a, b) покрывает индекс (a)
		(a.indexdef LIKE b.indexdef || ',%')
		OR
		(b.indexdef LIKE a.indexdef || ',%')
	 )
	WHERE a.schemaname = 'public'
	GROUP BY a.tablename
	LIMIT 10;`

	rows, err := db.Query(query)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()

	var results []string
	for rows.Next() {
		var table string
		var indexes string
		if err := rows.Scan(&table, &indexes); err != nil {
			log.Fatal(err)
		}
		results = append(results, fmt.Sprintf("%s: [%s]", table, indexes))
	}
	return results
}

// findFragmentedIndexes находит индексы, где idx_tup_read >> idx_tup_fetch
func findFragmentedIndexes(db *sql.DB) []IndexInfo {
	query := `
	SELECT 
		schemaname,
		relname AS table_name,
		indexrelname AS index_name,
		pg_relation_size(indexrelid) AS size_bytes,
		idx_scan,
		idx_tup_read,
		idx_tup_fetch
	FROM pg_stat_user_indexes
	WHERE idx_scan > 0
	  AND idx_tup_fetch > 0
	  AND (idx_tup_read::float / idx_tup_fetch) > 10
	ORDER BY pg_relation_size(indexrelid) DESC
	LIMIT 10;`

	return queryIndexes(db, query)
}

// findIndexesWithHeapFetches находит индексы, где много Heap Fetches
// (признак того, что Index Only Scan не работает из-за устаревшей VM)
func findIndexesWithHeapFetches(db *sql.DB) []IndexInfo {
	query := `
	SELECT 
		schemaname,
		relname AS table_name,
		indexrelname AS index_name,
		pg_relation_size(indexrelid) AS size_bytes,
		idx_scan,
		idx_tup_read,
		idx_tup_fetch
	FROM pg_stat_user_indexes
	WHERE idx_scan > 0
	  AND idx_tup_read > idx_tup_fetch * 2
	ORDER BY (idx_tup_read - idx_tup_fetch) DESC
	LIMIT 10;`

	return queryIndexes(db, query)
}

// queryIndexes — вспомогательная функция для запросов, возвращающих IndexInfo
func queryIndexes(db *sql.DB, query string) []IndexInfo {
	rows, err := db.Query(query)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()

	var indexes []IndexInfo
	for rows.Next() {
		var idx IndexInfo
		if err := rows.Scan(&idx.Schema, &idx.Table, &idx.Index,
			&idx.SizeBytes, &idx.IdxScan, &idx.IdxTupRead, &idx.IdxTupFetch); err != nil {
			log.Fatal(err)
		}
		indexes = append(indexes, idx)
	}
	return indexes
}

// formatSize форматирует размер в человекочитаемый вид
func formatSize(bytes int64) string {
	const unit = 1024
	if bytes < unit {
		return fmt.Sprintf("%d B", bytes)
	}
	div, exp := int64(unit), 0
	for n := bytes / unit; n >= unit; n /= unit {
		div *= unit
		exp++
	}
	return fmt.Sprintf("%.1f %cB", float64(bytes)/float64(div), "KMGTPE"[exp])
}
```

### Как это работает

#### 1. Неиспользуемые индексы

Запрос к `pg_stat_user_indexes` — системному представлению, где PostgreSQL хранит статистику использования индексов:

- `idx_scan` — сколько раз индекс был использован при сканировании.
- Если `idx_scan = 0` — индекс **ни разу не использовался**.

Такой индекс:

- Занимает место на диске.
- Замедляет вставку (каждый INSERT обновляет все индексы таблицы).
- Не даёт никакой выгоды.

**Действие:** `DROP INDEX` — удалить.

#### 2. Дублирующиеся индексы

Сравниваем определения индексов. Если индекс `(a, b)` и индекс `(a)` существуют вместе — второй **полностью покрывается** первым (подглава 3.8: правило крайнего левого префикса).

```sql
-- Дубли:
CREATE INDEX idx_a ON orders(user_id);
CREATE INDEX idx_ab ON orders(user_id, created_at);
-- idx_a ЛИШНИЙ: idx_ab уже обслуживает WHERE user_id = ...
```

**Действие:** `DROP INDEX idx_a` — удалить одиночный, оставить составной.

#### 3. Индексы с фрагментацией

Если `idx_tup_read` (прочитано строк из индекса) сильно превышает `idx_tup_fetch` (реально получено строк из таблицы), значит, индекс читает много **мёртвых ключей** (подглава 3.7).

```
idx_tup_read = 100 000  — прочитали ключей из индекса
idx_tup_fetch = 10 000  — реально получили строк из таблицы
Соотношение: 10x — много мёртвых ключей
```

**Действие:** `REINDEX INDEX` — пересоздать индекс.

#### 4. Индексы с Heap Fetches

`Heap Fetches` — метрика из `EXPLAIN (ANALYZE, BUFFERS)` для Index Only Scan: сколько строк пришлось читать из таблицы, потому что VM не подтвердила видимость (подглава 3.9).

В `pg_stat_user_indexes` это косвенно видно как разница `idx_tup_read - idx_tup_fetch`.

**Действие:** запустить `VACUUM` или настроить Autovacuum.

## 3.13 DDL без блокировок: CONCURRENTLY команды

До сих пор мы говорили о создании индексов как об операции, которая «просто работает». Но на продакшене **любая DDL-операция** — это потенциальный простой.

### Проблема: обычный CREATE INDEX блокирует запись

Вспомни подглаву 3.3: `CREATE INDEX` выполняет твой Backend-процесс — читает всю таблицу, сортирует, строит B-tree.

**Но что происходит с другими транзакциями в это время?**

```
Обычный CREATE INDEX:

  Транзакция A: CREATE INDEX idx_users_name ON users(name);
  → Захватывает блокировку SHARE на таблицу users.
  → Это означает: другим транзакциям РАЗРЕШЕНО читать (SELECT),
    но ЗАПРЕЩЕНО писать (INSERT/UPDATE/DELETE).

  Транзакция B: INSERT INTO users ...;
  → ЖДЁТ, пока CREATE INDEX завершится.

  Таблица users на 10 млн строк:
    CREATE INDEX работает 5 минут.
    Всё это время INSERT'ы ждут.
    Очередь растёт. Пользователи жалуются.
```

**Почему блокировка нужна:** обычный `CREATE INDEX` строит **снапшот данных** и не может увидеть изменения, которые происходят во время его работы. Если разрешить запись, индекс получится **несогласованным** — часть строк будет отсутствовать.

### Решение: CREATE INDEX CONCURRENTLY

```sql
CREATE INDEX CONCURRENTLY idx_users_name ON users(name);
```

**Что делает CONCURRENTLY:**

1. **Не блокирует запись.** INSERT/UPDATE/DELETE продолжают работать параллельно.
2. **Строит индекс в фоне**, в несколько проходов.
3. **В начале** ждёт, пока завершатся все активные транзакции.
4. **В конце** ждёт ещё раз и «догоняет» изменения, которые произошли во время построения.

**Как это работает под капотом:**

```
CREATE INDEX CONCURRENTLY — алгоритм:

ШАГ 1: Backend-процесс создаёт «невалидный» индекс в системном каталоге.
       Индекс физически существует, но помечен как неготовый.

ШАГ 2: Ждёт завершения всех активных транзакций.
       (Технически: ждёт, пока не останется транзакций, которые
        могли видеть таблицу без индекса.)

ШАГ 3: Первый проход — читает таблицу, строит B-tree.
       Параллельно: INSERT/UPDATE/DELETE продолжают работать.

ШАГ 4: Второй проход — «догоняет» изменения, которые произошли
       во время первого прохода (строки, вставленные/обновлённые
       после того, как Backend-процесс прочитал их страницу).

ШАГ 5: Ждёт ещё раз, пока завершатся транзакции, начавшиеся
       во время построения.

ШАГ 6: Помечает индекс как «валидный».
       Планировщик (Глава 7) начинает его использовать.
```

**Важно:** CONCURRENTLY работает **медленнее** обычного CREATE INDEX (в 2-3 раза), потому что делает несколько проходов и ждёт транзакции.

### Ограничения CREATE INDEX CONCURRENTLY

**❌ Нельзя в транзакции:**

```sql
BEGIN;
CREATE INDEX CONCURRENTLY ...;  -- ОШИБКА!
-- ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
COMMIT;
```

**Причина:** CONCURRENTLY сам управляет транзакциями — ждёт завершения других, делает несколько проходов. Внутри явной транзакции это невозможно.

**❌ Если упадёт — останется «невалидный» индекс:**

```
Если сервер упадёт или запрос будет прерван во время CREATE INDEX CONCURRENTLY,
в системном каталоге останется индекс, помеченный как INVALID.

Что делать:

  -- Найти невалидные индексы:
  SELECT relname FROM pg_class
  WHERE relkind = 'i' AND NOT indisvalid;

  -- Удалить невалидный индекс:
  DROP INDEX CONCURRENTLY idx_users_name;

  -- Или пересоздать:
  DROP INDEX CONCURRENTLY idx_users_name;
  CREATE INDEX CONCURRENTLY idx_users_name ON users(name);
```

### REINDEX CONCURRENTLY — пересоздание без блокировки

Вспомни подглаву 3.7: фрагментированный индекс нужно пересоздать через `REINDEX`. Обычный `REINDEX` **блокирует запись** так же, как обычный `CREATE INDEX`.

**Решение:** `REINDEX CONCURRENTLY` (доступно с PostgreSQL 12+):

```sql
-- Обычный REINDEX — блокирует запись:
REINDEX INDEX idx_orders_user_id;
-- Минуты/часы простоя!

-- REINDEX CONCURRENTLY — без блокировки:
REINDEX INDEX CONCURRENTLY idx_orders_user_id;
-- INSERT/UPDATE/DELETE продолжают работать.
```

**Как работает:**

```
ШАГ 1: Создаёт НОВЫЙ индекс (как CREATE INDEX CONCURRENTLY).
ШАГ 2: Строит его параллельно с работой таблицы.
ШАГ 3: Подменяет старый индекс новым.
ШАГ 4: Удаляет старый.
```

**Когда использовать:**

- После массового DELETE (удаление 50% строк) — индекс стал фрагментированным.
- После многих UPDATE индексируемой колонки — накопились мёртвые ключи.
- Когда `pgstattuple` показывает `leaf_fragmentation > 30%` (подглава 3.7).

### DROP INDEX CONCURRENTLY — удаление без блокировки

Обычный `DROP INDEX` блокирует запись на короткое время. Для больших таблиц этого может быть достаточно, чтобы заметить простой.

```sql
-- Обычный DROP INDEX — кратковременная блокировка:
DROP INDEX idx_old;

-- DROP INDEX CONCURRENTLY — без блокировки:
DROP INDEX CONCURRENTLY idx_old;
```

**Когда использовать:**

- Удаление неиспользуемого индекса на проде (подглава 3.12).
- Удаление дублирующего индекса.
- Удаление невалидного индекса после сбоя.

**Ограничение:** `DROP INDEX CONCURRENTLY` **нельзя** использовать для удаления индексов, поддерживающих ограничения (PRIMARY KEY, UNIQUE). Для них нужно `ALTER TABLE ... DROP CONSTRAINT`.

### Бизнес через год: добавили колонку для поиска

**Сценарий:**

```
Сегодня:
  Таблица orders: 50 млн строк.
  Запросы фильтруют по user_id → индекс idx_orders_user_id.

Через год:
  Бизнес добавил страницу «Мои заказы за период».
  Новый запрос:
    SELECT * FROM orders WHERE user_id = ? AND created_at BETWEEN ? AND ?;

  Без нового индекса:
    Index Scan по user_id → читает ВСЕ заказы пользователя (может быть 1000+)
    → потом фильтрует по дате вручную.
    → Медленно.

  Нужен составной индекс (user_id, created_at).

  НО таблица на проде! 50 млн строк!
  Обычный CREATE INDEX заблокирует запись на 20-30 минут.

Решение:
  CREATE INDEX CONCURRENTLY idx_orders_user_date 
    ON orders(user_id, created_at);

  Запись продолжает работать.
  Индекс строится в фоне 40-60 минут (медленнее, но без простоя).
  После завершения планировщик начинает использовать новый индекс.
```

### 💡 Практика: CONCURRENTLY команды

**✅ ОБЯЗАТЕЛЬНО:**

1. **На проде всегда используй CONCURRENTLY для CREATE INDEX:**
   ```sql
   CREATE INDEX CONCURRENTLY idx_users_name ON users(name);
   ```

2. **Для пересоздания — REINDEX CONCURRENTLY:**
   ```sql
   REINDEX INDEX CONCURRENTLY idx_orders_user_id;
   ```

3. **Для удаления неиспользуемых — DROP INDEX CONCURRENTLY:**
   ```sql
   DROP INDEX CONCURRENTLY idx_old;
   ```

**👍 СТОИТ:**

4. **Проверяй невалидные индексы после сбоев:**
   ```sql
   SELECT relname FROM pg_class
   WHERE relkind = 'i' AND NOT indisvalid;
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **CONCURRENTLY на маленьких таблицах** (< 100 тыс строк) — обычный CREATE INDEX займёт секунды, CONCURRENTLY не нужен.

**❌ НЕ ДЕЛАЙ:**

6. **Не запускай CREATE INDEX CONCURRENTLY в транзакции** — он не может работать внутри транзакционного блока.

7. **Не игнорируй невалидные индексы** — они занимают место и не используются, но всё ещё обновляются при вставке.

### Итог подглавы 3.13

- **Обычный CREATE INDEX** блокирует запись (SHARE lock) на всё время построения.
- **CREATE INDEX CONCURRENTLY** строит индекс в фоне, не блокируя запись. Медленнее в 2-3 раза.
- **Ограничения CONCURRENTLY:** нельзя в транзакции, при сбое остаётся невалидный индекс.
- **REINDEX CONCURRENTLY** — пересоздание фрагментированного индекса без блокировки.
- **DROP INDEX CONCURRENTLY** — удаление индекса без блокировки.
- **Невалидные индексы** — находить через `pg_class` и удалять через DROP INDEX CONCURRENTLY.

## 3.14 Выводы и типичные ошибки

**Что мы узнали?**

Индекс — это **отдельная структура данных**, которая хранит отсортированные значения колонок и TID'ы строк. B-tree — тип индекса по умолчанию, сбалансированное дерево, где поиск занимает O(log N) операций.

**Ключевые свойства B-tree:**

- Все листья на одном уровне — путь от корня к листу одинаковый для всех значений.
- Каждая страница содержит сотни ключей — высота дерева редко превышает 3-4 уровня.
- Листья (level=0) связаны в двусвязный список — быстрый проход по диапазону значений.
- Вставка через расщепление страниц — локальная операция, не требует сдвига всего массива.
- Дерево **растёт вверх** при вставках — никогда не пересобирается с нуля.
- Страницы индексов живут в том же `shared_buffers`, что и страницы таблиц, и точно так же логируются в WAL.

**Продвинутые техники:**

- **Составной индекс** — порядок колонок определяет, какие запросы он ускоряет.
- **Покрывающий индекс** — Index Only Scan, когда все нужные колонки есть в индексе.
- **Частичный индекс** — индекс для подмножества строк через `WHERE`.
- **Функциональный индекс** — индекс по результату выражения.
- **CONCURRENTLY команды** — DDL без блокировки записи на проде.

**Каждый индекс имеет цену:** замедляет вставку, занимает место на диске. Создавай индекс под конкретный запрос, а не «на всякий случай».

**Типичные ошибки:**

- ❌ **Индекс на каждую колонку «на всякий случай».** Каждый лишний индекс замедляет вставку и занимает место. Индекс под запрос, а не запрос под индекс.
- ❌ **Неправильный порядок колонок в составном индексе.** Индекс `(created_at, user_id)` не поможет запросу `WHERE user_id = 42` — поиск по второй колонке без первой невозможен.
- ❌ **Забывать про индекс для FK-колонок.** `REFERENCES` не создаёт индекс. Запрос `WHERE user_id = 42` по таблице с внешним ключом без индекса — это Seq Scan. Всегда создавай индекс для колонок, по которым часто фильтруешь или джойнишь, даже если они — внешние ключи.
- ❌ **Не учитывать статистику использования.** Индекс может существовать годами, но ни разу не использоваться. Анализируй `pg_stat_user_indexes` и удаляй неиспользуемые.
- ❌ **Забывать про Index Only Scan.** Если запрос выбирает только индексированные колонки, но всё равно читает таблицу — проверь, актуальна ли Visibility Map (нужен VACUUM).
- ❌ **Игнорировать фрагментацию.** После многих UPDATE в индексе накапливаются мёртвые строки. Индекс нужно периодически пересоздавать (`REINDEX`) или настраивать `fillfactor`.
- ❌ **Использовать обычный CREATE INDEX на проде.** Для больших таблиц это минуты/часы блокировки записи. Всегда используй `CREATE INDEX CONCURRENTLY`.
- ❌ **Запускать CREATE INDEX CONCURRENTLY в транзакции.** Это невозможно — команда должна выполняться вне транзакционного блока.
- ❌ **Игнорировать невалидные индексы.** После сбоя CONCURRENTLY может оставить невалидный индекс — он занимает место и обновляется при вставке, но не используется. Находи и удаляй.

## 3.15 Для быстрого повторения

- **B-tree:** сбалансированное дерево, все листья на одном уровне. Поиск O(log N). Высота дерева для 5 млн строк — 3 уровня.
- **Страница B-tree:** 8 КБ, содержит Page Header (24 байта), BTree Special (16 байт), ItemId-массив, Index Tuples. Листья (level=0) связаны в двусвязный список через `btpo_prev`/`btpo_next`.
- **Индекс создаётся:** автоматически (PRIMARY KEY, UNIQUE, EXCLUDE) или вручную (CREATE INDEX). `REFERENCES` **не создаёт** индекс.
- **Создание на пустой таблице:** создаются только метаданные. Дерево растёт по мере вставки — первая вставка создаёт лист, который является корнем. Расщепление создаёт новый корень. Дерево **не пересобирается**.
- **Поиск по B-tree:** спуск от корня к листу — 3 чтения индекса + 1 чтение таблицы = 4 страницы вместо 62 500 при Seq Scan. Все чтения идут через Buffer Manager (код в контексте Backend-процесса).
- **Расщепление:** при заполнении листа создаётся новый, половина записей переносится. Родитель получает указатель. Локальная операция O(log N).
- **Составной индекс:** ключ — комбинация колонок. Порядок колонок определяет, какие запросы ускоряются. `(a, b)` помогает для `WHERE a = x`, но не для `WHERE b = x`.
- **Покрывающий индекс:** все нужные колонки в индексе → Index Only Scan. Требует актуальную VM (обновляется VACUUM'ом). `INCLUDE` добавляет неключевые колонки.
- **Частичный индекс:** `WHERE` в индексе. Для подмножества строк — меньше размер, быстрее поиск, дешевле обновление.
- **Функциональный индекс:** индекс по выражению. `lower(email)`, `date(created_at)`. Выражение в запросе должно точно совпадать.
- **CONCURRENTLY:** `CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY` — DDL без блокировки записи. Нельзя в транзакции. При сбое остаётся невалидный индекс.

## 3.17 Ответы

### Ответ 1

Seq Scan имеет линейную сложность O(N). Для 5 миллионов строк при ~80 строках на страницу нужно прочитать ~62 500 страниц (500 МБ). Время растёт линейно с ростом таблицы. При 100 запросах в секунду это 50 ГБ/с — нереально для любого диска.

### Ответ 2

**Неявные способы создания индекса:**
- `PRIMARY KEY` — создаёт уникальный индекс.
- `UNIQUE` — создаёт уникальный индекс.
- `EXCLUDE` — создаёт индекс (обычно GiST или GIN).
- `ALTER TABLE ... ADD PRIMARY KEY / UNIQUE / EXCLUDE` — индекс создаётся при выполнении.

**`REFERENCES` (внешний ключ) НЕ создаёт индекс.** Индекс по FK-колонке нужно создавать вручную.

### Ответ 3

Если таблица пустая, `CREATE INDEX` создаёт **только метаданные** индекса. Физический файл индекса пуст — B-tree ещё не существует. При первой вставке создаётся первая листовая страница (level=0), которая одновременно является корнем. Последующие вставки заполняют эту страницу. Когда она заполняется — расщепление: новый лист + новый корень (level=1). **Дерево не пересобирается с нуля** — оно растёт вверх через локальные расщепления, каждое из которых затрагивает O(log N) страниц.

### Ответ 4

При `CREATE INDEX` на таблице с данными PostgreSQL: (1) читает всю таблицу; (2) для каждой строки извлекает значение индексируемой колонки и TID; (3) сортирует пары (значение, TID) по значению; (4) упаковывает отсортированные пары в листовые страницы; (5) строит дерево (внутренние страницы и корень) над листьями. Стоимость: O(N log N). Выполняет твой Backend-процесс.

### Ответ 5

**Три отличия:**
1. **`special`:** в странице таблицы пустой (0), в странице индекса — 16 байт BTree Special с `btpo_flags`, `btpo_prev`, `btpo_next`, `btpo_level`.
2. **Содержимое:** таблица хранит полные строки с `t_xmin`/`t_xmax`. Индекс хранит только ключ + TID, без MVCC-полей.
3. **Связи:** страницы таблицы не связаны. Страницы индекса связаны вертикально (родитель → дочерняя) и горизонтально (листья через `btpo_prev`/`btpo_next`).

### Ответ 6

**Листья** — страницы с level = 0. Они хранят **значения индексируемой колонки и TID'ы строк таблицы** — это конечная цель поиска. **Внутренние страницы** (level > 0) хранят **указатели на дочерние страницы** — они нужны только для навигации. Корень — это внутренняя страница с максимальным level.

### Ответ 7

Двусвязный список листьев позволяет проходить по диапазону значений **без возврата к корню**. Без него: для каждого следующего листа нужен спуск от корня (O(log N) на лист). С ним: один спуск до первого листа, затем переход по `btpo_next` (O(1) на лист). Это ускоряет `BETWEEN`, `ORDER BY`, `LIMIT` после сортировки.

### Ответ 8

При fanout ~400 (ключей на страницу): высота 1 = 400 строк, высота 2 = 160 000, высота 3 = 64 миллиона. Для 5 миллионов строк высота = 3. Поиск: 3 чтения индекса + 1 чтение таблицы = 4 страницы.

### Ответ 9

Вставка: спуск от корня к нужному листу. Если на листе есть место — вставка в правильную позицию (сдвиг в пределах одной страницы). Если места нет — расщепление: новая страница, половина записей переносится, родитель получает указатель. Локальная операция O(log N).

### Ответ 10

`fillfactor` — параметр, задающий процент заполнения страниц при создании/пересоздании индекса. Дефолт для B-tree — **90**. Менять на 70 для случайных вставок (UUID, email), чтобы меньше расщеплений. 100 — экзотика для append-only.

### Ответ 11

Составной индекс: ключ — комбинация колонок, отсортированная лексикографически. Порядок важен: `(a, b)` может обслуживать `WHERE a = x` и `WHERE a = x AND b = y`, но НЕ `WHERE b = y` (по второй колонке без первой поиск невозможен).

### Ответ 12

Index Only Scan: все нужные колонки есть в индексе → таблица не читается. Условие: страница таблицы должна быть помечена как all-visible в VM (Visibility Map). Если VM устарела — Index Only Scan превращается в Index Scan с чтением таблицы.

### Ответ 13

`INCLUDE`-колонки хранятся только в листовых страницах, не участвуют в поиске и сортировке. Обычные колонки составного индекса — часть ключа, влияют на порядок. `INCLUDE` полезен, когда нужно покрыть запрос, не раздувая дерево.

### Ответ 14

Частичный индекс: индекс с `WHERE`-условием, индексирует только подмножество строк. Выгоден, когда условие отбирает <10% строк и часто используется в запросах. Пример: `CREATE INDEX idx_active ON orders(user_id) WHERE status = 'active'`.

### Ответ 15

Функциональный индекс: индекс по выражению от колонки. Нужен, когда запрос фильтрует по функции: `WHERE lower(email) = '...'`. Обычный индекс по `email` не поможет, потому что в нём оригинальные значения, а не результат `lower()`.

### Ответ 16

Обычный `CREATE INDEX` блокирует запись (SHARE lock) на всё время построения. `CREATE INDEX CONCURRENTLY` строит индекс в фоне, не блокируя запись, но: (1) медленнее в 2-3 раза; (2) нельзя в транзакции; (3) при сбое остаётся невалидный индекс.

### Ответ 17

`REINDEX CONCURRENTLY` — пересоздание индекса без блокировки записи. Используется после массовых DELETE/UPDATE, когда индекс фрагментирован (`leaf_fragmentation > 30%`). Невалидный индекс — индекс, оставшийся после сбоя `CREATE INDEX CONCURRENTLY`; он помечен как `NOT indisvalid` в `pg_class`, не используется планировщиком, но обновляется при вставке. Найти: `SELECT relname FROM pg_class WHERE relkind = 'i' AND NOT indisvalid`. Удалить: `DROP INDEX CONCURRENTLY`.

## 3.18 Куда идти дальше?

Мы разобрали B-tree — самый важный тип индекса в PostgreSQL. Но это не единственный. В следующей главе мы разберём остальные типы индексов и поймём, когда какой использовать:

- **Hash** — для точечного поиска по равенству (быстрее B-tree, но без диапазонов).
- **GiST** — для геоданных, полнотекстового поиска, диапазонов.
- **GIN** — для массивов, JSONB, полнотекстового поиска.
- **BRIN** — для очень больших таблиц с коррелированными данными.
- **SP-GiST** — для специальных структур (quadtrees, k-d деревья).

Мы также узнаем, как PostgreSQL **выбирает**, какой индекс использовать, и почему иногда планировщик ошибается и выбирает Seq Scan вместо Index Scan.
