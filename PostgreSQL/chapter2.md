# 📂 Глава 2: Организация данных на диске — от кластера до страницы

### 📝 1. Структура: «От конкретного к абстрактному»

В Главе 1 мы разобрали, как Backend-процесс выполняет `UPDATE users SET name = 'Alice' WHERE id = 1`. Мы выяснили, что:

- Backend-процесс через Buffer Manager запрашивает страницу с данными. Если страницы нет в `shared_buffers` — читает её с диска.
- Изменённая страница становится «грязной» и позже сбрасывается на диск (Background Writer'ом или самим Backend-процессом).
- Параллельно изменение записывается в WAL-буфер, откуда WAL Writer сбрасывает его в файлы `pg_wal/`.

Но мы **не ответили на главный вопрос**: где физически лежит эта страница на диске? Как PostgreSQL организует дисковое пространство? И как мы от базы данных приходим к конкретной странице?

❓ **Почему нельзя просто хранить все данные в одном файле?**

Представь файл на 1 ТБ, в котором лежат все таблицы, индексы и системные каталоги. Чтобы найти строку в таблице `users`, нужно либо просканировать весь этот гигантский файл, либо иметь сложную систему смещений. При удалении таблицы пришлось бы «дырявить» файл. При сбое риск потерять вообще всё.

💡 Решение: **иерархическая организация дискового пространства**. Данные организованы в виде строгой иерархии: кластер → базы данных → схемы → таблицы и индексы → файлы → страницы. Каждый уровень имеет чёткие границы и управляется независимо.

### 🗂️ 2. Иерархия дискового пространства PostgreSQL

Прежде чем погружаться в страницы, нужно понять, как PostgreSQL видит дисковое пространство. Вот полная иерархия — от самого верхнего уровня до конкретной страницы:

```
УРОВЕНЬ 1: КЛАСТЕР БАЗ ДАННЫХ (Database Cluster)
├── Инициализируется командой initdb
├── Это одна директория на диске (PGDATA)
├── Содержит ВСЕ базы данных этого экземпляра PostgreSQL
├── Именно здесь лежат конфигурационные файлы (postgresql.conf, pg_hba.conf)
│
├── УРОВЕНЬ 2: БАЗА ДАННЫХ (Database)
│   ├── Создаётся командой CREATE DATABASE
│   ├── Физически: поддиректория внутри PGDATA/base/
│   ├── Идентифицируется по OID (Object Identifier)
│   ├── Каждая база изолирована: нельзя сделать JOIN между таблицами разных баз
│   │
│   ├── УРОВЕНЬ 3: СХЕМА (Schema)
│   │   ├── Создаётся командой CREATE SCHEMA
│   │   ├── Это ЛОГИЧЕСКОЕ пространство имён, а не физическая директория
│   │   ├── Схема public создаётся по умолчанию в каждой базе
│   │   ├── В одной базе может быть много схем
│   │   ├── Схемы позволяют организовать таблицы в логические группы
│   │   │
│   │   ├── УРОВЕНЬ 4: ТАБЛИЦЫ, ИНДЕКСЫ, МАТЕРИАЛИЗОВАННЫЕ ПРЕДСТАВЛЕНИЯ
│   │   │   ├── Создаются командами CREATE TABLE, CREATE INDEX и т.д.
│   │   │   ├── Каждый объект имеет свой OID
│   │   │   ├── Физически: ОДИН или НЕСКОЛЬКО файлов на диске
│   │   │   ├── Каждый файл не превышает 1 ГБ (если таблица больше — создаётся новый файл)
│   │   │   │
│   │   │   ├── УРОВЕНЬ 5: ФАЙЛЫ ТАБЛИЦЫ (Relation Files)
│   │   │   │   ├── Основной файл: 16385 (relfilenode)
│   │   │   │   ├── Карта свободного места: 16385_fsm
│   │   │   │   ├── Карта видимости: 16385_vm
│   │   │   │   ├── Если таблица > 1 ГБ: 16385.1, 16385.2, ...
│   │   │   │   │
│   │   │   │   ├── УРОВЕНЬ 6: СТРАНИЦЫ (Pages / Blocks)
│   │   │   │   │   ├── Размер по умолчанию: 8 КБ
│   │   │   │   │   ├── Каждый файл состоит из множества страниц
│   │   │   │   │   ├── Страница — минимальная единица чтения/записи
│   │   │   │   │   └── Внутри страницы: заголовок, массив указателей, кортежи
```

### 💿 3. Уровень 1: Кластер баз данных

**Кластер баз данных** (database cluster) — это **самый верхний уровень**. Это одна директория на диске, которая создаётся командой `initdb` и содержит **все** базы данных одного экземпляра PostgreSQL.

Термин «кластер» здесь не имеет отношения к кластеризации серверов (как в Patroni). Это логическое понятие: «набор баз данных, управляемых одним процессом postmaster».

```
/var/lib/postgresql/data/          ← PGDATA (корень кластера)
├── postgresql.conf                ← основной конфигурационный файл
├── pg_hba.conf                    ← настройки аутентификации
├── PG_VERSION                     ← версия PostgreSQL
├── base/                          ← ВСЕ базы данных (самое важное!)
├── pg_wal/                        ← WAL-файлы (журнал предзаписи)
├── pg_tblspc/                     ← символические ссылки на tablespace
├── pg_stat/                       ← статистика
├── pg_logical/                    ← слоты логической репликации
└── global/                        ← общие системные каталоги (pg_database, pg_authid)
```

**Почему это важно:** на одном сервере может работать **только один** экземпляр PostgreSQL с одним кластером. Если нужно несколько изолированных наборов баз, запускают несколько экземпляров PostgreSQL на разных портах с разными `PGDATA`.

### 🗄️ 4. Уровень 2: База данных

Когда ты выполняешь `CREATE DATABASE mydb`, PostgreSQL создаёт **поддиректорию** внутри `PGDATA/base/`. Имя этой поддиректории — **OID базы данных** (числовой идентификатор).

```
/var/lib/postgresql/data/base/
├── 1/          ← системная база template1
├── 4/          ← системная база template0
├── 16384/      ← твоя база mydb (OID = 16384)
└── 16385/      ← другая база (OID = 16385)
```

Узнать OID своей базы можно запросом:

```sql
SELECT oid, datname FROM pg_database;
-- oid=16384, datname='mydb'
```

**Изоляция:** базы данных в PostgreSQL **полностью изолированы** друг от друга. Нельзя сделать JOIN между таблицами из разных баз. Нельзя использовать одну транзакцию для изменения данных в двух базах. Для запросов между базами используют Foreign Data Wrappers (FDW).

### 📁 5. Уровень 3: Схема — логическое пространство имён

**Схема** (schema) — это **логическое пространство имён** внутри базы данных. В отличие от баз данных, схемы **не имеют физического представления на диске** — нет директории с именем схемы.

Схемы создаются внутри базы данных:

```sql
CREATE SCHEMA accounting;     -- схема для бухгалтерии
CREATE SCHEMA warehouse;      -- схема для склада

-- Теперь можно создавать таблицы в разных схемах:
CREATE TABLE accounting.invoices (...);
CREATE TABLE warehouse.products (...);
```

#### Как PostgreSQL управляет схемами

Схемы хранятся в системном каталоге `pg_namespace` — это обычная таблица внутри базы данных, которая содержит информацию о всех схемах:

```sql
SELECT oid, nspname FROM pg_namespace;
-- oid=11, nspname='pg_catalog'    (системные таблицы)
-- oid=2200, nspname='public'      (схема по умолчанию)
-- oid=16384, nspname='accounting' (пользовательская схема)
-- oid=16385, nspname='warehouse'  (пользовательская схема)
```

Каждая таблица в `pg_class` имеет поле `relnamespace`, которое ссылается на OID схемы из `pg_namespace`. Именно так PostgreSQL понимает, к какой схеме принадлежит таблица.

**Механизм `search_path`** определяет, в каких схемах искать таблицы:

```sql
SHOW search_path;
-- "$user", public

-- Это означает: сначала ищем в схеме с именем текущего пользователя,
-- потом в схеме public
```

Когда ты пишешь `SELECT * FROM users`, PostgreSQL:
1. Смотрит `search_path` — получает список схем для поиска.
2. Идёт в `pg_namespace`, находит OID'ы этих схем.
3. Идёт в `pg_class`, ищет таблицу с именем `users`, у которой `relnamespace` равен OID'у одной из схем.
4. Если таблица найдена — получает её `relfilenode` и идёт читать файлы.

**Зачем нужны схемы:**
- Логическая группировка таблиц (по отделам, по модулям приложения).
- Управление правами доступа: можно дать доступ к схеме `accounting` только бухгалтерам.
- Изоляция: можно иметь таблицы с одинаковыми именами в разных схемах (`accounting.orders` и `warehouse.orders`).

### 📄 6. Уровень 4 и 5: Таблицы, индексы и их файлы

Когда ты создаёшь таблицу, PostgreSQL назначает ей **уникальный OID** (Object Identifier) — 32-битное число, которое идентифицирует объект внутри кластера. OID'ы используются для всех объектов: таблиц, индексов, схем, функций, представлений.

Для таблиц и индексов есть ещё одно важное число — **relfilenode** (relation file node). Это **имя файла** на диске. Обычно `relfilenode` совпадает с OID, но может измениться после операций вроде `VACUUM FULL`, `CLUSTER` или `TRUNCATE`.

#### Что такое 16385, 16385_fsm и 16385_vm

Когда ты видишь файлы с такими именами в директории базы данных:

```
/var/lib/postgresql/data/base/16384/
    ├── 16385              ← основной файл таблицы (САМИ ДАННЫЕ)
    ├── 16385_fsm          ← Free Space Map (карта свободного места)
    └── 16385_vm           ← Visibility Map (карта видимости)
```

- **16385** — это `relfilenode`. Основной файл, содержащий **все страницы** с данными таблицы. Если таблица больше 1 ГБ, создаются дополнительные файлы: `16385.1`, `16385.2` и т.д.

- **16385_fsm** — **Free Space Map**. Вспомогательный файл, который хранит информацию о том, сколько свободного места есть на каждой странице. Когда нужно вставить новую строку, PostgreSQL смотрит в FSM и быстро находит страницу с достаточным местом — без сканирования всей таблицы.

- **16385_vm** — **Visibility Map**. Вспомогательный файл, который хранит битовую карту: для каждой страницы отмечено, все ли строки на ней видны всем транзакциям. Это нужно для Index Only Scan: если все строки на странице видны всем, можно не читать саму таблицу.

Все эти файлы привязаны к `relfilenode`. Узнать его можно запросом:

```sql
SELECT relname, relfilenode, oid, relpages, reltuples
FROM pg_class 
WHERE relname = 'users';
-- relname='users', relfilenode=16385, oid=16385, relpages=12800, reltuples=1000000
```

### 📑 7. Уровень 6: Как файл разбивается на страницы

Теперь самый важный вопрос: **как файл таблицы разбивается на страницы?**

#### Физическое разбиение: страницы идут последовательно

Файл таблицы **физически** разбит на страницы фиксированного размера. Это не логическое деление (как схемы), а **реальное физическое разбиение** на диске. Каждая страница занимает ровно `BLCKSZ` байт (по умолчанию 8192 байта = 8 КБ), и они идут друг за другом без зазоров:

```
ФАЙЛ ТАБЛИЦЫ (16385) НА ДИСКЕ:
┌──────────────────────────────────────────────────────────────────┐
│                          ФАЙЛ НА ДИСКЕ                            │
│  (последовательность байт, без разрывов)                          │
│                                                                  │
│  Байты 0–8191         Байты 8192–16383      Байты 16384–24575   │
│  ┌────────────────┐   ┌────────────────┐   ┌────────────────┐   │
│  │                │   │                │   │                │   │
│  │  СТРАНИЦА 0    │   │  СТРАНИЦА 1    │   │  СТРАНИЦА 2    │   │
│  │  (8 КБ)        │   │  (8 КБ)        │   │  (8 КБ)        │   │
│  │                │   │                │   │                │   │
│  └────────────────┘   └────────────────┘   └────────────────┘   │
│                                                                  │
│  ... и так до конца файла ...                                    │
│                                                                  │
│  Байты (N-1)*8192 – N*8192-1                                     │
│  ┌────────────────┐                                              │
│  │                │                                              │
│  │  СТРАНИЦА N    │                                              │
│  │  (8 КБ)        │                                              │
│  │                │                                              │
│  └────────────────┘                                              │
│                                                                  │
│  ВАЖНО: каждая страница начинается с границы, кратной 8192.      │
│  Страница 0 → смещение 0                                         │
│  Страница 1 → смещение 8192                                      │
│  Страница 2 → смещение 16384                                     │
│  Страница N → смещение N * 8192                                  │
└──────────────────────────────────────────────────────────────────┘
```

#### Как PostgreSQL находит страницу в файле

Когда Buffer Manager'у нужна страница №100, он вычисляет смещение в файле:

```
смещение = номер_страницы * размер_страницы
         = 100 * 8192
         = 819200 байт
```

И выполняет системный вызов `pread()` для чтения 8192 байт начиная со смещения 819200. Это одна операция ввода-вывода. После этого страница загружается в `shared_buffers`.

#### Что происходит, когда таблица растёт

Когда создаётся новая страница (например, при вставке, когда все существующие страницы заполнены), PostgreSQL просто дописывает 8192 байт в конец файла. Файл растёт скачками по 8 КБ.

Если файл достигает 1 ГБ, PostgreSQL **автоматически создаёт новый файл** с суффиксом `.1`:

```
16385        ← 0 – 1 ГБ (страницы 0 – 131071)
16385.1      ← 1 ГБ – 2 ГБ (страницы 131072 – 262143)
16385.2      ← 2 ГБ – 3 ГБ (страницы 262144 – 393215)
```

Страницы внутри каждого файла нумеруются **с нуля относительно начала этого файла**, но логически они продолжают общую нумерацию. Страница 131072 — это страница 0 в файле `16385.1`.

#### Визуализация: как таблица растёт на диске

```
ВРЕМЯ →
──────────────────────────────────────────────────────────────────→

t=0: Только что создали таблицу CREATE TABLE users (...)
  Файл: 16385 (0 байт — пустой)

t=1: Вставили первые строки
  Файл: 16385 (8 КБ = 1 страница)
  ┌────────┐
  │ Стр. 0 │
  └────────┘

t=2: Вставили ещё строки, первая страница заполнилась
  Файл: 16385 (16 КБ = 2 страницы)
  ┌────────┬────────┐
  │ Стр. 0 │ Стр. 1 │
  └────────┴────────┘

t=3: Таблица выросла до 1 ГБ
  Файл: 16385 (1 ГБ = 131072 страницы)
  ┌────────┬────────┬────────┬─────┬────────────┐
  │ Стр. 0 │ Стр. 1 │ Стр. 2 │ ... │ Стр. 131071│
  └────────┴────────┴────────┴─────┴────────────┘

t=4: Таблица превысила 1 ГБ
  Файлы:
  16385   (1 ГБ) ┌────────┬─────┬────────────┐
                 │ Стр. 0 │ ... │ Стр. 131071│
                 └────────┴─────┴────────────┘
  16385.1 (8 КБ) ┌────────────┐
                 │ Стр. 131072│  ← логически продолжает нумерацию
                 └────────────┘
```

### 🔍 8. Практический пример: находим свою таблицу на диске

Допустим, ты хочешь **физически** найти файлы своей таблицы на диске:

```sql
-- 1. Узнаём OID базы данных
SELECT oid, datname FROM pg_database WHERE datname = 'mydb';
-- oid = 16384

-- 2. Узнаём relfilenode таблицы
SELECT relfilenode, relname, relpages, reltuples 
FROM pg_class WHERE relname = 'users';
-- relfilenode = 16385, relpages = 12800, reltuples = 1000000

-- 3. Вычисляем размер таблицы
-- 12800 страниц * 8 КБ = 102 400 КБ ≈ 100 МБ

-- 4. Идём на сервер и находим файлы:
-- cd /var/lib/postgresql/data/base/16384/
-- ls -la 16385*
-- -rw------- 1 postgres postgres 104857600 Jan 1 00:00 16385
-- -rw------- 1 postgres postgres     24576 Jan 1 00:00 16385_fsm
-- -rw------- 1 postgres postgres      8192 Jan 1 00:00 16385_vm
```

Ты только что нашёл физические файлы, в которых лежат данные таблицы `users`. Именно эти файлы читает и изменяет Buffer Manager, когда ты делаешь `SELECT` или `UPDATE`. Страница №100 лежит по смещению 100 × 8192 = 819200 байт в файле `16385`.

### 💾 9. Выбор размера блока: не только 8 КБ

Размер блока выбирается **один раз при инициализации всего кластера баз данных** (при `initdb`) и не может быть изменён потом для отдельной базы или таблицы.

По умолчанию блок равен 8 КБ, но PostgreSQL можно собрать из исходников с другим значением `BLCKSZ` — степенью двойки от 1 до 32 КБ:

```
+-----------------------------------------------------------+
| ВОЗМОЖНЫЕ РАЗМЕРЫ БЛОКА (степень двойки, от 1 до 32 КБ)   |
+-----------------------------------------------------------+
|  1 КБ  |  Не используется, слишком мал                   |
|  2 КБ  |  Теоретически возможен                          |
|  4 КБ  |  Экзотика для систем с мелкими записями         |
|  8 КБ  |  СТАНДАРТНЫЙ РАЗМЕР ПО УМОЛЧАНИЮ               |
| 16 КБ  |  OLAP-системы, меньше накладных расходов        |
| 32 КБ  |  МАКСИМАЛЬНЫЙ РАЗМЕР (тяжёлый OLAP)            |
+-----------------------------------------------------------+
```

**Зачем менять размер блока?**
- **32 КБ**: используется в OLAP-системах (аналитических), где много последовательного чтения больших объёмов данных. Чем больше блок, тем меньше накладных расходов на чтение множества мелких блоков с диска.
- **4 КБ**: экзотика для систем с очень большим количеством случайных точечных записей. Меньший блок уменьшает «оказываемое воздействие» при записи (WAL-записи могут быть меньше), но увеличивает фрагментацию.

**Жёсткое следствие:** максимальная строка не может превышать примерно 1/4 блока. Для 8 КБ это ~2 КБ, для 32 КБ — ~8 КБ. Всё, что больше, уходит в TOAST.

### 📄 10. Анатомия страницы (блока): полная карта

Вне зависимости от размера, каждый блок имеет одну и ту же внутреннюю структуру. Данные растут с двух сторон навстречу друг другу, а между ними — динамическое свободное пространство:

```
+====================================================================+
|                    СТРАНИЦА (БЛОК) — 8 КБ (8192 байта)              |
|  0                                                          8191  |
+====================================================================+
|                            |                            |          |
|  PageHeader (24 байта)     |          >>> FREE <<<      |  Tuple 3 |
|  - lsn (позиция в WAL)    |          >>> SPACE <<<     |  ('Bob') |
|  - checksum                |                            |          |
|  - lower (конец ItemId)   |                            |  Tuple 2 |
|  - upper (начало кортежей)|                            | ('Alice')|
|  - special (для индексов) |                            |          |
+----------------------------+                            +----------+
|  ItemId [0] LP_UNUSED      |                            |  Tuple 1 |
|  ItemId [1] → Tuple1       |                            | (старая  |
|  ItemId [2] → Tuple2       |                РАСТЁТ      | версия)  |
|  ItemId [3] → Tuple3       |                 ВВЕРХ ↑    |          |
|          ...               |                            |          |
|    РАСТЁТ ВНИЗ ↓          |                            |          |
+====================================================================+
                             |                            |
                         lower                        upper
                         (граница ItemId)            (начало кортежей)
```

| Секция | Направление роста | Описание |
|:---|:---|:---|
| **Page Header** | Фиксирован (24 байта) | Метаданные блока: LSN, контрольная сумма, границы |
| **ItemIdData Array** | Вниз ↓ | Массив указателей (по 4 байта), каждый описывает один кортеж |
| **Free Space** | Динамическое | Пространство между указателями и кортежами |
| **Tuple Data** | Вверх ↑ | Сами данные строк — живые и мёртвые версии |

**Почему данные растут с двух сторон навстречу друг другу?**
- `ItemId` (указатели) растут вниз от заголовка.
- Сами кортежи (строки) растут вверх от конца страницы.
- Свободное пространство — это «буферная зона» между ними. Когда новый кортеж не влезает — он идёт на другую страницу, а эта помечается в FSM.

### 🏷️ 11. Заголовок страницы (Page Header, 24 байта)

```
+-----------------------------------------------------------+
|                  PAGE HEADER (24 байта)                     |
+-------+--------+-------+-------+-------+-------+-----+-----+
|  lsn  |checksum| flags | lower | upper |special|pages| ver |
|(8 байт|(2 байта|(2 байт|(2 байт|(2 байт|(2 байт|size |(2 б)|
|       |        |       |       |       |       |(2 б)|     |
+-------+--------+-------+-------+-------+-------+-----+-----+
|                  prune_xid (4 байта)                        |
+-----------------------------------------------------------+
```

| Поле | Размер | Назначение |
|:---|:---|:---|
| `lsn` | 8 байт | Смещение в WAL последнего изменения на этой странице. Критично для восстановления |
| `checksum` | 2 байта | Контрольная сумма для защиты от повреждений на диске |
| `flags` | 2 байта | Битовые флаги (например, `PD_PAGE_FULL`) |
| `lower` | 2 байта | Смещение до конца массива ItemId (граница «сверху») |
| `upper` | 2 байта | Смещение до начала самого нижнего кортежа (граница «снизу») |
| `special` | 2 байта | Смещение до специальной области (только в индексах) |
| `pagesize` | 2 байта | Размер блока (8000 для 8 КБ, 16384 для 16 КБ...) |
| `version` | 2 байта | Версия раскладки страницы |
| `prune_xid` | 4 байта | ID старейшей транзакции на момент последней очистки HOT |

### 📇 12. ItemIdData (массив указателей)

Каждый элемент массива — это 4 байта, работающие как «оглавление» страницы:

```
+-----------------------------------------------------------+
|              МАССИВ ItemId (по 4 байта каждый)             |
+-----------------------------------------------------------+
| [0]  | lp_off=0,lp_flags=LP_UNUSED,lp_len=0 | (свободен)  |
| [1]  | lp_off=7890,lp_flags=LP_NORMAL,lp_len=45 | 45 байт |
| [2]  | lp_off=7830,lp_flags=LP_NORMAL,lp_len=60 | 60 байт |
| [3]  | lp_off=7820,lp_flags=LP_DEAD,lp_len=10  | (мёртв)   |
| [4]  | lp_off=0,lp_flags=LP_REDIRECT,lp_len=0  | -> [2]    |
+-----------------------------------------------------------+
```

| Поле | Размер | Описание |
|:---|:---|:---|
| `lp_off` | 15 бит | Смещение кортежа от начала страницы |
| `lp_flags` | 2 бита | Состояние указателя |
| `lp_len` | 15 бит | Длина кортежа в байтах |

**Флаги `lp_flags`:**
- `LP_UNUSED` (0) — слот свободен, можно занять
- `LP_NORMAL` (1) — слот занят живым кортежем
- `LP_REDIRECT` (2) — HOT-редирект на другой слот (оптимизация обновлений)
- `LP_DEAD` (3) — кортеж мёртв, слот ждёт VACUUM

```
+-----------------------------------------------------------+
| TID (Tuple ID) = (block_number, item_pointer_offset)      |
|                                                           |
| Пример: TID (123, 5)                                      |
|   1. Идём в блок таблицы № 123                           |
|   2. Смотрим в массиве ItemId слот № 5                  |
|   3. Из lp_off узнаём смещение кортежа на странице       |
|   4. Читаем данные по этому смещению                     |
+-----------------------------------------------------------+
```

### 📦 13. Tuple (кортеж): структура строки

Теперь рассмотрим саму строку — **кортеж**:

```
+====================================================================+
|                       КОРТЕЖ (СТРОКА)                               |
+====================================================================+
|                          |        |       |                |        |
| TupleHeader (23 байта)   | Null   | OID   | Данные         |Padding |
|                          | Bitmap |(4 б)  | столбцов       |(выравн)|
+====================================================================+
| <-------------- t_hoff (смещение до данных) --------------->        |
+====================================================================+
```

| Часть кортежа | Описание |
|:---|:---|
| **Tuple Header (23 байта)** | Фиксированный заголовок с метаданными для MVCC и доступа |
| **Null Bitmap** | Битовая карта NULL-значений. 1 бит на столбец. Присутствует, если есть NULLable-столбцы |
| **Object ID (OID)** | 4 байта. **Только если таблица создана с `WITH OIDS`** (сейчас не рекомендуется) |
| **Данные столбцов** | Значения полей в порядке создания столбцов, выровненные по границам |
| **Padding** | Дополнение для выравнивания общей длины кортежа (обычно кратно `MAXALIGN`) |

### 🏷️ 14. Заголовок кортежа (HeapTupleHeaderData, 23 байта)

```
+-----------------------------------------------------------+
|        ЗАГОЛОВОК КОРТЕЖА (HeapTupleHeaderData, 23 байта)   |
+-------+-------+-------+-------+---------+---------+-------+
|t_xmin |t_xmax | t_cid |t_ctid |infomask2|infomask |t_hoff |
|(4 байт|(4 байт|(4 байт|(6 байт|(2 байта)|(2 байта)|(1 байт|
|       |       |       |       |         |         |       |
+-------+-------+-------+-------+---------+---------+-------+
```

| Поле | Размер | Назначение |
|:---|:---|:---|
| `t_xmin` | 4 байта | ID транзакции, создавшей эту версию строки |
| `t_xmax` | 4 байта | ID транзакции, удалившей/обновившей эту версию (0 = жива) |
| `t_cid` | 4 байта | Command ID — номер команды внутри транзакции-создателя |
| `t_ctid` | 6 байт | TID новой версии при UPDATE (или указывает на себя) |
| `t_infomask2` | 2 байта | Флаги: количество атрибутов в Null Bitmap, есть ли OID |
| `t_infomask` | 2 байта | Ключевые флаги видимости и состояния |
| `t_hoff` | 1 байт | Размер заголовка — смещение до начала данных |

**Флаги `t_infomask` (подсказки видимости):**

```
+-----------------------------------------------------------+
|    ФЛАГИ t_infomask (подсказки видимости)                 |
+-----------------------------------------------------------+
| HEAP_XMIN_COMMITTED  | xmin транзакция точно закоммичена  |
| HEAP_XMIN_INVALID    | xmin транзакция откатилась/сбой    |
| HEAP_XMAX_COMMITTED  | xmax транзакция точно закоммичена  |
| HEAP_XMAX_INVALID    | xmax транзакция откатилась         |
| HEAP_HASNULL         | в строке есть NULL-значения        |
| HEAP_HOT_UPDATED     | строка обновлена по HOT            |
| HEAP_ONLY_TUPLE      | строка создана как HOT-кортеж      |
+-----------------------------------------------------------+
```

Зачем нужны эти флаги? Без них, чтобы узнать статус транзакции `xmin`, нужно идти в системный каталог `pg_xact` (ранее `pg_clog`). С флагами статус «зашит» прямо в строку — это экономит огромное количество обращений.

### 🔗 15. Цепочка версий при UPDATE

Наш запрос `UPDATE users SET name = 'Alice' WHERE id = 1`. Вот что происходит на странице:

```
ДО UPDATE:
+----------------------------------------------------------------+
| Слот [1] LP_NORMAL                                              |
|   t_xmin=100, t_xmax=0, t_ctid=(0,1)                           |
|   name = 'Bob'                                                  |
+----------------------------------------------------------------+

ПОСЛЕ UPDATE (транзакция 200):
+----------------------------------------------------------------+
| Слот [1] LP_NORMAL                                              |
|   t_xmin=100, t_xmax=200, t_ctid=(0,2) ----→ указывает на слот 2|
|   name = 'Bob'                           |                      |
+----------------------------------------------------------------+
                                           |
+------------------------------------------|---------------------+
| Слот [2] LP_NORMAL (новая строка!)       ↓                     |
|   t_xmin=200, t_xmax=0, t_ctid=(0,2) — указывает на себя      |
|   name = 'Alice'                                               |
+----------------------------------------------------------------+

ЧТО ВИДЯТ ДРУГИЕ ТРАНЗАКЦИИ:
  • Транзакция, начавшаяся ДО транзакции 200:
    видит слот [1], name='Bob' (её снимок не включает изменения)

  • Транзакция, начавшаяся ПОСЛЕ COMMIT транзакции 200:
    видит t_xmax=200 у слота [1], проверяет что 200 закоммичена,
    идёт по t_ctid → слот [2] → name='Alice'
```

### 🗺️ 16. Свободное пространство и FSM

Когда на странице не хватает места для новой версии строки, она ищется в другой странице. Для быстрого поиска существует **Free Space Map (FSM)** — отдельные файлы с суффиксом `_fsm`:

```
+-----------------------------------------------------------+
| FREE SPACE MAP (FSM) - древовидная структура              |
|                                                           |
|                   [Корень: max free]                       |
|                  /                    \                    |
|        [Страницы 0-99]        [Страницы 100-199]          |
|         /        \               /          \             |
|    [0-49]      [50-99]      [100-149]    [150-199]       |
|                                                           |
| Каждый узел хранит МАКСИМАЛЬНЫЙ размер свободного         |
| куска в своей группе страниц.                             |
| Это позволяет БЫСТРО найти страницу с нужным местом.     |
+-----------------------------------------------------------+
```

FSM хранит в виде дерева информацию о примерном количестве свободного места на каждой странице, чтобы при вставке не сканировать всю таблицу.

### 📦 17. TOAST: когда строка не влезает в страницу

Что если наша таблица хранит огромный JSON или текст? Строка может быть больше 8 КБ! Если строка превышает примерно 2 КБ (четверть страницы), PostgreSQL сначала пытается сжать поля, а если даже после сжатия не влезает — выносит данные во внешнюю TOAST-таблицу.

```
ОСНОВНАЯ ТАБЛИЦА (users)
+-------------------+--------------------------------------------------+
| id | name | bio  |                                                  |
+----+------+------+                                                  |
| 1  | Alice| (TOAST-указатель)                                       |
|    |      |   тип: сжатый (PGLZ)                                   |
|    |      |   исходный размер: 15 КБ                                |
|    |      |   сжатый размер: 6 КБ                                  |
|    |      |   TOAST-таблица: pg_toast.pg_toast_16541                |
|    |      |   toast_id: 42                                          |
+----+------+---------------------------------------------------------+
            |
            | PostgreSQL автоматически создаёт TOAST-таблицу
            ▼
TOAST-ТАБЛИЦА (pg_toast.pg_toast_16541) — отдельные файлы на диске
+----------+-----------+----------------------------+
| chunk_id | chunk_seq | chunk_data                 |
+----------+-----------+----------------------------+
| 42       | 0         | [первые ~2 КБ сжатых данных]|
| 42       | 1         | [следующие ~2 КБ]           |
| 42       | 2         | [последние ~2 КБ]           |
+----------+-----------+----------------------------+
```

**Стратегии хранения TOAST (можно задать для столбца):**

| Стратегия | Поведение |
|:---|:---|
| `EXTENDED` (по умолчанию) | Сжать и вынести, если не влезает |
| `EXTERNAL` | Вынести БЕЗ сжатия. Быстрее для `substring()` |
| `MAIN` | Сжать, но оставить в основной таблице, если возможно |
| `PLAIN` | Запрет на TOAST и сжатие (для коротких данных) |

**Важно:** при `SELECT * FROM users` без обращения к TOAST-полю (например, только `id` и `name`) TOAST-таблица **не читается вообще**.

### ⚙️ 18. Аннотации сложности и контекста

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| **Поиск страницы в файле** | O(1) — прямое вычисление смещения: `N * 8192` | 1 страница в `shared_buffers` | Buffer Manager: «дай страницу №100» |
| **Поиск строки по TID** | O(1) — прямое смещение в странице через ItemId | 1 страница в `shared_buffers` | После Index Scan: «дай мне блок 100, слот 5» |
| **Создание новой версии (UPDATE)** | O(1) — если есть место на странице, иначе поиск через FSM | Новый кортеж + запись в WAL | Каждый UPDATE/DELETE |
| **Чтение TOAST-значения** | O(N) — N чанков надо прочитать | Зависит от размера TOAST-объекта | `SELECT large_column FROM ...` |
| **Проверка видимости (MVCC)** | O(1) — после установки hint bits | Чтение флагов из заголовка кортежа | Каждое чтение строки |

### ⭐🚀🔧 19. Разделение на «базу» и «продвинутые» паттерны

⭐ **Must-know:**
- Кластер → База → Схема → Таблица → Файл → Страница → Кортеж. Это полная иерархия хранения.
- Страница — 8 КБ, это атомарная единица ввода-вывода. Страницы физически последовательно расположены в файлах.
- `relfilenode` — имя файла на диске. `_fsm` — карта свободного места. `_vm` — карта видимости.
- Схема — логическое пространство имён, управляется через `pg_namespace` и `search_path`.
- Кортеж имеет заголовок с `t_xmin`/`t_xmax` для MVCC.
- TOAST автоматически выносит большие значения во внешнюю таблицу.
- UPDATE создаёт новую версию строки, старая не удаляется.

🚀 **Advanced:**
- Hint bits (`HEAP_XMIN_COMMITTED`) экономят обращения к `pg_xact`.
- Стратегии TOAST: `EXTERNAL` ускоряет `substring()`, `MAIN` минимизирует обращения к TOAST-таблице.
- HOT (Heap-Only Tuple) — оптимизация, когда обновление не затрагивает индексированные колонки.
- FSM — древовидная структура для быстрого поиска свободного места.
- OID и relfilenode могут различаться после VACUUM FULL, CLUSTER, TRUNCATE.

🔧 **Toolbox:**
- `pg_database` — узнать OID базы данных.
- `pg_class` — узнать relfilenode, количество страниц и строк.
- `pg_namespace` — посмотреть все схемы в базе.
- `pg_total_relation_size()` — узнать размер таблицы с индексами и TOAST.
- Расширение `pageinspect` — заглянуть внутрь страницы.
- `pgstattuple` — оценить раздувание (сколько мёртвых кортежей).

### 📜 20. Принцип «завершённых шагов» на примере чтения строки

Ты выполняешь `SELECT name FROM users WHERE id = 1`. Индекс уже дал TID: (блок 100, слот 5).

1.  **Вычислить смещение в файле**
    - *Зачем:* Buffer Manager вычисляет: 100 × 8192 = 819200 байт. Это смещение в файле таблицы.

2.  **Запросить страницу у Buffer Manager**
    - *Зачем:* Buffer Manager проверяет `shared_buffers`. Если страница №100 уже там — отлично. Если нет — выполняет `pread()` на файле таблицы и загружает страницу в кэш.

3.  **Найти кортеж через массив ItemId**
    - *Зачем:* В странице идём в `ItemId[5]`, читаем `lp_off` (смещение кортежа) и `lp_len` (длина). Теперь мы знаем, где именно лежат данные строки.

4.  **Прочитать заголовок кортежа**
    - *Зачем:* Смотрим `t_xmin` (кто создал), `t_xmax` (удалена ли), флаги `t_infomask` (закоммичен ли создатель). Это нужно для проверки видимости (MVCC).

5.  **Принять решение о видимости**
    - *Зачем:* Если `t_xmin` — это незакоммиченная или откаченная транзакция, строка нам не видна. Идём по цепочке `t_ctid` или возвращаем «строка не найдена».

6.  **Прочитать данные столбцов**
    - *Зачем:* Если строка видна, отступаем `t_hoff` байт от начала кортежа (пропускаем заголовок и Null Bitmap) и читаем значения столбцов в том порядке, в котором они идут в таблице.

### 🏛️ 21. Аналогия: страница как страница в библиотечной книге

Представь, что таблица `users` — это огромная бухгалтерская книга.

- **Кластер** — это весь архив (здание). В нём много комнат (баз данных).
- **База данных** — это отдельная комната в архиве. В каждой комнате свои шкафы с книгами.
- **Схема** — это каталог в комнате: «Книги по бухгалтерии — на этой полке, по складу — на той». Сам каталог не занимает места на полках, это просто указатели.
- **Таблица** — это одна книга. У неё есть инвентарный номер (relfilenode).
- **Страница книги** — это блок PostgreSQL (8 КБ). Библиотекарь не может прочитать «полслова», он всегда переворачивает страницу целиком.
- **Оглавление страницы (ItemId)** — это колонтитул вверху: «Запись №1 — строка 5, Запись №2 — строка 20».
- **TOAST** — это когда запись не влезает на одну страницу, и библиотекарь говорит: «Продолжение записи смотри в Приложении №3, стр. 42».
- **MVCC** — это правило: **«Никогда не зачёркивай старую запись»**. Если данные изменились, библиотекарь делает новую запись, а на старой пишет: «Актуальная версия на странице 42».

### ❓ 22. Интерактивность: вопросы для самопроверки

#### 📌 Вопрос 1

Размер блока по умолчанию — 8 КБ. Что произойдёт с производительностью, если сделать его 32 КБ для OLAP-нагрузки? А для OLTP?

#### ✅ Ответ 1

**Для OLAP (аналитика, много последовательного чтения):**
- **Улучшение производительности.** Большие блоки означают меньше накладных расходов на чтение заголовков. Один запрос `SELECT * FROM huge_table` читает меньше блоков с диска, что эффективнее.
- Меньше фрагментации: строки реже переносятся на другие страницы.

**Для OLTP (транзакции, много точечных записей):**
- **Ухудшение производительности.** Каждый `UPDATE` затрагивает целый блок в 32 КБ, даже если меняется одна строка. Это увеличивает объём WAL-записей.
- Выше фрагментация внутри страницы: при частых мелких изменениях в блоке остаётся много мёртвых версий.
- Больше данных приходится перезаписывать при контрольных точках.

---

#### 📌 Вопрос 2

Ты делаешь `SELECT id FROM users WHERE id = 1`. Поле `id` проиндексировано. Сколько раз PostgreSQL обратится к странице таблицы, если в ней лежит 100 строк?

#### ✅ Ответ 2

**Один раз.** PostgreSQL не сканирует всю страницу в поисках строки. У него есть массив `ItemId`, который работает как оглавление. Индекс даёт точный TID — (блок, слот). Процесс идёт прямо к нужному слоту в массиве `ItemId`, читает смещение (`lp_off`) и длину (`lp_len`), и получает кортеж. Остальные 99 строк на странице не читаются.

---

#### 📌 Вопрос 3

Что хранится в `t_ctid` у самой свежей версии строки? А у старой?

#### ✅ Ответ 3

- **У самой свежей версии:** `t_ctid` указывает на саму себя (тот же блок и слот). Это признак того, что это актуальная версия и дальше по цепочке идти не нужно.
- **У старой версии:** `t_ctid` указывает на TID новой версии (другой блок и/или слот). Это формирует цепочку версий: старая → новая → самая новая (указывает на себя).

---

#### 📌 Вопрос 4

Ты написал `SELECT * FROM users`, но в таблице есть колонка `bio` с огромным текстом. Будет ли PostgreSQL читать TOAST-таблицу?

#### ✅ Ответ 4

**Да, будет.** `SELECT *` запрашивает **все** колонки, включая `bio`. PostgreSQL увидит TOAST-указатель в основной таблице, найдёт `toast_id` и пойдёт в TOAST-таблицу читать все чанки.

Если бы запрос был `SELECT id, name FROM users` (без колонки `bio`), TOAST-таблица **не читалась бы вообще** — указатель просто пропускается.

**Совет:** для больших текстовых полей, где часто нужен только `substring()`, используй стратегию `EXTERNAL` — она позволяет читать часть данных, не вытаскивая весь TOAST-объект.

---

#### 📌 Вопрос 5

Как PostgreSQL находит, на какую страницу вставить новую строку? Неужели сканирует всю таблицу?

#### ✅ Ответ 5

**Нет, не сканирует.** Для этого существует **Free Space Map (FSM)** — отдельный файл с суффиксом `_fsm`. FSM хранит древовидную структуру, где каждый узел показывает максимальный размер свободного куска в своей группе страниц.

При вставке PostgreSQL:
1. Смотрит в FSM: «Есть ли страница с достаточным свободным местом?»
2. Если да — идёт прямо к этой странице.
3. Если нет — выделяет новую страницу в конце файла таблицы.

Без FSM пришлось бы сканировать всю таблицу в поисках места, что было бы катастрофой для производительности.

---

#### 📌 Вопрос 6

Чем схема отличается от базы данных? Почему нельзя просто создать две базы данных вместо двух схем?

#### ✅ Ответ 6

**База данных** — это физически изолированный набор данных со своей директорией на диске. Базы **полностью изолированы**: нельзя сделать JOIN между таблицами разных баз, нельзя использовать одну транзакцию.

**Схема** — это логическое пространство имён внутри одной базы. Таблицы из разных схем лежат в одних и тех же файлах (одна директория базы), и между ними можно делать JOIN без ограничений.

**Когда использовать схемы:** когда нужно логически сгруппировать таблицы, но сохранить возможность JOIN и единого управления (например, `accounting.invoices` и `warehouse.products` — разные отделы, но могут понадобиться общие отчёты).

**Когда использовать разные базы:** когда нужна полная изоляция (разные клиенты в SaaS) или разные настройки (разные `search_path`, разные расширения).

---

#### 📌 Вопрос 7

Что произойдёт с `relfilenode` после `VACUUM FULL`? Почему это важно?

#### ✅ Ответ 7

После `VACUUM FULL` (или `CLUSTER`) `relfilenode` **изменится**, потому что PostgreSQL создаёт **новый физический файл** и копирует в него только живые строки. Старый файл удаляется.

Это важно по двум причинам:
1. Если ты запомнил старый `relfilenode` и ожидаешь найти файл на диске — его там больше нет.
2. Изменение `relfilenode` инвалидирует кэш планов запросов, которые ссылались на старый файл.

Обычно `relfilenode` меняется редко, и для большинства приложений это незаметно.

### 💡 23. Выводы и типичные ошибки

**Что мы узнали?**
Дисковое пространство PostgreSQL организовано в строгую иерархию: кластер → база данных → схема → таблица → файлы → страницы → кортежи. Страницы — это физические блоки по 8 КБ, последовательно расположенные в файлах. Схемы — логическое пространство имён, управляемое через `pg_namespace`. Каждая таблица идентифицируется `relfilenode` — именем её файла на диске. Внутри страницы данные растут с двух сторон, а специальный массив ItemId работает как оглавление для быстрого доступа к кортежам.

**Типичные ошибки:**
- ❌ **Путать схему и базу данных.** Схема не создаёт директорию на диске, это чисто логическое разделение.
- ❌ **Думать, что размер строки не ограничен.** Даже с TOAST, строка должна поместиться хотя бы в 1/4 страницы (~2 КБ), иначе вставка невозможна.
- ❌ **Забывать про `t_ctid` при анализе производительности.** Если цепочка версий длинная (много UPDATE без VACUUM), чтение «свежей» версии будет прыгать по многим версиям.
- ❌ **Не учитывать стратегию TOAST.** Если делать `SELECT substring(bio, 1, 100)`, а столбец в режиме `EXTENDED` (сжатый), PostgreSQL всё равно прочитает и распакует ВЕСЬ TOAST-объект. Для таких запросов лучше `EXTERNAL`.
- ❌ **Игнорировать FSM и VM.** Без FSM вставка новой строки будет сканировать всю таблицу в поисках места. Без VM не будет работать Index Only Scan.

| Концепт | Суть | Ключевой факт |
|:---|:---|:---|
| **Кластер БД** | Директория `PGDATA` | Инициализируется `initdb`. Содержит ВСЕ базы данных |
| **База данных** | Поддиректория в `base/` с OID | Полная изоляция: нет JOIN между базами |
| **Схема** | Логическое пространство имён | Хранится в `pg_namespace`. Ищется через `search_path`. Нет физического представления |
| **relfilenode** | Имя файла таблицы на диске | Обычно равен OID. Меняется при VACUUM FULL, CLUSTER |
| **FSM** | Free Space Map (`_fsm`) | Древовидная карта свободного места. Быстрый поиск куда вставить |
| **VM** | Visibility Map (`_vm`) | Битовая карта: все ли строки на странице видны всем? |
| **Страница (Block)** | 8 КБ, мин. единица чтения/записи | Физически последовательно в файле. Смещение = N * 8192 |
| **Page Header** | 24 байта метаданных | LSN для WAL, контрольная сумма, границы lower/upper |
| **ItemId (указатель)** | 4 байта: смещение + длина + флаги | Позволяет найти кортеж без сканирования страницы |
| **Кортеж (Tuple)** | Строка с заголовком 23 байта | `t_xmin`/`t_xmax` для MVCC, `t_ctid` для цепочки версий |
| **Hint bits** | Флаги в `t_infomask` | Кэшируют статус транзакции прямо в строке |
| **TOAST** | Вынос больших значений | Автоматически срабатывает при >2 КБ. 4 стратегии хранения |
