## 4.0 Пролог: когда B-tree не справляется

В Главе 3 мы разобрали B-tree — самый универсальный тип индекса. Он отлично работает для:

- Точечного поиска (`WHERE id = 42`)
- Диапазонов (`WHERE id BETWEEN 1 AND 100`)
- Сортировки (`ORDER BY id`)
- Составных ключей (`WHERE user_id = 42 AND created_at > ...`)

Но есть задачи, где B-tree **бессилен** или **неэффективен**:

```sql
-- Задача 1: Поиск по массиву
SELECT * FROM users WHERE tags @> ARRAY['golang', 'postgres'];
-- B-tree не умеет искать по элементам массива

-- Задача 2: Поиск по JSONB
SELECT * FROM events WHERE data->>'type' = 'purchase';
-- B-tree не умеет искать внутри JSON

-- Задача 3: Полнотекстовый поиск
SELECT * FROM articles WHERE body LIKE '%postgres%';
-- B-tree не поможет с подстрокой в середине текста

-- Задача 4: Геоданные
SELECT * FROM places WHERE location <-> point(37.6, 55.7) < 10;
-- B-tree не умеет работать с геометрическими операторами

-- Задача 5: Огромная таблица (100+ ГБ)
CREATE INDEX ON events(created_at);
-- B-tree будет размером с саму таблицу
```

В каждом из этих случаев нужен **другой тип индекса**, спроектированный под конкретную структуру данных и конкретные операторы.

❓ **Почему бы не использовать B-tree везде?**

Потому что B-tree оптимизирован для **одномерных, сортируемых значений**: числа, строки, даты. Он не понимает:

- **Многозначные поля** (массивы, JSONB) — где у одной строки много ключей
- **Геометрические операции** (близость, пересечение, вхождение)
- **Полнотекстовый поиск** (слова в тексте, а не значения колонки)
- **Корреляцию с физическим порядком** (BRIN использует это для сжатия)

Для каждой из этих задач PostgreSQL предоставляет **специализированный тип индекса**.

## 4.1 Обзор типов индексов в PostgreSQL

PostgreSQL поддерживает **шесть встроенных типов индексов**:

| Тип | Полное название | Оптимален для | Не подходит для |
|:---|:---|:---|:---|
| **B-tree** | Balanced Tree | Числа, строки, даты, диапазоны, сортировка | Массивы, JSONB, геоданные |
| **Hash** | Hash Index | Только точечный поиск `=` | Диапазоны, сортировка |
| **GiST** | Generalized Search Tree | Геоданные, полнотекстовый поиск, диапазоны | Простые числа |
| **SP-GiST** | Space-Partitioned GiST | Точки на плоскости, IP-адреса | — |
| **GIN** | Generalized Inverted Index | Массивы, JSONB, полнотекстовый поиск | Сортировка |
| **BRIN** | Block Range Index | Очень большие таблицы с коррелированными данными | Случайные данные |

### Как PostgreSQL выбирает тип индекса

Вспомни Главу 3: когда ты создаёшь индекс через `CREATE INDEX`, по умолчанию используется **B-tree**:

```sql
-- Неявно B-tree
CREATE INDEX idx_users_id ON users(id);
```

Чтобы использовать другой тип, указываешь `USING`:

```sql
-- Явно указываем тип
CREATE INDEX idx_users_tags ON users USING GIN (tags);
CREATE INDEX idx_places_location ON places USING GiST (location);
CREATE INDEX idx_events_created_at ON events USING BRIN (created_at);
```

**Каждый тип индекса поддерживает свой набор операторов.**

Например:

- B-tree: `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`
- Hash: только `=`
- GIN: `@>`, `<@`, `?`, `?|`, `?&`
- GiST: `&&`, `<->`, `<<`, `>>`, `@>`, `<@`
- BRIN: `=`, `<`, `<=`, `>`, `>=`

Если оператор в `WHERE` не поддерживается типом индекса — планировщик **не сможет использовать** этот индекс.

### Визуализация: структура каждого типа на страницах

Каждый тип индекса — это **разные структуры данных**, но все они хранятся в **тех же 8-КБ страницах**, что и B-tree (Глава 2).

```
B-tree (Глава 3):                GIN:
  Дерево с ключами                 Инвертированный список:
  в листьях                        ключ → список TID'ов

GiST:                            BRIN:
  Дерево с предикатами             Диапазоны блоков:
  в узлах                          блоки 1-100: min-max

Hash:                            SP-GiST:
  Хэш-таблица                      Дерево разбиения пространства
```

### Связь с предыдущими главами

Всё, что мы разбирали раньше, **применимо и к другим типам индексов**:

- **Глава 1**: страницы индексов живут в том же `shared_buffers`, логируются в WAL.
- **Глава 2**: у индекса свой `relfilenode`, свои `_fsm`, `_vm`.
- **Глава 3**: `CREATE INDEX` выполняет Backend-процесс, алгоритм создания аналогичен.

**Отличие только в структуре страниц и алгоритмах поиска.**

## 4.2 GIN: инвертированный индекс для массивов и JSONB

В подглаве 4.1 мы увидели, что B-tree не умеет работать с массивами и JSONB. Теперь разберём **GIN** — тип индекса, который решает эту задачу.

### Проблема: почему B-tree не работает с массивами

Представь таблицу:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    tags TEXT[]  -- массив тегов: ['golang', 'postgres', 'docker']
);

-- Частый запрос: найти всех, у кого есть тег 'golang'
SELECT * FROM users WHERE tags @> ARRAY['golang'];
```

Оператор `@>` означает «содержит». Как B-tree мог бы обслужить этот запрос?

B-tree хранит **одно значение** колонки как ключ. Но `tags` — это **массив**. В одной строке может быть 10 тегов. B-tree не может «разложить» массив на элементы и индексировать каждый отдельно.

Если создать B-tree по `tags`:

```sql
CREATE INDEX idx_users_tags_btree ON users(tags);
```

PostgreSQL **не сможет** использовать его для `tags @> ARRAY['golang']`, потому что B-tree не понимает оператор `@>`.

### Идея GIN: инвертированный индекс

Вспомни аналогию из Главы 3: B-tree — это оглавление книги (значение → страницы). Но для массива нужно **другое оглавление**: не «значение → TID», а «**элемент → список TID'ов**».

Это и есть **GIN (Generalized Inverted Index)** — **инвертированный индекс**.

**Инвертированный** — потому что он «переворачивает» отношение: не «строка → элементы», а «элемент → строки».

```
Обычное хранение (таблица):

  Строка 1: tags = ['golang', 'postgres', 'docker']
  Строка 2: tags = ['python', 'postgres']
  Строка 3: tags = ['golang', 'docker']

GIN-индекс (инвертированный):

  'docker'   → TID(0,1), TID(0,3)
  'golang'   → TID(0,1), TID(0,3)
  'postgres' → TID(0,1), TID(0,2)
  'python'   → TID(0,2)
```

Теперь запрос `tags @> ARRAY['golang']` работает так:

1. Ищем ключ `'golang'` в GIN-индексе.
2. Получаем список TID'ов: `(0,1), (0,3)`.
3. Читаем эти строки из таблицы.

Никакого сканирования всей таблицы — только точечный поиск по элементу.

### Внутренняя структура GIN

GIN-индекс хранится в **тех же 8-КБ страницах**, что и B-tree (Глава 2), но структура страниц **другая**.

```
СТРАНИЦА GIN-ИНДЕКСА:

┌───────────────────────────────────────────────────────────┐
│ PageHeader (24 байта)                                     │
│ special = ... (GIN-специфичная метаинформация)            │
├───────────────────────────────────────────────────────────┤
│ Элементы (keys):                                          │
│   'docker'   → указатель на список TID'ов                │
│   'golang'   → указатель на список TID'ов                │
│   'postgres' → указатель на список TID'ов                │
│   'python'   → указатель на список TID'ов                │
├───────────────────────────────────────────────────────────┤
│ Posting Lists (списки TID'ов):                            │
│   Для 'docker':   [TID(0,1), TID(0,3)]                   │
│   Для 'golang':   [TID(0,1), TID(0,3)]                   │
│   Для 'postgres': [TID(0,1), TID(0,2)]                   │
│   Для 'python':   [TID(0,2)]                              │
└───────────────────────────────────────────────────────────┘
```

**Ключевые компоненты GIN:**

| Компонент | Описание |
|:---|:---|
| **Ключ (element)** | Значение элемента (тег, слово, ключ JSON) |
| **Posting List** | Список TID'ов строк, содержащих этот элемент |
| **Posting Tree** | Дерево для длинных posting lists (> 1000 TID'ов) |

Если элемент встречается в **очень многих** строках (например, тег `'golang'` в 1 млн строк), его posting list становится длинным. GIN разделяет его на **posting tree** — это B-tree внутри GIN, который хранит TID'ы по страницам.

### Как GIN обслуживает разные операторы

GIN поддерживает несколько операторов для массивов:

| Оператор | Значение | Пример |
|:---|:---|:---|
| `@>` | Содержит все элементы | `tags @> ARRAY['golang']` |
| `<@` | Содержится в | `tags <@ ARRAY['golang', 'docker']` |
| `&&` | Пересекается (хотя бы один общий) | `tags && ARRAY['golang', 'python']` |

**Поиск `tags @> ARRAY['golang', 'docker']` (содержит оба):**

1. Ищем `'golang'` → получаем TID'ы: `(0,1), (0,3)`.
2. Ищем `'docker'` → получаем TID'ы: `(0,1), (0,3)`.
3. **Пересекаем** списки: `(0,1), (0,3)`.
4. Читаем эти строки из таблицы.

**Поиск `tags && ARRAY['golang', 'python']` (пересекается):**

1. Ищем `'golang'` → `(0,1), (0,3)`.
2. Ищем `'python'` → `(0,2)`.
3. **Объединяем** списки: `(0,1), (0,2), (0,3)`.
4. Читаем строки.

### GIN для JSONB

GIN также работает с **JSONB** — бинарным JSON с поддержкой индексации.

```sql
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    data JSONB
);

INSERT INTO events(data) VALUES 
    ('{"type": "purchase", "user_id": 42}'),
    ('{"type": "visit", "user_id": 7}'),
    ('{"type": "purchase", "user_id": 100}');

-- Частый запрос: найти все покупки
SELECT * FROM events WHERE data @> '{"type": "purchase"}';
```

Для этого нужен GIN-индекс по JSONB:

```sql
CREATE INDEX idx_events_data ON events USING GIN (data);
```

**Как GIN индексирует JSONB:**

```
JSONB: {"type": "purchase", "user_id": 42}

GIN извлекает элементы:
  'type'    → 'purchase'  (ключ и значение)
  'user_id' → 42

Получаются составные ключи:
  "type=purchase" → TID
  "user_id=42"    → TID
```

Запрос `data @> '{"type": "purchase"}'`:

1. Формирует ключ `"type=purchase"`.
2. Ищет в GIN → получает TID'ы.
3. Читает строки.

### Визуализация: GIN для JSONB

```
ТАБЛИЦА events:

  Строка 1: data = {"type": "purchase", "user_id": 42}
  Строка 2: data = {"type": "visit", "user_id": 7}
  Строка 3: data = {"type": "purchase", "user_id": 100}

GIN-ИНДЕКС (упрощённо):

  Ключ "type=purchase" → TID(0,1), TID(0,3)
  Ключ "type=visit"    → TID(0,2)
  Ключ "user_id=42"    → TID(0,1)
  Ключ "user_id=7"     → TID(0,2)
  Ключ "user_id=100"   → TID(0,3)
```

### Как GIN создаётся

Вспомни Главу 3: `CREATE INDEX` выполняет Backend-процесс, читает таблицу, строит индекс.

Для GIN алгоритм похож, но **вместо сортировки** он:

1. Читает каждую строку.
2. **Разбирает** массив или JSONB на отдельные элементы.
3. Для каждого элемента добавляет TID в posting list.
4. Строит структуру GIN.

Это **дороже**, чем создание B-tree, потому что обработка каждого элемента — отдельная операция.

### Сравнение: B-tree vs GIN для массивов

| Аспект | B-tree по массиву | GIN по массиву |
|:---|:---|:---|
| Поддерживает `@>`? | ❌ Нет | ✅ Да |
| Размер индекса | Не имеет смысла | Компактный (элементы + TID'ы) |
| Скорость вставки | — | Медленнее (разбор массива) |
| Скорость поиска `@>` | — | Быстрый (точечный по элементу) |

### 💡 Практика: когда использовать GIN

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Частые запросы по массивам:**
   ```sql
   CREATE INDEX idx_users_tags ON users USING GIN (tags);
   SELECT * FROM users WHERE tags @> ARRAY['golang'];
   ```

2. **Частые запросы по JSONB:**
   ```sql
   CREATE INDEX idx_events_data ON events USING GIN (data);
   SELECT * FROM events WHERE data @> '{"type": "purchase"}';
   ```

3. **Полнотекстовый поиск** (разберём в подглаве 4.3, где сравним GIN и GiST).

**👍 СТОИТ СДЕЛАТЬ:**

4. **Если нужны оба типа поиска (по массиву и по JSONB)** — создай два отдельных GIN-индекса.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Если массив редко используется в WHERE.** GIN замедляет вставку — каждая вставка разбирает массив и обновляет индекс.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй GIN для простых колонок** (числа, строки). Для них B-tree быстрее.

### Как понять по метрикам, что нужен GIN

**Метрика 1: План показывает Seq Scan**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE tags @> ARRAY['golang'];
```

Если видишь `Seq Scan` — B-tree не может обслужить `@>`, нужен GIN.

**Метрика 2: Частота запроса**

```sql
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
WHERE query LIKE '%@>%'
ORDER BY total_exec_time DESC
LIMIT 5;
```

Частые запросы с `@>` = кандидаты на GIN.

**Метрика 3: Проверка после создания**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE tags @> ARRAY['golang'];
```

| Метрика | До GIN | После GIN |
|:---|:---|:---|
| План | Seq Scan | **Bitmap Index Scan** |
| Чтений страниц | 62 500 | **~5** |
| Время | 250 мс | **< 1 мс** |

### Итог подглавы 4.2

- **GIN** — инвертированный индекс: «элемент → список TID'ов».
- **Для массивов** — индексирует каждый элемент массива отдельно.
- **Для JSONB** — индексирует ключи и значения как составные элементы.
- **Операторы** — `@>`, `<@`, `&&`.
- **Структура** — ключи + posting lists (списки TID'ов), в тех же 8-КБ страницах.
- **Создание** — дороже B-tree (разбор массивов/JSONB), но окупается при частых запросах.
- **Практика:** обязательно — частые `@>` по массивам/JSONB; не делай — для простых колонок.

## 4.3 GiST: сбалансированное дерево для геоданных и полнотекстового поиска

В подглаве 4.2 мы разобрали GIN — инвертированный индекс для массивов и JSONB. Теперь перейдём к **GiST** — более универсальному и сложному типу.

### Проблема: задачи, которые не решаются ни B-tree, ни GIN

Есть запросы, которые требуют **пространственных** или **иерархических** отношений:

```sql
-- Геоданные: найти места рядом с точкой
SELECT * FROM places 
WHERE location <-> point(37.6173, 55.7558) < 1000;  -- ближе 1 км

-- Пересечение диапазонов: найти брони, пересекающиеся с интервалом
SELECT * FROM reservations 
WHERE during && tsrange('2024-01-01', '2024-02-01');

-- Полнотекстовый поиск: найти статьи по словам
SELECT * FROM articles 
WHERE body_tsvector @@ to_tsquery('postgresql & indexing');
```

Что общего у этих задач?

- **Геоданные**: нужно искать **близость** (`<->`), **пересечение** (`&&`), **вхождение** (`@>`).
- **Диапазоны**: нужно искать **пересечение** интервалов (`&&`).
- **Полнотекстовый поиск**: нужно искать **вхождение слов** (`@@`).

Ни B-tree (одномерные ключи), ни GIN (инвертированный список) **не подходят** для этих операторов.

**Решение: GiST (Generalized Search Tree)** — обобщённое дерево поиска.

### Идея GiST: дерево предикатов

Вспомни B-tree (Глава 3): каждая страница хранит **ключи** (значения), а внутренние страницы — **разделители** (например, «значения ≤ 100 ищи слева»).

GiST работает **похоже**, но вместо ключей хранит **предикаты** — логические условия, описывающие **что находится в поддереве**.

```
B-TREE (Глава 3):                  GiST:
                                   
  Корень: [100] [500] [1000]       Корень: [bbox_1] [bbox_2] [bbox_3]
  «≤100 ищи в child1»              «bbox_1 покрывает все точки в child1»
                                   
  Лист: [42, TID] [50, TID]        Лист: [point(37.6, 55.7), TID]
                                     [point(37.7, 55.8), TID]
```

**Предикат** — это не точное значение, а **описание области**:

- Для геоданных: **bounding box** (ограничивающий прямоугольник) — «в этом поддереве все точки лежат внутри прямоугольника X».
- Для диапазонов: **интервал** — «в этом поддереве все диапазоны пересекаются с интервалом Y».
- Для полнотекстового поиска: **сигнатура слов** — «в этом поддереве есть слова A, B, C».

### Как GiST устроен физически

GiST хранится в **тех же 8-КБ страницах**, что и B-tree (Глава 2), но структура **другая**.

```
СТРАНИЦА GiST-ИНДЕКСА:

┌───────────────────────────────────────────────────────────┐
│ PageHeader (24 байта)                                     │
│ special = ... (GiST-специфичная метаинформация)           │
├───────────────────────────────────────────────────────────┤
│ ItemId Array                                             │
├───────────────────────────────────────────────────────────┤
│ GiST-кортежи:                                            │
│   Внутренняя страница:                                   │
│     [предикат: bbox(37.0..38.0, 55.0..56.0) → child]    │
│     [предикат: bbox(38.0..39.0, 55.0..56.0) → child]    │
│                                                          │
│   Листовая страница:                                     │
│     [ключ: point(37.61, 55.75), TID]                     │
│     [ключ: point(37.62, 55.76), TID]                     │
└───────────────────────────────────────────────────────────┘
```

**Ключевое отличие от B-tree:**

- B-tree: внутренние страницы хранят **точные ключи-разделители**.
- GiST: внутренние страницы хранят **предикаты** (области, bounding box'ы, сигнатуры).

**Поиск по GiST** — это спуск по дереву, где на каждом уровне проверяем, **может ли искомое быть в поддереве**:

```
ЗАПРОС: WHERE location <-> point(37.6, 55.7) < 10  (ближе 10 км)

ШАГ 1: Читаем корень (level=2)
  [bbox: 37.0..38.0, 55.0..56.0 → child=100]
  [bbox: 38.0..39.0, 55.0..56.0 → child=101]
  
  Точка (37.6, 55.7) попадает в bbox child=100? Да.
  Идём в child=100.

ШАГ 2: Читаем внутреннюю страницу (level=1)
  [bbox: 37.0..37.5, 55.0..55.5 → child=200]
  [bbox: 37.5..38.0, 55.5..56.0 → child=201]
  
  Точка (37.6, 55.7) попадает в child=201.
  Идём в child=201.

ШАГ 3: Читаем лист (level=0)
  [point(37.61, 55.75), TID(500,1)]
  [point(37.62, 55.76), TID(500,2)]
  ...
  
  Проверяем каждую точку: distance < 10?
  Да → читаем строку из таблицы.
```

### GiST для геоданных (PostGIS)

Самый частый сценарий GiST — **геоданные** через расширение **PostGIS**.

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE places (
    id SERIAL PRIMARY KEY,
    name TEXT,
    location GEOMETRY(Point, 4326)  -- WGS 84 (GPS-координаты)
);

-- GiST-индекс для геометрии
CREATE INDEX idx_places_location ON places USING GiST (location);
```

**Типичные запросы:**

```sql
-- Найти 10 ближайших мест к точке
SELECT name, location <-> point(37.6173, 55.7558) AS distance
FROM places
ORDER BY location <-> point(37.6173, 55.7558)
LIMIT 10;

-- Найти места внутри прямоугольника
SELECT * FROM places
WHERE location && ST_MakeEnvelope(37.0, 55.0, 38.0, 56.0, 4326);
```

**Как GiST ускоряет гео-запросы:**

1. Корень GiST хранит **bounding box** всего индекса.
2. Внутренние страницы — bounding box'ы своих поддеревьев.
3. При поиске точки PostgreSQL **спускается только в те поддеревья, чьи bbox'ы пересекаются с искомой областью**.

```
Весь мир: bbox(37.0..38.0, 55.0..56.0)
  ├── Север: bbox(37.0..38.0, 55.5..56.0)
  │   ├── Северо-запад: bbox(37.0..37.5, 55.5..56.0)
  │   └── Северо-восток: bbox(37.5..38.0, 55.5..56.0)
  └── Юг: bbox(37.0..38.0, 55.0..55.5)
      ├── Юго-запад: bbox(37.0..37.5, 55.0..55.5)
      └── Юго-восток: bbox(37.5..38.0, 55.5..55.5)  ← только сюда идём
```

Это похоже на B-tree, но **в двух измерениях**.

### GiST для диапазонов (типы range)

PostgreSQL имеет встроенные **range-типы**: `int4range`, `int8range`, `tsrange`, `daterange`.

```sql
CREATE TABLE reservations (
    id SERIAL PRIMARY KEY,
    room_id INT,
    during TSRANGE  -- диапазон времени
);

-- GiST-индекс для диапазонов
CREATE INDEX idx_reservations_during ON reservations USING GiST (during);

-- Найти брони, пересекающиеся с интервалом
SELECT * FROM reservations
WHERE during && tsrange('2024-01-01 10:00', '2024-01-01 12:00');
```

**Как GiST работает с диапазонами:**

- Каждый узел хранит **объединённый диапазон** (union) всех диапазонов в поддереве.
- При поиске пересечения PostgreSQL спускается только в поддеревья, чьи диапазоны **пересекаются** с искомым.

### GiST для полнотекстового поиска

GiST также может использоваться для **полнотекстового поиска** (tsvector/tsquery).

```sql
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    body TEXT,
    body_tsvector TSVECTOR
);

-- Обновляем tsvector
UPDATE articles SET body_tsvector = to_tsvector('english', body);

-- GiST-индекс для полнотекстового поиска
CREATE INDEX idx_articles_tsv ON articles USING GiST (body_tsvector);

-- Поиск
SELECT * FROM articles
WHERE body_tsvector @@ to_tsquery('postgresql & indexing');
```

**Но для полнотекстового поиска чаще используют GIN** — он быстрее для чтения, хотя и больше по размеру. Подробное сравнение — ниже.

### Сравнение: GIN vs GiST для полнотекстового поиска

| Аспект | GIN | GiST |
|:---|:---|:---|
| **Скорость поиска** | Быстрее (прямой доступ по слову) | Медленнее (спуск по дереву) |
| **Скорость вставки** | Медленнее (обновление posting lists) | Быстрее (просто добавляем лист) |
| **Размер индекса** | Больше (каждое слово + TID'ы) | Меньше (сжатие предикатов) |
| **Когда использовать** | Частые запросы, редкие вставки | Частые вставки, редкие запросы |

### 💡 Практика: когда использовать GiST

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Геоданные (PostGIS):**
   ```sql
   CREATE INDEX idx_places_location ON places USING GiST (location);
   ```
   Только GiST поддерживает геометрические операторы (`<->`, `&&`, `@>`).

2. **Диапазоны (range-типы):**
   ```sql
   CREATE INDEX idx_reservations_during ON reservations USING GiST (during);
   ```
   Проверка пересечений (`&&`) без GiST — это Seq Scan.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Полнотекстовый поиск, если вставки частые:**
   ```sql
   CREATE INDEX idx_articles_tsv ON articles USING GiST (body_tsvector);
   ```
   GiST быстрее на вставке, но медленнее на чтении. Если вставки редкие — лучше GIN.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для простых чисел и строк.** B-tree быстрее и меньше.

**❌ НЕ ДЕЛАЙ:**

5. **Не используй GiST, если не работаешь с гео/диапазонами/tsvector.** Для остального есть B-tree и GIN.

---

### Итог подглавы 4.3

- **GiST** — обобщённое дерево поиска: внутренние страницы хранят **предикаты** (bounding box'ы, диапазоны, сигнатуры).
- **Для геоданных** (PostGIS) — незаменим: ускоряет поиск близости и пересечений.
- **Для диапазонов** (range-типы) — ускоряет `&&`, `@>`, `<@`.
- **Для полнотекстового поиска** — альтернатива GIN: быстрее на вставке, медленнее на чтении.
- **Структура** — дерево предикатов в 8-КБ страницах, отличается от B-tree только содержимым внутренних страниц.
- **Практика:** обязательно — геоданные и диапазоны; не делай — для простых колонок.

## 4.4 BRIN: компактный индекс для огромных таблиц

В подглавах 4.2 и 4.3 мы разобрали GIN и GiST — индексы для специфических типов данных. Теперь рассмотрим **BRIN** — принципиально другой подход к индексированию.

### Проблема: B-tree слишком большой для огромных таблиц

Вспомни Главу 3: B-tree хранит **каждое значение** как отдельный ключ. Для таблицы на 100 ГБ с 1 млрд строк B-tree по `created_at` будет занимать **десятки гигабайт** и иметь высоту 4-5 уровней.

```
Таблица events: 1 млрд строк, 100 ГБ
B-tree индекс по created_at: ~30 ГБ (30% от таблицы!)
```

Это **дорого**: место на диске, время на вставку, память для кэша.

**Но есть наблюдение:** если данные в таблице **физически отсортированы** (например, events пишутся в хронологическом порядке), то значения `created_at` **коррелируют** с номерами страниц.

```
Страница 0:    created_at = 2024-01-01 00:00 .. 2024-01-01 00:15
Страница 1:    created_at = 2024-01-01 00:15 .. 2024-01-01 00:30
Страница 2:    created_at = 2024-01-01 00:30 .. 2024-01-01 00:45
...
Страница 1000: created_at = 2024-01-02 00:00 .. 2024-01-02 00:15
```

**Вопрос:** зачем хранить **каждое значение**, если можно хранить **диапазон для группы страниц**?

**Ответ:** это и есть **BRIN (Block Range Index)**.

### Идея BRIN: диапазоны блоков

BRIN хранит **не каждое значение**, а **минимальное и максимальное значение для группы страниц** (range).

```
Обычная таблица (events):

  Страницы 0-127:    created_at от '2024-01-01 00:00' до '2024-01-01 02:00'
  Страницы 128-255:  created_at от '2024-01-01 02:00' до '2024-01-01 04:00'
  Страницы 256-383:  created_at от '2024-01-01 04:00' до '2024-01-01 06:00'
  ...

BRIN-индекс:

  Диапазон 1 (страницы 0-127):    min='2024-01-01 00:00', max='2024-01-01 02:00'
  Диапазон 2 (страницы 128-255):  min='2024-01-01 02:00', max='2024-01-01 04:00'
  Диапазон 3 (страницы 256-383):  min='2024-01-01 04:00', max='2024-01-01 06:00'
  ...
```

**Размер BRIN-индекса — крошечный** по сравнению с B-tree:

```
Таблица events: 1 млрд строк, 100 ГБ
B-tree: ~30 ГБ
BRIN:   ~10-50 МБ (в 1000 раз меньше!)
```

### Как BRIN работает при поиске

Запрос:

```sql
SELECT * FROM events 
WHERE created_at = '2024-01-01 05:30';
```

**Как BRIN обслуживает этот запрос:**

```
BRIN-индекс:

  Диапазон 1: min=00:00, max=02:00 → 05:30 НЕ попадает → пропускаем
  Диапазон 2: min=02:00, max=04:00 → 05:30 НЕ попадает → пропускаем
  Диапазон 3: min=04:00, max=06:00 → 05:30 ПОПАДАЕТ → читаем страницы 256-383!

BRIN не даёт точный TID, он даёт ДИАПАЗОН СТРАНИЦ.
PostgreSQL читает эти страницы и фильтрует по created_at = '05:30'.
```

**Важное отличие от B-tree:**

- B-tree: «значение 42 лежит в странице 500, слот 15» → читаем **одну** страницу.
- BRIN: «значение 42 где-то в страницах 256-383» → читаем **128 страниц** и фильтруем.

BRIN **менее точен**, но **во много раз меньше**. Для коррелированных данных эта неточность окупается.

### Внутренняя структура BRIN

BRIN хранится в **тех же 8-КБ страницах** (Глава 2), но структура **очень простая**.

```
СТРАНИЦА BRIN-ИНДЕКСА:

┌───────────────────────────────────────────────────────────┐
│ PageHeader (24 байта)                                     │
├───────────────────────────────────────────────────────────┤
│ Резюме (summaries) — по одному на диапазон блоков:        │
│                                                          │
│   Диапазон 1: страницы 0-127                             │
│     min_created_at = '2024-01-01 00:00'                  │
│     max_created_at = '2024-01-01 02:00'                  │
│                                                          │
│   Диапазон 2: страницы 128-255                           │
│     min_created_at = '2024-01-01 02:00'                  │
│     max_created_at = '2024-01-01 04:00'                  │
│                                                          │
│   ...                                                    │
└───────────────────────────────────────────────────────────┘
```

**Параметр `pages_per_range`** определяет, сколько страниц таблицы покрывает один диапазон:

```sql
-- По умолчанию: 128 страниц на диапазон
CREATE INDEX idx_events_date ON events USING BRIN (created_at);

-- Явно: 32 страницы на диапазон (точнее, но индекс больше)
CREATE INDEX idx_events_date_32 ON events USING BRIN (created_at)
    WITH (pages_per_range = 32);

-- Явно: 512 страниц на диапазон (компактнее, но менее точно)
CREATE INDEX idx_events_date_512 ON events USING BRIN (created_at)
    WITH (pages_per_range = 512);
```

**Как выбрать `pages_per_range`:**

| Значение | Точность | Размер индекса | Когда |
|:---|:---|:---|:---|
| 32 | Высокая (меньше страниц читать) | Больше | Данные слабо коррелированы |
| 128 (дефолт) | Средняя | Средний | Обычный случай |
| 512 | Низкая (много страниц фильтровать) | Меньше | Данные сильно коррелированы |

### Когда BRIN работает хорошо, а когда плохо

**✅ Работает хорошо:**

```
Данные коррелированы с физическим порядком:

  INSERT INTO events(created_at, ...) VALUES (now(), ...);
  -- Вставки всегда в конец → страницы физически отсортированы по времени
```

**❌ Работает плохо:**

```
Данные случайны:

  INSERT INTO users(email, ...) VALUES ('a' || random(), ...);
  -- Значения email разбросаны по всем страницам
  -- Каждый диапазон будет: min='a...', max='z...' (весь алфавит)
  -- BRIN не сможет отсечь ни один диапазон → прочитает всю таблицу
```

### Event Sourcing: идеальный кейс для BRIN

**Event Sourcing** — паттерн, где таблица событий — это append-only журнал: только `INSERT`, без `UPDATE` и `DELETE`.

```sql
CREATE TABLE events (
    event_id UUID DEFAULT gen_random_uuid(),
    aggregate_id UUID NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB,
    created_at TIMESTAMPTZ DEFAULT now()
);
```

**Почему BRIN идеален здесь:**

1. **Вставки всегда в конец** → `created_at` монотонно растёт → идеальная корреляция.
2. **Запросы по времени** → «дай события за период» → BRIN отсекает ненужные диапазоны.
3. **Таблица огромная** → B-tree был бы десятки гигабайт, BRIN — мегабайты.

```
Запрос: дай события за 2024-01-15

BRIN-индекс:
  Диапазон 1: 2024-01-01 .. 2024-01-02  → не попадает
  Диапазон 2: 2024-01-02 .. 2024-01-03  → не попадает
  ...
  Диапазон 14: 2024-01-14 .. 2024-01-16 → ПОПАДАЕТ → читаем эти страницы

Читаем только те страницы, где лежат события за нужный день.
```

### Можно ли отказаться от PRIMARY KEY?

**Да, в event sourcing можно.**

Обычная таблица:

```sql
CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,  -- B-tree индекс ~20-30 ГБ для 1 млрд строк
    ...
);
```

Event sourcing без PRIMARY KEY:

```sql
CREATE TABLE events (
    event_id UUID DEFAULT gen_random_uuid(),
    ...
);
-- Нет PRIMARY KEY → нет огромного B-tree
-- Экономия: 20-30 ГБ дискового пространства
```

**Когда можно отказаться от PRIMARY KEY:**

| Аспект | Оставить PRIMARY KEY | Убрать PRIMARY KEY |
|:---|:---|:---|
| Поиск по id | ✅ Быстро | ❌ Seq Scan |
| Гарантия уникальности | ✅ | ❌ |
| UPDATE/DELETE по id | ✅ | ❌ (но их нет в event sourcing) |
| Вставка | Медленнее (B-tree) | **Быстрее** (без B-tree) |
| Размер | +20-30 ГБ | **Экономия** |

**Но нужна идемпотентность** — чтобы не вставить одно событие дважды. Решения:

```sql
-- Вариант 1: Уникальный индекс по event_id (UUID)
CREATE UNIQUE INDEX idx_events_event_id ON events(event_id);
-- Тоже B-tree, но по UUID (16 байт) — меньше, чем по BIGSERIAL (8 байт)

-- Вариант 2: Проверка на стороне приложения
-- Прочитать, есть ли событие с таким event_id, потом вставить

-- Вариант 3: Хранить обработанные event_id в отдельной компактной таблице
```

### Рекомендуемая схема для event sourcing

```sql
CREATE TABLE events (
    event_id UUID DEFAULT gen_random_uuid(),
    aggregate_id UUID NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB,
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 1. BRIN по created_at — для чтения по времени (основной сценарий)
CREATE INDEX idx_events_created_at ON events USING BRIN (created_at)
    WITH (pages_per_range = 64);  -- точнее для событий за короткий период

-- 2. BRIN по aggregate_id — для чтения событий конкретного агрегата
--    (работает, если события одного агрегата пишутся рядом)
CREATE INDEX idx_events_aggregate ON events USING BRIN (aggregate_id);

-- 3. Уникальный индекс для идемпотентности
CREATE UNIQUE INDEX idx_events_event_id ON events(event_id);
-- Этот индекс будет B-tree, но это плата за гарантию уникальности

-- 4. GIN по payload — если часто ищешь по содержимому событий
CREATE INDEX idx_events_payload ON events USING GIN (payload);
```

### Сравнение: B-tree vs BRIN для коррелированных данных

| Аспект | B-tree | BRIN |
|:---|:---|:---|
| **Точность** | Точный TID → читает 1 страницу | Диапазон страниц → читает 128 |
| **Размер** | ~30% от таблицы | **~0.01% от таблицы** |
| **Скорость вставки** | Медленнее (обновление дерева) | **Быстрее** (просто обновить min/max) |
| **Память (кэш)** | Может не влезать в shared_buffers | **Всегда влезает** |
| **Когда** | Точный точечный поиск | Огромные таблицы, корреляция |

### Практический пример: насколько BRIN меньше

```
Таблица events:
  1 млрд строк
  created_at: timestamp (8 байт)
  Размер таблицы: ~80 ГБ

B-tree по created_at:
  Ключ: 8 байт + TID 6 байт = ~14 байт на запись
  1 млрд записей × 14 байт ≈ 14 ГБ
  Плюс внутренние страницы: ~20 ГБ итого

BRIN по created_at:
  pages_per_range = 128
  1 млрд строк / 80 строк на страницу = 12.5 млн страниц
  12.5 млн / 128 = ~98 000 диапазонов
  Каждый диапазон: min+max = 16 байт + заголовок ~8 байт = ~24 байта
  98 000 × 24 байта ≈ 2.4 МБ

ИТОГ:
  B-tree: ~20 ГБ
  BRIN:   ~2.4 МБ
  BRIN в 8 000 раз меньше!
```

### 💡 Практика: когда использовать BRIN

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Огромные таблицы (100+ ГБ) с коррелированными данными:**
   ```sql
   -- Логи, события, метрики — пишутся в конец
   CREATE INDEX idx_events_created_at ON events USING BRIN (created_at);
   ```

2. **Event sourcing** — append-only таблица событий, где `created_at` монотонно растёт.

3. **Когда B-tree не влезает в shared_buffers:**
   BRIN всегда влезает — его размер крошечный.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Когда вставки идут быстрее, чем B-tree успевает обновляться:**
   BRIN обновляется быстрее — это просто min/max.

5. **Отказаться от PRIMARY KEY в append-only таблицах** — экономия 20-30 ГБ на индекс.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Для маленьких таблиц (< 1 ГБ).** B-tree точнее и не сильно больше.

**❌ НЕ ДЕЛАЙ:**

7. **Не используй BRIN для случайных данных** (email, UUID). Каждый диапазон будет покрывать весь спектр значений — BRIN бесполезен.

### Как понять по метрикам, что BRIN подходит

**Метрика 1: Корреляция данных**

```sql
SELECT correlation
FROM pg_stats
WHERE tablename = 'events' AND attname = 'created_at';
```

| correlation | Что означает | Что делать |
|:---|:---|:---|
| 1.0 | Идеальная корреляция | BRIN идеален |
| 0.7-1.0 | Хорошая корреляция | BRIN хорош |
| 0.3-0.7 | Средняя | Может быть BRIN или B-tree |
| 0.0-0.3 | Слабая | B-tree или GIN |

**Метрика 2: Размер B-tree**

```sql
SELECT pg_size_pretty(pg_relation_size('idx_events_created_at_btree')) AS btree_size;
```

Если B-tree > 10 ГБ — BRIN может быть лучше.

**Метрика 3: Проверка после создания**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE created_at = '2024-01-01 05:30';
```

| Метрика | B-tree | BRIN |
|:---|:---|:---|
| Чтений страниц | 4 | 128+ (диапазон) |
| Размер индекса | 20 ГБ | 2.4 МБ |
| Время | < 1 мс | 5-20 мс (больше чтений) |

BRIN **медленнее** на точечных запросах, но **радикально меньше** по размеру. Для больших таблиц, которые не влезают в кэш, BRIN может быть **быстрее** просто потому, что его страницы всегда в памяти.

### Итог подглавы 4.4

- **BRIN** — индекс диапазонов блоков: хранит min/max для групп страниц, а не каждое значение.
- **Размер** — в тысячи раз меньше B-tree (мегабайты вместо гигабайт).
- **Точность** — ниже: вместо TID даёт диапазон страниц, которые нужно прочитать и отфильтровать.
- **Работает хорошо** — для коррелированных данных (логи, события, метрики).
- **Идеальный кейс** — event sourcing: append-only, монотонный `created_at`, огромные объёмы.
- **Можно отказаться от PRIMARY KEY** — экономия 20-30 ГБ, если не нужен поиск по id.
- **pages_per_range** — параметр точности: 32 (точнее), 128 (дефолт), 512 (компактнее).
- **Практика:** обязательно — огромные таблицы с корреляцией и event sourcing; не делай — случайные данные, маленькие таблицы.

## 4.5 Hash: точечный поиск по равенству

В подглавах 4.2-4.4 мы разобрали GIN, GiST и BRIN — специализированные индексы для массивов, геоданных и огромных таблиц. Теперь рассмотрим **Hash** — самый простой из не-B-tree индексов.

### Проблема: B-tree избыточен для простого равенства

Вспомни Главу 3: B-tree хранит ключи **отсортированными**. Это даёт:

- Точечный поиск `=` — O(log N)
- Диапазоны `BETWEEN`, `<`, `>` — O(log N + M)
- Сортировку `ORDER BY` — бесплатно

Но что, если запрос использует **только** равенство?

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

Для этого не нужна сортировка, не нужны диапазоны. Нужен только **быстрый точечный поиск по равенству**.

**Hash-индекс** решает ровно эту задачу — и **ничего больше**.

### Как работает Hash-индекс

Hash-индекс использует **хэш-функцию**: преобразует значение ключа в число, которое определяет, в какой «корзине» (bucket) искать.

```
Хэш-функция: hash('alice@example.com') = 42

Hash-индекс:
  Bucket 42 → TID(0,1)
  Bucket 99 → TID(0,2)
  ...
```

**Поиск `email = 'alice@example.com'`:**

1. Вычисляем `hash('alice@example.com')` = 42.
2. Идём в bucket 42.
3. Получаем TID.
4. Читаем строку из таблицы.

**Сложность:** O(1) — **быстрее**, чем B-tree (O(log N))!

Но **только для `=`**. Hash не поддерживает:

- `BETWEEN`, `<`, `>`, `<=`, `>=`
- `ORDER BY` с использованием индекса
- Составные ключи (частично)

### Почему Hash долго был «второсортным»

Исторически Hash-индекс в PostgreSQL **не рекомендовали**:

| Проблема | До PostgreSQL 10 | После PostgreSQL 10 |
|:---|:---|:---|
| Не журналировался в WAL | ❌ Не восстанавливался после сбоя | ✅ Полностью WAL-логируется |
| Не реплицировался | ❌ | ✅ |
| Размер | Больше B-tree | **Меньше B-tree** |
| Скорость | Не быстрее B-tree | **Быстрее на `=`** |

Начиная с **PostgreSQL 10**, Hash-индекс стал полноценным гражданином. Но **привычка** «не использовать Hash» осталась.

### Сравнение: B-tree vs Hash для точечного поиска

```sql
-- B-tree (дефолт)
CREATE INDEX idx_users_email_btree ON users(email);

-- Hash
CREATE INDEX idx_users_email_hash ON users USING HASH (email);
```

| Аспект | B-tree | Hash |
|:---|:---|:---|
| **`=`** | O(log N) — 3-4 чтения | **O(1) — 1-2 чтения** |
| **`BETWEEN`, `<`, `>`** | ✅ Поддерживает | ❌ Не поддерживает |
| **`ORDER BY`** | ✅ Бесплатно | ❌ Требует сортировку |
| **Размер** | ~30% от таблицы | **~20% от таблицы** |
| **Вставка** | O(log N) | **O(1)** |
| **Составной** | ✅ | ✅ (с PostgreSQL 10+) |
| **UNIQUE** | ✅ | ❌ |

**Вывод:** для **чистого точечного поиска** Hash быстрее и компактнее. Но B-tree универсальнее.

### Внутренняя структура Hash-индекса

Hash-индекс хранится в **тех же 8-КБ страницах** (Глава 2), но организован как **хэш-таблица**.

```
СТРАНИЦА HASH-ИНДЕКСА:

┌───────────────────────────────────────────────────────────┐
│ PageHeader (24 байта)                                     │
├───────────────────────────────────────────────────────────┤
│ Bucket 0: [hash=0, TID(0,1)] [hash=256, TID(0,5)]        │
│ Bucket 1: [hash=1, TID(0,2)]                             │
│ Bucket 2: [hash=2, TID(0,3)] [hash=514, TID(0,6)]        │
│ ...                                                       │
└───────────────────────────────────────────────────────────┘
```

**Коллизии** — когда два разных значения дают один hash — решаются помещением обоих в один bucket. При поиске PostgreSQL проверяет **реальное значение** (не только hash), чтобы исключить ложные совпадения.

### 💡 Практика: когда использовать Hash

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Точечный поиск по UUID или email, где не нужен диапазон:**
   ```sql
   CREATE INDEX idx_sessions_token ON sessions USING HASH (token);
   SELECT * FROM sessions WHERE token = '...';
   ```

**👍 СТОИТ СДЕЛАТЬ:**

2. **Когда B-tree не влезает в кэш, а Hash влезает** — Hash меньше на ~30%.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

3. **Если запросы могут расшириться** (добавится BETWEEN или ORDER BY). B-tree универсальнее.

**❌ НЕ ДЕЛАЙ:**

4. **Не используй Hash для UNIQUE** — PostgreSQL не поддерживает уникальные Hash-индексы.

5. **Не используй Hash, если колонка в ORDER BY** — Hash не сохраняет порядок.

### Итог подглавы 4.5

- **Hash** — индекс на основе хэш-таблицы: O(1) для `=`.
- **Поддерживает только `=`** — нет диапазонов, нет сортировки.
- **Размер** — меньше B-tree (~20% от таблицы).
- **Вставка** — быстрее (O(1) против O(log N)).
- **Не поддерживает UNIQUE**.
- **Полноценен с PostgreSQL 10+** (WAL, репликация).
- **Практика:** используй для чистого точечного поиска; не делай — если нужны диапазоны, сортировка или уникальность.

## 4.6 Практика Go: выбор типа индекса

В предыдущих подглавах мы разобрали пять типов индексов. Теперь напишем **утилиту на Go**, которая анализирует таблицы и **подсказывает, какой тип индекса нужен**.

### Что будет утилита

Утилита `index-advisor` подключается к базе, анализирует:

- Статистику по колонкам (`pg_stats`)
- Существующие индексы (`pg_indexes`)
- Частоту запросов (`pg_stat_statements`)

И выводит рекомендации:

```
=== РЕКОМЕНДАЦИИ ПО ИНДЕКСАМ ===

Таблица events:
  Колонка created_at: корреляция 0.99
    → Рекомендация: BRIN (огромная таблица, коррелированные данные)
  Колонка payload (JSONB): частые @> запросы
    → Рекомендация: GIN

Таблица places:
  Колонка location (geometry): частые <-> запросы
    → Рекомендация: GiST

Таблица sessions:
  Колонка token (UUID): только точечный поиск =
    → Рекомендация: Hash или B-tree
```

### Полный код

```go
package main

import (
	"database/sql"
	"fmt"
	"log"
	"os"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type ColumnStats struct {
	Table       string
	Column      string
	DataType    string
	Correlation float64
	NullFrac    float64
}

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	fmt.Println("=== РЕКОМЕНДАЦИИ ПО ИНДЕКСАМ ===\n")

	// Анализируем колонки с высокой корреляцией (для BRIN)
	brinCandidates := findBrinCandidates(db)
	if len(brinCandidates) > 0 {
		fmt.Println("BRIN-КАНДИДАТЫ (корреляция > 0.7):")
		for _, c := range brinCandidates {
			fmt.Printf("  %s.%s: корреляция %.2f\n", c.Table, c.Column, c.Correlation)
		}
		fmt.Println()
	}

	// Анализируем JSONB-колонки (для GIN)
	jsonbCandidates := findJsonbCandidates(db)
	if len(jsonbCandidates) > 0 {
		fmt.Println("GIN-КАНДИДАТЫ (JSONB):")
		for _, c := range jsonbCandidates {
			fmt.Printf("  %s.%s\n", c.Table, c.Column)
		}
		fmt.Println()
	}

	// Анализируем гео-колонки (для GiST)
	gistCandidates := findGistCandidates(db)
	if len(gistCandidates) > 0 {
		fmt.Println("GiST-КАНДИДАТЫ (geometry/geography):")
		for _, c := range gistCandidates {
			fmt.Printf("  %s.%s\n", c.Table, c.Column)
		}
		fmt.Println()
	}
}

// findBrinCandidates находит колонки с высокой корреляцией
func findBrinCandidates(db *sql.DB) []ColumnStats {
	query := `
	SELECT 
		tablename,
		attname,
		data_type,
		correlation,
		null_frac
	FROM pg_stats
	WHERE correlation > 0.7
	  AND null_frac < 0.5
	  AND data_type IN ('timestamp', 'timestamptz', 'date', 'integer', 'bigint')
	ORDER BY correlation DESC
	LIMIT 10;`

	return queryColumns(db, query)
}

// findJsonbCandidates находит JSONB-колонки
func findJsonbCandidates(db *sql.DB) []ColumnStats {
	query := `
	SELECT 
		tablename,
		attname,
		data_type,
		0 AS correlation,
		null_frac
	FROM pg_stats
	WHERE data_type = 'jsonb'
	  AND null_frac < 0.5
	LIMIT 10;`

	return queryColumns(db, query)
}

// findGistCandidates находит геометрические колонки
func findGistCandidates(db *sql.DB) []ColumnStats {
	query := `
	SELECT 
		tablename,
		attname,
		data_type,
		0 AS correlation,
		null_frac
	FROM pg_stats
	WHERE data_type IN ('geometry', 'geography', 'point', 'polygon')
	  AND null_frac < 0.5
	LIMIT 10;`

	return queryColumns(db, query)
}

// queryColumns — вспомогательная функция
func queryColumns(db *sql.DB, query string) []ColumnStats {
	rows, err := db.Query(query)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()

	var columns []ColumnStats
	for rows.Next() {
		var c ColumnStats
		var dataType string
		if err := rows.Scan(&c.Table, &c.Column, &dataType, &c.Correlation, &c.NullFrac); err != nil {
			log.Fatal(err)
		}
		c.DataType = dataType
		columns = append(columns, c)
	}
	return columns
}
```

### Как это работает

1. **BRIN-кандидаты** — колонки с `correlation > 0.7` в `pg_stats`. Это значит, данные физически отсортированы → BRIN будет эффективен.

2. **GIN-кандидаты** — колонки типа `jsonb`. Для них GIN — стандартный выбор.

3. **GiST-кандидаты** — колонки типа `geometry`, `geography`, `point`. Для них GiST — единственный вариант.

### Запуск

```bash
export DATABASE_URL="postgres://alice@localhost/mydb"
go run index-advisor.go
```

### Пример вывода

```
=== РЕКОМЕНДАЦИИ ПО ИНДЕКСАМ ===

BRIN-КАНДИДАТЫ (корреляция > 0.7):
  events.created_at: корреляция 0.99
  events.aggregate_id: корреляция 0.85

GIN-КАНДИДАТЫ (JSONB):
  events.payload

GiST-КАНДИДАТЫ (geometry/geography):
  places.location
```

### Связь с предыдущими подглавами

- **4.2 GIN** — утилита находит JSONB для GIN.
- **4.3 GiST** — утилита находит гео-колонки для GiST.
- **4.4 BRIN** — утилита находит коррелированные колонки для BRIN.
- **4.5 Hash** — утилита не находит Hash автоматически (нужен анализ запросов).

## 4.7 Выводы и типичные ошибки

**Что мы узнали?**

PostgreSQL поддерживает шесть типов индексов, каждый со своей специализацией:

- **B-tree** — универсальный: числа, строки, даты, диапазоны, сортировка.
- **Hash** — только `=`, самый быстрый точечный поиск.
- **GIN** — массивы, JSONB, полнотекстовый поиск.
- **GiST** — геоданные, диапазоны, полнотекстовый поиск.
- **BRIN** — огромные таблицы с коррелированными данными.
- **SP-GiST** — специальные структуры (точки, IP-адреса).

Все типы хранятся в **тех же 8-КБ страницах** (Глава 2), живут в `shared_buffers` (Глава 1) и создаются через `CREATE INDEX` (Глава 3).

**Типичные ошибки:**

- ❌ **Использовать B-tree для массивов и JSONB.** B-tree не понимает `@>`, `&&`. Нужен GIN.
- ❌ **Использовать B-tree для геоданных.** B-tree не понимает `<->`, `&&`. Нужен GiST.
- ❌ **Использовать B-tree для огромных коррелированных таблиц.** B-tree будет 30% от таблицы. BRIN — 0.01%.
- ❌ **Использовать Hash для диапазонов.** Hash поддерживает только `=`.
- ❌ **Использовать GIN для простых колонок.** B-tree быстрее и меньше.
- ❌ **Держать PRIMARY KEY в event sourcing таблицах.** Если нет поиска по id — PRIMARY KEY не нужен, экономия 20-30 ГБ.

---

## 4.8 Для быстрого повторения

- **B-tree** — универсальный: `=`, `BETWEEN`, `ORDER BY`. Дефолтный тип.
- **Hash** — только `=`. O(1). Меньше B-tree. Не поддерживает UNIQUE. Полноценен с PG 10+.
- **GIN** — массивы и JSONB: `@>`, `<@`, `&&`. Инвертированный: «элемент → TID'ы».
- **GiST** — геоданные и диапазоны: `<->`, `&&`. Дерево предикатов (bbox'ы).
- **BRIN** — огромные коррелированные таблицы. Хранит min/max для групп страниц. В 1000 раз меньше B-tree.
- **SP-GiST** — точки, IP-адреса. Дерево разбиения пространства.
- **Event sourcing** — BRIN по `created_at`, отказ от PRIMARY KEY, уникальный индекс по `event_id` для идемпотентности.

## 4.10 Ответы

### Ответ 1

B-tree хранит **одно значение** как ключ. Массив — это **много значений** в одной строке. B-tree не может «разложить» массив на элементы и индексировать каждый отдельно. Для поиска по массивам нужен **GIN** — инвертированный индекс, который хранит «элемент → список TID'ов».

### Ответ 2

GIN хранит **ключи** (элементы массива или JSON) и **posting lists** (списки TID'ов строк, содержащих этот элемент). **Инвертированный** — потому что отношение «перевёрнуто»: не «строка → элементы», а «элемент → строки». **Posting list** — это список TID'ов строк, где встречается элемент.

### Ответ 3

| Оператор | Значение |
|:---|:---|
| `@>` | Содержит все элементы |
| `<@` | Содержится в |
| `&&` | Пересекается (хотя бы один общий) |

### Ответ 4

GIN извлекает ключи и значения из JSONB и формирует составные ключи:

```
"type=purchase" → TID
"user_id=42"    → TID
```

### Ответ 5

B-tree хранит в внутренних страницах **точные ключи-разделители** (например, «значения ≤ 100»). GiST хранит **предикаты** — логические описания областей (например, bounding box для геоданных: «все точки в этом поддереве лежат внутри прямоугольника X»).

### Ответ 6

GiST незаменим для:

- **Геоданных** (PostGIS) — операторы `<->`, `&&`, `@>`
- **Диапазонов** (range-типы) — оператор `&&`

B-tree не подходит, потому что не понимает геометрические операторы и пересечения диапазонов.

### Ответ 7

| Аспект | GIN | GiST |
|:---|:---|:---|
| Чтение | Быстрее | Медленнее |
| Вставка | Медленнее | Быстрее |
| Размер | Больше | Меньше |

**GIN** — для частых запросов, редких вставок. **GiST** — для частых вставок, редких запросов.

### Ответ 8

BRIN хранит **min/max для группы страниц** (range), а не каждое значение. Для таблицы с 1 млрд строк: B-tree хранит 1 млрд ключей (~20 ГБ), BRIN хранит ~98 000 диапазонов (~2.4 МБ).

### Ответ 9

`pages_per_range` — сколько страниц таблицы покрывает один диапазон BRIN. Меньше значение → точнее, но индекс больше. Дефолт: 128. Для слабо коррелированных данных — 32. Для сильно коррелированных — 512.

### Ответ 10

Event sourcing — append-only таблица, `created_at` монотонно растёт → идеальная корреляция. BRIN отсекает ненужные диапазоны при поиске по времени. От PRIMARY KEY можно отказаться, если нет поиска по id и нет UPDATE/DELETE по id. Экономия: 20-30 ГБ на индекс.

### Ответ 11

Hash поддерживает **только `=`**. Не поддерживает `BETWEEN`, `<`, `>`, `ORDER BY`. Долго не рекомендовали, потому что до PostgreSQL 10 не журналировался в WAL и не реплицировался. С PG 10 — полноценный.

### Ответ 12

| Задача | Тип индекса |
|:---|:---|
| Массив тегов | **GIN** |
| Геоданные | **GiST** |
| Коррелированная таблица событий | **BRIN** |
| Точечный поиск по UUID | **Hash** (или B-tree) |

## 4.11 Куда идти дальше?

Мы разобрали все типы индексов в PostgreSQL. Но индекс — это только **инструмент**, который планировщик может использовать или не использовать.

Следующий логический шаг — **понять, как планировщик решает, какой индекс выбрать**:

- Почему иногда выбирается Seq Scan вместо Index Scan?
- Как статистика (`pg_stats`) влияет на выбор?
- Что такое cardinality и selectivity?
- Как читать `EXPLAIN` и понимать стоимость операций?

**Глава 7: Планировщик запросов — почему один и тот же запрос то летает, то ползает.**

Но перед этим нам нужно разобрать **MVCC** (Глава 5) — как PostgreSQL обеспечивает конкурентный доступ, и **VACUUM** (Глава 6) — как борется с раздуванием. Потому что планировщик опирается на статистику, которую собирает VACUUM, а видимость строк определяется через MVCC.
