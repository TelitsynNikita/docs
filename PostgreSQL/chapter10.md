## 10.0 Пролог: тип данных, который всё замедлил

Ты спроектировал таблицу:

```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id VARCHAR(255),     -- ❌ должно быть BIGINT
    total VARCHAR(50),        -- ❌ должно быть NUMERIC
    created_at VARCHAR(100)   -- ❌ должно быть TIMESTAMPTZ
);
```

**Почему это проблема?**

### 1. Сравнение строк медленнее, чем чисел

```sql
-- VARCHAR: сравнение строк — O(длина строки)
WHERE user_id = '42';

-- BIGINT: сравнение чисел — O(1)
WHERE user_id = 42;
```

### 2. Строки занимают больше места

```
BIGINT: 8 байт.
VARCHAR: '42' → ~20 байт.

При 10 млн строк:
  BIGINT: 80 МБ
  VARCHAR: 200 МБ — в 2.5 раза больше!
```

### 3. Нет проверки типов

```sql
INSERT INTO orders (user_id) VALUES ('абвгд');  -- VARCHAR позволит!
INSERT INTO orders (user_id) VALUES ('абвгд');  -- BIGINT: ОШИБКА!
```

### 4. Ломает сортировку и агрегацию

```sql
'2024-01-2' < '2024-01-12'  -- '2' < '1' в строковом сравнении!
```

### Что это даёт в связке с предыдущими главами

- **Размер таблицы** → больше страниц → больше чтений Seq Scan (Глава 9).
- **Размер индексов** → B-tree больше → выше дерево (Глава 3).
- **Сравнение строк** → медленнее JOIN'ы (Глава 9).
- **Неправильные типы** → мусорные данные → ошибки в приложении.

## 10.1 Числовые типы: smallint, integer, bigint, numeric, real, double precision, money

### Начальные данные

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    quantity INT,
    price NUMERIC(10,2),
    discount REAL,
    weight DOUBLE PRECISION,
    revenue NUMERIC(12,2)
);
```

---

### smallint

**Определение:** целое число фиксированного размера **2 байта**.

```
Диапазон: от -32 768 до 32 767
Размер: всегда 2 байта
```

**Когда использовать:** возраст, коды статусов, количество попыток.

**Когда НЕ использовать:** количество товаров (может превысить 32 767), ID.

---

### integer (int)

**Определение:** целое число фиксированного размера **4 байта**.

```
Диапазон: от -2 147 483 648 до 2 147 483 647
Размер: всегда 4 байта
```

**Когда использовать:** стандартный выбор для целых.

**Когда НЕ использовать:** если таблица вырастет > 2.1 млрд строк → bigint.

---

### bigint

**Определение:** целое число фиксированного размера **8 байт**.

```
Диапазон: ±9.2 квинтиллиона
Размер: всегда 8 байт
```

**Когда использовать:** event sourcing, большие ID, внешние ID.

**Практическое следствие:** B-tree по bigint на 43% больше, чем по integer.

---

### numeric / decimal

**Определение:** **точное** дробное число с указанной точностью.

```
numeric(10, 2): 10 цифр всего, 2 после запятой
```

**Размер: переменный** — зависит от числа.

**Как хранится:** base-10000, 4 цифры = 2 байта.

```
Число 123.45:
  Группа [123]: 2 байта
  Группа [4500]: 2 байта
  Заголовок: 8 байт
  Итого: 12 байт

Формула: 8 байт + 2 байта × ceil(количество_цифр / 4)
```

**Когда использовать:** **деньги — всегда numeric!**

---

### real / double precision

**Определение:** числа с плавающей точкой (IEEE 754). **Приблизительные!**

| Тип | Размер | Точность |
|:---|:---|:---|
| `real` | 4 байта | ~7 значащих цифр |
| `double precision` | 8 байт | ~15 значащих цифр |

**Почему приблизительные:**

```sql
SELECT 0.1::DOUBLE PRECISION + 0.2::DOUBLE PRECISION;
-- 0.30000000000000004 (НЕ 0.3!)
```

**Когда использовать:** метрики, аналитика. **Никогда для денег.**

---

### money

**Определение:** денежный тип, привязанный к валюте базы.

**Проблемы:**

- Одна валюта на базу.
- Деление округляет.
- Не для мультивалютных систем.

**Рекомендация:** не использовать. Вместо — `numeric(10,2)` + `currency CHAR(3)`.

---

### serial vs identity

**SERIAL** — псевдоним: INTEGER + SEQUENCE + DEFAULT.

**IDENTITY** — современный стандарт (SQL-стандарт).

**Почему IDENTITY лучше:**

| Аспект | SERIAL | IDENTITY |
|:---|:---|:---|
| DROP TABLE | Sequence остаётся | Удаляется вместе |
| TRUNCATE | Не сбрасывается | `RESTART IDENTITY` |
| Случайная вставка id | Разрешена | Запрещена |
| Копирование таблицы | Sequence не копируется | Копируется |
| Рекомендация | Для старых проектов | **Для новых** |

---

### 💡 Практика: числовые типы

**✅ ОБЯЗАТЕЛЬНО:**

1. **Деньги — `numeric(10,2)` или `numeric(20,2)`** + `currency`.
2. **Целые по умолчанию — `integer`.**
3. **Большие ID — `bigint`.**
4. **Автоинкремент — `IDENTITY`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `real`/`double` для денег.**
6. **Не используй `money`.**
7. **Не используй `VARCHAR` для чисел.**

## 10.2 Строковые типы: text, varchar, char, bytea

### text

**Определение:** строковый тип **без ограничения длины** (до ~1 ГБ).

**Размер:** переменный — `5 байт заголовок + длина строки`.

**Когда использовать:** по умолчанию для строк.

**Проблема:** text без ограничения — дыра. Хакер может вставить 100 МБ.

**Решение:** `text` + `CHECK (length(col) <= n)`.

---

### varchar(n)

**Определение:** строковый тип с ограничением длины до n.

**Миф:** varchar(n) быстрее или компактнее, чем text. **Это не так.**

```
'Hello' в text:          10 байт
'Hello' в varchar(255):  10 байт
```

**Когда использовать:** стандартные поля с известным лимитом (email, phone).

---

### text + CHECK vs varchar(n)

**Сценарий:** через год бизнес изменил лимит.

**varchar(255) → varchar(320):**

```sql
ALTER TABLE users ALTER COLUMN email TYPE VARCHAR(320);
-- Переписывает ВСЮ таблицу! Минуты/часы блокировки!
```

**text + CHECK:**

```sql
ALTER TABLE users DROP CONSTRAINT email_length_check;  -- мгновенно
ALTER TABLE users ADD CONSTRAINT email_length_check 
    CHECK (length(email) <= 320) NOT VALID;  -- мгновенно
ALTER TABLE users VALIDATE CONSTRAINT email_length_check;  -- фон
```

**Всё — без блокировки!**

**Важно:** `ADD CHECK` без `NOT VALID` **блокирует** — проверяет все строки. С `NOT VALID` — мгновенно, проверка в фоне.

---

### char(n)

**Определение:** строковый тип **фиксированной длины**, дополняемый пробелами.

```sql
'A' в CHAR(2): 'A ' (с пробелом!)
```

**char(n) почти никогда не нужен.**

---

### bytea

**Определение:** бинарные данные.

**Когда использовать:** миниатюры, документы **до 1 МБ**.

**Когда НЕ использовать:** большие файлы → S3 + путь в text.

**Сравнение:**

| Файлы < 1 МБ | Файлы > 1 МБ |
|:---|:---|
| `bytea` — транзакционно, удобно | S3 + `avatar_path TEXT` — масштабируемо |

---

### 💡 Практика: строковые типы

**✅ ОБЯЗАТЕЛЬНО:**

1. **По умолчанию — `text`.**
2. **Лимит — `text` + `CHECK (length(col) <= n)`.**
3. **Стандартные поля — `varchar(n)` допустим.**
4. **Изменение лимита — `NOT VALID` + `VALIDATE`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `char(n)`.**
6. **Не оставляй text без ограничений для атакуемых полей.**
7. **Не храни файлы > 1 МБ в БД.**

## 10.3 Дата и время: timestamp, timestamptz, date, interval

### date

**Определение:** дата без времени. **4 байта**.

**Когда:** дата рождения, дата доставки.

---

### timestamp (без таймзоны)

**Определение:** дата + время **без часового пояса**. **8 байт**.

**Проблема:** непонятно, чьё это время.

**Когда:** редко — только если всегда одно время.

---

### timestamptz (с таймзоной) — рекомендуемый

**Определение:** дата + время **с часовым поясом**. **8 байт**.

**Как хранится:** внутри **всегда UTC**, отображение по таймзоне сессии.

```sql
SET timezone = 'Europe/Moscow';
SELECT created_at;  -- '2024-01-15 10:30:00+03:00'

SET timezone = 'Europe/London';
SELECT created_at;  -- '2024-01-15 07:30:00+00:00'
```

**Когда:** **почти всегда для бизнес-данных.**

---

### interval

**Определение:** интервал времени.

```sql
SELECT now() + INTERVAL '7 days';
SELECT now() - INTERVAL '2 hours';
SELECT age(now(), birth_date);
```

---

### 💡 Практика: даты

**✅ ОБЯЗАТЕЛЬНО:**

1. **Для бизнес-данных — всегда `timestamptz`.**
2. **Для дат без времени — `date`.**
3. **Настрой таймзону сервера: `UTC`.**

**❌ НЕ ДЕЛАЙ:**

4. **Не используй `timestamp` без таймзоны.**
5. **Не используй `created_at::DATE` в WHERE** — убивает индекс.

## 10.4 UUID vs SERIAL: что выбрать для PRIMARY KEY

### Сравнение

| Аспект | SERIAL/IDENTITY | UUID |
|:---|:---|:---|
| **Размер** | 8 байт | 16 байт |
| **Генерация** | Централизованная | На клиенте |
| **Сортировка** | ✅ | ❌ (v4 случайный) |
| **INSERT** | В конец индекса | В середину |
| **Угадываемость** | Легко | Не угадаешь |

### Когда UUID действительно нужен

1. **Офлайн-генерация ID на клиенте.**
2. **Шардирование (Citus)** — несколько нод с записью.
3. **Мульти-мастер (BDR).**
4. **Объединение данных из нескольких источников.**
5. **Публичные ID** (заказы, счета).

### Когда UUID НЕ нужен

**Микросервисы с одной базой** — SERIAL/IDENTITY работает отлично.

**Физическая репликация** — Primary один, Standby только читают.

### Терминология

| Термин | UUID нужен? |
|:---|:---|
| Репликация (Primary → Standby) | ❌ Нет |
| Шардирование (Citus) | ✅ Да |
| Мульти-мастер (BDR) | ✅ Да |
| Микросервисы с одной БД | ❌ Нет |

## 10.5 JSONB vs отдельные колонки

### json vs jsonb

| Аспект | json | jsonb |
|:---|:---|:---|
| Хранение | Текст | Бинарный |
| Размер | Меньше | Больше |
| Чтение | Медленнее (парсинг) | Быстрее |
| Индексы | ❌ | ✅ GIN |
| Порядок ключей | Сохраняет | Сортирует |
| Дубликаты | Сохраняет | Удаляет |

### Сколько занимают (1 млн строк)

| Подход | Размер |
|:---|:---|
| Отдельные колонки | **~78 МБ** |
| json | ~100 МБ |
| jsonb | ~120 МБ |

### Скорость вставки (1 млн строк)

| Подход | Время |
|:---|:---|
| Колонки | **~5 сек** |
| json | ~6 сек |
| jsonb | ~12-15 сек (парсинг) |

### Скорость изменения

```sql
-- Колонки: обновляет одну колонку — быстро.
UPDATE users_columns SET is_active = false WHERE id = 42;

-- jsonb: читает весь JSONB, парсит, меняет, сериализует — медленно!
UPDATE users_jsonb SET data = jsonb_set(data, '{is_active}', 'false') WHERE id = 42;
```

### Гибрид — лучший подход

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,        -- частые поля — колонки
    email TEXT NOT NULL,
    is_active BOOLEAN,
    settings JSONB,            -- редкие — JSONB
    metadata JSONB
);
```

## 10.6 Массивы, ENUM, композитные типы

### Массивы

**Когда:** теги, категории. **Индекс:** GIN.

### ENUM

**Когда:** фиксированные статусы. **Компактный:** 4 байта.

**Проблема миграции:**

```sql
-- Добавить значение — легко:
ALTER TYPE user_status ADD VALUE 'suspended';

-- Удалить значение — НЕЛЬЗЯ!
-- Нужно пересоздание типа → полная блокировка таблицы.
```

**TEXT + CHECK — гибче:**

```sql
-- Миграция без блокировки:
ALTER TABLE users DROP CONSTRAINT users_status_check;
ALTER TABLE users ADD CONSTRAINT users_status_check 
    CHECK (status IN ('active', 'blocked', 'suspended')) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_status_check;
```

### Композитные типы

**Когда:** объединение связанных полей. **Не для частых поисков по полям.**

### Range

**Когда:** бронирования, интервалы. **Индекс:** GiST.

## 10.7 Неявные преобразования типов: как они убивают индексы

### Что это

PostgreSQL **автоматически** меняет тип для сравнения:

```sql
WHERE age = '25'  -- '25' (text) → 25 (integer)
```

### Проблема: колонка преобразуется → индекс не используется

```sql
-- ❌ НЕ использует индекс:
SELECT * FROM orders WHERE user_id = '42';

-- EXPLAIN:
-- Seq Scan
--   Filter: ((user_id)::text = '42'::text)
--             ↑ колонка преобразована!
```

### Как избежать

```go
// ✅ Из Go передавай правильные типы:
db.Query("SELECT * FROM users WHERE age = $1", 30)  // число

// ✅ Для UUID — явное:
db.Query("SELECT * FROM users WHERE id = $1::UUID", userID)

// ✅ Для дат — диапазон:
WHERE created_at >= '2024-01-15 00:00:00+00:00'
  AND created_at < '2024-01-16 00:00:00+00:00'
```

## 10.8 Практика Go: работа с типами

```go
package main

import (
    "database/sql"
    "fmt"
    "log"
    "os"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

type User struct {
    ID        int64
    Name      string
    Email     string
    Age       int32
    IsActive  bool
    CreatedAt time.Time
    Settings  []byte  // JSONB
}

func main() {
    db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close()

    // ✅ Правильные типы из Go:
    var age int32 = 30
    rows, _ := db.Query("SELECT * FROM users WHERE age = $1", age)

    // ❌ Неправильно: строка вместо числа:
    // db.Query("SELECT * FROM users WHERE age = $1", "30")

    defer rows.Close()
    for rows.Next() {
        var u User
        rows.Scan(&u.ID, &u.Name, &u.Email, &u.Age, &u.IsActive, &u.CreatedAt, &u.Settings)
        fmt.Printf("%+v\n", u)
    }
}
```

## 10.9 Выводы и типичные ошибки

**Что мы узнали?**

Тип данных — это **фундамент** производительности. Правильный тип: компактность, скорость, типобезопасность. Неправильный: раздувание, медленные сравнения, мусор.

**Типичные ошибки:**

- ❌ VARCHAR для чисел и дат.
- ❌ real/double для денег.
- ❌ timestamp без таймзоны.
- ❌ UUID без необходимости (одна база).
- ❌ Хранить всё в JSONB.
- ❌ ENUM для изменяющихся наборов.
- ❌ Неявные преобразования (передавать строки в числа).
- ❌ `::DATE` в WHERE.

## 10.10 Для быстрого повторения

- **integer** — стандарт для целых (4 байта).
- **bigint** — большие ID (8 байт).
- **numeric(p,s)** — деньги, точный, переменный.
- **text** — строки по умолчанию + CHECK для лимита.
- **timestamptz** — всегда для бизнес-данных.
- **IDENTITY** — современный автоинкремент.
- **UUID** — для шардирования, офлайн-генерации.
- **JSONB** — для гибких данных + GIN.
- **Явные преобразования** — не давай PostgreSQL менять тип колонки.

## 10.12 Ответы

### Ответ 1

1. Сравнение строк медленнее (O(длина) vs O(1)).
2. Больше места (~20 байт vs 4-8 байт).
3. Нет проверки типов — мусорные данные.

### Ответ 2

SERIAL = integer + sequence (не связаны). IDENTITY = стандарт SQL, sequence привязан к таблице. IDENTITY лучше: DROP TABLE удаляет sequence, TRUNCATE сбрасывает, защита от случайной вставки id.

### Ответ 3

numeric хранит цифры в base-10000: 4 цифры = 2 байта. 123.45 = [123][4500] → 2+2 байта + 8 байт заголовок = 12 байт.

### Ответ 4

timestamptz хранит UTC внутри, отображает по таймзоне сессии. timestamp — без таймзоны, путаница при сравнении.

### Ответ 5

UUID нужен: шардирование, офлайн-генерация, мульти-мастер. SERIAL достаточен: одна БД, микросервисы с общей БД.

### Ответ 6

json — текст, jsonb — бинарный. jsonb медленнее при вставке, потому что PostgreSQL парсит JSON и конвертирует в бинарный формат.

### Ответ 7

Неявное преобразование — PostgreSQL сам меняет тип. Если колонка преобразуется в `WHERE col = 'value'` — индекс не используется (Seq Scan вместо Index Scan).

### Ответ 8

```sql
ALTER TABLE t DROP CONSTRAINT c;  -- мгновенно
ALTER TABLE t ADD CONSTRAINT c CHECK (...) NOT VALID;  -- мгновенно
ALTER TABLE t VALIDATE CONSTRAINT c;  -- фон
```

### Ответ 9

ENUM нельзя удалять значения — только пересоздание типа → блокировка. TEXT + CHECK — просто DROP/ADD, без блокировки.

### Ответ 10

JSONB окупается: гибкая структура, редкие изменения, поиск по ключам. Не окупается: структурированные данные, частые обновления, нужна типобезопасность.
