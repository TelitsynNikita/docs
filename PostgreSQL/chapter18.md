## 18.0 Пролог: база лежит, а виноваты соединения

Ты запустил микросервисы. 30 сервисов, каждый открывает пул по 100 соединений к PostgreSQL.

```
30 сервисов × 100 соединений = 3000 коннектов к одной базе.
```

База начинает тормозить. `pg_stat_activity` (глава 1) показывает 3000 строк. CPU на 100%, хотя запросы простые.

❓ **Что происходит?**

💡 Ответ: **слишком много соединений**. Вспомни главу 1: PostgreSQL — архитектура «процесс на соединение». Каждый коннект = **отдельный процесс ОС**.

```
3000 коннектов × 10-15 МБ RAM на процесс = 30-45 ГБ только под процессы.
3000 процессов конкурируют за CPU.
Переключение контекста съедает процессор.
```

**Решение:** **пул соединений**. Вместо 3000 прямых коннектов — 50-100 реальных, которые переиспользуются.

---

## 18.1 Почему много соединений — это проблема

### Процесс на соединение

Вспомни главу 1: для каждого клиента PostgreSQL создаёт **отдельный процесс ОС** через `fork()`.

```
max_connections = 3000 → до 3000 процессов.
```

**Цена каждого процесса:**

| Ресурс | Значение |
|:---|:---|
| Память | 10-15 МБ на процесс |
| CPU | Переключение контекста |
| Планировщик ОС | Больше процессов = больше overhead |

**Пример:**

```
100 соединений → 1-1.5 ГБ RAM, нормально.
1000 соединений → 10-15 ГБ RAM, тяжело.
3000 соединений → 30-45 ГБ RAM, катастрофа.
```

### Проблема не только в памяти

Даже если памяти хватает, **3000 процессов** конкурируют за:

- **CPU** — планировщик Linux CFS переключает контексты.
- **Блокировки** (глава 14) — больше одновременных транзакций = больше конфликтов.
- **WAL** (глава 1) — больше записей = больше конкуренции за WALInsertLock.
- **shared_buffers** (глава 1) — больше процессов = больше вытеснений.

### Сколько соединений реально нужно

| Нагрузка | Рекомендуемое max_connections |
|:---|:---|
| Разработка | 50 |
| Мелкий прод | 100 |
| Средний прод | 200-300 |
| Крупный прод | 300-500 |
| Очень крупный | 500+ с PgBouncer |

**Правило:** PostgreSQL эффективен до ~200-300 **активных** запросов. Дальше — деградация.

## 18.2 Что такое пул соединений

### Определение

> **Пул соединений (connection pool)** — прокси между приложением и PostgreSQL, который держит **небольшое число реальных соединений** и переиспользует их для множества клиентов.

**Простыми словами:**

```
Без пула:
  3000 клиентов → 3000 прямых коннектов → PostgreSQL

С пулом:
  3000 клиентов → PgBouncer → 100 реальных коннектов → PostgreSQL
```

### Как это работает

```
Клиент 1: хочет сделать SELECT
  → PgBouncer берёт свободное соединение из пула
  → Передаёт запрос
  → Получает ответ
  → Возвращает соединение в пул

Клиент 2: хочет UPDATE
  → Берёт то же соединение (или другое свободное)
  → ...
```

**Ключевое:** клиенты **не держат** соединения постоянно. Они берут на время запроса и возвращают.

### Зачем пул

1. **Экономия памяти** — 100 процессов вместо 3000.
2. **Экономия CPU** — меньше переключений контекста.
3. **Быстрее подключение** — не нужно делать `fork()` для каждого клиента.
4. **Защита базы** — пул ограничивает число одновременных запросов.

## 18.3 PgBouncer: режимы session, transaction, statement

**PgBouncer** — самый популярный пул соединений для PostgreSQL.

### Три режима

| Режим | Когда соединение возвращается в пул | Для чего |
|:---|:---|:---|
| **session** | После закрытия соединения клиентом | Совместимость со всем |
| **transaction** | После COMMIT/ROLLBACK | Веб-приложения |
| **statement** | После каждого SQL-запроса | Автокоммит, только простые запросы |

### Session mode

```
Клиент открывает соединение → PgBouncer даёт реальное соединение.
Клиент работает (BEGIN, SELECT, UPDATE, COMMIT).
Клиент закрывает соединение → PgBouncer возвращает в пул.
```

**Плюсы:** работает со всеми фичами (курсоры, prepared statements, session variables).

**Минусы:** клиент, который держит соединение долго, **не возвращает** его в пул.

### Transaction mode (рекомендуется для веба)

```
Клиент выполняет BEGIN → PgBouncer берёт соединение из пула.
Клиент выполняет SELECT, UPDATE.
Клиент выполняет COMMIT → PgBouncer ВОЗВРАЩАЕТ соединение в пул.
```

**Ключевое:** соединение возвращается в пул **после каждой транзакции**, даже если клиент не закрыл своё соединение.

**Плюсы:**
- 3000 клиентов могут сидеть с открытыми коннектами, но реально используется только 100.
- Идеально для веб-приложений: запрос → транзакция → ответ.

**Минусы:**
- Не работает с session-level фичами: `SET` сбрасывается, prepared statements ограничены, курсоры не работают.

### Statement mode

```
Каждый SQL-запрос берёт соединение и сразу возвращает.
```

**Самый агрессивный.** Только для автокоммита.

### Сравнение

| Режим | Возврат в пул | Совместимость | Когда |
|:---|:---|:---|:---|
| session | При закрытии клиентом | Полная | Всё работает |
| transaction | После COMMIT | Высокая | Веб, API |
| statement | После каждого запроса | Низкая | Автокоммит |

### Настройка PgBouncer

```ini
# /etc/pgbouncer/pgbouncer.ini

[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 3000
default_pool_size = 100
```

**Ключевые параметры:**

| Параметр | Что означает |
|:---|:---|
| `pool_mode` | Режим: session, transaction, statement |
| `max_client_conn` | Сколько клиентов может подключиться к PgBouncer |
| `default_pool_size` | Сколько реальных соединений держит PgBouncer |

### Go-приложение подключается к PgBouncer

```go
db, _ := sql.Open("postgres", "host=localhost port=6432 user=alice dbname=mydb")
// Порт 6432 — PgBouncer, а не PostgreSQL (5432).
```

## 18.4 Настройка пула в Go: database/sql и pgx

Даже без PgBouncer, Go-приложение должно **само** держать пул соединений.

### database/sql: встроенный пул

```go
db, _ := sql.Open("postgres", "host=localhost user=alice dbname=mydb")

// Настройка пула:
db.SetMaxOpenConns(50)        // максимум 50 реальных соединений
db.SetMaxIdleConns(10)        // до 10 простаивающих соединений
db.SetConnMaxIdleTime(5 * time.Minute) // закрыть idle через 5 мин
db.SetConnMaxLifetime(30 * time.Minute) // максимум жизни соединения
```

### Что означают параметры

| Параметр | Что делает | Рекомендация |
|:---|:---|:---|
| `SetMaxOpenConns` | Максимум реальных соединений | 50-100 (если нет PgBouncer) |
| `SetMaxIdleConns` | Сколько держать простаивающими | ~50% от MaxOpen |
| `SetConnMaxIdleTime` | Через сколько закрыть idle | 5 минут |
| `SetConnMaxLifetime` | Максимальная жизнь соединения | 30 минут |

**Почему не ставить MaxOpenConns = 1000:**

```
1000 горутин → 1000 соединений → 1000 Backend-процессов.
Пул в Go — это не PgBouncer! Он не «переиспользует» для 1000 клиентов 50 коннектов,
он ОТКРЫВАЕТ до 50 соединений, а остальные горутины ЖДУТ.
```

**Как работает Go-пул:**

```
50 горутин делают db.Query → пул открывает 50 соединений.
51-я горутина делает db.Query → ждёт, пока одна из 50 не освободится.
→ Пул НЕ создаёт 51-е соединение (MaxOpenConns = 50).
→ Горутина ждёт в очереди.
```

**Это хорошо:** база защищена от перегрузки.

### pgx: нативный пул

```go
config, _ := pgx.ParseConfig("postgres://alice@localhost/mydb")

config.MaxConns = 50
config.MinConns = 5
config.MaxConnIdleTime = 5 * time.Minute
config.MaxConnLifetime = 30 * time.Minute

conn, _ := pgx.ConnectConfig(context.Background(), config)
```

| Параметр | Что делает |
|:---|:---|
| `MaxConns` | Максимум соединений |
| `MinConns` | Минимум (держит всегда) |
| `MaxConnIdleTime` | Через сколько закрыть idle |
| `MaxConnLifetime` | Максимум жизни |

### Полная архитектура

```
Без PgBouncer:
  30 Go-сервисов × 100 коннектов = 3000 → PostgreSQL

С PgBouncer:
  30 Go-сервисов × 100 = 3000 клиентских коннектов → PgBouncer → 100 реальных → PostgreSQL
```

**Go-сервис при этом может держать свои 100 коннектов к PgBouncer** — они дешёвые (PgBouncer не создаёт процессы), а PgBouncer держит только 100 реальных к PostgreSQL.

### 💡 Практика

**✅ ОБЯЗАТЕЛЬНО:**

1. **Всегда настраивай `SetMaxOpenConns`** — дефолт `database/sql` = unlimited!

```go
db.SetMaxOpenConns(50)
```

2. **Для микросервисов** — маленький пул (20-50).

3. **Для одного большого приложения** — 50-100.

**👍 СТОИТ:**

4. **Добавь PgBouncer** — если сервисов > 5.

**❌ НЕ ДЕЛАЙ:**

5. **Не оставляй дефолтный unlimited** — 1000 горутин откроют 1000 соединений.

## 18.5 Мониторинг соединений и поиск утечек

### Как увидеть текущие соединения

```sql
SELECT 
    count(*) AS total_connections,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_tx
FROM pg_stat_activity;
```

**Что смотреть:**

| Метрика | Проблема |
|:---|:---|
| `total_connections` растёт к `max_connections` | Утечка |
| `idle_in_tx > 0` | Зависшие транзакции (глава 1) |
| `idle` > 80% | Перерасход, можно уменьшить пул |

### По каким приложениям распределены соединения

```sql
SELECT 
    application_name,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY application_name
ORDER BY connections DESC;
```

### Найти зависшие соединения

```sql
SELECT 
    pid,
    usename,
    application_name,
    state,
    now() - state_change AS state_duration,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
   OR (state = 'idle' AND now() - state_change > interval '10 minutes')
ORDER BY state_change;
```

### Как найти утечку в Go

```go
// ❌ Утечка: rows не закрыт
rows, _ := db.Query("SELECT * FROM users")
// rows.Close() ЗАБЫЛИ!

// ❌ Утечка: транзакция не завершена
tx, _ := db.Begin()
// tx.Commit() / tx.Rollback() ЗАБЫЛИ!

// ✅ Правильно:
rows, _ := db.Query("SELECT * FROM users")
defer rows.Close()

tx, _ := db.Begin()
defer tx.Rollback()
```

### Метрики пула в Go

```go
stats := db.Stats()
fmt.Printf("Open: %d, InUse: %d, Idle: %d\n", stats.OpenConnections, stats.InUse, stats.Idle)
```

### 💡 Практика

**✅ ОБЯЗАТЕЛЬНО:**

1. **Мониторь `total_connections`** в Grafana (Приложение E).
2. **Алерт на `idle in transaction`**.
3. **В Go всегда `defer rows.Close()` и `defer tx.Rollback()`**.
4. **Настрой `idle_in_transaction_session_timeout`** (глава 1).

**👍 СТОИТ:**

5. **Логируй `application_name`**:

```go
db, _ := sql.Open("postgres", "host=... application_name=checkout-service")
```

## 18.6 Практика Go: пул + PgBouncer

```go
package main

import (
    "database/sql"
    "fmt"
    "log"
    "os"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
    // Подключение к PgBouncer:
    db, err := sql.Open("postgres", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close()

    // Настройка пула:
    db.SetMaxOpenConns(100)
    db.SetMaxIdleConns(25)
    db.SetConnMaxIdleTime(5 * time.Minute)
    db.SetConnMaxLifetime(30 * time.Minute)

    // Проверка соединения:
    err = db.Ping()
    if err != nil {
        log.Fatal(err)
    }

    // Метрики пула:
    stats := db.Stats()
    fmt.Printf("Open: %d, InUse: %d, Idle: %d\n",
        stats.OpenConnections, stats.InUse, stats.Idle)

    // Выполнение запроса:
    var count int
    err = db.QueryRow("SELECT COUNT(*) FROM users").Scan(&count)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Printf("Пользователей: %d\n", count)
}
```

## 18.7 Выводы и типичные ошибки

**Что мы узнали?**

PostgreSQL — архитектура «процесс на соединение», поэтому много коннектов = много процессов = деградация. Пул соединений (PgBouncer) держит мало реальных соединений и переиспользует их для тысяч клиентов. Go-приложение тоже должно настраивать свой пул: `SetMaxOpenConns` обязателен. Мониторинг через `pg_stat_activity` показывает утечки и зависшие транзакции.

**Типичные ошибки:**

- ❌ Не настраивать `SetMaxOpenConns` — дефолт unlimited.
- ❌ 30 микросервисов × 100 коннектов = 3000 соединений.
- ❌ Забывать `rows.Close()` и `tx.Rollback()` — утечки.
- ❌ Игнорировать `idle in transaction` — зависшие транзакции.
- ❌ Увеличивать `max_connections` вместо установки PgBouncer.

## 18.8 Для быстрого повторения

- **Процесс на соединение** — каждый коннект = процесс ОС (10-15 МБ).
- **Пул соединений** — переиспользование малого числа реальных коннектов.
- **PgBouncer** — режимы: session, transaction, statement.
- **Transaction mode** — соединение возвращается в пул после COMMIT.
- **Go-пул** — `SetMaxOpenConns` обязателен.
- **Мониторинг** — `pg_stat_activity`, `application_name`.
- **Утечки** — `rows.Close()`, `tx.Rollback()`, `idle_in_transaction_session_timeout`.

## 18.10 Ответы

### Ответ 1

Каждый коннект = процесс ОС (10-15 МБ RAM). 3000 = 30-45 ГБ только под процессы + переключение контекста CPU.

### Ответ 2

Прокси, который держит мало реальных соединений и переиспользует их для множества клиентов.

### Ответ 3

**session** — возврат при закрытии клиентом. **transaction** — после COMMIT. **statement** — после каждого запроса.

### Ответ 4

### Ответ 7

Открыта транзакция, клиент молчит. Держит снимок, мешает VACUUM.

### Ответ 8


### Ответ 9

Когда микросервисов > 5 и суммарное число коннектов > 300.

### Ответ 10

Go-пул ограничивает число коннектов, но не мультиплексирует. PgBouncer мультиплексирует: 3000 клиентов → 100 реальных.
