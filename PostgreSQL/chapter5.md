## 5.0 Пролог: два запроса, одна строка

Представь: интернет-магазин. Два пользователя одновременно покупают **последний товар** на складе.

```sql
-- Пользователь А (транзакция 100):
BEGIN;
SELECT quantity FROM products WHERE id = 42;  -- quantity = 1
-- Пользователь А думает: «Товар есть, покупаю!»

-- Пользователь Б (транзакция 200), в тот же момент:
BEGIN;
SELECT quantity FROM products WHERE id = 42;  -- quantity = 1
-- Пользователь Б тоже думает: «Товар есть, покупаю!»

-- Пользователь А:
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;

-- Пользователь Б:
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;

-- Итог: оба купили один товар. Остаток = 0.
-- Но продан он дважды!
```

Это **классическая проблема конкурентного доступа**. Две транзакции прочитали одно и то же значение, обе приняли решение на основе этого значения, и обе записали результат — **перезаписав** друг друга.

В мире баз данных это называется **lost update** — потерянное обновление.

❓ **Как PostgreSQL решает эту проблему?**

Ответ — **MVCC (Multiversion Concurrency Control)** — многоверсионное управление конкурентным доступом.

Вместо того чтобы блокировать строку при чтении (как делают некоторые базы), PostgreSQL хранит **несколько версий строки** одновременно. Каждая транзакция видит **свой снимок** данных — как будто она одна работает с базой.

Но MVCC сам по себе **не решает** потерянные обновления. Разберёмся, какие инструменты есть.

### Решение проблемы: атомарный UPDATE

Вместо `SELECT` + `UPDATE` с фиксированным значением:

```sql
-- ❌ Плохо: читаем, потом записываем фиксированное значение
SELECT quantity FROM products WHERE id = 42;  -- = 1
UPDATE products SET quantity = 0 WHERE id = 42;
-- Между SELECT и UPDATE другой мог изменить quantity.
-- Мы записываем устаревшее значение.
```

**Используй атомарный UPDATE с условием:**

```sql
-- ✅ Хорошо: атомарно вычитаем с проверкой
UPDATE products 
SET quantity = quantity - 1 
WHERE id = 42 AND quantity >= 1;
```

**Как это работает при конкуренции:**

```
Транзакция А: UPDATE ... WHERE id=42 AND quantity >= 1;
Транзакция Б: UPDATE ... WHERE id=42 AND quantity >= 1;

1. Обе находят строку (quantity = 1).
2. А получает блокировку строки ПЕРВОЙ.
3. А: quantity = 1 - 1 = 0. COMMIT.

4. Б ждала блокировку.
5. После COMMIT А, Б перечитывает строку: quantity = 0.
6. Б проверяет WHERE: quantity >= 1? НЕТ (0 >= 1 = false).
7. Б НЕ обновляет строку. Возвращает «0 rows affected».

Итог: quantity = 0, продан ОДИН раз. Потерянного обновления нет!
```

**Дополнительная защита: ограничение целостности**

```sql
ALTER TABLE products 
ADD CONSTRAINT quantity_non_negative CHECK (quantity >= 0);
```

Если какой-то запрос забудет `WHERE quantity >= 1`, то:

```sql
UPDATE products SET quantity = quantity - 1 WHERE id = 42;
-- Если quantity = 0 → quantity = -1 → ОШИБКА: check constraint violated
```

**Важно:** приложение **должно проверять**, сколько строк обновлено:

```go
result, err := db.Exec(
    "UPDATE products SET quantity = quantity - 1 WHERE id = $1 AND quantity >= $2",
    42, 1,
)
if err != nil {
    return err
}

rowsAffected, _ := result.RowsAffected()
if rowsAffected == 0 {
    return errors.New("товар не доступен")
}
```

### Почему это работает при любом уровне изоляции

- Уровень изоляции влияет на **чтение** (снимки).
- Но `UPDATE` всегда работает с **актуальной** версией строки (перечитывает её перед записью).
- Блокировка строки обеспечивает **последовательность** при конкурентных UPDATE.
- Условие `WHERE quantity >= 1` проверяется **после** перечитывания.

Это **лучший паттерн** для операций списания/начисления баланса.

## 5.1 Проблема: конкурентный доступ без блокировок

### Два подхода к конкурентности

**Подход 1: Блокировки на чтение (`FOR UPDATE`)**

```sql
BEGIN;
SELECT * FROM products WHERE id = 42 FOR UPDATE;  -- БЛОКИРУЕТ строку
-- Все остальные транзакции ждут, пока ты не COMMIT/ROLLBACK
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;
```

- **Работа со строкой становится последовательной** — один за другим.
- **Результат предсказуемый** — второй видит то, что записал первый.
- **Но читатели блокируют читателей** — при большой конкуренции все ждут.

**Подход 2: MVCC (PostgreSQL)**

```sql
BEGIN;
SELECT * FROM products WHERE id = 42;  -- НЕ блокирует
-- Другие транзакции могут читать и изменять эту строку
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;
```

- **Читатели не блокируют** — SELECT никогда не ждёт.
- **Писатели не блокируют читателей** — UPDATE не мешает SELECT'ам.
- **Но результат может быть непредсказуемым** — нужно думать о потерянных обновлениях.

### Что даёт MVCC: конкретный выигрыш

**Сценарий: отчёт + приём заказов**

```sql
-- Транзакция А (финансовый отчёт):
BEGIN;
SELECT SUM(total) FROM orders WHERE created_at = today();
-- Читает миллионы строк, работает 10 секунд.

-- Транзакция Б (новый заказ):
BEGIN;
INSERT INTO orders (...) VALUES (...);
-- Вставляется мгновенно.
```

**С блокировками на чтение:**

- Транзакция А блокирует заказы за сегодня на 10 секунд.
- Транзакция Б **ждёт 10 секунд**, чтобы вставить новый заказ.
- Покупатели ждут. Деньги теряются.

**С MVCC (PostgreSQL):**

- Транзакция А читает **снимок** заказов — ничего не блокирует.
- Транзакция Б **вставляет заказ параллельно**.
- Никто не ждёт.

**Вот суть MVCC:** читатели и писатели работают **одновременно**, не мешая друг другу.

### Что MVCC НЕ решает

MVCC **не решает** потерянные обновления автоматически:

```sql
-- Транзакция А:
SELECT quantity FROM products WHERE id = 42;  -- видит 1
UPDATE products SET quantity = 0 WHERE id = 42;

-- Транзакция Б (в тот же момент):
SELECT quantity FROM products WHERE id = 42;  -- видит 1
UPDATE products SET quantity = 0 WHERE id = 42;
-- Оба записали 0 — потерянное обновление.
```

**Для потерянных обновлений нужны:**

- **Атомарный UPDATE с условием** (рекомендуется — см. пролог):
  ```sql
  UPDATE products SET quantity = quantity - 1 WHERE id = 42 AND quantity >= 1;
  ```
- `SELECT ... FOR UPDATE` (явная блокировка)
- Уровень изоляции `REPEATABLE READ` (прерывает одну из транзакций)

### Аномалии глазами пользователя

Аномалия — это ситуация, когда пользователь **видит то, чего не должен видеть**, или **не видит то, что должен**.

**Пример с интернет-магазином:**

```
Таблица products (ассортимент):
  id | name          | quantity
  ---+---------------+----------
  42 | iPhone 15 Pro | 1

Пользователь А (покупатель):
  Заходит на страницу товара → видит: «В наличии: 1 шт.»
  Нажимает «Купить».

Пользователь Б (другой покупатель):
  В тот же момент заходит на страницу → видит: «В наличии: 1 шт.»
  Тоже нажимает «Купить».

Администратор:
  В это же время обновляет цену или описание товара.
```

**Какие аномалии могут увидеть пользователи:**

1. **Потерянное обновление (Lost Update):**
   Оба покупателя видят «1 шт.», оба нажимают «Купить». Один должен получить товар, второй должен увидеть «Нет в наличии». Но если оба UPDATE записали `quantity = 0` — оба «купили», товар продан дважды.

2. **Неповторяемое чтение (Non-Repeatable Read):**
   Пользователь открыл корзину → видит цену 100 000 ₽. Пока он думал, администратор изменил цену на 120 000 ₽. Пользователь нажимает «Оформить» → видит уже 120 000 ₽. В **рамках одной** транзакции он увидел **разные** значения.

3. **Фантомное чтение (Phantom Read):**
   Пользователь ищет «iPhone» → видит 10 товаров. Пока он листает, администратор добавил ещё 2 iPhone. Пользователь обновил страницу → видит уже 12 товаров. Появились **новые строки**, которых не было в начале.

4. **Грязное чтение (Dirty Read):**
   Администратор начал обновлять цену, но ещё не закоммитил. Пользователь видит **новую** цену — но админ потом откатывает. Пользователь увидел то, что **никогда не существовало**. В PostgreSQL это **невозможно**.

### Разница между MVCC и FOR UPDATE глазами пользователя

**MVCC (обычный SELECT):**

```
Пользователь открыл страницу товара:
  SELECT * FROM products WHERE id = 42;
  → Видит: quantity = 1, price = 100 000

Пользователь НЕ блокирует строку.
Другие пользователи тоже могут смотреть.
Администратор может менять цену параллельно.

Пользователь видит СНИМОК — данные на момент его SELECT.
Если админ изменил цену ПОСЛЕ — пользователь этого не видит.
```

**FOR UPDATE:**

```
Пользователь открыл страницу для ПОКУПКИ:
  SELECT * FROM products WHERE id = 42 FOR UPDATE;
  → Строка ЗАБЛОКИРОВАНА на время транзакции

Другие пользователи НЕ могут изменить эту строку.
Администратор НЕ может поменять цену, пока пользователь не COMMIT.

Пользователь видит актуальные данные и МОЖЕТ быть уверен:
  никто не изменит строку, пока он думает.
```

**Таблица: что видит пользователь**

| Сценарий | MVCC (без FOR UPDATE) | FOR UPDATE |
|:---|:---|:---|
| **Читает страницу товара** | Видит снимок. Никому не мешает. | Блокирует строку. Все ждут. |
| **Админ меняет цену в тот же момент** | Изменение видно **только после COMMIT админа** | Админ **ждёт**, пока пользователь не завершит |
| **Два пользователя покупают последний товар** | Оба видят «1 шт.», оба UPDATE → **потерянное обновление** | Первый блокирует, второй **ждёт**, потом видит «0 шт.» |
| **Пользователь долго думает** | Никто не ждёт | Все, кто хочет изменить строку, ждут |

### Что такое MVCC

> **MVCC (Multiversion Concurrency Control)** — механизм, при котором каждая транзакция работает со **снимком** данных, а изменения создают **новые версии** строк, не блокируя читателей.

**Ключевое:** MVCC — это **базовый режим** работы PostgreSQL. `FOR UPDATE` — **точечный инструмент** для явной блокировки, когда нужна гарантия, что строка не изменится.

### Как это связано с Главами 1-2

- `t_xmin`/`t_xmax` (Глава 2) — поля заголовка кортежа, на которых строится MVCC.
- Страницы в `shared_buffers` (Глава 1) — где физически лежат версии строк.
- VACUUM (Глава 6) — очищает старые версии.

### Уровни изоляции: короткий обзор

| Уровень | Что гарантирует | Аномалии |
|:---|:---|:---|
| **Read Committed** (дефолт) | Каждый запрос видит последние закоммиченные данные | Неповторяемое чтение |
| **Repeatable Read** | Вся транзакция видит один снимок | Только фантомы |
| **Serializable** | Как будто транзакции выполнялись по очереди | Никаких |

Подробно — в подглаве 5.4.

## 5.2 Версии строк: t_xmin, t_xmax и цепочки

### Физическая реальность: что лежит на странице

Когда транзакция 100 выполняет `UPDATE`, **физически** на странице появляются **две версии** строки.

**Исходное состояние:**

```
Страница 500, слот 1:
  t_xmin = 90   (создана транзакцией 90)
  t_xmax = 0    (жива)
  t_ctid = (500,1)
  quantity = 1
```

**После UPDATE транзакцией 100 (до COMMIT):**

```
Страница 500:

  Слот 1 (СТАРАЯ версия):
    t_xmin = 90
    t_xmax = 100   ← пометка СРАЗУ, не ждёт COMMIT!
    t_ctid = (500,2)  ← указывает на новую версию
    quantity = 1

  Слот 2 (НОВАЯ версия):
    t_xmin = 100   ← создана транзакцией 100
    t_xmax = 0
    t_ctid = (500,2)
    quantity = 0
```

**Ключевой момент:** `t_xmax = 100` появляется **в момент UPDATE**, а не после COMMIT. Это **пометка** «транзакция 100 обновила эту версию», а не «закоммиченное удаление».

### Логическая видимость: что видят другие транзакции

**До COMMIT транзакции 100:**

- Другая транзакция читает строку → видит слот 1 → `t_xmax = 100`.
- Проверяет статус транзакции 100: **не закоммичена**.
- Значит, удаление **не подтверждено** → видит `quantity = 1` (старую версию).

**После COMMIT транзакции 100:**

- Другая транзакция читает строку → видит слот 1 → `t_xmax = 100`.
- Проверяет статус транзакции 100: **закоммичена**.
- Значит, удаление **подтверждено** → идёт по `t_ctid` → слот 2 → видит `quantity = 0`.

**После ROLLBACK транзакции 100:**

- Другая транзакция читает строку → видит слот 1 → `t_xmax = 100`.
- Проверяет статус транзакции 100: **откатилась**.
- Значит, удаление **отменено** → видит `quantity = 1`.

**Физически обе версии остаются на странице** во всех трёх случаях. Логически видимость разная.

### Пример с таблицей пользователей: когда аномалий не видно

```
Таблица users:
  id | username | email
  ---+----------+------------------
  42 | alice    | alice@mail.com

Пользователь А (Alice) меняет email:

  BEGIN;
  SELECT * FROM users WHERE id = 42;  -- видит alice@mail.com
  UPDATE users SET email = 'alice.new@mail.com' WHERE id = 42;
  COMMIT;
```

**Что видит Alice:**

- Она **единственная**, кто меняет эту строку.
- Другие пользователи **не имеют доступа** к её строке.
- Администраторы **теоретически** могут, но в реальности это редкий случай.

**Аномалий нет**, потому что **конкуренции нет** — строка принадлежит одному пользователю.

### Пример с таблицей ассортимента: когда аномалии видны

```
Таблица products (ассортимент):
  id | name          | quantity | price
  ---+---------------+----------+---------
  42 | iPhone 15 Pro | 1        | 100000

Доступ имеют ВСЕ:
  - Покупатели читают
  - Администраторы меняют цену и количество
  - Администраторы добавляют новые товары
  - Администраторы удаляют старые

ВЫСОКАЯ КОНКУРЕНЦИЯ!
```

**Сценарий: два покупателя, последний iPhone**

```
Транзакция А (Покупатель А):
  BEGIN;
  SELECT quantity FROM products WHERE id = 42;
  → Видит: quantity = 1

Транзакция Б (Покупатель Б):
  BEGIN;
  SELECT quantity FROM products WHERE id = 42;
  → Видит: quantity = 1  (то же самое!)

Покупатель А:
  UPDATE products SET quantity = 0 WHERE id = 42;
  COMMIT;

Покупатель Б:
  UPDATE products SET quantity = 0 WHERE id = 42;
  COMMIT;

Итог: quantity = 0, но iPhone «продан» дважды.
Это ПОТЕРЯННОЕ ОБНОВЛЕНИЕ.
```

**Решение — атомарный UPDATE (из пролога):**

```sql
-- Оба покупателя выполняют:
UPDATE products SET quantity = quantity - 1 WHERE id = 42 AND quantity >= 1;

-- Один обновит (quantity: 1 → 0), второй получит «0 rows affected».
-- Потерянного обновления нет.
```

**Сценарий: неповторяемое чтение**

```
Покупатель А (в одной транзакции):
  BEGIN;
  SELECT price FROM products WHERE id = 42;
  → Видит: price = 100000

  (Пока он читает, Администратор в другой транзакции:
     UPDATE products SET price = 120000 WHERE id = 42;
     COMMIT;)

  SELECT price FROM products WHERE id = 42;
  → Видит: price = 120000  (ДРУГОЕ ЗНАЧЕНИЕ!)

В рамках ОДНОЙ транзакции пользователь увидел ДВА разных значения.
Это НЕПОВТОРЯЕМОЕ ЧТЕНИЕ.
```

**Сценарий: фантомное чтение**

```
Пользователь А (ищет iPhone):
  BEGIN;
  SELECT * FROM products WHERE name LIKE '%iPhone%';
  → Видит: 10 строк

  (Администратор добавляет 2 новых iPhone)

  SELECT * FROM products WHERE name LIKE '%iPhone%';
  → Видит: 12 строк  (ПОЯВИЛИСЬ НОВЫЕ СТРОКИ!)

В рамках ОДНОЙ транзакции пользователь увидел РАЗНОЕ количество строк.
Это ФАНТОМНОЕ ЧТЕНИЕ.
```

### Цепочка версий

Если строку обновляли несколько раз:

```
UPDATE quantity = 0 (транзакция 100)
UPDATE quantity = 5 (транзакция 150)
UPDATE quantity = 3 (транзакция 200)

ФИЗИЧЕСКИ на странице:

  Слот 1: t_xmin=90,  t_xmax=100, t_ctid=(500,2), quantity=1
  Слот 2: t_xmin=100, t_xmax=150, t_ctid=(500,3), quantity=0
  Слот 3: t_xmin=150, t_xmax=200, t_ctid=(500,4), quantity=5
  Слот 4: t_xmin=200, t_xmax=0,   t_ctid=(500,4), quantity=3  ← актуальная
```

**Чтение актуальной версии:**

1. Идём по TID → слот 1.
2. `t_xmax = 100` закоммичена → идём по `t_ctid` → слот 2.
3. `t_xmax = 150` закоммичена → идём по `t_ctid` → слот 3.
4. `t_xmax = 200` закоммичена → идём по `t_ctid` → слот 4.
5. `t_xmax = 0` → вот актуальная версия: `quantity = 3`.

**Проблема:** длинная цепочка = много прыжков = медленное чтение. VACUUM (Глава 6) физически удаляет старые версии.

### Что мы узнали в подглаве 5.2

- **UPDATE создаёт новую версию** — физически на странице появляются обе версии.
- **`t_xmax` меняется в момент UPDATE** — не ждёт COMMIT.
- **Логическая видимость** зависит от статуса транзакции в `t_xmax`.
- **Цепочка версий** — последовательность `t_ctid` от старой к актуальной.
- **Аномалии видны при высокой конкуренции** — таблицы ассортимента, заказов.
- **Аномалий нет при низкой конкуренции** — личные данные пользователя.
- **Атомарный UPDATE** — лучшее решение для списания/начисления.

## 5.3 Снимки (snapshots): что видит транзакция

В подглаве 5.2 мы разобрали, как физически устроены версии строк. Теперь ключевой вопрос: **как транзакция понимает, какую версию видеть?**

Ответ: через **снимок (snapshot)**.

### Что такое снимок

**Снимок** — это набор данных, который определяет, какие транзакции считаются «закоммиченными» на момент начала нашей транзакции.

Когда транзакция начинается (первый `SELECT` после `BEGIN`), PostgreSQL делает **мгновенный срез** всех активных транзакций:

- Кто уже закоммичен → их изменения **видимы**.
- Кто ещё работает → их изменения **не видимы**.
- Кто начнёт позже → их изменения **не видимы**.

```
Транзакция 100: BEGIN (снимок S100)
  → В этот момент закоммичены: ..., 88, 89, 90
  → Ещё работают: 101, 102
  → Начнут позже: 103, 104, ...

Снимок S100:
  «Я вижу всё, что закоммичено до 100.
   Я НЕ вижу то, что делают 101, 102, 103, ...»
```

### Как снимок хранится в памяти Backend-процесса

Вспомни Главу 1: каждый Backend-процесс хранит в своей памяти **состояние транзакции**. Снимок — часть этого состояния.

Снимок содержит три компонента:

| Компонент | Что означает |
|:---|:---|
| **xmin** | Минимальный ID транзакции, чьи изменения ещё могут быть не закоммичены. Все транзакции `< xmin` точно закоммичены |
| **xmax** | Максимальный ID транзакции + 1. Все транзакции `≥ xmax` начались после нас |
| **xip_list** | Список ID активных транзакций, которые начались до нас, но ещё не закоммичены |

```
Пример снимка S100 (когда транзакция 100 началась):

  xmin = 90   (транзакции < 90 точно закоммичены)
  xmax = 103  (транзакции ≥ 103 начались после нас — не видимы)
  xip_list = [101, 102]  (активные в момент нашего старта)

Что видит транзакция 100:
  - Транзакции < 90 → ВИДНЫ (закоммичены до нашего старта)
  - Транзакции 90-102 → смотрим в xip_list:
      - Если в списке → активная → НЕ ВИДНА
      - Если не в списке → закоммичена → ВИДНА
  - Транзакции ≥ 103 → НЕ ВИДНЫ (начались после нас)
```

### Как снимок связан с версиями строк и Buffer Manager

Когда транзакция 100 читает строку, Backend-процесс:

1. Через Buffer Manager идёт к странице в `shared_buffers`.
2. Находит слот с нужной строкой.
3. Читает `t_xmin` — кто создал эту версию.
4. **Проверяет по снимку:** «Вижу ли я эту транзакцию?»

```
Backend-процесс транзакции 100 читает строку:

  Слот 1: t_xmin = 95, t_xmax = 0

  Проверяем t_xmin = 95 по снимку S100:
    xmin = 90, xmax = 103, xip_list = [101, 102]
    
    95 < 90? Нет.
    95 ≥ 103? Нет.
    95 в xip_list? Нет.
    
    Значит, 95 закоммичена до нашего старта → ВИДНА.
    
  Строка видима с quantity = 1.
```

### Визуализация: что видит транзакция 100

```
ВРЕМЯ →

t=0: Транзакция 95: UPDATE quantity = 5; COMMIT;  (закоммичена)
t=1: Транзакция 101: BEGIN; UPDATE ...;  (ещё работает)
t=2: Транзакция 100: BEGIN; (СНИМОК S100!)
     В этот момент:
       - 95: закоммичена → видна
       - 101: активна → не видна
t=3: Транзакция 101: COMMIT;
t=4: Транзакция 103: BEGIN; UPDATE ...;  (после нас)

Транзакция 100 читает строку:
  Версия с t_xmin=95 → ВИДНА (закоммичена до S100)
  Версия с t_xmin=101 → НЕ ВИДНА (была активна в момент S100)
  Версия с t_xmin=103 → НЕ ВИДНА (началась после S100)
```

### Снимок в Read Committed vs Repeatable Read

**Read Committed (дефолт):**

```
Снимок СБРАСЫВАЕТСЯ перед каждым SQL-запросом в транзакции.

BEGIN;
SELECT ...;  -- снимок S1 (видит закоммиченное на момент S1)
-- Другая транзакция: COMMIT;
SELECT ...;  -- снимок S2 (видит закоммиченное на момент S2 — ВКЛЮЧАЯ чужие COMMIT!)
COMMIT;
```

Каждый `SELECT` видит **последние закоммиченные** данные.

**Почему так:** Backend-процесс не «держит» снимок в памяти между запросами — он создаёт **новый** снимок перед каждым SQL-запросом. Это дёшево: снимок — это просто копия трёх чисел (`xmin`, `xmax`, `xip_list`).

**Repeatable Read:**

```
Снимок ФИКСИРУЕТСЯ один раз в начале транзакции.

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT ...;  -- снимок S1 (видит закоммиченное на момент S1)
-- Другая транзакция: COMMIT;
SELECT ...;  -- ВСЁ ЕЩЁ снимок S1 (НЕ видит чужие COMMIT!)
COMMIT;
```

Все `SELECT` видят **один и тот же** снимок.

**Почему так:** Backend-процесс **сохраняет** снимок в своей памяти и **переиспользует** его для всех запросов в транзакции.

Подробно уровни изоляции разберём в подглаве 5.4.

### Пример с интернет-магазином: что видит покупатель

**Read Committed:**

```
Таблица products: iPhone, quantity = 1

Покупатель А:
  BEGIN;
  SELECT quantity FROM products WHERE id = 42;
    → Снимок S1: видит quantity = 1

  Администратор (другая транзакция):
    UPDATE quantity = 0; COMMIT;

  SELECT quantity FROM products WHERE id = 42;
    → Снимок S2 (НОВЫЙ): видит quantity = 0

Покупатель А видит, что товар закончился.
Это НОРМАЛЬНО для Read Committed: каждый SELECT видит свежие данные.
```

**Repeatable Read:**

```
Покупатель Б:
  BEGIN ISOLATION LEVEL REPEATABLE READ;
  SELECT quantity FROM products WHERE id = 42;
    → Снимок S1: видит quantity = 1

  Администратор (другая транзакция):
    UPDATE quantity = 0; COMMIT;

  SELECT quantity FROM products WHERE id = 42;
    → ВСЁ ЕЩЁ снимок S1: видит quantity = 1

Покупатель Б НЕ видит изменение админа.
Он работает со стабильным снимком.
```

### Связь с VACUUM (Глава 6)

Снимок напрямую влияет на то, **какие версии строк VACUUM может удалить**:

```
VACUUM удаляет старые версии, которые НЕ нужны НИ ОДНОЙ активной транзакции.

Если есть транзакция с Repeatable Read и старым снимком:
  Она может быть должна видеть СТАРЫЕ версии строк.
  VACUUM НЕ МОЖЕТ их удалить, пока эта транзакция активна.

Read Committed → снимки короткие (на один запрос) → VACUUM может удалять быстрее.
Repeatable Read → снимки длинные (на всю транзакцию) → VACUUM ждёт → больше bloat.
```

Это **ещё одна причина**, почему длинные транзакции вредны: они мешают VACUUM'у очищать старые версии, что приводит к раздуванию таблиц (Глава 6).

### Итог подглавы 5.3

- **Снимок** — мгновенный срез закоммиченных транзакций на момент старта.
- **Три компонента** — `xmin`, `xmax`, `xip_list`.
- **Backend-процесс** хранит снимок в своей памяти (Глава 1).
- **Read Committed** — новый снимок на каждый SQL-запрос.
- **Repeatable Read** — один снимок на всю транзакцию.
- **Снимок определяет** — какую версию строки увидит транзакция.
- **Снимок влияет на VACUUM** — длинные снимки мешают очистке старых версий.

## 5.4 Уровни изоляции: Read Committed vs Repeatable Read

В подглаве 5.3 мы разобрали, что такое снимок. Теперь разберём **как именно** каждый уровень изоляции добивается своего поведения — без магии, через механизмы PostgreSQL.

---

### 5.4.1 Read Committed: новый снимок на каждый запрос

**Read Committed** — уровень по умолчанию.

**Как это работает внутри:**

1. Backend-процесс **не хранит** снимок между SQL-запросами.
2. Перед каждым `SELECT` он вызывает функцию `GetSnapshotData()`.
3. Эта функция **собирает** снимок: смотрит в общую память (shared memory), где хранится статус всех транзакций.
4. Снимок живёт **только на время выполнения** текущего SQL-запроса, потом уничтожается.

```
Backend-процесс (Read Committed):

  BEGIN;  ← снимок НЕ создаётся

  SELECT ... → GetSnapshotData():
    - Смотрим в shared memory: кто закоммичен, кто активен
    - Собираем снимок S1
    - Выполняем SELECT с S1
    - УНИЧТОЖАЕМ S1

  (другая транзакция COMMIT)

  SELECT ... → GetSnapshotData():
    - Снова смотрим в shared memory
    - Собираем НОВЫЙ снимок S2 (видит чужие COMMIT!)
    - Выполняем SELECT с S2
    - УНИЧТОЖАЕМ S2

  COMMIT;
```

**Ключевые сущности:**

| Сущность | Роль |
|:---|:---|
| **GetSnapshotData()** | Функция в исходном коде PostgreSQL |
| **Shared memory** | Там хранится статус всех транзакций (закоммичена/активна/откатилась) |
| **Backend-процесс** | Вызывает GetSnapshotData() перед каждым SELECT, потом забывает снимок |

**Пример с интернет-магазином:**

```sql
BEGIN;

SELECT price FROM products WHERE id = 42;
-- GetSnapshotData() → S1 → видит price = 100000
-- S1 уничтожен

-- Администратор: UPDATE price = 120000; COMMIT;

SELECT price FROM products WHERE id = 42;
-- GetSnapshotData() → S2 (НОВЫЙ!) → видит price = 120000
-- S2 уничтожен

COMMIT;
```

**Что видит покупатель:** 100 000 ₽ → 120 000 ₽. Это **неповторяемое чтение**.

**Когда это нормально:** CRUD-операции, пользовательский интерфейс — каждый запрос должен видеть свежие данные.

---

### 5.4.2 Repeatable Read: один снимок на всю транзакцию

**Как это работает внутри:**

1. Backend-процесс создаёт снимок **один раз** — при первом `SELECT`.
2. **Сохраняет** снимок в своей памяти (переменная `SavedSnapshot`).
3. Все последующие `SELECT` используют **тот же** сохранённый снимок — **не вызывают** `GetSnapshotData()` заново.

```
Backend-процесс (Repeatable Read):

  BEGIN ISOLATION LEVEL REPEATABLE READ;  ← снимок НЕ создаётся

  SELECT ... → GetSnapshotData():
    - Собираем снимок S1
    - СОХРАНЯЕМ S1 в памяти Backend-процесса (SavedSnapshot = S1)
    - Выполняем SELECT с S1

  (другая транзакция COMMIT)

  SELECT ... → НЕ вызываем GetSnapshotData() заново!
    - Берём СОХРАНЁННЫЙ снимок S1 (SavedSnapshot)
    - Выполняем SELECT с S1 (НЕ видим чужие COMMIT!)

  COMMIT;  ← SavedSnapshot уничтожается
```

**Ключевые сущности:**

| Сущность | Роль |
|:---|:---|
| **Память Backend-процесса** | Переменная `SavedSnapshot` хранит снимок S1 всю транзакцию |
| **GetSnapshotData()** | Вызывается ОДИН раз — при первом SELECT |
| **Shared memory** | Читается только при создании S1, потом НЕ читается |

**Пример с интернет-магазином:**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT price FROM products WHERE id = 42;
-- GetSnapshotData() → S1 → видит price = 100000
-- SavedSnapshot = S1

-- Администратор: UPDATE price = 120000; COMMIT;

SELECT price FROM products WHERE id = 42;
-- Используем SavedSnapshot (S1) → видит price = 100000 (НЕ изменился!)

COMMIT;
```

**Что видит покупатель:** 100 000 ₽ → 100 000 ₽. Стабильный снимок.

---

### 5.4.3 Как предотвращается потерянное обновление в Repeatable Read

Это **самый важный механизм**, который отличает Repeatable Read от Read Committed.

**Проблема:** что будет, если транзакция А попытается обновить строку, которую уже обновила транзакция Б?

```
Транзакция А (Repeatable Read):
  SELECT quantity FROM products WHERE id = 42;
  → Снимок S1: видит quantity = 1 (версия с t_xmin=90, t_xmax=0)

Транзакция Б:
  UPDATE products SET quantity = 0 WHERE id = 42;
  COMMIT;
  → Новая версия: quantity = 0 (t_xmin=200, t_xmax=0)
  → Старая версия помечена: t_xmax=200

Транзакция А:
  UPDATE products SET quantity = 0 WHERE id = 42;
  → Что произойдёт?
```

**Механизм: EvalPlanQual (проверка перед UPDATE)**

Когда транзакция А выполняет `UPDATE`, PostgreSQL **перед записью** перечитывает строку и сравнивает с тем, что видит А:

```
ШАГ 1: А выполнила SELECT → увидела версию с t_xmin=90, t_xmax=0.

ШАГ 2: Б обновила строку → t_xmax старой версии = 200, создана новая.

ШАГ 3: А пытается UPDATE → PostgreSQL ПЕРЕЧИТЫВАЕТ строку:
       «Какая версия сейчас актуальна?»
       → Новая версия: t_xmin=200, t_xmax=0 (создана Б)

ШАГ 4: PostgreSQL сравнивает:
       «Снимок А (S1) видит версию с t_xmin=90?» → Да.
       «Но актуальная версия — t_xmin=200?» → Да.

ШАГ 5: КОНФЛИКТ! А пытается обновить версию, которую уже обновила Б.

ШАГ 6: В Repeatable Read → ОШИБКА:
       «ERROR: could not serialize access due to concurrent update»
```

**В Read Committed — другое поведение:**

```
ШАГ 6: В Read Committed → НЕТ ошибки.
       PostgreSQL ПЕРЕЧИТЫВАЕТ строку (новый снимок S2):
       → Видит версию t_xmin=200 (quantity=0)
       → Обновляет ЕЁ (quantity=0 → quantity=0, или минус, если приложение так написано)

Итог: потерянное обновление ВОЗМОЖНО в Read Committed.
      В Repeatable Read — ПРЕДОТВРАЩЕНО ошибкой сериализации.
```

---

### 5.4.4 Serializable: SSI (Serializable Snapshot Isolation)

Serializable в PostgreSQL использует **SSI** — расширение обычного MVCC.

**Идея:** отслеживать **зависимости** между транзакциями и прерывать те, которые могут создать аномалию.

**Как SSI работает:**

```
1. Каждая транзакция получает снимок (как в Repeatable Read).

2. PostgreSQL отслеживает ЗАВИСИМОСТИ:
   - Транзакция А прочитала строку X (снимок S1).
   - Транзакция Б обновила строку X.
   - Записывается: «Б зависит от А» (Б изменила то, что читала А).

3. Если образуется ЦИКЛ зависимостей → одна из транзакций прерывается:
   «ERROR: could not serialize access due to read/write dependencies»
```

**Пример: фантом, который предотвращает Serializable**

```
Транзакция А (Serializable):
  SELECT * FROM products WHERE category = 'phone';
  → Видит 10 строк

Транзакция Б:
  INSERT INTO products (category = 'phone', ...);
  COMMIT;

Транзакция А:
  SELECT * FROM products WHERE category = 'phone';
  → В Repeatable Read: ВСЁ ЕЩЁ видит 10 строк (снимок S1).
  → В Serializable: PostgreSQL ОТСЛЕЖИВАЕТ, что Б вставила строку,
    которую А должна была бы увидеть.

Если А попытается выполнить UPDATE по категории 'phone':
  PostgreSQL видит конфликт: А читала по категории, Б вставила в категорию.
  → Прерывает одну из транзакций.
```

### 5.4.5 Сводная таблица: как каждый уровень реализован

| Уровень | Механизм | Как достигается |
|:---|:---|:---|
| **Read Committed** | Новый снимок на каждый SELECT | `GetSnapshotData()` вызывается перед каждым запросом |
| **Repeatable Read** | Один снимок на всю транзакцию | `SavedSnapshot` хранится в памяти Backend-процесса |
| **Serializable** | SSI | PostgreSQL отслеживает зависимости между транзакциями и прерывает конфликтующие |

### 5.4.6 Что видит пользователь: сравнительная таблица

| Сценарий | Read Committed | Repeatable Read | Serializable |
|:---|:---|:---|:---|
| **Два SELECT в одной транзакции** | Могут видеть разные значения | Видят одно и то же | Видят одно и то же |
| **UPDATE конкурентной строки** | Перезаписывает (потерянное обновление) | **Ошибка сериализации** | **Ошибка сериализации** |
| **Фантомы (новые строки)** | Видит | Не видит | Не видит + прерывает при конфликте |
| **Производительность** | Максимальная | Чуть ниже | Самая низкая |

### 💡 Практика: какой уровень изоляции выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Read Committed (дефолт) для большинства запросов:**
   - CRUD, пользовательский интерфейс, логи — каждому запросу нужны свежие данные.

2. **Атомарный UPDATE для списания/начисления:**
   ```sql
   UPDATE products SET quantity = quantity - 1 WHERE id = 42 AND quantity >= 1;
   ```

3. **Repeatable Read для отчётов:**
   ```sql
   BEGIN ISOLATION LEVEL REPEATABLE READ;
   SELECT ... FROM orders WHERE created_at = today();
   -- Весь отчёт видит ОДИН снимок → согласованные данные
   COMMIT;
   ```

4. **Serializable для финансовых операций:**
   ```sql
   BEGIN ISOLATION LEVEL SERIALIZABLE;
   -- Списание, начисление, баланс — абсолютная изоляция
   COMMIT;
   ```

**👍 СТОИТ СДЕЛАТЬ:**

5. **`SELECT ... FOR UPDATE` когда нужно ПРОЧИТАТЬ, а ПОТОМ изменить:**
   ```sql
   BEGIN;
   SELECT * FROM products WHERE id = 42 FOR UPDATE;
   -- Строка заблокирована, можешь спокойно работать
   UPDATE products SET ... WHERE id = 42;
   COMMIT;
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Serializable для простых операций.** Медленнее, чаще ошибки сериализации.

**❌ НЕ ДЕЛАЙ:**

7. **Не держи длинные транзакции на Repeatable Read.** Они мешают VACUUM'у (Глава 6).

8. **Не используй Repeatable Read для интерактивных операций** — пользователь видит устаревшие данные.

### Метрики: как понять, что уровень изоляции выбран неправильно

**Метрика 1: Ошибки сериализации**

```sql
SELECT datname, conflicts
FROM pg_stat_database
WHERE datname = 'mydb';
```

Растущий `conflicts` → много прерываний на Serializable/Repeatable Read.

**Метрика 2: Длинные транзакции**

```sql
SELECT pid, now() - xact_start AS duration, state
FROM pg_stat_activity
WHERE state = 'active'
  AND xact_start IS NOT NULL
ORDER BY duration DESC;
```

Транзакции дольше 1 минуты на Repeatable Read → мешают VACUUM'у.

**Метрика 3: Раздувание таблиц**

```sql
SELECT schemaname, relname, n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

Много `n_dead_tup` → VACUUM не успевает (возможно, из-за длинных снимков).

### Итог подглавы 5.4

- **Read Committed** — `GetSnapshotData()` перед каждым SELECT, снимок живёт один запрос.
- **Repeatable Read** — `SavedSnapshot` в памяти Backend-процесса, снимок живёт всю транзакцию.
- **Предотвращение потерянных обновлений** — `EvalPlanQual` перечитывает строку перед UPDATE и прерывает транзакцию при конфликте.
- **Serializable** — SSI отслеживает зависимости между транзакциями и прерывает при циклах.
- **Атомарный UPDATE** — лучший паттерн для списания/начисления без блокировок.
- **Выбор уровня** — по задаче: CRUD → Read Committed, отчёты → Repeatable Read, финансы → Serializable.
- **Метрики** — `conflicts`, длинные транзакции, `n_dead_tup`.

## 5.5 Аномалии: потерянные обновления, неповторяемое чтение, фантомы

В подглавах 5.1-5.4 мы неоднократно упоминали аномалии. Теперь разберём **каждую** максимально подробно: что это, как воспроизвести, как предотвратить.

---

### 5.5.1 Потерянное обновление (Lost Update)

**Определение:** две транзакции читают одно и то же значение, обе на его основе записывают новое. Результат первой **теряется** — перезаписан второй.

### Как воспроизвести

```sql
-- Исходное состояние: quantity = 1

-- Транзакция А:
BEGIN;
SELECT quantity FROM products WHERE id = 42;  -- видит 1

-- Транзакция Б (в тот же момент):
BEGIN;
SELECT quantity FROM products WHERE id = 42;  -- видит 1

-- А:
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;

-- Б:
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;

-- Итог: quantity = 0. Оба «купили». Потерянное обновление.
```

### Почему это происходит

- Транзакция Б **не видит** изменения А, потому что работала со снимком **до** COMMIT А.
- При UPDATE Б **перечитывает** строку (Read Committed) → видит `quantity = 0` → но записывает **фиксированное** значение `0`, не проверяя, что значение изменилось.

### Как предотвратить

**Способ 1: Атомарный UPDATE (рекомендуется)**

```sql
UPDATE products SET quantity = quantity - 1 WHERE id = 42 AND quantity >= 1;
-- Один обновит (1 → 0), второй получит «0 rows affected».
```

**Способ 2: SELECT ... FOR UPDATE (пессимистично)**

```sql
BEGIN;
SELECT quantity FROM products WHERE id = 42 FOR UPDATE;  -- блокируем
-- Никто не изменит, пока мы не COMMIT
UPDATE products SET quantity = 0 WHERE id = 42;
COMMIT;
```

**Способ 3: Repeatable Read (оптимистично)**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT quantity FROM products WHERE id = 42;  -- снимок S1
UPDATE products SET quantity = 0 WHERE id = 42;
-- Если другая транзакция уже обновила → ОШИБКА сериализации
COMMIT;
```

**Способ 4: Оптимистичная проверка версии**

```sql
-- Добавляем колонку version
ALTER TABLE products ADD COLUMN version INT DEFAULT 0;

-- Обновляем с проверкой
UPDATE products 
SET quantity = 0, version = version + 1 
WHERE id = 42 AND version = $expected_version;
-- Если version изменилась → 0 rows affected → конфликт
```

---

### 5.5.2 Неповторяемое чтение (Non-Repeatable Read)

**Определение:** в рамках **одной транзакции** два одинаковых `SELECT` возвращают **разные** значения одной и той же строки.

### Как воспроизвести

```sql
-- Транзакция А:
BEGIN;
SELECT price FROM products WHERE id = 42;  -- видит 100000

-- Транзакция Б (в этот момент):
UPDATE products SET price = 120000 WHERE id = 42;
COMMIT;

-- А:
SELECT price FROM products WHERE id = 42;  -- видит 120000 (ДРУГОЕ!)

COMMIT;
```

### Почему это происходит

Read Committed создаёт **новый снимок** для каждого SELECT. Второй SELECT видит изменение, закоммиченное между первым и вторым.

### Как предотвратить

**Способ 1: Repeatable Read**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT price FROM products WHERE id = 42;  -- снимок S1: 100000
-- Б: UPDATE; COMMIT;
SELECT price FROM products WHERE id = 42;  -- всё ещё S1: 100000
COMMIT;
```

**Способ 2: Serializable**

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT price FROM products WHERE id = 42;  -- 100000
-- Б: UPDATE; COMMIT;
SELECT price FROM products WHERE id = 42;  -- всё ещё 100000
COMMIT;
```

**Когда неповторяемое чтение допустимо:**

- Пользовательский интерфейс — каждое обновление страницы должно видеть свежие данные.
- Обычные CRUD — не критично.

---

### 5.5.3 Фантомное чтение (Phantom Read)

**Определение:** в рамках **одной транзакции** два одинаковых `SELECT` возвращают **разное количество строк** (появились новые).

### Как воспроизвести

```sql
-- Транзакция А:
BEGIN;
SELECT * FROM products WHERE category = 'phone';  -- 10 строк

-- Транзакция Б (в этот момент):
INSERT INTO products (category, ...) VALUES ('phone', ...);
COMMIT;

-- А:
SELECT * FROM products WHERE category = 'phone';  -- 12 строк (ФАНТОМ!)

COMMIT;
```

### Отличие от неповторяемого чтения

| Аномалия | Что меняется | Почему |
|:---|:---|:---|
| **Неповторяемое чтение** | Значение **одной** строки | UPDATE/DELETE существующей строки |
| **Фантом** | **Количество** строк | INSERT новых строк |

### Как предотвратить

**В PostgreSQL: Repeatable Read предотвращает и фантомы!**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM products WHERE category = 'phone';  -- 10 строк (снимок S1)
-- Б: INSERT; COMMIT;
SELECT * FROM products WHERE category = 'phone';  -- всё ещё 10 строк (S1)
COMMIT;
```

**В стандарте SQL** Repeatable Read **не** гарантирует защиту от фантомов — только Serializable. Но в PostgreSQL реализация Repeatable Read **дополнительно** предотвращает фантомы.

---

### 5.5.4 Грязное чтение (Dirty Read)

**Определение:** транзакция видит **незакоммиченные** изменения другой транзакции.

### В PostgreSQL грязное чтение НЕВОЗМОЖНО

```sql
-- Транзакция А:
BEGIN;
UPDATE products SET price = 50000 WHERE id = 42;
-- НЕ COMMIT!

-- Транзакция Б:
SELECT price FROM products WHERE id = 42;
-- Видит СТАРОЕ значение (100000), а НЕ 50000!

-- А: ROLLBACK;
-- Б никогда не увидит 50000.
```

PostgreSQL **всегда** предотвращает грязное чтение — на **всех** уровнях изоляции. Даже Read Committed не видит незакоммиченные изменения.

---

### Сводная таблица аномалий

| Аномалия | Read Committed | Repeatable Read | Serializable |
|:---|:---:|:---:|:---:|
| **Грязное чтение** | ❌ Невозможно | ❌ Невозможно | ❌ Невозможно |
| **Потерянное обновление** | ⚠️ Возможно (без атомарного UPDATE) | ✅ Предотвращено | ✅ Предотвращено |
| **Неповторяемое чтение** | ⚠️ Возможно | ✅ Предотвращено | ✅ Предотвращено |
| **Фантом** | ⚠️ Возможно | ✅ Предотвращено (в PostgreSQL) | ✅ Предотвращено |

---

### Что делать при ошибке сериализации

При использовании Repeatable Read или Serializable может возникнуть:

```
ERROR: could not serialize access due to concurrent update
```

**Это не баг — это механизм защиты.** Приложение **должно** обрабатывать такие ошибки:

```go
func buyProduct(db *sql.DB, productID int, quantity int) error {
    maxRetries := 3
    for attempt := 0; attempt < maxRetries; attempt++ {
        tx, err := db.BeginTx(ctx, &sql.TxOptions{
            Isolation: sql.LevelRepeatableRead,
        })
        if err != nil {
            return err
        }
        defer tx.Rollback()

        result, err := tx.Exec(
            "UPDATE products SET quantity = quantity - $1 WHERE id = $2 AND quantity >= $1",
            quantity, productID,
        )
        if err != nil {
            // Проверяем ошибку сериализации (SQLSTATE 40001)
            if isSerializationError(err) {
                continue  // Повторяем транзакцию
            }
            return err
        }

        rowsAffected, _ := result.RowsAffected()
        if rowsAffected == 0 {
            return errors.New("товар не доступен")
        }

        return tx.Commit()
    }
    return errors.New("не удалось после 3 попыток")
}

func isSerializationError(err error) bool {
    // SQLSTATE 40001 = serialization_failure
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) {
        return pgErr.Code == "40001"
    }
    return false
}
```

### 💡 Практика: как предотвращать аномалии

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Атомарный UPDATE для списания/начисления:**
   ```sql
   UPDATE products SET quantity = quantity - 1 WHERE id = 42 AND quantity >= 1;
   ```

2. **Проверяй `RowsAffected()` в коде** — если 0, товар закончился или конфликт.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Обрабатывай ошибки сериализации** (SQLSTATE 40001) — повторяй транзакцию.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Serializable для простых операций** — избыточно.

**❌ НЕ ДЕЛАЙ:**

5. **Не используй SELECT + UPDATE с фиксированным значением** для конкурентных сценариев.

### Итог подглавы 5.5

- **Потерянное обновление** — решается атомарным UPDATE, FOR UPDATE, Repeatable Read.
- **Неповторяемое чтение** — разное значение одной строки, решается Repeatable Read.
- **Фантом** — разное количество строк, в PostgreSQL решается Repeatable Read.
- **Грязное чтение** — невозможно в PostgreSQL на всех уровнях.
- **Ошибка сериализации** — механизм защиты, приложение должно её обрабатывать.

## 5.6 Как PostgreSQL определяет видимость: пошаговый алгоритм

В подглавах 5.2-5.5 мы много раз говорили «PostgreSQL проверяет видимость строки». Теперь разберём **точный алгоритм** — по шагам, с учётом всех сущностей, которые мы ввели ранее.

---

### Задача

Транзакция читает строку. Нужно определить: **видна ли эта версия строки данной транзакции?**

### Входные данные

```
Строка (кортеж):
  t_xmin = 95   — кто создал эту версию
  t_xmax = 0    — кто удалил/обновил (0 = жива)
  t_ctid = (500,1)

Снимок транзакции (S100):
  xmin = 90
  xmax = 103
  xip_list = [101, 102]
```

### Шаг 1: Проверяем t_xmin (кто создал)

**Вопрос:** «Вижу ли я транзакцию, создавшую эту версию?»

```
t_xmin = 95

Алгоритм проверки:
  1. 95 < xmin (90)? → НЕТ
  2. 95 ≥ xmax (103)? → НЕТ
  3. 95 в xip_list [101, 102]? → НЕТ
  
Вывод: 95 закоммичена до нашего снимка → СОЗДАТЕЛЬ ВИДИМ.
```

**Если бы t_xmin = 101 (в xip_list):**

```
  1. 101 < 90? → НЕТ
  2. 101 ≥ 103? → НЕТ
  3. 101 в xip_list? → ДА → активная транзакция
  
Вывод: 101 ещё не закоммичена → СОЗДАТЕЛЬ НЕ ВИДИМ → строка НЕ видима.
```

**Особый случай: t_xmin = наша транзакция (100):**

```
t_xmin = 100 (мы сами)

Вывод: СОЗДАТЕЛЬ ВИДИМ (мы всегда видим свои изменения).
```

### Шаг 2: Проверяем t_xmax (кто удалил/обновил)

**Если t_xmax = 0:**
```
Строка жива — никто не удалял.
Если t_xmin видим → СТРОКА ВИДИМА.
```

**Если t_xmax = 200 (не ноль):**

```
Вопрос: «Подтверждено ли удаление?»

Алгоритм проверки (аналогично t_xmin):
  1. 200 < xmin (90)? → НЕТ
  2. 200 ≥ xmax (103)? → НЕТ
  3. 200 в xip_list [101, 102]? → НЕТ
     → 200 закоммичена → УДАЛЕНИЕ ПОДТВЕРЖДЕНО → строка НЕ видима.

Если бы 200 = 101 (в xip_list):
     → 101 активна → УДАЛЕНИЕ НЕ ПОДТВЕРЖДЕНО → строка ВИДИМА (старая версия).
```

### Шаг 3: Если строка не видима — идём по цепочке

Если `t_xmax` закоммичена (удаление подтверждено), строка **устарела**. Идём по `t_ctid` к следующей версии:

```
Слот 1: t_xmin=90, t_xmax=100, t_ctid=(500,2)
  → t_xmax=100 закоммичена → устарела → идём в слот 2.

Слот 2: t_xmin=100, t_xmax=0, t_ctid=(500,2)
  → Проверяем t_xmin=100 по снимку:
    → Видим? Да.
  → t_xmax=0 → жива.
  → СТРОКА ВИДИМА с quantity=0.
```

---

### Полный алгоритм в виде блок-схемы

```
НАЧАЛО: читаем кортеж (слот N)

  │
  ▼
ПРОВЕРЯЕМ t_xmin (кто создал):
  ├── t_xmin < xmin (закоммичена до нас) → ВИДИМ → идём к t_xmax
  ├── t_xmin в xip_list (активна) → НЕ ВИДИМ → идём по t_ctid
  ├── t_xmin ≥ xmax (после нас) → НЕ ВИДИМ → идём по t_ctid
  └── t_xmin = мы → ВИДИМ → идём к t_xmax

  │
  ▼
ПРОВЕРЯЕМ t_xmax (кто удалил):
  ├── t_xmax = 0 → ЖИВА → СТРОКА ВИДИМА (конец)
  ├── t_xmax в xip_list (активна) → УДАЛЕНИЕ НЕ ПОДТВЕРЖДЕНО → ВИДИМА (конец)
  ├── t_xmax ≥ xmax (после нас) → УДАЛЕНИЕ НЕ ПОДТВЕРЖДЕНО → ВИДИМА (конец)
  └── t_xmax < xmin (закоммичена до нас) → УДАЛЕНИЕ ПОДТВЕРЖДЕНО → НЕ ВИДИМА → идём по t_ctid

  │
  ▼
ИДЁМ ПО t_ctid к следующей версии (слот N+1) → повторяем алгоритм.
Если t_ctid указывает сама на себя → СТРОКА НЕ ВИДИМА (удалена).
```

---

### Практический пример: полный проход

```
Страница 500, четыре версии:

  Слот 1: t_xmin=90,  t_xmax=100, t_ctid=(500,2), quantity=1
  Слот 2: t_xmin=100, t_xmax=150, t_ctid=(500,3), quantity=0
  Слот 3: t_xmin=150, t_xmax=200, t_ctid=(500,4), quantity=5
  Слот 4: t_xmin=200, t_xmax=0,   t_ctid=(500,4), quantity=3

Снимок S250:
  xmin = 180
  xmax = 260
  xip_list = [220, 230]

ШАГ 1: Читаем слот 1.
  t_xmin=90:
    90 < 180? ДА → закоммичена до нас → ВИДИМА.
  t_xmax=100:
    100 < 180? ДА → закоммичена до нас → УДАЛЕНИЕ ПОДТВЕРЖДЕНО → НЕ ВИДИМА.
  → Идём по t_ctid → слот 2.

ШАГ 2: Читаем слот 2.
  t_xmin=100:
    100 < 180? ДА → ВИДИМА.
  t_xmax=150:
    150 < 180? ДА → УДАЛЕНИЕ ПОДТВЕРЖДЕНО → НЕ ВИДИМА.
  → Идём по t_ctid → слот 3.

ШАГ 3: Читаем слот 3.
  t_xmin=150:
    150 < 180? ДА → ВИДИМА.
  t_xmax=200:
    200 < 180? НЕТ.
    200 ≥ 260? НЕТ.
    200 в xip_list? НЕТ → 200 закоммичена → УДАЛЕНИЕ ПОДТВЕРЖДЕНО → НЕ ВИДИМА.
  → Идём по t_ctid → слот 4.

ШАГ 4: Читаем слот 4.
  t_xmin=200:
    200 < 180? НЕТ.
    200 ≥ 260? НЕТ.
    200 в xip_list? НЕТ → закоммичена → ВИДИМА.
  t_xmax=0 → ЖИВА.
  → СТРОКА ВИДИМА: quantity = 3.
```

---

### Связь с сущностями из предыдущих глав

| Сущность | Роль в алгоритме видимости |
|:---|:---|
| **Backend-процесс** | Выполняет алгоритм в контексте своей транзакции |
| **Снимок (xmin, xmax, xip_list)** | Хранится в памяти Backend-процесса, определяет видимость |
| **t_xmin / t_xmax / t_ctid** | Поля заголовка кортежа (Глава 2) |
| **Buffer Manager** | Читает страницы из shared_buffers (Глава 1) |
| **GetSnapshotData()** | Функция, собирающая снимок из shared memory |
| **VACUUM** | Удаляет старые версии, когда они не нужны ни одной транзакции (Глава 6) |

---

### Итог подглавы 5.6

- **Видимость строки** определяется по `t_xmin` (кто создал) и `t_xmax` (кто удалил/обновил).
- **Снимок** транзакции содержит `xmin`, `xmax`, `xip_list` и определяет, какие транзакции видимы.
- **Алгоритм** — последовательная проверка `t_xmin` → `t_xmax` → переход по `t_ctid`.
- **Цепочка версий** — если строка устарела, идём к следующей версии.
- **Backend-процесс** выполняет алгоритм в контексте своей транзакции.

## 5.7 Hint bits: кэширование статуса транзакций

В подглаве 5.6 мы разобрали алгоритм видимости. Но есть **проблема производительности**: на каждом чтении строки PostgreSQL должен проверять статус транзакции из `t_xmin`/`t_xmax` — закоммичена ли она, откатилась ли.

Эта проверка требует обращения к **статусу транзакций** в shared memory (структура `pg_xact`, ранее `pg_clog`). Если делать это для **каждой строки** при каждом чтении — это **очень дорого**.

**Решение:** hint bits — подсказки в заголовке кортежа.

---

### Что такое pg_xact и где он живёт

`pg_xact` (ранее `pg_clog`) — структура в **shared memory**, где хранится статус всех транзакций: закоммичена, активна, откатилась.

**Shared memory** — это область оперативной памяти, доступная **всем процессам** PostgreSQL (Глава 1). В ней лежат:

```
SHARED MEMORY (общая память):
│
├── shared_buffers (обычно 25% от RAM)
│   └── Кэш страниц данных (таблиц, индексов, FSM, VM)
│
├── WAL-буфер (обычно 16 МБ)
│   └── Буфер журнала изменений (WAL-записи)
│
├── pg_xact (статусы транзакций)
│   └── Для MVCC: закоммичена/активна/откатилась
│
├── pg_locks (блокировки)
│   └── Информация о блокировках
│
└── Статистика (pg_stat_*)
    └── Счётчики для мониторинга
```

Обращение к `pg_xact` требует **синхронизации** (спинлоки, как в WAL-буфере из Главы 1), потому что несколько процессов могут читать/писать одновременно.

**Hint bits решают эту проблему** — кэшируют статус в заголовке кортежа, чтобы не обращаться к `pg_xact` при каждом чтении.

---

### Проблема: проверка статуса транзакции — дорогая операция

Когда транзакция читает строку с `t_xmin = 95`, она должна узнать: **транзакция 95 закоммичена?**

Для этого PostgreSQL обращается к `pg_xact`:

```
pg_xact (в shared memory):

  Транзакция 95: ЗАКОММИЧЕНА
  Транзакция 96: ОТКАЧЕНА
  Транзакция 97: ЗАКОММИЧЕНА
  ...
  Транзакция 101: АКТИВНА
```

Этот доступ:

- Требует **синхронизации** (спинлоки, как в WAL-буфере из Главы 1).
- Происходит **для каждой строки** при чтении.
- При Seq Scan на 1 млн строк — 1 млн обращений к `pg_xact`.

**Это узкое место.**

---

### Решение: hint bits

**Hint bits** — это битовые флаги в заголовке кортежа (`t_infomask` из Главы 2), которые **кэшируют** статус транзакции прямо в строке.

Вспомни Главу 2:

```
t_infomask (2 байта) — флаги видимости:

  HEAP_XMIN_COMMITTED  — t_xmin точно закоммичена
  HEAP_XMIN_INVALID    — t_xmin откатилась
  HEAP_XMAX_COMMITTED  — t_xmax точно закоммичена
  HEAP_XMAX_INVALID    — t_xmax откатилась
```

**Идея:** когда транзакция **впервые** проверяет статус другой транзакции, она **записывает результат** в hint bits строки. Следующие читатели **не обращаются** к `pg_xact` — они видят готовый ответ в заголовке кортежа.

---

### Как это работает

```
ПЕРВОЕ ЧТЕНИЕ (транзакция 100 читает строку):

  Строка: t_xmin = 95, t_infomask = 0 (hint bits пусты)

  1. Backend-процесс проверяет t_xmin = 95.
  2. Обращается к pg_xact: «Транзакция 95 закоммичена?» → ДА.
  3. УСТАНАВЛИВАЕТ hint bit: HEAP_XMIN_COMMITTED = 1.
  4. Возвращает строку как видимую.

ВТОРОЕ ЧТЕНИЕ (любая другая транзакция):

  Строка: t_xmin = 95, t_infomask = HEAP_XMIN_COMMITTED (уже установлен!)

  1. Backend-процесс видит hint bit.
  2. НЕ обращается к pg_xact.
  3. Сразу знает: t_xmin закоммичена → строка видима (если t_xmax = 0).
```

---

### Что именно кэшируется

| Hint bit | Что означает | Когда устанавливается |
|:---|:---|:---|
| `HEAP_XMIN_COMMITTED` | `t_xmin` закоммичена | При первом чтении строки |
| `HEAP_XMIN_INVALID` | `t_xmin` откатилась | При первом чтении строки |
| `HEAP_XMAX_COMMITTED` | `t_xmax` закоммичена | При первом чтении строки |
| `HEAP_XMAX_INVALID` | `t_xmax` откатилась | При первом чтении строки |

---

### Визуализация: до и после hint bits

**До установки hint bits:**

```
Строка:
  t_xmin = 95
  t_xmax = 100
  t_infomask = 0 (ничего не установлено)

Чтение строки:
  1. Проверяем t_xmin=95 → идём в pg_xact → «закоммичена» (дорого!)
  2. Проверяем t_xmax=100 → идём в pg_xact → «закоммичена» (дорого!)
  3. Решаем видимость.
```

**После установки hint bits:**

```
Строка:
  t_xmin = 95
  t_xmax = 100
  t_infomask = HEAP_XMIN_COMMITTED | HEAP_XMAX_COMMITTED

Чтение строки:
  1. Видим HEAP_XMIN_COMMITTED → t_xmin закоммичена (без pg_xact!)
  2. Видим HEAP_XMAX_COMMITTED → t_xmax закоммичена (без pg_xact!)
  3. Решаем видимость — быстро!
```

---

### Когда hint bits устанавливаются

**При чтении (SELECT):**

```sql
SELECT * FROM products WHERE id = 42;
-- Если строка прочитана впервые, Backend-процесс:
--   1. Проверяет t_xmin в pg_xact.
--   2. Устанавливает HEAP_XMIN_COMMITTED или HEAP_XMIN_INVALID.
--   3. Проверяет t_xmax в pg_xact.
--   4. Устанавливает HEAP_XMAX_COMMITTED или HEAP_XMAX_INVALID.
--   5. Записывает обновлённый заголовок обратно на страницу.
```

**При UPDATE/DELETE:**

```sql
UPDATE products SET quantity = 0 WHERE id = 42;
-- UPDATE сам обращается к pg_xact для проверки конкурентности.
-- При этом также устанавливает hint bits.
```

**При VACUUM:**

```sql
VACUUM products;
-- VACUUM проходит по всем строкам и устанавливает hint bits
-- для тех, у кого они ещё не установлены.
-- Это «прогревает» таблицу — следующие чтения будут быстрее.
```

---

### Почему hint bits важны для производительности

**Без hint bits (первое чтение):**

```
Seq Scan по 1 млн строк:

  Для каждой строки:
    - Проверить t_xmin в pg_xact → синхронизация
    - Проверить t_xmax в pg_xact → синхронизация
  
  Итого: 2 млн обращений к pg_xact, 2 млн синхронизаций.
  Это МЕДЛЕННО.
```

**С hint bits (повторное чтение):**

```
Seq Scan по 1 млн строк:

  Для каждой строки:
    - Видим hint bits → проверка в заголовке кортежа (без pg_xact!)
    - Без синхронизаций.
  
  Итого: 0 обращений к pg_xact.
  Это БЫСТРО.
```

---

### Практический эффект

```
Первый SELECT после VACUUM:

  SELECT * FROM users WHERE id < 1000000;
  → 500 мс (устанавливает hint bits для 1 млн строк)

Второй SELECT того же запроса:

  SELECT * FROM users WHERE id < 1000000;
  → 100 мс (hint bits уже установлены!)
```

**Вот почему VACUUM важен не только для очистки** — он также «прогревает» hint bits, делая последующие чтения быстрее.

---

### Связь с сущностями из предыдущих глав

| Сущность | Роль |
|:---|:---|
| **t_infomask** | Поле заголовка кортежа (Глава 2) — где хранятся hint bits |
| **pg_xact** | Структура в shared memory, где хранится статус транзакций |
| **Shared memory** | Общая память для всех процессов (Глава 1) |
| **Backend-процесс** | Проверяет статус в pg_xact и устанавливает hint bits |
| **VACUUM** | «Прогревает» hint bits, проходя по всем строкам |
| **shared_buffers** | Страницы с установленными hint bits кэшируются |

---

### Итог подглавы 5.7

- **Hint bits** — флаги в `t_infomask`, кэширующие статус транзакции.
- **pg_xact** — структура в shared memory со статусами транзакций.
- **Проблема** — проверка статуса через `pg_xact` дорогая (синхронизации).
- **Решение** — установить hint bits при первом чтении, потом читать их вместо `pg_xact`.
- **Устанавливаются** — при SELECT, UPDATE, VACUUM.
- **Эффект** — второе чтение быстрее первого (hint bits уже установлены).
- **VACUUM** — не только очищает, но и «прогревает» hint bits.

## 5.8 Практика Go: анализ видимости строк

В предыдущих подглавах мы разобрали теорию MVCC. Теперь напишем **утилиту на Go**, которая показывает, как hint bits и версии строк выглядят на практике.

### Что будет утилита

Утилита `mvcc-inspect`:

1. Создаёт тестовую таблицу.
2. Выполняет несколько UPDATE, создавая версии строк.
3. Через `pageinspect` показывает `t_xmin`, `t_xmax`, `t_ctid`, hint bits.
4. Показывает, как VACUUM влияет на hint bits и цепочки версий.

### Полный код

```go
package main

import (
	"database/sql"
	"fmt"
	"log"
	"os"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// Подготовка
	mustExec(db, "CREATE EXTENSION IF NOT EXISTS pageinspect")
	mustExec(db, "DROP TABLE IF EXISTS products")
	mustExec(db, `
		CREATE TABLE products (
			id SERIAL PRIMARY KEY,
			name TEXT,
			quantity INT
		)
	`)

	// Вставляем строку
	mustExec(db, "INSERT INTO products (name, quantity) VALUES ('iPhone', 1)")

	fmt.Println("=== ПОСЛЕ INSERT ===\n")
	printHeapItems(db)

	// UPDATE 1
	mustExec(db, "UPDATE products SET quantity = 0 WHERE id = 1")
	fmt.Println("\n=== ПОСЛЕ UPDATE 1 ===\n")
	printHeapItems(db)

	// UPDATE 2
	mustExec(db, "UPDATE products SET quantity = 5 WHERE id = 1")
	fmt.Println("\n=== ПОСЛЕ UPDATE 2 ===\n")
	printHeapItems(db)

	// UPDATE 3
	mustExec(db, "UPDATE products SET quantity = 3 WHERE id = 1")
	fmt.Println("\n=== ПОСЛЕ UPDATE 3 ===\n")
	printHeapItems(db)

	// VACUUM
	mustExec(db, "VACUUM products")
	fmt.Println("\n=== ПОСЛЕ VACUUM ===\n")
	printHeapItems(db)
}

func mustExec(db *sql.DB, query string) {
	_, err := db.Exec(query)
	if err != nil {
		log.Fatal(err)
	}
}

func printHeapItems(db *sql.DB) {
	rows, err := db.Query(`
		SELECT 
			lp,
			lp_flags,
			lp_len,
			t_xmin,
			t_xmax,
			t_ctid,
			t_infomask
		FROM heap_page_items(get_raw_page('products', 0))
		WHERE lp_flags != 0
		ORDER BY lp;
	`)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()

	fmt.Printf("%-5s %-10s %-10s %-10s %-10s %-12s %-20s\n",
		"lp", "lp_flags", "t_xmin", "t_xmax", "t_ctid", "t_infomask", "hint bits")
	fmt.Println("----- ---------- ---------- ---------- ---------- ------------ --------------------")

	for rows.Next() {
		var lp, lpFlags, tXmin, tXmax int
		var tCtid string
		var tInfomask int
		if err := rows.Scan(&lp, &lpFlags, &tXmin, &tXmax, &tCtid, &tInfomask); err != nil {
			log.Fatal(err)
		}

		hints := decodeHintBits(tInfomask)
		fmt.Printf("%-5d %-10d %-10d %-10d %-10s %-12d %-20s\n",
			lp, lpFlags, tXmin, tXmax, tCtid, tInfomask, hints)
	}
}

func decodeHintBits(mask int) string {
	hints := ""
	if mask&0x0010 != 0 { // HEAP_XMIN_COMMITTED
		hints += "XMIN_COMMITTED "
	}
	if mask&0x0020 != 0 { // HEAP_XMIN_INVALID
		hints += "XMIN_INVALID "
	}
	if mask&0x0040 != 0 { // HEAP_XMAX_COMMITTED
		hints += "XMAX_COMMITTED "
	}
	if mask&0x0080 != 0 { // HEAP_XMAX_INVALID
		hints += "XMAX_INVALID "
	}
	if hints == "" {
		hints = "(пусто)"
	}
	return hints
}
```

### Пример вывода

```
=== ПОСЛЕ INSERT ===

lp    lp_flags   t_xmin     t_xmax     t_ctid      t_infomask  hint bits
----- ---------- ---------- ---------- ---------- ------------ --------------------
1     1          100        0          (0,1)       0           (пусто)

=== ПОСЛЕ UPDATE 1 ===

lp    lp_flags   t_xmin     t_xmax     t_ctid      t_infomask  hint bits
----- ---------- ---------- ---------- ---------- ------------ --------------------
1     1          100        101        (0,2)       0           (пусто)
2     1          101        0          (0,2)       0           (пусто)

=== ПОСЛЕ UPDATE 2 ===

lp    lp_flags   t_xmin     t_xmax     t_ctid      t_infomask  hint bits
----- ---------- ---------- ---------- ---------- ------------ --------------------
1     1          100        101        (0,2)       0           (пусто)
2     1          101        102        (0,3)       0           (пусто)
3     1          102        0          (0,3)       0           (пусто)

=== ПОСЛЕ UPDATE 3 ===

lp    lp_flags   t_xmin     t_xmax     t_ctid      t_infomask  hint bits
----- ---------- ---------- ---------- ---------- ------------ --------------------
1     1          100        101        (0,2)       0           (пусто)
2     1          101        102        (0,3)       0           (пусто)
3     1          102        103        (0,4)       0           (пусто)
4     1          103        0          (0,4)       0           (пусто)

=== ПОСЛЕ VACUUM ===

lp    lp_flags   t_xmin     t_xmax     t_ctid      t_infomask  hint bits
----- ---------- ---------- ---------- ---------- ------------ --------------------
4     1          103        0          (0,4)       0           (пусто)
```

**Что видно:**

- **После INSERT**: одна версия, `t_xmax = 0` (жива).
- **После UPDATE 1**: две версии — старая (`t_xmax = 101`) и новая (`t_xmin = 101`).
- **После UPDATE 2**: три версии — цепочка через `t_ctid`.
- **После UPDATE 3**: четыре версии.
- **После VACUUM**: старые версии удалены, осталась только актуальная.

### Что это даёт

Утилита показывает **физическую реальность** MVCC:

- Версии строк действительно лежат на странице.
- `t_xmax` меняется сразу при UPDATE.
- `t_ctid` связывает версии в цепочку.
- VACUUM физически удаляет старые версии.

## 5.9 Выводы и типичные ошибки

**Что мы узнали?**

MVCC — механизм, при котором читатели не блокируют писателей. Каждая транзакция работает со снимком данных, а изменения создают новые версии строк. Видимость определяется через `t_xmin`/`t_xmax` и снимок транзакции. Hint bits кэшируют статус транзакций для ускорения чтения. Потерянные обновления решаются атомарными UPDATE, а не MVCC.

**Типичные ошибки:**

- ❌ **Думать, что MVCC решает потерянные обновления.** MVCC решает читатель-писатель конфликты. Потерянные обновления решаются атомарным UPDATE, FOR UPDATE или Repeatable Read.

- ❌ **Использовать SELECT + UPDATE с фиксированным значением** в конкурентных сценариях. Это прямой путь к потерянным обновлениям.

- ❌ **Держать длинные транзакции на Repeatable Read.** Они мешают VACUUM'у очищать старые версии → раздувание таблиц.

- ❌ **Игнорировать ошибки сериализации** (SQLSTATE 40001). Приложение должно повторять транзакцию.

- ❌ **Не проверять RowsAffected() после UPDATE.** Если обновлено 0 строк — возможно, конфликт или товар закончился.

---

## 5.10 Для быстрого повторения

- **MVCC** — многоверсионное управление конкурентным доступом: читатели не блокируют писателей.
- **Версии строк** — UPDATE создаёт новую версию, старая помечается через `t_xmax`.
- **t_xmin / t_xmax / t_ctid** — поля заголовка кортежа (Глава 2).
- **Снимок** — `xmin`, `xmax`, `xip_list` — определяет видимые транзакции.
- **Read Committed** — новый снимок на каждый SELECT (`GetSnapshotData()`).
- **Repeatable Read** — один снимок на всю транзакцию (`SavedSnapshot`).
- **Serializable** — SSI отслеживает зависимости между транзакциями.
- **Атомарный UPDATE** — `SET quantity = quantity - 1 WHERE quantity >= 1` — решение потерянных обновлений.
- **Hint bits** — кэшируют статус транзакций в `t_infomask`, ускоряют чтение.
- **VACUUM** — удаляет старые версии и «прогревает» hint bits.

## 5.12 Ответы

### Ответ 1

MVCC (Multiversion Concurrency Control) — механизм, при котором каждая транзакция работает со снимком данных, а изменения создают новые версии строк. Читатели не блокируют писателей, потому что читают **снимок** — стабильную картину данных на момент начала транзакции, а не актуальные строки, которые могут быть заблокированы.

### Ответ 2

При UPDATE физически на странице появляются **две версии**:
- Старая версия: `t_xmax` меняется на ID транзакции, `t_ctid` указывает на новую.
- Новая версия: `t_xmin = ID транзакции`, `t_xmax = 0` (жива).

Старая версия не перезаписывается, а помечается как устаревшая.

### Ответ 3

`t_xmax = 100` означает «транзакция 100 пометила эту версию как удалённую/обновлённую». Это поле меняется **в момент UPDATE**, а не при COMMIT. COMMIT только **подтверждает** удаление — но `t_xmax` уже записан.

### Ответ 4

Снимок — это данные о том, какие транзакции видимы. Состоит из:
- `xmin` — минимальный ID транзакции (всё < xmin закоммичено).
- `xmax` — максимальный ID + 1 (всё ≥ xmax началось после нас).
- `xip_list` — список активных транзакций.

### Ответ 5

Read Committed вызывает `GetSnapshotData()` перед каждым SELECT — снимок живёт один запрос. Repeatable Read сохраняет снимок в памяти Backend-процесса (`SavedSnapshot`) и переиспользует его всю транзакцию.

### Ответ 6

Через `EvalPlanQual`: перед UPDATE PostgreSQL перечитывает строку. Если версия, которую видит транзакция (по своему снимку), отличается от актуальной — в Repeatable Read возникает ошибка сериализации.

### Ответ 7

Serializable использует SSI (Serializable Snapshot Isolation): PostgreSQL отслеживает зависимости между транзакциями (кто что читал/писал). Если образуется цикл зависимостей — одна из транзакций прерывается.

### Ответ 8

Атомарный UPDATE не читает значение заранее. Он проверяет условие `WHERE quantity >= 1` **в момент** UPDATE, после перечитывания строки. При конкуренции один UPDATE обновит строку, второй получит 0 rows affected.

### Ответ 9

Hint bits — флаги в `t_infomask`, кэширующие статус транзакции. При первом чтении Backend-процесс проверяет статус в `pg_xact` (в shared memory, с синхронизацией) и записывает результат в hint bits. Последующие чтения видят hint bits и не обращаются к `pg_xact`.

### Ответ 10

VACUUM не только удаляет старые версии, но и «прогревает» hint bits, проходя по всем строкам. Первый SELECT после VACUUM может быть медленным (устанавливает hint bits), но последующие — быстрыми.

### Ответ 11

Ошибка «could not serialize access due to concurrent update» (SQLSTATE 40001) — это механизм защиты от аномалий. Приложение должно:
1. Поймать ошибку.
2. Откатить транзакцию (ROLLBACK).
3. Повторить транзакцию (обычно с ограничением на число попыток).

## 5.13 Куда идти дальше?

Мы разобрали MVCC — как PostgreSQL обеспечивает конкурентный доступ. Но мы оставили **один важный вопрос**: что происходит со старыми версиями строк?

Каждый UPDATE создаёт новую версию. Старые версии остаются на странице. Если их не удалять:

- Таблица раздувается (bloat).
- Чтение замедляется (длинные цепочки `t_ctid`).
- Диск и кэш используются неэффективно.

**Кто удаляет старые версии? VACUUM.**
