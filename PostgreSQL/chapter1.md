## 1.0 Пролог: запрос, который требует надёжности

Ты написал бэкенд для интернет-магазина 🛒. Пользователь нажал «Сохранить» в профиле, и твой код отправил в базу простой запрос:

```sql
UPDATE users SET name = 'Alice' WHERE id = 1;
```

Что происходит дальше? База данных не просто «меняет строчку». Ей нужно **принять соединение**, **проверить права**, **найти данные на диске**, **изменить их**, и сделать это так, чтобы:

- 🔒 Параллельный запрос от другого пользователя не увидел «полуизменённые» данные.
- ⚡ При внезапном отключении электричества данные не исчезли.
- 🔄 Даже если база упадёт, её можно было восстановить за секунды.

❓ Вопрос: **какой механизм внутри PostgreSQL всё это обеспечивает?**

💡 Ответ: PostgreSQL запущен как **набор процессов операционной системы**. Это не «один процесс», а целая команда, где каждый делает свою работу. Когда говорят «архитектура процесса на соединение», имеют в виду, что для **каждого** подключающегося клиента PostgreSQL создаёт **отдельный процесс ОС**, который будет обслуживать только этого клиента. Это сделано для изоляции: если один клиент выполняет тяжёлый запрос, он не «вешает» остальных.

Все компоненты PostgreSQL — это **процессы**, а не потоки. У каждого процесса своя виртуальная память, и крах одного процесса (например, из-за бага в расширении) не затрагивает остальные. Цена такого подхода — большее потребление памяти (каждый процесс держит свою таблицу страниц) и чуть более дорогое переключение контекста по сравнению с потоками. Для типичных нагрузок в 50–200 соединений это не проблема.

## 1.2 Как клиент подключается к PostgreSQL: протокол и процесс

Прежде чем выполнять запрос, клиент должен **подключиться**. Клиент и PostgreSQL общаются по сети через **TCP-протокол** (по умолчанию порт 5432). Но TCP — это просто «труба», которая передаёт байты от клиента к серверу и обратно. Нужен ещё **протокол прикладного уровня**, который определяет, **что именно означают эти байты**. В PostgreSQL эту роль выполняет **PostgreSQL Wire Protocol**.

### 📡 Что такое PostgreSQL Wire Protocol

Это **бинарный протокол прикладного уровня**, который работает поверх TCP. Он определяет **формат каждого сообщения** между клиентом и сервером. Почему бинарный, а не текстовый (как HTTP)?

- ⚡ **Эффективность.** Числа передаются в нативном бинарном формате (integer как 4 байта, float как 8 байт), а не как текстовая строка. Это экономит трафик и процессорное время на парсинг.
- 🎯 **Однозначность.** Нет проблем с экранированием спецсимволов. Бинарный формат жёстко задан: поле всегда определённой длины, перепутать невозможно.
- 🌊 **Потоковая передача.** Сервер может начать отправлять строки результата **до того, как весь запрос выполнен до конца**. Это полезно для больших выборок: клиент получает первые строки сразу, а не ждёт, пока сервер соберёт все.

### 📦 Структура сообщений протокола

Каждое сообщение в протоколе имеет одинаковую структуру:

```
┌──────────────────────────────────────────────────────────┐
│  📨 Структура одного сообщения (для клиента и сервера)   │
├──────────┬───────────────────────────────────────────────┤
│ 1 байт   │ 4 байта  │ (N - 4) байт                      │
│ Тип      │ Длина    │ Тело сообщения                     │
│ сообщения│ сообщения│ (зависит от типа)                  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'Q' = Query │ длина всей│ 📝 Текст SQL-запроса            │
│             │ структуры │                                  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'T' = RowDescr│ ...   │ 📋 Описание колонок результата    │
├──────────┼────────────┼──────────────────────────────────┤
│ 'D' = DataRow│ ...    │ 📄 Одна строка данных результата  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'E' = Error │ ...     │ ❌ Код и текст ошибки             │
├──────────┼────────────┼──────────────────────────────────┤
│ 'Z' = ReadyForQuery│ 5│ ✅ Состояние: готов к новому запросу│
└──────────┴───────────────────────────────────────────────┘

📤 Примеры типов сообщений от клиента:
  'Q' — простой SQL-запрос
  'P' — Parse (подготовка параметризованного запроса)
  'B' — Bind (привязка параметров)
  'E' — Execute (выполнение подготовленного)

📥 Примеры типов сообщений от сервера:
  'R' — ответ аутентификации (AuthenticationXxx)
  'K' — ключ отмены запроса (BackendKeyData)
  'Z' — ReadyForQuery (сервер готов к новому запросу)
  'T' — RowDescription (описание колонок результата)
  'D' — DataRow (строка данных)
  'C' — CommandComplete (запрос выполнен, строк затронуто: N)
  'E' — ErrorResponse (ошибка)
  'N' — NoticeResponse (предупреждение)
```

### 🔐 Две фазы протокола (Startup и Normal)

Протокол PostgreSQL делится на две логические фазы: **Startup** (подключение и аутентификация) и **Normal** (работа с запросами).

**Важное разъяснение: как именно работают эти две фазы**

1. **Это НЕ два TCP-соединения.** Клиент устанавливает **одно** TCP-соединение с сервером (стандартное трёхстороннее рукопожатие: SYN, SYN-ACK, ACK), и весь дальнейший обмен идёт внутри этого одного соединения.
2. **Это НЕ хэндшейк TCP.** TCP-рукопожатие — это отдельный процесс на транспортном уровне, который происходит до отправки любого сообщения протокола PostgreSQL. Startup-фаза происходит уже **после** установки TCP-соединения, на прикладном уровне.
3. **Это логическое деление потока сообщений.** Внутри одного TCP-соединения сообщения идут последовательно:
  - **Сначала** клиент отправляет особое сообщение `StartupMessage` (без байта типа), затем происходит обмен сообщениями аутентификации — это фаза Startup.
  - **После** того как сервер отправляет `ReadyForQuery ('Z')`, фаза Startup завершена. С этого момента клиент может отправлять SQL-запросы (сообщения типа `'Q'`), а сервер — возвращать результаты — это фаза Normal.
  - TCP-соединение при этом **не прерывается и не пересоздаётся**. Байты обеих фаз передаются по одному и тому же TCP-каналу.

**Аналогия:** Представь телефонный звонок:

- **TCP-соединение** — это набор номера и поднятие трубки («алло?» — «алло!»).
- **Startup-фаза** — это представление: «Здравствуйте, это Алексей, соедините с отделом продаж». Секретарь проверяет, можно ли переключить.
- **Normal-фаза** — это разговор по существу: «Мне нужно узнать статус заказа №12345».

Весь разговор идёт по одному телефонному соединению, но логически делится на «представление» и «обсуждение вопроса».

```

  │                                                 │
  │  ╔══════════════════════════════════════════════╗│
  │  ║  TCP-рукопожатие (транспортный уровень)      ║│
  │  ║  SYN, SYN-ACK, ACK                           ║│
  │  ║  После этого TCP-соединение установлено,      ║│
  │  ║  начинается обмен на прикладном уровне        ║│
  │  ╚══════════════════════════════════════════════╝│
  │                                                 │
  │  === НАЧАЛО ФАЗЫ STARTUP (прикладной уровень) ===│
  │                                                 │
  │  StartupMessage (первое сообщение!)              │
  │  Тип: специальный (без байта типа)               │
  │  Содержит:                                       │
  │    • protocol_version: 3.0                      │

  │      "database" → "mydb"                         │
  │      "application_name" → "myapp"                │
  │      "client_encoding" → "UTF8"                  │
  │────────────────────────────────────────────────→│
  │                                                 │
  │  Сервер проверяет pg_hba.conf:                   │
  │  «Кто такой alice? С какого IP?                  │
  │   Какой метод аутентификации?»                  │
  │                                                 │
  │  ┌─ Если метод = trust (без пароля):             │
  │  │  AuthenticationOk ('R')                       │
  │  │←─────────────────────────────────────────────│
  │  │  BackendKeyData ('K') — ключ для отмены       │
  │  │←─────────────────────────────────────────────│
  │  │  ReadyForQuery ('Z') — "я готов!"            │
  │  │←─────────────────────────────────────────────│
  │  │                                              │
  │  └─ Если метод = scram-sha-256 (пароль):        │
  │     AuthenticationScramSha256 ('R')              │
  │     (сервер: "докажи, что знаешь пароль")        │
  │←───────────────────────────────────────────────│
  │     ClientScramSha256Response                   │
  │     (клиент: "вот доказательство")               │
  │────────────────────────────────────────────────→│
  │     ServerScramSha256Final                      │
  │     (сервер: "принято, вот моё подтверждение")   │
  │←───────────────────────────────────────────────│
  │     AuthenticationOk ('R')                      │
  │←───────────────────────────────────────────────│
  │     BackendKeyData ('K')                        │
  │←───────────────────────────────────────────────│
  │     ReadyForQuery ('Z')                         │
  │←───────────────────────────────────────────────│
  │                                                 │
  │  === КОНЕЦ ФАЗЫ STARTUP ===                      │
  │  === НАЧАЛО ФАЗЫ NORMAL ===                      │

```

После того как сервер отправляет `ReadyForQuery ('Z')`, фаза Startup завершена, и протокол переходит в фазу Normal **внутри того же самого TCP-соединения**.

### 🚪 Кто принимает соединение на стороне сервера

На стороне сервера работает главный процесс — **Postmaster**. Это **один процесс ОС**, который запускается самым первым и работает всё время, пока живёт PostgreSQL.

**Как устроен Postmaster:**

- Всё время висит в памяти и слушает порт 5432.
- Пока нет подключений, он **не потребляет CPU**: он ждёт на системном вызове `select()` (или `poll()`), который блокирует процесс до появления входящего TCP-запроса.
- Когда приходит новое подключение, Postmaster просыпается, проверяет `pg_hba.conf`, делает `fork()` (системный вызов, занимающий доли миллисекунды), создавая Backend-процесс, передаёт ему TCP-соединение и **немедленно возвращается к ожиданию** следующего подключения.
- Сам он **никогда не обрабатывает SQL-запросы** и не работает с данными.

**Потребление ресурсов:**

- Пока нет подключений: **0% CPU**, несколько мегабайт памяти.
- При шквале подключений: кратковременные всплески CPU на `fork()`, но в целом нагрузка минимальна.
- Postmaster — это «диспетчер», а не «рабочий». Он только распределяет входящие соединения.

Когда приходит новый клиент и устанавливает TCP-соединение, Postmaster:

1. ✅ Принимает TCP-соединение (трёхстороннее рукопожатие на транспортном уровне).
2. 📖 Читает StartupMessage (первое сообщение прикладного уровня).
3. 🔍 Проверяет по `pg_hba.conf`, разрешено ли подключение для этого пользователя с этого IP.
4. 🍴 Создаёт (через системный вызов `fork()`) новый процесс операционной системы — **Backend-процесс**.
5. 🔗 Передаёт ему TCP-соединение.
6. 🔄 Возвращается к прослушиванию порта.

С этого момента клиент общается **только со своим Backend-процессом**, который и проводит аутентификацию (фаза Startup), и обрабатывает SQL-запросы (фаза Normal) — всё внутри одного TCP-соединения.

### 💻 Как это выглядит в реальном Go-приложении

Рассмотрим типичное веб-приложение на Go, использующее пул соединений к PostgreSQL:

```go
// main.go — инициализация при старте сервера
db, _ := sql.Open("postgres", "host=localhost user=alice dbname=mydb")
db.SetMaxOpenConns(25)        // максимум 25 одновременных Backend-процессов
db.SetMaxIdleConns(10)        // до 10 простаивающих TCP-соединений
db.SetConnMaxIdleTime(5 * time.Minute) // закрыть idle-соединение через 5 мин

// Хэндлер — вызывается при HTTP-запросе
func getUsers(w http.ResponseWriter, r *http.Request) {
    rows, _ := db.Query("SELECT id, name FROM users")
    // ...
}
```

**Когда и как происходят TCP-соединение, Startup и Normal:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ВРЕМЕННАЯ ШКАЛА ЖИЗНИ ПРИЛОЖЕНИЯ                 │
│                                                                     │
│  t=0   Запуск приложения                                            │
│        sql.Open() — НИКАКИХ соединений не создаётся.                │
│        Только настройка пула в памяти.                              │
│                                                                     │
│  t=1   Первый HTTP-запрос (GET /users)                              │
│        Пул соединений пуст — нужно создать новое соединение.         │
│        ├── TCP-рукопожатие (SYN, SYN-ACK, ACK)                     │
│        ├── Postmaster делает fork() → создан Backend PID 100       │
│        ├── StartupMessage                                           │
│        ├── Аутентификация (scram-sha-256)                          │
│        ├── ReadyForQuery ('Z')                                     │
│        ├── Query ('Q') "SELECT ..."                                │
│        ├── DataRow, DataRow, ...                                   │
│        └── ReadyForQuery ('Z')                                     │
│        TCP-соединение остаётся ОТКРЫТЫМ → возвращается в пул (idle) │
│                                                                     │
│  t=2   Второй HTTP-запрос (GET /orders)                             │
│        Пул видит idle-соединение → использует его.                   │
│        ├── (TCP уже есть — рукопожатие пропускается)                │
│        ├── (Startup уже пройден — аутентификация пропускается)      │
│        ├── Query ('Q') "SELECT ..."                                │
│        ├── DataRow, DataRow, ...                                   │
│        └── ReadyForQuery ('Z')                                     │
│        Соединение снова возвращается в пул (idle)                    │
│        Все запросы обработал один и тот же процесс PID 100!          │
│                                                                     │
│  t=3   Два одновременных HTTP-запроса                               │
│        Пул даёт каждому СВОЁ TCP-соединение:                        │
│        ├── Запрос A → idle-соединение №1 → Backend PID 100          │
│        └── Запрос B → idle-соединение №2 → Backend PID 101          │
│        Два разных процесса, два разных TCP-соединения.               │
│                                                                     │
│  t=300 Если соединение простаивало > 5 мин (MaxIdleTime):           │
│        Go отправляет TCP FIN → соединение закрывается                │
│        Backend PID 100 завершается                                  │
│        Следующий запрос создаст новое TCP-соединение и новый процесс │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевой вывод:** `sql.Open()` не создаёт TCP-соединений. Соединение, fork() и аутентификация происходят **при первом реальном SQL-запросе**, если в пуле нет свободного idle-соединения. После завершения запроса TCP-соединение **не закрывается**, а возвращается в пул для повторного использования. StartupMessage и аутентификация происходят **ровно один раз** за всё время жизни TCP-соединения, а не для каждого SQL-запроса.

### 📌 PostgreSQL — это монолит, а не микросервисы

Прежде чем двигаться дальше, важно проговорить одну вещь, которая часто приводит к непониманию.

**PostgreSQL — это монолитное приложение, а не набор микросервисов.**

Все процессы, которые мы только что перечислили — Postmaster, Backend-процессы, Background Writer, WAL Writer, Checkpointer — это **один и тот же бинарный файл**, запущенный в разных режимах.

Когда ты запускаешь PostgreSQL, ты запускаешь **одну программу**:

```bash
# Запуск PostgreSQL — один бинарник
postgres
```

Дальше эта программа сама создаёт свои процессы через системный вызов `fork()`. Каждый новый процесс — это **копия того же самого бинарника**, но выполняющая **разную ветку кода** в зависимости от роли.

**Как это устроено в исходном коде:**

В исходном коде PostgreSQL есть один главный бинарный файл — `postgres`. Когда он запускается, он смотрит на параметры и решает, какую роль выполнять:

```c
// Упрощённый пример из исходного кода PostgreSQL
int main(int argc, char *argv[]) {
    if (строка запуска == "--walwriter") {
        WalWriterMain();          // код WAL Writer
    } else if (строка запуска == "--background-writer") {
        BackgroundWriterMain();   // код Background Writer
    } else if (строка запуска == "--checkpointer") {
        CheckpointerMain();       // код Checkpointer
    } else {
        PostmasterMain();         // код Postmaster (главный процесс)
    }
}
```

Postmaster при `fork()` передаёт дочернему процессу роль: «ты будешь Backend'ом», «ты будешь WAL Writer'ом», «ты будешь Checkpointer'ом». Дочерний процесс выполняет ту же программу, но заходит в нужную ветку кода.

**Buffer Manager — это библиотека, а не процесс:**

**Buffer Manager — это не процесс и не микросервис.** Это **набор функций** в исходном коде PostgreSQL, который **вкомпилирован** в тот же самый бинарный файл.

Когда Backend-процессу нужна страница, он **вызывает функцию** из этой библиотеки:

```c
// Backend-процесс вызывает функцию Buffer Manager
Buffer buffer = ReadBuffer(relation, block_number);

// ReadBuffer внутри:
// 1. Проверить shared_buffers (общая память)
// 2. Если нет — прочитать с диска
// 3. Вернуть указатель на буфер
```

Когда Background Writer обходит `shared_buffers` и сбрасывает грязные страницы, он **вызывает те же самые функции** Buffer Manager. Когда Checkpointer делает контрольную точку — **тоже вызывает их**.

Это как в твоём Go-приложении: у тебя есть пакет `bufferManager` с функциями `ReadPage()`, `WritePage()`, `EvictPage()`. Эти функции вызываются из разных горутин, но сам пакет — это просто код, а не отдельный сервис.

**Сравнение: монолит vs микросервисы:**

| Аспект | Микросервисы | PostgreSQL |
|:---|:---|:---|
| **Процессы** | Отдельные бинарники, отдельные машины | Один бинарник, несколько процессов ОС через `fork()` |
| **Обмен данными** | HTTP/gRPC/очереди сообщений | Общая память (shared memory) + системные вызовы |
| **Изоляция** | Полная: падение одного сервиса не трогает другие | Частичная: падение Backend-процесса не трогает Postmaster, но падение Postmaster роняет всё |
| **Buffer Manager** | Был бы отдельным сервисом | Набор функций, выполняется в контексте любого процесса |
| **Масштабирование** | Горизонтальное (больше машин) | Вертикальное (больше ядер, памяти на одной машине) |

**Почему это важно понимать:**

Когда мы говорим «Backend-процесс вызывает Buffer Manager» — это **вызов функции внутри того же процесса**, а не сетевое обращение к другому сервису.

Когда мы говорим «WAL Writer сбрасывает WAL-буфер» — это **другой процесс ОС**, но он запущен из **того же бинарного файла** и имеет доступ к **той же общей памяти**.

Когда мы говорим «Background Writer обходит shared_buffers» — он обращается к **той же области памяти**, к которой имеют доступ все процессы PostgreSQL.

**Аналогия:**

Представь, что PostgreSQL — это **одно большое Go-приложение**, скомпилированное в один бинарник. Внутри него:

- `main()` — это Postmaster.
- Воркеры — это Backend-процессы (только вместо горутин — процессы ОС через `fork()`).
- `go backgroundWriter()` — это Background Writer.
- `go walWriter()` — это WAL Writer.
- Пакет `bufferManager` — это Buffer Manager (набор функций, вызываемых из всех воркеров).

**Это не микросервисы. Это один монолит, разделённый на процессы ОС для изоляции памяти.**

### 🧵 Как 50 Backend-процессов работают на 12-ядерном сервере

Когда `max_connections = 50`, а физических ядер — 12 (24 потока с Hyper-Threading), все 50 процессов **выполняются конкурентно**, а не последовательными пачками по 24.

Планировщик операционной системы (Linux CFS) раздаёт кванты процессорного времени всем 50 процессам, постоянно переключаясь между ними:

```
┌─────────────────────────────────────────────────────────────────────┐
│              ВРЕМЯ → (кванты ~1-10 мс на процесс)                   │
│                                                                     │
│  Ядро 0: [PID 1][PID25][PID 1][PID 7][PID13][PID19][PID 1]...     │
│  Ядро 1: [PID 2][PID 8][PID14][PID20][PID 2][PID26][PID32]...     │
│  Ядро 2: [PID 3][PID 9][PID15][PID21][PID 3][PID27][PID33]...     │
│  Ядро 3: [PID 4][PID10][PID16][PID22][PID 4][PID28][PID34]...     │
│  ...                                                               │
│                                                                     │
│  Все 50 процессов продвигаются ОДНОВРЕМЕННО.                        │
│  Никто не ждёт «своей очереди» в пачке из 24 процессов.             │
└─────────────────────────────────────────────────────────────────────┘
```

Более того, большинство Backend-процессов **часто ждут не процессор, а диск или сеть**. Пока один процесс ждёт чтения страницы с диска (~5-10 мс), ядро ОС отдаёт его квант другому процессу. Поэтому PostgreSQL может эффективно обслуживать сотни соединений даже на небольшом количестве ядер.

**Ограничения:** при очень большом количестве процессов (500+) начинают сказываться два фактора:

- **Память:** каждый Backend-процесс потребляет 10-15 МБ RAM только на свою виртуальную память.
- **Переключение контекста:** планировщик ОС тратит всё больше времени на переключение между процессами вместо полезной работы.

Именно для этого используют **пул соединений** (PgBouncer): 5000 клиентов → 50 реальных Backend-процессов.

### 💡 Практика: сколько соединений ставить

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

- **Не ставь `max_connections = 5000` «на всякий случай».** Каждый Backend-процесс потребляет 10-15 МБ RAM, а 5000 процессов = 50-75 ГБ только на память.

**👍 СТОИТ СДЕЛАТЬ:**

- **Держи 50-200 соединений** на обычный сервер (8-16 ядер, 32-64 ГБ RAM).
- **Используй PgBouncer** перед PostgreSQL: 5000 клиентов → 50-200 реальных Backend-процессов.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

- Увеличивать `max_connections` до 1000+, если нет PgBouncer. Выигрыша не будет — процессы будут конкурировать за CPU и память.

**❌ НЕ ДЕЛАЙ:**

- **Не позволяй каждому микросервису открывать свой пул по 100 коннектов.** 20 микросервисов × 100 = 2000 соединений — база захлебнётся.

## 1.4 Память в PostgreSQL: shared_buffers

Backend-процесс обрабатывает запрос и работает с данными. Но данные лежат **на диске** 💿. Читать с диска — очень медленно (в тысячи раз медленнее, чем из оперативной памяти 🚀).

Поэтому PostgreSQL выделяет **общую область памяти** (shared memory), которую называют **shared_buffers**. Это кэш, в котором хранятся **копии страниц данных с диска**.

```
💿 Физический диск (медленно)          🚀 Оперативная память (быстро)
┌────────────────────┐              ┌────────────────────────┐
│ 📁 Файл таблицы     │              │   🗂️ shared_buffers     │
│ users (100 ГБ)     │              │   (обычно 25% от RAM)  │
│                    │   загрузка   │                        │
│ ┌────────────────┐ │◄────────────│ ┌────────────────────┐ │
│ │ 📄 страница 0   │ │             │ │ 📄 копия стр. 0    │ │
│ │ 📄 страница 1   │ │             │ │ 📄 копия стр. 5    │ │
│ │ 📄 страница 2   │ │             │ │ 📄 копия стр. 100  │ │
│ │ ...            │ │             │ │ ...                │ │
│ │ 📄 страница 100K│ │             │ │ (только часто      │ │
│ └────────────────┘ │             │ │  используемые)     │ │
└────────────────────┘              └────────────────────────┘
```

**Как это работает:**

1. Backend-процесс хочет прочитать строку с `id = 1`.
2. Он узнаёт, что эта строка лежит в **странице №100** (страница — это блок данных фиксированного размера, обычно 8 КБ).
3. Backend-процесс идёт в `shared_buffers`: «Есть тут копия страницы №100?»
  - ✅ **Если страница уже лежит в кэше** (в `shared_buffers`): Backend-процесс просто читает данные из оперативной памяти. Это быстро, обращения к диску не происходит.
  - ❌ **Если страницы в кэше нет**: Backend-процесс вынужден прочитать страницу №100 с диска, загрузить её копию в `shared_buffers`, и только потом прочитать данные уже из памяти. Это медленнее, потому что включает физическое чтение с диска.

**Кто управляет shared_buffers — Buffer Manager**

Все операции с `shared_buffers` — поиск страницы, загрузка с диска, вытеснение — выполняет **Buffer Manager**. Это не отдельный процесс, а **набор функций**, который работает в контексте каждого Backend-процесса (и фоновых процессов тоже) и управляет общей памятью.

Buffer Manager отвечает за:

- Поиск страницы в кэше по её номеру (хэш-таблица буферов).
- Загрузку страницы с диска, если её нет в кэше.
- Вытеснение старых страниц по алгоритму Clock-Sweep, когда нужно освободить место для новой.
- Отслеживание «грязных» страниц (изменённых в памяти, но не сброшенных на диск).

Именно Buffer Manager реализует алгоритм Clock-Sweep и решает, какую страницу вытеснить, когда кэш заполнен. Когда Backend-процессу нужна страница, он вызывает Buffer Manager, а тот уже внутри себя проверяет хэш-таблицу, загружает с диска или вытесняет старые страницы.

### 💡 Практика: как выбирать размер shared_buffers

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

- **Знай дефолт: 128 МБ** — это слишком мало для продакшена. PostgreSQL будет постоянно читать с диска.

**👍 СТОИТ СДЕЛАТЬ:**

- **На продакшене ставь 25% от RAM:**
  ```
  Сервер 64 ГБ RAM → shared_buffers = 16 ГБ
  Сервер 32 ГБ RAM → shared_buffers = 8 ГБ
  ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

- **Ставить больше 40% от RAM.** Операционная система тоже использует память для page cache — если отдать всё PostgreSQL, ОС начнёт свопить.

**❌ НЕ ДЕЛАЙ:**

- **Не ставь больше 8 ГБ без тестирования.** На больших значениях накладные расходы на управление кэшем могут съесть выгоду.

## 1.5 Грязные страницы и Background Writer

Когда Backend-процесс выполняет наш `UPDATE`, он изменяет копию страницы в `shared_buffers` (добавляет новую версию строки). Теперь копия страницы в памяти **отличается** от версии на диске.

Такая страница называется **«грязной» (dirty)** 📝 — она изменена в памяти, но ещё не записана на диск.

**Сколько версий строки создаётся при многих UPDATE?**
Если одну и ту же строку (например, `id=1`) изменить 10 раз, то в таблице будет лежать **10 версий этой строки**: одна текущая (актуальная) и девять старых (устаревших). PostgreSQL не перезаписывает старую версию — он создаёт новую версию строки на странице, а старая остаётся лежать мёртвым грузом. Потом специальный процесс VACUUM пометит место старых версий как свободное.

**Что происходит, когда shared_buffers заполняется?**
`shared_buffers` имеет фиксированный размер (выделяется при старте сервера). Когда все буферы заняты, а серверу нужно прочитать новую страницу с диска, Buffer Manager должен выбрать одну из старых страниц для **вытеснения** (замены). Для этого используется алгоритм **Clock-Sweep** (разновидность LRU — «вытеснение наиболее давно не использовавшейся»):

- У каждой страницы в кэше есть **счётчик обращений** (usage count) — число от 0 до 5 (определяется константой `BM_MAX_USAGE_COUNT` в исходном коде). Когда страницу читают или изменяют, счётчик увеличивается (но не выше 5). Он показывает, насколько часто страница используется.
- Специальный указатель (стрелка часов) циклически обходит все страницы в `shared_buffers`. При каждом проходе он смотрит на счётчик обращений текущей страницы. Если счётчик > 0, указатель уменьшает его на единицу и переходит к следующей странице. Если счётчик уже равен 0, страница становится кандидатом на вытеснение.
- Если вытесняемая страница «грязная», её **нужно сначала записать на диск**, а это занимает время ⏳.

**Как Background Writer решает, какие страницы сбрасывать?**

Background Writer 🟢 — это **один фоновый процесс ОС** (не поток!). Он создаётся при старте PostgreSQL и работает в бесконечном цикле. Он использует **тот же самый указатель** Clock-Sweep, что и обычное вытеснение в Buffer Manager. Он проходится по буферному кэшу и ищет страницы, которые:

1. **Грязные** (изменены в памяти, но не на диске).
2. Имеют **низкий счётчик обращений** (usage count близок к 0) — то есть редко используются.

Алгоритм работает так:

- Background Writer просыпается каждые `bgwriter_delay` миллисекунд (по умолчанию 200 мс).
- Он начинает обход страниц с того места, где остановился в прошлый раз (указатель никуда не сбрасывается).
- Для каждой страницы смотрит: грязная ли она? Если да — сбрасывает на диск и обнуляет грязный флаг (страница становится «чистой»).
- Если страница чистая или имеет высокий usage count — пропускает её (уменьшая счётчик, как и обычный Clock-Sweep).
- За один раунд сбрасывает не более `bgwriter_lru_maxpages` страниц (по умолчанию 100).

**Как Background Writer выполняется на процессоре:**

- Он работает **конкурентно** с остальными процессами на общих ядрах — никакого выделенного CPU или ядра для него нет.
- Планировщик Linux CFS ставит его в общую очередь со всеми остальными процессами (Backend'ы, WAL Writer, Checkpointer).
- Его работа очень лёгкая: обойти 100 страниц в памяти, проверить флаги, сбросить грязные на диск. Даже при высокой нагрузке он потребляет доли процента CPU.
- Если Background Writer не успевает за темпом изменений (из-за ограничения `bgwriter_lru_maxpages`), **обычные Backend-процессы берут запись грязных страниц на себя**.

**Зачем это нужно?** Когда Buffer Manager'у потребуется вытеснить страницу, он с большой вероятностью найдёт уже «чистую» страницу (которую Background Writer заранее сбросил) и сможет заменить её мгновенно, без ожидания записи на диск.

```
🧑‍💻 Backend-процесс:                  🟢 Background Writer:
«Изменил страницу №100               «Каждые 200 мс просыпаюсь,
 в памяти. Она стала грязной.»       иду по буферам.
                                     Страница №100 грязная?
                                     usage count высокий (5) —
                                     пропускаю, уменьшаю до 4.
                                     Страница №50 грязная?
                                     usage count = 0 —
                                     СБРАСЫВАЮ на диск!»
         │                                    │
         │                                    ▼
         │                           ┌────────────────┐
         │                           │ 💿 Диск: стр.  │
         │                           │ №50 обновлена  │
         │                           │ (№100 пока ждёт)│
         │                           └────────────────┘
```

### Может ли Backend-процесс сам записывать грязные страницы на диск?

**Да, может.** Backend-процесс не только умеет записывать грязные страницы на диск, но и **регулярно это делает**. Background Writer не даёт гарантии, что все грязные страницы будут сброшены заранее — он лишь **снижает вероятность** того, что Backend-процесс застрянет на записи.

**Когда Backend-процесс вынужден записывать грязные страницы:**

Это происходит в трёх сценариях:

**Сценарий 1: Вытеснение страницы.** Backend-процесс хочет прочитать новую страницу с диска, но все буферы в `shared_buffers` заняты. Buffer Manager по алгоритму Clock-Sweep находит страницу с usage count = 0 для вытеснения. Если эта страница **грязная**, Backend-процесс **сам** записывает её на диск перед тем, как загрузить на её место новую страницу. Это происходит синхронно, прямо во время выполнения пользовательского запроса, и добавляет задержку.

**Сценарий 2: Контрольная точка.** Во время контрольной точки Checkpointer 🔴 сбрасывает все грязные страницы. Но Checkpointer не работает в одиночку — он **координирует** процесс, а фактическую запись могут выполнять и обычные Backend-процессы. Если какой-то Backend-процесс обращается к странице, которую Checkpointer ещё не успел сбросить, он может взять эту работу на себя.

**Сценарий 3: Высокая скорость изменений.** Если приложение делает очень много UPDATE в минуту, Background Writer может просто не успевать за темпом. Его ограничение — `bgwriter_lru_maxpages` страниц за раунд (по умолчанию 100 каждые 200 мс = 500 страниц в секунду). Если грязные страницы появляются быстрее, они накапливаются, и Backend-процессам приходится сбрасывать их самостоятельно при вытеснении.

**Почему это проблема:** когда Backend-процесс записывает грязную страницу, он делает это **синхронно** — пользовательский запрос висит и ждёт завершения записи на диск. Background Writer делает ту же работу **асинхронно**, в фоне, поэтому пользовательские запросы не замечают задержки.

```
Обычная ситуация (Background Writer успевает):
  [Backend читает] [Backend читает] [Backend читает]
  [🟢 BW сбрасывает грязные страницы в фоне]

Проблемная ситуация (Background Writer не успевает):
  [Backend читает] [Backend ЖДЁТ записи] [Backend читает]
  [🟢 BW сбрасывает] [🟢 BW сбрасывает] [🟢 BW сбрасывает]
                    ^
                    Backend-процесс вынужден сам писать на диск
```

**Основные параметры Background Writer:**

| Параметр                  | По умолчанию | Что делает                                   |
| ------------------------- | ------------ | -------------------------------------------- |
| `bgwriter_delay`          | 200 мс       | Пауза между раундами                         |
| `bgwriter_lru_maxpages`   | 100          | Максимум страниц за раунд                    |
| `bgwriter_lru_multiplier` | 2.0          | Множитель агрессивности при высокой нагрузке |

### 💡 Практика: когда настраивать Background Writer

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

- **Знай дефолты:** `bgwriter_delay = 200 мс`, `bgwriter_lru_maxpages = 100`. Background Writer сбрасывает до 500 страниц/сек.

**👍 СТОИТ СДЕЛАТЬ:**

- **Увеличь `bgwriter_lru_maxpages` до 300-500**, если видишь частые синхронные записи Backend'ом (запросы тормозят на записи грязных страниц).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

- **Менять `bgwriter_delay` без причины.** Меньше задержка = больше CPU на фоновую запись. Больше задержка = грязные страницы накапливаются.

**❌ НЕ ДЕЛАЙ:**

- **Не отключай Background Writer.** Без него Backend'ы будут тонуть в синхронной записи при каждом вытеснении.

## 1.6 WAL: журнал предзаписи и WAL Writer

Теперь подумаем о надёжности. Представь: Backend-процесс изменил страницу в памяти (сделал её «грязной»), но Background Writer ещё не сбросил её на диск. Внезапно ⚡ отключается питание.

❓ **Что произойдёт?** Изменения в памяти потеряны. Пользователь думал, что его UPDATE сохранился, но на диске его нет.

💡 **Решение:** WAL (Write-Ahead Log — журнал предзаписи). Принцип прост:

> 🔐 **Любое изменение ДОЛЖНО быть записано в журнал WAL на диск ДО того, как соответствующая страница данных будет сброшена на диск.**

WAL — это **отдельный набор файлов на диске** (обычно в каталоге `pg_wal`), в который пишутся **записи об изменениях**. Запись в WAL очень быстрая, потому что это **последовательная запись** в конец файла ⚡ (в отличие от случайной записи в разные места файлов таблиц).

### 6.1 Подробное объяснение: shared_buffers и WAL-буфер — это разные сущности

**WAL-буфер** и **shared_buffers** — это **две совершенно разные области памяти**, которые решают разные задачи. Их часто путают, потому что оба находятся в разделяемой памяти (shared memory) и оба связаны с дисковым вводом-выводом.

**shared_buffers — кэш страниц данных.** Когда ты выполняешь `SELECT * FROM users WHERE id = 1`, Backend-процессу нужна страница, содержащая эту строку. Он читает её в `shared_buffers` с диска (если её там ещё нет) и работает с ней в памяти. Когда ты делаешь `UPDATE`, он изменяет эту же страницу прямо в `shared_buffers`, делая её «грязной». Позже Background Writer или Checkpointer сбросят её в файл таблицы на диске. `shared_buffers` — это **рабочая область** для данных. Все операции чтения и изменения страниц таблиц и индексов проходят через неё.

**WAL-буфер — буфер журнала изменений.** Когда Backend-процесс выполняет `UPDATE`, он **одновременно** с изменением страницы в `shared_buffers` записывает **запись об изменении** в WAL-буфер. Это не копия страницы и не сами данные строки — это **логическое описание изменения**: «транзакция 12345 изменила страницу №100, смещение 456: записать байты XYZ». WAL-буфер — это **маленький кольцевой буфер**, куда все Backend-процессы дописывают свои WAL-записи в порядке их совершения. WAL Writer периодически сбрасывает накопленные записи в файлы `pg_wal/` на диске. При COMMIT сброс происходит принудительно.

**Как это выглядит в памяти:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    🚀 ОПЕРАЦИОННАЯ ПАМЯТЬ (RAM)                      │
│                                                                     │
│  ┌────────────────────────────────────┐  ┌────────────────────────┐ │
│  │       🗂️ shared_buffers            │  │   📝 WAL-буфер          │ │
│  │       (кэш СТРАНИЦ ДАННЫХ)         │  │   (буфер ЖУРНАЛА)       │ │
│  │       Размер: до 25% RAM (ГБ)      │  │   Размер: ~16 МБ        │ │
│  │                                    │  │                        │ │
│  │  ┌──────┐ ┌──────┐ ┌──────┐       │  │  [ЗАПИСЬ1][ЗАПИСЬ2]...│ │
│  │  │Стр. 0│ │Стр. 5│ │Стр.100│ ...   │  │  последовательный      │ │
│  │  │(8 КБ)│ │(8 КБ)│ │(8 КБ)│       │  │  поток байт            │ │
│  │  └──────┘ └──────┘ └──────┘       │  │                        │ │

│  └────────────────────────────────────┘  └────────────────────────┘ │
│           ↑          ↑                             ↑                │
│           │          │                             │                │
│  ┌────────┴──────────┴──────┐           ┌───────────┴──────────┐   │
│  │  🟢 Background Writer    │           │  🟡 WAL Writer        │   │
│  │  Сбрасывает грязные      │           │  Сбрасывает буфер     │   │
│  │  страницы в файлы таблиц │           │  в файлы pg_wal/     │   │
│  └──────────────────────────┘           └──────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────────────────────────────────────────────────────┐
│                         💿 ДИСК                                      │
│                                                                     │
│  ┌──────────────────────────┐    ┌──────────────────────────────┐  │
│  │  📁 Файлы таблиц         │    │   📁 Файлы WAL (pg_wal/)    │  │
│  │  /base/DBOID/RELOID      │    │   000000010000000000000001   │  │
│  │  Содержат: страницы      │    │   Содержат: WAL-записи       │  │
│  │  с актуальными данными   │    │   (история всех изменений)   │  │
│  └──────────────────────────┘    └──────────────────────────────┘  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевое отличие в сценариях использования:**

**Сценарий: чтение данных (`SELECT`)**
- Backend-процесс обращается **только** к `shared_buffers` через Buffer Manager.
- WAL-буфер **не используется вообще**, потому что никаких изменений нет.

**Сценарий: изменение данных (`UPDATE`)**
- Backend-процесс:
  1. Находит страницу в `shared_buffers` через Buffer Manager (или загружает с диска).
  2. Изменяет страницу в `shared_buffers` → страница становится «грязной».
  3. **Одновременно** записывает описание изменения в **WAL-буфер**.
- Это две **параллельные** операции с разными областями памяти.

**Сценарий: восстановление после сбоя**
- PostgreSQL читает **только** файлы WAL (`pg_wal/`), «доприменяет» изменения к страницам в файлах таблиц.
- `shared_buffers` в этот момент пуст (сервер только что запустился).

**Почему WAL-буфер такой маленький?**

`wal_buffers` по умолчанию = 16 МБ (или 1/32 от `shared_buffers`, если `shared_buffers` большой).

Причины:

1. **Данные сбрасываются быстро.** WAL Writer сбрасывает буфер каждые 200 мс, а при COMMIT — мгновенно. Данные не задерживаются надолго.
2. **Последовательная запись.** В отличие от `shared_buffers`, где страницы читаются и пишутся в случайном порядке, WAL — это **один непрерывный поток**. Маленького буфера достаточно, чтобы сгладить пики.
3. **Экономия памяти.** Большой WAL-буфер не даёт выигрыша: если сервер упадёт, всё, что не сброшено в файлы WAL, потеряется.

### 6.2 Как WAL-записи попадают в WAL-буфер и к WAL Writer

Мы сказали: «Backend-процесс записывает изменение в WAL-буфер». Но как это происходит **технически**? Как несколько десятков Backend-процессов одновременно пишут в один буфер, не мешая друг другу? И как WAL Writer узнаёт, что пора сбрасывать данные на диск?

Вот полный путь — от формирования WAL-записи до физической записи на диск.

#### Шаг 1: Backend-процесс формирует WAL-запись

Когда Backend-процесс выполняет `UPDATE`, он изменяет страницу в `shared_buffers`. Но **перед тем как изменить страницу**, он должен сформировать **WAL-запись** — описание того, что именно он собирается изменить.

WAL-запись содержит:
- **LSN** (Log Sequence Number) — порядковый номер записи в журнале. Монотонно возрастающее число, указывающее позицию записи в WAL-потоке.
- **Тип операции** — что именно произошло: вставка кортежа, обновление, удаление, создание индекса и т.д.
- **Номер страницы** — какую страницу в каком файле изменяет эта операция.
- **Смещение внутри страницы** — в каком месте страницы будут изменения.
- **Сами данные** — байты, которые нужно записать (новая версия кортежа, изменение заголовка и т.д.).

```
Backend-процесс выполняет UPDATE users SET name='Alice' WHERE id=1:

1. Нашёл страницу №100 в shared_buffers.
2. Нашёл кортеж в слоте 5.
3. Сформировал WAL-запись:
   ┌────────────────────────────────────────────────┐
   │ LSN: 5/789ABC123 (позиция в WAL-потоке)        │
   │ Тип: HEAP_UPDATE                               │
   │ Страница: 100 (файл таблицы users)             │
   │ Смещение: 456 (позиция кортежа на странице)    │
   │ Данные: новая версия кортежа (имя='Alice')     │
   └────────────────────────────────────────────────┘
4. Теперь нужно записать эту WAL-запись в WAL-буфер.
```

#### Шаг 2: Запись в WAL-буфер через спинлок

WAL-буфер — это **общая область памяти** (shared memory). В неё пишут **все** Backend-процессы одновременно. Чтобы они не мешали друг другу (не перезаписали чужие данные), PostgreSQL использует **спинлок** (spinlock) — примитив синхронизации.

**Как работает запись в WAL-буфер:**

```
WAL-буфер (кольцевой, 16 МБ):
┌──────────────────────────────────────────────────────────────────┐
│ [запись 1][запись 2][запись 3]...[свободное место]...            │
│                                ↑                                 │
│                          текущая позиция (LSN)                    │
└──────────────────────────────────────────────────────────────────┘

Backend-процесс хочет записать новую WAL-запись:

1. Захватывает спинлок WALInsertLock.
   (если другой процесс держит спинлок — крутится в цикле и ждёт)

2. Проверяет: есть ли свободное место в WAL-буфере?
   → Да: 
     • Копирует свою WAL-запись в свободное место.
     • Продвигает указатель текущей позиции LSN вперёд.
     • Отпускает спинлок.
     • ГОТОВО. WAL-запись теперь в буфере.

   → Нет (буфер заполнен):
     • Отпускает спинлок.
     • ЖДЁТ, пока WAL Writer сбросит буфер на диск.
     • После сброса снова захватывает спинлок и записывает.
```

**Ключевой момент:** запись в WAL-буфер — это **копирование байтов в память**. Это очень быстрая операция (микросекунды), даже с учётом ожидания спинлока.

#### Шаг 3: WAL Writer сбрасывает буфер на диск

WAL Writer — это фоновый процесс, который **не знает**, какие записи появились в буфере. Он просто **периодически просыпается** (каждые `wal_writer_delay` = 200 мс) и сбрасывает всё, что накопилось.

**Но есть и другой механизм — более умный:**

Когда Backend-процесс записывает в WAL-буфер, он **проверяет, сколько места осталось**. Если буфер заполнен больше чем на определённый порог (`wal_writer_flush_after`, по умолчанию 1 МБ), Backend-процесс **сам сигнализирует WAL Writer'у**: «Проснись и сбрось!»

```
Backend-процесс записал WAL-запись.
Проверил: WAL-буфер заполнен на 12 МБ из 16 МБ.
Порог: wal_writer_flush_after = 1 МБ (новых данных с прошлого сброса).

→ Backend-процесс ставит флаг «пора сбрасывать».
→ WAL Writer просыпается раньше, чем через 200 мс.
→ Сбрасывает буфер на диск.
```

Это не блокирует Backend-процесс — он просто «будит» WAL Writer'а и продолжает свою работу.

#### Шаг 4: Сброс на диск — как это происходит физически

WAL Writer сбрасывает буфер в файлы `pg_wal/`. Технически:

1. WAL Writer берёт текущую позицию LSN — сколько данных накопилось в буфере.
2. Выполняет системный вызов `write()` — копирует байты из WAL-буфера (в RAM) в **page cache операционной системы** (тоже в RAM, но уже под управлением ядра ОС).
3. Выполняет системный вызов `fsync()` — заставляет ядро ОС **физически записать** данные из page cache на диск (на SSD/NVMe/HDD).

```
WAL-буфер (shared memory PostgreSQL)
    │
    │ write() — копирование в page cache ядра ОС
    ▼
Page Cache (память ядра ОС)
    │
    │ fsync() — физическая запись на диск
    ▼
Файлы WAL (pg_wal/) на диске
```

**Важно:** только после успешного `fsync()` данные гарантированно на диске. Если сервер упадёт между `write()` и `fsync()` — данные потеряны (они были только в page cache, который очищается при сбое).

#### Шаг 5: COMMIT — принудительный сброс

Когда транзакция выполняет `COMMIT`, Backend-процесс **не ждёт** WAL Writer'а. Он сам:

1. Захватывает спинлок.
2. Записывает WAL-запись о COMMIT в буфер.
3. Отпускает спинлок.
4. **Сам** выполняет `fsync()` — сбрасывает весь WAL-буфер (включая свои записи) на диск.
5. Ждёт завершения `fsync()`.
6. Только после этого отправляет клиенту «COMMIT успешен».

Это гарантирует: любая транзакция, получившая подтверждение COMMIT, **физически** записана в файлы WAL на диске.

|:---|:---|:---|

### 6.3 Что будет, если сбой произошёл, когда записи ещё в WAL-буфере?

Это критически важный вопрос. **Да, если сбой происходит в момент, когда записи были только в WAL-буфере (в RAM) и не были сброшены на диск — эти изменения будут потеряны.** Но PostgreSQL спроектирован так, чтобы **минимизировать это окно потерь** до миллисекунд. И для любого изменения, которое получило `COMMIT`, это окно закрывается полностью.

Сброс WAL-буфера на диск происходит **не только** через WAL Writer. Есть два независимых механизма:

**Механизм 1: WAL Writer (фоновый, асинхронный).** WAL Writer просыпается каждые `wal_writer_delay` миллисекунд (по умолчанию 200 мс) и сбрасывает накопившиеся записи из WAL-буфера в файлы `pg_wal/`. Это фоновая операция: она не привязана к конкретной транзакции и не даёт гарантий для каждой отдельной записи. **Окно уязвимости:** до 200 мс.

**Механизм 2: Принудительный сброс при COMMIT (синхронный).** Когда транзакция выполняет `COMMIT`, PostgreSQL **не ждёт** следующего пробуждения WAL Writer. Он **принудительно** сбрасывает WAL-буфер на диск немедленно через системный вызов `fsync()`, который гарантирует физическую запись на диск. Только после успешного завершения `fsync()` клиент получает ответ «COMMIT выполнен». **Окно уязвимости:** 0 мс для закоммиченных транзакций.

**Сценарий A: Сбой до COMMIT.** Транзакция сделала UPDATE (запись в WAL-буфере), но не сделала COMMIT. Сбой питания. **Результат:** изменение потеряно. Но это нормально — транзакция не была подтверждена, клиент не получил «COMMIT успешен».

**Сценарий B: Сбой сразу после COMMIT.** Транзакция сделала COMMIT, PostgreSQL принудительно сбросил WAL-буфер через `fsync()`, клиент получил подтверждение. Через микросекунду — сбой. **Результат:** изменение НЕ потеряно. WAL-запись гарантированно на диске. При восстановлении PostgreSQL применит её.

**Сценарий C: Асинхронный COMMIT (исключение).** В режиме `synchronous_commit = off` COMMIT **не ждёт** сброса WAL на диск. В этом режиме окно потерь для закоммиченных транзакций может составлять до `wal_writer_delay` × 3 (по умолчанию до 600 мс). Используется для некритичных данных, где скорость важнее гарантии.

**Визуализация:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ВРЕМЯ →                                           │
│                                                                     │
│  WAL Writer сбрасывает буфер каждые 200 мс:                         │
│  [сброс]──────────[сброс]──────────[сброс]──────────[сброс]──       │
│      ↑                ↑                ↑                ↑           │
│                                                                     │
│  Транзакция A:                                                      │
│    UPDATE ─── COMMIT (fsync!)                                      │
│    │          │                                                     │
│    │          └─ принудительный сброс, гарантия                      │
│                                                                     │
│  Транзакция B:                                                      │
│    UPDATE ──────────────────── 💥 СБОЙ                               │
│    │                                                                 │
│    └─ без COMMIT: запись в WAL-буфере, но не на диске → ПОТЕРЯНА   │
│                                                                     │
│  Транзакция C:                                                      │
│    UPDATE ─── [WAL Writer сбросил] ─── 💥 СБОЙ                       │
│    │              │                                                  │
│    │              └─ запись попала на диск случайно                  │
│    └─ без COMMIT: запись на диске, но транзакция не подтверждена     │
│       → при восстановлении будет ОТКАЧЕНА (rollback)                │
└─────────────────────────────────────────────────────────────────────┘
```

```
🧑‍💻 Backend-процесс:                  🟡 WAL Writer:
«Я изменил страницу №100.           «Сбрасываю WAL-буфер
 Сначала записываю это               в файлы WAL на диске
 изменение в WAL-буфер»              каждые wal_writer_delay мс»
         │                                    │
         ▼                                    ▼
┌────────────────┐                  ┌────────────────┐
│ 📝 WAL-буфер    │─────────────────→│ 💿 Файлы WAL   │
│ (в RAM)        │   сброс на диск  │ (в pg_wal/)    │
└────────────────┘                  └────────────────┘

💥 ЕСЛИ ПРОИЗОШЁЛ СБОЙ:
  1. 📄 Страница №100 в файле таблицы на диске — старая версия.
  2. Но в файлах WAL (pg_wal/) есть запись: «изменить страницу №100 так-то».
  3. 🔄 При восстановлении PostgreSQL читает WAL-файлы
     и «доприменяет» изменения к страницам таблиц → данные не потеряны!
```

🔴 **Почему WAL Writer критически важен?**

- Если WAL-запись не попала на диск (в файлы `pg_wal`) до сбоя → изменение **потеряно навсегда**.
- Если страница таблицы не попала на диск до сбоя → не страшно, она восстановится из файлов WAL.

### 💡 Практика: когда жертвовать Durability ради скорости

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

- **Держи `synchronous_commit = on` для критичных данных** (платежи, заказы, аккаунты). Потеря даже одной закоммиченной транзакции недопустима.

**👍 СТОИТ СДЕЛАТЬ:**

- **Используй `synchronous_commit = off` для некритичных данных:**
  ```sql
  -- На уровне транзакции
  SET synchronous_commit = off;
  INSERT INTO sessions ...;
  ```
  Подходит для: сессий, кэшей, логов, счётчиков просмотров. Потеря последних 200-600 мс данных при сбое — не катастрофа.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

- **Менять `synchronous_commit` глобально.** Лучше управлять на уровне транзакций — там, где нужна скорость.

**❌ НЕ ДЕЛАЙ:**

- **Не отключай `synchronous_commit` глобально, не подумав.** Если упадёт сервер, потеряются последние транзакции во **всех** таблицах, включая критические.

## 1.7 Checkpointer: контрольные точки

Представь, что сервер работал год без сбоев, а потом упал 💥. WAL-файлы за год — это сотни гигабайт. При восстановлении PostgreSQL пришлось бы перечитывать **все WAL-файлы с самого начала**, что заняло бы часы ⏳.

💡 **Решение:** Checkpointer 🔴.

**Checkpointer** — это фоновый процесс, который **раз в несколько минут** (по умолчанию 5 минут) делает **контрольную точку**:

1. 💾 **Сбрасывает ВСЕ «грязные» страницы** из `shared_buffers` в файлы таблиц на диске.
2. 🏁 **Отмечает в WAL**: «В этом месте все страницы на диске актуальны. При восстановлении можно начинать отсюда, а не с самого начала».

```
❌ Без Checkpointer:                 ✅ С Checkpointer:
Восстановление:                      Восстановление:
[читать все WAL-файлы с 0]           [пропустить до последней контрольной точки]
│                                    │
▼                                    ▼
⏳ Часы чтения WAL                    ⚡ Минуты чтения WAL
```

2. ✏️ Backend-процесс изменяет страницу в памяти → страница становится «грязной».
3. 📝 Backend-процесс формирует WAL-запись и записывает её в WAL-буфер (через спинлок).
4. 🟡 **WAL Writer** сбрасывает WAL-буфер в файлы WAL на диске → изменение защищено от сбоя. Если WAL Writer ещё не сбросил, а транзакция делает COMMIT — Backend-процесс сам вызывает `fsync()`.
5. 🟢 Когда-нибудь позже **Background Writer** найдёт эту страницу при обходе (когда её usage count станет низким) и сбросит в файл таблицы на диске. Если Background Writer не успевает — **Backend-процесс сделает это сам** при вытеснении страницы.
6. 🔴 Раз в 5 минут **Checkpointer** сбросит **все** грязные страницы и отметит контрольную точку.

## 1.9 Выводы и типичные ошибки

**Что мы узнали?**

PostgreSQL — это ансамбль процессов ОС: Postmaster (диспетчер, слушает порт 5432, делает `fork()` для каждого нового подключения), Backend-процессы (по одному на TCP-соединение, обрабатывают Parse → Rewrite → Plan → Execute), Background Writer (ленивый сброс «грязных» страниц из `shared_buffers`), WAL Writer (сброс WAL-буфера в файлы `pg_wal/`), Checkpointer (контрольные точки для быстрого восстановления). Buffer Manager управляет общим кэшем `shared_buffers` через алгоритм Clock-Sweep. WAL (журнал предзаписи) гарантирует сохранность данных: изменения всегда попадают в WAL на диск до того, как страницы данных сбрасываются в файлы таблиц.

**Типичные ошибки:**

- ❌ **Путать WAL Writer и Background Writer.** Первый пишет последовательный журнал изменений в `pg_wal/` — это гарантия Durability (сохранности при сбое). Второй сбрасывает случайные страницы данных из `shared_buffers` в файлы таблиц — это оптимизация производительности (чтобы при вытеснении не ждать записи на диск).
- ❌ **Думать, что** `UPDATE` **меняет строку на месте.** В PostgreSQL это `INSERT` новой версии строки + пометка старой (`t_xmax`). Без периодического VACUUM таблица «распухает» от старых версий.
- ❌ **Игнорировать настройку Checkpointer.** Слишком большой `checkpoint_timeout` → долгое восстановление после сбоя (много WAL-файлов). Слишком маленький → чрезмерная нагрузка на дисковую подсистему (частые массовые сбросы).
- ❌ **Ставить** `max_connections` **слишком большим.** Каждый Backend-процесс потребляет 10–15 МБ RAM только на свою виртуальную память. 1000 соединений = 10–15 ГБ только на процессы, ещё до начала обработки запросов.
- ❌ **Думать, что** `sql.Open()` **в Go создаёт TCP-соединения.** `sql.Open()` только парсит DSN и настраивает пул в памяти. TCP-рукопожатие, `fork()` и аутентификация происходят при первом `db.Query()`/`db.Exec()`, если в пуле нет свободного idle-соединения.
- ❌ **Считать, что Background Writer гарантирует отсутствие синхронной записи Backend'ом.** Background Writer — оптимизация, а не гарантия. При высоком темпе изменений или заполненном `shared_buffers` Backend-процесс будет вынужден сам сбрасывать грязные страницы при вытеснении, что добавляет задержку к пользовательским запросам.

## 1.10 Для быстрого повторения

- **Postmaster** — один процесс ОС, слушает порт 5432, при подключении делает `fork()`, создавая Backend-процесс. Пока нет подключений — спит на `select()`, 0% CPU.
- **Backend Process** — по одному на TCP-соединение. Выполняет Parse → Rewrite → Plan → Execute. Может сам сбрасывать грязные страницы при вытеснении.
- **PostgreSQL — монолит.** Все процессы (Postmaster, Backend, Background Writer, WAL Writer, Checkpointer) — это один бинарный файл, запущенный в разных режимах через `fork()`. Buffer Manager — набор функций внутри этого бинарника, а не отдельный процесс.
- **shared_buffers** — общий кэш страниц данных в RAM. Buffer Manager (подсистема, не процесс) управляет им через Clock-Sweep: usage count 0–5, вытеснение при 0, если страница грязная — синхронная запись на диск.
- **WAL (Write-Ahead Log)** — изменения пишутся в журнал (`pg_wal/`) до попадания в файлы таблиц. Запись в WAL-буфер — через спинлок WALInsertLock. WAL Writer сбрасывает асинхронно (каждые 200 мс или при пороге 1 МБ), COMMIT — синхронно (`fsync()` самим Backend-процессом). Окно потерь для незакоммиченных транзакций — до 200 мс, для закоммиченных — 0.
- **Background Writer** — лениво сбрасывает грязные страницы с usage count = 0 в фоне (каждые 200 мс, до 100 страниц за раунд). Оптимизация, не гарантия.
- **Checkpointer** — раз в 5 минут сбрасывает ВСЕ грязные страницы и отмечает контрольную точку в WAL для быстрого восстановления.
- **PostgreSQL Wire Protocol** — бинарный протокол поверх TCP. Две фазы в одном TCP-соединении: Startup (аутентификация, 1 раз) и Normal (SQL-запросы).
- **Процессы vs потоки:** PostgreSQL использует процессы для изоляции памяти. Цена — большее потребление RAM (10–15 МБ на процесс) и более дорогое переключение контекста. Для 50–200 соединений это не проблема; для тысяч — используют пул соединений (PgBouncer).

## 1.12 Ответы

### Ответ 1

Архитектура «процесс на соединение» решает проблему **изоляции**: крах одного клиентского соединения не затрагивает остальные, ошибка в памяти одного процесса не распространяется на другие. PostgreSQL использует процессы, а не потоки, по историческим причинам (в 90-х потоки были нестабильны на Unix) и ради полной изоляции памяти. **Trade-off:** большее потребление RAM (каждый процесс — своя таблица страниц, 10–15 МБ) и более дорогое переключение контекста (переключение процессов тяжелее, чем потоков). Для 50–200 соединений это некритично; для тысяч — используют пул соединений (PgBouncer).

### Ответ 2

Протокол делится на **Startup** (подключение и аутентификация) и **Normal** (работа с запросами). TCP-рукопожатие (SYN, SYN-ACK, ACK) происходит **до** отправки любого сообщения протокола PostgreSQL — это транспортный уровень. StartupMessage отправляется **после** установки TCP-соединения — это первое сообщение прикладного уровня. Это НЕ одно и то же: TCP-рукопожатие — транспорт, Startup — прикладной уровень. Обе фазы протокола работают внутри одного TCP-соединения, которое не прерывается между ними.

### Ответ 3

`sql.Open()` **не создаёт TCP-соединений** — только парсит DSN и настраивает пул в памяти. TCP-рукопожатие, `fork()` (создание Backend-процесса Postmaster'ом) и аутентификация происходят при **первом** `db.Query()` **или** `db.Exec()`, если в пуле нет свободного idle-соединения. После завершения запроса TCP-соединение не закрывается, а возвращается в пул для повторного использования. StartupMessage и аутентификация происходят ровно один раз за жизнь TCP-соединения.

### Ответ 4

`shared_buffers` — общая область памяти (shared memory), кэш страниц данных с диска. Выделяется при старте сервера (обычно 25% от RAM). **Buffer Manager** — подсистема (не процесс!), работающая в контексте каждого Backend-процесса; управляет `shared_buffers`: поиск страницы по хэш-таблице, загрузка с диска, вытеснение по **Clock-Sweep**. Алгоритм Clock-Sweep: у каждой страницы есть usage count (0–5); указатель циклически обходит страницы, уменьшая usage count на 1 за проход; страница с usage count = 0 становится кандидатом на вытеснение; если она грязная — сначала синхронная запись на диск.

### Ответ 5

«Грязная» страница — страница в `shared_buffers`, изменённая в памяти, но ещё не записанная на диск. **Background Writer** — фоновый процесс, который лениво сбрасывает грязные страницы с usage count = 0 в фоне, чтобы при вытеснении Buffer Manager находил уже «чистые» страницы и не ждал записи. **Backend-процесс вынужден сам записывать грязные страницы в трёх сценариях:** (1) вытеснение — все буферы заняты, Clock-Sweep выбрал грязную страницу с usage=0, Backend синхронно записывает её перед загрузкой новой; (2) помощь Checkpointer'у — при контрольной точке Backend сбрасывает страницы, к которым обращается, если Checkpointer ещё не обработал их; (3) высокий темп изменений — Background Writer не успевает (ограничение ~500 страниц/сек), грязные страницы накапливаются.

### Ответ 6

`shared_buffers` хранит **копии страниц данных** (строки таблиц). Размер — гигабайты. Используется для чтения (`SELECT`) и записи (`UPDATE`). `WAL-буфер` хранит **описания изменений** (WAL records: «транзакция X изменила страницу Y»). Размер — ~16 МБ. Используется только для записи. **Причины маленького размера WAL-буфера:** (1) данные сбрасываются быстро — каждые 200 мс WAL Writer'ом и мгновенно при COMMIT; (2) последовательная запись в WAL — маленького буфера достаточно для сглаживания пиков; (3) экономия памяти — всё, что не сброшено на диск, потеряется при сбое, большой буфер не даёт выигрыша.

### Ответ 7

Запись в WAL-буфер сериализуется через **спинлок WALInsertLock**. Backend-процесс: (1) захватывает спинлок (если он занят — крутится в цикле, ожидая освобождения); (2) проверяет, есть ли свободное место в буфере; (3) если есть — копирует WAL-запись, продвигает указатель LSN, отпускает спинлок; (4) если места нет — отпускает спинлок, ждёт сброса WAL Writer'ом, затем повторяет. Спинлок — это примитив синхронизации, который блокирует доступ к общей памяти для всех процессов, кроме одного.

### Ответ 8

**(а) Сбой до COMMIT:** записи в WAL-буфере (RAM) потеряны. Это нормально — транзакция не была подтверждена, клиент не получил «COMMIT успешен», с точки зрения ACID она считается откаченной. **(б) Сбой сразу после COMMIT:** потеря невозможна. При COMMIT Backend-процесс **сам** вызывает `fsync()`, не дожидаясь WAL Writer'а. Клиент получает подтверждение только после успешного `fsync()`. При восстановлении изменение будет применено из WAL. **(в)** `synchronous_commit = off`**:** COMMIT не ждёт сброса WAL на диск. Окно потерь для закоммиченных транзакций — до `wal_writer_delay` × 3 (по умолчанию до 600 мс). Используется для некритичных данных, где скорость важнее гарантии сохранности.

### Ответ 9

Background Writer и Checkpointer решают **разные задачи**. Background Writer проактивно сбрасывает редко используемые грязные страницы в фоне, чтобы при вытеснении не было задержки (оптимизация производительности). Checkpointer периодически сбрасывает **все** грязные страницы и отмечает контрольную точку в WAL. **Контрольная точка решает проблему времени восстановления:** без неё после сбоя пришлось бы читать все WAL-файлы с самого начала (часы), с ней — только от последней контрольной точки (минуты). Checkpointer также гарантирует, что все изменения в конечном счёте попадают в файлы таблиц.

### Ответ 10

**Конкурентно.** Планировщик Linux CFS раздаёт кванты времени (1–10 мс) всем 50 процессам, постоянно переключаясь между ними. Никто не ждёт очереди пачками по 24. Пока одни процессы ждут дискового ввода-вывода (~5–10 мс), ядро отдаёт их кванты другим. **Ограничения при 500+ процессах:** (1) память — каждый процесс 10–15 МБ, 500 процессов = 5–7.5 ГБ только на виртуальную память; (2) переключение контекста — планировщик тратит всё больше времени на переключение вместо полезной работы. Решение — пул соединений (PgBouncer).

### Ответ 11

Высокий `shared_blks_read` означает, что страницы читаются с диска, а не берутся из кэша `shared_buffers`. Для повторного запроса это указывает на то, что нужные страницы были **вытеснены** из кэша между выполнениями. Возможные причины: (1) `shared_buffers` слишком мал для рабочего набора данных; (2) между запросами другие операции загрузили много новых страниц, вытеснив старые (алгоритм Clock-Sweep); (3) Background Writer не справляется, грязные страницы накапливаются, и при вытеснении происходит интенсивная запись, что косвенно может влиять на доступность кэша. Решение: увеличить `shared_buffers` или оптимизировать запрос, чтобы читать меньше страниц.

## 1.14 Чек-лист

| Компонент                    | Тип                        | Функция                                                                                                              |
| ---------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Postmaster**               | 1 процесс ОС               | Слушает порт 5432, принимает TCP, читает StartupMessage, делает `fork()`. Спит на `select()`, 0% CPU без подключений |
| **Backend Process**          | Процесс ОС (на соединение) | Аутентификация, Parse → Rewrite → Plan → Execute. Может сам сбрасывать грязные страницы при вытеснении               |
| **PostgreSQL Wire Protocol** | Бинарный протокол          | 'Q' — запрос, 'T' — описание колонок, 'D' — строка, 'Z' — готов. Startup + Normal в одном TCP-соединении             |
| **shared_buffers**           | Общая память (ГБ)          | Кэш страниц данных. Buffer Manager управляет через Clock-Sweep                                                       |
| **WAL-буфер**                | Общая память (~16 МБ)      | Буфер журнала изменений. Только запись. Сброс: асинхронно (200 мс) + синхронно при COMMIT                            |
| **WALInsertLock**            | Спинлок                    | Сериализует запись в WAL-буфер. Только один процесс пишет одновременно                                                 |
| **Background Writer**        | 1 процесс ОС               | Каждые 200 мс сбрасывает грязные страницы с usage=0 (до 100). Оптимизация, не гарантия                               |
| **WAL Writer**               | 1 процесс ОС               | Сбрасывает WAL-буфер в `pg_wal/` через `write()` + `fsync()`. COMMIT — Backend сам вызывает `fsync()`               |
| **Checkpointer**             | 1 процесс ОС               | Раз в 5 мин сбрасывает ВСЕ грязные страницы, отмечает точку восстановления                                           |
| **Buffer Manager**           | Подсистема (код в бинарнике) | Управляет `shared_buffers`: поиск, загрузка, вытеснение, Clock-Sweep. Выполняется в контексте любого процесса      |
| **Планировщик ОС (CFS)**     | Ядро Linux                 | Кванты 1–10 мс, конкурентное выполнение 50 процессов на 12 ядрах                                                     |

🔐 **Ключевая идея:** PostgreSQL — это **монолит**: один бинарник, несколько процессов ОС через `fork()`. Изменения пишутся в WAL на диск **до** попадания в файлы таблиц. Один Backend-процесс = одно TCP-соединение = много SQL-запросов. `fork()` — при установке соединения, не на каждый запрос. Background Writer снижает вероятность синхронной записи Backend'ом, но не исключает её. Запись в WAL-буфер сериализуется спинлоком, сброс на диск — `write()` + `fsync()`.
