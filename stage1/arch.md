# 🏗️ Этап 1: Архитектура PostgreSQL и путь одного запроса

### 📝 1. Структура: «От конкретного к абстрактному»

Представь: ты написал бэкенд для интернет-магазина 🛒. Пользователь нажал «Сохранить» в профиле, и твой код отправил в базу простой запрос:

```sql
UPDATE users SET name = 'Alice' WHERE id = 1;
```

Что происходит дальше? База данных не просто «меняет строчку». Ей нужно **принять соединение**, **проверить права**, **найти данные на диске**, **изменить их**, и сделать это так, чтобы:

- 🔒 Параллельный запрос от другого пользователя не увидел «полуизменённые» данные.
- ⚡ При внезапном отключении электричества данные не исчезли.
- 🔄 Даже если база упадёт, её можно было восстановить за секунды.

❓ Вопрос: **какой механизм внутри PostgreSQL всё это обеспечивает?**

💡 Ответ: PostgreSQL запущен как **набор процессов операционной системы**. Это не «один процесс», а целая команда, где каждый делает свою работу. Когда говорят «архитектура процесса на соединение», имеют в виду, что для **каждого** подключающегося клиента PostgreSQL создаёт **отдельный процесс ОС**, который будет обслуживать только этого клиента. Это сделано для изоляции: если один клиент выполняет тяжёлый запрос, он не «вешает» остальных.

Все компоненты PostgreSQL — это **процессы**, а не потоки. У каждого процесса своя виртуальная память, и крах одного процесса (например, из-за бага в расширении) не затрагивает остальные. Цена такого подхода — большее потребление памяти (каждый процесс держит свою таблицу страниц) и чуть более дорогое переключение контекста по сравнению с потоками. Для типичных нагрузок в 50–200 соединений это не проблема.

### 🔌 2. Как клиент подключается к PostgreSQL: протокол и процесс

Прежде чем выполнять запрос, клиент должен **подключиться**. Клиент и PostgreSQL общаются по сети через **TCP-протокол** (по умолчанию порт 5432). Но TCP — это просто «труба», которая передаёт байты от клиента к серверу и обратно. Нужен ещё **протокол прикладного уровня**, который определяет, **что именно означают эти байты**. В PostgreSQL эту роль выполняет **PostgreSQL Wire Protocol**.

#### 📡 Что такое PostgreSQL Wire Protocol

Это **бинарный протокол прикладного уровня**, который работает поверх TCP. Он определяет **формат каждого сообщения** между клиентом и сервером. Почему бинарный, а не текстовый (как HTTP)?

- ⚡ **Эффективность.** Числа передаются в нативном бинарном формате (integer как 4 байта, float как 8 байт), а не как текстовая строка. Это экономит трафик и процессорное время на парсинг.
- 🎯 **Однозначность.** Нет проблем с экранированием спецсимволов. Бинарный формат жёстко задан: поле всегда определённой длины, перепутать невозможно.
- 🌊 **Потоковая передача.** Сервер может начать отправлять строки результата **до того, как весь запрос выполнен до конца**. Это полезно для больших выборок: клиент получает первые строки сразу, а не ждёт, пока сервер соберёт все.

#### 📦 Структура сообщений протокола

Каждое сообщение в протоколе имеет одинаковую структуру:

```
┌──────────────────────────────────────────────────────────┐
│  📨 Структура одного сообщения (для клиента и сервера)   │
├──────────┬───────────────────────────────────────────────┤
│ 1 байт   │ 4 байта  │ (N - 4) байт                      │
│ Тип      │ Длина    │ Тело сообщения                     │
│ сообщения│ сообщения│ (зависит от типа)                  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'Q' = Query │ длина всей│ 📝 Текст SQL-запроса            │
│             │ структуры │                                  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'T' = RowDescr│ ...   │ 📋 Описание колонок результата    │
├──────────┼────────────┼──────────────────────────────────┤
│ 'D' = DataRow│ ...    │ 📄 Одна строка данных результата  │
├──────────┼────────────┼──────────────────────────────────┤
│ 'E' = Error │ ...     │ ❌ Код и текст ошибки             │
├──────────┼────────────┼──────────────────────────────────┤
│ 'Z' = ReadyForQuery│ 5│ ✅ Состояние: готов к новому запросу│
└──────────┴───────────────────────────────────────────────┘

📤 Примеры типов сообщений от клиента:
  'Q' — простой SQL-запрос
  'P' — Parse (подготовка параметризованного запроса)
  'B' — Bind (привязка параметров)
  'E' — Execute (выполнение подготовленного)

📥 Примеры типов сообщений от сервера:
  'R' — ответ аутентификации (AuthenticationXxx)
  'K' — ключ отмены запроса (BackendKeyData)
  'Z' — ReadyForQuery (сервер готов к новому запросу)
  'T' — RowDescription (описание колонок результата)
  'D' — DataRow (строка данных)
  'C' — CommandComplete (запрос выполнен, строк затронуто: N)
  'E' — ErrorResponse (ошибка)
  'N' — NoticeResponse (предупреждение)
```

#### 🔐 Две фазы протокола (Startup и Normal)

Протокол PostgreSQL делится на две логические фазы: **Startup** (подключение и аутентификация) и **Normal** (работа с запросами).

**Важное разъяснение: как именно работают эти две фазы**

1. **Это НЕ два TCP-соединения.** Клиент устанавливает **одно** TCP-соединение с сервером (стандартное трёхстороннее рукопожатие: SYN, SYN-ACK, ACK), и весь дальнейший обмен идёт внутри этого одного соединения.

2. **Это НЕ хэндшейк TCP.** TCP-рукопожатие — это отдельный процесс на транспортном уровне, который происходит до отправки любого сообщения протокола PostgreSQL. Startup-фаза происходит уже **после** установки TCP-соединения, на прикладном уровне.

3. **Это логическое деление потока сообщений.** Внутри одного TCP-соединения сообщения идут последовательно:
   - **Сначала** клиент отправляет особое сообщение `StartupMessage` (без байта типа), затем происходит обмен сообщениями аутентификации — это фаза Startup.
   - **После** того как сервер отправляет `ReadyForQuery ('Z')`, фаза Startup завершена. С этого момента клиент может отправлять SQL-запросы (сообщения типа `'Q'`), а сервер — возвращать результаты — это фаза Normal.
   - TCP-соединение при этом **не прерывается и не пересоздаётся**. Байты обеих фаз передаются по одному и тому же TCP-каналу.

**Аналогия:** Представь телефонный звонок:
- **TCP-соединение** — это набор номера и поднятие трубки («алло?» — «алло!»).
- **Startup-фаза** — это представление: «Здравствуйте, это Алексей, соедините с отделом продаж». Секретарь проверяет, можно ли переключить.
- **Normal-фаза** — это разговор по существу: «Мне нужно узнать статус заказа №12345».

Весь разговор идёт по одному телефонному соединению, но логически делится на «представление» и «обсуждение вопроса».

##### 🔑 Фаза 1: Startup (подключение и аутентификация)

```
👤 Клиент                                🖥️ Сервер (Postmaster → Backend)
  │                                                 │
  │  ╔══════════════════════════════════════════════╗│
  │  ║  TCP-рукопожатие (транспортный уровень)      ║│
  │  ║  SYN, SYN-ACK, ACK                           ║│
  │  ║  После этого TCP-соединение установлено,      ║│
  │  ║  начинается обмен на прикладном уровне        ║│
  │  ╚══════════════════════════════════════════════╝│
  │                                                 │
  │  === НАЧАЛО ФАЗЫ STARTUP (прикладной уровень) ===│
  │                                                 │
  │  StartupMessage (первое сообщение!)              │
  │  Тип: специальный (без байта типа)               │
  │  Содержит:                                       │
  │    • protocol_version: 3.0                      │
  │    • пары ключ-значение:                         │
  │      "user" → "alice"                            │
  │      "database" → "mydb"                         │
  │      "application_name" → "myapp"                │
  │      "client_encoding" → "UTF8"                  │
  │────────────────────────────────────────────────→│
  │                                                 │
  │  Сервер проверяет pg_hba.conf:                   │
  │  «Кто такой alice? С какого IP?                  │
  │   Какой метод аутентификации?»                  │
  │                                                 │
  │  ┌─ Если метод = trust (без пароля):             │
  │  │  AuthenticationOk ('R')                       │
  │  │←─────────────────────────────────────────────│
  │  │  BackendKeyData ('K') — ключ для отмены       │
  │  │←─────────────────────────────────────────────│
  │  │  ReadyForQuery ('Z') — "я готов!"            │
  │  │←─────────────────────────────────────────────│
  │  │                                              │
  │  └─ Если метод = scram-sha-256 (пароль):        │
  │     AuthenticationScramSha256 ('R')              │
  │     (сервер: "докажи, что знаешь пароль")        │
  │←───────────────────────────────────────────────│
  │     ClientScramSha256Response                   │
  │     (клиент: "вот доказательство")               │
  │────────────────────────────────────────────────→│
  │     ServerScramSha256Final                      │
  │     (сервер: "принято, вот моё подтверждение")   │
  │←───────────────────────────────────────────────│
  │     AuthenticationOk ('R')                      │
  │←───────────────────────────────────────────────│
  │     BackendKeyData ('K')                        │
  │←───────────────────────────────────────────────│
  │     ReadyForQuery ('Z')                         │
  │←───────────────────────────────────────────────│
  │                                                 │
  │  === КОНЕЦ ФАЗЫ STARTUP ===                      │
  │  === НАЧАЛО ФАЗЫ NORMAL ===                      │
  │  (TCP-соединение то же самое, байты идут дальше) │
```

После того как сервер отправляет `ReadyForQuery ('Z')`, фаза Startup завершена, и протокол переходит в фазу Normal **внутри того же самого TCP-соединения**.

##### 📝 Фаза 2: Normal (работа с запросами)

```
👤 Клиент                                🖥️ Сервер
  │                                                 │
  │  === ФАЗА NORMAL (продолжение того же TCP-соединения) ===
  │                                                 │
  │  Query ('Q')                                    │
  │  Содержит: "UPDATE users SET name='Alice'       │
  │             WHERE id=1"                         │
  │────────────────────────────────────────────────→│
  │                                                 │
  │  Сервер выполняет запрос.                        │
  │  Для UPDATE ответ состоит из:                    │
  │                                                 │
  │  CommandComplete ('C')                          │
  │  "UPDATE 1"  (затронута 1 строка)               │
  │←───────────────────────────────────────────────│
  │                                                 │
  │  ReadyForQuery ('Z')                            │
  │  "Я готов к следующему запросу"                 │
  │←───────────────────────────────────────────────│
  │                                                 │
  │  (можно отправлять следующий запрос              │
  │   в этом же TCP-соединении)                      │
```

Если бы это был `SELECT`, ответ был бы сложнее:

```
  RowDescription ('T') — 📋 имена и типы колонок      │
←───────────────────────────────────────────────│
  DataRow ('D') — 📄 строка 1                         │
←───────────────────────────────────────────────│
  DataRow ('D') — 📄 строка 2                         │
←───────────────────────────────────────────────│
  ...                                               │
  CommandComplete ('C') — "SELECT 42"               │
←───────────────────────────────────────────────│
  ReadyForQuery ('Z')                               │
←───────────────────────────────────────────────│
```

#### 🚪 Кто принимает соединение на стороне сервера

На стороне сервера работает главный процесс — **Postmaster**. Это **один процесс ОС**, который запускается самым первым и работает всё время, пока живёт PostgreSQL.

**Как устроен Postmaster:**
- Всё время висит в памяти и слушает порт 5432.
- Пока нет подключений, он **не потребляет CPU**: он ждёт на системном вызове `select()` (или `poll()`), который блокирует процесс до появления входящего TCP-запроса.
- Когда приходит новое подключение, Postmaster просыпается, проверяет `pg_hba.conf`, делает `fork()` (системный вызов, занимающий доли миллисекунды), создавая Backend-процесс, передаёт ему TCP-соединение и **немедленно возвращается к ожиданию** следующего подключения.
- Сам он **никогда не обрабатывает SQL-запросы** и не работает с данными.

**Потребление ресурсов:**
- Пока нет подключений: **0% CPU**, несколько мегабайт памяти.
- При шквале подключений: кратковременные всплески CPU на `fork()`, но в целом нагрузка минимальна.
- Postmaster — это «диспетчер», а не «рабочий». Он только распределяет входящие соединения.

Когда приходит новый клиент и устанавливает TCP-соединение, Postmaster:

1. ✅ Принимает TCP-соединение (трёхстороннее рукопожатие на транспортном уровне).
2. 📖 Читает StartupMessage (первое сообщение прикладного уровня).
3. 🔍 Проверяет по `pg_hba.conf`, разрешено ли подключение для этого пользователя с этого IP.
4. 🍴 Создаёт (через системный вызов `fork()`) новый процесс операционной системы — **Backend-процесс**.
5. 🔗 Передаёт ему TCP-соединение.
6. 🔄 Возвращается к прослушиванию порта.

С этого момента клиент общается **только со своим Backend-процессом**, который и проводит аутентификацию (фаза Startup), и обрабатывает SQL-запросы (фаза Normal) — всё внутри одного TCP-соединения.

#### 💻 Как это выглядит в реальном Go-приложении

Рассмотрим типичное веб-приложение на Go, использующее пул соединений к PostgreSQL:

```go
// main.go — инициализация при старте сервера
db, _ := sql.Open("postgres", "host=localhost user=alice dbname=mydb")
db.SetMaxOpenConns(25)        // максимум 25 одновременных Backend-процессов
db.SetMaxIdleConns(10)        // до 10 простаивающих TCP-соединений
db.SetConnMaxIdleTime(5 * time.Minute) // закрыть idle-соединение через 5 мин

// Хэндлер — вызывается при HTTP-запросе
func getUsers(w http.ResponseWriter, r *http.Request) {
    rows, _ := db.Query("SELECT id, name FROM users")
    // ...
}
```

**Когда и как происходят TCP-соединение, Startup и Normal:**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ВРЕМЕННАЯ ШКАЛА ЖИЗНИ ПРИЛОЖЕНИЯ                 │
│                                                                     │
│  t=0   Запуск приложения                                            │
│        sql.Open() — НИКАКИХ соединений не создаётся.                │
│        Только настройка пула в памяти.                              │
│                                                                     │
│  t=1   Первый HTTP-запрос (GET /users)                              │
│        Пул соединений пуст — нужно создать новое соединение.         │
│        ├── TCP-рукопожатие (SYN, SYN-ACK, ACK)                     │
│        ├── Postmaster делает fork() → создан Backend PID 100       │
│        ├── StartupMessage                                           │
│        ├── Аутентификация (scram-sha-256)                          │
│        ├── ReadyForQuery ('Z')                                     │
│        ├── Query ('Q') "SELECT ..."                                │
│        ├── DataRow, DataRow, ...                                   │
│        └── ReadyForQuery ('Z')                                     │
│        TCP-соединение остаётся ОТКРЫТЫМ → возвращается в пул (idle) │
│                                                                     │
│  t=2   Второй HTTP-запрос (GET /orders)                             │
│        Пул видит idle-соединение → использует его.                   │
│        ├── (TCP уже есть — рукопожатие пропускается)                │
│        ├── (Startup уже пройден — аутентификация пропускается)      │
│        ├── Query ('Q') "SELECT ..."                                │
│        ├── DataRow, DataRow, ...                                   │
│        └── ReadyForQuery ('Z')                                     │
│        Соединение снова возвращается в пул (idle)                    │
│        Все запросы обработал один и тот же процесс PID 100!          │
│                                                                     │
│  t=3   Два одновременных HTTP-запроса                               │
│        Пул даёт каждому СВОЁ TCP-соединение:                        │
│        ├── Запрос A → idle-соединение №1 → Backend PID 100          │
│        └── Запрос B → idle-соединение №2 → Backend PID 101          │
│        Два разных процесса, два разных TCP-соединения.               │
│                                                                     │
│  t=300 Если соединение простаивало > 5 мин (MaxIdleTime):           │
│        Go отправляет TCP FIN → соединение закрывается                │
│        Backend PID 100 завершается                                  │
│        Следующий запрос создаст новое TCP-соединение и новый процесс │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевой вывод:** `sql.Open()` не создаёт TCP-соединений. Соединение, fork() и аутентификация происходят **при первом реальном SQL-запросе**, если в пуле нет свободного idle-соединения. После завершения запроса TCP-соединение **не закрывается**, а возвращается в пул для повторного использования. StartupMessage и аутентификация происходят **ровно один раз** за всё время жизни TCP-соединения, а не для каждого SQL-запроса.

### 🗺️ 3. Визуализация: Карта процессов внутри PostgreSQL

Теперь посмотрим на **все** процессы, которые работают внутри PostgreSQL:

```
                          ┌───────────┐
                          │  👤 Клиент │
                          └─────┬─────┘
                                │ TCP, порт 5432
                                │ 📡 PostgreSQL Wire Protocol
                                ▼
┌──────────────────────────────────────────────────────────────┐
│                    🚪 POSTMASTER (Диспетчер)                 │
│                                                              │
│  Что делает:                                                 │
│  • Слушает порт 5432                                         │
│  • Принимает TCP-соединения                                  │
│  • Читает StartupMessage                                     │
│  • Проверяет pg_hba.conf                                     │
│  • Создаёт (fork) Backend-процесс для каждого клиента        │
│  • Следит за здоровьем всех процессов                        │
│  • Перезапускает упавшие фоновые процессы                    │
│                                                              │
│  Это ОДИН процесс ОС на весь сервер.                         │
│  Пока нет подключений — спит на select(), 0% CPU.           │
│  Сам запросы НЕ обрабатывает!                                │
│  Один fork() = один Backend-процесс = одно TCP-соединение    │
│  Fork() делается при УСТАНОВКЕ соединения, а не на запрос    │
└─────────────────────────┬────────────────────────────────────┘
                          │ fork() — создаёт новый процесс ОС
                          ▼
┌──────────────────────────────────────────────────────────────┐
│                🧑‍💻 BACKEND PROCESS (Ваш личный процесс)       │
│                                                              │
│  Что делает:                                                 │
│  • Забирает TCP-соединение у Postmaster'а                    │
│  • Проводит аутентификацию (обменивается сообщениями)        │
│  • Получает SQL-запросы от клиента (сообщения типа 'Q')      │
│  • Обрабатывает запрос: Parse → Rewrite → Plan → Execute     │
│  • Отправляет результат обратно клиенту                      │
│  • Живёт, пока TCP-соединение не закроется                   │
│  • ОДИН процесс обслуживает ВСЕ запросы в своём соединении   │
│  • МОЖЕТ сам сбрасывать грязные страницы при вытеснении      │
│  • Хранит в своей памяти: состояние транзакции, план запроса │
│                                                              │
│  Этапы обработки одного запроса:                             │
│    1. 🔍 Parse   — разбор SQL (проверка синтаксиса)         │
│    2. 🔄 Rewrite — применение правил (если есть)            │
│    3. 🧠 Plan    — выбор оптимального способа выполнения    │
│    4. ⚙️ Execute — выполнение шаг за шагом                  │
└──────────────────────────────────────────────────────────────┘
```

#### 🧵 Как 50 Backend-процессов работают на 12-ядерном сервере

Когда `max_connections = 50`, а физических ядер — 12 (24 потока с Hyper-Threading), все 50 процессов **выполняются конкурентно**, а не последовательными пачками по 24.

Планировщик операционной системы (Linux CFS) раздаёт кванты процессорного времени всем 50 процессам, постоянно переключаясь между ними:

```
┌─────────────────────────────────────────────────────────────────────┐
│              ВРЕМЯ → (кванты ~1-10 мс на процесс)                   │
│                                                                     │
│  Ядро 0: [PID 1][PID25][PID 1][PID 7][PID13][PID19][PID 1]...     │
│  Ядро 1: [PID 2][PID 8][PID14][PID20][PID 2][PID26][PID32]...     │
│  Ядро 2: [PID 3][PID 9][PID15][PID21][PID 3][PID27][PID33]...     │
│  Ядро 3: [PID 4][PID10][PID16][PID22][PID 4][PID28][PID34]...     │
│  ...                                                               │
│                                                                     │
│  Все 50 процессов продвигаются ОДНОВРЕМЕННО.                        │
│  Никто не ждёт «своей очереди» в пачке из 24 процессов.             │
└─────────────────────────────────────────────────────────────────────┘
```

Более того, большинство Backend-процессов **часто ждут не процессор, а диск или сеть**. Пока один процесс ждёт чтения страницы с диска (~5-10 мс), ядро ОС отдаёт его квант другому процессу. Поэтому PostgreSQL может эффективно обслуживать сотни соединений даже на небольшом количестве ядер.

**Ограничения:** при очень большом количестве процессов (500+) начинают сказываться два фактора:
- **Память:** каждый Backend-процесс потребляет 10-15 МБ RAM только на свою виртуальную память.
- **Переключение контекста:** планировщик ОС тратит всё больше времени на переключение между процессами вместо полезной работы.

Именно для этого используют **пул соединений** (PgBouncer): 5000 клиентов → 50 реальных Backend-процессов.

### 💾 4. Память в PostgreSQL: что такое shared_buffers и зачем они нужны

Backend-процесс обрабатывает запрос и работает с данными. Но данные лежат **на диске** 💿. Читать с диска — очень медленно (в тысячи раз медленнее, чем из оперативной памяти 🚀).

Поэтому PostgreSQL выделяет **общую область памяти** (shared memory), которую называют **shared_buffers**. Это кэш, в котором хранятся **копии страниц данных с диска**.

```
💿 Физический диск (медленно)          🚀 Оперативная память (быстро)
┌────────────────────┐              ┌────────────────────────┐
│ 📁 Файл таблицы     │              │   🗂️ shared_buffers     │
│ users (100 ГБ)     │              │   (обычно 25% от RAM)  │
│                    │   загрузка   │                        │
│ ┌────────────────┐ │◄────────────│ ┌────────────────────┐ │
│ │ 📄 страница 0   │ │             │ │ 📄 копия стр. 0    │ │
│ │ 📄 страница 1   │ │             │ │ 📄 копия стр. 5    │ │
│ │ 📄 страница 2   │ │             │ │ 📄 копия стр. 100  │ │
│ │ ...            │ │             │ │ ...                │ │
│ │ 📄 страница 100K│ │             │ │ (только часто      │ │
│ └────────────────┘ │             │ │  используемые)     │ │
└────────────────────┘              └────────────────────────┘
```

**Как это работает:**
1. Backend-процесс хочет прочитать строку с `id = 1`.
2. Он узнаёт, что эта строка лежит в **странице №100** (страница — это блок данных фиксированного размера, обычно 8 КБ).
3. Backend-процесс идёт в `shared_buffers`: «Есть тут копия страницы №100?»
   - ✅ **Если страница уже лежит в кэше** (в `shared_buffers`): Backend-процесс просто читает данные из оперативной памяти. Это быстро, обращения к диску не происходит.
   - ❌ **Если страницы в кэше нет**: Backend-процесс вынужден прочитать страницу №100 с диска, загрузить её копию в `shared_buffers`, и только потом прочитать данные уже из памяти. Это медленнее, потому что включает физическое чтение с диска.

### 💧 5. Что такое «грязные страницы» и зачем нужен Background Writer

Когда Backend-процесс выполняет наш `UPDATE`, он изменяет копию страницы в `shared_buffers` (добавляет новую версию строки). Теперь копия страницы в памяти **отличается** от версии на диске.

Такая страница называется **«грязной» (dirty)** 📝 — она изменена в памяти, но ещё не записана на диск.

**Сколько версий строки создаётся при многих UPDATE?**
Если одну и ту же строку (например, `id=1`) изменить 10 раз, то в таблице будет лежать **10 версий этой строки**: одна текущая (актуальная) и девять старых (устаревших). PostgreSQL не перезаписывает старую версию — он создаёт новую версию строки на странице, а старая остаётся лежать мёртвым грузом. Потом специальный процесс VACUUM пометит место старых версий как свободное.

**Что происходит, когда shared_buffers заполняется?**
`shared_buffers` имеет фиксированный размер (выделяется при старте сервера). Когда все буферы заняты, а серверу нужно прочитать новую страницу с диска, приходится выбрать одну из старых страниц для **вытеснения** (замены). Для этого PostgreSQL использует алгоритм **Clock-Sweep** (разновидность LRU — «вытеснение наиболее давно не использовавшейся»):

- У каждой страницы в кэше есть **счётчик обращений** (usage count) — число от 0 до 5 (определяется константой `BM_MAX_USAGE_COUNT` в исходном коде). Когда страницу читают или изменяют, счётчик увеличивается (но не выше 5). Он показывает, насколько часто страница используется.
- Специальный указатель (стрелка часов) циклически обходит все страницы в `shared_buffers`. При каждом проходе он смотрит на счётчик обращений текущей страницы. Если счётчик > 0, указатель уменьшает его на единицу и переходит к следующей странице. Если счётчик уже равен 0, страница становится кандидатом на вытеснение.
- Если вытесняемая страница «грязная», её **нужно сначала записать на диск**, а это занимает время ⏳.

**Как Background Writer решает, какие страницы сбрасывать?**

Background Writer 🟢 — это **один фоновый процесс ОС** (не поток!). Он создаётся при старте PostgreSQL и работает в бесконечном цикле. Он использует **тот же самый указатель** Clock-Sweep, что и обычное вытеснение. Он проходится по буферному кэшу и ищет страницы, которые:

1. **Грязные** (изменены в памяти, но не на диске).
2. Имеют **низкий счётчик обращений** (usage count близок к 0) — то есть редко используются.

Алгоритм работает так:
- Background Writer просыпается каждые `bgwriter_delay` миллисекунд (по умолчанию 200 мс).
- Он начинает обход страниц с того места, где остановился в прошлый раз (указатель никуда не сбрасывается).
- Для каждой страницы смотрит: грязная ли она? Если да — сбрасывает на диск и обнуляет грязный флаг (страница становится «чистой»).
- Если страница чистая или имеет высокий usage count — пропускает её (уменьшая счётчик, как и обычный Clock-Sweep).
- За один раунд сбрасывает не более `bgwriter_lru_maxpages` страниц (по умолчанию 100).

**Как Background Writer выполняется на процессоре:**
- Он работает **конкурентно** с остальными процессами на общих ядрах — никакого выделенного CPU или ядра для него нет.
- Планировщик Linux CFS ставит его в общую очередь со всеми остальными процессами (Backend'ы, WAL Writer, Checkpointer).
- Его работа очень лёгкая: обойти 100 страниц в памяти, проверить флаги, сбросить грязные на диск. Даже при высокой нагрузке он потребляет доли процента CPU.
- Если Background Writer не успевает за темпом изменений (из-за ограничения `bgwriter_lru_maxpages`), **обычные Backend-процессы берут запись грязных страниц на себя**.

**Зачем это нужно?** Когда обычному Backend-процессу потребуется вытеснить страницу, он с большой вероятностью найдёт уже «чистую» страницу (которую Background Writer заранее сбросил) и сможет заменить её мгновенно, без ожидания записи на диск.

```
🧑‍💻 Backend-процесс:                  🟢 Background Writer:
«Изменил страницу №100               «Каждые 200 мс просыпаюсь,
 в памяти. Она стала грязной.»       иду по буферам.
                                     Страница №100 грязная?
                                     usage count высокий (5) —
                                     пропускаю, уменьшаю до 4.
                                     Страница №50 грязная?
                                     usage count = 0 —
                                     СБРАСЫВАЮ на диск!»
         │                                    │
         │                                    ▼
         │                           ┌────────────────┐
         │                           │ 💿 Диск: стр.  │
         │                           │ №50 обновлена  │
         │                           │ (№100 пока ждёт)│
         │                           └────────────────┘
```

#### Может ли Backend-процесс сам записывать грязные страницы на диск?

**Да, может.** Backend-процесс не только умеет записывать грязные страницы на диск, но и **регулярно это делает**. Background Writer не даёт гарантии, что все грязные страницы будут сброшены заранее — он лишь **снижает вероятность** того, что Backend-процесс застрянет на записи.

**Когда Backend-процесс вынужден записывать грязные страницы:**

Это происходит в трёх сценариях:

**Сценарий 1: Вытеснение страницы.** Backend-процесс хочет прочитать новую страницу с диска, но все буферы в `shared_buffers` заняты. Clock-Sweep находит страницу с usage count = 0 для вытеснения. Если эта страница **грязная**, Backend-процесс **сам** записывает её на диск перед тем, как загрузить на её место новую страницу. Это происходит синхронно, прямо во время выполнения пользовательского запроса, и добавляет задержку.

**Сценарий 2: Контрольная точка.** Во время контрольной точки Checkpointer 🔴 сбрасывает все грязные страницы. Но Checkpointer не работает в одиночку — он **координирует** процесс, а фактическую запись могут выполнять и обычные Backend-процессы. Если какой-то Backend-процесс обращается к странице, которую Checkpointer ещё не успел сбросить, он может взять эту работу на себя.

**Сценарий 3: Высокая скорость изменений.** Если приложение делает очень много UPDATE в минуту, Background Writer может просто не успевать за темпом. Его ограничение — `bgwriter_lru_maxpages` страниц за раунд (по умолчанию 100 каждые 200 мс = 500 страниц в секунду). Если грязные страницы появляются быстрее, они накапливаются, и Backend-процессам приходится сбрасывать их самостоятельно при вытеснении.

**Почему это проблема:** когда Backend-процесс записывает грязную страницу, он делает это **синхронно** — пользовательский запрос висит и ждёт завершения записи на диск. Background Writer делает ту же работу **асинхронно**, в фоне, поэтому пользовательские запросы не замечают задержки.

```
Обычная ситуация (Background Writer успевает):
  [Backend читает] [Backend читает] [Backend читает]
  [🟢 BW сбрасывает грязные страницы в фоне]

Проблемная ситуация (Background Writer не успевает):
  [Backend читает] [Backend ЖДЁТ записи] [Backend читает]
  [🟢 BW сбрасывает] [🟢 BW сбрасывает] [🟢 BW сбрасывает]
                    ^
                    Backend-процесс вынужден сам писать на диск
```

**Основные параметры Background Writer:**

| Параметр | По умолчанию | Что делает |
|:---|:---|:---|
| `bgwriter_delay` | 200 мс | Пауза между раундами |
| `bgwriter_lru_maxpages` | 100 | Максимум страниц за раунд |
| `bgwriter_lru_multiplier` | 2.0 | Множитель агрессивности при высокой нагрузке |

### 📝 6. Что такое WAL (журнал предзаписи) и зачем нужен WAL Writer

Теперь подумаем о надёжности. Представь: Backend-процесс изменил страницу в памяти (сделал её «грязной»), но Background Writer ещё не сбросил её на диск. Внезапно ⚡ отключается питание.

❓ **Что произойдёт?** Изменения в памяти потеряны. Пользователь думал, что его UPDATE сохранился, но на диске его нет.

💡 **Решение:** WAL (Write-Ahead Log — журнал предзаписи). Принцип прост:

> 🔐 **Любое изменение ДОЛЖНО быть записано в журнал WAL на диск ДО того, как соответствующая страница данных будет сброшена на диск.**

WAL — это **отдельный набор файлов на диске** (обычно в каталоге `pg_wal`), в который пишутся **записи об изменениях**. Запись в WAL очень быстрая, потому что это **последовательная запись** в конец файла ⚡ (в отличие от случайной записи в разные места файлов таблиц).

#### Подробное объяснение: shared_buffers и WAL-буфер — это разные сущности

**WAL-буфер** и **shared_buffers** — это **две совершенно разные области памяти**, которые решают разные задачи. Их часто путают, потому что оба находятся в разделяемой памяти (shared memory) и оба связаны с дисковым вводом-выводом.

**shared_buffers — кэш страниц данных.** Когда ты выполняешь `SELECT * FROM users WHERE id = 1`, Backend-процессу нужна страница, содержащая эту строку. Он читает её в `shared_buffers` с диска (если её там ещё нет) и работает с ней в памяти. Когда ты делаешь `UPDATE`, он изменяет эту же страницу прямо в `shared_buffers`, делая её «грязной». Позже Background Writer или Checkpointer сбросят её в файл таблицы на диске. `shared_buffers` — это **рабочая область** для данных. Все операции чтения и изменения страниц таблиц и индексов проходят через неё.

**WAL-буфер — буфер журнала изменений.** Когда Backend-процесс выполняет `UPDATE`, он **одновременно** с изменением страницы в `shared_buffers` записывает **запись об изменении** в WAL-буфер. Это не копия страницы и не сами данные строки — это **логическое описание изменения**: «транзакция 12345 изменила страницу №100, смещение 456: записать байты XYZ». WAL-буфер — это **маленький кольцевой буфер**, куда все Backend-процессы дописывают свои WAL-записи в порядке их совершения. WAL Writer периодически сбрасывает накопленные записи в файлы `pg_wal/` на диске. При COMMIT сброс происходит принудительно.

#### Ключевое отличие в сценариях использования

**Сценарий: чтение данных (`SELECT`)**
- Backend-процесс обращается **только** к `shared_buffers`.
- WAL-буфер **не используется вообще**, потому что никаких изменений нет.

**Сценарий: изменение данных (`UPDATE`)**
- Backend-процесс:
  1. Находит страницу в `shared_buffers` (или загружает с диска).
  2. Изменяет страницу в `shared_buffers` → страница становится «грязной».
  3. **Одновременно** записывает описание изменения в **WAL-буфер**.
- Это две **параллельные** операции с разными областями памяти.

**Сценарий: восстановление после сбоя**
- PostgreSQL читает **только** файлы WAL (`pg_wal/`), «доприменяет» изменения к страницам в файлах таблиц.
- `shared_buffers` в этот момент пуст (сервер только что запустился).

#### Почему WAL-буфер такой маленький?

`wal_buffers` по умолчанию = 16 МБ (или 1/32 от `shared_buffers`, если `shared_buffers` большой).

Причины:
1. **Данные сбрасываются быстро.** WAL Writer сбрасывает буфер каждые 200 мс, а при COMMIT — мгновенно. Данные не задерживаются надолго.
2. **Последовательная запись.** В отличие от `shared_buffers`, где страницы читаются и пишутся в случайном порядке, WAL — это **один непрерывный поток**. Маленького буфера достаточно, чтобы сгладить пики.
3. **Экономия памяти.** Большой WAL-буфер не даёт выигрыша: если сервер упадёт, всё, что не сброшено в файлы WAL, потеряется.

#### Как работает WAL Writer

**WAL Writer** 🟡 — это фоновый процесс, который сбрасывает данные из **WAL-буфера** (область памяти в RAM) в **файлы WAL на диске**. Он работает часто и маленькими порциями, чтобы гарантировать, что данные не потеряются.

#### Что будет, если сбой произошёл, когда записи ещё в WAL-буфере?

Это критически важный вопрос. **Да, если сбой происходит в момент, когда записи были только в WAL-буфере (в RAM) и не были сброшены на диск — эти изменения будут потеряны.** Но PostgreSQL спроектирован так, чтобы **минимизировать это окно потерь** до миллисекунд. И для любого изменения, которое получило `COMMIT`, это окно закрывается полностью.

Сброс WAL-буфера на диск происходит **не только** через WAL Writer. Есть два независимых механизма:

**Механизм 1: WAL Writer (фоновый, асинхронный).** WAL Writer просыпается каждые `wal_writer_delay` миллисекунд (по умолчанию 200 мс) и сбрасывает накопившиеся записи из WAL-буфера в файлы `pg_wal/`. Это фоновая операция: она не привязана к конкретной транзакции и не даёт гарантий для каждой отдельной записи. **Окно уязвимости:** до 200 мс.

**Механизм 2: Принудительный сброс при COMMIT (синхронный).** Когда транзакция выполняет `COMMIT`, PostgreSQL **не ждёт** следующего пробуждения WAL Writer. Он **принудительно** сбрасывает WAL-буфер на диск немедленно через системный вызов `fsync()`, который гарантирует физическую запись на диск. Только после успешного завершения `fsync()` клиент получает ответ «COMMIT выполнен». **Окно уязвимости:** 0 мс для закоммиченных транзакций.

**Сценарий A: Сбой до COMMIT.** Транзакция сделала UPDATE (запись в WAL-буфере), но не сделала COMMIT. Сбой питания. **Результат:** изменение потеряно. Но это нормально — транзакция не была подтверждена, клиент не получил «COMMIT успешен».

**Сценарий B: Сбой сразу после COMMIT.** Транзакция сделала COMMIT, PostgreSQL принудительно сбросил WAL-буфер через `fsync()`, клиент получил подтверждение. Через микросекунду — сбой. **Результат:** изменение НЕ потеряно. WAL-запись гарантированно на диске. При восстановлении PostgreSQL применит её.

**Сценарий C: Асинхронный COMMIT (исключение).** В режиме `synchronous_commit = off` COMMIT **не ждёт** сброса WAL на диск. В этом режиме окно потерь для закоммиченных транзакций может составлять до `wal_writer_delay` × 3 (по умолчанию до 600 мс). Используется для некритичных данных, где скорость важнее гарантии.

### 🎯 7. Checkpointer: контрольные точки для быстрого восстановления

Представь, что сервер работал год без сбоев, а потом упал 💥. WAL-файлы за год — это сотни гигабайт. При восстановлении PostgreSQL пришлось бы перечитывать **все WAL-файлы с самого начала**, что заняло бы часы ⏳.

💡 **Решение:** Checkpointer 🔴.

**Checkpointer** — это фоновый процесс, который **раз в несколько минут** (по умолчанию 5 минут) делает **контрольную точку**:

1. 💾 **Сбрасывает ВСЕ «грязные» страницы** из `shared_buffers` в файлы таблиц на диске.
2. 🏁 **Отмечает в WAL**: «В этом месте все страницы на диске актуальны. При восстановлении можно начинать отсюда, а не с самого начала».

```
❌ Без Checkpointer:                 ✅ С Checkpointer:
Восстановление:                      Восстановление:
[читать все WAL-файлы с 0]           [пропустить до последней контрольной точки]
│                                    │
▼                                    ▼
⏳ Часы чтения WAL                    ⚡ Минуты чтения WAL
```

### ❓ 9. Интерактивность: вопросы для самопроверки

#### 📌 Вопрос 1

Backend-процесс изменил страницу в `shared_buffers`, но Background Writer ещё не сбросил её на диск. Внезапно отключается питание ⚡. Данные потеряны?

#### ✅ Ответ 1

**Нет, данные не потеряны.** Когда Backend-процесс изменяет страницу в `shared_buffers`, он одновременно записывает изменение в WAL-буфер. WAL Writer сбрасывает его на диск, а при COMMIT сброс происходит принудительно. После сбоя PostgreSQL восстанавливает страницу из WAL.

---

#### 📌 Вопрос 2

Зачем нужен Background Writer 🟢, если Checkpointer 🔴 и так сбрасывает все грязные страницы раз в 5 минут?

#### ✅ Ответ 2

Background Writer и Checkpointer решают **разные задачи**. Background Writer проактивно сбрасывает редко используемые грязные страницы в фоне, чтобы при вытеснении Backend-процесс не ждал записи на диск. Checkpointer сбрасывает **все** грязные страницы и отмечает контрольную точку в WAL для быстрого восстановления после сбоя.

---

#### 📌 Вопрос 3

Клиент посылает SQL-запрос серверу. В каком сообщении протокола он его отправляет? Как называется сообщение, которым сервер говорит «запрос выполнен, я готов к следующему»?

#### ✅ Ответ 3

**Клиент отправляет запрос в сообщении типа `'Q'` (Query).** **Сервер говорит о готовности сообщением `'Z'` (ReadyForQuery).** Клиент не должен отправлять новый запрос, пока не получит ReadyForQuery.

---

#### 📌 Вопрос 4

PostgreSQL настроен с `max_connections = 100`. К серверу пытаются подключиться 150 клиентов одновременно. Что произойдёт с «лишними» 50?

#### ✅ Ответ 4

Postmaster отклонит их с ошибкой `FATAL: sorry, too many clients already`. TCP-соединение закроется, Backend-процесс не создастся.

---

#### 📌 Вопрос 5

Может ли один Backend-процесс обслуживать запросы двух разных клиентов по очереди?

#### ✅ Ответ 5

**Нет.** Один Backend-процесс = одно TCP-соединение = один клиент на всю жизнь процесса. При разрыве TCP-соединения процесс завершается.

---

#### 📌 Вопрос 6

В Go-приложении с `sql.DB`: когда происходит TCP-рукопожатие, `fork()` и StartupMessage?

#### ✅ Ответ 6

При первом `db.Query()` (или `db.Exec()`), **а не** при `sql.Open()`. `sql.Open()` только настраивает пул в памяти. После выполнения запроса TCP-соединение возвращается в пул (idle) и переиспользуется без повторной аутентификации.

---

#### 📌 Вопрос 7

Если `max_connections = 50`, а ядер — 12 (24 потока), будут ли 50 одновременных запросов выполняться конкурентно или пачками?

#### ✅ Ответ 7

**Конкурентно.** Планировщик ОС раздаёт кванты времени всем 50 процессам, постоянно переключаясь между ними. Пока одни процессы ждут диск/сеть, другие используют CPU.

---

#### 📌 Вопрос 8

Как Background Writer решает, какую страницу сбрасывать на диск?

#### ✅ Ответ 8

Background Writer использует алгоритм Clock-Sweep: циклически обходит страницы в `shared_buffers`, уменьшая usage count. Если страница грязная **и** usage count = 0 — сбрасывает её на диск.

---

#### 📌 Вопрос 9

Есть ли у Backend-процесса возможность записать грязную страницу на диск? В каких случаях это происходит?

#### ✅ Ответ 9

**Да, Backend-процесс умеет и регулярно вынужден записывать грязные страницы на диск.** Это происходит в трёх сценариях:

1. **Вытеснение страницы.** Когда `shared_buffers` заполнен, а нужно прочитать новую страницу с диска, Clock-Sweep выбирает страницу для вытеснения. Если она грязная — Backend-процесс **синхронно** записывает её на диск перед загрузкой новой. Это добавляет задержку к пользовательскому запросу.

2. **Помощь Checkpointer'у.** Во время контрольной точки Checkpointer координирует сброс всех грязных страниц, но часть работы могут взять на себя обычные Backend-процессы при обращении к ещё не сброшенным страницам.

3. **Высокий темп изменений.** Если приложение генерирует грязные страницы быстрее, чем Background Writer успевает их сбрасывать (ограничение: `bgwriter_lru_maxpages` × `bgwriter_delay`), они накапливаются, и Backend-процессам приходится сбрасывать их самостоятельно.

Background Writer — это оптимизация, а не гарантия. Он **снижает вероятность** того, что Backend-процесс застрянет на синхронной записи, но не исключает её полностью.

---

#### 📌 Вопрос 10

Background Writer и Postmaster — это потоки внутри одного процесса или отдельные процессы? Выполняются ли они на выделенных ядрах?

#### ✅ Ответ 10

**Background Writer и Postmaster — это отдельные процессы ОС, а не потоки.** Они работают конкурентно с остальными процессами PostgreSQL на общих ядрах. Никакого выделенного CPU или ядра для них нет.

- **Postmaster** — один процесс, который всё время слушает порт 5432. Пока нет подключений, он спит на системном вызове `select()` и потребляет 0% CPU.
- **Background Writer** — один процесс, который каждые 200 мс просыпается, обходит до 100 страниц в `shared_buffers` и сбрасывает грязные на диск. Его работа очень лёгкая — даже при высокой нагрузке он потребляет доли процента CPU.

Оба процесса работают на тех же ядрах, что и Backend-процессы, и планировщик Linux CFS распределяет между ними кванты времени наравне со всеми.

---

#### 📌 Вопрос 11

Чем WAL-буфер отличается от shared_buffers? Это одна и та же сущность?

#### ✅ Ответ 11

**Это две совершенно разные области памяти.**

`shared_buffers` — это **большой кэш страниц данных** (гигабайты). В нём хранятся копии страниц таблиц и индексов (по 8 КБ), с которыми работают Backend-процессы: читают строки, изменяют их, делают страницы «грязными».

`WAL-буфер` — это **маленький кольцевой буфер** (~16 МБ), куда Backend-процессы дописывают **описания изменений** (WAL records). Это не копии страниц, а логические записи вида «транзакция 12345 изменила страницу №100».

Ключевые отличия:
- `shared_buffers` используется и для чтения (`SELECT`), и для записи (`UPDATE`). WAL-буфер — **только для записи**.
- `shared_buffers` хранит **сами данные** (строки таблиц). WAL-буфер хранит **описание изменений**.
- Сброс `shared_buffers` — случайная запись в файлы таблиц. Сброс WAL-буфера — последовательная запись в `pg_wal/`.
- При восстановлении после сбоя PostgreSQL читает **только WAL-файлы**, `shared_buffers` в этот момент пуст.

**Аналогия:** `shared_buffers` — это рабочие столы с папками документов. `WAL-буфер` — это чековая лента кассового аппарата, куда записывается каждая операция **до** того, как она попадёт в папку.

---

#### 📌 Вопрос 12

Что будет, если сбой питания произойдёт в тот момент, когда записи об изменениях ещё находятся в WAL-буфере и WAL Writer не успел их сбросить на диск?

#### ✅ Ответ 12

Записи, которые были только в WAL-буфере (в RAM) и не были сброшены на диск, **будут потеряны**. Однако важно различать два случая:

- **Транзакция не делала COMMIT:** потеря записи — это нормально. Транзакция не была подтверждена, клиент не получил «COMMIT успешен». С точки зрения ACID такая транзакция считается откаченной.

- **Транзакция сделала COMMIT:** потеря **невозможна**, потому что при COMMIT PostgreSQL **принудительно** сбрасывает WAL-буфер на диск через `fsync()`, не дожидаясь WAL Writer'а. Клиент получает подтверждение только после того, как `fsync()` завершился успешно. Окно потерь для закоммиченных транзакций — 0 секунд.

Единственное исключение — режим `synchronous_commit = off`, в котором COMMIT не ждёт сброса WAL на диск. В этом режиме окно потерь может составлять до 600 мс.
