## 4.0 Пролог: поиск, который ускорился в тысячу раз

В прологе Главы 2 ты столкнулся с проблемой: сервис хранил 50 миллионов событий в связном списке, и поиск по ID занимал секунды. Ты переписал хранение на `map[string]*Event`, и поиск ускорился в тысячи раз.

Что произошло? Ты заменил **линейный поиск** (O(n)) на **поиск по хеш-таблице** (O(1) в среднем).

Но как это работает? Как `map[id]` умудряется найти нужный элемент среди 50 миллионов за **константное время**, не перебирая их?

Ответ — **хеш-функция**. Она превращает ключ (например, строку `"user:12345"`) в **число** — индекс в массиве. И вместо того чтобы искать по всем 50 миллионам, ты сразу идёшь в нужную ячейку.

Это звучит как магия. Но за этой магией стоит математика: функции, коллизии, рехеширование, load factor. В этой главе мы разберём всё до дна.

## 4.1 Хеш-функция: превращаем ключ в индекс

### 🔌 Проблема: как найти элемент в массиве, не перебирая все?

Представь: у тебя массив из 1000 ячеек. Ты хочешь хранить в нём данные, но не по индексу 0, 1, 2, ..., а по **ключу** — например, по строке `"user:12345"`. Как это сделать?

Первая мысль: хранить в каждой ячейке пару `(ключ, значение)` и искать линейно. Но это O(n) — не годится.

Вторая мысль: превратить ключ в **число** и использовать его как индекс. Но как превратить строку `"user:12345"` в число от 0 до 999?

Для этого нужна **хеш-функция**.

### 📐 Что такое хеш-функция

**Хеш-функция** — это функция, которая принимает **ключ** (строку, число, что угодно) и возвращает **число** фиксированного размера — **хеш-код**.

Пример простой хеш-функции для строки: сложить ASCII-коды всех символов.

```go
func simpleHash(s string) int {
    sum := 0
    for _, ch := range s {
        sum += int(ch)
    }
    return sum
}
```

Для строки `"abc"`:
- 'a' = 97, 'b' = 98, 'c' = 99
- sum = 97 + 98 + 99 = 294

Теперь 294 — это **хеш-код**. Чтобы получить индекс в массиве из 1000 ячеек, берём остаток от деления:

```
index = hash(key) % size
index = 294 % 1000 = 294
```

Всё. Ключ `"abc"` будет храниться в ячейке 294.

### 🔬 Свойства хорошей хеш-функции

Не любая функция подойдёт. Хорошая хеш-функция должна:

**1. Быть детерминированной.** Один и тот же ключ всегда даёт один и тот же хеш-код. Иначе поиск не сработает.

**2. Равномерно распределять ключи.** Если все ключи попадают в одну ячейку — это не хеш-таблица, а связный список. Хеш-функция должна «размазывать» ключи по всему диапазону.

**3. Быть быстрой.** Если хеш-функция работает за O(n), где n — длина ключа, то вся хеш-таблица работает за O(n). Это всё ещё быстро (обычно ключи короткие), но не должно быть хуже.

**4. Лавинный эффект.** Маленькое изменение ключа → большое изменение хеш-кода. Иначе похожие ключи (`"user:12345"` и `"user:12346"`) будут попадать в соседние ячейки, создавая кластеры.

### 🔬 Пример плохой хеш-функции

Вернёмся к `simpleHash` — сложение ASCII-кодов. Это **плохая** хеш-функция для строк. Почему?

Строки `"abc"` и `"cba"` дают **одинаковый** хеш-код (97 + 98 + 99 = 294), потому что сложение коммутативно. Анаграммы будут попадать в одну ячейку — коллизии.

Лучшая хеш-функция для строк — **полиномиальный хеш**:

```go
func polynomialHash(s string) int {
    hash := 0
    for _, ch := range s {
        hash = hash*31 + int(ch)
    }
    return hash
}
```

Здесь каждый символ вносит вклад, зависящий от его позиции. `"abc"` и `"cba"` дадут разные хеш-коды.

Число 31 — это **простое число**, выбранное эмпирически. Простые множители дают лучшее распределение по модулю.

### 📊 Хеш-функции в реальных языках

Разные языки используют разные хеш-функции:

- **Go** — для строк использует алгоритм **AES-based** или **wyhash** (в зависимости от версии). Быстрая и хорошо распределяет.
- **Java** — для строк использует полиномиальный хеш с множителем 31.
- **Python** — использует **SipHash** для защиты от hash-flooding атак.
- **Rust** — использует **SipHash** по умолчанию.

**Почему не одна универсальная:** разные языки оптимизируют под разные задачи. Python и Rust жертвуют скоростью ради защиты от атак. Go и Java — оптимизируют под скорость.

### 🧮 Как из хеш-кода получить индекс

Хеш-код — это число (обычно 32 или 64 бита). Но массив у нас имеет конечный размер, например 1000 ячеек. Как из хеш-кода получить индекс от 0 до 999?

**Остаток от деления:** `index = hash % size`.

Почему size часто выбирают **степенью двойки** (1024, 2048)? Потому что тогда `hash % size` заменяется на **битовую маску**: `hash & (size - 1)`. Это работает в разы быстрее — одна битовая операция вместо деления.

Пример для size = 1024 (2^10):

```
index = hash & 1023
```

Битовая операция `&` с 1023 (двоичное `1111111111`) оставляет только младшие 10 бит хеш-кода — ровно то, что нужно.

### 💡 Что мы узнали?

- Хеш-функция превращает ключ в число — хеш-код.
- Индекс в массиве вычисляется как `hash(key) % size`.
- Хорошая хеш-функция: детерминированная, равномерная, быстрая, с лавинным эффектом.
- Полиномиальный хеш лучше, чем сложение ASCII-кодов.
- Для size, равного степени двойки, `% size` заменяется на битовую маску `& (size-1)`.

## 4.2 Коллизии: цепочки

### 🔌 Проблема: два ключа дают одинаковый индекс

В подглаве 4.1 мы разобрали, как хеш-функция превращает ключ в индекс. Но есть фундаментальная проблема.

Хеш-функция возвращает число **фиксированного размера** (например, 64 бита). А массив, в котором мы храним данные, имеет **конечный размер** (например, 1024 ячейки). Даже если хеш-функция идеально равномерна, рано или поздно два разных ключа дадут **одинаковый индекс**.

Это называется **коллизия**.

**Пример:** у нас массив на 10 ячеек. Ключи `"user:1"` и `"order:5"` имеют разные хеш-коды, но `hash % 10` для обоих равен 3. Оба ключа претендуют на одну ячейку.

**Вопрос:** что делать, когда два ключа попадают в одну ячейку?

Есть два основных подхода:

1. **Цепочки (chaining).** В каждой ячейке хранится не одно значение, а **список** значений.
2. **Открытая адресация (open addressing).** Если ячейка занята, ищем следующую свободную.

В этой подглаве разберём **цепочки**.

### 📐 Как работает метод цепочек

**Идея:** каждая ячейка массива — это не одно значение, а **указатель на связный список**. Все ключи, попавшие в одну ячейку, хранятся в этом списке.

```
Массив (10 ячеек):

[0] → nil
[1] → ("user:1", data1) → ("order:5", data2) → nil
[2] → ("product:7", data3) → nil
[3] → nil
[4] → ("user:2", data4) → ("event:9", data5) → ("log:3", data6) → nil
[5] → nil
...
```

Когда мы ищем ключ:

1. Вычисляем `index = hash(key) % size`.
2. Идём в ячейку `index`.
3. Проходим по списку, сравнивая ключи.
4. Если нашли — возвращаем значение. Если нет — ключа нет в таблице.

**Сложность поиска:**

- **Лучший случай:** список содержит один элемент — O(1).
- **Средний случай:** список содержит α элементов, где α — **load factor** (среднее количество элементов на ячейку). Поиск — O(1 + α).
- **Худший случай:** все ключи в одной ячейке — O(n).

Если α остаётся константой (например, ≤ 1), то средняя сложность поиска — **O(1)**.

### 🔬 Реализация на Go

```go
type Entry struct {
    Key   string
    Value interface{}
    Next  *Entry
}

type HashTable struct {
    buckets []*Entry // массив списков
    size    int      // количество ячеек
    count   int      // количество элементов
}

func NewHashTable(size int) *HashTable {
    return &HashTable{
        buckets: make([]*Entry, size),
        size:    size,
    }
}

func (h *HashTable) hash(key string) int {
    hash := 0
    for _, ch := range key {
        hash = hash*31 + int(ch)
    }
    if hash < 0 {
        hash = -hash
    }
    return hash % h.size
}

func (h *HashTable) Put(key string, value interface{}) {
    idx := h.hash(key)
    
    for e := h.buckets[idx]; e != nil; e = e.Next {
        if e.Key == key {
            e.Value = value
            return
        }
    }
    
    h.buckets[idx] = &Entry{
        Key:   key,
        Value: value,
        Next:  h.buckets[idx],
    }
    h.count++
}

func (h *HashTable) Get(key string) (interface{}, bool) {
    idx := h.hash(key)
    
    for e := h.buckets[idx]; e != nil; e = e.Next {
        if e.Key == key {
            return e.Value, true
        }
    }
    
    return nil, false
}

func (h *HashTable) Delete(key string) {
    idx := h.hash(key)
    
    if h.buckets[idx] != nil && h.buckets[idx].Key == key {
        h.buckets[idx] = h.buckets[idx].Next
        h.count--
        return
    }
    
    prev := h.buckets[idx]
    for prev != nil && prev.Next != nil {
        if prev.Next.Key == key {
            prev.Next = prev.Next.Next
            h.count--
            return
        }
        prev = prev.Next
    }
}
```

### 🧮 Преимущества и недостатки цепочек

**Преимущества:**

1. **Простота.** Легко реализовать.
2. **Устойчивость к переполнению.** Таблица может содержать больше элементов, чем ячеек (load factor > 1).
3. **Удаление простое.** Не нужно искать «следующую свободную ячейку».
4. **Нет кластеризации.** Элементы распределяются по спискам.

**Недостатки:**

1. **Дополнительная память.** Каждый элемент требует указатель (8 байт).
2. **Плохая кэш-локальность.** Списки разбросаны по памяти.
3. **Деградация при плохой хеш-функции.** O(n) на поиск.
4. **Динамическое выделение памяти.** Нагрузка на GC.

### 🔬 Где метод цепочек встречается в реальности

Классический метод цепочек — это **учебная модель**. В реальных языках он используется с оптимизациями, а иногда от него полностью отказываются.

**Java (`HashMap`):** цепочки + деревья. Когда список в ячейке длиннее 8 элементов — превращается в красно-чёрное дерево. Поиск — O(log n) вместо O(n). Разберём в Главе 9.

**C++ (`std::unordered_map`):** классические цепочки без оптимизаций.

**Python (`dict`):** цепочек **нет**. Используется открытая адресация.

**Go 1.23 и раньше:** гибрид: бакеты по 8 слотов + overflow-цепочки.

**Go 1.24 и новее:** от цепочек **полностью отказались**. Swiss Table — открытая адресация с SIMD-оптимизациями.

### 💡 Что мы узнали?

- Коллизия — ситуация, когда два ключа дают одинаковый индекс.
- Метод цепочек: каждая ячейка — указатель на связный список.
- Вставка: O(1) — добавляем в начало списка.
- Поиск: O(1 + α), где α — load factor.
- Преимущества: простота, устойчивость к переполнению.
- Недостатки: память, кэш-локальность, деградация.

## 4.3 Коллизии: открытая адресация

### 🔌 Проблема: цепочки требуют указателей и плохо ложатся в кэш

В подглаве 4.2 мы разобрали метод цепочек. Но у него есть недостатки: указатели, плохая кэш-локальность, нагрузка на GC.

Возникает вопрос: **можно ли хранить все элементы прямо в массиве, без указателей и списков?**

Ответ — **открытая адресация (open addressing)**.

### 📐 Как работает открытая адресация

**Идея:** все элементы хранятся **прямо в массиве**. Если ячейка занята — ищем **следующую свободную** по определённому правилу.

**Алгоритм вставки:**

1. Вычисляем `index = hash(key) % size`.
2. Если ячейка `index` пуста — кладём элемент туда.
3. Если занята — пробуем следующую ячейку (по правилу **проб**).
4. Продолжаем, пока не найдём свободную.

**Алгоритм поиска:**

1. Вычисляем `index = hash(key) % size`.
2. Если ячейка `index` пуста — ключа нет.
3. Если в ячейке другой ключ — пробуем следующую (по тому же правилу).
4. Если нашли нужный ключ — возвращаем значение.

**Ключевая идея:** при вставке и при поиске используется **одна и та же последовательность проб**.

### 🔬 Виды проб

**1. Линейное пробирование (linear probing)**

```
index = (hash(key) + i) % size,  где i = 0, 1, 2, 3, ...
```

Простое, но даёт **кластеризацию**: несколько ключей подряд образуют длинный кластер занятых ячеек. Следующий ключ пройдёт весь кластер.

**2. Квадратичное пробирование (quadratic probing)**

```
index = (hash(key) + c1*i + c2*i²) % size
```

Например: `index = (hash + i²) % size`. Пробы: `hash`, `hash+1`, `hash+4`, `hash+9`, ... Это уменьшает первичную кластеризацию, но появляется **вторичная** — ключи с одинаковым хешем идут по одной последовательности.

**3. Двойное хеширование (double hashing)**

```
index = (hash1(key) + i * hash2(key)) % size
```

Каждый ключ имеет **свою уникальную** последовательность проб, зависящую от `hash2(key)`. Минимизирует и первичную, и вторичную кластеризацию. `hash2` должна возвращать значения, взаимно простые с размером массива.

### 🧮 Удаление в открытой адресации

Удаление — самая сложная операция.

**Наивный подход:** поставить `nil` в ячейку. **Это ломает поиск.** Если ключ A и B имели одинаковый хеш, A в ячейке 3, B в ячейке 4. Удаляем A: ставим `nil` в ячейку 3. Ищем B: ячейка 3 пуста → останавливаемся → «ключ не найден». Но B же в ячейке 4!

**Решение:** использовать **tombstone** — специальный маркер «удалено».

- При удалении ставим tombstone.
- При поиске tombstone не останавливает — продолжаем искать.
- При вставке tombstone можно перезаписать новым элементом.

**Цена tombstone:** они «загрязняют» таблицу. Со временем все ячейки могут стать tombstone или занятыми. Решение — **периодическая пересборка** таблицы (рехеширование без tombstone).

### 📊 Сравнение: цепочки vs открытая адресация

| | Цепочки | Открытая адресация |
|:---|:---|:---|
| Где хранятся элементы | В списках вне массива | Прямо в массиве |
| Память на элемент | Данные + указатель (8 байт) | Только данные |
| Кэш-локальность | Плохая (списки разбросаны) | Хорошая (всё в массиве) |
| Load factor | Может быть > 1 | Должен быть < 1 |
| Удаление | Простое | Сложное (tombstone) |
| Нагрузка на GC | Высокая | Низкая |
| Деградация | O(n) при плохой хеш-функции | O(n) при load factor ~1 |

**Главное преимущество открытой адресации:** кэш-локальность.
**Главный недостаток:** при load factor, близком к 1, производительность рушится.

### 🔬 Swiss Table: открытая адресация с SIMD

Классическая открытая адресация даёт кэш-локальность, но каждая проба — это **сравнение ключа**. Если ключи длинные, сравнение дорогое.

**Swiss Table** (Google, используется в Go 1.24+, C++, Rust) решает проблему через **управляющее слово (control word)**:

- Хеш делится на **h1** (старшие биты) и **h2** (младшие 7 бит).
- h1 выбирает **группу** — 8 слотов.
- h2 хранится в управляющем слове — 64-битном значении, где каждый байт описывает состояние слота.
- **Поиск:** одной SIMD-инструкцией сравниваем h2 со всеми 8 байтами управляющего слова. Если есть совпадения — проверяем полный ключ только в этих слотах.
- **Нет цепочек.** Коллизии разрешаются пробированием по группам.

**Почему это быстро:** одна SIMD-инструкция проверяет 8 слотов сразу. Меньше промахов кэша.

### 📊 Когда использовать открытую адресацию

**Хороша, когда:**

- Кэш-локальность критична.
- Ключи — небольшие.
- Память ограничена.
- Load factor ≤ 0.75.

**Плоха, когда:**

- Нужна устойчивость к переполнению.
- Частое удаление.
- Ключи — длинные строки.

### 💡 Что мы узнали?

- Открытая адресация: все элементы прямо в массиве, без списков.
- При коллизии ищем следующую свободную ячейку по правилу проб.
- Линейное пробирование простое, но даёт кластеризацию.
- Двойное хеширование — лучший вариант.
- Удаление требует **tombstone**, иначе поиск ломается.
- Load factor < 1 (обычно ≤ 0.75).
- Swiss Table — оптимизация через control word и SIMD. Используется в Go 1.24+.

## 4.4 Рехеширование и load factor

### 🔌 Проблема: таблица заполняется, производительность падает

Представь: у тебя хеш-таблица на 1000 ячеек. Ты вставил 500 элементов. Load factor = 0.5. Поиск быстрый.

900 элементов. Load factor = 0.9. Поиск — 5–10 проб.

1000 элементов. Load factor = 1.0. **Таблица заполнена.** Вставить некуда.

**Вопрос:** что делать?

Ответ — **рехеширование**: создать новую таблицу большего размера и перенести туда все элементы.

### 📐 Что такое рехеширование

**Рехеширование** — это создание новой таблицы с другим размером и **пересчёт** хеш-кодов всех существующих ключей для нового размера.

**Алгоритм:**

1. Создаём новую таблицу размером `newSize > oldSize`.
2. Проходим по всем элементам старой таблицы.
3. Вычисляем новый индекс: `hash(key) % newSize`.
4. Вставляем элемент в новую таблицу.
5. Освобождаем старую.

### 📊 Load factor

**Load factor** = `count / size`.

| Реализация | Метод | Порог load factor |
|:---|:---|:---|
| Java HashMap | Цепочки + деревья | 0.75 |
| Python dict | Открытая адресация | 0.66 |
| Go map (≤1.23) | Бакеты + overflow | ~6.5 элементов/бакет (~0.81) |
| Go map (1.24+) | Swiss Table | ~0.875 (7/8) |
| C++ unordered_map | Цепочки | 1.0 |

**Почему не 1.0:** при load factor, близком к 1, производительность рушится. При 0.9 в открытой адресации поиск может пройти 10+ ячеек.

**Почему не 0.5:** половина памяти тратится впустую.

**Оптимум:** 0.7–0.8.

### 🔬 Размер новой таблицы

**Вариант 1: удвоение (size × 2)**

- Простая формула, размер всегда степень двойки (быстрый `% size` через битовую маску).
- Недостаток: при плохой хеш-функции кластеры сохраняются.

**Вариант 2: следующее простое число**

- Лучшее распределение ключей по модулю.
- Недостаток: `% size` медленнее, чем битовая маска.

**Кто что использует:**

- Java HashMap, Python dict, Go map — удвоение.
- C++ unordered_map — следующее простое число.

### 📊 Стоимость рехеширования

**Наивное рехеширование:** копируем все элементы за один проход. O(n).

**Проблема:** в реальных системах рехеширование миллионов элементов занимает секунды. Это **latency spike** — внезапная задержка, которая ломает SLA.

### 🔬 Инкрементальное рехеширование

**Идея:** не переносить все элементы сразу, а **постепенно**, по несколько элементов за операцию.

**Как работает:**

1. Создаётся новая таблица.
2. Старая помечается как `oldbuckets`.
3. При каждой операции переносится **один бакет** (или группа).
4. Пока перенос не завершён, операции ищут элемент **в обеих таблицах**.
5. Когда все бакеты перенесены, старая освобождается.

**Преимущества:**

- Каждая операция занимает **O(1)** дополнительного времени.
- **Нет latency spike**.
- Суммарная стоимость — O(n), но «размазана» по n операциям.

**В Go map** используется именно инкрементальное рехеширование. Поле `nevacuate` отслеживает прогресс.

### 🧮 Амортизированная сложность

Рехеширование n элементов — O(n). Но происходит **редко**: только при превышении порога.

Между двумя рехешированиями — не менее n/2 операций.

```
Амортизированная стоимость = O(n) / (n/2) = O(1)
```

Тот же принцип, что и с расширением slice (подглава 2.3).

### 💡 Что мы узнали?

- Рехеширование — создание новой таблицы и пересчёт хеш-кодов.
- Load factor = count / size. Порог — 0.7–0.8.
- Размер новой: удвоение (Go, Java) или простое число (C++).
- Наивное рехеширование — O(n), latency spike.
- Инкрементальное — постепенный перенос, амортизированное O(1).
- В Go map — инкрементальное рехеширование.

## 4.5 Map в Go: как устроена внутри

### 🔌 Проблема: как `m[key]` находит значение за O(1)?

Ты пишешь `m["user:12345"]` и получаешь значение. Мгновенно. Даже если в map 10 миллионов записей.

Но как это работает? И тут есть важный нюанс: **реализация map в Go изменилась в версии 1.24**. То, что писали в статьях до 2025 года, описывает **старую** архитектуру. Новая — принципиально другая. Разберём обе.

---

## Часть 1: Go 1.23 и раньше — бакеты + overflow-цепочки

### 📐 Структура hmap

Map в Go (до 1.24) — это структура `hmap`:

```go
type hmap struct {
    count     int            // количество элементов
    flags     uint8          // флаги состояния
    B         uint8          // log_2 от количества бакетов
    noverflow uint16         // количество overflow-бакетов
    hash0     uint32         // seed для хеш-функции
    buckets   unsafe.Pointer // массив бакетов (2^B штук)
    oldbuckets unsafe.Pointer // старый массив при эвакуации
    nevacuate uintptr        // счётчик эвакуации
    extra     *mapextra      // дополнительная информация
}
```

**Что важно:**

- **`B`** — количество бакетов равно `2^B`. Если B = 10, бакетов 1024.
- **`buckets`** — указатель на массив бакетов. Непрерывный блок памяти.
- **`oldbuckets`** — используется при эвакуации (инкрементальном рехешировании).
- **`hash0`** — случайный seed, добавляется к хеш-коду. Защита от **hash-flooding атак**.

### 📐 Структура bucket

Каждый бакет — структура `bmap`:

```go
type bmap struct {
    tophash [8]uint8 // старшие 8 бит хеша для каждого из 8 слотов
    // далее: 8 ключей, потом 8 значений, потом указатель на overflow
}
```

**Ключевой момент:** в одном бакете **8 слотов**. Почему именно 8?

- 8 слотов × 8 байт tophash = 64 байта — ровно **одна строка кэша** (подглава 2.2).

**Что такое tophash:** младшие B бит хеша выбирают бакет. Старшие 8 бит сохраняются в `tophash` — быстрый фильтр. Сначала сравниваем 1 байт, потом полный ключ.

**Расположение ключей и значений:**

```
[bucket]
  tophash: [h0, h1, ..., h7]
  keys:    [k0, k1, ..., k7]
  values:  [v0, v1, ..., v7]
  overflow: *bmap
```

Почему не `k0, v0, k1, v1, ...`? Потому что это **устраняет padding** между полями разного размера.

### 🔬 Как происходит поиск

1. **Вычисляется хеш:** `hash("user:12345") + hash0`.
2. **Младшие B бит** определяют номер бакета.
3. **Идём в бакет.**
4. **Сравниваем tophash** для каждого из 8 слотов.
5. **Если tophash совпал** — сравниваем полный ключ.
6. **Если не нашли** — идём по указателю `overflow` в следующий бакет.

### 🔬 Overflow-бакеты

Если все 8 слотов заняты, создаётся **overflow-бакет** — связанный с основным указателем.

```
[bucket 0] → [overflow 0] → [overflow 1] → nil
```

Это **цепочка**. При высокой коллизии цепочка растёт. Поиск деградирует к O(n). Именно из-за этой проблемы Go 1.24 переписал map.

### 🔬 Эвакуация

Когда load factor превышает **6.5 элементов на бакет** (~0.81), запускается эвакуация.

1. Создаётся новый массив бакетов, в **2 раза больше**.
2. Старый сохраняется в `oldbuckets`.
3. При каждой операции эвакуируется **один бакет**.
4. Пока эвакуация не завершена, поиск идёт в обоих массивах.

## Часть 2: Go 1.24+ — Swiss Table

### 🔌 Почему отказались от бакетов

Старая реализация имела врождённые проблемы:

1. **Overflow-цепочки.** При плохом распределении — O(n).
2. **Плохая кэш-локальность.** Overflow-бакеты разбросаны.
3. **Сложность эвакуации.**
4. **Latency miss.**

Go 1.24 заменил всё это на **Swiss Table** — открытую адресацию с SIMD-оптимизациями.

### 📐 Swiss Table: структура

**1. Группы (groups) по 8 слотов**

Вместо бакетов — **группы**. Если группа заполнена, поиск продолжается в **следующей группе** (пробирование), а не в overflow-бакете.

**2. Управляющее слово (control word)**

У каждой группы — **64-битное управляющее слово**. Каждый байт — один слот:

- `0x80` — слот пуст.
- `0xFE` — слот удалён (tombstone).
- `0x00–0x7F` — слот занят, байт содержит **h2**.

**3. Разделение хеша на h1 и h2**

- **h1 (старшие 57 бит)** — выбирает **начальную группу**.
- **h2 (младшие 7 бит)** — хранится в управляющем слове.

### 🔬 Как происходит поиск

1. **Вычисляется хеш.**
2. **Разделяется на h1 и h2.**
3. **h1 определяет начальную группу.**
4. **SIMD-сравнение:** одной инструкцией сравниваем h2 со **всеми 8 байтами управляющего слова**.
5. **Если есть совпадения** — для каждого совпавшего слота сравниваем полный ключ.
6. **Если нет** — переходим к следующей группе.

**Ключевое отличие:** в старой реализации сравнивали tophash **по одному байту**, в цикле. В Swiss Table — **одной SIMD-инструкцией** проверяем все 8 слотов.

### 📊 SIMD: почему это быстро

SIMD (Single Instruction, Multiple Data) — процессорные инструкции, обрабатывающие несколько значений **за одну операцию**.

Вместо цикла по 8 слотам — одна SIMD-инструкция. На современных процессорах это 1–3 такта вместо 8–24.

### 📊 Сравнение: Go ≤1.23 vs Go 1.24+

| | Go ≤1.23 | Go 1.24+ |
|:---|:---|:---|
| **Структура** | hmap + бакеты | Swiss Table (groups + control word) |
| **Метод коллизий** | Цепочки (overflow) | Открытая адресация |
| **Размер группы** | 8 слотов | 8 слотов |
| **Управление** | tophash (по байту) | control word (SIMD) |
| **Поиск в группе** | Линейный цикл | Одна SIMD-инструкция |
| **Overflow** | Есть | Нет |
| **Load factor** | ~0.81 | ~0.875 |
| **Кэш-локальность** | Плохая | Хорошая |
| **Худший случай** | O(n) (цепочка) | O(n) (много проб) |

### 📊 Что изменилось для программиста

**API не изменился.** `m[key]`, `m[key] = value`, `delete(m, key)` — всё как раньше.

**Изменилась производительность:**

- Поиск быстрее за счёт SIMD.
- Меньше промахов кэша.
- Меньше latency spike при эвакуации.

**Что осталось прежним:**

- Map **не потокобезопасна**.
- Итерация **не детерминирована**.
- `len(m)` — O(1).

### 💡 Что мы узнали?

- **Go ≤1.23:** hmap + бакеты + overflow-цепочки. Поиск: tophash по байту.
- **Go 1.24+:** Swiss Table — открытая адресация + SIMD. Нет overflow.
- **Почему перешли:** цепочки, кэш-локальность, latency.
- **Хеш делится на h1 и h2:** h1 выбирает группу, h2 — в управляющем слове.
- **API не изменился.**

## 4.6 LRU Cache: хеш-таблица + двусвязный список

### 🔌 Проблема: как ускорить доступ к данным, которые не помещаются в память?

В подглаве 2.5 мы упомянули LRU Cache. Теперь разберём детально — это **самая частая задача на собеседованиях** после Two Sum.

**Задача:** у тебя есть медленное хранилище. Данные запрашиваются часто, но не все. Ты хочешь **кэшировать** самые популярные записи в RAM. Но RAM ограничена.

**LRU (Least Recently Used)** — вытесняй ту, к которой **дольше всего не обращались**.

**Требования:**

1. `get(key)` — O(1).
2. `put(key, value)` — O(1).
3. При переполнении — вытеснить наименее недавно использованную.

### 📐 Почему одной структуры недостаточно

**Хеш-таблица:** O(1) на `get` и `put`, но **не хранит порядок использования**.

**Связный список:** хранит порядок, но `get(key)` требует поиска по ключу — O(n).

**Вывод:** нужна **комбинация**:

- **Хеш-таблица** — для O(1) доступа по ключу.
- **Двусвязный список** — для O(1) управления порядком.

### 🔬 Как устроен LRU Cache

- Хеш-таблица хранит **указатели на узлы**: `key → *Node`.
- Двусвязный список хранит **порядок**: голова — самый свежий, хвост — самый старый.

```
Хеш-таблица:
"user:1"  → *Node(A)
"user:2"  → *Node(B)
"user:3"  → *Node(C)

Двусвязный список:
head ⇄ [A: user:1] ⇄ [C: user:3] ⇄ [B: user:2] ⇄ tail
```

**`get(key)`:**
1. Ищем узел в хеш-таблице — O(1).
2. Если нашли — **перемещаем узел в голову**.
3. Возвращаем значение.

**`put(key, value)`:**
1. Если ключ есть — обновляем значение, перемещаем в голову.
2. Если нет — создаём узел, добавляем в хеш-таблицу и в голову.
3. Если размер превышает capacity — **удаляем хвост** и его ключ из хеш-таблицы.

### 🔬 Почему двусвязный, а не односвязный

**Односвязный** хранит только `Next`. Чтобы удалить узел, нужно знать **предыдущий**. Найти его за O(1) нельзя.

**Двусвязный** хранит **и `Prev`, и `Next`**. Удаление любого узла — O(1). Перемещение в голову — O(1).

### 🧮 Реализация на Go

```go
type Node struct {
    key   string
    value interface{}
    prev  *Node
    next  *Node
}

type LRUCache struct {
    capacity int
    cache    map[string]*Node
    head     *Node
    tail     *Node
}

func NewLRUCache(capacity int) *LRUCache {
    return &LRUCache{
        capacity: capacity,
        cache:    make(map[string]*Node),
    }
}

func (c *LRUCache) remove(node *Node) {
    if node.prev != nil {
        node.prev.next = node.next
    } else {
        c.head = node.next
    }
    
    if node.next != nil {
        node.next.prev = node.prev
    } else {
        c.tail = node.prev
    }
}

func (c *LRUCache) addToHead(node *Node) {
    node.prev = nil
    node.next = c.head
    
    if c.head != nil {
        c.head.prev = node
    }
    c.head = node
    
    if c.tail == nil {
        c.tail = node
    }
}

func (c *LRUCache) moveToHead(node *Node) {
    c.remove(node)
    c.addToHead(node)
}

func (c *LRUCache) Get(key string) (interface{}, bool) {
    node, ok := c.cache[key]
    if !ok {
        return nil, false
    }
    c.moveToHead(node)
    return node.value, true
}

func (c *LRUCache) Put(key string, value interface{}) {
    if node, ok := c.cache[key]; ok {
        node.value = value
        c.moveToHead(node)
        return
    }
    
    newNode := &Node{key: key, value: value}
    
    if len(c.cache) >= c.capacity {
        oldTail := c.tail
        c.remove(oldTail)
        delete(c.cache, oldTail.key)
    }
    
    c.cache[key] = newNode
    c.addToHead(newNode)
}
```

**Почему узел хранит ключ:** чтобы при удалении из хвоста можно было удалить запись из хеш-таблицы за O(1).

### 📊 Сложность

| Операция | Сложность |
|:---|:---|
| `get` | O(1) |
| `put` (обновление) | O(1) |
| `put` (новый ключ) | O(1) |
| Память | O(capacity) |

### 🔬 Варианты LRU

**LFU (Least Frequently Used):** вытесняем самую редко используемую. Каждый узел хранит счётчик.

**2Q (Two Queue):** гибрид LRU и LFU. Две очереди — для новых и для часто используемых.

**Segmented LRU:** кэш делится на probationary и protected сегменты.

### 🔬 LRU Cache в реальных системах

- **Page cache в Linux.** Ядро вытесняет страницы по LRU-подобному алгоритму.
- **Redis.** Политики `allkeys-lru`, `volatile-lru`, `allkeys-lfu`.
- **DNS-резолверы.** Кэшируют результаты с TTL.
- **CDN.** Кэшируют контент на граничных серверах.

### 💡 Что мы узнали?

- LRU Cache требует **двух структур**: хеш-таблицы и двусвязного списка.
- Двусвязный список — потому что удаление требует указателя на `prev`.
- Узел хранит ключ для O(1) удаления из хеш-таблицы.
- Все операции — **гарантированно O(1)**.
- Варианты: LRU + TTL, LFU, 2Q, Segmented LRU.

## 4.7 Практика: решаем задачи

### 🔌 Проблема: как применять хеш-таблицу?

Мы разобрали теорию. Теперь — практика. Решим четыре задачи, каждая из которых использует хеш-таблицу.

---

### 📝 Задача 1: Two Sum

**Формулировка:** дан массив чисел и target. Найди два числа, сумма которых равна target. Верни их индексы.

**Пример:**

```
Вход: nums = [2, 7, 11, 15], target = 9
Выход: [0, 1]
Объяснение: nums[0] + nums[1] = 2 + 7 = 9
```

**Подход:**

Наивное решение: два вложенных цикла — O(n²).

**Оптимальное:** идём по массиву. Для каждого числа x проверяем, есть ли в хеш-таблице `target - x`. Если есть — нашли пару. Если нет — кладём x в хеш-таблицу (индекс → значение).

**Код:**

```go
func twoSum(nums []int, target int) []int {
    seen := make(map[int]int) // значение → индекс
    
    for i, x := range nums {
        complement := target - x
        if j, ok := seen[complement]; ok {
            return []int{j, i}
        }
        seen[x] = i
    }
    
    return nil
}
```

**Разбор на `[2, 7, 11, 15]`, target = 9:**

```
i=0, x=2: complement=7. 7 нет в seen. seen[2]=0.
i=1, x=7: complement=2. 2 есть в seen (индекс 0). Возвращаем [0, 1].
```

**Сложность:** O(n) по времени, O(n) по памяти.

**Почему хеш-таблица:** поиск `complement` — O(1) в среднем. Без неё — O(n) на каждый запрос.

### 📝 Задача 2: Group Anagrams

**Формулировка:** дан массив строк. Сгруппируй анаграммы вместе.

**Пример:**

```
Вход: ["eat", "tea", "tan", "ate", "nat", "bat"]
Выход: [["eat", "tea", "ate"], ["tan", "nat"], ["bat"]]
```

**Подход:**

Анаграммы имеют **одинаковый набор символов**. Если отсортировать символы в каждой строке, анаграммы дадут **одинаковый ключ**.

Например: `"eat"`, `"tea"`, `"ate"` → отсортированные: `"aet"`. Все три дают ключ `"aet"`.

Используем хеш-таблицу: ключ — отсортированная строка, значение — список анаграмм.

**Код:**

```go
func groupAnagrams(strs []string) [][]string {
    groups := make(map[string][]string)
    
    for _, s := range strs {
        // Сортируем символы — получаем ключ
        chars := []rune(s)
        sort.Slice(chars, func(i, j int) bool {
            return chars[i] < chars[j]
        })
        key := string(chars)
        
        groups[key] = append(groups[key], s)
    }
    
    result := make([][]string, 0, len(groups))
    for _, group := range groups {
        result = append(result, group)
    }
    return result
}
```

**Сложность:** O(n · k log k), где n — количество строк, k — средняя длина строки (сортировка занимает k log k).

**Альтернатива без сортировки:** использовать массив из 26 счётчиков как ключ. Сложность: O(n · k).

### 📝 Задача 3: Subarray Sum Equals K

**Формулировка:** дан массив чисел (могут быть отрицательные) и число k. Найди количество подмассивов, сумма которых равна k.

**Пример:**

```
Вход: nums = [1, 1, 1], k = 2
Выход: 2
Объяснение: [1,1] (индексы 0-1) и [1,1] (индексы 1-2)
```

**Подход:**

Наивное решение: два вложенных цикла — O(n²).

**Оптимальное:** используем **префиксные суммы**.

Идея: пусть `prefix[i]` — сумма элементов от 0 до i. Тогда сумма подмассива от i+1 до j = `prefix[j] - prefix[i]`. Мы ищем такие i, j, что `prefix[j] - prefix[i] = k`, то есть `prefix[i] = prefix[j] - k`.

Идём по массиву, накапливаем префиксную сумму. Для каждого `prefix[j]` проверяем, сколько раз `prefix[j] - k` встречался раньше. Используем хеш-таблицу: `prefix_sum → count`.

**Код:**

```go
func subarraySum(nums []int, k int) int {
    count := 0
    prefixSum := 0
    seen := map[int]int{0: 1} // prefix_sum → количество вхождений
    
    for _, x := range nums {
        prefixSum += x
        // Сколько раз встречалась сумма prefixSum - k?
        count += seen[prefixSum-k]
        seen[prefixSum]++
    }
    
    return count
}
```

**Разбор на `[1, 1, 1]`, k = 2:**

```
seen = {0: 1}
prefixSum = 0

x=1: prefixSum=1. seen[1-2]=seen[-1]=0. seen[1]=1.
x=1: prefixSum=2. seen[2-2]=seen[0]=1 → count=1. seen[2]=1.
x=1: prefixSum=3. seen[3-2]=seen[1]=1 → count=2. seen[3]=1.

Итог: 2.
```

**Сложность:** O(n) по времени, O(n) по памяти.

## 4.8 Итог: что мы узнали о хеш-таблицах

Мы начали с пролога: поиск по 50 миллионам записей тормозил. Мы переписали на `map`, и поиск ускорился в тысячи раз.

Теперь у нас есть полная картина:

1. **Хеш-функция** — превращает ключ в число. Хорошая функция: детерминированная, равномерная, быстрая, с лавинным эффектом.

4. **Map в Go** — до 1.24: бакеты + overflow-цепочки. С 1.24: Swiss Table (открытая адресация + SIMD).
5. **LRU Cache** — хеш-таблица + двусвязный список. O(1) на все операции.
6. **Практика** — Two Sum, Group Anagrams, Subarray Sum, LRU Cache.

Хеш-таблица — это **самая важная структура** после массива. Она даёт O(1) там, где без неё был бы O(n). И она лежит в основе реальных систем: базы данных, кэши, индексы.

## Что мы узнали?

- Хеш-таблица даёт **O(1) в среднем** на поиск, вставку, удаление.

- LRU Cache — хеш-таблица + двусвязный список. O(1) на все операции.

## Типичные ошибки

- ❌ **Использовать плохую хеш-функцию.** Все ключи в одном бакете — O(n) на поиск.
- ❌ **Забывать про hash-flooding атаки.** Без seed злоумышленник может подобрать ключи, попадающие в один бакет.
- ❌ **Хранить в map ключи-указатели.** Указатели меняются, хеш ломается.
- ❌ **Итерировать map и ожидать порядок.** Порядок не определён.
- ❌ **Использовать map в конкурентном коде без синхронизации.** `fatal error: concurrent map writes`.
- ❌ **Реализовывать LRU Cache на одной структуре.** Нужна комбинация: хеш-таблица + двусвязный список.
- ❌ **Удалять из открытой адресации через `nil`.** Ломает поиск. Используй tombstone.

## Для быстрого повторения

- **Хеш-функция:** ключ → число. Индекс = hash % size.
- **Коллизии:** цепочки (список на ячейку) или открытая адресация (пробирование).
- **Пробирование:** линейное, квадратичное, двойное хеширование.
- **Load factor:** 0.7–0.8. Рехеширование при превышении.
- **Go map:** ≤1.23 — бакеты + overflow. 1.24+ — Swiss Table (SIMD).
- **LRU Cache:** хеш-таблица + двусвязный список. O(1) на всё.
- **Паттерны:** Two Sum (map значение→индекс), Group Anagrams (map ключ→список), Subarray Sum (префиксные суммы + map).

## Ответы

**1.** Хеш-функция — функция, превращающая ключ в число (хеш-код). Хорошая функция: детерминированная (один ключ → один хеш), равномерная (ключи распределены по всему диапазону), быстрая, с лавинным эффектом (маленькое изменение ключа → большое изменение хеша).

**2.** Коллизия — ситуация, когда два разных ключа дают одинаковый индекс после `hash % size`. Методы: **цепочки** (каждая ячейка — связный список) и **открытая адресация** (при коллизии ищем следующую свободную ячейку).

**3.** Метод цепочек: массив ячеек, каждая — указатель на связный список. При вставке добавляем в начало списка (O(1)). При поиске проходим по списку, сравнивая ключи. Сложность: O(1 + α), где α — load factor.

**4.** Открытая адресация: все элементы прямо в массиве. При коллизии ищем следующую свободную ячейку по правилу проб. Три вида: **линейное** (index+1, index+2, ...), **квадратичное** (index+i²), **двойное хеширование** (index + i·hash2(key)).

**5.** `nil` останавливает поиск. Если ключи A и B имели одинаковый хеш, A в ячейке 3, B в ячейке 4. Удаляем A — ставим `nil` в ячейку 3. Ищем B: ячейка 3 пуста → останавливаемся → «ключ не найден», хотя B в ячейке 4. Решение — **tombstone** (маркер «удалено»), который не останавливает поиск.

**6.** Load factor = count / size. Показывает, насколько заполнена таблица. В Go ≤1.23 порог ~0.81 (6.5 элементов/бакет). В Go 1.24+ (Swiss Table) порог ~0.875 (7/8).

**7.** Рехеширование — создание новой таблицы большего размера и перенос всех элементов с пересчётом хешей. Наивное рехеширование — O(n), latency spike. **Инкрементальное** — постепенный перенос (по одному бакету за операцию), амортизированное O(1) на операцию, нет latency spike.

**8.** **Go ≤1.23:** hmap + бакеты по 8 слотов + overflow-цепочки. Поиск: сравнение tophash по одному байту, переход по цепочке. **Go 1.24+:** Swiss Table — открытая адресация с группами по 8 слотов и control word. Поиск: одна SIMD-инструкция. Нет overflow.

**9.** Swiss Table — реализация открытой адресации от Google. Хеш делится на **h1** (выбирает группу) и **h2** (хранится в control word). Control word — 64-битное слово, где каждый байт описывает слот: пусто, удалено, занято (с h2). Поиск: одна SIMD-инструкция сравнивает h2 со всеми 8 байтами control word. Быстрее, чем цикл по слотам.

**10.** LRU Cache требует двух структур: **хеш-таблицу** (O(1) доступ по ключу) и **двусвязный список** (O(1) управление порядком использования). Одна структура не справляется: хеш-таблица не хранит порядок, список не даёт O(1) поиск.

**11.** Двусвязный список хранит указатели **и на `Next`, и на `Prev`**. Удаление узла требует указателя на **предыдущий** узел (чтобы обновить его `Next`). В односвязном списке найти предыдущий за O(1) нельзя. Двусвязный даёт O(1) на удаление любого узла.

**12.** Two Sum: идём по массиву, для каждого x проверяем, есть ли в хеш-таблице `target - x`. Если есть — нашли пару. Если нет — кладём x. Сложность O(n) по времени, O(n) по памяти. Хеш-таблица ускоряет, потому что поиск `target - x` — O(1) вместо O(n).
