## 9.0 Пролог: индекс, который не влез в память

В Главе 8 мы разобрали AVL-дерево. Оно гарантирует O(log n) в худшем случае, балансируется автоматически. Отлично.

Ты пишешь базу данных. Хранишь миллионы записей на диске. Строишь индекс на AVL-дереве в памяти.

Проблема 1: **AVL-дерево не помещается в память**. Для миллиарда записей нужно ~16 ГБ только на узлы дерева. А нужно ещё хранить сами данные.

Проблема 2: **каждый поиск — это случайное обращение к диску**. AVL-дерево — это бинарное дерево. Высота log₂(n) ≈ 30 для миллиарда. Каждый узел — отдельная страница на диске. 30 случайных чтений с диска (каждое ~10 мс для HDD) = 300 мс на один запрос. Катастрофа.

Проблема 3: **AVL делает много поворотов при вставке**. Для базы данных, где записи вставляются постоянно, это дорого.

Решения:

1. **Красно-чёрное дерево** — менее строгий баланс, меньше поворотов. Лучше для частых вставок/удалений.
2. **B-дерево** — специально для дисковых операций. Один узел = одна страница диска. Высота ~3–4 для миллиарда записей. 3–4 чтения с диска вместо 30.

В этой главе мы разберём оба. И поймём, почему индексы в PostgreSQL — это B-деревья, а не AVL.

## 9.1 Красно-чёрное дерево: инварианты и свойства

### 🔌 Проблема: AVL делает слишком много поворотов

AVL-дерево поддерживает **строгий** баланс: разница высот ≤ 1. Это даёт лучший поиск (высота ≤ 1.44 log n), но требует **много поворотов** при вставке и удалении. В худшем случае — O(log n) поворотов на одну вставку.

Для систем с частыми вставками/удалениями это дорого. Нужен компромисс: **чуть менее строгий баланс**, но **меньше поворотов**.

Этот компромисс — **красно-чёрное дерево**.

### 📐 Что такое красно-чёрное дерево

**Красно-чёрное дерево** — это BST, где каждый узел имеет **цвет**: красный или чёрный. Цвета поддерживают **инварианты**, которые гарантируют, что дерево остаётся «достаточно сбалансированным».

**Пять инвариантов:**

1. **Каждый узел либо красный, либо чёрный.**
2. **Корень — чёрный.**
3. **Все листья (nil) — чёрные.** (В реализации nil считается чёрным.)
4. **У красного узла оба потомка — чёрные.** (Не может быть двух красных подряд.)
5. **Для каждого узла все пути от него до листьев содержат одинаковое количество чёрных узлов.** (Чёрная высота.)

**Ключевое следствие инварианта 5:** самый длинный путь (красный-чёрный-красный-...) не более чем **в два раза** длиннее самого короткого (только чёрные). Значит, высота дерева ≤ 2 · log₂(n+1). Гарантированно O(log n).

### 📊 Сравнение с AVL

| | AVL | Красно-чёрное |
|:---|:---|:---|
| Баланс | Строгий (разница высот ≤ 1) | Менее строгий (высота ≤ 2 log n) |
| Высота | ≤ 1.44 log n | ≤ 2 log n |
| Поиск | Чуть быстрее | Чуть медленнее |
| Вставка/удаление | Много поворотов | Меньше поворотов |
| Когда выбирать | Частый поиск | Частые вставки/удаления |

### 🔬 Пример красно-чёрного дерева

```
        10(B)
       /     \
    5(R)     15(R)
   /   \    /    \
 3(B) 7(B) 12(B) 18(B)
```

Проверим инварианты:

1. Все узлы красные или чёрные. ✅
2. Корень 10 — чёрный. ✅
3. Листья — чёрные (nil). ✅
4. Красные узлы (5, 15) имеют чёрных потомков. ✅
5. Чёрная высота: от корня до любого листа — 2 чёрных узла (10, 3/7/12/18). ✅

### 📐 Почему это работает

**Ключевая идея:** красные узлы — это «промежуточные» элементы, которые **не увеличивают чёрную высоту**. Они позволяют дереву быть «шире», но не выше.

Максимальная высота: если чередовать красные и чёрные, высота = 2 · чёрная_высота. Чёрная высота ≤ log₂(n+1). Значит, высота ≤ 2 log₂(n+1).

**Это гарантирует O(log n) на все операции.**

### 💡 Что мы узнали?

- Красно-чёрное дерево — BST с цветами и пятью инвариантами.
- Ключевые инварианты: корень чёрный, нет двух красных подряд, одинаковая чёрная высота.
- Высота ≤ 2 log n — гарантированно O(log n).
- Меньше поворотов, чем AVL — лучше для частых вставок/удалений.

## 9.2 Вставка в красно-чёрное дерево

### 🔌 Проблема: как вставить элемент, не нарушив инварианты?

Вставка в BST — простая. Но в красно-чёрном дереве нужно сохранить инварианты. Если вставить красный узел — можно нарушить инвариант 4 (два красных подряд). Если чёрный — нарушить инвариант 5 (чёрная высота).

**Стандартный подход:** вставляем **красный** узел. Если нарушены инварианты — исправляем поворотами и перекраской.

### 📐 Алгоритм вставки

1. **Стандартная BST вставка.** Новый узел — красный.
2. **Проверка инвариантов.** Если родитель нового узла — чёрный, инварианты не нарушены. Готово.
3. **Если родитель красный** — нарушен инвариант 4. Нужно исправить. Возможны три случая (по цвету «дяди» — брата родителя):
   - **Случай 1:** дядя красный → перекрашиваем родителя и дядю в чёрный, деда в красный, продолжаем проверку с деда.
   - **Случай 2:** дядя чёрный, новый узел — «внутренний» потомок → поворот, чтобы сделать «внешним».
   - **Случай 3:** дядя чёрный, новый узел — «внешний» потомок → перекраска + поворот.

### 🔬 Пошаговый пример

Вставим узлы `10, 20, 30, 15` в пустое красно-чёрное дерево.

**Вставка 10:**

```
10(B)   ← корень всегда чёрный
```

**Вставка 20:**

```
10(B)
  \
  20(R)
```

Родитель 10 — чёрный. Инварианты не нарушены.

**Вставка 30:**

```
10(B)
  \
  20(R)
    \
    30(R)
```

Родитель 20 — красный. Нарушен инвариант 4. Дядя 30 — nil (чёрный). Случай 3 (внешний потомок).

**Исправление:**

1. Перекрашиваем родителя (20) в чёрный, деда (10) в красный.
2. Делаем left rotation вокруг 10.

```
     20(B)
    /     \
  10(R)   30(R)
```

Инварианты восстановлены. ✅

**Вставка 15:**

```
     20(B)
    /     \
  10(R)   30(R)
    \
    15(R)
```

Родитель 10 — красный, дядя 30 — красный. Случай 1.

**Исправление:** перекрашиваем родителя (10) и дядю (30) в чёрный, деда (20) в красный.

```
     20(R)
    /     \
  10(B)   30(B)
    \
    15(R)
```

Корень 20 — красный. Нарушен инвариант 2. Перекрашиваем корень в чёрный.

```
     20(B)
    /     \
  10(B)   30(B)
    \
    15(R)
```

Инварианты восстановлены. ✅

### 🧮 Сложность вставки

**O(log n)** — высота дерева O(log n), на каждом уровне O(1) работы (повороты и перекраска).

**Количество поворотов:** не более **2** на одну вставку. Это ключевое преимущество перед AVL (там может быть O(log n) поворотов).

### 💡 Что мы узнали?

- Вставка: стандартная BST + новый узел красный.
- Если родитель красный — три случая по цвету дяди.
- Исправление: перекраска + повороты.
- Не более 2 поворотов на вставку.
- Сложность O(log n).

## 9.3 Удаление в красно-чёрном дереве

### 🔌 Проблема: удаление сложнее вставки

Удаление в BST — три случая (лист, один потомок, два потомка). В красно-чёрном дереве добавляется ещё сложность: удаление может нарушить инвариант 5 (чёрная высота).

**Ключевая идея:** если удаляем **красный** узел — инварианты не нарушаются (красные не вносят вклад в чёрную высоту). Если удаляем **чёрный** — нарушается чёрная высота, нужно исправлять.

### 📐 Алгоритм удаления

1. **Стандартное BST удаление.**
2. **Если удалённый узел был чёрным** — нарушена чёрная высота. Нужно исправить.
3. **Исправление:** «двойная чёрность» — концептуальный механизм. Узел, который «заменил» удалённый, получает дополнительный чёрный цвет. Нужно «передать» этот чёрный вверх или перекрасить.

**Четыре случая** (по цвету «брата» — sibling):

1. **Брат красный** → перекраска + поворот.
2. **Брат чёрный, оба его потомка чёрные** → перекрашиваем брата в красный, передаём двойную чёрность родителю.
3. **Брат чёрный, левый потомок красный, правый чёрный** → поворот + перекраска.
4. **Брат чёрный, правый потомок красный** → перекраска + поворот, готово.

### 📊 Сложность удаления

**O(log n)** — как и вставка. Количество поворотов — не более **3**.

### 💡 Что мы узнали?

- Удаление сложнее вставки из-за инварианта чёрной высоты.
- Если удаляем красный — инварианты не нарушаются.
- Если чёрный — «двойная чёрность» и четыре случая исправления.
- Сложность O(log n), не более 3 поворотов.

## 9.4 AVL vs красно-чёрное: когда что выбирать

### 📊 Сравнение

| | AVL | Красно-чёрное |
|:---|:---|:---|
| Баланс | Строгий | Менее строгий |
| Высота | ≤ 1.44 log n | ≤ 2 log n |
| Поиск | Быстрее (меньше высота) | Медленнее |
| Вставка | Много поворотов | ≤ 2 поворотов |
| Удаление | Много поворотов | ≤ 3 поворотов |
| Память на узел | Высота (int) | Цвет (1 бит) |
| Реализация | Сложнее | Сложнее |

### 📐 Когда что выбирать

**AVL:**

- Частый **поиск**, редкие вставки/удаления.
- Нужна **минимальная высота** (например, для кэша).
- Range queries (inorder обход).

**Красно-чёрное:**

- Частые **вставки/удаления**.
- Нужна **предсказуемость** (не более 2–3 поворотов).
- Стандартные библиотеки (`std::map` в C++, `TreeMap` в Java, `map` в Linux).

### 📊 Где используется красно-чёрное дерево

1. **Java `TreeMap` и `TreeSet`.**
2. **C++ `std::map`, `std::set`.**
3. **Linux kernel** — для планировщика, для управления виртуальной памятью.
4. **Java `HashMap`** — когда цепочка в бакете становится длинной (> 8), она превращается в красно-чёрное дерево.
5. **Nginx** — для таймеров.
6. **PostgreSQL** — для некоторых индексов.

### 📊 Почему Go не использует красно-чёрное дерево в стандартной библиотеке

В Go нет стандартного `TreeMap`. Есть `container/list` (связный список), но нет дерева.

Причины:

1. **Go фокусируется на простоте.** Красно-чёрное дерево — сложная структура, которую нужно поддерживать.
2. **Map покрывает большинство сценариев.** Для упорядоченных операций можно отсортировать map или использовать slice.
3. **Сообщество предоставляет реализации.** `github.com/emirpasic/gods` и другие.

Но в **Go 1.24+** map использует Swiss Table, а не деревья. В Java HashMap — деревья для длинных цепочек.

### 💡 Что мы узнали?

- AVL — для частого поиска, красно-чёрное — для частых вставок/удалений.
- Красно-чёрное — стандарт в библиотеках (C++, Java, Linux).
- Go не имеет стандартного дерева, но сообщество предоставляет.
- В Go map (1.24+) — Swiss Table, в Java HashMap — деревья для длинных цепочек.

## 9.5 B-дерево: структура и операции

### 🔌 Проблема: красно-чёрное дерево не подходит для диска

Красно-чёрное дерево — бинарное. Каждый узел содержит **один ключ** и два указателя. Высота O(log n).

Для миллиарда записей высота ≈ 30. Каждый узел — отдельная страница на диске. Поиск = 30 случайных чтений с диска. При 10 мс на чтение (HDD) — 300 мс. Катастрофа.

**Проблема:** бинарное дерево делает **много обращений к диску**. Каждое обращение — дорого (10 мс для HDD, 0.1 мс для SSD).

**Решение:** **B-дерево**. Узел содержит **много ключей** (обычно сотни), а не один. Один узел = **одна страница диска** (обычно 4–16 КБ).

### 📐 Что такое B-дерево

**B-дерево** — это сбалансированное дерево поиска, где:

1. **Каждый узел содержит несколько ключей** (от t-1 до 2t-1, где t — минимальная степень).
2. **Ключи в узле отсортированы.**
3. **Каждый узел имеет потомков:** для k ключей — k+1 потомков.
4. **Все листья на одном уровне.**
5. **Высота O(log_t n).**

**Параметр t (минимальная степень):**

- Минимум ключей в узле: t-1.
- Максимум ключей: 2t-1.
- Минимум потомков: t.
- Максимум потомков: 2t.

**Пример B-дерева с t=2:**

```
        [10, 20]
       /    |    \
    [5]   [15]   [25, 30]
```

- Корень: 2 ключа, 3 потомка.
- Листья: 1, 1, 2 ключа.

### 📊 Почему B-дерево быстрое для диска

**Ключевая идея:** один узел B-дерева = **одна страница диска** (4–16 КБ). В одну страницу помещается **сотни ключей**.

**Высота B-дерева:**

- При t=100, каждый узел содержит до 199 ключей.
- Для миллиарда записей: log₁₀₀(1 000 000 000) ≈ 5. Высота = 5.
- Поиск = 5 чтений с диска. Вместо 30 у красно-чёрного.

**Ещё оптимизация:** корень и верхние уровни кэшируются в памяти. Реально с диска читаются только нижние 1–2 уровня. Поиск = 1–2 чтения с диска.

### 🔬 Поиск в B-дереве

**Алгоритм:**

1. Начинаем с корня.
2. В узле ищем ключ **бинарным поиском** (ключи отсортированы).
3. Если нашли — возвращаем.
4. Если нет — определяем, в какого потомка идти (между какими ключами).
5. Переходим к потомку, повторяем.

**Сложность:** O(log_t n) обращений к диску, каждое — O(log t) сравнений в памяти.

### 🔬 Вставка в B-дерево

**Алгоритм:**

1. Находим лист, куда должен попасть новый ключ.
2. Вставляем ключ в лист (в отсортированном порядке).
3. Если лист **переполнен** (больше 2t-1 ключей) — **разбиваем** его на два:
   - Средний ключ поднимается в родителя.
   - Левые ключи — в левый узел.
   - Правые ключи — в правый узел.
4. Если родитель тоже переполнен — повторяем.

**Пример (t=2, максимум 3 ключа):**

Вставляем 5 в узел `[1, 2, 3]`:

```
Было: [1, 2, 3]
Стало: [1, 2, 3, 5] → переполнение!

Разбиваем:
- Средний ключ (2) поднимается в родителя.
- Левый узел: [1]
- Правый узел: [3, 5]
```

### 🔬 Удаление в B-дереве

**Алгоритм:**

1. Находим ключ.
2. Если ключ в листе — удаляем.
3. Если ключ во внутреннем узле — заменяем его **предшественником** (максимум в левом поддереве) или **преемником** (минимум в правом).
4. Если после удаления узел **недозаполнен** (меньше t-1 ключей) — **заимствуем** ключ у соседа или **сливаем** с соседом.

### 📊 Сложность B-дерева

| Операция | Сложность |
|:---|:---|
| Поиск | O(log_t n) обращений к диску |
| Вставка | O(log_t n) |
| Удаление | O(log_t n) |

### 💡 Что мы узнали?

- B-дерево: узел содержит много ключей, один узел = одна страница диска.
- Высота O(log_t n) — логарифм по основанию t (сотни).
- Поиск: 1–5 чтений с диска вместо 30.
- Вставка: разбиение переполненных узлов.
- Удаление: заимствование или слияние.

## 9.6 B+дерево: почему индексы в базах данных

### 🔌 Проблема: B-дерево хранит данные в каждом узле

В B-дереве **каждый узел содержит ключи и данные** (или указатели на данные). Это значит:

- Внутренние узлы тоже содержат данные — тратят место.
- Range queries (поиск диапазона) требуют обхода всего дерева.

Для индексов в базе данных это неоптимально.

### 📐 Что такое B+дерево

**B+дерево** — модификация B-дерева:

1. **Внутренние узлы содержат только ключи** (без данных). Только листья содержат данные (или указатели на данные).
2. **Все листья связаны в связный список.** Это позволяет быстро делать range queries.
3. **Ключи могут дублироваться** во внутренних узлах и листьях.

**Пример B+дерева:**

```
Внутренние:
         [10, 20]
        /    |    \

Листья:
  [5, 8] → [10, 15] → [20, 25, 30]
```

### 📊 Почему B+дерево лучше для индексов

**1. Больше ключей во внутренних узлах.** Раз нет данных — в узел помещается больше ключей. Высота меньше.

**2. Range queries быстрее.** Листья связаны в список. Найти диапазон — найти начало и пройти по списку.

**3. Все данные на одном уровне.** Листья на одном уровне — поиск предсказуем.

**4. Данные только в листьях.** Внутренние узлы можно кэшировать в памяти.

### 🔬 Пример: индекс в PostgreSQL

```sql
CREATE INDEX idx_users_age ON users(age);

-- Запрос:
SELECT * FROM users WHERE age BETWEEN 25 AND 35;
```

**PostgreSQL использует B+дерево:**

1. Находит лист с ключом 25.
2. Идёт по связанному списку листьев до ключа 35.
3. Для каждого ключа — указатель на запись в таблице.

**Сложность:** O(log n + k), где k — количество записей в диапазоне.

### 📊 B-дерево vs B+дерево

| | B-дерево | B+дерево |
|:---|:---|:---|
| Данные в узлах | Все узлы | Только листья |
| Ключи во внутренних узлах | Меньше (место под данные) | Больше |
| Высота | Выше | Ниже |
| Range queries | Медленнее | Быстрее (связный список) |
| Применение | Файловые системы | Индексы баз данных |

### 📊 Где используется B+дерево

1. **PostgreSQL** — B+дерево для индексов (называется просто «B-tree», но реализация — B+).
2. **MySQL (InnoDB)** — B+дерево для индексов.
3. **SQLite** — B-дерево (не B+) для таблиц и индексов.
4. **Oracle** — B+дерево для индексов.
5. **Файловые системы** — NTFS, ext4, XFS, Btrfs используют B-деревья или их варианты.

### 📊 Почему в базах данных не используют AVL или красно-чёрное

1. **Слишком высокая высота** для диска. 30 чтений вместо 3–5.
2. **Маленькие узлы.** Один ключ на узел — трата места.
3. **Плохая кэш-локальность.** Узлы разбросаны по памяти.
4. **Нет range queries.** Нужно обходить всё дерево.

B-деревья специально спроектированы для диска: **большие узлы**, **маленькая высота**, **range queries через связный список**.

### 💡 Что мы узнали?

- B+дерево: данные только в листьях, листья связаны списком.
- Лучше для индексов: больше ключей во внутренних узлах, range queries.
- PostgreSQL, MySQL, Oracle используют B+дерево для индексов.
- B-дерево лучше для файловых систем (данные в узлах).

## 9.7 Практика: решаем задачи

### 📝 Задача 1: Валидация красно-чёрного дерева

**Формулировка:** дано бинарное дерево с цветами. Проверь, является ли оно красно-чёрным.

**Подход:** проверить все пять инвариантов рекурсивно.

```go
type RBNode struct {
    Key    int
    Color  bool // true = red, false = black
    Left   *RBNode
    Right  *RBNode
}

func isRedBlack(root *RBNode) bool {
    if root == nil {
        return true
    }
    // Инвариант 2: корень чёрный
    if root.Color {
        return false
    }
    _, ok := checkRB(root)
    return ok
}

// Возвращает чёрную высоту и флаг валидности
func checkRB(n *RBNode) (int, bool) {
    if n == nil {
        return 1, true // nil считается чёрным
    }
    
    // Инвариант 4: красный узел не может иметь красных потомков
    if n.Color {
        if (n.Left != nil && n.Left.Color) || (n.Right != nil && n.Right.Color) {
            return 0, false
        }
    }
    
    leftHeight, leftOK := checkRB(n.Left)
    rightHeight, rightOK := checkRB(n.Right)
    
    if !leftOK || !rightOK {
        return 0, false
    }
    
    // Инвариант 5: одинаковая чёрная высота
    if leftHeight != rightHeight {
        return 0, false
    }
    
    if n.Color {
        return leftHeight, true
    }
    return leftHeight + 1, true
}
```

**Сложность:** O(n).

---

### 📝 Задача 2: Преобразование BST в красно-чёрное дерево

**Формулировка:** дан BST. Преобразуй его в красно-чёрное дерево.

**Подход:** это сложная задача, обычно не решается «в лоб». На практике используется **вставка** элементов BST в новое красно-чёрное дерево.

```go
func bstToRB(root *Node) *RBNode {
    var rb *RBNode
    // Inorder обход BST (отсортированный порядок)
    var inorder func(n *Node)
    inorder = func(n *Node) {
        if n == nil {
            return
        }
        inorder(n.Left)
        rb = rbInsert(rb, n.Key)
        inorder(n.Right)
    }
    inorder(root)
    return rb
}
```

**Сложность:** O(n log n) — n вставок по O(log n).

---

### 📝 Задача 3: B-дерево: проверка свойств

**Формулировка:** дано B-дерево. Проверь, что оно валидно.

**Подход:** рекурсивно проверить:

1. Все листья на одном уровне.
2. Каждый узел (кроме корня) имеет от t-1 до 2t-1 ключей.
3. Ключи в узле отсортированы.
4. Ключи в поддеревьях между ключами.

```go
type BNode struct {
    Keys     []int
    Children []*BNode
    Leaf     bool
}

func isValidBTree(root *BNode, t int) bool {
    if root == nil {
        return true
    }
    // Корень может иметь от 1 до 2t-1 ключей
    if len(root.Keys) < 1 || len(root.Keys) > 2*t-1 {
        return false
    }
    _, ok := checkBNode(root, t, true)
    return ok
}

func checkBNode(n *BNode, t int, isRoot bool) (int, bool) {
    // Проверка количества ключей
    if !isRoot && (len(n.Keys) < t-1 || len(n.Keys) > 2*t-1) {
        return 0, false
    }
    
    // Проверка сортировки ключей
    for i := 1; i < len(n.Keys); i++ {
        if n.Keys[i-1] >= n.Keys[i] {
            return 0, false
        }
    }
    
    // Лист
    if n.Leaf {
        return 1, true
    }
    
    // Проверка потомков
    if len(n.Children) != len(n.Keys)+1 {
        return 0, false
    }
    
    var leafDepth int
    for i, child := range n.Children {
        depth, ok := checkBNode(child, t, false)
        if !ok {
            return 0, false
        }
        if i == 0 {
            leafDepth = depth
        } else if depth != leafDepth {
            return 0, false // листья на разной глубине
        }
        
        // Проверка диапазона ключей
        if i > 0 && child.Keys[len(child.Keys)-1] >= n.Keys[i-1] {
            return 0, false
        }
        if i < len(n.Keys) && child.Keys[0] <= n.Keys[i] {
            return 0, false
        }
    }
    
    return leafDepth + 1, true
}
```

**Сложность:** O(n).

---

### 📝 Задача 4: Range Query в B+дереве

**Формулировка:** найти все ключи в диапазоне [low, high] в B+дереве.

**Подход:**

1. Найти лист с ключом ≥ low.
2. Идти по связанному списку листьев, собирая ключи ≤ high.

```go
func rangeQuery(root *BNode, low, high int) []int {
    result := []int{}
    leaf := findLeaf(root, low)
    
    for leaf != nil {
        for _, key := range leaf.Keys {
            if key >= low && key <= high {
                result = append(result, key)
            }
            if key > high {
                return result
            }
        }
        leaf = leaf.Next // указатель на следующий лист
    }
    
    return result
}
```

**Сложность:** O(log n + k), где k — количество результатов.

---

### 💡 Что мы узнали?

- **Валидация КЧ-дерева:** проверить 5 инвариантов рекурсивно. O(n).
- **BST → КЧ-дерево:** inorder обход + вставка. O(n log n).
- **Валидация B-дерева:** рекурсивная проверка свойств. O(n).
- **Range query в B+дереве:** найти лист + пройти по списку. O(log n + k).

## 9.8 Итог: что мы узнали о деревьях поиска

Мы начали с пролога: AVL-дерево не подходит для базы данных из-за высоты и дисковых операций. Решения — красно-чёрное дерево и B-дерево.

Теперь у нас полная картина:

1. **Красно-чёрное дерево:** BST с цветами, 5 инвариантов. Высота ≤ 2 log n. Меньше поворотов, чем AVL.
2. **Вставка:** новый узел красный, исправление через перекраску и повороты.
3. **Удаление:** сложнее вставки, «двойная чёрность», четыре случая.
4. **B-дерево:** узел содержит много ключей, один узел = страница диска. Высота O(log_t n).
5. **B+дерево:** данные только в листьях, листья связаны списком. Идеально для индексов.
6. **Почему в базах данных — B+дерево:** меньше высота, range queries, данные на одном уровне.

**Главные выводы:**

- AVL — для частого поиска, красно-чёрное — для частых вставок/удалений.
- B-деревья — для дисковых операций.
- B+деревья — для индексов баз данных.
- Выбор структуры зависит от того, где хранятся данные: память или диск.

| Термин | Определение |
|:---|:---|
| **Красно-чёрное дерево** | BST с цветами и 5 инвариантами, гарантирует O(log n) |
| **Чёрная высота** | Количество чёрных узлов на пути от узла до листа |
| **Двойная чёрность** | Концептуальный механизм при удалении чёрного узла |
| **B-дерево** | Сбалансированное дерево с несколькими ключами в узле |
| **B+дерево** | B-дерево с данными только в листьях и связным списком |
| **Минимальная степень t** | Параметр B-дерева: от t-1 до 2t-1 ключей в узле |
| **Разбиение** | Разделение переполненного узла B-дерева |
| **Заимствование** | Взятие ключа у соседа при недозаполнении |
| **Слияние** | Объединение двух узлов B-дерева |
| **Range query** | Поиск всех ключей в диапазоне |

## Что мы узнали?

- Красно-чёрное дерево — BST с 5 инвариантами, высота ≤ 2 log n.
- Меньше поворотов, чем AVL (≤ 2 на вставку, ≤ 3 на удаление).
- B-дерево — много ключей в узле, один узел = страница диска.
- B+дерево — данные только в листьях, связный список для range queries.
- B-деревья используются в файловых системах, B+деревья — в индексах БД.
- Выбор структуры зависит от того, где хранятся данные.

## Типичные ошибки

- ❌ **Путать AVL и красно-чёрное.** AVL строже, красно-чёрное — мягче.
- ❌ **Забывать про инвариант чёрной высоты.** Это ключевой инвариант.
- ❌ **Считать, что B-дерево — бинарное.** Нет, узел содержит много ключей.
- ❌ **Путать B-дерево и B+дерево.** В B+ данные только в листьях.
- ❌ **Использовать AVL для дисковых операций.** B-дерево лучше.
- ❌ **Забывать про параметр t в B-дереве.** От него зависит высота.

---

## Для быстрого повторения

- **Красно-чёрное:** 5 инвариантов, высота ≤ 2 log n, ≤ 2 поворотов на вставку.
- **AVL vs КЧ:** AVL строже, КЧ — меньше поворотов.
- **B-дерево:** много ключей в узле, высота O(log_t n), разбиение при переполнении.
- **B+дерево:** данные только в листьях, связный список, range queries.
- **Где используется:** КЧ — std::map, TreeMap, Linux kernel; B+ — PostgreSQL, MySQL, Oracle.
- **Правило:** память → КЧ, диск → B-дерево.

## Вопросы для самопроверки

1. Почему AVL не всегда лучший выбор? Когда красно-чёрное дерево лучше?
2. Какие пять инвариантов красно-чёрного дерева?
3. Почему высота красно-чёрного дерева ≤ 2 log n?
4. Как вставка в красно-чёрное дерево восстанавливает инварианты?
5. Почему удаление сложнее вставки в красно-чёрном дереве?
6. Что такое B-дерево? Чем отличается от бинарного дерева?
7. Почему B-дерево быстрое для дисковых операций?
8. Чем B+дерево отличается от B-дерева?
9. Почему в базах данных используют B+дерево, а не AVL?
10. Где используется красно-чёрное дерево, а где — B-дерево?

## Ответы

**1.** AVL строже балансируется (разница высот ≤ 1), делает много поворотов при вставке/удалении. Красно-чёрное дерево менее строгое (высота ≤ 2 log n), делает меньше поворотов. AVL лучше для частого поиска, красно-чёрное — для частых вставок/удалений.

**2.** (1) Каждый узел красный или чёрный. (2) Корень чёрный. (3) Все листья (nil) чёрные. (4) У красного узла оба потомка чёрные. (5) Для каждого узла все пути до листьев содержат одинаковое количество чёрных узлов.

**3.** Чёрная высота ≤ log₂(n+1) (как у обычного BST). Самый длинный путь чередует красные и чёрные узлы. Красных не может быть больше, чем чёрных (инвариант 4). Значит, высота ≤ 2 × чёрная высота ≤ 2 log₂(n+1).

**4.** Новый узел — красный. Если родитель красный — нарушение инварианта 4. Исправление зависит от цвета «дяди»: (1) дядя красный → перекраска; (2) дядя чёрный, внутренний → поворот + перекраска; (3) дядя чёрный, внешний → перекраска + поворот.

**5.** Удаление может нарушить инвариант 5 (чёрная высота), если удаляется чёрный узел. Нужен механизм «двойной чёрности» и четыре случая исправления. Вставка нарушает только инвариант 4 — три случая.

**6.** B-дерево — сбалансированное дерево, где каждый узел содержит **много ключей** (от t-1 до 2t-1) и **много потомков** (от t до 2t). Не бинарное. Все листья на одном уровне.

**7.** Один узел B-дерева = одна страница диска (4–16 КБ). В одну страницу помещается **сотни ключей**. Высота O(log_t n) — для миллиарда записей 3–5 уровней. Поиск = 3–5 чтений с диска вместо 30 у бинарного дерева.

**8.** В B+дереве **все данные только в листьях**, внутренние узлы содержат только ключи. Листья **связаны в связный список**. Это даёт: (1) больше ключей во внутренних узлах → меньше высота; (2) быстрые range queries через список.

**9.** B+дерево: (1) высота 3–5 вместо 30 у AVL; (2) range queries через связный список; (3) данные на одном уровне; (4) внутренние узлы кэшируются в памяти. AVL не подходит для диска из-за высокой высоты и случайных чтений.

**10.** Красно-чёрное: `std::map` (C++), `TreeMap` (Java), Linux kernel, Nginx. B-дерево: файловые системы (NTFS, ext4, XFS). B+дерево: индексы PostgreSQL, MySQL, Oracle.
