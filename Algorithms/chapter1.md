## 1.0 Пролог: алгоритм, который работал быстро, а потом сервер упал

Ты написал сервис, который ищет пользователей по email. В базе — 1000 записей. Ты пишешь простой линейный поиск:

```go
func findUser(users []User, email string) *User {
    for i := range users {
        if users[i].Email == email {
            return &users[i]
        }
    }
    return nil
}
```

Тестируешь на 1000 пользователей — работает мгновенно. Деплоишь в продакшен. Через месяц в базе уже 100 000 пользователей. Запросы всё ещё отрабатывают быстро. Через год — 10 миллионов. И вот тут сервис начинает тормозить: каждый запрос занимает секунды, CPU загружен на 100%, пользователи жалуются.

Что произошло? Алгоритм не изменился — он всё тот же линейный поиск. Изменился **размер входных данных**. И поведение алгоритма, которое было незаметно на 1000 элементах, стало катастрофой на 10 миллионах.

**Почему так вышло?** Потому что ты не оценил **сложность** алгоритма до того, как запустил его в продакшен. Ты не задал себе вопрос: «Как время работы этого алгоритма зависит от размера входных данных?»

**Сложность алгоритма** — это то, как растёт время его работы (или потребление памяти) при увеличении размера входных данных. Не «сколько секунд он работает на 1000 элементах», а «во сколько раз он замедлится, если элементов станет в 10 раз больше».

В этой главе мы научимся отвечать на этот вопрос **до написания кода**. Мы разберём O-нотацию — язык, на котором инженеры говорят о производительности. Мы узнаем, почему O(2n) и O(n) — это одно и то же, а O(n) и O(n²) — принципиально разные. Мы разберём амортизированный анализ — способ оценки сложности, который объясняет, почему добавление в динамический массив в среднем O(1), хотя иногда O(n). И мы поймём, почему иногда алгоритм с «худшей» сложностью работает быстрее на реальных данных.

## 1.1 Что такое O-нотация и зачем она нужна

### 🔌 Проблема: как сравнивать алгоритмы, не запуская их?

У тебя есть два алгоритма для одной задачи. Первый обрабатывает массив за 100 миллисекунд на 1000 элементах. Второй — за 50 миллисекунд. Какой лучше? Казалось бы, второй — он быстрее вдвое.

Но это сравнение **на конкретном размере данных**. Что будет на 100 000 элементах? На 10 миллионах? Будет ли второй алгоритм всё ещё быстрее? Или первый алгоритм растёт медленнее и обгонит второй на больших данных?

Без понимания **скорости роста** ты не можешь ответить на этот вопрос. А скорость роста — это то, что описывает O-нотация.

### 📐 Что такое O-нотация

O-нотация (читается «О-большое») описывает **верхнюю границу** скорости роста времени работы алгоритма при стремлении размера входных данных к бесконечности.

Когда мы говорим «алгоритм работает за O(n)», мы имеем в виду:

> Существует константа c > 0 и число n₀ такие, что для всех n ≥ n₀ время работы алгоритма T(n) ≤ c · n.

Проще: **при достаточно больших n время работы растёт не быстрее, чем n, умноженное на некоторую константу**.

Важные следствия:

1. **Мы отбрасываем константы.** O(2n) = O(n) = O(100n). Константа не влияет на **скорость роста** — она влияет только на абсолютное время.

2. **Мы отбрасываем младшие члены.** O(n² + n) = O(n²). При больших n член n² доминирует настолько, что n становится несущественным.

3. **Мы смотрим только на асимптотику.** O-нотация говорит о поведении при n → ∞, а не о конкретных значениях времени.

### 🔍 Аналогия: скорость роста как тип роста

Представь, что ты сравниваешь скорость роста двух растений. Первое растёт на 1 сантиметр в день. Второе — на 10 сантиметров в день. Второе растёт быстрее, но **тип роста** у обоих одинаковый — линейный.

Теперь представь третье растение, которое растёт так: каждый день его высота удваивается. В первый день — 1 см, во второй — 2 см, в третий — 4 см, в четвёртый — 8 см. Через 30 дней его высота превысит расстояние от Земли до Луны.

O-нотация описывает **тип скорости роста**, а не конкретную скорость:

- Линейный рост — O(n)
- Квадратичный рост — O(n²)
- Логарифмический рост — O(log n)
- Экспоненциальный рост — O(2ⁿ)

И эти типы роста отличаются **качественно**, а не количественно. O(n²) — это не «в два раза хуже O(n)», а «катастрофически хуже при больших n».

### 📊 Таблица роста: что значит каждая сложность

| Сложность | Название | n=10 | n=100 | n=1000 | n=1000000 |
|:---|:---|:---|:---|:---|:---|
| O(1) | Константная | 1 | 1 | 1 | 1 |
| O(log n) | Логарифмическая | 3 | 7 | 10 | 20 |
| O(n) | Линейная | 10 | 100 | 1000 | 1 000 000 |
| O(n log n) | Линейно-логарифмическая | 30 | 700 | 10 000 | 20 000 000 |
| O(n²) | Квадратичная | 100 | 10 000 | 1 000 000 | 10¹² |
| O(2ⁿ) | Экспоненциальная | 1024 | 10³⁰ | 10³⁰⁰ | невообразимо |

Смотри на последние две строки. O(n²) на миллионе элементов — это 10¹² операций. Если одна операция занимает 1 наносекунду, это 1000 секунд — почти 17 минут. А O(n log n) на том же миллионе — 20 миллионов операций — это 20 миллисекунд.

Вот почему выбор алгоритма с правильной сложностью — это не «оптимизация», а **вопрос выживания** при больших данных.

### 🧮 Как определить сложность: базовые правила

**Правило 1: Одиночный цикл — O(n)**

```go
for i := 0; i < n; i++ {
    // O(1) операций внутри
}
// Сложность: O(n)
```

**Правило 2: Два последовательных цикла — O(n), не O(2n)**

```go
for i := 0; i < n; i++ {
    // ...
}
for i := 0; i < n; i++ {
    // ...
}
// Сложность: O(n) + O(n) = O(2n) = O(n)
```

**Правило 3: Вложенные циклы — перемножаются**

```go
for i := 0; i < n; i++ {
    for j := 0; j < n; j++ {
        // O(1) операций внутри
    }
}
// Сложность: O(n × n) = O(n²)
```

**Правило 4: Цикл с делением пополам — O(log n)**

```go
for i := 1; i < n; i *= 2 {
    // O(1) операций внутри
}
// Сложность: O(log n)
```

Почему log n? Потому что i принимает значения 1, 2, 4, 8, 16, ... — каждую итерацию удваивается. Сколько раз можно удвоить число, пока не достигнешь n? Это log₂(n) раз.

**Правило 5: Если на каждой итерации выполняется функция — учитывай её сложность**

```go
for i := 0; i < n; i++ {
    binarySearch(arr, target) // O(log n)
}
// Сложность: O(n × log n) = O(n log n)
```

### 💡 Что мы узнали?

- O-нотация описывает **скорость роста** времени работы алгоритма при увеличении размера входных данных.
- Мы отбрасываем константы и младшие члены — они не влияют на асимптотику.
- O(2n) = O(n), а O(n² + n) = O(n²).
- Вложенные циклы перемножаются, последовательные — складываются.
- Цикл с удвоением счётчика — O(log n).

## 1.2 Анализ циклов: от O(1) до O(n²)

### 🔌 Проблема: как понять сложность реального кода?

В 1.1 мы разобрали базовые правила. Но реальный код редко выглядит как «одиночный цикл» или «два вложенных цикла». В реальном коде есть условия, вызовы функций, изменение счётчика на переменную величину, ранние выходы из цикла.

В этой подглаве мы разберём **типичные паттерны** и научимся определять их сложность.

### 📊 Паттерн 1: Одиночный цикл с O(1) внутри — O(n)

```go
func sum(arr []int) int {
    total := 0
    for _, x := range arr {
        total += x
    }
    return total
}
```

Анализ: цикл выполняется n раз, внутри — константная операция (сложение). Сложность: **O(n)**.

### 📊 Паттерн 2: Два последовательных цикла — O(n)

```go
func process(arr []int) {
    for i := 0; i < len(arr); i++ {
        fmt.Println(arr[i])
    }
    for i := 0; i < len(arr); i++ {
        arr[i] *= 2
    }
}
```

Анализ: первый цикл — O(n), второй — O(n). Суммарно: O(n) + O(n) = O(2n) = **O(n)**.

**Важно:** два последовательных цикла — это не O(n²). O(n²) будет только если циклы **вложенные**.

### 📊 Паттерн 3: Вложенные циклы — O(n²)

```go
func printPairs(arr []int) {
    for i := 0; i < len(arr); i++ {
        for j := 0; j < len(arr); j++ {
            fmt.Println(arr[i], arr[j])
        }
    }
}
```

Анализ: внешний цикл — n итераций. Для каждой итерации внешнего цикла внутренний — n итераций. Итого: n × n = n² операций. Сложность: **O(n²)**.

### 📊 Паттерн 4: Вложенные циклы с уменьшающимся внутренним — тоже O(n²)

```go
func printPairs(arr []int) {
    for i := 0; i < len(arr); i++ {
        for j := i + 1; j < len(arr); j++ {
            fmt.Println(arr[i], arr[j])
        }
    }
}
```

Анализ: внутренний цикл выполняется не n раз, а (n - i - 1) раз. Суммарно:

```
(n-1) + (n-2) + ... + 1 + 0 = n(n-1)/2 = n²/2 - n/2
```

Отбрасываем константу 1/2 и младший член n/2: **O(n²)**.

**Важно:** то, что внутренний цикл «уменьшается», не меняет асимптотику. Это всё ещё O(n²), просто с меньшей константой.

### 📊 Паттерн 5: Цикл с удвоением — O(log n)

```go
func printPowers(n int) {
    for i := 1; i < n; i *= 2 {
        fmt.Println(i)
    }
}
```

Анализ: i принимает значения 1, 2, 4, 8, 16, ... Сколько раз можно удвоить 1, пока не достигнешь n?

```
2^k ≥ n
k ≥ log₂(n)
```

Сложность: **O(log n)**.

**Почему log n — это хорошо:** log₂(1 000 000) ≈ 20. Алгоритм с O(log n) на миллионе элементов делает всего 20 итераций.

### 📊 Паттерн 6: Цикл с делением — O(log n)

```go
func countdown(n int) {
    for n > 1 {
        n = n / 2
    }
}
```

Анализ: n уменьшается вдвое каждую итерацию. Количество итераций — log₂(n). Сложность: **O(log n)**.

### 📊 Паттерн 7: Цикл внутри цикла с логарифмом — O(n log n)

```go
func process(arr []int) {
    for i := 0; i < len(arr); i++ {
        // Внутренний цикл с удвоением
        for j := 1; j < len(arr); j *= 2 {
            // O(1)
        }
    }
}
```

Анализ: внешний цикл — n итераций. Внутренний — log n. Итого: n × log n. Сложность: **O(n log n)**.

Это сложность эффективных сортировок (merge sort, быстрая сортировка в среднем).

### 📊 Паттерн 8: Ранний выход из цикла — всё равно O(n)

```go
func find(arr []int, target int) int {
    for i := 0; i < len(arr); i++ {
        if arr[i] == target {
            return i // ранний выход
        }
    }
    return -1
}
```

Анализ: в лучшем случае target на первой позиции — O(1). В худшем — target последний или отсутствует — O(n). В среднем — O(n/2) = O(n).

O-нотация обычно описывает **худший случай**. Поэтому сложность этого алгоритма — **O(n)**.

### 🧮 Практика: определяем сложность

Разберём несколько примеров и определим их сложность.

**Пример 1:**

```go
func foo(n int) {
    for i := 0; i < n; i++ {
        for j := 0; j < 100; j++ {
            fmt.Println(i, j)
        }
    }
}
```

Внутренний цикл — 100 итераций, константа. Внешний — n итераций. Сложность: O(n × 100) = **O(n)**.

**Пример 2:**

```go
func bar(n int) {
    for i := 0; i < n; i++ {
        for j := 0; j < i; j++ {
            fmt.Println(i, j)
        }
    }
}
```

Внутренний цикл: 0 + 1 + 2 + ... + (n-1) = n(n-1)/2. Сложность: **O(n²)**.

**Пример 3:**

```go
func baz(n int) {
    for i := n; i > 0; i /= 3 {
        fmt.Println(i)
    }
}
```

i: n, n/3, n/9, n/27, ... Сколько раз делить на 3, пока не достигнем 1?

```
n / 3^k ≤ 1
3^k ≥ n
k ≥ log₃(n)
```

Сложность: O(log₃ n) = **O(log n)** (основание логарифма — константа, отбрасываем).

**Пример 4:**

```go
func qux(n int) {
    for i := 0; i < n; i++ {
        for j := 1; j < n; j *= 2 {
            for k := 0; k < n; k++ {
                fmt.Println(i, j, k)
            }
        }
    }
}
```

Внешний цикл: n. Средний: log n. Внутренний: n. Итого: n × log n × n = **O(n² log n)**.

### 💡 Что мы узнали?

- Последовательные циклы складываются: O(n) + O(n) = O(n).
- Вложенные циклы перемножаются: O(n) × O(n) = O(n²).
- Цикл с удвоением или делением — O(log n).
- Уменьшающийся внутренний цикл (j = i + 1) — всё ещё O(n²).
- Ранний выход не меняет худший случай — O(n).
- O-нотация описывает худший случай, если не оговорено иное.

## 1.3 Амортизированный анализ: когда O(n) — это на самом деле O(1)

### 🔌 Проблема: добавление в динамический массив — O(1) или O(n)?

До сих пор мы оценивали сложность циклов — последовательных и вложенных. Но есть операции, сложность которых не очевидна. Например, добавление элемента в динамический массив.

В Go динамический массив — это slice. Когда ты делаешь `append(s, x)`, возможны два сценария:

1. **Ёмкости хватает:** элемент записывается в существующий блок памяти. Сложность: O(1).
2. **Ёмкости не хватает:** выделяется новый блок (обычно в 2 раза больше), все элементы копируются, старый блок освобождается. Сложность: O(n).

Так `append` — это O(1) или O(n)?

**Ответ: амортизированно O(1).** И вот почему.

### 📐 Что такое амортизированный анализ

**Амортизированный анализ** — это способ оценки сложности, при котором мы смотрим не на одну операцию, а на **последовательность** операций, и вычисляем **среднюю стоимость** одной операции в этой последовательности.

Идея: некоторые операции могут быть дорогими (O(n)), но они происходят **редко**. Если распределить стоимость дорогих операций на все дешёвые, получится, что в среднем каждая операция стоит O(1).

Это как платить за квартиру: каждый месяц ты платишь аренду (дешёвая операция), но раз в год платишь страховку (дорогая операция). Если распределить страховку на 12 месяцев, получится, что каждый месяц ты платишь чуть больше аренды — но не в 12 раз больше.

### 🔬 Как работает расширение слайса в Go

Когда ты создаёшь слайс с ёмкостью 1 и начинаешь добавлять элементы:

```go
s := make([]int, 0, 1) // длина 0, ёмкость 1

s = append(s, 1)  // Ёмкости хватает → O(1)
s = append(s, 2)  // Ёмкости НЕ хватает → выделяем массив размером 2, копируем 1 элемент → O(1)
s = append(s, 3)  // Ёмкости НЕ хватает → выделяем массив размером 4, копируем 2 элемента → O(2)
s = append(s, 4)  // Ёмкости хватает → O(1)
s = append(s, 5)  // Ёмкости НЕ хватает → выделяем массив размером 8, копируем 4 элемента → O(4)
// ... и так далее
```

Закономерность: когда ёмкость исчерпана, новый массив выделяется **в 2 раза больше**, и копируются все текущие элементы.

### 🧮 Считаем суммарную стоимость

Допустим, мы сделали n операций `append`, начиная с ёмкости 1.

**Сколько раз произошло расширение?** Расширения происходят при ёмкостях 1, 2, 4, 8, 16, ..., 2^k. То есть **log₂(n)** раз.

**Сколько элементов скопировано суммарно?** При последнем расширении скопировано n/2 элементов (примерно), при предпоследнем — n/4, при пред-предпоследнем — n/8, и так далее:

```
Суммарно скопировано = n/2 + n/4 + n/8 + ... + 1 = n - 1
```

Это геометрическая прогрессия с суммой n - 1.

**Итого:** за n операций append мы сделали:
- n записей элементов (каждая O(1)) → суммарно O(n)
- n - 1 копирований при расширениях → суммарно O(n)

**Суммарная стоимость n операций:** O(n) + O(n) = O(n).

**Средняя стоимость одной операции:** O(n) / n = **O(1)**.

Это и есть **амортизированная сложность**: в среднем одна операция append стоит O(1), хотя иногда (при расширении) она стоит O(n).

### 📊 Почему расширение именно в 2 раза?

Если бы слайс расширялся не в 2 раза, а на **фиксированное** количество элементов (например, +10), амортизированная сложность была бы другой.

**Расширение на +10 элементов:**

При добавлении n элементов произойдёт n/10 расширений. При каждом расширении копируется в среднем n/2 элементов. Суммарно скопировано:

```
(n/10) × (n/2) = n²/20
```

Средняя стоимость одной операции: n²/20 / n = n/20 = **O(n)**.

Это катастрофа: добавление в конец становится O(n) в среднем.

**Расширение в k раз (k > 1):**

Суммарно скопировано: n/(k-1) элементов (геометрическая прогрессия).

Средняя стоимость: O(n) / n = **O(1)**.

**Вывод:** расширение в k раз (k > 1) даёт амортизированную O(1). Расширение на фиксированное число — O(n). Вот почему все динамические массивы (slice в Go, list в Python, ArrayList в Java) расширяются умножением, а не сложением.

### 🔬 Амортизированный анализ методом потенциала

Есть и другой способ думать об амортизированной сложности — **метод потенциала**.

Представь, что у каждой структуры данных есть «банковский счёт». Когда ты делаешь дешёвую операцию, ты **кладёшь монетку** на счёт. Когда приходит время дорогой операции, ты **снимаешь монетки** со счёта, чтобы оплатить её.

**Для слайса с расширением в 2 раза:**

- Каждый `append`, который не вызывает расширение, стоит 1 (фактическая работа) + 1 (монетка на счёт). Итого: 2 монетки.
- Каждый `append`, который вызывает расширение, стоит 1 (фактическая работа) + n (копирование) - n (снимаем монетки со счёта). Итого: 1 монетка.

Средняя стоимость: около 2 монеток на операцию = O(1).

**Метод потенциала** — мощный инструмент. Мы будем использовать его в Главе про кучи (Фибоначчиева куча) и в других местах, где амортизированный анализ не так очевиден.

### 🔍 Как это применить на практике

Когда ты решаешь задачу и думаешь о сложности:

1. **Если структура расширяется умножением** — добавление в конец амортизированно O(1).
2. **Если структура расширяется сложением** — добавление в конец O(n).
3. **Если в задаче нужно часто добавлять элементы** — используй структуру с амортизированной O(1).
4. **Если нужны гарантии на каждую операцию** (реальное время, а не в среднем) — амортизированная O(1) может не подойти.

Пример, где амортизированная O(1) **не подходит**: системы реального времени (управление двигателем, тормозами). Там недопустимо, чтобы одна операция из миллиона заняла O(n) — это может привести к катастрофе. Для таких систем нужны структуры с гарантированной O(1) на каждую операцию.

### 💡 Что мы узнали?

- Амортизированный анализ смотрит на **последовательность** операций и вычисляет **среднюю стоимость**.
- Динамический массив с расширением в k раз (k > 1) имеет амортизированную O(1) на добавление.
- При расширении в 2 раза суммарное копирование — O(n) за n операций → O(1) в среднем.
- Расширение на фиксированное число элементов даёт O(n) в среднем — это плохо.
- Метод потенциала — способ думать о «накоплении» дешёвых операций для оплаты дорогих.

## 1.4 Рекуррентные соотношения и мастер-теорема

### 🔌 Проблема: как оценить сложность рекурсивного алгоритма?

Мы разобрали циклы. Но многие алгоритмы — рекурсивные: merge sort, бинарный поиск, обход дерева. Как оценить их сложность?

Рекурсивный алгоритм вызывает сам себя на **меньших** подзадачах. Чтобы оценить его сложность, нужно:

1. Понять, на сколько частей разбивается задача.
2. Понять, какого размера каждая часть.
3. Понять, сколько стоит объединение результатов.

Это описывается **рекуррентным соотношением** — уравнением, которое выражает сложность через сложность подзадач.

### 📐 Рекуррентное соотношение: определение

**Рекуррентное соотношение** — это уравнение, которое определяет значение функции через её значения на меньших аргументах.

Общий вид:

```
T(n) = a · T(n/b) + f(n)
```

Где:

- **a** — количество подзадач.
- **n/b** — размер каждой подзадачи.
- **f(n)** — стоимость разбиения и объединения результатов.

Примеры:

**Бинарный поиск:** T(n) = T(n/2) + O(1)

- Разбиваем на 1 подзадачу (a=1).
- Размер подзадачи — n/2 (b=2).
- Стоимость объединения — O(1).

**Merge sort:** T(n) = 2T(n/2) + O(n)

- Разбиваем на 2 подзадачи (a=2).
- Размер каждой — n/2 (b=2).
- Стоимость объединения (слияние) — O(n).

### 🧮 Как решать рекуррентные соотношения

Есть три способа:

1. **Метод подстановки** — угадать решение и доказать по индукции.
2. **Дерево рекурсии** — нарисовать дерево вызовов и посчитать суммарную стоимость.
3. **Мастер-теорема** — применить готовую формулу.

Разберём каждый.

### 📊 Дерево рекурсии

**Дерево рекурсии** — это визуализация всех вызовов рекурсивной функции.

**Пример: merge sort, T(n) = 2T(n/2) + O(n)**

```
Уровень 0:              T(n)                        ← стоимость O(n)
                       /    \
Уровень 1:          T(n/2)   T(n/2)                 ← стоимость O(n/2) + O(n/2) = O(n)
                    /  \      /  \
Уровень 2:      T(n/4) T(n/4) T(n/4) T(n/4)         ← стоимость 4 × O(n/4) = O(n)
                ...                                  ...

Уровень log n:    T(1) T(1) ... T(1)                ← стоимость n × O(1) = O(n)
```

**Анализ:**

- Глубина дерева: log₂(n) уровней (каждый уровень уменьшает размер вдвое).
- Стоимость каждого уровня: O(n).
- Суммарная стоимость: O(n) × log₂(n) = **O(n log n)**.

**Пример: бинарный поиск, T(n) = T(n/2) + O(1)**

```
Уровень 0:              T(n)                        ← стоимость O(1)
                        |
Уровень 1:            T(n/2)                        ← стоимость O(1)
                        |
Уровень 2:          T(n/4)                          ← стоимость O(1)
                        |
                       ...
                        |
Уровень log n:        T(1)                          ← стоимость O(1)
```

**Анализ:**

- Глубина дерева: log₂(n) уровней.
- Стоимость каждого уровня: O(1).
- Суммарная стоимость: O(1) × log₂(n) = **O(log n)**.

### 🧮 Мастер-теорема

**Мастер-теорема** — это готовая формула для рекуррентных соотношений вида:

```
T(n) = a · T(n/b) + f(n)
```

Сравниваем f(n) с n^(log_b a):

**Случай 1:** Если f(n) = O(n^(log_b a - ε)) для некоторого ε > 0, то:

```
T(n) = Θ(n^(log_b a))
```

Интуиция: стоимость объединения **меньше**, чем стоимость подзадач. Подзадачи доминируют.

**Случай 2:** Если f(n) = Θ(n^(log_b a)), то:

```
T(n) = Θ(n^(log_b a) · log n)
```

Интуиция: стоимость объединения **сравнима** со стоимостью подзадач. Вклад обоих одинаков.

**Случай 3:** Если f(n) = Ω(n^(log_b a + ε)) для некоторого ε > 0, и a · f(n/b) ≤ c · f(n) для некоторого c < 1, то:

```
T(n) = Θ(f(n))
```

Интуиция: стоимость объединения **больше**, чем стоимость подзадач. Объединение доминирует.

### 📊 Применяем мастер-теорему

**Пример 1: T(n) = 2T(n/2) + O(n)**

- a = 2, b = 2, f(n) = n
- log_b a = log₂ 2 = 1
- n^(log_b a) = n¹ = n
- f(n) = n = Θ(n) → **Случай 2**

Ответ: **T(n) = Θ(n log n)**.

**Пример 2: T(n) = T(n/2) + O(1)**

- a = 1, b = 2, f(n) = 1
- log_b a = log₂ 1 = 0
- n^(log_b a) = n⁰ = 1
- f(n) = 1 = Θ(1) → **Случай 2**

Ответ: **T(n) = Θ(log n)**.

**Пример 3: T(n) = 2T(n/2) + O(n²)**

- a = 2, b = 2, f(n) = n²
- log_b a = log₂ 2 = 1
- n^(log_b a) = n¹ = n
- f(n) = n² = Ω(n^(1 + 1)) → **Случай 3**

Ответ: **T(n) = Θ(n²)**.

### 💡 Что мы узнали?

- Рекуррентное соотношение: T(n) = aT(n/b) + f(n).
- Дерево рекурсии — визуальный способ посчитать суммарную стоимость.
- Мастер-теорема — готовая формула для рекуррентных соотношений.
- Merge sort: T(n) = 2T(n/2) + O(n) → O(n log n).
- Бинарный поиск: T(n) = T(n/2) + O(1) → O(log n).

## 1.5 Константы, кэш и реальная производительность

### 🔌 Проблема: O(n log n) быстрее, чем O(n)?

Ты знаешь, что O(n) лучше O(n log n). Но вот реальный случай: алгоритм с O(n log n) работает **быстрее**, чем алгоритм с O(n) на данных размером до миллиона элементов. Как такое возможно?

Ответ: **константы и кэш-локальность**.

O-нотация отбрасывает константы. Но на реальном железе константы могут отличаться в сотни и тысячи раз. Алгоритм с O(n log n) и константой 1 может быть быстрее алгоритма с O(n) и константой 1000 на всех данных, которые помещаются в память.

### 📐 Константы: что отбрасывает O-нотация

Когда мы говорим «этот алгоритм — O(n)», мы имеем в виду:

```
T(n) ≤ c · n для n ≥ n₀
```

Константа **c** может быть любой. У одного алгоритма с O(n) константа может быть 1 наносекунда на элемент. У другого — 1 миллисекунда на элемент. Оба — O(n), но второй в миллион раз медленнее.

**Откуда берутся большие константы:**

- Дорогие операции внутри цикла (деление, модуль, плавающая точка).
- Частые вызовы функций.
- Промахи кэша.
- Блокировки.
- Сетевые запросы.

**Пример:** хеш-таблица с плохой хеш-функцией. Сложность в среднем — O(1), но константа может быть настолько большой (из-за коллизий), что бинарный поиск по отсортированному массиву (O(log n)) будет быстрее.

### 🔬 Кэш-локальность: почему массивы быстрее списков

В Главе 2 мы детально разберём связные списки. Но уже сейчас важно понять: **физическое расположение данных в памяти влияет на скорость**.

**Массив:** элементы лежат в непрерывном блоке памяти. Когда ты обращаешься к `arr[100]`, процессор загружает в кэш **соседние** элементы — `arr[101]`, `arr[102]`, `arr[103]`. Следующее обращение к `arr[101]` будет из кэша, а не из RAM. Кэш быстрее RAM в 100 раз.

**Связный список:** элементы разбросаны по памяти. Когда ты переходишь от узла к узлу, каждый раз обращение к новой области памяти. Кэш не помогает — каждый переход это промах кэша.

**Результат:** обход массива может быть в 10–100 раз быстрее обхода связного списка того же размера, хотя оба — O(n).

### 📊 Когда асимптотика важнее констант

Константы важны при **малых** n. Асимптотика — при **больших**.

Представь два алгоритма:

- Алгоритм A: T(n) = 100n (O(n))
- Алгоритм B: T(n) = n² (O(n²))

| n | A (100n) | B (n²) | Кто быстрее |
|:---|:---|:---|:---|
| 10 | 1 000 | 100 | B быстрее |
| 100 | 10 000 | 10 000 | Одинаково |
| 1000 | 100 000 | 1 000 000 | A быстрее |
| 10 000 | 1 000 000 | 100 000 000 | A быстрее |

При n = 100 алгоритмы одинаковы. При n > 100 алгоритм A быстрее. При n = 10 000 алгоритм A быстрее в 100 раз.

**Мораль:** если ты знаешь, что n всегда будет маленьким (меньше 100), не обязательно гнаться за лучшей асимптотикой. Но если n может вырасти до миллионов — асимптотика решает всё.

### 🔬 Практический пример: сортировка вставками vs merge sort

**Сортировка вставками:** O(n²). Константа очень маленькая — просто сдвигаем элементы.

**Merge sort:** O(n log n). Константа больше — нужно выделять память, копировать, сливать.

На массиве из 10 элементов сортировка вставками быстрее — O(100) с маленькой константой против O(10 log 10) с большой константой.

На массиве из 1 000 000 элементов сортировка вставками делает 10¹² операций (часы), а merge sort — 20 миллионов (миллисекунды).

**Стандартные библиотеки используют гибридные сортировки:** быстрая сортировка (O(n log n)) для больших подмассивов, сортировка вставками (O(n²) с маленькой константой) для маленьких. В Go `sort.Slice` использует **pdqsort** — гибрид из quicksort, heapsort и insertion sort.

### 💡 Что мы узнали?

- O-нотация отбрасывает константы, но константы могут отличаться в миллионы раз.
- Кэш-локальность может сделать O(n) алгоритм на массиве быстрее O(n) алгоритма на списке.
- Асимптотика важнее при больших n, константы — при малых.
- Гибридные алгоритмы сочетают лучшее из обоих миров.

## 1.6 Типичные ошибки при оценке сложности

### 🔌 Проблема: сложность оценили, а алгоритм всё равно медленный

Ты оценил сложность алгоритма как O(n). Запустил — медленно. Почему?

Возможно, ты допустил одну из типичных ошибок. Разберём самые частые.

### ❌ Ошибка 1: Забыл про скрытый цикл

Многие операции, которые выглядят как O(1), на самом деле внутри содержат цикл.

**Пример:** в Python `list.remove(x)` удаляет первое вхождение x. Чтобы найти x, нужно пройтись по списку — это O(n). Затем сдвинуть элементы — ещё O(n). Итого: O(n), а не O(1).

**Пример:** в Go `s = append(s[:i], s[i+1:]...)` удаляет элемент из слайса. Копирование хвоста — O(n). Не O(1).

**Как избежать:** знай сложность операций стандартной библиотеки. Мы разберём их для каждой структуры данных в следующих главах.

### ❌ Ошибка 2: Путаешь O(n) и O(n²)

**Пример:** два последовательных цикла — это O(n), а не O(n²).

```go
for i := 0; i < n; i++ { /* O(1) */ }
for i := 0; i < n; i++ { /* O(1) */ }
// O(n), не O(n²)
```

**Пример:** вложенный цикл, где внутренний цикл — константа, это O(n), а не O(n²).

```go
for i := 0; i < n; i++ {
    for j := 0; j < 100; j++ { /* O(1) */ }
}
// O(100n) = O(n), не O(n²)
```

### ❌ Ошибка 3: Забываешь про сложность операций со строками

**Пример:** конкатенация строк в цикле.

```go
s := ""
for i := 0; i < n; i++ {
    s += "x" // Создаётся новая строка, старая копируется
}
// O(n²), а не O(n)
```

Каждая конкатенация копирует всю строку. Суммарно: 1 + 2 + 3 + ... + n = O(n²).

**Как избежать:** используй `strings.Builder` в Go или `StringBuilder` в Java — они амортизируют стоимость.

### ❌ Ошибка 4: Не учитываешь рекурсию

**Пример:** рекурсивное вычисление чисел Фибоначчи.

```go
func fib(n int) int {
    if n <= 1 {
        return n
    }
    return fib(n-1) + fib(n-2)
}
// O(2ⁿ), а не O(n)
```

Каждый вызов порождает два новых. Дерево вызовов имеет 2ⁿ узлов.

**Как избежать:** используй мемоизацию (динамическое программирование) или итеративный подход. Разберём в Главе про DP.

### ❌ Ошибка 5: Смотришь на лучший случай вместо худшего

**Пример:** поиск элемента в неотсортированном массиве.

Лучший случай: элемент первый — O(1).
Худший случай: элемент последний — O(n).

O-нотация описывает **худший случай** (если не оговорено иное). Поэтому сложность — O(n), а не O(1).

### ❌ Ошибка 6: Игнорируешь амортизацию

**Пример:** добавление в динамический массив.

Единичная операция может быть O(n) при расширении. Но **амортизированно** это O(1). Если ты оцениваешь сложность как O(n) для каждой операции, ты переоцениваешь алгоритм в n раз.

### 💡 Что мы узнали?

- Скрытые циклы в операциях стандартной библиотеки меняют сложность.
- Последовательные циклы — это O(n), не O(n²).
- Конкатенация строк в цикле — O(n²).
- Рекурсивные алгоритмы могут быть экспоненциальными.
- O-нотация описывает худший случай.
- Амортизация делает дорогие операции дешёвыми в среднем.

## 1.7 Итог: что мы узнали о сложности

Мы начали с пролога: алгоритм работал быстро на 1000 элементах, но упал на 10 миллионах. Мы узнали, что причина — **скорость роста** времени работы при увеличении размера входных данных.

Теперь у нас есть полный инструментарий для оценки сложности:

1. **O-нотация** — язык описания скорости роста. O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ).
2. **Анализ циклов** — последовательные складываются, вложенные перемножаются.
3. **Амортизированный анализ** — средняя стоимость по последовательности операций.
4. **Рекуррентные соотношения** — T(n) = aT(n/b) + f(n), мастер-теорема.
5. **Константы и кэш** — почему асимптотика не всегда решает.
6. **Типичные ошибки** — скрытые циклы, конкатенация строк, рекурсия без мемоизации.

Это фундамент, на котором стоит всё остальное. В следующих главах мы будем применять эти инструменты к конкретным структурам данных и алгоритмам.

## Глоссарий

| Термин | Определение |
|:---|:---|
| **Сложность алгоритма** | Зависимость времени работы (или памяти) от размера входных данных |
| **O-нотация** | Верхняя граница скорости роста. T(n) ≤ c · g(n) для n ≥ n₀ |
| **Асимптотика** | Поведение функции при n → ∞ |
| **Амортизированный анализ** | Средняя стоимость операции по последовательности операций |
| **Рекуррентное соотношение** | Уравнение, выражающее сложность через сложность подзадач |
| **Мастер-теорема** | Формула для решения рекуррентных соотношений вида T(n) = aT(n/b) + f(n) |
| **Кэш-локальность** | Свойство доступа к соседним ячейкам памяти — быстрее из-за кэша процессора |
| **Худший случай** | Максимальное время работы при наихудших входных данных |
| **Амортизированная O(1)** | В среднем O(1) на операцию, хотя отдельные операции могут быть O(n) |
| **Логарифмическая сложность** | O(log n) — количество операций растёт как логарифм от n |

---

## Что мы узнали?

- O-нотация описывает **скорость роста**, а не конкретное время работы.
- Константы отбрасываются: O(2n) = O(n), O(n² + n) = O(n²).
- Вложенные циклы перемножаются, последовательные — складываются.
- Динамический массив с расширением в 2 раза даёт амортизированную O(1) на добавление.
- Рекурсивные алгоритмы оцениваются через рекуррентные соотношения и мастер-теорему.
- Кэш-локальность может сделать O(n) на массиве быстрее O(n) на списке.
- Асимптотика важнее при больших n, константы — при малых.

---

## Типичные ошибки

- ❌ **Считать два последовательных цикла O(n²).** Они складываются: O(n) + O(n) = O(n).
- ❌ **Забывать про скрытые циклы в операциях стандартной библиотеки.** `list.remove()` в Python — O(n).
- ❌ **Конкатенировать строки в цикле.** Каждая конкатенация копирует строку — O(n²) суммарно.
- ❌ **Оценивать рекурсивный алгоритм как линейный.** Фибоначчи через рекурсию — O(2ⁿ).
- ❌ **Смотреть на лучший случай вместо худшего.** Поиск в массиве — O(n), не O(1).
- ❌ **Игнорировать амортизацию.** Добавление в слайс — амортизированно O(1), не O(n).

---

## Для быстрого повторения

- **Сложности по возрастанию:** O(1) → O(log n) → O(n) → O(n log n) → O(n²) → O(2ⁿ).
- **Последовательные циклы:** O(n) + O(n) = O(n).
- **Вложенные циклы:** O(n) × O(n) = O(n²).
- **Цикл с удвоением:** O(log n).
- **Расширение в 2 раза:** амортизированная O(1).
- **Merge sort:** T(n) = 2T(n/2) + O(n) → O(n log n).
- **Бинарный поиск:** T(n) = T(n/2) + O(1) → O(log n).
- **Кэш-локальность:** массивы быстрее списков на практике.

10. Ты написал алгоритм с O(n log n). Коллега написал с O(n²). При каком n твой алгоритм гарантированно быстрее? Можно ли это сказать без констант?

---

## Ответы

**1.** O-нотация описывает **верхнюю границу скорости роста** времени работы при n → ∞. O(2n) = O(n), потому что константа 2 не влияет на **скорость роста** — оба растут линейно. O-нотация отбрасывает константы и младшие члены.

**2.** Два последовательных цикла: O(n) + O(n) = O(2n) = **O(n)**. Два вложенных: O(n) × O(n) = **O(n²)**.

**3.** При расширении в 2 раза суммарное копирование за n операций: n/2 + n/4 + ... + 1 = n - 1 = O(n). Средняя стоимость: O(n)/n = O(1). Если расширяться на фиксированное число k, произойдёт n/k расширений, каждое копирует в среднем n/2 элементов: (n/k) × (n/2) = n²/(2k) = O(n²). Средняя стоимость: O(n²)/n = O(n).

**4.** T(n) = 2T(n/4) + O(√n).

- a = 2, b = 4, f(n) = √n = n^0.5
- log_b a = log₄ 2 = 0.5
- n^(log_b a) = n^0.5 = √n
- f(n) = √n = Θ(√n) → Случай 2

Ответ: **T(n) = Θ(√n · log n)**.

**5.** Из-за кэш-локальности. Элементы массива лежат в непрерывном блоке — при обращении к одному элементу процессор загружает в кэш соседние. Следующее обращение — из кэша (быстро). Элементы списка разбросаны по памяти — каждое обращение это промах кэша (медленно). Разница может быть в 10–100 раз.

**6.** Конкатенация строк в цикле — O(n²). Каждая `s += "x"` создаёт новую строку и копирует всю старую. Суммарно: 1 + 2 + ... + n = O(n²). Исправить: использовать `strings.Builder` (Go) или `StringBuilder` (Java) — амортизированная O(1) на добавление.

**7.** Рекурсивный Фибоначчи — O(2ⁿ). Каждый вызов порождает два новых, дерево вызовов имеет 2ⁿ узлов. Улучшить: мемоизация (запоминание вычисленных значений) — O(n), или итеративный подход — O(n) по времени и O(1) по памяти.

**8.** Метод потенциала: каждая дешёвая операция «кладёт монетку» на счёт, дорогая — «снимает». Для динамического массива: каждый append без расширения стоит 2 (1 работа + 1 монетка). Append с расширением стоит 1 + n - n = 1 (1 работа + n копирование - n монеток со счёта). Средняя стоимость: около 2 = O(1).

**9.** Константы важнее при малых n. Сортировка вставками (O(n²) с маленькой константой) быстрее merge sort (O(n log n) с большой константой) на массивах до ~10 элементов. Стандартные библиотеки используют гибридные сортировки.

**10.** Нельзя сказать без констант. Алгоритм с O(n log n) быстрее алгоритма с O(n²) **асимптотически**, но при каком именно n — зависит от констант. Если константа у O(n²) алгоритма в 1000 раз меньше, он может быть быстрее до n = 1000 и более. Нужно измерять на реальных данных.
