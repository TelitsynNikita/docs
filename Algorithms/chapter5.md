## 5.0 Пролог: сортировка, которая замедлила сервис в десять раз

Ты пишешь сервис аналитики. Пользователь загружает CSV с транзакциями, а ты показываешь топ-10 крупнейших по сумме. Данных немного — обычно несколько тысяч строк. Ты пишешь простое решение:

```go
func top10(transactions []Transaction) []Transaction {
    // Сортируем по сумме (убывание)
    sort.Slice(transactions, func(i, j int) bool {
        return transactions[i].Amount > transactions[j].Amount
    })
    // Берём первые 10
    return transactions[:10]
}
```

Тестируешь на 1000 транзакций — работает мгновенно. Деплоишь. Через месяц один клиент загружает CSV на 10 миллионов транзакций. Запрос занимает **40 секунд** и вешает весь сервис. Остальные клиенты получают таймауты.

Что произошло? Сортировка 10 миллионов элементов занимает секунды, а тебе нужны только **10 элементов**. Ты сортируешь весь массив ради десяти. Это как сортировать всю библиотеку, чтобы найти десять самых толстых книг.

Проблема не в сортировке как таковой — она работает корректно. Проблема в **выборе алгоритма под задачу**.

В этой главе мы не будем заучивать сортировки. Мы будем **выводить** их — каждую из конкретной проблемы. Ты увидишь, что каждая сортировка — это ответ на вопрос «а что если сделать вот так?», а не заклинание из учебника.

Начнём с вопроса: что вообще значит «отсортировать»?

## 5.1 Что такое сортировка и зачем она нужна

### 🔌 Проблема: зачем сортировать данные?

Дан массив чисел. Ты хочешь найти в нём максимальный элемент. Что ты делаешь? Проходишь по всему массиву, сравнивая с текущим максимумом. O(n). Просто.

Теперь ты хочешь найти **медиану**. Или **топ-10**. Или **уникальные элементы**. Или **найти элемент за O(log n)** (бинарный поиск). Все эти задачи **требуют отсортированных данных**.

Сортировка — это не самоцель. Это **подготовка данных**, которая открывает другие алгоритмы:

1. **Бинарный поиск** (Глава 7) работает только на отсортированных данных. Найти элемент за O(log n) вместо O(n) — огромная разница.
2. **Удаление дубликатов** — одинаковые элементы идут подряд, можно пройти за один раз.
3. **Слияние данных** из двух источников — быстро, если оба отсортированы.
4. **Аналитика** — топ-N, медиана, процентили.
5. **Проверка уникальности, пересечения, разности** — все ускоряются на отсортированных данных.

Сортировка — как расставить книги на полке по алфавиту: сама по себе бесполезна, но когда ты ищешь книгу — экономишь часы.

### 📐 Что значит «отсортировать»

Формально: дан массив `arr`. Нужно переставить элементы так, чтобы выполнялось:

```
arr[0] ≤ arr[1] ≤ arr[2] ≤ ... ≤ arr[n-1]
```

Или в обратном порядке (убывание).

**Три важных свойства сортировки:**

- **Стабильность.** Сортировка **стабильна**, если элементы с одинаковыми ключами сохраняют **исходный порядок**. Пример: сортируем людей по возрасту. У нас два человека 25 лет — Алиса и Боб, Алиса была первой. Стабильная сортировка сохранит порядок: Алиса, Боб.
- **In-place.** Сортировка **на месте**, если использует O(1) дополнительной памяти.
- **Сравнительная.** Сортировка **сравнительная**, если сравнивает элементы попарно. Есть сортировки без сравнений (подсчётом, поразрядная) — они работают за O(n) в специальных условиях (Глава 6).

### 📊 Классификация сортировок

**По сложности (время работы):**

| Класс | Сортировки | Когда работает |
|:---|:---|:---|
| O(n²) | Пузырьковая, вставками, выбором | Маленькие массивы, почти отсортированные данные |
| O(n log n) | Слиянием, быстрая, пирамидальная | Общий случай, большие массивы |
| O(n + k) | Подсчётом, поразрядная, блочная | Ограниченный диапазон значений, целые числа |

**По дополнительной памяти:**

| Класс | Сортировки | Память |
|:---|:---|:---|
| In-place (O(1)) | Пузырьковая, вставками, выбором, quicksort | Не требуют дополнительного массива |
| O(log n) | Quicksort (стек рекурсии) | Только стек вызовов |
| O(n) | Merge sort, Timsort, сортировка подсчётом | Требуют дополнительный массив |

**По стабильности:**

| Стабильные | Нестабильные |
|:---|:---|
| Пузырьковая, вставками, слиянием, подсчётом, Timsort | Выбором, быстрая, пирамидальная, поразрядная (LSD — стабильна) |

**По методу:**

| Метод | Сортировки | Идея |
|:---|:---|:---|
| Обмен | Пузырьковая, быстрая | Меняем элементы местами |
| Вставка | Вставками | Вставляем элемент в отсортированную часть |
| Выбор | Выбором, пирамидальная | Выбираем минимум/максимум |
| Слияние | Слиянием, Timsort | Сливаем отсортированные части |
| Без сравнений | Подсчётом, поразрядная, блочная | Используют структуру ключей |

**Сводная таблица базовых сортировок:**

| Сортировка | Среднее | Худшее | Память | Стабильна | In-place |
|:---|:---|:---|:---|:---|:---|
| Пузырьковая | O(n²) | O(n²) | O(1) | ✅ | ✅ |
| Вставками | O(n²) | O(n²) | O(1) | ✅ | ✅ |
| Выбором | O(n²) | O(n²) | O(1) | ❌ | ✅ |
| Слиянием | O(n log n) | O(n log n) | O(n) | ✅ | ❌ |
| Быстрая | O(n log n) | O(n²) | O(log n) | ❌ | ✅ |

### 🧮 Нижняя граница для сравнительных сортировок

Можно ли отсортировать массив **быстрее**, чем за O(n log n), используя только сравнения? Ответ — **нет**. Это доказано математически.

**Идея:** сортировка — это перестановка. Для n элементов существует n! перестановок. Каждое сравнение даёт 1 бит информации (да/нет). Чтобы различить n! перестановок, нужно log₂(n!) бит. По формуле Стирлинга log₂(n!) ≈ n log₂ n = Θ(n log n). Меньше — не различить все перестановки.

**Вывод:** merge sort и quicksort **оптимальны** для сравнительных сортировок. Быстрее — только сортировки без сравнений (Глава 6).

### 💡 Что мы узнали?

- Сортировка — подготовка данных, открывающая другие алгоритмы.
- Классификация: по сложности, по памяти, по стабильности, по методу.
- Сравнительные сортировки имеют нижнюю границу Ω(n log n).
- Merge sort и quicksort оптимальны для сравнительных сортировок.

## 5.2 Сортировка пузырьком: как дойти до неё от проблемы

### 🔌 Проблема: как отсортировать массив, если мы умеем только сравнивать два элемента?

У нас есть массив. Мы умеем делать только одну операцию: сравнить два элемента и, если нужно, поменять их местами. Всё. Никаких «сортировать по возрастанию» из коробки.

**Первая наивная мысль:** как найти минимум?

Проходим по массиву, сравниваем текущий элемент с текущим минимумом. Если меньше — запоминаем. В конце первый элемент — минимум. Меняем его с первым. Потом ищем второй минимум, ставим на второе место. И так далее.

Это **сортировка выбором**. Мы дойдём до неё позже. Но сначала — есть ещё более простая мысль.

**Вторая наивная мысль:** а что если просто пройтись по массиву и проверить, что каждый элемент **не больше следующего**? Если где-то `arr[i] > arr[i+1]` — поменяем их местами. Может быть, одного прохода хватит?

Проверим на `[5, 3, 8, 1, 9, 2]`:

```
j=0: 5 > 3 → swap. [3, 5, 8, 1, 9, 2]
j=1: 5 < 8 → ok
j=2: 8 > 1 → swap. [3, 5, 1, 8, 9, 2]
j=3: 8 < 9 → ok
j=4: 9 > 2 → swap. [3, 5, 1, 8, 2, 9]
```

Прошли один раз. Массив: `[3, 5, 1, 8, 2, 9]`. Не отсортирован. Но обрати внимание: **9 оказалась в конце**. Это не случайно — 9 «всплыла» в конец, потому что она больше всех, и каждый раз, когда она встречала меньшего соседа, она с ним менялась.

**Идея:** повторим проход несколько раз. Каждый проход ставит **один элемент** на финальное место — тот, что «всплывает» в конец.

Так мы пришли к **пузырьковой сортировке**. Не потому что она «существовала в природе», а потому что это **первое, что приходит в голову**: проходим, меняем соседей, повторяем.

### 📐 Вывод алгоритма пошагово

**Шаг 1: базовый проход по массиву**

```go
for j := 0; j < n-1; j++ {
    if arr[j] > arr[j+1] {
        arr[j], arr[j+1] = arr[j+1], arr[j]
    }
}
```

**Шаг 2: заметили, что один проход не сортирует**

Нужно повторить проход несколько раз:

```go
for i := 0; i < n-1; i++ {
    for j := 0; j < n-1; j++ {
        if arr[j] > arr[j+1] {
            arr[j], arr[j+1] = arr[j+1], arr[j]
        }
    }
}
```

**Шаг 3: заметили, что каждый проход ставит один элемент в конец**

Значит, хвост массива уже отсортирован. Не нужно его трогать.

```go
for i := 0; i < n-1; i++ {
    for j := 0; j < n-1-i; j++ {
        if arr[j] > arr[j+1] {
            arr[j], arr[j+1] = arr[j+1], arr[j]
        }
    }
}
```

**Шаг 4: заметили, что если проход не сделал ни одного обмена — массив отсортирован**

```go
for i := 0; i < n-1; i++ {
    swapped := false
    for j := 0; j < n-1-i; j++ {
        if arr[j] > arr[j+1] {
            arr[j], arr[j+1] = arr[j+1], arr[j]
            swapped = true
        }
    }
    if !swapped {
        break
    }
}
```

Вот мы и **вывели** пузырьковую сортировку — начиная с простейшей идеи и добавляя оптимизации.

### 🧮 Сложность

- **Худший случай:** O(n²). Обратный порядок — каждое сравнение даёт обмен.
- **Средний случай:** O(n²).
- **Лучший случай:** O(n) с `swapped` — если массив уже отсортирован, один проход и выход.
- **Память:** O(1).
- **Стабильность:** ✅ (условие `>` не меняет равные элементы).

### 🔬 Почему пузырьковая сортировка плоха

Даже после всех оптимизаций:

1. **O(n²) в среднем.** Для миллиона элементов — триллион операций.
2. **Много обменов.** Каждый обмен — три записи в память.
3. **Слабая адаптивность.** `swapped` срабатывает только когда массив **полностью** отсортирован. Если первый элемент стоит в конце, все проходы будут полными.

Пузырьковая сортировка — хороший **учебный пример** и плохой **продакшен-выбор**.

### 💡 Что мы узнали?

- Пузырьковая сортировка **выведена** из идеи «пройтись, поменять соседей, повторить».
- Оптимизации (`n-1-i`, `swapped`) появились как ответы на замеченные проблемы.
- O(n²) в среднем. Стабильна, in-place, но бесполезна на больших данных.
- Ключевой урок: **простой алгоритм — не значит хороший**.

## 5.3 Сортировка вставками: как дойти до неё от проблемы

### 🔌 Проблема: пузырьковая сортировка делает много лишнего

Пузырьковая сортировка каждый проход идёт по всему массиву. Даже если массив почти отсортирован, она всё равно делает полные проходы. Это расточительно.

**Новая идея:** а что если мы будем **расширять отсортированную часть** шаг за шагом? Представим, что первые `i` элементов уже отсортированы. Берём `(i+1)`-й элемент и **вставляем** его в правильное место среди первых `i`. Тогда к концу массива всё будет отсортировано.

Это **сортировка вставками**.

### 📊 Аналогия: раскладываем карты в руке

Представь, что ты играешь в карты. Ты берёшь карты по одной и вставляешь каждую в правильное место среди уже взятых. Сначала у тебя одна карта — она «отсортирована». Берёшь вторую — вставляешь до или после первой. Берёшь третью — вставляешь в правильное место. И так далее.

Ты не сортируешь всю руку заново — ты **вставляешь новую карту в нужное место**.

### 📐 Вывод алгоритма пошагово

**Шаг 1: первый элемент уже «отсортирован»**

Массив из одного элемента отсортирован по определению. Значит, первые 1 элементы — отсортированы.

**Шаг 2: берём следующий элемент и вставляем его на место**

Возьмём `arr[1]`. Он должен встать где-то среди `arr[0..0]`. Если `arr[0] > arr[1]` — меняем местами. Теперь первые 2 элемента отсортированы.

**Шаг 3: продолжаем для всех i от 1 до n-1**

На каждом шаге у нас есть отсортированный префикс `arr[0..i-1]`. Мы берём `arr[i]` и вставляем его в правильное место.

**Как именно вставить?** Сдвигаем все элементы больше `arr[i]` вправо, пока не найдём место.

```go
key := arr[i]        // запоминаем элемент
j := i - 1
for j >= 0 && arr[j] > key {
    arr[j+1] = arr[j]  // сдвигаем больше вправо
    j--
}
arr[j+1] = key       // вставляем на освободившееся место
```

**Шаг 4: полный код**

```go
func insertionSort(arr []int) {
    n := len(arr)
    for i := 1; i < n; i++ {
        key := arr[i]
        j := i - 1
        for j >= 0 && arr[j] > key {
            arr[j+1] = arr[j]
            j--
        }
        arr[j+1] = key
    }
}
```

### 🔬 Разбор на конкретном примере

Массив `[5, 3, 8, 1, 9, 2]`.

**i = 1:** `key = 3`. Сдвигаем `5` вправо (5 > 3). Вставляем 3 на позицию 0.
```
[3, 5, 8, 1, 9, 2]
```

**i = 2:** `key = 8`. 5 < 8 — останавливаемся. Вставляем 8 на позицию 2 (на месте).
```
[3, 5, 8, 1, 9, 2]
```

**i = 3:** `key = 1`. Сдвигаем 8, 5, 3 вправо. Вставляем 1 на позицию 0.
```
[1, 3, 5, 8, 9, 2]
```

**i = 4:** `key = 9`. 8 < 9 — останавливаемся. Вставляем 9 на позицию 4.
```
[1, 3, 5, 8, 9, 2]
```

**i = 5:** `key = 2`. Сдвигаем 9, 8, 5, 3 вправо. Вставляем 2 после 1.
```
[1, 2, 3, 5, 8, 9]
```

Готово.

### 🧮 Сложность

- **Худший случай:** O(n²). Обратный порядок — каждый элемент сдвигается на i позиций.
- **Средний случай:** O(n²).
- **Лучший случай:** O(n). Если массив уже отсортирован, каждая итерация делает 1 сравнение и 0 сдвигов.
- **Память:** O(1).
- **Стабильность:** ✅ (условие `>` не сдвигает равные).

### 📊 Почему сортировка вставками быстра на почти отсортированных данных

Ключевое отличие от пузырьковой: **каждый элемент сдвигается только тогда, когда это необходимо**.

Если массив почти отсортирован (каждый элемент не более чем в k позициях от своего места), количество сдвигов на каждом шаге — O(k). Суммарно — **O(n·k)**. Для k = 2 это O(n).

Пузырьковая сортировка такой адаптивности не имеет: она всегда делает полный проход по всему диапазону.

### 🔬 Где сортировка вставками используется на практике

**1. Маленькие массивы (n < 16–32).** Быстрее, чем merge sort и quicksort из-за меньшей константы и лучшей кэш-локальности. Поэтому гибридные сортировки (pdqsort, Timsort) используют её для маленьких подмассивов.

**2. Почти отсортированные данные.** Лог-файлы, где время почти монотонно. Работает за O(n).

**3. Онлайн-обработка.** Данные поступают по одному элементу — можно поддерживать отсортированный массив, вставляя каждый новый элемент.

### 💡 Что мы узнали?

- Сортировка вставками **выведена** из идеи «расширять отсортированную часть, вставляя каждый новый элемент».
- Это **естественное** решение, если ты уже понял, что пузырьковая сортировка делает лишнюю работу.
- O(n²) в среднем, O(n) в лучшем случае.
- Стабильна, in-place, быстра на почти отсортированных данных.
- Используется в гибридных сортировках для маленьких массивов.

## 5.4 Сортировка выбором: как дойти до неё от проблемы

### 🔌 Проблема: что если обмены дорогие?

Пузырьковая и вставками сортировки делают много **сдвигов и обменов**. Каждый обмен — три записи в память (временная переменная, два присваивания). Если элементы большие (например, структуры на 1 КБ), это дорого.

**Новая идея:** а можно ли минимизировать **обмены**, даже если придётся делать больше сравнений?

Да. Если мы сначала **найдём** минимум, а потом **один раз** поменяем его с первым элементом — мы сделаем ровно один обмен вместо многих.

Это **сортировка выбором**.

### 📐 Вывод алгоритма пошагово

**Шаг 1: найти минимум в массиве**

Проходим по массиву, находим минимум. O(n).

**Шаг 2: поменять минимум с первым элементом**

Один обмен.

**Шаг 3: повторить для оставшейся части**

Теперь ищем минимум в `arr[1..n-1]`, ставим на позицию 1. Потом в `arr[2..n-1]`, ставим на позицию 2. И так далее.

**Шаг 4: полный код**

```go
func selectionSort(arr []int) {
    n := len(arr)
    for i := 0; i < n-1; i++ {
        minIdx := i
        for j := i + 1; j < n; j++ {
            if arr[j] < arr[minIdx] {
                minIdx = j
            }
        }
        if minIdx != i {
            arr[i], arr[minIdx] = arr[minIdx], arr[i]
        }
    }
}
```

### 🔬 Разбор на примере

Массив `[5, 3, 8, 1, 9, 2]`.

**i = 0:** ищем минимум в `[5, 3, 8, 1, 9, 2]`. Минимум = 1 (индекс 3). Меняем arr[0] и arr[3].
```
[1, 3, 8, 5, 9, 2]
```

**i = 1:** ищем минимум в `[3, 8, 5, 9, 2]`. Минимум = 2 (индекс 5). Меняем.
```
[1, 2, 8, 5, 9, 3]
```

**i = 2:** ищем минимум в `[8, 5, 9, 3]`. Минимум = 3 (индекс 5). Меняем.
```
[1, 2, 3, 5, 9, 8]
```

**i = 3:** ищем минимум в `[5, 9, 8]`. Минимум = 5 (индекс 3). Не меняем.
```
[1, 2, 3, 5, 9, 8]
```

**i = 4:** ищем минимум в `[9, 8]`. Минимум = 8 (индекс 5). Меняем.
```
[1, 2, 3, 5, 8, 9]
```

Готово.

### 🧮 Сложность

- **Худший, средний, лучший:** O(n²). **Не адаптивна** — даже если массив отсортирован, делает все сравнения.
- **Обменов:** ровно **n-1** (по одному на итерацию).
- **Память:** O(1).
- **Стабильность:** ❌ нестабильна.

### 🔬 Почему сортировка выбором не используется в реальных системах

1. **Не адаптивна.** Даже на отсортированном массиве — O(n²) сравнений.
2. **Нестабильна.** Обмен может поменять порядок равных.
3. **O(n²) в любом случае.** Нет ни одного сценария, где она работала бы за O(n).
4. **Плохая кэш-локальность.** Обмены могут «прыгать» по массиву.

Единственный сценарий: когда **сравнения дешёвые, а обмены очень дорогие**. На практике в 99% случаев есть лучший выбор.

### 💡 Что мы узнали?

- Сортировка выбором **выведена** из идеи «минимизировать обмены за счёт большего числа сравнений».
- O(n²) в любом случае — не адаптивна.
- **Ровно n-1 обменов** — минимум среди всех сортировок.
- Нестабильна. Практически не используется.

## 5.5 Сортировка слиянием: как дойти до неё от проблемы

### 🔌 Проблема: как сортировать за O(n log n)?

Мы разобрали три сортировки, каждая за O(n²). Это катастрофа при больших данных. Возникает вопрос: **можно ли быстрее?**

В Главе 1 мы видели рекуррентные соотношения. Пришло время их применить.

**Ключевая идея:** сортировка маленького массива — быстрая. Сортировка большого — медленная. **А что если разбить большой массив на маленькие, отсортировать их, а потом объединить?**

Это идея **divide and conquer** (разделяй и властвуй). Реализация для сортировки — **сортировка слиянием (merge sort)**.

### 📐 Вывод алгоритма пошагово

**Шаг 1: базовый случай**

Массив из 0 или 1 элемента — уже отсортирован. Возвращаем его.

**Шаг 2: разделить**

Разбиваем массив пополам: `left = arr[:mid]`, `right = arr[mid:]`.

**Шаг 3: завоевать (рекурсивно отсортировать)**

Вызываем merge sort на `left` и на `right`. По индукции получаем два отсортированных массива.

**Шаг 4: объединить (слить)**

Теперь у нас два **отсортированных** массива. Как получить один отсортированный?

**Ключевая операция — слияние:**

1. Ставим два указателя: `i` на начало `left`, `j` на начало `right`.
2. Сравниваем `left[i]` и `right[j]`. Берём меньший, записываем в результат, двигаем указатель.
3. Когда один массив исчерпан — копируем оставшиеся элементы другого.

```
left:  [1, 3, 5, 7]
right: [2, 4, 6, 8]

i=0, j=0: 1 < 2 → берём 1. result=[1], i=1
i=1, j=0: 3 > 2 → берём 2. result=[1,2], j=1
i=1, j=1: 3 < 4 → берём 3. result=[1,2,3], i=2
i=2, j=1: 5 > 4 → берём 4. result=[1,2,3,4], j=2
... и так далее
```

**Шаг 5: полный код**

```go
func mergeSort(arr []int) []int {
    if len(arr) <= 1 {
        return arr
    }
    mid := len(arr) / 2
    left := mergeSort(arr[:mid])
    right := mergeSort(arr[mid:])
    return merge(left, right)
}

func merge(left, right []int) []int {
    result := make([]int, 0, len(left)+len(right))
    i, j := 0, 0
    for i < len(left) && j < len(right) {
        if left[i] <= right[j] {
            result = append(result, left[i])
            i++
        } else {
            result = append(result, right[j])
            j++
        }
    }
    result = append(result, left[i:]...)
    result = append(result, right[j:]...)
    return result
}
```

### 🧮 Анализ сложности

**Рекуррентное соотношение:**

```
T(n) = 2·T(n/2) + O(n)
```

- 2 — две половины.
- n/2 — размер каждой.
- O(n) — слияние.

**Решение через мастер-теорему** (подглава 1.4): a=2, b=2, f(n)=n. log_b a = 1, n¹ = n = f(n) → случай 2 → **T(n) = Θ(n log n)**.

**Интуиция через дерево рекурсии:**

```
Уровень 0:              T(n)                  ← стоимость O(n)
                       /    \
Уровень 1:          T(n/2)   T(n/2)           ← O(n)
                    /  \      /  \
Уровень 2:      T(n/4) T(n/4) T(n/4) T(n/4)   ← O(n)
                ...                            ...

Уровень log n:    T(1) T(1) ... T(1)          ← O(n)
```

Глубина — log₂(n). Стоимость каждого уровня — O(n). Итого — **O(n log n)**.

### 📊 Преимущества и недостатки

**Преимущества:**

1. **O(n log n) в любом случае.** Даже на обратно отсортированных данных. Нет деградации.
2. **Стабильна.** При слиянии `left[i] <= right[j]` — равные берутся из левого первыми.
3. **Хорошая кэш-локальность** при слиянии.

**Недостатки:**

1. **O(n) дополнительной памяти.**
2. **Медленнее quicksort на практике** из-за аллокаций.

### 💡 Что мы узнали?

- Merge sort **выведена** из идеи «разбить, отсортировать, слить».
- Ключевая операция — **слияние двух отсортированных массивов** за O(n).
- O(n log n) в любом случае, стабильна, но O(n) памяти.
- Используется во внешней сортировке, Timsort, параллельной сортировке.

## 5.6 Быстрая сортировка: как дойти до неё от проблемы

### 🔌 Проблема: merge sort требует O(n) дополнительной памяти

Merge sort даёт O(n log n), но требует **O(n) дополнительной памяти**. А что если мы хотим сортировать **на месте** (in-place)?

**Новая идея:** а что если вместо разделения пополам выбрать **опорный элемент (pivot)** и разбить массив на две части — меньше pivot и больше pivot? Тогда pivot окажется на своём финальном месте, а обе части можно отсортировать рекурсивно.

Это **быстрая сортировка (quicksort)**.

### 📐 Вывод алгоритма пошагово

**Шаг 1: выбрать pivot**

Возьмём последний элемент массива как pivot.

**Шаг 2: разбить массив (partition)**

Переставим элементы так, чтобы слева от pivot были меньшие, справа — большие. После этого pivot стоит на **финальном** месте.

**Как это сделать in-place?**

- Указатель `i` — граница «меньших».
- Указатель `j` идёт от low до high-1.
- Если `arr[j] < pivot` — меняем `arr[i]` и `arr[j]`, `i++`.
- В конце меняем `arr[i]` и `arr[high]` (pivot на место).

```
[5, 3, 8, 1, 9, 2], pivot = 2

i=0, j=0: 5 > 2 → пропускаем
i=0, j=1: 3 > 2 → пропускаем
i=0, j=2: 8 > 2 → пропускаем
i=0, j=3: 1 < 2 → swap(arr[0], arr[3]), i=1
          [1, 3, 8, 5, 9, 2]
i=1, j=4: 9 > 2 → пропускаем
Конец. swap(arr[1], arr[5])
[1, 2, 8, 5, 9, 3]
```

Pivot 2 на позиции 1. Слева — `[1]`, справа — `[8, 5, 9, 3]`.

**Шаг 3: рекурсивно отсортировать обе части**

**Шаг 4: полный код**

```go
func quicksort(arr []int, low, high int) {
    if low < high {
        p := partition(arr, low, high)
        quicksort(arr, low, p-1)
        quicksort(arr, p+1, high)
    }
}

func partition(arr []int, low, high int) int {
    pivot := arr[high]
    i := low
    for j := low; j < high; j++ {
        if arr[j] < pivot {
            arr[i], arr[j] = arr[j], arr[i]
            i++
        }
    }
    arr[i], arr[high] = arr[high], arr[i]
    return i
}
```

### 🧮 Анализ сложности

**Лучший случай:** pivot делит массив **пополам**.

```
T(n) = 2·T(n/2) + O(n) = O(n log n)
```

**Худший случай:** pivot каждый раз — минимум или максимум. Одна часть пустая, другая n-1.

```
T(n) = T(n-1) + O(n) = O(n²)
```

**Средний случай:** O(n log n).

### 🎯 Как избежать худшего случая

Проблема: если данные отсортированы, а pivot всегда последний — O(n²). Решения:

**1. Случайный pivot.** Меняем последний элемент со случайным, потом делаем partition. Вероятность худшего — ничтожна.

```go
randIdx := low + rand.Intn(high-low+1)
arr[randIdx], arr[high] = arr[high], arr[randIdx]
```

**2. Медиана трёх.** Берём медиану из `arr[low]`, `arr[mid]`, `arr[high]`.

**3. Introsort.** Следим за глубиной рекурсии. Если > 2·log(n) — переключаемся на heapsort. Гарантирует O(n log n). Именно так работает pdqsort в Go.

### 📊 Сравнение merge sort и quicksort

| | Merge sort | Quicksort |
|:---|:---|:---|
| Среднее | O(n log n) | O(n log n) |
| Худшее | O(n log n) | O(n²) |
| Память | O(n) | O(log n) |
| Стабильность | ✅ | ❌ |
| In-place | ❌ | ✅ |
| Константа | Больше | Меньше |
| Кэш-локальность | Хорошая | Очень хорошая |

**Почему quicksort быстрее:** меньше аллокаций, лучше кэш.

### 💡 Что мы узнали?

- Quicksort **выведена** из идеи «выбрать pivot, разбить, рекурсивно отсортировать».
- Ключевая операция — **partition** (разбиение).
- Среднее: O(n log n). Худшее: O(n²).
- In-place, но нестабильна.
- Выбор pivot критичен: случайный, медиана трёх, introsort.

## 5.7 Гибридные сортировки: pdqsort в Go

### 🔌 Проблема: какую сортировку использовать?

У каждой сортировки свои преимущества и недостатки. **Что если комбинировать их?**

Именно так работает **pdqsort** — сортировка, которую Go использует в `sort.Slice`.

### 📐 Как pdqsort комбинирует алгоритмы

**1. Основа — quicksort** с **медианой трёх** для выбора pivot.

**2. Маленькие массивы (≤ 12) → сортировка вставками.** Она быстрее из-за меньшей константы и лучшей кэш-локальности.

**3. Плохой pivot → heapsort.** pdqsort считает глубину рекурсии. Если > 2·log(n) — переключается на heapsort. Heapsort гарантирует O(n log n) в любом случае.

**4. Много повторов → three-way partition.** Разбиение на три части: меньше, равно, больше. Решает проблему, когда все элементы одинаковые.

**5. Уже отсортированные данные → быстрый выход.** Проверяет, отсортирован ли массив, завершает за O(n).

### 📊 Сравнение сортировок в Go

| Функция | Алгоритм | Стабильность |
|:---|:---|:---|
| `sort.Ints`, `sort.Strings` | pdqsort | ❌ |
| `sort.Slice` | pdqsort | ❌ |
| `sort.SliceStable` | Timsort | ✅ |

### 💡 Что мы узнали?

- pdqsort — гибрид: quicksort + вставками + heapsort.
- Маленькие массивы → вставками. Плохой pivot → heapsort.
- Go использует pdqsort в `sort.Slice`.
- `sort.SliceStable` — Timsort (стабильная, но медленнее).
- Свою сортировку писать не нужно.

## 5.8 Практика: решаем задачи

### 📝 Задача 1: Проверка анаграмм

**Формулировка:** даны две строки. Проверь, являются ли они анаграммами.

**Подход 1: сортировка**

```go
func isAnagram(s, t string) bool {
    if len(s) != len(t) {
        return false
    }
    sChars := []rune(s)
    tChars := []rune(t)
    sort.Slice(sChars, func(i, j int) bool { return sChars[i] < sChars[j] })
    sort.Slice(tChars, func(i, j int) bool { return tChars[i] < tChars[j] })
    return string(sChars) == string(tChars)
}
```

**Сложность:** O(n log n).

**Подход 2: хеш-таблица**

```go
func isAnagram(s, t string) bool {
    if len(s) != len(t) {
        return false
    }
    counts := make(map[rune]int)
    for _, ch := range s {
        counts[ch]++
    }
    for _, ch := range t {
        counts[ch]--
        if counts[ch] < 0 {
            return false
        }
    }
    return true
}
```

**Сложность:** O(n).

### 📝 Задача 2: Слияние интервалов

**Формулировка:** дан массив интервалов. Слей пересекающиеся.

```go
func mergeIntervals(intervals [][]int) [][]int {
    if len(intervals) <= 1 {
        return intervals
    }
    sort.Slice(intervals, func(i, j int) bool {
        return intervals[i][0] < intervals[j][0]
    })
    result := [][]int{intervals[0]}
    for i := 1; i < len(intervals); i++ {
        last := result[len(result)-1]
        current := intervals[i]
        if current[0] <= last[1] {
            if current[1] > last[1] {
                last[1] = current[1]
            }
        } else {
            result = append(result, current)
        }
    }
    return result
}
```

**Сложность:** O(n log n).

func findKthLargest(nums []int, k int) int {

### 📝 Задача 4: Top-K частых элементов

```go
func topKFrequent(nums []int, k int) []int {
    counts := make(map[int]int)
    for _, x := range nums {
        counts[x]++
    }
    unique := make([]int, 0, len(counts))
    for x := range counts {
        unique = append(unique, x)
    }
    sort.Slice(unique, func(i, j int) bool {
        return counts[unique[i]] > counts[unique[j]]
    })
    return unique[:k]
}
```

**Сложность:** O(n + m log m).

Мы не заучивали сортировки — мы **выводили** их из проблем:

- **Пузырьковая** — из идеи «пройтись, поменять соседей, повторить».
- **Вставками** — из идеи «расширять отсортированную часть».
- **Выбором** — из идеи «минимизировать обмены».
- **Слиянием** — из идеи «разбить, отсортировать, слить».

Каждая сортировка — это **ответ на конкретную проблему** предыдущей. Поняв это, ты не будешь заучивать — ты будешь **понимать**, почему каждая работает именно так.

| **Merge** | Слияние двух отсортированных массивов |
| **Quickselect** | Поиск k-го элемента через partition |
| **pdqsort** | Гибридная сортировка в Go |
| **Timsort** | Стабильная гибридная сортировка |
| **Heapsort** | O(n log n) сортировка через кучу |
| **Median of three** | Выбор pivot как медианы из трёх |

## Что мы узнали?

- Сравнительные сортировки имеют нижнюю границу Ω(n log n).
- Каждая сортировка **выводится** из конкретной проблемы.
- Пузырьковая, вставками, выбором — O(n²).
- Сортировка вставками быстра на почти отсортированных данных.
- Merge sort: O(n log n) всегда, стабильна, O(n) памяти.
- Quicksort: O(n log n) в среднем, O(n²) в худшем, in-place.
- pdqsort: гибрид, используемый в Go.
- Сортировка — часто первый шаг в решении задачи.

---

## Типичные ошибки

- ❌ **Использовать пузырьковую сортировку в продакшене.**
- ❌ **Сортировать весь массив, когда нужны только k элементов.**
- ❌ **Выбирать последний элемент как pivot без защиты.**
- ❌ **Забыть про стабильность.**
- ❌ **Игнорировать кэш-локальность.**
- ❌ **Писать свою сортировку вместо стандартной.**

---

## Для быстрого повторения

- **Пузырьковая:** O(n²), простая, не используется.
- **Вставками:** O(n²), но O(n) на почти отсортированных.
- **Выбором:** O(n²), n-1 обменов, нестабильна.
- **Слиянием:** O(n log n) всегда, стабильна, O(n) памяти.
- **Быстрая:** O(n log n) в среднем, O(n²) в худшем, in-place.
- **pdqsort:** quicksort + вставками + heapsort.
- **В Go:** `sort.Slice` (pdqsort), `sort.SliceStable` (Timsort).

## Ответы

**1.** Сортировка — перестановка. Для n элементов n! перестановок. Каждое сравнение даёт 1 бит. Нужно log₂(n!) = Θ(n log n) бит, чтобы различить все перестановки.

**2.** Стабильность — сохранение порядка равных. Пример: сортируем по возрасту, у нас два человека 25 лет — Алиса (первая) и Боб (второй). Стабильная сортировка сохранит порядок.

**3.** Идея: пройтись, сравнить соседей, поменять, если неправильный порядок. Заметили, что один проход не сортирует — повторить. Заметили, что хвост сортирован — уменьшить диапазон. Заметили, что без обменов массив отсортирован — выйти.

**4.** Пузырьковая делает полные проходы. Идея: расширять отсортированную часть, вставляя каждый новый элемент в правильное место. Каждый элемент сдвигается только когда нужно.

**5.** Когда массив **уже отсортирован**. Каждая итерация делает 1 сравнение и 0 сдвигов. Также O(n·k) на почти отсортированных данных, где k — максимальное расстояние от места.

**6.** Сортировка выбором делает **ровно n-1 обменов**. Это минимум среди всех сортировок. Важно, когда обмены дорогие (большие структуры).

**7.** Идея: сортировка маленького массива быстрая, большого — медленная. Разбить на маленькие, отсортировать, слить. Слияние двух отсортированных — O(n). T(n) = 2T(n/2) + O(n) → O(n log n).

**8.** Merge sort требует O(n) памяти. Идея: выбрать pivot, разбить массив на две части, рекурсивно отсортировать. Pivot оказывается на финальном месте. Работает in-place.

**9.** Способы: (1) случайный pivot, (2) медиана трёх, (3) introsort — переключение на heapsort при глубокой рекурсии.

**10.** pdqsort — гибрид: quicksort + вставками + heapsort. Маленькие массивы → вставками. Плохой pivot → heapsort. Гарантирует O(n log n).

**11.** `sort.Slice` использует pdqsort — нестабильная, быстрая. `sort.SliceStable` использует Timsort — стабильная, но медленнее.

**12.** Quicksort in-place: меньше аллокаций и лучше кэш-локальность. Merge sort требует O(n) памяти. На практике quicksort быстрее в 2–3 раза.

## Куда идти дальше?

Мы разобрали базовые сортировки — и главное, **вывели** их из проблем, а не заучили.

Остались сортировки, которые работают **быстрее, чем O(n log n)** — за счёт отказа от сравнений. Это **линейные сортировки**: подсчётом, поразрядная, блочная. Они работают за O(n) в специальных условиях и используются в реальных системах: от сортировки IP-адресов до обработки потоков данных.

В **Главе 6** мы разберём:

- Сортировку подсчётом: O(n + k), где k — диапазон значений.
- Поразрядную сортировку (radix sort): LSD и MSD.
- Блочную сортировку (bucket sort).
- Когда линейные сортировки применимы, а когда нет.
- Почему нижняя граница Ω(n log n) их не касается.
