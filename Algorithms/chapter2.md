## 2.0 Пролог: поиск, который тормозил из-за выбора структуры

Ты работаешь над сервисом, который обрабатывает события. Каждое событие — это запись с уникальным ID, временем и данными. События приходят пачками, их нужно хранить и часто искать по ID.

Ты выбираешь связный список. Логика простая: события приходят постоянно, нужно быстро вставлять новые — а вставка в начало списка это O(1). Ты реализуешь:

```go
type Event struct {
    ID   string
    Data string
    Next *Event
}

func insert(head *Event, e *Event) *Event {
    e.Next = head
    return e
}

func find(head *Event, id string) *Event {
    for head != nil {
        if head.ID == id {
            return head
        }
        head = head.Next
    }
    return nil
}
```

Тестируешь на 1000 событий — поиск мгновенный. На 100 000 — тоже быстро. Деплоишь в продакшен.

Через месяц в списке 50 миллионов событий. И вот тут начинаются проблемы: поиск по ID занимает секунды, CPU загружен, пользователи жалуются на таймауты.

Ты профилируешь и видишь: 95% времени уходит на `find`. Линейный проход по связному списку. 50 миллионов узлов, разбросанных по памяти. Каждый переход к следующему узлу — промах кэша.

Ты переписываешь хранение на map (хеш-таблицу):

```go
events := make(map[string]*Event)
event := events[id] // O(1) в среднем
```

И поиск ускоряется в тысячи раз. Проблема решена.

**Что произошло?** Ты выбрал связный список там, где нужен был доступ по ключу. Список хорош для вставки в начало, но ужасен для поиска. А хеш-таблица — наоборот.

В этой главе мы разберём две самые базовые структуры данных — **массивы** и **связные списки**. Мы поймём, как они устроены на физическом уровне, почему массивы быстрые, а списки гибкие, и как выбирать между ними. Это фундамент, на котором строятся все остальные структуры: хеш-таблицы, деревья, кучи, графы.

## 2.1 Массив: непрерывный блок памяти

### 🔌 Проблема: почему доступ к arr[100] занимает O(1)?

Ты используешь массивы каждый день. В Go это `[5]int`, `[]string`. В Python — `list`. В Java — `int[]`. Ты пишешь `arr[100]` и получаешь элемент мгновенно. Но **почему** это мгновенно? Что происходит под капотом?

Если бы массив был связным списком, тебе пришлось бы пройти 100 узлов, чтобы добраться до элемента. Это O(n). Но массив — не список. У него другое устройство.

### 📐 Как массив устроен в памяти

**Массив** — это **непрерывный блок памяти**. Все элементы лежат друг за другом, без промежутков. Если массив из 5 целых чисел (каждое 8 байт), он занимает ровно 40 байт подряд.

```
Память (адреса в байтах):

1000: [элемент 0]  ← arr[0]
1008: [элемент 1]  ← arr[1]
1016: [элемент 2]  ← arr[2]
1024: [элемент 3]  ← arr[3]
1032: [элемент 4]  ← arr[4]
```

Ключевое слово — **непрерывный**. Между элементами нет ни зазоров, ни указателей, ни метаданных. Просто данные, идущие подряд.

Когда ты пишешь `arr[2]`, процессор вычисляет адрес элемента:

```
адрес = базовый_адрес + индекс × размер_элемента
адрес = 1000 + 2 × 8 = 1016
```

И всё. Одно умножение и одно сложение. Процессор делает это за **одну инструкцию**.

**Вот почему доступ к массиву — O(1):** адрес вычисляется арифметически, а не ищется перебором. Индекс — это не «номер элемента, который нужно найти», а **смещение от начала блока**.

### 🔬 Что такое «непрерывный блок» физически

Когда ты создаёшь массив в Go:

```go
arr := [5]int{10, 20, 30, 40, 50}
```

Компилятор выделяет в памяти ровно 40 байт подряд. Где именно — решает рантайм, но это **всегда непрерывный кусок**.

Ты можешь проверить, что элементы лежат рядом:

```go
package main

import "fmt"

func main() {
    arr := [5]int{10, 20, 30, 40, 50}
    
    for i := range arr {
        fmt.Printf("arr[%d] = %d, адрес: %p\n", i, arr[i], &arr[i])
    }
}
```

Вывод (адреса будут отличаться при каждом запуске, но разница между соседями — всегда 8 байт):

```
arr[0] = 10, адрес: 0xc000012345
arr[1] = 20, адрес: 0xc00001234d
arr[2] = 30, адрес: 0xc000012355
arr[3] = 40, адрес: 0xc00001235d
arr[4] = 50, адрес: 0xc000012365
```

Обрати внимание: разница между соседними адресами — ровно 8 байт (размер `int` в Go на 64-битной системе). Это и есть непрерывность.

### 🔍 Почему непрерывность даёт O(1)

В Главе 1 мы разобрали O-нотацию. Теперь применим её.

Доступ к массиву по индексу:

```go
x := arr[100]
```

Что происходит:

1. Процессор вычисляет адрес: `база + 100 × 8`.
2. Процессор читает 8 байт по этому адресу.

Обе операции занимают **константное время** — не зависят от размера массива. `arr[100]` вычисляется так же быстро, как `arr[1000000]`. Поэтому сложность — **O(1)**.

Сравни со связным списком: чтобы добраться до 100-го элемента, нужно пройти 99 указателей. Каждый переход — чтение из памяти. Суммарно — 99 операций. Это O(n).

### 📊 Что даёт и что ограничивает непрерывность

**Преимущества непрерывности:**

1. **O(1) на доступ по индексу.** Адрес вычисляется, а не ищется.
2. **Кэш-локальность.** Когда процессор читает `arr[100]`, он загружает в кэш соседние элементы — `arr[101]`, `arr[102]`. Следующее обращение к соседу — из кэша, а не из RAM.
3. **Простота.** Массив — это просто блок памяти. Никаких указателей, никаких метаданных.

**Ограничения непрерывности:**

1. **Фиксированный размер.** Если ты выделил массив на 10 элементов, 11-й уже не влезет. Нужно выделять новый массив большего размера и копировать.
2. **Вставка в середину — O(n).** Чтобы вставить элемент на позицию i, нужно сдвинуть все элементы справа на одну позицию.
3. **Удаление из середины — O(n).** Нужно сдвинуть элементы влево.

### 🧮 Вставка в середину массива

Допустим, у тебя массив `[10, 20, 30, 40, 50]`, и ты хочешь вставить `25` на позицию 2 (между 20 и 30).

```
До вставки:
[10] [20] [30] [40] [50]
 0    1    2    3    4

После вставки:
[10] [20] [25] [30] [40] [50]
 0    1    2    3    4    5
```

Что нужно сделать:

1. Сдвинуть `[30, 40, 50]` вправо на одну позицию.
2. Записать `25` на освободившееся место.

Сдвиг `[30, 40, 50]` — это 3 операции копирования. В общем случае, если вставляем в позицию i, нужно сдвинуть (n - i) элементов. В худшем случае (вставка в начало) — n элементов. Сложность: **O(n)**.

### 🧮 Удаление из середины массива

Удаление — то же самое, только сдвиг влево:

```
До удаления (удаляем 30 на позиции 2):
[10] [20] [30] [40] [50]
 0    1    2    3    4

После удаления:
[10] [20] [40] [50]
 0    1    2    3
```

Сдвиг `[40, 50]` влево — 2 операции. В общем случае — O(n).

### 📊 Статический массив в Go

В Go статический массив — это `[N]T`:

```go
arr := [5]int{10, 20, 30, 40, 50}
```

Размер массива — часть типа. `[5]int` и `[10]int` — разные типы. Нельзя передать `[5]int` в функцию, которая ждёт `[10]int`.

**Важно:** статический массив **неизменяем по размеру**. Если ты хочешь добавить 6-й элемент — не получится. Компилятор не даст.

```go
arr := [5]int{10, 20, 30, 40, 50}
arr[5] = 60 // ошибка компиляции: index out of range
```

Именно поэтому в Go редко используют статические массивы напрямую. Вместо этого используют **слайсы** — динамические массивы, которые мы разберём в следующей подглаве.

### 💡 Что мы узнали?

- Массив — это **непрерывный блок памяти**. Элементы лежат друг за другом.
- Доступ по индексу — O(1), потому что адрес вычисляется: `база + индекс × размер`.
- Непрерывность даёт кэш-локальность: соседи загружаются в кэш вместе.
- Вставка в середину — O(n): нужно сдвигать элементы.
- Удаление из середины — O(n): тоже сдвиг.
- Статический массив в Go (`[N]T`) неизменяем по размеру.

## 2.2 Кэш-локальность: почему массивы быстрее списков

### 🔌 Проблема: два алгоритма с O(n), но один в 100 раз медленнее

В подглаве 2.1 мы разобрали, что массив — это непрерывный блок памяти, а доступ по индексу — O(1). В подглаве 2.4 мы разберём связный список и увидим, что обход списка — тоже O(n).

Но вот загадка: **обход массива из 1 миллиона элементов может быть в 50–100 раз быстрее, чем обход связного списка из того же количества узлов**. Хотя оба алгоритма имеют сложность O(n).

Почему? Ответ — **кэш-локальность**.

Это не абстрактное «массивы быстрее». Это конкретное физическое свойство: **процессор читает память не побайтово, а блоками по 64 байта**. И от того, как твои данные расположены в этих блоках, зависит, сколько обращений к RAM придётся сделать.

### 📐 Что такое строка кэша

Когда процессор обращается к оперативной памяти, он **никогда не читает один байт** или одно число. Он всегда читает **строку кэша (cache line)** — блок памяти фиксированного размера.

На большинстве современных процессоров (x86_64, ARM64) размер строки кэша — **64 байта**.

Это значит: когда ты обращаешься к `arr[0]`, процессор загружает в кэш **64 байта**, начиная с адреса, где лежит `arr[0]`. Если `arr` — это массив `int` (8 байт на элемент на 64-битной системе), то в одну строку кэша влезает:

```
64 байта / 8 байт на элемент = 8 элементов
```

То есть, обратившись к `arr[0]`, ты **бесплатно** получил в кэше `arr[1]`, `arr[2]`, ..., `arr[7]`. Следующие 7 обращений к соседям будут из кэша — а это в 100 раз быстрее, чем из RAM.

### 🔬 Как процессор работает с кэшем

Давай разберём физику процесса.

**Кэш** — это небольшая, но очень быстрая память внутри процессора. Она работает на частоте процессора и доступна за несколько тактов. RAM — это внешняя память, доступ к которой занимает **сотни тактов**.

Когда процессор хочет прочитать данные:

1. **Сначала он проверяет кэш.** Если данные там есть — это **попадание (cache hit)**. Чтение занимает ~4 такта.

2. **Если данных в кэше нет** — это **промах (cache miss)**. Процессор обращается к RAM, загружает оттуда **строку кэша** (64 байта) и сохраняет её в кэш. Чтение занимает ~200–400 тактов.

Разница между попаданием и промахом — **в 50–100 раз**.

Поэтому задача разработчика — **организовать данные так, чтобы процессор чаще попадал в кэш и реже промахивался**.

### 📊 Массив: почти идеальное использование кэша

Элементы массива лежат **непрерывно**. Когда ты обращаешься к `arr[0]`, процессор загружает строку кэша, в которой лежат `arr[0]`...`arr[7]`.

Дальше ты обращаешься к `arr[1]` — **попадание**. `arr[2]` — **попадание**. И так до `arr[7]`. Все 8 обращений после первого — из кэша.

Когда ты доходишь до `arr[8]` — **промах**, потому что `arr[8]` лежит в следующей строке кэша. Процессор загружает новую строку с `arr[8]`...`arr[15]`. И снова 7 попаданий.

**Итог для массива:** при последовательном обходе промах кэша происходит **один раз на 8 элементов**. Эффективность использования кэша — 87.5%.

```
Обход массива (последовательно):

[arr[0]] → промах, загружается строка с arr[0]...arr[7]
 arr[1]  → попадание
 arr[2]  → попадание
 ...
 arr[7]  → попадание
[arr[8]] → промах, загружается строка с arr[8]...arr[15]
 arr[9]  → попадание
 ...
```

### 📊 Связный список: промах на каждом узле

Теперь посмотрим на связный список. Узел списка — это структура с данными и указателем:

```go
type Node struct {
    Value int      // 8 байт
    Next  *Node    // 8 байт (указатель)
}
```

Узел занимает 16 байт. В строку кэша (64 байта) формально влезает 4 узла. **Но** есть проблема: узлы не лежат рядом в памяти.

Когда ты создаёшь связный список через `new(Node)` или `&Node{...}`, Go выделяет память для каждого узла **отдельно**. Аллокатор может разместить их в совершенно разных местах кучи:

```
Узел 0: адрес 0x1000
Узел 1: адрес 0x5000  ← не рядом с узлом 0
Узел 2: адрес 0x2000  ← не рядом с узлом 1
Узел 3: адрес 0x8000  ← не рядом с узлом 2
```

Когда ты переходишь от узла 0 к узлу 1:

1. Читаешь `Next` из узла 0 — он указывает на адрес `0x5000`.
2. Процессор проверяет кэш: там лежит строка с `0x1000` (узлом 0) и, возможно, что-то рядом — но **не** `0x5000`.
3. Происходит **промах кэша**. Процессор читает из RAM строку с `0x5000`.
4. В этой строке лежит узел 1 (16 байт) и **мусор** — какие-то другие объекты, не имеющие отношения к списку.

**Итог для связного списка:** каждый переход к следующему узлу — это **промах кэша**. Если в списке 1 миллион узлов, ты получаешь 1 миллион промахов. Строка кэша используется на 25% (16 байт полезных из 64), остальное — мусор.

```
Обход связного списка:

[Узел 0] → промах, загружается строка с узлом 0 и мусором
    ↓ переход по указателю
[Узел 1] → промах, загружается строка с узлом 1 и мусором
    ↓ переход по указателю
[Узел 2] → промах, загружается строка с узлом 2 и мусором
...
```

### 📊 Сравнение в цифрах

| Структура | Что загружается в кэш | Полезных данных | Эффективность |
|:---|:---|:---|:---|
| Массив `int` (8 байт) | 8 элементов подряд | 8 из 8 | 100% |
| Массив структур (16 байт) | 4 элемента подряд | 4 из 4 | 100% |
| Связный список | 1 узел + случайные объекты | 1 из 4 возможных | 25% |

**Вывод:** массив использует строку кэша **полностью** — все 64 байта несут полезные данные. Связный список использует строку кэша **на 25%** — остальное мусор.

### 🧪 Эксперимент: измеряем разницу

Давай проверим это на Go. Сравним скорость обхода массива и связного списка.

```go
package main

import (
    "fmt"
    "time"
)

type Node struct {
    Value int
    Next  *Node
}

func main() {
    const n = 10_000_000 // 10 миллионов элементов

    // === МАССИВ ===
    arr := make([]int, n)
    for i := range arr {
        arr[i] = i
    }

    start := time.Now()
    sum := 0
    for i := range arr {
        sum += arr[i]
    }
    arrTime := time.Since(start)

    // === СВЯЗНЫЙ СПИСОК ===
    var head *Node
    for i := n - 1; i >= 0; i-- {
        head = &Node{Value: i, Next: head}
    }

    start = time.Now()
    sum = 0
    for cur := head; cur != nil; cur = cur.Next {
        sum += cur.Value
    }
    listTime := time.Since(start)

    fmt.Printf("Массив:      %v\n", arrTime)
    fmt.Printf("Список:      %v\n", listTime)
    fmt.Printf("Список медленнее в %.1f раз\n", float64(listTime)/float64(arrTime))
}
```

**Примерный вывод** (зависит от железа):

```
Массив:      8ms
Список:      380ms
Список медленнее в 47.5 раз
```

**Что происходит:** оба алгоритма делают 10 миллионов операций сложения. Оба O(n). Но массив читает данные **последовательно**, попадая в кэш 7 раз из 8. Список промахивается **на каждом узле**, и каждый промах — это чтение из RAM, которое в 50–100 раз медленнее кэша.

### 🔍 Почему разница именно такая

Задержки на современных процессорах (примерные):

| Уровень памяти | Задержка | Размер |
|:---|:---|:---|
| L1 кэш | ~1 ns (4 такта) | 32–64 КБ |
| L2 кэш | ~4 ns (14 тактов) | 256–512 КБ |
| L3 кэш | ~12 ns (40 тактов) | 8–32 МБ |
| RAM | ~100 ns (300 тактов) | десятки ГБ |

Когда массив попадает в кэш, чтение занимает ~1–12 наносекунд. Когда список промахивается — ~100 наносекунд на каждый узел.

10 миллионов узлов × 100 ns = 1 секунда. Но в реальности список обходится быстрее, потому что процессор использует **prefetching** — предзагрузку данных, которые могут понадобиться. Однако prefetching плохо работает со связными списками, потому что адрес следующего узла неизвестен, пока не прочитан текущий.

### 📐 Почему prefetching не спасает списки

**Prefetching** — это механизм, при котором процессор **угадывает**, какие данные понадобятся дальше, и загружает их в кэш заранее.

Для массива это работает идеально: процессор видит, что ты читаешь `arr[0]`, `arr[1]`, `arr[2]` — и **предсказывает**, что следующим будет `arr[3]`. Он загружает `arr[3]`...`arr[10]` в кэш ещё до того, как ты к ним обратишься.

Для связного списка это **не работает**: адрес следующего узла хранится **внутри** текущего узла. Пока процессор не прочитает `Next`, он не знает, куда переходить. Предсказывать нечего — переход может быть в любое место памяти.

### 💡 Что мы узнали?

- Процессор читает память **строками кэша** по 64 байта, а не побайтово.
- Массив использует строку кэша **полностью**: промах один раз на 8 элементов (для `int`).
- Связный список использует строку кэша **на 25%**: промах на каждом узле, потому что узлы разбросаны по памяти.
- Разница между попаданием и промахом кэша — в 50–100 раз.
- Prefetching ускоряет массивы, но не помогает спискам — адрес следующего узла неизвестен заранее.
- Поэтому обход массива может быть в десятки раз быстрее обхода списка, хотя оба O(n).

## 2.3 Динамический массив: slice в Go

### 🔌 Проблема: массив фиксирован, а данных всё больше

В подглаве 2.1 мы разобрали статический массив — непрерывный блок памяти фиксированного размера. Если ты выделил массив на 10 элементов, 11-й уже не влезет:

```go
arr := [10]int{} // статический массив на 10 элементов
arr[10] = 5      // ошибка компиляции: index out of range
```

Но в реальных задачах количество данных **заранее неизвестно**. Ты читаешь события из Kafka, строки из файла, записи из базы — и не знаешь, сколько их будет. Тебе нужна структура, которая:

1. Начинается с небольшого размера.
2. **Растёт** по мере добавления элементов.
3. Сохраняет O(1) на доступ по индексу.

Такая структура называется **динамический массив**. В Go это **slice**.

### 📐 Как устроен slice в Go

**Slice** — это не массив. Это **структура-обёртка** над массивом. Внутри slice три поля:

```go
type slice struct {
    ptr    *T    // указатель на непрерывный блок памяти (массив)
    len    int   // текущая длина — сколько элементов реально заполнено
    cap    int   // ёмкость — сколько всего выделено памяти
}
```

**Что это значит:**

- `ptr` — указывает на массив в памяти. Это тот самый непрерывный блок, о котором мы говорили в 2.1.
- `len` — сколько элементов ты **реально** добавил. Это то, что возвращает `len(s)`.
- `cap` — сколько элементов **может** вместить выделенный массив. Это то, что возвращает `cap(s)`.

**Когда ты создаёшь slice:**

```go
s := make([]int, 0, 5) // длина 0, ёмкость 5
```

Go выделяет массив на 5 элементов, но длина slice — 0. Это значит, что в массиве есть место для 5 элементов, но пока ты не добавил ни одного.

### 🔬 Как работает добавление элементов

Когда ты делаешь `append(s, x)`, возможны два сценария:

**Сценарий 1: ёмкости хватает (len < cap)**

Элемент записывается в уже выделенный массив. Длина увеличивается на 1. Сложность — **O(1)**.

```go
s := make([]int, 0, 5) // len=0, cap=5, массив: [_, _, _, _, _]

s = append(s, 1) // len=1, cap=5, массив: [1, _, _, _, _]
s = append(s, 2) // len=2, cap=5, массив: [1, 2, _, _, _]
s = append(s, 3) // len=3, cap=5, массив: [1, 2, 3, _, _]
// Все три добавления — O(1), потому что место уже выделено
```

**Сценарий 2: ёмкости не хватает (len == cap)**

Нужно выделить **новый массив большего размера**, скопировать все элементы, записать новый элемент, обновить `ptr` и `cap`. Сложность — **O(n)**, где n — текущая длина.

```go
s := make([]int, 0, 3) // len=0, cap=3

s = append(s, 1) // len=1, cap=3, O(1)
s = append(s, 2) // len=2, cap=3, O(1)
s = append(s, 3) // len=3, cap=3, O(1) — ёмкость исчерпана!

s = append(s, 4) // len=3 == cap=3 → нужно расширяться!
// 1. Выделяется новый массив размером cap*2 = 6
// 2. Копируются элементы [1, 2, 3] в новый массив
// 3. Записывается 4
// 4. ptr обновляется на новый массив, cap = 6
// Сложность: O(3) — скопировали 3 элемента
```

### 📐 Стратегия расширения в Go

Вопрос: **на сколько увеличивать ёмкость при расширении?**

Если увеличивать **на фиксированное число** (например, +10), то при добавлении n элементов произойдёт n/10 расширений. Каждое расширение копирует в среднем n/2 элементов. Суммарно: (n/10) × (n/2) = n²/20. Средняя стоимость: **O(n)** на операцию. Это плохо.

Если увеличивать **в k раз** (например, в 2 раза), то расширений будет log₂(n), а суммарное копирование — n - 1 (геометрическая прогрессия). Средняя стоимость: **O(1)** на операцию. Это то, что нужно.

**В Go стратегия такая:**

- Если cap < 1024 — новый cap = old cap × 2 (удвоение).
- Если cap ≥ 1024 — новый cap = old cap × 1.25 (увеличение на 25%).

Почему после 1024 рост замедляется? Потому что удвоение больших массивов приводит к огромным скачкам памяти. Если у тебя slice на 1 ГБ, удвоение выделит ещё 2 ГБ — это может быть слишком много. Рост на 25% — компромисс между количеством расширений и эффективностью памяти.

### 🧮 Амортизированная сложность append

Мы разобрали это в Главе 1, подглава 1.3. Повторим кратко:

- Одиночный `append` может быть O(1) или O(n).
- Но **в среднем** по n операциям — O(1).
- Потому что дорогие расширения происходят редко, а дешёвые записи — часто.

**Итог:** `append` в Go — **амортизированно O(1)**.

### 📊 Как slice выглядит в памяти

Допустим, ты создал slice с len=3, cap=5:

```go
s := make([]int, 0, 5)
s = append(s, 10, 20, 30) // len=3, cap=5
```

В памяти это выглядит так:

```
slice (структура в стеке или куче):
┌──────────┐
│ ptr: 0x1000 │ → указывает на массив
│ len: 3      │
│ cap: 5      │
└──────────┘

Массив (в куче):
0x1000: [10]
0x1008: [20]
0x1016: [30]
0x1024: [пусто]
0x1032: [пусто]
```

**Ключевые моменты:**

1. **slice — это маленькая структура** (24 байта на 64-битной системе: 8 для ptr + 8 для len + 8 для cap).
2. **Данные лежат в массиве** — непрерывном блоке памяти.
3. **Длина и ёмкость — разные вещи.** Длина — сколько заполнено. Ёмкость — сколько выделено.
4. **ptr может меняться** при расширении — это тот самый «переезд скопом».

### 🔬 Почему slice — это не массив

Важное различие, которое часто путают:

**Массив `[5]int`** — это тип. Размер — часть типа. `[5]int` и `[10]int` — разные типы. Передаётся по значению (копируется при передаче в функцию).

**Slice `[]int`** — это структура. Размер не зафиксирован. Передаётся **по ссылке на данные** (ptr копируется, но указывает на тот же массив).

```go
// Статический массив: копируется при передаче
func modifyArray(arr [5]int) {
    arr[0] = 999 // меняет копию, оригинал не изменится
}

// Slice: передаётся ptr на тот же массив
func modifySlice(s []int) {
    s[0] = 999 // меняет оригинальные данные
}
```

### 📊 Срезы и переезды

Когда ты делаешь **срез** (slice expression) от слайса, ты **не создаёшь новый массив**. Ты создаёшь новую структуру slice с новыми len и cap, но с **тем же ptr**:

```go
original := []int{1, 2, 3, 4, 5} // len=5, cap=5

sliced := original[1:3] // len=2, cap=4, ptr указывает на элемент 1 (число 2)

fmt.Println(sliced) // [2 3]

// Изменяем через срез — меняется оригинал
sliced[0] = 999
fmt.Println(original) // [1 999 3 4 5]
```

**Что здесь произошло:**

- `sliced` — это **не копия** данных. Это новая структура с ptr, указывающим на `original[1]`.
- `len(sliced) = 2`, `cap(sliced) = 4` (от элемента 1 до конца массива).
- Изменение `sliced[0]` меняет `original[1]` — потому что это **один и тот же массив**.

**Это важный нюанс**, который часто приводит к багам: срез не копирует данные, а создаёт «окно» в тот же массив.

### 🧪 Практика: проверяем len и cap

```go
package main

import "fmt"

func main() {
    s := make([]int, 0, 3)
    
    for i := 1; i <= 10; i++ {
        s = append(s, i)
        fmt.Printf("append %d: len=%d, cap=%d, slice=%v\n", i, len(s), cap(s), s)
    }
}
```

**Вывод:**

```
append 1: len=1, cap=3, slice=[1]
append 2: len=2, cap=3, slice=[1 2]
append 3: len=3, cap=3, slice=[1 2 3]
append 4: len=4, cap=6, slice=[1 2 3 4]   ← расширились с 3 до 6
append 5: len=5, cap=6, slice=[1 2 3 4 5]
append 6: len=6, cap=6, slice=[1 2 3 4 5 6]
append 7: len=7, cap=12, slice=[1 2 3 4 5 6 7]  ← расширились с 6 до 12
append 8: len=8, cap=12, slice=[1 2 3 4 5 6 7 8]
...
```

**Что видно:**

1. До исчерпания ёмкости cap не меняется — новые элементы просто записываются в выделенный массив.
2. При исчерпании cap удваивается: 3 → 6 → 12.
3. len всегда равен количеству реально добавленных элементов.

### 💡 Что мы узнали?

- Slice в Go — это **структура-обёртка** над массивом: ptr, len, cap.
- При добавлении, если len < cap — O(1): запись в уже выделенный массив.
- Если len == cap — O(n): выделяется новый массив в 2 раза больше (до 1024) или в 1.25 раза (после 1024), элементы копируются.
- Амортизированная сложность append — O(1).
- Срез (`s[1:3]`) не копирует данные — создаёт новое «окно» в тот же массив.
- Массив `[N]T` — тип с фиксированным размером. Slice `[]T` — динамическая обёртка.

## 2.4 Связный список: узлы и указатели

### 🔌 Проблема: вставка в середину массива — O(n). А если вставлять нужно часто?

В подглаве 2.1 мы разобрали: вставка в середину массива требует сдвига всех элементов справа. Если массив из миллиона элементов, вставка в начало — это миллион операций копирования. O(n).

Теперь представь задачу: ты пишешь редактор текста. Пользователь печатает символы, удаляет их, вставляет в середину. Каждая операция — это изменение структуры. Если хранить текст в массиве, каждая вставка в середину — O(n). При длинном тексте редактор будет тормозить.

Нужна структура, где **вставка в любое место — O(1)**. Эта структура — **связный список**.

### 📐 Как устроен связный список

**Связный список** — это последовательность **узлов**, где каждый узел содержит:

1. **Данные** (value).
2. **Указатель на следующий узел** (next).

```
Голова (head)
    │
    ▼
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ Value: 10│    │ Value: 20│    │ Value: 30│    │ Value: 40│
│ Next: ───┼───→│ Next: ───┼───→│ Next: ───┼───→│ Next: nil│
└─────────┘    └─────────┘    └─────────┘    └─────────┘
```

**Ключевое отличие от массива:** элементы **не лежат в непрерывном блоке памяти**. Каждый узел — это отдельный объект в куче. Связь между узлами — через указатели, а не через физическое соседство.

В Go узел списка выглядит так:

```go
type Node struct {
    Value int
    Next  *Node
}
```

Сам список — это просто указатель на первый узел (**голову**):

```go
var head *Node // nil — список пуст
```

### 🔬 Почему вставка — O(1)

Допустим, у нас есть список:

```
head → [10] → [20] → [30] → nil
```

Мы хотим вставить `25` между `20` и `30`. Что нужно сделать:

1. Создать новый узел `[25]`.
2. Установить `Next` нового узла на `[30]`.
3. Установить `Next` узла `[20]` на новый узел.

```
До вставки:
head → [10] → [20] → [30] → nil
                  ↑
                 тут вставляем

После вставки:
head → [10] → [20] → [25] → [30] → nil
                  ↑       ↑
                 Next    Next
```

**Сколько операций?** Три присваивания указателей. Никаких сдвигов. Никакого копирования. Время — **константное**, O(1), независимо от размера списка.

**Вот код:**

```go
func insertAfter(prev *Node, value int) *Node {
    newNode := &Node{Value: value}
    newNode.Next = prev.Next  // 1. Новый узел указывает на следующий
    prev.Next = newNode       // 2. Предыдущий указывает на новый
    return newNode
}
```

Сравни с массивом: чтобы вставить элемент в середину, нужно сдвинуть все элементы справа. O(n). Список делает это за O(1).

### 🔬 Вставка в начало — тоже O(1)

Вставка в начало списка ещё проще:

```go
func insertAtHead(head *Node, value int) *Node {
    newNode := &Node{Value: value}
    newNode.Next = head // Новый узел указывает на старую голову
    return newNode      // Новая голова — новый узел
}
```

Всё — O(1). Сравни с массивом: вставка в начало требует сдвига всех элементов. O(n).

### 🧮 Обход списка — O(n)

Но у списка есть обратная сторона. Чтобы добраться до **i-го** элемента, нужно пройти по цепочке от головы:

```go
func get(head *Node, index int) *Node {
    cur := head
    for i := 0; i < index && cur != nil; i++ {
        cur = cur.Next
    }
    return cur
}
```

Чтобы получить 100-й элемент, нужно пройти 99 указателей. Каждый переход — чтение из памяти. Сложность — **O(n)**.

Сравни с массивом: `arr[100]` — это O(1), адрес вычисляется арифметически.

**Вывод:** связный список — это компромисс. Мы получаем O(1) на вставку, но теряем O(1) на доступ по индексу.

### 📊 Поиск в списке — O(n)

Поиск элемента по значению — линейный проход:

```go
func find(head *Node, value int) *Node {
    for cur := head; cur != nil; cur = cur.Next {
        if cur.Value == value {
            return cur
        }
    }
    return nil
}
```

Сложность — **O(n)** в худшем случае. Как и в массиве (линейный поиск). Но на практике массив быстрее из-за кэш-локальности (подглава 2.2).

### 🔬 Удаление из списка — O(1)

Чтобы удалить узел, нужно изменить указатель предыдущего узла:

```go
func deleteAfter(prev *Node) {
    if prev == nil || prev.Next == nil {
        return
    }
    prev.Next = prev.Next.Next // Перепрыгиваем удаляемый узел
}
```

Удаление — O(1), если у нас есть указатель на **предыдущий** узел. Но чтобы найти этот предыдущий узел, нужно обойти список — O(n).

### 📊 Типы связных списков

**Односвязный список (singly linked list):**

```
head → [10] → [20] → [30] → nil
```

Каждый узел указывает только на **следующий**. Нельзя вернуться назад.

**Двусвязный список (doubly linked list):**

```
head → [10] ⇄ [20] ⇄ [30] → nil
        ← prev / next →
```

Каждый узел указывает и на **следующий**, и на **предыдущий**. Это позволяет двигаться в обе стороны. Цена — дополнительный указатель в каждом узле (больше памяти).

**Кольцевой список (circular linked list):**

```
head → [10] → [20] → [30]
        ↑               │
        └───────────────┘
```

Последний узел указывает на первый. Нет `nil` — список замкнут.

### 🔬 Где связные списки реально используются

**1. Реализация стека и очереди** (Глава 3).

Стек на связном списке: вставка в начало (push) — O(1), удаление из начала (pop) — O(1). Очередь: вставка в конец — O(1), удаление из начала — O(1).

**2. LRU Cache** (Глава 4).

Кэш, который вытесняет самые старые элементы. Реализуется через **двусвязный список + хеш-таблицу**. Список хранит порядок использования, хеш-таблица даёт O(1) на поиск.

**3. Реализация `container/list` в Go.**

В стандартной библиотеке Go есть `container/list` — двусвязный список. Но на практике его используют редко — слайсы почти всегда быстрее из-за кэш-локальности.

**4. История в браузере.**

Страницы назад/вперёд — это двусвязный список. Каждая страница — узел. Кнопка «назад» — переход по prev, «вперёд» — по next.

**5. Плейлист в музыкальном плеере.**

Песни в плейлисте — узлы. Переключение вперёд/назад — переход по next/prev.

### 🧪 Практика: реализуем список

Полная реализация односвязного списка:

```go
package main

import "fmt"

type Node struct {
    Value int
    Next  *Node
}

func insertAtHead(head *Node, v int) *Node {
    return &Node{Value: v, Next: head}
}

func insertAtTail(head *Node, v int) *Node {
    newNode := &Node{Value: v}
    if head == nil {
        return newNode
    }
    cur := head
    for cur.Next != nil {
        cur = cur.Next
    }
    cur.Next = newNode
    return head
}

func length(head *Node) int {
    count := 0
    for cur := head; cur != nil; cur = cur.Next {
        count++
    }
    return count
}

func printList(head *Node) {
    for cur := head; cur != nil; cur = cur.Next {
        fmt.Printf("%d → ", cur.Value)
    }
    fmt.Println("nil")
}

func main() {
    var head *Node

    head = insertAtTail(head, 10)
    head = insertAtTail(head, 20)
    head = insertAtTail(head, 30)

    printList(head) // 10 → 20 → 30 → nil
    fmt.Println("Длина:", length(head)) // 3

    head = insertAtHead(head, 5)
    printList(head) // 5 → 10 → 20 → 30 → nil
}
```

### 📊 Пространственная сложность

Каждый узел списка занимает:

- Данные: 8 байт (для `int`).
- Указатель `Next`: 8 байт.

Итого: **16 байт на узел** + накладные расходы аллокатора (обычно ещё 16 байт на заголовок объекта в Go).

Массив из `int` занимает **8 байт на элемент**, без накладных расходов.

**Вывод:** связный список требует **в 2–4 раза больше памяти**, чем массив, из-за указателей и фрагментации.

### 💡 Что мы узнали?

- Связный список — это цепочка **узлов**, каждый содержит данные и указатель на следующий.
- Вставка в начало, середину (при наличии указателя на prev) — O(1).
- Обход и поиск — O(n).
- Доступ по индексу — O(n), в отличие от массива.
- Список требует больше памяти из-за указателей.
- Типы: односвязный, двусвязный, кольцевой.
- Реальные применения: LRU cache, история браузера, стек/очередь.

## 2.5 Массив vs связный список: сравнение

### 🔌 Проблема: как выбрать структуру под задачу?

Мы разобрали массивы (2.1), кэш-локальность (2.2), динамические массивы (2.3) и связные списки (2.4). Теперь главный вопрос: **когда что использовать?**

Новички часто думают: «Связный список — это продвинутая структура, значит, она лучше массива». Или наоборот: «Массив быстрее, всегда использую массив». Оба подхода неверны.

Выбор структуры зависит от **операций**, которые ты выполняешь чаще всего. Давай сравним системно.

### 📊 Таблица сложностей

| Операция | Массив (статический) | Slice (динамический) | Связный список |
|:---|:---|:---|:---|
| Доступ по индексу | O(1) | O(1) | O(n) |
| Вставка в конец | N/A | O(1)* | O(n)** |
| Вставка в начало | O(n) | O(n) | O(1) |
| Вставка в середину | O(n) | O(n) | O(1)*** |
| Удаление из конца | N/A | O(1) | O(n)** |
| Удаление из начала | O(n) | O(n) | O(1) |
| Удаление из середины | O(n) | O(n) | O(1)*** |
| Поиск по значению | O(n) | O(n) | O(n) |
| Память на элемент | T | T | T + указатель |
| Кэш-локальность | ✅ | ✅ | ❌ |

\* Амортизированно, при расширении в 2 раза.  
\** Для односвязного списка. Для двусвязного с указателем на хвост — O(1).  
\*** Если есть указатель на предыдущий узел.

### 🔍 Разбор ключевых различий

**1. Доступ по индексу**

- **Массив:** O(1). Адрес вычисляется: `база + индекс × размер`.
- **Список:** O(n). Нужно пройти по цепочке от головы.

**Когда важно:** если ты часто обращаешься по индексу (бинарный поиск, сортировка, произвольный доступ) — только массив.

**2. Вставка в середину**

- **Массив:** O(n). Нужно сдвинуть все элементы справа.
- **Список:** O(1). Нужно изменить два указателя.

**Когда важно:** если ты часто вставляешь в середину (редактор текста, live-очередь) — список.

**Но:** чтобы вставить в середину списка, нужно **сначала найти** место вставки. А поиск — O(n). Поэтому реальная вставка «в середину по индексу» — O(n) для обеих структур.

Список выигрывает только когда у тебя **уже есть указатель** на место вставки.

**3. Кэш-локальность**

- **Массив:** элементы лежат рядом → кэш используется полностью.
- **Список:** узлы разбросаны → промах на каждом шаге.

**Когда важно:** если ты обходишь структуру последовательно (суммирование, фильтрация, map/reduce) — массив быстрее в 50–100 раз.

### 📐 Когда массив — правильный выбор

- Частый доступ по индексу.
- Последовательный обход (кэш-локальность).
- Хранение фиксированного набора данных.
- Сортировка, бинарный поиск.
- Все задачи, где данные **читают** чаще, чем **изменяют**.

**Примеры:**

- Хранение логов: данные добавляются в конец, читаются последовательно.
- Матрицы, таблицы.
- Буферы, кэши с доступом по индексу.

### 📐 Когда связный список — правильный выбор

- Частая вставка/удаление в начало или середину (при наличии указателя).
- Данные **изменяют** чаще, чем **читают** по индексу.
- Нужно хранить порядок с частыми перестановками.
- Реализация стека, очереди, LRU cache.

**Примеры:**

- LRU cache: элементы перемещаются в начало при обращении (двусвязный список).
- История браузера: назад/вперёд.
- Очередь задач: добавление в конец, удаление из начала.

### 🔬 Реальный кейс: LRU Cache

Классический пример, где связный список **незаменим** — **LRU Cache** (Least Recently Used — «наименее недавно использованный»).

**Задача:** кэш фиксированного размера. Когда кэш заполнен, при добавлении нового элемента нужно удалить тот, к которому обращались **давно**.

**Требования:**

- Доступ по ключу — O(1).
- Обновление порядка использования — O(1).
- Удаление самого старого — O(1).

**Решение:** **двусвязный список + хеш-таблица**.

- Хеш-таблица: ключ → указатель на узел списка. Даёт O(1) на доступ.
- Двусвязный список: хранит порядок использования. Голова — самый свежий, хвост — самый старый.

Когда кэш заполнен, удаляем хвост (O(1)). Когда обращаются к элементу, перемещаем его в голову (O(1)).

**Массив для этой задачи не подходит:** перемещение элемента в начало требует сдвига всех элементов — O(n). А список делает это за O(1).

Мы разберём LRU Cache детально в Главе 4, когда будем проходить хеш-таблицы.

### 📊 Почему в Go редко используют связные списки

В стандартной библиотеке Go есть `container/list` — двусвязный список. Но на практике его используют редко. Почему?

**1. Slice покрывает большинство сценариев.**

В большинстве задач данные **добавляются в конец** и **читаются последовательно**. Slice отлично это делает: добавление — амортизированное O(1), чтение — O(1) с кэш-локальностью.

**2. Указатели делают список дорогим по памяти.**

Каждый узел списка — это отдельный объект в куче. Плюс указатель. Плюс накладные расходы аллокатора. Slice хранит данные в непрерывном блоке — минимум накладных расходов.

**3. Кэш-локальность.**

Slice быстрее при последовательном обходе. А последовательный обход — самый частый сценарий.

**4. GC-нагрузка.**

Каждый узел списка — отдельный объект для сборщика мусора. Миллион узлов — миллион объектов для GC. Slice — один объект (массив).

**Когда `container/list` всё-таки нужен:**

- Задача, где нужно часто вставлять/удалять в середину **по указателю**.
- Структуры, где O(1) на перемещение элемента критично (LRU cache).
- Когда размер элементов большой и копирование при сдвиге слишком дорогое.

### 🧪 Практика: сравниваем скорость

Измерим, насколько slice быстрее списка при последовательном обходе:

```go
package main

import (
    "container/list"
    "fmt"
    "time"
)

func main() {
    const n = 10_000_000

    // Slice
    s := make([]int, n)
    for i := range s {
        s[i] = i
    }

    start := time.Now()
    sum := 0
    for _, v := range s {
        sum += v
    }
    sliceTime := time.Since(start)

    // Связный список (container/list)
    l := list.New()
    for i := 0; i < n; i++ {
        l.PushBack(i)
    }

    start = time.Now()
    sum = 0
    for e := l.Front(); e != nil; e = e.Next() {
        sum += e.Value.(int)
    }
    listTime := time.Since(start)

    fmt.Printf("Slice: %v\n", sliceTime)
    fmt.Printf("List:  %v\n", listTime)
    fmt.Printf("List медленнее в %.1f раз\n", float64(listTime)/float64(sliceTime))
}
```

**Примерный вывод:**

```
Slice: 8ms
List:  450ms
List медленнее в 56.2 раз
```

Оба — O(n). Но разница в 56 раз из-за кэш-локальности.

### 📊 Итоговая таблица выбора

| Сценарий | Что выбрать | Почему |
|:---|:---|:---|
| Доступ по индексу | Массив/Slice | O(1) vs O(n) |
| Последовательный обход | Массив/Slice | Кэш-локальность |
| Добавление в конец | Slice | Амортизированное O(1) |
| Вставка в начало | Связный список | O(1) vs O(n) |
| Вставка в середину (по указателю) | Связный список | O(1) vs O(n) |
| Частые перестановки | Связный список | Нет сдвигов |
| LRU Cache | Двусвязный список + map | Нужен порядок + O(1) доступ |
| Хранение фиксированных данных | Массив | Минимум накладных расходов |

### 💡 Что мы узнали?

- Массив выигрывает по доступу по индексу, кэш-локальности и экономии памяти.
- Связный список выигрывает по вставке/удалению в начало и середину (при наличии указателя).
- В Go slice покрывает большинство сценариев, поэтому `container/list` редко нужен.
- LRU Cache — классический случай, где связный список незаменим.
- Выбор структуры — это **компромисс**: ты жертвуешь одним, чтобы получить другое.

## 2.6 Паттерны: быстрый и медленный указатель, разворот, слияние

### 🔌 Проблема: задачи на связные списки — это не только обход

Ты прошёл 30 задач на связные списки. Значит, ты уже сталкивался с типовыми сценариями: найти середину, определить цикл, развернуть список, слить два отсортированных списка.

Эти сценарии решаются не перебором, а **паттернами** — проверенными шаблонами, которые работают для целого класса задач. В этой подглаве мы разберём три ключевых паттерна:

1. **Быстрый и медленный указатель** (fast and slow pointer).
2. **Разворот списка** (reverse linked list).
3. **Слияние двух списков** (merge two sorted lists).

Каждый паттерн — это не просто «как написать код», а **образ мышления**: как увидеть задачу и сразу понять, какой паттерн применить.

### 📊 Паттерн 1: Быстрый и медленный указатель

**Идея:** два указателя двигаются по списку с разной скоростью. Медленный (`slow`) — один шаг за раз. Быстрый (`fast`) — два шага за раз.

```
Шаг 0: slow = head, fast = head
Шаг 1: slow = slow.Next, fast = fast.Next.Next
Шаг 2: slow = slow.Next, fast = fast.Next.Next
...
```

Когда `fast` достигнет конца списка, `slow` будет **ровно посередине**. Почему? Потому что `fast` двигается в два раза быстрее — он проходит два узла, пока `slow` проходит один.

#### 🔬 Задача 1: Найти середину списка

```go
func middleNode(head *Node) *Node {
    slow, fast := head, head
    
    for fast != nil && fast.Next != nil {
        slow = slow.Next       // один шаг
        fast = fast.Next.Next  // два шага
    }
    
    return slow // slow — посередине
}
```

**Что происходит:**

- Когда `fast` прошёл 2n узлов, `slow` прошёл n узлов.
- Если в списке 5 узлов: slow остановится на 3-м узле (0-indexed: на индексе 2).
- Если в списке 6 узлов: slow остановится на 4-м узле (индекс 3).

**Сложность:** O(n) по времени, O(1) по памяти.

#### 🔬 Задача 2: Определить цикл в списке

Классическая задача: определить, есть ли в списке цикл (узел, указывающий на предыдущий).

**Идея:** если `fast` и `slow` когда-нибудь встретятся — цикл есть. Если `fast` достиг конца (`nil`) — цикла нет.

```go
func hasCycle(head *Node) bool {
    slow, fast := head, head
    
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
        
        if slow == fast {
            return true // встретились — есть цикл
        }
    }
    
    return false // fast достиг конца — цикла нет
}
```

**Почему это работает:**

- Если цикла нет: `fast` рано или поздно станет `nil`, цикл завершится.
- Если цикл есть: `fast` и `slow` оба бегают по кругу. `fast` двигается быстрее, поэтому **догоняет** `slow`. Когда они встречаются — цикл подтверждён.

#### 🔬 Задача 3: Найти начало цикла

Усложнение: не просто определить цикл, а найти узел, с которого он начинается.

**Алгоритм Флойда (Floyd's cycle detection):**

1. Двигаем `slow` и `fast`, пока они не встретятся (если цикла нет — возвращаем nil).
2. Перемещаем `slow` на `head`, оставляем `fast` на точке встречи.
3. Двигаем оба на один шаг. Когда они встретятся — это и есть начало цикла.

```go
func detectCycle(head *Node) *Node {
    slow, fast := head, head
    
    // Шаг 1: ищем точку встречи
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
        
        if slow == fast {
            // Шаг 2: сбрасываем slow на head
            slow = head
            
            // Шаг 3: двигаем оба на один шаг
            for slow != fast {
                slow = slow.Next
                fast = fast.Next
            }
            
            return slow // начало цикла
        }
    }
    
    return nil // цикла нет
}
```

**Почему это работает:** математическое доказательство через расстояния. Не будем углубляться — просто запомни: **алгоритм Флойда находит начало цикла за O(n) без дополнительной памяти**.

### 📊 Паттерн 2: Разворот списка

**Идея:** развернуть список — значит изменить направление всех указателей.

```
До разворота:
head → [1] → [2] → [3] → nil

После разворота:
head → [3] → [2] → [1] → nil
```

**Алгоритм:** три указателя — `prev`, `cur`, `next`.

```go
func reverseList(head *Node) *Node {
    var prev *Node
    cur := head
    
    for cur != nil {
        next := cur.Next  // сохраняем следующий узел
        cur.Next = prev   // разворачиваем указатель
        prev = cur        // двигаем prev вперёд
        cur = next        // двигаем cur вперёд
    }
    
    return prev // новая голова
}
```

**Пошагово:**

```
Начало:
prev = nil, cur = [1] → [2] → [3] → nil

Итерация 1:
next = [2]
cur.Next = nil  (развернули)
prev = [1]
cur = [2]
Список: [1] → nil   |   [2] → [3] → nil

Итерация 2:
next = [3]
cur.Next = [1]  (развернули)
prev = [2]
cur = [3]
Список: [2] → [1] → nil   |   [3] → nil

Итерация 3:
next = nil
cur.Next = [2]  (развернули)
prev = [3]
cur = nil
Список: [3] → [2] → [1] → nil

Готово. prev = [3] — новая голова.
```

**Сложность:** O(n) по времени, O(1) по памяти.

**Когда применяется:** задачи, где нужно обработать список с конца, или где нужно «перевернуть» порядок.

### 📊 Паттерн 3: Слияние двух отсортированных списков

**Идея:** два указателя идут по двум спискам, на каждом шаге выбираем меньший элемент.

```go
func mergeTwoLists(l1, l2 *Node) *Node {
    dummy := &Node{} // фиктивный узел-заглушка
    cur := dummy
    
    for l1 != nil && l2 != nil {
        if l1.Value < l2.Value {
            cur.Next = l1
            l1 = l1.Next
        } else {
            cur.Next = l2
            l2 = l2.Next
        }
        cur = cur.Next
    }
    
    // Добавляем оставшиеся элементы
    if l1 != nil {
        cur.Next = l1
    } else {
        cur.Next = l2
    }
    
    return dummy.Next // реальная голова
}
```

**Пошагово:**

```
l1: [1] → [3] → [5] → nil
l2: [2] → [4] → [6] → nil

dummy → nil
cur = dummy

Шаг 1: 1 < 2 → cur.Next = [1], l1 = [3]
dummy → [1] → ...
cur = [1]

Шаг 2: 3 > 2 → cur.Next = [2], l2 = [4]
dummy → [1] → [2] → ...
cur = [2]

Шаг 3: 3 < 4 → cur.Next = [3], l1 = [5]
dummy → [1] → [2] → [3] → ...
cur = [3]

... и так далее
```

**Сложность:** O(n + m) по времени, где n и m — длины списков. O(1) по дополнительной памяти.

**Когда применяется:** задача «merge two sorted lists» — базовая. Более сложная — «merge k sorted lists» (нужна куча, Глава 10).

### 🧪 Практика: применяем паттерны

Разберём классическую задачу: **определить, является ли список палиндромом**.

**Задача:** `[1] → [2] → [2] → [1]` — палиндром. `[1] → [2] → [3]` — нет.

**Решение через паттерны:**

1. Найти середину (быстрый и медленный указатель).
2. Развернуть вторую половину (разворот списка).
3. Сравнить первую и вторую половины.

```go
func isPalindrome(head *Node) bool {
    if head == nil || head.Next == nil {
        return true
    }
    
    // 1. Находим середину
    slow, fast := head, head
    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next
    }
    
    // 2. Разворачиваем вторую половину
    secondHalf := reverseList(slow)
    firstHalf := head
    
    // 3. Сравниваем
    for secondHalf != nil {
        if firstHalf.Value != secondHalf.Value {
            return false
        }
        firstHalf = firstHalf.Next
        secondHalf = secondHalf.Next
    }
    
    return true
}
```

**Сложность:** O(n) по времени, O(1) по памяти.

### 💡 Что мы узнали?

- **Быстрый и медленный указатель:** середина списка, цикл, начало цикла — всё за O(n) и O(1).
- **Разворот списка:** три указателя — prev, cur, next.
- **Слияние:** dummy-узел + два указателя.
- Паттерны **комбинируются** для решения сложных задач (палиндром).
- Сложность паттернов — O(n) по времени, O(1) по памяти.

### 📝 Задача 1: Удалить N-й узел с конца списка

**Формулировка:** дан связный список и число n. Удали n-й узел с конца и верни голову.

**Пример:**

```
Список: [1] → [2] → [3] → [4] → [5], n = 2
После удаления 2-го с конца (узел 4): [1] → [2] → [3] → [5]
```

**Подход:**

Наивное решение: два прохода. Первый — посчитать длину списка, второй — дойти до (длина - n)-го узла и удалить. Сложность: O(n) + O(n) = O(n), но два прохода.

Лучшее решение: **быстрый и медленный указатель**. Двигаем `fast` на n шагов вперёд. Затем двигаем `fast` и `slow` одновременно, пока `fast` не достигнет конца. Тогда `slow` окажется **ровно перед удаляемым узлом**.

**Правильный алгоритм:**

1. Создаём dummy-узел перед головой. Это нужно для случая, когда удаляем саму голову.
2. Двигаем `fast` на n+1 шагов вперёд от dummy.
3. Двигаем `slow` и `fast` одновременно, пока `fast` не станет nil.
4. Тогда `slow` будет **перед** удаляемым узлом.
5. Удаляем: `slow.Next = slow.Next.Next`.

**Код:**

```go
func removeNthFromEnd(head *Node, n int) *Node {
    dummy := &Node{Next: head}
    slow, fast := dummy, dummy
    
    // Двигаем fast на n+1 шагов вперёд
    for i := 0; i <= n; i++ {
        fast = fast.Next
    }
    
    // Двигаем оба, пока fast не достигнет конца
    for fast != nil {
        slow = slow.Next
        fast = fast.Next
    }
    
    // slow — перед удаляемым узлом
    slow.Next = slow.Next.Next
    
    return dummy.Next
}
```

**Разбор на примере:**

```
Список: dummy → [1] → [2] → [3] → [4] → [5], n = 2

Шаг 1: fast двигаем на 3 шага (n+1 = 3)
slow = dummy, fast = [3]

Шаг 2: двигаем оба
slow = dummy, fast = [3]
slow = [1], fast = [4]
slow = [2], fast = [5]
slow = [3], fast = nil

slow = [3], удаляем slow.Next = [4]
Результат: [1] → [2] → [3] → [5]
```

**Почему dummy-узел важен:** если нужно удалить голову (n = длина списка), без dummy было бы некуда повесить указатель. Dummy даёт «точку опоры» перед головой.

**Сложность:** O(n) по времени (один проход), O(1) по памяти.

### 📝 Задача 2: Пересечение двух списков

**Формулировка:** даны два односвязных списка. Определи, пересекаются ли они, и найди узел пересечения.

**Пример:**

```
Список A: a1 → a2
                  ↘
                   c1 → c2 → c3
                  ↗
Список B: b1 → b2 → b3

Пересечение: c1
```

**Подход:**

Списки могут иметь разную длину. Если мы будем идти по обоим одновременно, то пропустим пересечение, потому что один список длиннее другого.

**Идея:** выровнять списки по длине.

1. Посчитать длины обоих списков.
2. Двигаем указатель более длинного списка вперёд на разницу длин.
3. Двигаем оба указателя одновременно — когда они встретятся, это пересечение.

**Код:**

```go
func getIntersectionNode(headA, headB *Node) *Node {
    lenA := length(headA)
    lenB := length(headB)
    
    // Выравниваем списки
    for lenA > lenB {
        headA = headA.Next
        lenA--
    }
    for lenB > lenA {
        headB = headB.Next
        lenB--
    }
    
    // Ищем пересечение
    for headA != headB {
        headA = headA.Next
        headB = headB.Next
    }
    
    return headA // nil, если нет пересечения
}
```

**Сложность:** O(n + m) по времени, O(1) по памяти.

### 📝 Задача 3: Слить k отсортированных списков

**Формулировка:** дан массив из k отсортированных связных списков. Слей их в один отсортированный список.

**Пример:**

```
Вход: [[1→4→5], [1→3→4], [2→6]]
Выход: [1→1→2→3→4→4→5→6]
```

**Подход 1: Последовательное слияние**

Сливаем первый со вторым, результат с третьим, и так далее.

```go
func mergeKLists(lists []*Node) *Node {
    var result *Node
    
    for _, list := range lists {
        result = mergeTwoLists(result, list)
    }
    
    return result
}
```

**Сложность:** O(k · N), где N — суммарное количество узлов. Почему: каждый раз мы проходим по уже слитой части заново. Если k велико — медленно.

**Подход 2: Разделяй и властвуй**

Сливаем списки попарно, как в merge sort.

```go
func mergeKLists(lists []*Node) *Node {
    if len(lists) == 0 {
        return nil
    }
    
    for len(lists) > 1 {
        var merged []*Node
        
        for i := 0; i < len(lists); i += 2 {
            if i+1 < len(lists) {
                merged = append(merged, mergeTwoLists(lists[i], lists[i+1]))
            } else {
                merged = append(merged, lists[i])
            }
        }
        
        lists = merged
    }
    
    return lists[0]
}
```

**Сложность:** O(N log k). Почему: на каждом уровне мы проходим по всем N узлов, уровней — log k.

**Подход 3: Куча (оптимальный)**

Используем min-heap для выбора минимального элемента среди голов всех списков. Это O(N log k), но эффективнее по константе. Разберём в Главе 10, когда дойдём до куч.

### 📝 Задача 4: Копирование списка со случайным указателем

**Формулировка:** дан связный список, где каждый узел имеет указатель `Next` и указатель `Random` на **произвольный** узел списка (или nil). Создай **глубокую копию** списка.

**Пример:**

```
Оригинал:
[1] → [2] → [3]
Random:
[1].Random → [3]
[2].Random → [1]
[3].Random → nil
```

**Подход 1: Хеш-таблица**

Создаём map: старый узел → новый узел. Проходим два раза: сначала создаём все узлы, потом расставляем указатели.

```go
type NodeWithRandom struct {
    Value  int
    Next   *NodeWithRandom
    Random *NodeWithRandom
}

func copyRandomList(head *NodeWithRandom) *NodeWithRandom {
    if head == nil {
        return nil
    }
    
    // Map: старый узел → новый узел
    m := make(map[*NodeWithRandom]*NodeWithRandom)
    
    // Проход 1: создаём копии всех узлов
    for cur := head; cur != nil; cur = cur.Next {
        m[cur] = &NodeWithRandom{Value: cur.Value}
    }
    
    // Проход 2: расставляем указатели
    for cur := head; cur != nil; cur = cur.Next {
        m[cur].Next = m[cur.Next]       // может быть nil — это норм
        m[cur].Random = m[cur.Random]   // может быть nil — это норм
    }
    
    return m[head]
}
```

**Сложность:** O(n) по времени, O(n) по памяти (хеш-таблица).

**Подход 2: Без дополнительной памяти (O(1) по памяти)**

Хитрый алгоритм: вставляем копии узлов **рядом** с оригиналами, расставляем Random, потом разделяем списки. Разберём его в Главе 4, когда будем говорить про хеш-таблицы и пространственные оптимизации.

---

### 💡 Что мы узнали?

- **Удаление N-го с конца:** быстрый и медленный указатель + dummy-узел.
- **Пересечение списков:** выравнивание по длине.
- **Слияние k списков:** разделяй и властвуй (а лучше — куча, Глава 10).
- **Копирование со случайным указателем:** хеш-таблица (а лучше — O(1) по памяти, Глава 4).
- Каждая задача — это **паттерн**, а не уникальное решение.

## 2.8 Итог: что мы узнали о массивах и списках

Мы начали с пролога: связный список, который тормозил из-за выбора неправильной структуры. Мы узнали, что выбор структуры — это **компромисс** между операциями, которые ты выполняешь чаще всего.

Теперь у нас есть полная картина:

1. **Массив** — непрерывный блок памяти. O(1) на доступ по индексу, O(n) на вставку/удаление в середину. Кэш-локальность.
2. **Slice** — динамический массив. Амортизированное O(1) на добавление в конец.
3. **Связный список** — цепочка узлов с указателями. O(1) на вставку/удаление при наличии указателя, O(n) на доступ по индексу.
4. **Кэш-локальность** — причина, почему массивы быстрее списков при последовательном обходе.
5. **Паттерны** — быстрый/медленный указатель, разворот, слияние.
6. **Практика** — удаление N-го с конца, пересечение, слияние k списков, копирование со случайным указателем.

Это фундамент. Теперь, когда ты видишь задачу, ты не просто думаешь «массив или список», а понимаешь **почему** и **какие компромиссы** стоят за выбором.

---

## Глоссарий

| Термин | Определение |
|:---|:---|
| **Массив** | Непрерывный блок памяти. Доступ по индексу O(1). |
| **Слайс (slice)** | Динамический массив в Go. Структура: ptr, len, cap. |
| **Связный список** | Цепочка узлов. Каждый узел содержит данные и указатель. |
| **Узел** | Элемент связного списка: данные + указатель(и). |
| **Голова (head)** | Первый узел списка. |
| **Кэш-локальность** | Свойство доступа к соседним ячейкам памяти. |
| **Строка кэша** | Блок памяти (64 байта), который процессор читает за раз. |
| **Промах кэша** | Обращение к данным, которых нет в кэше. Требует чтения из RAM. |
| **Prefetching** | Предзагрузка данных в кэш процессором. |
| **Амортизированная O(1)** | Средняя стоимость операции по последовательности операций. |
| **Dummy-узел** | Фиктивный узел-заглушка для упрощения граничных случаев. |
| **Двусвязный список** | Список, где каждый узел указывает на следующий и предыдущий. |
| **Кольцевой список** | Список, где последний узел указывает на первый. |
| **LRU Cache** | Кэш, вытесняющий наименее недавно использованные элементы. |

## Что мы узнали?

- Массив — непрерывный блок памяти, O(1) на доступ по индексу.
- Связный список — цепочка узлов, O(1) на вставку при наличии указателя.
- Slice — динамический массив с амортизированной O(1) на добавление.
- Кэш-локальность — причина, почему массивы быстрее списков в 50–100 раз.
- Паттерны (быстрый/медленный указатель, разворот, слияние) решают большинство задач на списки.
- Выбор структуры — компромисс между операциями доступа и изменения.

---

## Типичные ошибки

- ❌ **Использовать связный список для доступа по индексу.** O(n) вместо O(1) у массива.
- ❌ **Использовать массив для частых вставок в начало.** O(n) вместо O(1) у списка.
- ❌ **Забывать, что вставка в середину списка требует поиска места.** Сама вставка O(1), но поиск O(n).
- ❌ **Думать, что `append` в Go всегда O(1).** При расширении это O(n). Амортизированно — O(1).
- ❌ **Игнорировать кэш-локальность.** Массив быстрее списка при обходе даже если оба O(n).
- ❌ **Забывать про dummy-узел.** Без него граничные случаи (удаление головы) становятся сложнее.
- ❌ **Копировать данные через срез без понимания, что это «окно» в тот же массив.**

---

## Для быстрого повторения

- **Массив:** O(1) доступ, O(n) вставка/удаление в середину, кэш-локальность.
- **Slice:** ptr + len + cap. Расширение в 2 раза (до 1024), потом в 1.25. Амортизированное O(1) на append.
- **Список:** O(1) вставка при указателе, O(n) доступ по индексу.
- **Кэш:** строка 64 байта. Массив — промах раз на 8 int'ов. Список — промах на каждом узле.
- **Паттерны:** fast/slow (середина, цикл), reverse (три указателя), merge (dummy + два указателя).
- **LRU Cache:** двусвязный список + map (детально в Главе 4).
- **Слияние k списков:** разделяй и властвуй O(N log k) или куча O(N log k) (Глава 10).

## Ответы

**1.** Адрес элемента вычисляется арифметически: `база + индекс × размер_элемента`. Одно умножение и одно сложение — константное время, не зависящее от размера массива. Сравни: в связном списке нужно пройти по цепочке указателей — O(n).

**2.** Кэш-локальность — свойство доступа к соседним ячейкам памяти. Процессор читает память строками по 64 байта. Массив: элементы лежат рядом → при обращении к arr[0] загружаются arr[1]...arr[7] → 7 из 8 обращений из кэша. Список: узлы разбросаны → каждое обращение — промах кэша → чтение из RAM, которое в 50–100 раз медленнее.

**3.** Slice — структура из трёх полей: ptr (указатель на массив), len (текущая длина), cap (ёмкость). При append: если len < cap — элемент записывается в существующий массив (O(1)). Если len == cap — выделяется новый массив в 2 раза больше (до 1024) или в 1.25 раза (после 1024), все элементы копируются (O(n)), ptr обновляется.

**4.** При расширении в 2 раза суммарное копирование за n операций: n/2 + n/4 + ... + 1 = n - 1 = O(n). Средняя стоимость: O(n)/n = O(1). При расширении на фиксированное число k: (n/k) × (n/2) = n²/(2k) → O(n) в среднем. Поэтому расширяются умножением, а не сложением.

**5.** Связный список быстрее при частой вставке/удалении в начало или середину **при наличии указателя на место**. Пример: LRU Cache — перемещение элемента в начало списка O(1), в массиве — O(n) из-за сдвига.

**6.** Два указателя двигаются с разной скоростью: slow — один шаг, fast — два. Когда fast достигает конца, slow — посередине. Если slow и fast встречаются — есть цикл. Решает: поиск середины, определение цикла, поиск начала цикла (алгоритм Флойда).

**7.** Три указателя: prev (предыдущий), cur (текущий), next (следующий). На каждом шаге: `next = cur.Next`, `cur.Next = prev`, `prev = cur`, `cur = next`. После цикла prev — новая голова.

**8.** Dummy-узел — фиктивный узел перед головой. Он упрощает обработку граничных случаев: когда результат пуст или когда нужно вставить в начало. Алгоритм: два указателя l1 и l2, на каждом шаге выбираем меньший элемент, присоединяем к cur, двигаем соответствующий указатель. После цикла добавляем оставшийся список.

**9.** Быстрый и медленный указатель: slow двигается на 1 шаг, fast — на 2. Когда fast достигает конца (fast == nil или fast.Next == nil), slow — посередине.

**10.** Потому что slice покрывает большинство сценариев: добавление в конец (амортизированное O(1)), доступ по индексу (O(1)), кэш-локальность. Список нужен, когда: частые вставки/удаления в середину по указателю, O(1) на перемещение элемента (LRU cache), большие элементы, где копирование дорогое.

В **Главе 3** мы перейдём к **стеку, очереди и деку** — трём линейным структурам, которые строятся **поверх** массивов и списков. Ты увидишь, как из простых блоков собираются более сложные структуры, и как они применяются в реальных задачах: парсинг выражений, undo-механизмы, планировщики задач, обходы графов.

Погнали. 🚀
