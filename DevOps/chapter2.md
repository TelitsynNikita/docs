## 2.0 Пролог: контейнер, который не запускается

Ты написал Go-приложение. Упаковал в Docker-образ. Отправил в registry. На сервере запустил:

```bash
docker run -d --name myapp -p 8080:8080 myapp:latest
```

Контейнер стартовал и... через 3 секунды упал. Ты смотришь логи:

```bash
docker logs myapp
# standard_init_linux.go:228: exec user process caused: exec format error
```

Что это значит? Ты собрал образ на маке с процессором Apple Silicon (ARM64), а сервер работает на x86_64. Бинарник внутри образа скомпилирован под ARM — он не может выполниться на x86.

Или другая ситуация. Контейнер работает, но приложение внутри не может подключиться к базе данных на хосте:

```
dial tcp 127.0.0.1:5432: connect: connection refused
```

Ты думаешь: «База же на хосте, слушает localhost:5432». Но контейнер — это изолированное окружение. Его `localhost` — это **не** localhost хоста. Это отдельный network namespace (вспомни подглаву 1.4).

Или ещё. Ты запустил контейнер, он работает день, два, а на третий падает с OOM. Ты смотришь: на хосте 64 ГБ памяти, свободно 50 ГБ. Но контейнер был запущен с `--memory=512m`, и его cgroup (вспомни подглаву 1.5) исчерпал лимит.

Это — три реальные проблемы DevOps-инженера. И все они решаются пониманием того, **как Docker работает под капотом**.

В Главе 1 мы разобрали фундамент: namespaces, cgroups, сетевой стек, файловую систему. Теперь мы посмотрим, как Docker использует этот фундамент, чтобы создавать контейнеры. Ты увидишь, что Docker — это не магия, а **удобная обёртка над механизмами ядра Linux**.

Начнём с главного вопроса: чем контейнер отличается от виртуальной машины?

## 2.1 Контейнер vs виртуальная машина

### 🔌 Проблема: почему нельзя просто использовать VM

Ты хочешь запустить 10 изолированных приложений на одном сервере. Первое, что приходит в голову — виртуальные машины. Каждой VM — своя ОС, своё ядро, своя память.

Но у VM есть цена:

- **Память.** Каждая VM с Ubuntu Server ест 300–500 МБ только на ядро и системные процессы. 10 VM = 3–5 ГБ потрачено впустую.
- **CPU.** Гипервизор эмулирует железо. Даже с аппаратной виртуализацией (VT-x, AMD-V) есть накладные расходы.
- **Запуск.** VM загружается 30–60 секунд: BIOS → загрузчик → ядро → systemd → сервисы.
- **Диск.** Каждая VM — это образ на несколько гигабайт.

Контейнеры решают эти проблемы. Но как?

### 📊 Сравнение: VM vs контейнер

```
Виртуальная машина:

┌─────────────────────────────────────────┐
│ Приложение A         Приложение B       │
├─────────────────────────────────────────┤
│ ОС (Ubuntu)          ОС (Ubuntu)        │
├─────────────────────────────────────────┤
│ Ядро Linux           Ядро Linux         │
├─────────────────────────────────────────┤
│ Гипервизор (KVM, VMware, Hyper-V)       │
├─────────────────────────────────────────┤
│ Хост-ОС (Linux)                         │
├─────────────────────────────────────────┤
│ Железо (CPU, RAM, диск)                 │
└─────────────────────────────────────────┘

Контейнеры:

┌─────────────────────────────────────────┐
│ Приложение A         Приложение B       │
├─────────────────────────────────────────┤
│ Контейнерный runtime (containerd, runc) │
├─────────────────────────────────────────┤
│ Ядро Linux (одно на всех!)              │
├─────────────────────────────────────────┤
│ Хост-ОС (Linux)                         │
├─────────────────────────────────────────┤
│ Железо (CPU, RAM, диск)                 │
└─────────────────────────────────────────┘
```

**Ключевые отличия:**

| Аспект | VM | Контейнер |
|:---|:---|:---|
| **Ядро** | Своё у каждой VM | Одно на всех (хост-ядро) |
| **Изоляция** | Полная (гипервизор) | namespaces + cgroups |
| **Память** | 300–500 МБ на VM | 5–10 МБ на контейнер |
| **Запуск** | 30–60 секунд | 0.1–0.5 секунды |
| **Размер образа** | Гигабайты | Мегабайты (иногда десятки МБ) |
| **Безопасность** | Выше (своё ядро) | Ниже (общее ядро) |

### 🔬 Что именно делает контейнер контейнером

Когда ты запускаешь `docker run nginx`, Docker:

1. **Скачивает образ** (если его нет локально) — набор слоёв файловой системы.
2. **Создаёт namespaces** (вспомни подглаву 1.4):
   - PID namespace — nginx видит только свои процессы.
   - Mount namespace — nginx видит только файлы из образа.
   - Network namespace — nginx получает свой IP, свой loopback.
   - UTS namespace — hostname контейнера.
   - IPC namespace — изолированная shared memory.
3. **Настраивает cgroups** (вспомни подглаву 1.5):
   - `memory.max` — лимит памяти.
   - `cpu.max` — лимит CPU.
   - `pids.max` — лимит процессов.
4. **Монтирует файловую систему** из слоёв образа (overlayfs).
5. **Запускает процесс** (nginx) внутри этих namespaces.

Процесс nginx внутри контейнера **думает**, что он один в системе. Он видит свой PID 1, свою файловую систему, свою сеть. Но на самом деле — это обычный процесс на хосте.

### 🔍 Как это проверить

Вспомни подглаву 1.4 — мы смотрели namespaces через `lsns` и `/proc/<PID>/ns/`.

**На хосте Linux** (не на маке — там Docker работает внутри VM):

```bash
# 1. Запусти контейнер
docker run -d --name nginx-test nginx

# 2. Найди PID процесса nginx на хосте
docker inspect nginx-test | grep -i pid
# "Pid": 12345

# 3. Посмотри namespaces этого процесса
ls -la /proc/12345/ns/
# Видишь: pid, mnt, net, uts, ipc — все разные от хостовых

# 4. Сравни с хостовым процессом
ls -la /proc/1/ns/
# Другие inode — значит, изолированы

# 5. Посмотри cgroup
cat /proc/12345/cgroup
# 0::/system.slice/docker-<container-id>.scope
```

На маке с Docker Desktop это скрыто внутри VM. Но ты можешь зайти в VM:

```bash
# На маке (Docker Desktop):
docker run -it --privileged --pid=host alpine nsenter -t 1 -m -u -i -n sh
# Это запустит shell внутри VM Docker
# Теперь можно смотреть /proc/<PID>/ns/
```

### 💡 Практика: что это даёт DevOps-инженеру

**1. Понимание ограничений.** Контейнер — это не «лёгкая VM». Это процесс с изолированным окружением. Поэтому:

- Контейнер не имеет своего ядра — он использует ядро хоста. Если ядро падает, падают все контейнеры.
- Контейнер не эмулирует железо — он работает на той же архитектуре (x86_64, ARM64). Образ, собранный под ARM, не запустится на x86.
- Контейнер разделяет ресурсы хоста — если cgroups не настроены, один контейнер съест всё.

**2. Диагностика.** Ты понимаешь, что `docker exec` — это запуск процесса в тех же namespaces. `docker stop` — отправка сигнала PID 1 внутри PID namespace. OOM в контейнере — это событие cgroup.

**3. Безопасность.** Ты знаешь, что namespace — не защита. Для реальной защиты нужны: user namespace, capabilities, seccomp, cgroups. Разберём в Главе 4.

### Где мы сейчас

Мы разобрали, чем контейнер отличается от VM. Контейнер — это процесс с изолированным окружением (namespaces) и ограниченными ресурсами (cgroups). Всё работает на одном ядре Linux.

Теперь посмотрим, **как управлять жизненным циклом контейнера** — запускать, останавливать, смотреть логи, заходить внутрь.

## 2.2 Жизненный цикл контейнера: run, ps, logs, exec, stop, rm

### 🔌 Проблема: контейнер запустился и молчит

Ты запустил свой первый контейнер:

```bash
docker run -d --name myapp myapp:latest
```

Команда вернула какой-то длинный идентификатор:

```
a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a
```

И всё. Никакого вывода. Контейнер работает? Или сразу упал? Как посмотреть, что внутри? Как зайти и проверить?

В этой подглаве мы разберём **жизненный цикл контейнера**: от запуска до удаления. Каждая команда — с флагами, примерами и типичными сценариями.

### 🚀 docker run: запуск контейнера

`docker run` — самая важная команда. Она **создаёт и запускает** контейнер из образа.

**Базовый синтаксис:**

```bash
docker run [OPTIONS] IMAGE [COMMAND] [ARG...]
```

**Самые частые флаги:**

| Флаг | Что делает | Пример |
|:---|:---|:---|
| `-d` | Detached — запустить в фоне | `docker run -d nginx` |
| `--name` | Имя контейнера | `--name myapp` |
| `-p` | Проброс порта (host:container) | `-p 8080:80` |
| `-v` | Монтирование volume | `-v /data:/var/lib/postgresql/data` |
| `-e` | Переменная окружения | `-e POSTGRES_PASSWORD=secret` |
| `--rm` | Удалить после остановки | `--rm` |
| `-it` | Интерактивный режим + TTY | `-it ubuntu bash` |
| `--memory` | Лимит памяти | `--memory=512m` |
| `--cpus` | Лимит CPU | `--cpus=1.5` |
| `--restart` | Политика перезапуска | `--restart=always` |

**Примеры:**

```bash
# Запустить nginx в фоне, пробросить порт 8080 хоста на порт 80 контейнера
docker run -d --name my-nginx -p 8080:80 nginx

# Запустить PostgreSQL с переменными окружения
docker run -d \
  --name my-postgres \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=mydb \
  -p 5432:5432 \
  postgres:16

# Запустить интерактивный контейнер с Ubuntu
docker run -it --rm ubuntu:24.04 bash

# Запустить контейнер, который удалится после остановки
docker run --rm -it alpine sh
```

### 📊 docker ps: смотрим, что запущено

`docker ps` показывает **работающие** контейнеры.

```bash
# Только работающие
docker ps

# Все контейнеры (включая остановленные)
docker ps -a

# Только ID
docker ps -q

# С фильтром по имени
docker ps --filter "name=myapp"

# С фильтром по статусу
docker ps --filter "status=exited"
```

Вывод:

```
CONTAINER ID   IMAGE          COMMAND                  CREATED         STATUS         PORTS                    NAMES
a1b2c3d4e5f6   nginx          "/docker-entrypoint.…"   5 minutes ago   Up 5 minutes   0.0.0.0:8080->80/tcp     my-nginx
```

**Ключевые колонки:**

| Колонка | Что означает |
|:---|:---|
| `CONTAINER ID` | Уникальный ID контейнера (можно использовать первые 12 символов) |
| `IMAGE` | Из какого образа запущен |
| `COMMAND` | Какая команда выполняется внутри |
| `STATUS` | Up (работает), Exited (остановлен), Restarting (перезапускается) |
| `PORTS` | Проброс портов |
| `NAMES` | Имя контейнера |

### 📝 docker logs: что контейнер выводит

Когда контейнер работает в фоне (`-d`), его вывод не виден. Чтобы посмотреть, что он пишет:

```bash
# Все логи
docker logs my-nginx

# Последние 50 строк
docker logs --tail 50 my-nginx

# Логи в реальном времени (как tail -f)
docker logs -f my-nginx

# С таймстампами
docker logs -t my-nginx
```

**Что логируют контейнеры:**

Всё, что процесс пишет в **stdout** и **stderr**, попадает в логи контейнера. Если приложение пишет в файл (`/var/log/app.log`), Docker это **не увидит** — логи нужно писать в stdout.

### 🔍 docker exec: зайти внутрь

`docker exec` запускает **дополнительный процесс** внутри работающего контейнера. Чаще всего — shell:

```bash
# Зайти в контейнер с bash
docker exec -it my-nginx bash

# Зайти с sh (если bash нет)
docker exec -it my-nginx sh

# Выполнить одну команду без интерактивного режима
docker exec my-nginx ls -la /etc/nginx/

# Выполнить команду от другого пользователя
docker exec -u postgres my-postgres psql -c "SELECT 1"
```

**Важно:** `docker exec` работает **только** с работающим контейнером. Если контейнер упал — `exec` не сработает.

### ⏹️ docker stop и docker kill: остановка

`docker stop` отправляет процессу PID 1 внутри контейнера сигнал **SIGTERM** — «пожалуйста, завершись». Даёт 10 секунд на graceful shutdown. Если процесс не завершился — отправляет SIGKILL.

```bash
# Мягкая остановка (SIGTERM → ждать 10 сек → SIGKILL)
docker stop my-nginx

# Остановка с другим таймаутом (5 секунд)
docker stop --time 5 my-nginx

# Жёсткая остановка (сразу SIGKILL)
docker kill my-nginx
```

**Почему это важно:** если приложение внутри контейнера обрабатывает запросы, `docker stop` даёт ему 10 секунд на завершение текущих операций. `docker kill` — мгновенное убийство без шансов сохраниться.

Вспомни подглаву 1.2: сигналы — это то, как systemd и Docker управляют процессами. `docker stop` = `systemctl stop`.

### 🔄 docker restart: перезапуск

```bash
# Перезапустить контейнер
docker restart my-nginx

# Перезапустить с задержкой
docker restart --time 5 my-nginx
```

### 🗑️ docker rm: удаление

`docker rm` удаляет **остановленный** контейнер. Работающий контейнер нужно сначала остановить (или использовать `-f`).

```bash
# Удалить остановленный контейнер
docker rm my-nginx

# Принудительно удалить (сначала stop, потом rm)
docker rm -f my-nginx

# Удалить все остановленные контейнеры
docker container prune
```

### 🧹 docker container prune: уборка

Со временем на диске накапливаются остановленные контейнеры, неиспользуемые образы, dangling volumes.

```bash
# Удалить все остановленные контейнеры
docker container prune

# Удалить все неиспользуемые образы
docker image prune

# Удалить всё неиспользуемое (контейнеры, образы, сети)
docker system prune

# Посмотреть, сколько места занимает Docker
docker system df
```

### 💡 Практика: полный цикл

Попробуй прямо сейчас:

```bash
# 1. Запусти nginx в фоне
docker run -d --name test-nginx -p 8080:80 nginx

# 2. Проверь, что работает
docker ps
# STATUS: Up X seconds

# 3. Сделай запрос
curl localhost:8080
# Вывод: HTML-страница nginx

# 4. Посмотри логи
docker logs test-nginx
# Вывод: access log от curl

# 5. Зайди внутрь
docker exec -it test-nginx bash

# 6. Посмотри процессы внутри
ps aux
# PID 1 — nginx master, остальные — worker'ы
# Ты видишь ТОЛЬКО процессы контейнера (PID namespace!)

# 7. Выйди
exit

# 8. Останови
docker stop test-nginx

# 9. Удали
docker rm test-nginx

# 10. Проверь, что удалён
docker ps -a | grep test-nginx
# (пусто)
```

### 📊 Жизненный цикл контейнера

```
                    ┌──────────────┐
                    │   docker run  │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   Created    │  ← контейнер создан, но не запущен
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   Running    │  ← процесс PID 1 работает
                    └──────┬───────┘
                           │
                ┌──────────┼──────────┐
                │          │          │
                ▼          ▼          ▼
         ┌──────────┐ ┌──────────┐ ┌──────────┐
         │  Paused  │ │  Stopped │ │ Restarting│
         └──────────┘ └────┬─────┘ └──────────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   Deleted    │  ← docker rm
                    └──────────────┘
```

**Состояния:**

| Состояние | Что означает | Как попасть |
|:---|:---|:---|
| `created` | Контейнер создан, но не запущен | `docker create` |
| `running` | Процесс PID 1 работает | `docker run`, `docker start` |
| `paused` | Процессы заморожены | `docker pause` |
| `stopped` | Процесс завершился, данные сохранены | `docker stop`, `docker kill` |
| `restarting` | Контейнер перезапускается | `--restart=always` при падении |
| `deleted` | Контейнер удалён с диска | `docker rm` |

### 💡 Практика: политики перезапуска

`--restart` определяет, что делать, когда контейнер падает:

| Политика | Поведение |
|:---|:---|
| `no` (по умолчанию) | Не перезапускать |
| `always` | Всегда перезапускать (даже после перезагрузки хоста) |
| `unless-stopped` | Перезапускать, если контейнер не был остановлен вручную |
| `on-failure:N` | Перезапускать только при ошибке, максимум N раз |

```bash
# Контейнер, который переживёт перезагрузку хоста
docker run -d --restart=always --name myapp myapp:latest

# Перезапускать при ошибке, но не чаще 3 раз
docker run -d --restart=on-failure:3 --name myapp myapp:latest
```

**Когда использовать:**

- **`always`** — для продакшен-сервисов (база данных, веб-сервер, бэкенд).
- **`on-failure`** — для задач, которые должны завершаться (обработчики, миграции).
- **`no`** — для dev-контейнеров и разовых задач.

### 💡 Практика: как правильно работать с контейнерами

**✅ ОБЯЗАТЕЛЬНО:**

1. **Всегда задавай `--name`.** Иначе Docker сгенерирует случайное имя (`admiring_curie`, `fervent_hopper`), и через час ты не вспомнишь, что это за контейнер:
   ```bash
   docker run -d --name myapp myapp:latest
   ```

2. **Всегда используй `--restart=always` для сервисов.** Если контейнер упадёт ночью, Docker поднимет его. Если хост перезагрузится — Docker тоже поднимет:
   ```bash
   docker run -d --restart=always --name nginx nginx
   ```

3. **Ограничивай ресурсы через `--memory` и `--cpus`.** Иначе один контейнер может съесть всю память хоста:
   ```bash
   docker run -d --memory=512m --cpus=1 --name myapp myapp:latest
   ```

**👍 СТОИТ:**

4. **Используй `--rm` для разовых контейнеров.** Если контейнер нужен только для одной задачи (миграция, тест, дебаг) — пусть удалится автоматически:
   ```bash
   docker run --rm -it alpine sh
   ```

5. **Используй `docker logs -f` во время отладки.** Это как `tail -f` для контейнера — видишь логи в реальном времени:
   ```bash
   docker logs -f myapp
   ```

6. **Пиши логи приложения в stdout, а не в файл.** Docker собирает только stdout/stderr. Файл внутри контейнера ты потеряешь при удалении контейнера.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

7. **`docker pause` / `docker unpause`.** Редко используется. Замораживает процессы через SIGSTOP. Нужно только для специфических сценариев.

8. **`docker create`.** Отдельное создание контейнера без запуска. Обычно `docker run` достаточно.

**❌ НЕ ДЕЛАЙ:**

9. **Не запускай контейнеры от root внутри контейнера.** Если приложение в контейнере работает от root, злоумышленник при взломе получит root на хосте. Используй `USER` в Dockerfile (подглава 2.4).

10. **Не храни данные в контейнере.** Контейнер эфемерен: `docker rm` — и все данные исчезли. Для данных используй volumes (Глава 4).

11. **Не копи файлы в работающий контейнер через `docker cp` как способ «задеплоить».** Это создаёт расхождение между образом и контейнером. Правильный путь — пересобрать образ и перезапустить контейнер.

12. **Не накапливай остановленные контейнеры.** После экспериментов запускай `docker container prune`. Иначе место на диске закончится неожиданно.

### Где мы сейчас

Мы разобрали жизненный цикл контейнера: запуск, просмотр, логи, заход внутрь, остановка, удаление. Это базовые команды, которые ты будешь использовать каждый день.

Теперь посмотрим на **образы** — откуда Docker берёт файловую систему для контейнера. Что такое registry, как качать и загружать образы.

## 2.3 Образы и registry: pull, push, tag

### 🔌 Проблема: откуда Docker берёт файлы для контейнера

Когда ты запускаешь `docker run nginx`, Docker:

1. Ищет образ `nginx` **локально**.
2. Если не находит — **скачивает** из registry (по умолчанию Docker Hub).
3. Создаёт контейнер из скачанного образа.

Образ — это **шаблон файловой системы** для контейнера. Это не один файл, а **набор слоёв** (мы разберём слои в подглаве 2.5). Сейчас важно понять: образ — это то, что **хранится на диске** и из чего **создаются** контейнеры.

**Registry** — это хранилище образов. Docker Hub — публичный registry по умолчанию. Но бывают и приватные: GitLab Container Registry, AWS ECR, GCP GCR, Harbor, Nexus.

### 📦 docker pull: скачать образ

```bash
# Скачать последнюю версию
docker pull nginx

# Скачать конкретную версию
docker pull nginx:1.25

# Скачать с конкретного registry
docker pull registry.example.com/myapp:latest

# Скачать с Docker Hub (явно)
docker pull docker.io/library/nginx:latest
```

**Структура имени образа:**

```
[registry/][namespace/]image[:tag]

registry — откуда качать (по умолчанию docker.io)
namespace — пользователь или организация (по умолчанию library — официальные образы)
image — имя образа
tag — версия (по умолчанию latest)
```

Примеры:

| Полное имя | Registry | Namespace | Image | Tag |
|:---|:---|:---|:---|:---|
| `nginx` | docker.io | library | nginx | latest |
| `nginx:1.25` | docker.io | library | nginx | 1.25 |
| `myuser/myapp:1.0` | docker.io | myuser | myapp | 1.0 |
| `ghcr.io/org/app:v2` | ghcr.io | org | app | v2 |

### 🏷️ docker tag: переименовать образ

`docker tag` создаёт **новую ссылку** на тот же образ. Образ не копируется — просто появляется ещё одно имя.

```bash
# Посмотреть локальные образы
docker images
# REPOSITORY   TAG       IMAGE ID       CREATED         SIZE
# nginx        latest    abc123def456   2 weeks ago     187 MB

# Создать новый тег
docker tag nginx:latest myuser/nginx:1.0

# Теперь один образ имеет два имени
docker images
# REPOSITORY        TAG       IMAGE ID       CREATED         SIZE
# nginx             latest    abc123def456   2 weeks ago     187 MB
# myuser/nginx      1.0       abc123def456   2 weeks ago     187 MB
```

**Обрати внимание:** `IMAGE ID` одинаковый — это **один и тот же образ** с двумя именами.

**Когда использовать:**

- Пометка локального образа перед отправкой в registry.
- Создание читаемых тегов (`v1.0.0`, `stable`, `prod`).

### 📤 docker push: загрузить образ в registry

```bash
# Загрузить в Docker Hub
docker push myuser/nginx:1.0

# Загрузить в другой registry
docker push registry.example.com/myapp:latest
```

**Обязательное условие:** имя образа должно содержать адрес registry. Docker не отправит `nginx:latest` в Docker Hub, если ты не добавишь namespace: `myuser/nginx:latest`.

### 🔐 Авторизация в registry

Для приватных registry нужна авторизация:

```bash
# Войти в Docker Hub
docker login

# Войти в другой registry
docker login registry.example.com
# Username: myuser
# Password: ********

# Посмотреть, куда залогинен
cat ~/.docker/config.json
```

**Для CI/CD:** вместо `docker login` с интерактивным вводом пароля используют переменные окружения:

```bash
echo $REGISTRY_PASSWORD | docker login registry.example.com -u $REGISTRY_USERNAME --password-stdin
```

Это безопаснее: пароль не светится в истории команд.

### 📋 docker images: что скачано

```bash
# Все локальные образы
docker images

# Только ID
docker images -q

# Образы с фильтром
docker images --filter "reference=nginx*"

# Сколько места занимают образы
docker system df
```

### 🗑️ docker rmi: удалить образ

```bash
# Удалить по имени
docker rmi nginx:latest

# Удалить по ID
docker rmi abc123def456

# Принудительно (даже если используется контейнером)
docker rmi -f nginx:latest

# Удалить все неиспользуемые образы
docker image prune
```

**Важно:** нельзя удалить образ, если из него запущен контейнер. Сначала `docker rm` контейнер, потом `docker rmi` образ.

### 🔍 docker inspect: метаданные образа

```bash
# Вся информация об образе
docker inspect nginx:latest

# Конкретные поля
docker inspect --format '{{.Architecture}} {{.Os}}' nginx:latest
# amd64 linux

# Размер образа
docker inspect --format '{{.Size}}' nginx:latest
```

`docker inspect` показывает:

- Архитектуру (amd64, arm64)
- ОС (linux)
- Слои (список SHA-хешей)
- Конфигурацию (CMD, ENTRYPOINT, ENV)
- Дату создания

### 🧪 Практика: полный цикл с образом

```bash
# 1. Скачай образ
docker pull alpine:latest

# 2. Посмотри на него
docker images | grep alpine
# alpine   latest   abc123...   2 weeks ago   7.38 MB

# 3. Создай свой тег
docker tag alpine:latest myuser/alpine:test

# 4. Запусти контейнер
docker run --rm -it myuser/alpine:test sh

# 5. Внутри контейнера проверь, что это Alpine
cat /etc/os-release
# NAME="Alpine Linux"

# 6. Выйди
exit
```

### 💡 Практика: как правильно работать с тегами

**✅ ОБЯЗАТЕЛЬНО:**

1. **Всегда указывай конкретный тег в продакшене.** `nginx:latest` — это «какая-то последняя версия». Сегодня это 1.25, завтра — 1.26 с breaking changes:
   ```bash
   # Плохо:
   docker run -d nginx:latest
   
   # Хорошо:
   docker run -d nginx:1.25.3
   ```

2. **Используй semantic versioning для своих образов:**
   ```bash
   docker build -t myapp:1.4.2 .
   docker tag myapp:1.4.2 myapp:1.4
   docker tag myapp:1.4.2 myapp:latest
   ```

**👍 СТОИТ:**

3. **Используй digest для полной воспроизводимости.** Digest — это SHA-хеш содержимого образа, он не меняется:
   ```bash
   docker pull nginx@sha256:abc123...
   ```
   Tag может указывать на разные версии, digest — всегда на конкретную.

4. **Настрой приватный registry для своих образов.** Не отправляй внутренние образы в публичный Docker Hub (если проект не open source).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Хранить все версии образов локально.** Достаточно последних 2-3. Остальное можно перекачать.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `latest` в docker-compose.yml или в CI/CD.** Ты должен точно знать, какая версия деплоится. `latest` — это сюрприз при каждом деплое.

7. **Не отправляй в registry образы с секретами внутри.** Пароли, ключи, токены, скомпилированные в образ, — это компрометация. Секреты передавай через переменные окружения (Глава 4).

8. **Не качай образы из непроверенных источников.** Образ из интернета может содержать майнер, бэкдор или вирус. Используй официальные образы (`library/*`) или проверенных авторов.

### Где мы сейчас

Мы разобрали образы и registry. Теперь ты знаешь:

- Образ — это шаблон файловой системы для контейнера.
- Registry — хранилище образов (Docker Hub, ECR, GCR, приватные).
- `docker pull` — скачать, `docker push` — загрузить, `docker tag` — переименовать.
- Всегда указывай конкретный тег, а не `latest`.

Теперь самый важный вопрос: **как создать свой образ?** В следующей подглаве мы разберём Dockerfile — рецепт сборки образа.

## 2.4 Dockerfile: FROM, RUN, COPY, CMD, ENTRYPOINT

### 🔌 Проблема: как создать свой образ

До сих пор мы запускали готовые образы: `nginx`, `alpine`, `postgres`. Но как создать **свой** образ с твоим приложением?

Есть два способа:

1. **Ручной (плохой):** запустить контейнер, зайти внутрь, установить всё вручную, сохранить изменения через `docker commit`. Проблема: неповторяемо, непрозрачно, невозможно автоматизировать.

2. **Dockerfile (правильный):** описать все шаги в текстовом файле, собрать образ одной командой. Повторяемо, версионируется в Git, автоматизируется в CI/CD.

**Dockerfile** — это рецепт сборки образа. Текстовый файл с инструкциями, которые Docker выполняет по порядку.

### 📝 Базовый Dockerfile

Вот минимальный Dockerfile для Go-приложения:

```dockerfile
# 1. Базовый образ
FROM golang:1.22-alpine

# 2. Рабочая директория внутри образа
WORKDIR /app

# 3. Копируем файлы проекта
COPY go.mod go.sum ./
COPY . .

# 4. Собираем приложение
RUN go build -o myapp .

# 5. Порт, который слушает приложение
EXPOSE 8080

# 6. Команда запуска
CMD ["./myapp"]
```

Сборка:

```bash
docker build -t myapp:1.0 .
```

Запуск:

```bash
docker run -d -p 8080:8080 myapp:1.0
```

Разберём каждую инструкцию.

### 📦 FROM: базовый образ

`FROM` указывает, **на основе чего** строится образ.

```dockerfile
FROM ubuntu:24.04
FROM golang:1.22-alpine
FROM node:20-slim
FROM scratch
```

**Что такое базовый образ:**

Это готовая файловая система с минимальным набором: ОС (или её часть), пакетный менеджер, библиотеки. Твой образ **наследует** всё, что есть в базовом.

**Популярные базовые образы:**

| Образ | Размер | Для чего |
|:---|:---|:---|
| `ubuntu:24.04` | ~78 МБ | Универсальный, много пакетов |
| `debian:bookworm-slim` | ~30 МБ | Урезанный Debian |
| `alpine:latest` | ~7 МБ | Минимальный, на musl libc |
| `golang:1.22-alpine` | ~250 МБ | Go-разработка |
| `scratch` | 0 байт | Пустой образ (для статически слинкованных бинарников) |

**Совет:** выбирай **минимально необходимый** базовый образ. Если приложению нужен только bash и curl — бери `alpine`. Если нужна glibc — `debian-slim`. Не тащи `ubuntu:24.04`, если достаточно `alpine`.

### 📂 WORKDIR: рабочая директория

`WORKDIR` устанавливает **текущую директорию** для всех последующих инструкций.

```dockerfile
WORKDIR /app
```

После этой инструкции все относительные пути (`COPY . .`, `RUN go build`) выполняются в `/app`.

Если директории не существует, Docker создаст её.

**Почему важно:** без `WORKDIR` все команды выполняются в `/` (корень). Файлы размазываются по всей файловой системе.

### 📋 COPY: копирование файлов

`COPY` копирует файлы из **контекста сборки** (папка на твоём маке) в **образ**.

```dockerfile
# Скопировать один файл
COPY go.mod /app/go.mod

# Скопировать несколько файлов
COPY go.mod go.sum /app/

# Скопировать всю папку
COPY . /app/

# Скопировать с переименованием
COPY config.yaml /etc/myapp/config.yaml
```

**Важные нюансы:**

- `COPY . .` копирует **всё**, включая `.git`, `node_modules`, логи, секреты. Используй `.dockerignore` (подглава 2.6), чтобы исключить лишнее.
- `COPY` создаёт **новый слой** — каждый `COPY` кэшируется отдельно (подглава 2.5).
- Не используй `COPY` для секретов (паролей, ключей) — они останутся в слоях образа навсегда.

### ⚙️ RUN: выполнение команд при сборке

`RUN` выполняет команду **во время сборки**. Результат фиксируется в слое образа.

```dockerfile
# Установка пакетов
RUN apt-get update && apt-get install -y curl

# Компиляция
RUN go build -o myapp .

# Создание директории
RUN mkdir -p /data
```

**Важные нюансы:**

- Каждая `RUN` — это **отдельный слой**. Чем больше `RUN`, тем больше слоёв.
- Объединяй команды в одну `RUN`, чтобы уменьшить количество слоёв и очистить мусор:

```dockerfile
# Плохо: 3 слоя, мусор остаётся
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Хорошо: 1 слой, мусор очищен в том же слое
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

### 🚀 CMD и ENTRYPOINT: что запускать

`CMD` и `ENTRYPOINT` определяют, **что запустится**, когда контейнер стартует. Это последние инструкции в Dockerfile.

**Разница:**

| | CMD | ENTRYPOINT |
|:---|:---|:---|
| **Что делает** | Команда по умолчанию | Основная команда |
| **Переопределение** | Легко переопределить при `docker run` | Сложнее (нужен `--entrypoint`) |
| **Формат** | `CMD ["executable", "arg1"]` | `ENTRYPOINT ["executable"]` |
| **Аргументы** | Может быть списком аргументов для ENTRYPOINT | Принимает аргументы от `CMD` или `docker run` |

**Пример 1: Только CMD**

```dockerfile
CMD ["nginx", "-g", "daemon off;"]
```

```bash
docker run myapp                  # запустит nginx -g "daemon off;"
docker run myapp bash             # переопределит: запустит bash
```

**Пример 2: Только ENTRYPOINT**

```dockerfile
ENTRYPOINT ["nginx"]
```

```bash
docker run myapp                  # запустит nginx
docker run myapp -g "daemon off;" # запустит nginx -g "daemon off;"
docker run --entrypoint bash myapp # переопределит: запустит bash
```

**Пример 3: ENTRYPOINT + CMD**

```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
```

```bash
docker run myapp                  # nginx -g "daemon off;"
docker run myapp -t               # nginx -t (CMD переопределён)
```

**Форматы записи:**

```dockerfile
# Exec form (рекомендуется)
CMD ["executable", "arg1", "arg2"]

# Shell form
CMD executable arg1 arg2
```

**Почему exec form лучше:**

- Shell form запускает через `/bin/sh -c`, что добавляет лишний процесс.
- Shell form не обрабатывает сигналы правильно — `docker stop` может не сработать.

### 🔍 Практический пример: Go-приложение

Создай простое Go-приложение и Dockerfile.

**main.go:**

```go
package main

import (
    "fmt"
    "net/http"
)

func handler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintf(w, "Hello from Docker!\n")
}

func main() {
    http.HandleFunc("/", handler)
    http.ListenAndServe(":8080", nil)
}
```

**Dockerfile:**

```dockerfile
FROM golang:1.22-alpine

WORKDIR /app

COPY go.mod ./
COPY . .

RUN go build -o myapp .

EXPOSE 8080

CMD ["./myapp"]
```

**Сборка и запуск:**

```bash
# 1. Собери
docker build -t myapp:1.0 .

# 2. Запусти
docker run -d --name myapp -p 8080:8080 myapp:1.0

# 3. Проверь
curl localhost:8080
# Hello from Docker!

# 4. Останови
docker stop myapp
docker rm myapp
```

### 💡 Практика: как писать Dockerfile правильно

**✅ ОБЯЗАТЕЛЬНО:**

1. **Используй exec form для CMD и ENTRYPOINT:**
   ```dockerfile
   CMD ["./myapp"]        # ✅ правильно
   CMD ./myapp            # ❌ shell form — проблемы с сигналами
   ```

2. **Объединяй RUN-команды в цепочки с `&&`:**
   ```dockerfile
   RUN apt-get update && \
       apt-get install -y curl && \
       rm -rf /var/lib/apt/lists/*
   ```

3. **Указывай конкретный тег базового образа:**
   ```dockerfile
   FROM golang:1.22-alpine   # ✅ конкретно
   FROM golang:latest        # ❌ сюрпризы при обновлении
   ```

**👍 СТОИТ:**

4. **Используй `.dockerignore`** для исключения лишних файлов из контекста (подглава 2.6).

5. **Добавь `EXPOSE`** для документации. Это не пробрасывает порт, но показывает, какой порт слушает приложение.

6. **Указывай `WORKDIR`** всегда, чтобы не зависеть от путей по умолчанию.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

7. **`LABEL`** — метаданные (автор, версия, описание). Полезно для больших команд, но не обязательно.

8. **`ARG`** — переменные сборки. Нужно, если собираешь разные версии из одного Dockerfile.

**❌ НЕ ДЕЛАЙ:**

9. **Не клади секреты в образ.** Никаких паролей, ключей, токенов в `COPY` или `RUN`. Всё, что попало в слой, останется там навсегда — даже если удалить в следующем слое.

10. **Не используй `docker commit`.** Это создаёт неповторяемый образ. Всё через Dockerfile.

11. **Не запускай от root.** Добавь `USER` в конец Dockerfile:
    ```dockerfile
    RUN adduser -D appuser
    USER appuser
    CMD ["./myapp"]
    ```

### Где мы сейчас

Мы разобрали Dockerfile — рецепт сборки образа. Теперь ты знаешь:

- `FROM` — базовый образ.
- `WORKDIR` — рабочая директория.
- `COPY` — копирование файлов из контекста.
- `RUN` — выполнение команд при сборке.
- `CMD` / `ENTRYPOINT` — что запускать при старте.
- Exec form vs shell form.
- Как собрать Go-приложение в образ.

Но мы не ответили на вопрос: **почему сборка иногда быстрая, а иногда медленная?** И почему изменение одной строки в Dockerfile заставляет пересобирать половину образа?

## 2.5 Слои и кэширование: почему сборка быстрая или медленная

### 🔌 Проблема: изменил одну строку — пересобрался весь образ

Ты написал Dockerfile. Собрал образ — заняло 3 минуты. Изменил одну строку в `main.go`. Пересобрал — снова 3 минуты. Хотя изменился только один файл из ста.

Или наоборот: ты запускаешь сборку в CI/CD, и она каждый раз качает все зависимости заново, хотя они не менялись.

Почему так? И как сделать сборку быстрой?

Ответ — в **слоях** и **кэшировании**.

### 📦 Что такое слой

Когда ты собираешь образ через `docker build`, каждая инструкция в Dockerfile создаёт **новый слой**:

```dockerfile
FROM golang:1.22-alpine          # Слой 1 (базовый образ)
WORKDIR /app                      # Слой 2 (метаданные)
COPY go.mod go.sum ./             # Слой 3 (файлы зависимостей)
COPY . .                          # Слой 4 (весь проект)
RUN go build -o myapp .           # Слой 5 (скомпилированный бинарник)
CMD ["./myapp"]                   # Слой 6 (метаданные)
```

**Слой** — это набор изменений файловой системы. Каждый слой:

- Хранит только **разницу** от предыдущего слоя.
- Имеет уникальный SHA-хеш.
- Неизменяем (immutable) после создания.
- Кэшируется отдельно.

**Образ** — это **стек слоёв**. Когда ты запускаешь контейнер, Docker **склеивает** слои в единую файловую систему через **overlayfs** (мы разберём overlayfs подробно в Главе 3).

Посмотреть слои образа:

```bash
docker history myapp:1.0
```

Вывод:

```
IMAGE          CREATED         CREATED BY                                      SIZE
abc123def456   2 minutes ago   CMD ["./myapp"]                                 0B
def456abc123   2 minutes ago   RUN /bin/sh -c go build -o myapp .             12.5MB
ghi789def456   3 minutes ago   COPY . .                                        45.2MB
jkl012ghi345   3 minutes ago   COPY go.mod go.sum ./                          1.8MB
mno345jkl678   1 week ago      WORKDIR /app                                   0B
pqr678mno901   1 week ago      /bin/sh -c apk add --no-cache git              5.3MB
... (слои базового образа golang:1.22-alpine)
```

**Каждая строка — это слой.** Колонка `SIZE` показывает, сколько места занимает слой.

### 🔄 Как работает кэширование

Когда ты запускаешь `docker build`, Docker:

1. Читает Dockerfile сверху вниз.
2. Для каждой инструкции проверяет: **есть ли в кэше слой с такими же параметрами?**
3. Если есть — **использует кэш**, не выполняет инструкцию заново.
4. Если нет — **выполняет инструкцию** и создаёт новый слой.

**Ключевой момент:** как только Docker встречает инструкцию, для которой кэша нет, **все последующие инструкции тоже выполняются заново** — даже если для них кэш есть.

Это называется **инвалидация кэша**.

### 📊 Пример: как инвалидация кэша замедляет сборку

Вот типичный Dockerfile для Node.js:

```dockerfile
FROM node:20-alpine

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm install

COPY . .

CMD ["node", "index.js"]
```

**Первая сборка:** всё выполняется, занимает 5 минут (npm install качает зависимости).

**Вторая сборка (изменил index.js):**

1. `FROM node:20-alpine` — кэш есть ✅
2. `WORKDIR /app` — кэш есть ✅
3. `COPY package.json package-lock.json ./` — файлы не изменились, кэш есть ✅
4. `RUN npm install` — кэш есть ✅ (самый долгий шаг пропущен!)
5. `COPY . .` — **файлы изменились, кэша нет** ❌
6. `CMD ["node", "index.js"]` — **выполняется заново** (но это быстро)

**Итог:** вторая сборка заняла 5 секунд вместо 5 минут.

**Теперь плохой пример:**

```dockerfile
FROM node:20-alpine

WORKDIR /app

COPY . .

RUN npm install

CMD ["node", "index.js"]
```

**Вторая сборка (изменил index.js):**

1. `COPY . .` — **файлы изменились, кэша нет** ❌
2. `RUN npm install` — **выполняется заново** ❌ (5 минут!)
3. `CMD` — выполняется заново

**Итог:** вторая сборка снова 5 минут, потому что `npm install` выполняется при каждом изменении любого файла.

**Правило:** копируй **только файлы зависимостей** → устанавливай зависимости → копируй **остальное**. Тогда изменение кода не инвалидирует кэш зависимостей.

### 📊 Аналогия для Go-приложения

```dockerfile
# Плохо: копируем всё, потом качаем зависимости
FROM golang:1.22-alpine

WORKDIR /app

COPY . .                    # ❌ любое изменение → инвалидация
RUN go mod download         # ❌ качается заново
RUN go build -o myapp .     # ❌ пересобирается

CMD ["./myapp"]
```

```dockerfile
# Хорошо: сначала зависимости, потом код
FROM golang:1.22-alpine

WORKDIR /app

COPY go.mod go.sum ./       # ✅ только файлы зависимостей
RUN go mod download         # ✅ кэшируется, пока go.mod/go.sum не меняются

COPY . .                    # ❌ изменение кода → инвалидация только отсюда
RUN go build -o myapp .     # ❌ пересобирается, но зависимости уже скачаны

CMD ["./myapp"]
```

### 🔧 Как ускорить сборку

**1. Правильный порядок инструкций:**

```
Сначала — что меняется редко, потом — что меняется часто:

1. FROM (базовый образ)
2. Установка системных пакетов (apt-get, apk add)
3. Копирование файлов зависимостей (go.mod, package.json)
4. Установка зависимостей (go mod download, npm install)
5. Копирование исходного кода
6. Компиляция
7. CMD/ENTRYPOINT
```

**2. Используй `.dockerignore`** (подглава 2.6) — чтобы `COPY . .` не копировал лишнее.

**3. Используй `--cache-from` в CI/CD** — чтобы переиспользовать кэш между сборками:

```bash
# В CI/CD: сначала скачай предыдущий образ для кэша
docker pull myapp:latest || true

# Собери с кэшем
docker build \
  --cache-from myapp:latest \
  -t myapp:new \
  .
```

**4. Объединяй RUN-команды** — меньше слоёв = быстрее сборка и меньше размер.

### 🧪 Практика: смотрим на кэш

```bash
# 1. Собери первый раз
docker build -t myapp:1.0 .
# Время: ~3 минуты

# 2. Собери второй раз без изменений
docker build -t myapp:1.0 .
# Время: ~1 секунда
# Все слои: CACHED

# 3. Измени main.go
echo "// change" >> main.go

# 4. Собери третий раз
docker build -t myapp:1.0 .
# Время: ~30 секунд
# Слои до COPY . . : CACHED
# Слои после COPY . . : пересобраны
```

### 💡 Практика: как правильно организовывать Dockerfile

**✅ ОБЯЗАТЕЛЬНО:**

1. **Разделяй зависимости и код:**
   ```dockerfile
   COPY go.mod go.sum ./
   RUN go mod download
   COPY . .
   ```
   Это **главный приём** ускорения сборки. Изменение кода не перекачивает зависимости.

2. **Порядок: от редкого к частому.** Сначала базовый образ, потом системные пакеты, потом зависимости, потом код.

**👍 СТОИТ:**

3. **Используй `--cache-from` в CI/CD** — переиспользование кэша между пайплайнами экономит минуты.

4. **Проверяй `docker history`** — смотри, какие слои занимают больше всего места.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Сквошить слои** (`--squash`). Уменьшает количество слоёв, но делает кэш менее гранулярным. В большинстве случаев не нужно.

**❌ НЕ ДЕЛАЙ:**

6. **Не копируй весь проект до установки зависимостей.** Это убивает кэш:
   ```dockerfile
   COPY . .           # ❌
   RUN go mod download # ❌ каждый раз заново
   ```

7. **Не добавляй `RUN apk update && apk upgrade` в каждый Dockerfile.** Обновление пакетов — это непредсказуемость: сегодня собирается, завтра — нет. Фиксируй версии.

8. **Не храни большие файлы в контексте сборки.** Если в папке есть дамп базы на 2 ГБ и нет `.dockerignore`, Docker будет загружать его при каждой сборке.

### Где мы сейчас

Мы разобрали слои и кэширование. Теперь ты знаешь:

- Каждая инструкция Dockerfile создаёт слой.
- Слои кэшируются, но инвалидируются при изменении.
- Правильный порядок: зависимости → код.
- `--cache-from` для CI/CD.
- `docker history` для анализа слоёв.

В следующей подглаве мы разберём **`.dockerignore`** — как не отправлять лишние файлы в контекст сборки. Это ускоряет сборку и защищает от случайного попадания секретов в образ.

## 2.6 `.dockerignore` и оптимизация контекста сборки

### 🔌 Проблема: в образ попал .git, а сборка занимает вечность

Ты выполняешь:

```bash
docker build -t myapp:1.0 .
```

И Docker начинает **отправлять весь контекст сборки** в демона. Контекст — это папка, которую ты указал в конце команды (`.` — текущая директория).

Внутри папки:

```
.
├── .git/                  ← 500 МБ (вся история коммитов)
├── node_modules/          ← 800 МБ (зависимости)
├── dist/                  ← 200 МБ (результаты сборки)
├── logs/                  ← 50 МБ (логи)
├── secrets/               ← ключи и пароли!
├── main.go
├── go.mod
├── go.sum
└── Dockerfile
```

Docker **отправит всё это** в демона перед началом сборки. На маке это может занять минуты. А `.git` и `secrets/` могут попасть в образ через `COPY . .`.

Решение: файл **`.dockerignore`**.

### 📄 Что такое .dockerignore

`.dockerignore` — это файл в корне контекста сборки, который указывает, **какие файлы и папки НЕ отправлять** в демона.

Синтаксис похож на `.gitignore`:

```dockerignore
# Исключить .git
.git

# Исключить node_modules
node_modules

# Исключить всё в dist
dist/

# Исключить логи
*.log

# Исключить секреты
.env
secrets/
*.pem
*.key

# Исключить README
README.md

# Исключить всё, кроме...
*
!main.go
!go.mod
!go.sum
!Dockerfile
```

### 🔍 Что даёт .dockerignore

**1. Скорость сборки.**

Без `.dockerignore` Docker отправляет 1.5 ГБ контекста. С `.dockerignore` — только 10 МБ нужных файлов. Отправка контекста занимает секунды вместо минут.

**2. Безопасность.**

`secrets/`, `.env`, `*.pem` — всё, что ты не исключил, может попасть в образ через `COPY . .`. А из образа секреты **не достать** (точнее, достать сложно, но возможно — они остаются в слоях). Правило: **что не в образе — того не украдут**.

**3. Предсказуемость.**

Если `.git` попал в контекст, `COPY . .` скопирует его в образ. Образ раздуется на 500 МБ. А если в `.git/config` лежит токен — он тоже попадёт в образ.

### 🔧 Как работает .dockerignore

```bash
docker build -t myapp:1.0 .
```

Что происходит:

1. Docker читает `.dockerignore` в корне контекста.
2. Docker формирует **список исключений**.
3. Docker **упаковывает** контекст (только неисключённые файлы) в tar-архив.
4. Docker отправляет архив в демона.
5. Демон распаковывает и начинает сборку.

**Важно:** `.dockerignore` влияет только на **контекст**, который отправляется в демона. Файлы, исключённые из контекста, **не могут быть скопированы** через `COPY`.

### 📊 Синтаксис .dockerignore

| Паттерн | Что исключает |
|:---|:---|
| `*.log` | Все файлы с расширением `.log` в корне |
| `**/*.log` | Все `.log` файлы на любой глубине |
| `.git` | Папка `.git` в корне |
| `**/.git` | Любая папка `.git` на любой глубине |
| `node_modules/` | Папка `node_modules` |
| `.env` | Файл `.env` |
| `*.pem` | Все `.pem` файлы |
| `!main.go` | Исключение из исключения (включить обратно) |

**Важный нюанс:** `!` (включение) работает только если родительская папка не исключена полностью. Если ты исключил `secrets/`, то `!secrets/public.pem` не сработает — нужно сначала включить папку, потом файл.

### 🧪 Практика: проверяем .dockerignore

**Эксперимент 1: Что отправляется в контекст**

```bash
# 1. Создай тестовую папку
mkdir docker-test && cd docker-test

# 2. Создай большой файл
dd if=/dev/zero of=bigfile bs=1M count=100

# 3. Создай Dockerfile
echo "FROM alpine" > Dockerfile
echo "COPY . /app" >> Dockerfile

# 4. Собери без .dockerignore и засеки время
time docker build -t test:1 .

# 5. Создай .dockerignore
echo "bigfile" > .dockerignore

# 6. Собери с .dockerignore и засеки время
time docker build -t test:2 .

# Разница во времени — это отправка контекста
```

**Эксперимент 2: Секреты в контексте**

```bash
# 1. Создай файл с секретом
echo "API_KEY=super-secret" > .env

# 2. Без .dockerignore
docker build -t test:3 .

# 3. Зайди в образ и проверь
docker run --rm test:3 cat /app/.env
# API_KEY=super-secret  ← секрет в образе!

# 4. Добавь .env в .dockerignore
echo ".env" > .dockerignore

# 5. Пересобери
docker build -t test:4 .

# 6. Проверь
docker run --rm test:4 cat /app/.env
# cat: can't open '/app/.env': No such file or directory  ← секрета нет
```

```dockerignore
# VCS
.git
.gitignore

# Логи
*.log
logs/

# Артефакты сборки

build/
```

### 💡 Практика: что делать, а что нет

**✅ ОБЯЗАТЕЛЬНО:**

1. **Всегда создавай `.dockerignore` в корне проекта.** Даже если кажется, что там нечего исключать. Лучше пустой, чем никакого.

2. **Исключай секреты первыми строками:**
   ```dockerignore
   .env
   .env.*
   *.pem
   *.key
   secrets/
   credentials/
   ```

3. **Исключай `.git`** — это самая большая папка в большинстве проектов, и она не нужна в образе.

**👍 СТОИТ:**

4. **Исключай артефакты сборки** (`dist/`, `build/`, `bin/`) — они пересобираются внутри образа.

5. **Исключай зависимости** (`node_modules/`, `vendor/`) — они устанавливаются внутри образа.

6. **Проверяй размер контекста** перед сборкой:
   ```bash
   du -sh .           # размер папки
   docker build -t myapp .  # смотри на строку "Sending build context"
   # Sending build context to Docker daemon  10.5MB  ← должно быть маленьким
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

7. **Исключать README.md** — он маленький. Но если хочется чистоты — можно.

**❌ НЕ ДЕЛАЙ:**

8. **Не используй `.dockerignore` как замену правильному порядку COPY.** Даже с `.dockerignore` порядок `COPY . .` → `RUN npm install` — плохой. Используй оба приёма вместе.

9. **Не игнорируй предупреждение «Sending build context».** Если Docker отправляет 1.5 ГБ — значит, `.dockerignore` не работает или отсутствует.

10. **Не исключай файлы, которые нужны для сборки.** Если исключил `go.sum`, а он нужен для `go mod download` — сборка упадёт.

### Где мы сейчас

Мы разобрали `.dockerignore` — последний инструмент оптимизации сборки. Теперь ты знаешь:

- Контекст сборки — это всё, что Docker отправляет в демона.
- `.dockerignore` исключает ненужные файлы из контекста.
- Это ускоряет сборку и защищает от утечки секретов.
- Всегда исключай `.git`, `.env`, `*.pem`, `node_modules/`.

Мы завершили практическую часть Главы 2. В следующей главе мы нырнём **под капот Docker**: overlayfs, containerd, runc, multi-stage builds. Ты поймёшь, как Docker собирает слои в файловую систему и кто на самом деле запускает контейнер.

## Глоссарий

| Термин | Определение |
|:---|:---|
| **Образ (image)** | Шаблон файловой системы для контейнера. Состоит из слоёв. |
| **Контейнер (container)** | Запущенный экземпляр образа. Процесс с изолированным окружением. |
| **Registry** | Хранилище образов (Docker Hub, ECR, GCR, приватные). |
| **Dockerfile** | Текстовый рецепт сборки образа. |
| **Слой (layer)** | Набор изменений файловой системы. Каждая инструкция Dockerfile создаёт слой. |
| **Overlayfs** | Файловая система, склеивающая слои образа в единое представление. |
| **Контекст сборки** | Папка, которую Docker отправляет в демона перед сборкой. |
| **`.dockerignore`** | Файл, исключающий ненужные файлы из контекста сборки. |
| **Кэш слоёв** | Механизм ускорения сборки: неизменённые слои переиспользуются. |
| **Инвалидация кэша** | Ситуация, когда изменение одной инструкции заставляет пересобрать все последующие. |
| **Namespace** | Механизм ядра Linux, изолирующий видимость ресурсов (PID, Mount, Network, UTS, IPC, User). |
| **Cgroup** | Механизм ядра Linux, ограничивающий ресурсы (CPU, память, I/O, PIDs). |
| **Exec form** | Формат записи CMD/ENTRYPOINT в виде JSON-массива: `["executable", "arg"]`. |
| **Shell form** | Формат записи CMD/ENTRYPOINT в виде строки: `executable arg`. Запускается через `/bin/sh -c`. |
| **Digest** | SHA-хеш содержимого образа. Уникален для каждой версии. |
| **Tag** | Человекочитаемая метка образа (например, `1.0`, `latest`). |
| **SIGTERM** | Сигнал «мягкого» завершения процесса. Даёт возможность graceful shutdown. |
| **SIGKILL** | Сигнал немедленного убийства процесса. Не может быть перехвачен. |

---

## Что мы узнали?

- **Контейнер — это не VM.** Это процесс с изолированным окружением (namespaces) и ограниченными ресурсами (cgroups). Всё работает на одном ядре Linux.
- **Жизненный цикл контейнера:** `docker run` → `docker ps` → `docker logs` → `docker exec` → `docker stop` → `docker rm`. Каждая команда решает свою задачу.
- **Образы хранятся в registry.** `docker pull` — скачать, `docker push` — загрузить, `docker tag` — переименовать. Всегда указывай конкретный тег, не `latest`.
- **Dockerfile — рецепт сборки.** FROM, WORKDIR, COPY, RUN, CMD, ENTRYPOINT. Exec form для CMD/ENTRYPOINT.
- **Слои и кэширование.** Каждая инструкция создаёт слой. Слои кэшируются, но инвалидируются при изменении. Правильный порядок: зависимости → код.
- **`.dockerignore`** исключает ненужные файлы из контекста. Ускоряет сборку и защищает от утечки секретов.
- **Логи — в stdout.** Docker собирает только stdout/stderr. Пиши логи в stdout, не в файл.
- **`--restart=always`** для сервисов. Контейнер переживёт падение и перезагрузку хоста.
- **`--memory` и `--cpus`** — обязательные лимиты. Один контейнер не должен съесть весь хост.

## Типичные ошибки

- ❌ **Использовать `latest` в продакшене.** Ты не знаешь, какая версия деплоится. Всегда указывай конкретный тег.
- ❌ **Копировать весь проект до установки зависимостей.** Это убивает кэш: `COPY . .` → `RUN go mod download` перекачивает зависимости при каждом изменении кода.
- ❌ **Писать логи в файл внутри контейнера.** Docker не увидит их. Пиши в stdout/stderr.
- ❌ **Хранить данные в контейнере.** `docker rm` — и данные исчезли. Используй volumes (Глава 4).
- ❌ **Запускать контейнеры без `--memory`.** Один контейнер может съесть всю память хоста и вызвать OOM у других.
- ❌ **Класть секреты в образ.** Пароли, ключи, токены в слоях образа останутся там навсегда. Используй переменные окружения (Глава 4).
- ❌ **Не создавать `.dockerignore`.** `.git`, `node_modules`, `secrets/` попадут в контекст и, возможно, в образ.
- ❌ **Использовать shell form для CMD/ENTRYPOINT.** `CMD ./myapp` вместо `CMD ["./myapp"]` — проблемы с сигналами и лишний процесс.
- ❌ **Использовать `docker commit`.** Неповторяемый, непрозрачный образ. Всё через Dockerfile.
- ❌ **Игнорировать `docker system df`.** Накопление старых образов и контейнеров съедает диск.

## Для быстрого повторения

- **Жизненный цикл:** `docker run -d --name X --restart=always --memory=512m IMAGE` → `docker ps -a` → `docker logs -f X` → `docker exec -it X sh` → `docker stop X` → `docker rm X`.
- **Образы:** `docker pull IMAGE:TAG` → `docker tag SRC DST` → `docker push IMAGE:TAG`. Имя: `[registry/][namespace/]image[:tag]`.
- **Dockerfile:** `FROM` → `WORKDIR` → `COPY deps` → `RUN install` → `COPY .` → `RUN build` → `EXPOSE` → `CMD ["..."]`.
- **Кэш:** слой кэшируется, если инструкция и контекст не изменились. Инвалидация — все последующие слои пересобираются.
- **`.dockerignore`:** исключает `.git`, `.env`, `*.pem`, `node_modules/`, `*.log` из контекста.
- **Exec form:** `CMD ["executable", "arg"]`. Shell form: `CMD executable arg` (не рекомендуется).
- **Политики перезапуска:** `no`, `always`, `unless-stopped`, `on-failure:N`.
- **Лимиты:** `--memory=512m`, `--cpus=1.5`, `--pids-limit=100`.

## Ответы

**1. Контейнер vs VM**

| Аспект | VM | Контейнер |
|:---|:---|:---|
| Ядро | Своё у каждой | Одно на всех (хост-ядро) |
| Изоляция | Гипервизор | namespaces + cgroups |
| Память | 300–500 МБ на VM | 5–10 МБ на контейнер |
| Запуск | 30–60 сек | 0.1–0.5 сек |
| Размер | Гигабайты | Мегабайты |

**2. Что делает `docker run nginx`**

1. Скачивает образ (если нет локально).
2. Создаёт namespaces (PID, Mount, Network, UTS, IPC).
3. Настраивает cgroups (memory.max, cpu.max, pids.max).
4. Монтирует файловую систему из слоёв образа (overlayfs).
5. Запускает процесс nginx внутри namespaces.

**3. Логи, exec, остановка**

```bash
docker logs -f myapp       # логи в реальном времени
docker exec -it myapp bash # зайти внутрь
docker stop myapp          # мягкая остановка (SIGTERM → 10 сек → SIGKILL)
docker rm myapp            # удалить
```

**4. Тег `latest`**

`latest` — это просто тег по умолчанию. Он не означает «последняя стабильная версия». Завтра он может указывать на breaking changes. Использовать: конкретные версии (`1.25.3`), semantic versioning, digest.

**5. Dockerfile для Go**

```dockerfile
FROM golang:1.22-alpine    # базовый образ
WORKDIR /app               # рабочая директория
COPY go.mod go.sum ./      # файлы зависимостей
RUN go mod download        # установка зависимостей
COPY . .                   # исходный код
RUN go build -o myapp .    # компиляция
EXPOSE 8080                # документирование порта
CMD ["./myapp"]            # команда запуска
```

**6. CMD vs ENTRYPOINT**

CMD — команда по умолчанию, легко переопределяется. ENTRYPOINT — основная команда, переопределяется через `--entrypoint`. ENTRYPOINT нужен, когда контейнер — это CLI-инструмент, и аргументы передаются как есть.

**7. Exec form vs shell form**

Exec form: `CMD ["nginx", "-g", "daemon off;"]` — процесс PID 1 получает сигналы правильно. Shell form: `CMD nginx -g "daemon off;"` — запускается через `/bin/sh -c`, сигналы не передаются, лишний процесс.

**8. Слои образа**

Слой — это набор изменений файловой системы. Каждая инструкция Dockerfile создаёт слой. Слои неизменяемы и кэшируются. Посмотреть: `docker history IMAGE`.

**9. Инвалидация кэша**

Когда инструкция меняется (или меняется её контекст), кэш для неё и всех последующих инструкций сбрасывается. Плохо: `COPY . .` → `RUN npm install` (npm install перезапускается при каждом изменении). Хорошо: `COPY package.json` → `RUN npm install` → `COPY . .` (npm install кэшируется).

**10. `.dockerignore`**

Файл, исключающий ненужные файлы из контекста сборки. Исключать: `.git`, `.env`, `*.pem`, `*.key`, `secrets/`, `node_modules/`, `dist/`, `*.log`.

**11. Архитектура образа**

Образ собран под ARM64 (Apple Silicon), сервер x86_64. Решение: `docker build --platform linux/amd64 -t myapp .` или использовать multi-arch сборку (buildx).

**12. `--restart=always`**

Политика перезапуска: контейнер перезапускается при падении и после перезагрузки хоста. Использовать для продакшен-сервисов. Не использовать для разовых задач.

**13. Лимиты ресурсов**

Без лимитов один контейнер может съесть всю память хоста (OOM Killer убьёт другие процессы) или весь CPU (другие контейнеры будут тормозить). Лимиты: `--memory=512m`, `--cpus=1`, `--pids-limit=100`.
