## 1.0 Пролог: первая горутина

Ты пишешь сервис, который обрабатывает заказы. В какой-то момент замечаешь: в хендлере нужно **отправить письмо** клиенту и **записать лог** в аналитику. Оба действия — это HTTP-запросы к внешним сервисам, каждый по 100–200 мс.

Если делать их **последовательно**, хендлер работает 400 мс. Клиент ждёт. Хочется быстрее.

Ты пишешь:

```go
func handleOrder(w http.ResponseWriter, r *http.Request) {
    order := parseOrder(r)
    
    go sendEmail(order)
    go logAnalytics(order)
    
    w.WriteHeader(http.StatusOK)
}
```

Хендлер отвечает мгновенно. Письма уходят. Логи пишутся. Всё быстро и красиво.

Но через неделю приходит алерт: **число горутин растёт**. Через час — OOM. Ты смотришь на код и не понимаешь, что не так.

❓ **Что произошло?** Ты создал горутины, но **никто их не ждёт**. Если `sendEmail` тормозит (внешний сервис лежит), горутины **накапливаются**. Каждая занимает память. Через час их тысячи.

💡 **Что нужно:** понимать, **что такое горутина**, **сколько она стоит**, **как её правильно запустить** и **как её завершить**. Именно этому посвящена глава.

> **Мост к следующим главам:** горутина — фундамент всего конкурентного кода в Go. Каналы (Глава 2), синхронизация (Глава 4), context (Глава 5) — всё работает поверх горутин. Понимание одной горутины даёт понимание всего остального.

## 1.1 Что такое горутина

Горутина — это **лёгкая единица выполнения**, которой управляет **runtime Go**, а не ядро операционной системы.

Чтобы понять разницу, сравним горутину с потоком ОС.

### Поток ОС

Поток — это единица планирования, которой управляет **ядро**. У потока есть:

- Свой стек — обычно **1–8 МБ**, фиксированный.
- Своя структура в ядре — `task_struct` в Linux, ~2 КБ.
- Своя запись в планировщике ядра.

Поток создаётся системным вызовом. Это **дорогая операция**: ядро выделяет память, инициализирует структуры, добавляет поток в очередь.

### Горутина

Горутина — это единица планирования, которой управляет **runtime Go**. У горутины есть:

- Свой стек — начинается с **2 КБ**, растёт по мере необходимости.
- Своя структура `g` — около 300 байт.
- Своё состояние — `_Grunnable`, `_Grunning`, `_Gwaiting` и другие.

Горутина создаётся **внутри runtime**, без системных вызовов. Это **дешёвая операция**: runtime выделяет структуру `g` и стек из пула.

### Сравнение в цифрах

| Характеристика | Поток ОС | Горутина |
|:---|:---|:---|
| Стартовый стек | 1–8 МБ | 2 КБ |
| Максимум стека | Фиксирован | 1 ГБ (растёт динамически) |
| Структура планировщика | `task_struct` в ядре (~2 КБ) | `g` в user space (~300 байт) |
| Создание | Системный вызов | Выделение из пула |
| Время создания | ~10–100 мкс | ~100–300 нс |
| Время переключения | ~1–10 мкс | ~100–200 нс |
| Максимум на процесс | ~10 000 | ~1 000 000 |

Разница — **в 1000 раз по памяти** и **в 50 раз по скорости переключения**.

### Почему горутина дешевле

Поток планируется **ядром**, которое ничего не знает о твоём приложении. Ядро переключает потоки по своим правилам, сохраняя и восстанавливая **все** регистры.

Горутина планируется **runtime Go**, который знает о приложении всё. Runtime знает, когда горутина добровольно отдаёт управление (через канал, `select`, `time.Sleep`), и сохраняет только нужные регистры. Переключение происходит **без системных вызовов** — в user space.

### Аналогия

Представь офис с 10 000 сотрудников (горутин) и 8 столами (ядрами).

**Потоки ОС** — как если бы **директор** (ядро) лично решал, кто из 10 000 сотрудников сейчас работает. Он бегает по офису, говорит «ты работай, ты подожди», и это занимает всё его время.

**Горутины** — как если бы у каждого стола был **менеджер** (runtime), который сам решает, кто из его сотрудников работает. Директор общается только с 8 менеджерами, а не с 10 000 сотрудников.

### 💡 Практика: как думать о горутинах

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: горутина — не поток ОС.** Это лёгкая структура в runtime Go.
2. **Для любой конкурентной задачи — горутину.** `go func()` идиоматичен.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для блокирующих системных вызовов** (файлы, сеть без netpoller) — горутина автоматически «отстёгивается» от потока. Тебе не нужно думать об этом.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **`runtime.LockOSThread()`** — если нужен поток ОС для специфичных задач (OpenGL, C-библиотеки). Редко.

**❌ НЕ ДЕЛАЙ:**

5. **Не создавай потоки ОС вручную.** Для 99.9% задач хватает горутин.
6. **Не бойся создавать много горутин.** Runtime справится.

## 1.2 Что происходит при go func()

Разберём, что делает runtime, когда ты пишешь `go func()`.

### Синтаксис

```go
go func() {
    fmt.Println("hello")
}()
```

Три части:

1. **Ключевое слово `go`** — оператор запуска горутины.
2. **Функция-литерал** `func() { ... }` — что будет выполнено.
3. **Вызов `()`** — немедленный запуск литерала как горутины.

### Схема: что делает runtime

```
go func() { ... }()
   │
   ▼
┌──────────────────────────────────────────────┐
│  runtime.newproc                             │
│                                              │
│  1. Получить структуру g из пула свободных   │
│     (или создать новую)                      │
│                                              │
│  2. Выделить стек 2 КБ из пула стеков        │
│                                              │
│  3. Скопировать аргументы функции            │
│     на стек новой горутины                   │
│                                              │
│  4. Установить точку входа:                  │
│     g.sched.pc = fn                          │
│                                              │
│  5. Пометить как _Grunnable                  │
│                                              │
│  6. Поместить в очередь готовых              │
│     (локальную очередь P или глобальную)     │
│                                              │
│  Время: ~100–300 нс                          │
└──────────────────────────────────────────────┘
   │
   ▼
Горутина в очереди, ждёт планировщика
```

### Ключевое: горутина не запускается сразу

После `go func()` горутина попадает **в очередь** и ждёт, пока планировщик её выберет. Это может произойти:

- Когда текущая горутина **добровольно** отдаст управление (через канал, `select`, `time.Sleep`).
- Когда текущая горутина **принудительно** вытеснена планировщиком.
- Когда текущая горутина **завершится**.

**Практическое следствие:** `go func()` **не гарантирует**, что функция начнёт выполняться сразу. Она лишь **планируется** к выполнению.

### Пример: замыкание и переменные цикла

Частая ошибка — захват переменной цикла:

```go
// ❌ Плохо (Go < 1.22): все горутины увидят последнее значение i
for i := 0; i < 10; i++ {
    go func() {
        fmt.Println(i)
    }()
}

// ✅ Хорошо: передаём i как аргумент
for i := 0; i < 10; i++ {
    go func(i int) {
        fmt.Println(i)
    }(i)
}
```

Начиная с Go 1.22, переменные цикла имеют собственную область видимости, и первый вариант тоже работает. Но **явная передача аргумента** — по-прежнему хорошая практика для ясности.

### 💡 Практика: как использовать go func()

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: `go func()` не гарантирует немедленный запуск.**
2. **Передавай переменные цикла как аргументы** — для ясности.
3. **Помни: аргументы копируются** на стек новой горутины.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Не создавай горутину, если задача быстрее 1 мкс.** Накладные расходы больше выгоды.

**❌ НЕ ДЕЛАЙ:**

5. **Не создавай горутины в бесконечном цикле без ограничения.** Это утечка (см. 1.8).

## 1.3 Стек горутины: 2 КБ, которые растут

Мы сказали: стек горутины начинается с **2 КБ** и **растёт**. Разберём, как.

### Почему 2 КБ, а не 1 МБ

Стек потока ОС обычно 1–8 МБ — выделяется сразу при создании. Это **фиксированный** размер: если потоку нужно больше — программа падает. Если меньше — память всё равно занята.

Стек горутины — **2 КБ**, и он **растёт**. Идея простая: большинство горутин используют мало стека, и выделять им сразу 1 МБ — расточительно.

```
100 000 горутин со стеком 2 КБ = 200 МБ
100 000 горутин со стеком 1 МБ = 100 ГБ ← невозможно
```

Именно поэтому горутины такие дешёвые.

### Как стек растёт

Компилятор вставляет **проверку** в начало каждой функции: не выходит ли указатель стека за границу?

```
Стек 2 КБ:
┌────────────────┐
│                │
│   Свободно     │
│                │
├────────────────┤ stackguard0 (граница)
│ main: данные   │
└────────────────┘ SP
```

Когда стек почти заполнен:

```
┌────────────────┐
│ f3()           │
│ f2()           │
│ f1()           │
│ main: данные   │
└────────────────┘ SP
                 ↑
        SP < stackguard0 → morestack!
```

Вызывается `morestack`, который:

1. Выделяет новый стек **в 2 раза больше**.
2. Копирует старое содержимое на новый стек.
3. Обновляет все указатели, которые ссылались на старый стек.
4. Возвращается к выполнению.

Старый стек возвращается в пул для переиспользования.

### Как часто растёт

Стек **удваивается** при каждом срабатывании `morestack`:

```
2 КБ → 4 КБ → 8 КБ → 16 КБ → 32 КБ → 64 КБ → ... → 1 ГБ
```

**Максимум — 1 ГБ**. Это защита от бесконечной рекурсии.

**На практике:** большинство горутин **никогда не растут**. 2 КБ хватает. Средний размер стека горутины в production — 4–8 КБ.

### Как стек сжимается

Runtime не только растёт, но и **сжимает** стеки. Это происходит во время GC: если горутина использует меньше четверти своего стека, runtime может уменьшить его.

Зачем: если горутина когда-то разрослась до 1 МБ, а потом перестала использовать много стека — нет смысла держать 1 МБ.

### 💡 Практика: как не убить стек

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: стек растёт автоматически.** Не нужно думать о размере.
2. **Помни: максимум 1 ГБ.** Глубокая рекурсия упрётся в этот лимит.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для рекурсивных алгоритмов проверяй глубину.** 100 000 уровней × ~100 байт = 10 МБ. Нормально, но лучше избегать.

**❌ НЕ ДЕЛАЙ:**

4. **Не храни большие массивы на стеке.** `var buf [1 << 20]byte` — 1 МБ на стеке. Лучше в куче.

## 1.4 Жизненный цикл горутины

Горутина, как и любой объект, имеет **жизненный цикл**: создаётся, выполняется, ждёт, завершается.

### Состояния

В runtime Go горутина может находиться в одном из **следующих состояний**:

| Состояние | Что означает |
|:---|:---|
| `_Gidle` | Только что создана, ещё не инициализирована |
| `_Grunnable` | Готова к выполнению, ждёт в очереди |
| `_Grunning` | Выполняется на потоке ОС |
| `_Gsyscall` | Выполняет системный вызов |
| `_Gwaiting` | Заблокирована (канал, mutex, select, `time.Sleep`) |
| `_Gdead` | Завершена, но структура `g` ещё не освобождена |

### Как это выглядит

```
Создание → _Gidle → _Grunnable → _Grunning → _Gdead
                        ↑            │
                        │            │ блокировка
                        │            ▼
                        └────── _Gwaiting
                        
                        │ syscall
                        ▼
                     _Gsyscall
```

### Что важно знать

**При блокировке горутина не занимает поток ОС.** Когда горутина ждёт данные из канала, она переходит в `_Gwaiting`, а поток ОС **освобождается** для других горутин. Именно поэтому 10 000 горутин, делающих HTTP-запросы, не блокируют 10 000 потоков — runtime создаст, скажем, 10–20 потоков.

**При системном вызове P передаётся другому потоку.** Пока один поток ждёт syscall, другой поток берёт его P и продолжает выполнять горутины.

**Завершение горутины — `runtime.goexit`.** Когда функция горутины возвращает управление:

1. Выполняются все отложенные `defer`.
2. Горутина переходит в `_Gdead`.
3. Стек возвращается в пул.
4. Структура `g` помещается в список свободных.

### Главное: main не ждёт горутины

**Критически важно:** если `main` завершится, **все остальные горутины будут убиты** без предупреждения.

```go
func main() {
    go func() {
        time.Sleep(1 * time.Second)
        fmt.Println("never printed")
    }()
    
    // main завершается сразу — программа выходит
}
```

Горутина не успевает напечатать. Программа выходит. `defer` в этой горутине **не выполнится**.

**Как ждать:** `sync.WaitGroup`, каналы, `context`. Разберём в следующих подглавах.

## 1.5 Паттерн: горутина + WaitGroup

Самый распространённый паттерн — запустить горутину и **дождаться** её завершения.

### Проблема

```go
func main() {
    go doWork()
    // main завершается сразу — doWork может не выполниться
}
```

Если `main` не ждёт — горутина убивается.

### Решение: WaitGroup

```go
func main() {
    var wg sync.WaitGroup
    wg.Add(1)
    
    go func() {
        defer wg.Done()
        doWork()
    }()
    
    wg.Wait()  // ждём завершения
}
```

**Что происходит:**

- `wg.Add(1)` — увеличиваем счётчик.
- `defer wg.Done()` — гарантированно уменьшаем счётчик даже при панике.
- `wg.Wait()` — блокируется, пока счётчик не станет 0.

### Схема

```
main:                              Горутина:
  wg.Add(1)                          │
  go func() { ... }() ─────────────► doWork()
  wg.Wait() ← блокируется            │
     │                               │
     │                               │ defer wg.Done()
     │                               ▼
     │                          (счётчик = 0)
     ▼
  продолжается
```

### Несколько горутин

```go
var wg sync.WaitGroup

for i := 0; i < 10; i++ {
    i := i
    wg.Add(1)
    go func() {
        defer wg.Done()
        process(i)
    }()
}

wg.Wait()  // ждём все 10
```

**Ключевое правило:** `Add` вызывается **до** `go func()`. Если вызвать внутри горутины, может быть race: `Wait` увидит счётчик 0 и вернётся раньше.

### Ошибки с WaitGroup

**1. Забыть `wg.Add`.** `Wait` вернётся сразу.

**2. `wg.Add` внутри горутины.**

```go
// ❌ Плохо
go func() {
    wg.Add(1)  // может выполниться после Wait
    defer wg.Done()
    doWork()
}()
wg.Wait()  // может вернуться сразу

// ✅ Хорошо
wg.Add(1)
go func() {
    defer wg.Done()
    doWork()
}()
wg.Wait()
```

**3. Копировать WaitGroup.**

```go
// ❌ Плохо
func process(wg sync.WaitGroup) {  // копия!
    defer wg.Done()
}

// ✅ Хорошо
func process(wg *sync.WaitGroup) {
    defer wg.Done()
}
```

`go vet` ловит копирование.

### 💡 Практика: как использовать WaitGroup

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Add` до `go func()`:**
   ```go
   wg.Add(1)
   go func() { defer wg.Done(); ... }()
   ```

2. **`defer wg.Done()`** — гарантирует вызов даже при панике.

3. **Передавай `*sync.WaitGroup`, не `sync.WaitGroup`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **`go vet ./...` в CI** — ловит копирование.

**❌ НЕ ДЕЛАЙ:**

5. **Не вызывай `Add` внутри горутины после `Wait`.**
6. **Не копируй `WaitGroup`.**

## 1.6 Паттерн: горутина + context

WaitGroup ждёт завершения, но не умеет **отменять** горутины. Если внешний вызов висит — `wg.Wait()` будет ждать вечно.

Для отмены нужен `context.Context`.

### Проблема

```go
func fetch(ctx context.Context) (*Response, error) {
    resp, err := http.Get("https://slow-api.example.com")  // может висеть вечно
    // ...
}
```

Если API тормозит — горутина зависает. Нет способа её прервать.

### Решение: context

```go
func fetch(ctx context.Context) (*Response, error) {
    req, err := http.NewRequestWithContext(ctx, "GET", url, nil)
    if err != nil {
        return nil, err
    }
    resp, err := http.DefaultClient.Do(req)  // отменится при ctx.Done()
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    // ...
}
```

**Что происходит:** если `ctx` отменён — `http.Do` вернёт ошибку `context.Canceled` немедленно. Горутина завершится.

### Полный пример

```go
func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    
    var wg sync.WaitGroup
    wg.Add(1)
    
    go func() {
        defer wg.Done()
        resp, err := fetch(ctx)
        if err != nil {
            log.Println("fetch error:", err)
            return
        }
        _ = resp
    }()
    
    wg.Wait()
}
```

**Что происходит:**

1. `WithTimeout` создаёт контекст на 5 секунд.
2. Горутина получает `ctx`.
3. Если HTTP-запрос длится больше 5 секунд — `ctx.Done()` срабатывает, `http.Do` возвращает ошибку.
4. Горутина завершается, `wg.Wait()` возвращается.

### Схема

```
main:                                Горутина:
  ctx, cancel := WithTimeout(5s)      │
  wg.Add(1)                            │
  go func() { ... }() ───────────────► fetch(ctx)
  wg.Wait() ← ждёт                     │ http.Get с ctx
     │                                 │
     │  через 5 секунд:                │
     │  ctx.Done() закрыт ───────────► http.Do возвращает err
     │                                 │
     │                                 ▼ defer wg.Done()
     ▼
  возвращается
```

### Сочетание WaitGroup + context

**Это самый частый паттерн** в production:

```go
func runWorkers(ctx context.Context, n int) {
    var wg sync.WaitGroup
    for i := 0; i < n; i++ {
        i := i
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return  // отмена
                case task := <-tasksCh:
                    process(ctx, task)
                }
            }
        }()
    }
    wg.Wait()
}
```

**Что происходит:**

- `WaitGroup` ждёт завершения всех воркеров.
- `ctx.Done()` позволяет **отменить** их досрочно.
- `select` реагирует и на отмену, и на новую задачу.

### 💡 Практика: как использовать context

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`context` — первый аргумент функции:**
   ```go
   func fetch(ctx context.Context, url string) (*Response, error)
   ```

2. **`defer cancel()`** — всегда.

3. **Проверяй `ctx.Done()` в `select`** — для отмены.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Передавай `ctx` во все внешние вызовы** (`http.NewRequestWithContext`, `db.QueryContext`).

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `context.Background()` в долгоживущих горутинах** — они не отменятся.
6. **Не забывай `cancel()`** — утечка таймера.

## 1.7 Паттерн: fire-and-forget

Иногда горутину запускают **без ожидания** — «отправить письмо и забыть». Это называется **fire-and-forget**.

### Идея

```go
func handleOrder(w http.ResponseWriter, r *http.Request) {
    order := parseOrder(r)
    
    go sendEmail(order)  // fire-and-forget
    go logAnalytics(order)
    
    w.WriteHeader(http.StatusOK)
}
```

Хендлер отвечает мгновенно. Горутины работают в фоне.

### Когда это уместно

- **Задача не влияет на ответ клиенту.** Email, лог, метрика — клиент не ждёт их завершения.
- **Ошибка некритична.** Если email не уйдёт — не беда (можно повторить позже).
- **Задача короткая.** Несколько секунд.

### Проблема: fire-and-forget без контроля

```go
// ❌ Плохо: горутины накапливаются
for _, order := range orders {
    go sendEmail(order)  // 10 000 goroutine → OOM
}
```

Если `sendEmail` тормозит — горутины копятся. Через час — 10 000 висящих горутин.

### Решение: ограниченный параллелизм

Ограничиваем число одновременных fire-and-forget задач через **семафор**:

```go
var emailSem = make(chan struct{}, 10)  // максимум 10 одновременно

func sendEmailAsync(order Order) {
    select {
    case emailSem <- struct{}{}:
        go func() {
            defer func() { <-emailSem }()
            sendEmail(order)
        }()
    default:
        // семафор полон — не запускаем
        log.Println("email queue full, skipping")
    }
}
```

**Что происходит:**

- Не более 10 горутин одновременно.
- Если семафор полон — задача **не запускается** (можно залогировать или отправить в очередь).
- Нет накопления горутин.

### Fire-and-forget с логированием паник

Fire-and-forget горутина **не должна** ронять программу при панике. Если она упадёт — вся программа умрёт, потому что паника в горутине не восстанавливается из main.

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("panic in background task: %v\n%s", r, debug.Stack())
        }
    }()
    sendEmail(order)
}()
```

**Что происходит:** `recover` внутри горутины ловит панику. Программа **не падает**. Паника логируется.

### Fire-and-forget с логированием ошибок

```go
func sendEmailAsync(order Order) {
    select {
    case emailSem <- struct{}{}:
        go func() {
            defer func() { <-emailSem }()
            defer func() {
                if r := recover(); r != nil {
                    log.Printf("panic: %v", r)
                }
            }()
            if err := sendEmail(order); err != nil {
                log.Printf("send email failed: %v", err)
            }
        }()
    default:
        log.Println("email queue full")
    }
}
```

### Схема

```
handleOrder:
  sendEmailAsync(order)
     │
     │ sem <- struct{}{}     ← захватить слот
     ▼
  go func() ─────────────────► sendEmail(order)
     │                              │
     │                              │ defer <-sem
     │                              │ defer recover
     │                              ▼
     │                          горутина завершилась
     ▼
  хендлер отвечает клиенту
```

### Альтернатива: очередь

Для больших объёмов fire-and-forget лучше использовать **очередь** (Kafka, NATS, Redis). Хендлер пишет в очередь, отдельный consumer обрабатывает.

Но это уже задача не горутин, а инфраструктуры.

### 💡 Практика: как использовать fire-and-forget

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Ограничивай параллелизм** через семафор.
2. **`recover` в каждой fire-and-forget горутине** — чтобы программа не падала.
3. **Логируй ошибки.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для больших объёмов — очередь** вместо горутин.

**❌ НЕ ДЕЛАЙ:**

5. **Не запускай fire-and-forget без ограничения** — утечка.
6. **Не используй fire-and-forget для критичных задач** — потеряются.

## 1.8 Утечки горутин

**Утечка горутин** — самая частая проблема Go-сервисов. Горутина, которая **никогда не завершится**, остаётся в памяти навсегда.

### Простой пример

```go
func leak() {
    ch := make(chan int)  // небуферизованный канал
    
    go func() {
        ch <- 42  // ← горутина ЗАБЛОКИРУЕТСЯ здесь навсегда
    }()
    
    // функция возвращается, не прочитав из канала
}
```

**Что происходит:**

1. Горутина создаётся.
2. Делает `ch <- 42`.
3. Канал небуферизованный, читателя нет — горутина блокируется.
4. Функция `leak()` возвращается.
5. Горутина **никогда не будет разбужена** — читателя нет.
6. **Утечка.**

### Три типичные причины

**1. Канал без читателя.**

```go
ch := make(chan int)
go func() { ch <- 42 }()  // утечка
```

**2. Range по незакрытому каналу.**

```go
ch := make(chan int)
go func() {
    for v := range ch {  // утечка: канал не закрыт
        process(v)
    }
}()
```

**3. HTTP без таймаута.**

```go
go func() {
    resp, _ := http.Get("http://slow-server.com")  // может висеть вечно
    _ = resp
}()
```

### Как исправить

**Для причины 1 — буферизованный канал:**

```go
ch := make(chan int, 1)  // буфер на 1
go func() {
    ch <- 42  // не блокируется
}()
```

**Для причины 2 — закрытие канала владельцем:**

```go
go func() {
    defer close(ch)  // владелец закрывает
    for i := 0; i < 10; i++ {
        ch <- i
    }
}()
```

**Для причины 3 — `context` с таймаутом:**

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

go func() {
    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    resp, err := http.DefaultClient.Do(req)
    // если таймаут — err != nil, горутина завершится
}()
```

### Как обнаружить

**1. `runtime.NumGoroutine()`:**

```go
go func() {
    for range time.Tick(10 * time.Second) {
        log.Printf("goroutines: %d", runtime.NumGoroutine())
    }
}()
```

Если число горутин **растёт и не падает** — утечка.

**2. pprof goroutine dump:**

```bash
curl http://localhost:6060/debug/pprof/goroutine?debug=2
```

Покажет стеки всех горутин. Ищи много горутин в одном состоянии (`chan send`, `chan receive`).

**3. `goleak` в тестах:**

```go
func TestMain(m *testing.M) {
    goleak.VerifyTestMain(m)
}
```

Тест упадёт, если остались горутины.

### 💡 Практика: как не допустить утечек

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Всегда используй `context` для горутин, которые могут жить долго:**
   ```go
   ctx, cancel := context.WithCancel(context.Background())
   defer cancel()
   go worker(ctx)
   ```

2. **Закрывай каналы владельцем** (тем, кто пишет):
   ```go
   go func() {
       defer close(ch)
       // ...
   }()
   ```

3. **Для «отправь и забудь» — буферизованный канал:**
   ```go
   ch := make(chan int, 1)
   ```

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь `runtime.NumGoroutine()` в production.**
5. **Таймауты на все внешние вызовы.**
6. **Используй `goleak` в тестах.**

**❌ НЕ ДЕЛАЙ:**

7. **Не создавай горутину без способа её завершить.**
8. **Не игнорируй `ctx.Done()`** в долгоживущих горутинах.
9. **Не закрывай канал на читателе.**

## 1.9 Практика Go: диагностика горутин

Разберём **три примера**: утечка, диагностика, бенчмарк.

### Пример 1: утечка и как её найти

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    fmt.Printf("goroutines before: %d\n", runtime.NumGoroutine())

    // Утечка: 1000 горутин пишут в канал без читателя
    for i := 0; i < 1000; i++ {
        ch := make(chan int)
        go func() {
            ch <- i
        }()
    }

    time.Sleep(100 * time.Millisecond)
    fmt.Printf("goroutines after: %d\n", runtime.NumGoroutine())

    // Дамп стеков
    buf := make([]byte, 1<<20)
    n := runtime.Stack(buf, true)
    fmt.Printf("goroutine dump (%d bytes):\n%s\n", n, buf[:n])
}
```

**Пример вывода:**

```
goroutines before: 1
goroutines after: 1001
goroutine dump (52345 bytes):
goroutine 1 [running]:
...
goroutine 18 [chan send]:
main.main.func1()
    /path/to/main.go:15 +0x...
created by main.main in goroutine 1
    /path/to/main.go:14 +0x...
... (повторяется 1000 раз)
```

**Что видно:** 1000 горутин в состоянии `chan send` на строке 15. Это утечка.

### Пример 2: мониторинг в реальном времени

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    // Мониторинг горутин в фоне
    go func() {
        for range time.Tick(500 * time.Millisecond) {
            fmt.Printf("[monitor] goroutines: %d\n", runtime.NumGoroutine())
        }
    }()

    // Утечка
    for i := 0; i < 100; i++ {
        ch := make(chan int)
        go func() {
            ch <- i
        }()
    }

    time.Sleep(2 * time.Second)
    fmt.Println("done")
}
```

**Пример вывода:**

```
[monitor] goroutines: 102
[monitor] goroutines: 102
[monitor] goroutines: 102
[monitor] goroutines: 102
done
```

**Что видно:** число горутин не падает — 102 и остаётся. Это утечка.

### Пример 3: стоимость горутин

```go
package main

import (
    "fmt"
    "runtime"
    "sync"
    "time"
)

func main() {
    for _, n := range []int{100, 1000, 10000, 100000} {
        measureGoroutines(n)
    }
}

func measureGoroutines(n int) {
    runtime.GC()

    var m1, m2 runtime.MemStats
    runtime.ReadMemStats(&m1)

    start := time.Now()

    var wg sync.WaitGroup
    wg.Add(n)
    for i := 0; i < n; i++ {
        go func() {
            defer wg.Done()
            time.Sleep(10 * time.Millisecond)
        }()
    }
    wg.Wait()

    elapsed := time.Since(start)
    runtime.ReadMemStats(&m2)

    fmt.Printf("N=%6d: time=%v, alloc=%d KB\n",
        n, elapsed, (m2.TotalAlloc-m1.TotalAlloc)/1024)
}
```

**Пример вывода:**

```
N=   100: time=10.5ms, alloc=612 KB
N=  1000: time=12.3ms, alloc=5920 KB
N= 10000: time=25.1ms, alloc=58600 KB
N=100000: time=180ms, alloc=585000 KB
```

**Что видно:** 100 000 горутин создаются за ~180 мс и используют ~580 МБ. Это **~5.8 КБ на горутину** (включая стек, структуру `g`, overhead).

### 💡 Практика: как диагностировать утечки

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Мониторь `runtime.NumGoroutine()` в production:**
   ```go
   go func() {
       for range time.Tick(30 * time.Second) {
           metrics.Gauge("goroutines", runtime.NumGoroutine())
       }
   }()
   ```

2. **Подключи pprof в production (localhost):**
   ```go
   import _ "net/http/pprof"
   go http.ListenAndServe("localhost:6060", nil)
   ```

3. **Используй `goleak` в тестах.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Алерт при росте горутин > N% за 5 минут.**

**❌ НЕ ДЕЛАЙ:**

5. **Не открывай pprof наружу без аутентификации.**
6. **Не игнорируй растущее число горутин.**

## 1.10 Выводы и типичные ошибки

**Что мы узнали?**

Горутина — это **лёгкая единица планирования**, которой управляет runtime Go, а не ядро. Стек начинается с 2 КБ и растёт динамически. Создание горутины занимает ~100–300 нс и ~2.3 КБ памяти. Горутина может находиться в состояниях `_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`, `_Gdead`. При блокировке горутина не занимает поток ОС. `main` не ждёт другие горутины. Мы разобрали три паттерна: **горутина + WaitGroup** (дождаться), **горутина + context** (отменить), **fire-and-forget** (запустить в фоне с ограничением). Утечки горутин — самая частая проблема.

**Типичные ошибки:**

- ❌ **Думать, что `go func()` создаёт поток ОС.** Горутина — лёгкая структура в runtime.
- ❌ **Считать, что горутина начинает выполняться немедленно.** `go func()` только планирует.
- ❌ **Игнорировать завершение горутин.** Если `main` завершается — все горутины убиваются.
- ❌ **`wg.Add` внутри горутины.** Race: `Wait` может вернуться раньше.
- ❌ **Копировать `WaitGroup`.** `go vet` ловит.
- ❌ **Не использовать `context` в долгоживущих горутинах.** Не отменятся.
- ❌ **Fire-and-forget без ограничения.** Утечка.
- ❌ **Fire-and-forget без `recover`.** Программа упадёт при панике.
- ❌ **Утечка через каналы.** Горутина пишет в небуферизованный канал без читателя.
- ❌ **Утечка через range.** Горутина читает из незакрытого канала.
- ❌ **Утечка через HTTP без таймаута.**
- ❌ **Не мониторить `runtime.NumGoroutine()`.**

## 1.11 Для быстрого повторения

- **Горутина — не поток ОС.** Лёгкая единица планирования в runtime Go. Стек 2 КБ (растёт), `g` ~300 байт, создание ~100–300 нс.
- **`go func()` → `runtime.newproc`.** Структура `g` из пула, стек из пула, горутина в очередь.
- **`go func()` не гарантирует немедленный запуск.**
- **Стек горутины растёт динамически.** 2 КБ → 4 КБ → 8 КБ → ... → 1 ГБ. Сжимается во время GC.
- **Состояния:** `_Gidle` → `_Grunnable` → `_Grunning` → `_Gwaiting`/`_Gsyscall` → `_Gdead`. При блокировке G не занимает поток.
- **`main` не ждёт горутины.** Если `main` завершается — все горутины убиваются.
- **Паттерн «горутина + WaitGroup»** — дождаться завершения. `Add` до `go func()`, `defer wg.Done()`.
- **Паттерн «горутина + context»** — отмена. `ctx.Done()` в `select`, `defer cancel()`.
- **Паттерн «fire-and-forget»** — фоновая задача с ограничением через семафор и `recover`.
- **Утечка горутин** — горутина навсегда в `_Gwaiting`. Причины: канал без читателя, range по незакрытому каналу, HTTP без таймаута.
- **Диагностика:** `runtime.NumGoroutine()`, pprof (`debug/pprof/goroutine?debug=2`), `goleak`.
- **100 000 горутин** создаются за ~180 мс и используют ~580 МБ (~5.8 КБ на горутину).

## 1.13 Ответы

### Ответ 1

Горутина — лёгкая единица планирования в runtime Go. Поток ОС — единица планирования в ядре. Ключевые отличия: горутина имеет стек 2 КБ (растёт), поток — 1–8 МБ (фиксирован). Создание горутины ~100–300 нс, потока — ~10–100 мкс. Переключение горутины ~100–200 нс, потока — ~1–10 мкс.

### Ответ 2

`go func()` компилируется в вызов `runtime.newproc`. Runtime:

1. Получает структуру `g` из пула.
2. Выделяет стек 2 КБ из пула.
3. Копирует аргументы.
4. Устанавливает точку входа.
5. Помещает горутину в очередь.

Горутина **не запускается сразу** — она планируется.

### Ответ 3

**Паттерн «горутина + WaitGroup»** — дождаться завершения горутины:

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    doWork()
}()
wg.Wait()
```

`Add` — до запуска. `defer wg.Done()` — гарантирует вызов.

### Ответ 4

**Отмена через `context`:**

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

go func() {
    select {
    case <-ctx.Done():
        return
    case result := <-doWork():
        process(result)
    }
}()
```

`ctx.Done()` в `select` позволяет горутине завершиться досрочно.

### Ответ 5

**Fire-and-forget** — запустить горутину без ожидания. Уместен, когда:

- Задача не влияет на ответ клиенту (email, лог, метрика).
- Ошибка некритична.
- Задача короткая.

**Ограничение:** через семафор + `recover` в каждой горутине.

### Ответ 6

**Три причины:**
1. Канал без читателя.
2. Range по незакрытому каналу.
3. HTTP без таймаута.

### Ответ 7

**Три способа:**
1. `runtime.NumGoroutine()` — рост без падения.
2. pprof goroutine dump: `curl http://localhost:6060/debug/pprof/goroutine?debug=2`.
3. `goleak` в тестах.

## 1.15 Чек-лист

| Компонент | Что это | Ключевые факты |
|:---|:---|:---|
| **Горутина** | Лёгкая единица планирования | Стек 2 КБ (растёт), `g` ~300 байт, создание ~100–300 нс |
| **`go func()`** | Оператор запуска | Компилируется в `runtime.newproc`, не syscall |
| **Стек горутины** | Область памяти | 2 КБ → 4 КБ → 8 КБ → ... → 1 ГБ. Сжимается во время GC |
| **`morestack`** | Функция роста стека | Удваивает стек, копирует данные |
| **Состояния** | `_Gidle`, `_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`, `_Gdead` | При блокировке G не занимает поток |
| **Паттерн WaitGroup** | Дождаться | `Add` до `go func()`, `defer wg.Done()` |
| **Паттерн context** | Отмена | `ctx.Done()` в `select`, `defer cancel()` |
| **Fire-and-forget** | Фон | Ограничение семафором, `recover` обязателен |
| **`runtime.NumGoroutine()`** | Число горутин | Для диагностики утечек |
| **Утечка горутин** | Горутина навсегда в `_Gwaiting` | Канал без читателя, range без close, HTTP без таймаута |
| **pprof** | Профилирование | `debug/pprof/goroutine?debug=2` — дамп стеков |
| **goleak** | Библиотека для тестов | `goleak.VerifyNone(t)` — ловит утечки |
| **`context`** | Механизм отмены | `WithCancel`, `WithTimeout` |
| **Буферизованный канал** | Канал с буфером | `make(chan int, 1)` — не блокирует отправителя |
| **Закрытие канала** | Сигнал читателям | Закрывает **владелец** (тот, кто пишет) |

🧵 **Ключевая идея:** Горутина — это **не поток ОС**. Это лёгкая структура в runtime Go. Стек начинается с 2 КБ и растёт динамически. Создание — ~100–300 нс, переключение — ~100–200 нс. При блокировке горутина не занимает поток. Три ключевых паттерна: **WaitGroup** (дождаться), **context** (отменить), **fire-and-forget** (фон с ограничением и `recover`). Главная проблема — **утечки**: горутина, которая никогда не завершится, остаётся в памяти навсегда. Диагностика через `runtime.NumGoroutine`, pprof и `goleak`. Предотвращение — `context`, буферизованные каналы, закрытие каналов владельцем. `main` не ждёт горутины — если `main` завершается, все горутины убиваются.
