## 27.0 Пролог: слишком много аллокаций

У нас есть HTTP-сервис, который обрабатывает 10 000 запросов в секунду. Каждый хендлер читает JSON, парсит его, обрабатывает, отдаёт ответ.

Пишем просто:

```go
func handleRequest(w http.ResponseWriter, r *http.Request) {
    var req Request
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, err.Error(), 400)
        return
    }
    // обработка
    json.NewEncoder(w).Encode(response)
}
```

Работает. Но смотрим CPU-профиль и видим **30% в GC**. Память растёт на 2 ГБ в минуту. Каждый запрос создаёт **десятки объектов**:

- `json.Decoder` — новый на каждый запрос.
- `Request` — новый.
- `response` — новый.
- Внутренние буферы JSON — новые.

Хочется **переиспользовать** эти объекты. Например, `Request` и `json.Decoder` — они короткоживущие, но их можно использовать повторно.

Это и есть задача **`sync.Pool`** — пул временных объектов, которые **переиспользуются** между запросами.

> **Мост к следующим главам:** `sync.Pool` — оптимизация для high-throughput сервисов. Он работает в паре с GC (Глава 28) и аллокатором. Понимание `sync.Pool` даёт понимание, **как снизить давление на память**.

## 27.1 Что такое sync.Pool

**`sync.Pool`** — стандартная библиотека для **пула временных объектов**.

### Идея

**Обычный объект:**

```go
buf := make([]byte, 1024)  // аллокация
// используем
// GC освободит позже
```

**Объект из пула:**

```go
buf := pool.Get().([]byte)  // переиспользуем
// используем
pool.Put(buf)  // возвращаем в пул
```

**Ключевое:** объект **не освобождается** GC, а **возвращается в пул** для повторного использования.

### Зачем это нужно

**GC работает быстрее, если меньше объектов.**

- 10 000 объектов в секунду → много работы для GC.
- 100 объектов в пуле → GC спокоен.

**Аллокации — дорогие.**

- `make` → malloc → обнуление.
- Из пула → уже готов.

### Схема

```
Без пула:
  Request1 → new → GC
  Request2 → new → GC
  Request3 → new → GC
  ...
  GC работает постоянно.

С пулом:
  Request1 → Get → используем → Put
  Request2 → Get (тот же объект) → используем → Put
  Request3 → Get (тот же объект) → используем → Put
  ...
  GC освобождает пул только при следующем цикле.
```

### Когда использовать sync.Pool

**1. Часто создаваемые объекты.**

- Буферы для чтения/записи.
- `json.Encoder/Decoder`.
- `bytes.Buffer`.
- Временные структуры.

**2. Объекты, которые можно переиспользовать.**

- Не содержат состояния между запросами.
- Легко **сбросить** перед использованием.

**3. High-throughput сервисы.**

- HTTP-серверы.
- Парсеры.
- Сериализаторы.

### Когда НЕ использовать sync.Pool

**1. Долгоживущие объекты.**

Пул для **временных**. Долгоживущие — в куче.

**2. Объекты с уникальным состоянием.**

Если объект нельзя **сбросить** — не подходит.

**3. Малая нагрузка.**

Если объектов мало — overhead пула больше пользы.

**4. Большие объекты.**

Пул для **маленьких** (до ~100 КБ).

### 💡 Практика: как думать о sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`sync.Pool` — для буферов и временных объектов.**
2. **Всегда сбрасывай перед использованием.**
3. **Не полагайся на содержимое пула.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмаркай до/после.**
5. **Проверяй `-benchmem`.**

**❌ НЕ ДЕЛАЙ:**

6. **Не используй для долгоживущих объектов.**
7. **Не забывай `Put`.**

## 27.2 Escape analysis: почему объекты в heap

Прежде чем разбирать пул, поймём, **почему** объекты попадают в heap.

### Stack vs heap

**Stack** — быстрая память. Освобождается при выходе из функции. **GC её не трогает.**

**Heap** — общая память. **GC её собирает.**

**Идея:** если объект **не убегает** из функции — на stack. Если **убегает** — на heap.

### Что значит «убегает»

**Объект убегает, если:**

1. **Возвращается** из функции.
2. **Сохраняется** в глобальную переменную.
3. **Передаётся** в другой поток (горутину).

### Пример

```go
// ❌ Убегает на heap
func newUser() *User {
    return &User{Name: "Alice"}
}

// ✅ На stack
func process() {
    u := User{Name: "Alice"}  // не убегает
    _ = u.Name
}
```

### Как проверить

```bash
go build -gcflags="-m" ./...
```

**Вывод:**

```
./main.go:10:6: &User{...} escapes to heap
./main.go:15:7: u does not escape
```

### Почему это важно для пула

**Если объект попадает в heap:**

- GC его обходит.
- Аллокация дороже.
- Давление на память.

**Пул помогает:** переиспользуем объекты **в heap**, но не создаём **новые**.

### Схема

```
Stack:
  func() {
    x := 5    ← stack
    return
  }           ← x освобождается автоматически

Heap:
  func() *int {
    x := 5    ← heap
    return &x
  }           ← GC освободит позже
```

### 💡 Практика: как минимизировать heap

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Возвращай значения, не указатели, если возможно.**
2. **Используй `-gcflags="-m"` для проверки.**
3. **Пул для тех объектов, что всё равно в heap.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **`sync.Pool` для буферов.**

**❌ НЕ ДЕЛАЙ:**

5. **Не оптимизируй вслепую.**
6. **Не забывай про `escape analysis`.**

## 27.3 Простейший пул на канале

Прежде чем использовать `sync.Pool`, построим **пул на канале** — чтобы понять механику.

### Идея

- Буферизованный канал на N объектов.
- `Get` — читаем из канала.
- `Put` — пишем в канал.
- Если пусто — создаём новый.

### Реализация

```go
type Pool[T any] struct {
    ch chan T
    fn func() T
}

func NewPool[T any](size int, fn func() T) *Pool[T] {
    p := &Pool[T]{
        ch: make(chan T, size),
        fn: fn,
    }
    for i := 0; i < size; i++ {
        p.ch <- fn()
    }
    return p
}

func (p *Pool[T]) Get() T {
    select {
    case v := <-p.ch:
        return v
    default:
        return p.fn()
    }
}

func (p *Pool[T]) Put(v T) {
    select {
    case p.ch <- v:
    default:
        // пул полон — объект уходит в GC
    }
}
```

**Что происходит:**

- Пул содержит **до N объектов**.
- `Get` — берём из канала или создаём.
- `Put` — возвращаем или дропаем.

### Потребитель

```go
func main() {
    pool := NewPool(10, func() []byte {
        return make([]byte, 1024)
    })
    
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            buf := pool.Get()
            // используем buf
            _ = buf
            pool.Put(buf)
        }()
    }
    wg.Wait()
}
```

### Проблемы с каналом

**1. Overhead.**

- `select` + канал — ~100 нс.
- `sync.Pool` — ~20 нс.

**2. Фиксированный размер.**

- Пул всегда N объектов.
- Если N маленькое — объекты создаются вне пула.

**3. GC не очищает.**

- Канал держит ссылки на объекты.
- Даже если объекты не нужны — они в памяти.

### Схема

```
NewPool(10, fn):
  ┌────────────────────────┐
  │ ch (буфер 10)          │
  │ [obj][obj][obj]...     │
  └────────────────────────┘

Get():
  select {
  case v := <-ch: return v     ← быстро
  default:       return fn()   ← создаём
  }

Put(v):
  select {
  case ch <- v:                 ← возвращаем
  default:                      ← дропаем
  }
```

### 💡 Практика: как писать пул на канале

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Буферизованный канал.**
2. **`select` с `default`.**
3. **`fn` для создания новых.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для понимания — да.**
5. **Для production — `sync.Pool`.**

**❌ НЕ ДЕЛАЙ:**

6. **Не используй канальный пул в production.**
7. **Не забывай про GC.**

## 27.4 sync.Pool: API и семантика

**`sync.Pool`** — стандартная библиотека.

### API

```go
var pool = sync.Pool{
    New: func() any {
        return make([]byte, 1024)
    },
}

// Get
buf := pool.Get().([]byte)

// Put
pool.Put(buf)
```

**Что даёт:**

- **`New`** — функция создания нового объекта.
- **`Get`** — взять из пула.
- **`Put`** — вернуть в пул.

### Семантика

**`Get`:**

1. Пытается взять из **локального** пула P.
2. Если пусто — из **разделяемого** пула.
3. Если пусто — из **другого P** (work stealing).
4. Если пусто — вызывает `New`.

**`Put`:**

1. Кладёт в **локальный** пул P.
2. Может быть **вытеснен** при GC.

### Схема

```
Get:
  ┌───────────────────────────┐
  │ 1. Локальный пул P        │
  │ 2. Разделяемый пул        │
  │ 3. Другой P               │
  │ 4. New()                  │
  └───────────────────────────┘

Put:
  ┌───────────────────────────┐
  │ Кладём в локальный пул P  │
  └───────────────────────────┘
```

### Пул и P (процессоры)

**`sync.Pool` использует P (логические процессоры) для снижения contention.**

- Каждый P имеет **свой** локальный пул.
- При `Get` — берём из своего пула.
- **Нет блокировок** между P.

**Детали в Главе 6 (Планировщик).**

### Важно: содержимое пула не сохраняется

**`sync.Pool` очищается при каждом GC.**

- Объекты в пуле **удаляются** при GC.
- Пул **не** гарантирует, что `Get` вернёт **тот же** объект.
- Пул **не** гарантирует, что `Put` сохранит объект.

**Это дизайн, а не баг.** Пул для временных объектов — не для кэша.

### Пример

```go
package main

import (
    "fmt"
    "sync"
)

var pool = sync.Pool{
    New: func() any {
        fmt.Println("New called")
        return make([]byte, 1024)
    },
}

func main() {
    buf1 := pool.Get().([]byte)
    pool.Put(buf1)
    
    buf2 := pool.Get().([]byte)
    fmt.Println("Same buf:", &buf1[0] == &buf2[0])  // true (скорее всего)
    
    runtime.GC()
    
    buf3 := pool.Get().([]byte)
    fmt.Println("Same after GC:", &buf1[0] == &buf3[0])  // false (скорее всего)
}
```

**Пример вывода:**

```
New called
Same buf: true
New called
Same after GC: false
```

**Что видно:** после GC пул **очищен**. `New` вызывается снова.

### 💡 Практика: как использовать sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Всегда задавай `New`.**
2. **Всегда сбрасывай объект перед использованием.**
3. **Не полагайся на состояние пула.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Только для временных объектов.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `sync.Pool` как кэш.**
6. **Не полагайся на сохранение объектов.**

## 27.5 Что происходит при GC

**GC очищает `sync.Pool`.** Это важное свойство.

### Как GC взаимодействует с пулом

**При каждом GC:**

1. **Все объекты в пуле удаляются.**
2. **Пул остаётся** (не nil).
3. **Следующий `Get` вызовет `New`.**

**Почему:**

- Пул для **временных** объектов.
- GC не знает, нужны ли они.
- Проще **очистить** пул, чем отслеживать.

### Схема

```
t=0:   pool = {obj1, obj2, obj3}
t=1:   Get → obj1
t=2:   Put(obj1) → pool = {obj2, obj3, obj1}
t=3:   GC!
       pool = {}  ← все объекты удалены
t=4:   Get → New()  ← создаём новый
```

### Что это значит на практике

**1. Пул помогает при высокой нагрузке.**

- Между GC много `Get`/`Put`.
- Объекты переиспользуются.

**2. Пул не помогает при низкой нагрузке.**

- GC очищает пул.
- Каждый `Get` создаёт новый.

**3. Пул не для долгоживущих объектов.**

- GC удалит их.

### 💡 Практика: как учитывать GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: GC очищает пул.**
2. **Пул для высокой нагрузки.**
3. **Не для долгоживущих.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь GC.**

**❌ НЕ ДЕЛАЙ:**

5. **Не полагайся на сохранение объектов после GC.**

## 27.6 Когда sync.Pool помогает, а когда нет

Разберём **когда** пул помогает.

### Помогает

**1. Высокая нагрузка.**

- 10 000 запросов/сек.
- Между GC много операций.

**2. Короткоживущие объекты.**

- Буферы на запрос.
- Временные структуры.

**3. Большие объекты (но не очень).**

- Буферы 1–100 КБ.
- Меньше давления на GC.

**4. Однотипные объекты.**

- `[]byte` одного размера.
- `bytes.Buffer` фиксированного capacity.

### Не помогает

**1. Низкая нагрузка.**

- GC очищает пул.
- Каждый `Get` = `New`.

**2. Уникальные объекты.**

- Каждый раз разного размера.
- Пул бесполезен.

**3. Долгоживущие объекты.**

- Кэш, а не пул.

**4. Маленькие объекты (< 100 байт).**

- Аллокация быстрая.
- Overhead пула больше пользы.

### Пример

**Помогает:**

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 32*1024)  // 32 КБ
    },
}

func handleHTTP(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    // читаем тело запроса в buf
    n, _ := r.Body.Read(buf)
    process(buf[:n])
}
```

**Что даёт:** 10 000 буферов по 32 КБ = **320 МБ** без пула. С пулом — **N буферов** (N = GOMAXPROCS).

### Бенчмарк

```go
func BenchmarkWithoutPool(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            buf := make([]byte, 32*1024)
            _ = buf
        }
    })
}

var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 32*1024)
    },
}

func BenchmarkWithPool(b *testing.B) {
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            buf := bufPool.Get().([]byte)
            _ = buf
            bufPool.Put(buf)
        }
    })
}
```

**Пример вывода:**

```
BenchmarkWithoutPool-8    5000000    300 ns/op    32768 B/op    1 allocs/op
BenchmarkWithPool-8      20000000     80 ns/op        0 B/op    0 allocs/op
```

**Что видно:** пул в **3.5 раза быстрее** и **0 аллокаций**.

### 💡 Практика: когда использовать пул

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Высокая нагрузка.**
2. **Объекты 1–100 КБ.**
3. **Однотипные.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмаркай до/после.**

**❌ НЕ ДЕЛАЙ:**

5. **Не для долгоживущих.**
6. **Не для маленьких (< 100 байт).**

## 27.7 Типичные ошибки

Разберём **ошибки** при работе с `sync.Pool`.

### 1. Забыть сбросить объект

**❌ Плохо:**

```go
buf := bufPool.Get().([]byte)
// используем
bufPool.Put(buf)
```

**Что происходит:** в буфере могут остаться **старые данные**. При следующем `Get` — они там.

**✅ Хорошо:**

```go
buf := bufPool.Get().([]byte)
defer func() {
    buf = buf[:0]  // сброс длины
    bufPool.Put(buf)
}()
// используем
```

### 2. Забыть `Put`

**❌ Плохо:**

```go
buf := bufPool.Get().([]byte)
// используем
// забыли Put
```

**Что происходит:** объект уходит в GC. Пул **пуст**.

**✅ Хорошо:**

```go
buf := bufPool.Get().([]byte)
defer bufPool.Put(buf)
```

### 3. Пул как кэш

**❌ Плохо:**

```go
// Хотим кэш объектов
pool.Put(user)
// ...
user := pool.Get().(*User)
```

**Что происходит:** GC очистит пул. Кэш **потерян**.

**✅ Хорошо:** для кэша — `sync.Map` или другой кэш.

### 4. Объекты с указателями на другие объекты

**❌ Плохо:**

```go
type Buffer struct {
    data []byte
    ref  *SomeLargeObject  // ← держит ссылку
}

pool.Put(buf)
// ref уходит в GC только когда пул очищен
```

**Что происходит:** пул **держит ссылки** на объекты, пока GC не очистит.

**✅ Хорошо:** обнулять ссылки перед `Put`:

```go
buf.ref = nil
pool.Put(buf)
```

### 5. Не задать `New`

**❌ Плохо:**

```go
var pool sync.Pool  // ← New == nil
buf := pool.Get().([]byte)  // ← panic
```

**Что происходит:** `Get` возвращает `nil`. Паника при type assertion.

**✅ Хорошо:**

```go
var pool = sync.Pool{
    New: func() any {
        return make([]byte, 1024)
    },
}
```

### Схема

```
Правильный Put:
  ┌──────────────────────────┐
  │ buf = buf[:0]            │ ← сброс длины
  │ (обнуление ссылок)       │
  │ pool.Put(buf)            │
  └──────────────────────────┘
```

### 💡 Практика: как избежать ошибок

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Всегда `New`.**
2. **Всегда сбрасывать перед `Put`.**
3. **`defer` для `Put`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Обнулять ссылки.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй как кэш.**
6. **Не забывай про ссылки.**

## 27.9 Практика Go: пул буферов

Разберём **полный пример**.

### Полный код

```go
package main

import (
    "bytes"
    "encoding/json"
    "fmt"
    "io"
    "sync"
    "time"
)

type User struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

var (
    bufPool = sync.Pool{
        New: func() any {
            return bytes.NewBuffer(make([]byte, 0, 1024))
        },
    }
    decoderPool = sync.Pool{
        New: func() any {
            return json.NewDecoder(nil)
        },
    }
)

func decodeUser(r io.Reader) (*User, error) {
    dec := decoderPool.Get().(*json.Decoder)
    defer decoderPool.Put(dec)
    
    dec.Reset(r)
    
    var u User
    if err := dec.Decode(&u); err != nil {
        return nil, err
    }
    return &u, nil
}

func encodeUser(w io.Writer, u *User) error {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()
        bufPool.Put(buf)
    }()
    
    enc := json.NewEncoder(buf)
    if err := enc.Encode(u); err != nil {
        return err
    }
    
    _, err := w.Write(buf.Bytes())
    return err
}

func main() {
    // Benchmark: without pool
    start := time.Now()
    for i := 0; i < 1_000_000; i++ {
        buf := new(bytes.Buffer)
        _ = buf
    }
    withoutPool := time.Since(start)
    
    // Benchmark: with pool
    start = time.Now()
    for i := 0; i < 1_000_000; i++ {
        buf := bufPool.Get().(*bytes.Buffer)
        buf.Reset()
        bufPool.Put(buf)
    }
    withPool := time.Since(start)
    
    fmt.Printf("Without pool: %v\n", withoutPool)
    fmt.Printf("With pool:    %v\n", withPool)
    fmt.Printf("Speedup:      %.1fx\n", float64(withoutPool)/float64(withPool))
    
    // Функциональность
    data := []byte(`{"id": 1, "name": "Alice"}`)
    u, err := decodeUser(bytes.NewReader(data))
    if err != nil {
        panic(err)
    }
    fmt.Printf("Decoded: %+v\n", u)
    
    var out bytes.Buffer
    if err := encodeUser(&out, u); err != nil {
        panic(err)
    }
    fmt.Printf("Encoded: %s", out.String())
}
```

**Пример вывода:**

```

With pool:    8ms
Speedup:      4.4x
Decoded: &{ID:1 Name:Alice}
Encoded: {"id":1,"name":"Alice"}
```

**Что демонстрирует:**

- **4.4x быстрее** с пулом.
- **Без аллокаций** для 1 миллиона операций.
- **Пул для `bytes.Buffer` и `json.Decoder`.**

## 27.10 Выводы и типичные ошибки

**Что мы узнали?**

`sync.Pool` — стандартная библиотека для пула временных объектов. **GC очищает пул** при каждом цикле. **Escape analysis** определяет, попадает ли объект в heap. **Пул на канале** — для понимания; `sync.Pool` — для production. **Помогает** при высокой нагрузке и однотипных объектах. **Не помогает** при низкой нагрузке и уникальных объектах. **Ошибки:** забыть сбросить, забыть `Put`, использовать как кэш, оставить ссылки.

**Типичные ошибки:**

- ❌ **Забыть `New`.** Паника при `Get`.
- ❌ **Забыть `Put`.** Объект уходит в GC.
- ❌ **Не сбросить перед использованием.** Старые данные.
- ❌ **Использовать как кэш.** GC очищает.
- ❌ **Оставить ссылки.** Пул держит объекты.
- ❌ **Пул для долгоживущих.** GC удалит.
- ❌ **Пул для маленьких объектов.** Overhead.
- ❌ **Пул при низкой нагрузке.** Нет выигрыша.
- ❌ **Не бенчмаркать.**
- ❌ **Не проверять `escape analysis`.**

## 27.13 Ответы

### Ответ 1

**`sync.Pool`** — стандартная библиотека для пула временных объектов. Решает задачу: **снижение давления на GC** через переиспользование объектов.

**Пример:** буферы для HTTP-запросов, `json.Decoder`.

### Ответ 2

**GC очищает пул** при каждом цикле. Все объекты удаляются, пул остаётся. Следующий `Get` вызывает `New`.

**Почему:** пул для **временных** объектов. GC не знает, нужны ли они.

### Ответ 3

**Escape analysis** — анализ компилятора: **убегает** ли объект из функции.

- **Не убегает** — stack.
- **Убегает** — heap.

**Проверка:** `go build -gcflags="-m"`.

### Ответ 4

**Пул на канале:**

```go
type Pool[T any] struct {
    ch chan T
    fn func() T
}

func (p *Pool[T]) Get() T {
    select {
    case v := <-p.ch:
        return v
    default:
        return p.fn()
    }
}

func (p *Pool[T]) Put(v T) {
    select {
    case p.ch <- v:
    default:
    }
}
```

**Минусы:** overhead `select`, фиксированный размер, GC не очищает.

### Ответ 5

**`sync.Pool` помогает:**

1. **Высокая нагрузка** — много операций между GC.
2. **Короткоживущие объекты** — буферы.
3. **Объекты 1–100 КБ.**
4. **Однотипные объекты.**

**Пример:** 10 000 HTTP-запросов/сек с буферами 32 КБ.

### Ответ 6

**`sync.Pool` не помогает:**

1. **Низкая нагрузка** — GC очищает.
2. **Уникальные объекты** — разный размер.
3. **Долгоживущие объекты** — GC удалит.
4. **Маленькие объекты (< 100 байт).**

### Ответ 7

**Избежать ошибок:**

1. **Всегда `New`.**
2. **Всегда сбрасывать перед `Put`:**
   ```go
   defer func() {
       buf = buf[:0]
       pool.Put(buf)
   }()
   ```
3. **`defer` для `Put`.**
4. **Обнулять ссылки.**
5. **Не использовать как кэш.**

### Ответ 8

**`sync.Pool` + HTTP:**

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 32*1024)
    },
}

func handleRequest(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf[:0])
    
    n, _ := io.ReadFull(r.Body, buf)
    process(buf[:n])
}
```

10 000 запросов/сек × 32 КБ = **320 МБ** без пула. С пулом — **N буферов** (N = GOMAXPROCS).
