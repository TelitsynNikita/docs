## 2.0 Пролог: как передать данные между горутинами

В предыдущей главе мы разобрали горутины. Мы умеем их запускать, знаем их стоимость, умеем находить утечки. Но есть одна вещь, которую мы пока не умеем: **горутины не могут обмениваться данными друг с другом**.

Представим задачу. У нас есть сервис, который получает заказы и обрабатывает их в фоне. Логично разделить его на две части: одну горутину, которая принимает заказы, и другую, которая их обрабатывает.

```go
func main() {
    go receiver()   // принимает заказы
    go processor()  // обрабатывает заказы
}
```

Но как `receiver` передаст заказ в `processor`? У них разные стеки, разная память. `receiver` не может просто «положить» заказ в переменную — `processor` её не увидит.

Можно было бы использовать общую переменную с мьютексом:

```go
var (
    mu   sync.Mutex
    task Task
)

func receiver() {
    for {
        t := receive()
        mu.Lock()
        task = t
        mu.Unlock()
    }
}

func processor() {
    for {
        mu.Lock()
        t := task
        mu.Unlock()
        if t != nil {
            process(t)
        }
    }
}
```

Это работает, но получается неудобно: `processor` должен постоянно проверять, появилась ли новая задача. И это не единственная проблема — если `receiver` производит быстрее, чем `processor` потребляет, задачи накапливаются в переменной.

Хочется чего-то более простого: механизма, который сам бы **синхронизировал** отправителя и получателя. Чтобы `receiver` клал заказ и **ждал**, пока `processor` его возьмёт. А если `processor` не готов — `receiver` ждёт, не теряя заказ.

Именно эту задачу решают **каналы**.

> **Мост к следующим главам:** каналы — основа всех паттернов в Go. Fan-in, fan-out, pipeline, worker pool — всё строится на каналах. Понимание каналов даёт понимание паттернов.

## 2.1 Канал — не очередь

Первое, что важно понять про каналы — это то, что они **не являются очередью**.

В классическом программировании «очередь» — это структура данных: `push` в конец, `pop` из начала. Producer кладёт элемент и **идёт дальше**, не дожидаясь consumer'а. Consumer забирает элемент, когда удобно.

Канал в Go работает **иначе**. Это **точка синхронизации** между двумя горутинами.

### Два режима работы

**Небуферизованный канал** — это как передача ключа из рук в руки.

Отправитель держит ключ и **ждёт**, пока получатель протянет руку. Только когда руки встречаются — ключ переходит. Если получатель не готов — отправитель стоит и ждёт.

```
Отправитель ──────┐
                  ├──► Рандеву
Получатель ───────┘
```

**Буферизованный канал** — это как ящик для ключей.

Можно положить ключ в ящик и уйти, если в ящике есть место. Получатель придёт и заберёт. Если ящик полон — придётся стоять и ждать, пока кто-то заберёт ключи.

```
Отправитель ──▶ [буфер] ──▶ Получатель
```

**Ключевое различие:** в небуферизованном случае отправитель и получатель **встречаются**. В буферизованном — **развязываются по времени**, но не полностью (буфер ограничен).

### Практическое следствие

Канал — это **не** «положил и забыл». Если получатель не готов — отправитель **ждёт**. Это **свойство**, а не баг. Именно оно делает каналы мощным инструментом синхронизации.

### 💡 Практика: как думать о канале

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Думай о канале как о точке синхронизации**, а не как об очереди.
2. **Для сигналов используй `chan struct{}`:**
   ```go
   done := make(chan struct{})
   close(done)  // сигнал всем читателям
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Небуферизованный канал — когда важна синхронизация.**
4. **Буферизованный канал — когда важна пропускная способность.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй канал как «очередь на всякий случай».** Если нужна настоящая очередь — посмотри на Kafka, NATS, Redis Streams.
6. **Не блокируй HTTP-хэндлер на отправке в канал без `select` + `default`.**

## 2.2 Создание и базовые операции

Разберём базовые операции с каналами.

### Создание канала

```go
// Небуферизованный
ch := make(chan int)

// Буферизованный на 10 элементов
ch := make(chan int, 10)

// Канал пустых структур — для сигналов
done := make(chan struct{})
```

**Что создаётся:**

- **`hchan`** — структура канала (~96 байт).
- **Буфер** (если буферизованный) — массив элементов.

### Отправка и получение

```go
ch <- 42     // отправить
v := <-ch    // получить
```

**Ключевое:** обе операции **блокирующие**, если другая сторона не готова.

- `ch <- 42` блокируется, пока есть читатель (для небуферизованного).
- `<-ch` блокируется, пока есть данные (для буферизованного) или отправитель (для небуферизованного).

### Получение с проверкой закрытия

```go
v, ok := <-ch
if !ok {
    // канал закрыт
}
```

`ok == false` — канал закрыт **и** буфер пуст.

### Range по каналу

```go
for v := range ch {
    process(v)
}
```

Цикл читает, пока канал **открыт**. Когда канал закрыт и буфер пуст — цикл завершается.

### 💡 Практика: базовые операции

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для сигналов — `chan struct{}`.** Ноль байт.
2. **Проверяй `ok` при получении, если важно отличить «ноль» от «закрыт».**
3. **Используй `range` для чтения всех значений до закрытия.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для буфера — разумный размер.** 10–1000 для большинства случаев.

**❌ НЕ ДЕЛАЙ:**

5. **Не забывай, что отправка в небуферизованный канал блокируется.** Это синхронизация.

## 2.3 Что происходит при отправке и получении

Разберём, что физически происходит при `ch <- v` и `<-ch`.

### Структура hchan

Канал в runtime Go представлен структурой `hchan`:

```go
type hchan struct {
    qcount   uint           // число элементов в буфере
    dataqsiz uint           // размер буфера
    buf      unsafe.Pointer // указатель на кольцевой буфер
    elemsize uint16         // размер элемента
    closed   uint32         // 1, если закрыт
    elemtype *_type         // тип элемента
    
    sendx    uint           // индекс записи
    recvx    uint           // индекс чтения
    
    recvq    waitq          // очередь горутин, ждущих получения
    sendq    waitq          // очередь горутин, ждущих отправки
    
    lock     mutex          // защита
}
```

Канал — это структура ~96 байт плюс буфер (если буферизованный). Все операции защищены **мьютексом `lock`** — это делает канал потокобезопасным.

### Схема трёх путей отправки

Когда горутина делает `ch <- v`, runtime проходит по трём сценариям **в порядке приоритета**:

```
ch <- v
   │
   ▼
┌──────────────────────────────────────────────┐
│  1. Захватить lock                           │
│  2. if closed: panic                         │
│                                              │
│  3. Быстрый путь: recvq не пуста?            │
│     → Извлечь sudog получателя               │
│     → Скопировать данные НАПРЯМУЮ            │
│       из стека отправителя в стек получателя │
│     → goready(получатель)                    │
│     → return                                 │
│                                              │
│  4. Средний путь: qcount < dataqsiz?         │
│     → Скопировать данные в буфер             │
│     → sendx++, qcount++                      │
│     → return                                 │
│                                              │
│  5. Медленный путь: места нет                │
│     → Создать sudog для отправителя          │
│     → Добавить в sendq                       │
│     → gopark (перейти в _Gwaiting)           │
│     → return при пробуждении                 │
└──────────────────────────────────────────────┘
```

**Ключевое:** при быстром пути данные копируются **напрямую из стека отправителя в стек получателя**. Нет промежуточного буфера. Это как передача ключа из рук в руки.

### Схема трёх путей получения

`<-ch` — зеркальная операция:

```
v := <-ch
   │
   ▼
┌──────────────────────────────────────────────┐
│  1. Захватить lock                           │
│  2. if closed && qcount == 0:                │
│     → v = zero, ok = false                   │
│     → return                                 │
│                                              │
│  3. Быстрый путь: sendq не пуста?            │
│     → Извлечь sudog отправителя              │
│     → Скопировать данные НАПРЯМУЮ            │
│     → goready(отправитель)                   │
│     → return                                 │
│                                              │
│  4. Средний путь: qcount > 0?                │
│     → Прочитать из буфера                    │
│     → recvx++, qcount--                      │
│     → return                                 │
│                                              │
│  5. Медленный путь: буфер пуст               │
│     → Создать sudog для получателя           │
│     → Добавить в recvq                       │
│     → gopark (перейти в _Gwaiting)           │
│     → return при пробуждении                 │
└──────────────────────────────────────────────┘
```

### Ключевое: горутина не занимает поток ОС

Когда горутина блокируется на канале, она переходит в `_Gwaiting`. Поток ОС **освобождается** для других горутин. Именно поэтому 10 000 горутин, ждущих канал, не блокируют 10 000 потоков.

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: отправка блокируется, пока получатель не готов.**
2. **Для больших структур — передавай указатели:**
   ```go
   ch := make(chan *BigStruct)  // ✅
   // ch := make(chan BigStruct)  // ❌ копирование
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Оценивай размер буфера.** Маленький → частые блокировки. Большой → накопление.

**❌ НЕ ДЕЛАЙ:**

4. **Не пиши в закрытый канал.** Паника.

## 2.4 Буферизованный канал

Буферизованный канал — канал с буфером на N элементов.

### Создание

```go
ch := make(chan int, 10)  // буфер на 10
```

### Как работает

- Отправка **не блокируется**, пока в буфере есть место.
- Получение **не блокируется**, пока в буфере есть данные.
- Когда буфер полон — отправитель ждёт.
- Когда буфер пуст — получатель ждёт.

### Кольцевой буфер

Внутри буфер реализован как **кольцевой массив**:

```
      ┌─────┬─────┬─────┬─────┐
buf:  │ [0] │ [1] │ [2] │ [3] │
      └─────┴─────┴─────┴─────┘
        ▲                 ▲
      recvx             sendx
      (читаем)          (пишем)
```

Когда `sendx` доходит до конца — оборачивается в 0. Когда `recvx` догоняет `sendx` — буфер пуст.

### Когда что использовать

**Небуферизованный канал:**

- Когда нужна **гарантия**, что получатель получил данные.
- Когда важна **синхронизация**, а не пропускная способность.

**Буферизованный канал:**

- Когда нужна **пропускная способность**: producer'ы не ждут consumer'ов.
- Когда важен **backpressure** с задержкой: буфер сглаживает пики.

### 💡 Практика: как выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для синхронизации — небуферизованный.**
2. **Для пропускной способности — буферизованный.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для сигналов — `chan struct{}` + `close`.**
4. **Для семафора — буферизованный канал с `struct{}`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй буферизованный канал «на всякий случай».** Это скрывает проблемы синхронизации.
6. **Не ставь буфер 100 000+.** Backpressure не работает.

## 2.5 close — сигнал, а не очистка

`close(ch)` — самая непонятая операция с каналами.

### Что делает close

`close(ch)`:

1. Устанавливает флаг `closed = 1`.
2. **Разблокирует всех получателей** из `recvq` — они получат `zero, false`.
3. **Отправители из `sendq` получат панику** при попытке отправки.

### Что close НЕ делает

- **Не освобождает память.** Память освободит GC.
- **Не очищает буфер.** Данные в буфере остаются доступны.
- **Не идемпотентен.** Повторный `close` — паника.

### Пример: данные в буфере остаются доступны

Это важный момент, который часто упускают. `close` **не стирает** данные, которые уже лежат в буфере — он только сигнализирует, что новых записей не будет.

```go
ch := make(chan int, 3)
ch <- 1
ch <- 2
close(ch)

fmt.Println(<-ch)      // 1
fmt.Println(<-ch)      // 2
fmt.Println(<-ch)      // 0, false (буфер пуст, канал закрыт)
fmt.Println(<-ch)      // 0, false (канал закрыт, не блокируется)
```

**Что происходит:**

- Первые два чтения возвращают **реальные данные** из буфера.
- Третье чтение: буфер пуст, канал закрыт → возвращает `zero, false`.
- Четвёртое: то же самое — не блокируется.

Это значит, что `range` по каналу **сначала отдаст все данные**, а потом завершится:

```go
ch := make(chan int, 3)
ch <- 1
ch <- 2
close(ch)

for v := range ch {
    fmt.Println(v)  // 1, 2 — и только потом цикл завершится
}
```

### Кто закрывает канал

**Правило:** канал закрывает **тот, кто пишет**.

```go
func producer(ch chan<- int) {
    defer close(ch)  // писатель закрывает
    for i := 0; i < 10; i++ {
        ch <- i
    }
}

func consumer(ch <-chan int) {
    for v := range ch {  // читатель читает до close
        fmt.Println(v)
    }
}
```

**Почему не читатель:** читатель не знает, когда писатель закончит. Если он закроет канал, а писатель попробует записать — паника.

**Почему не несколько писателей:** если писателей несколько, никто не знает, когда **все** закончат. Нужен `WaitGroup` + отдельная горутина для `close`.

### 💡 Практика: как использовать close

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Закрывай канал на писателе, не на читателе.**
2. **Проверяй `ok` при получении, если канал может быть закрыт.**
3. **Помни: `close` не стирает буфер.** `range` отдаст данные перед завершением.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для нескольких писателей — `WaitGroup` + `close` в отдельной горутине.**

**❌ НЕ ДЕЛАЙ:**

5. **Не закрывай канал дважды.** Паника.
6. **Не отправляй в закрытый канал.** Паника.
7. **Не думай, что `close` освобождает память.**

## 2.6 Паттерн: сигнал через close

Один из фундаментальных паттернов Go — использовать `close` как **broadcast-сигнал** для всех ждущих горутин.

### Идея

`close(ch)` разблокирует **всех** получателей. Это отличается от отправки значения `ch <- struct{}{}`, которая разбудит **только одного**.

Это делает `close` идеальным инструментом для сигналов «остановись», «готово», «отмена».

### Простейший пример

```go
done := make(chan struct{})

go func() {
    // ... работа ...
    close(done)  // сигнал: «готово»
}()

<-done  // ждём сигнала
```

Здесь `struct{}` — пустая структура, ноль байт. Мы передаём не данные, а **факт события**.

### Broadcast для нескольких горутин

```go
done := make(chan struct{})

for i := 0; i < 100; i++ {
    go func(id int) {
        <-done  // все 100 горутин ждут
        fmt.Printf("goroutine %d woke up\n", id)
    }(i)
}

time.Sleep(100 * time.Millisecond)
close(done)  // разбудит ВСЕ 100 горутин одновременно
time.Sleep(100 * time.Millisecond)
```

**Что происходит:**

- 100 горутин ждут `<-done`.
- `close(done)` разблокирует **все** — они одновременно получают `zero, false`.
- Если бы мы сделали `done <- struct{}{}` 100 раз — это разбудило бы их по одному, и нам пришлось бы отправить 100 значений.

### Где это используется

**1. `context.Context`.**

```go
ctx, cancel := context.WithCancel(context.Background())

go worker(ctx)

cancel()  // close(ctx.Done()) — все, кто ждёт, просыпаются
```

`ctx.Done()` — это канал, который закрывается при отмене. Это тот же паттерн «сигнал через close».

**2. Graceful shutdown.**

```go
shutdown := make(chan struct{})

go func() {
    <-shutdown
    // начать shutdown
}()

close(shutdown)  // сигнал всем компонентам
```

**3. Fan-in с завершением.**

Когда один из источников закрыт — сигнализируем остальным, что пора завершаться.

### Сравнение: `close` vs отправка

| Способ | Разблокирует | Память | Идемпотентно |
|:---|:---|:---|:---|
| `ch <- struct{}{}` | Одного | 0 байт | Нет |
| `close(ch)` | Всех | 0 байт | Нет (паника при повторе) |

**Когда использовать `close`:**

- Нужно разбудить **всех** ждущих.
- Сигнал означает **событие**, а не данные.
- Только один отправитель.

**Когда использовать отправку:**

- Нужно передать **данные**.
- Нужно разбудить **одного** из нескольких.
- Много отправителей.

### 💡 Практика: как использовать сигнал через close

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для broadcast-сигналов — `close`:**
   ```go
   done := make(chan struct{})
   close(done)
   ```

2. **Для одного сигнала — тоже `close`.** Проще, чем отправка `struct{}{}`.

**👍 СТОИТ СДЕЛАТЬ:**

3. **`chan struct{}` для сигналов** — ноль байт, ясно по смыслу.

**❌ НЕ ДЕЛАЙ:**

4. **Не закрывай канал дважды.** Паника.
5. **Не используй `close` для передачи данных.** Только для сигналов.

## 2.7 Паттерн: отправка без блокировки

Иногда нужно **не блокироваться**, если получатель не готов. Например, в HTTP-хэндлере: лучше вернуть ошибку «сервер занят», чем висеть.

### Проблема

```go
func handler(w http.ResponseWriter, r *http.Request) {
    tasksCh <- task  // ← если буфер полон — хэндлер виснет
    w.WriteHeader(http.StatusAccepted)
}
```

Если буфер `tasksCh` полон, хэндлер **блокируется**. При 1000 таких запросов — 1000 висящих соединений.

### Решение: select + default

```go
func handler(w http.ResponseWriter, r *http.Request) {
    select {
    case tasksCh <- task:
        w.WriteHeader(http.StatusAccepted)
    default:
        http.Error(w, "server busy", http.StatusServiceUnavailable)
    }
}
```

**Что происходит:**

- Если в буфере есть место → отправка проходит, отвечаем **202 Accepted**.
- Если буфер полон → `select` идёт в `default`, отвечаем **503 Service Unavailable**.
- Хэндлер **никогда не блокируется**.

### Вариант с таймаутом

Иногда лучше подождать немного:

```go
func handler(w http.ResponseWriter, r *http.Request) {
    select {
    case tasksCh <- task:
        w.WriteHeader(http.StatusAccepted)
    case <-time.After(100 * time.Millisecond):
        http.Error(w, "server busy", http.StatusServiceUnavailable)
    case <-r.Context().Done():
        return  // клиент отключился
    }
}
```

**Что происходит:**

- Если есть место → отправляем сразу.
- Если нет → ждём 100 мс.
- Если за 100 мс место не появилось → 503.
- Если клиент отключился → просто выходим.

### Тот же паттерн для получения

```go
select {
case v := <-ch:
    process(v)
default:
    // нет данных — делаем что-то другое
}
```

**Когда использовать:** для опроса канала без блокировки — например, в цикле, где есть другая работа.

### Где это критично

**1. HTTP-хэндлеры.**

Висящие соединения = 500-е ошибки для клиентов. Лучше быстро вернуть 503.

**2. Producer'ы с медленными consumer'ами.**

Если consumer тормозит, producer не должен копить бесконечно.

**3. Опрос нескольких каналов.**

В цикле обработки событий, где нельзя залипнуть на одном канале.

### 💡 Практика: как использовать неблокирующую отправку

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **В HTTP-хэндлерах — `select` с `default`:**
   ```go
   select {
   case tasksCh <- task:
       w.WriteHeader(http.StatusAccepted)
   default:
       http.Error(w, "server busy", http.StatusServiceUnavailable)
   }
   ```

2. **Для мягкого ожидания — `select` с таймаутом.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Проверять `ctx.Done()` в `select`** — для отмены.

**❌ НЕ ДЕЛАЙ:**

4. **Не отправляй в канал без `select` в хэндлере.** Висящие соединения.
5. **Не используй `default` там, где нужно гарантировать доставку.** Данные потеряются.

## 2.8 Направленные каналы

Направленные каналы ограничивают **направление** операций.

### Синтаксис

```go
chan T      // двунаправленный
chan<- T    // только для отправки
<-chan T    // только для получения
```

Стрелка показывает, куда идут данные.

### Зачем нужны

**1. Документация.** Функция, которая принимает `<-chan T`, **не может** отправить в канал. Это видно из сигнатуры.

**2. Защита от ошибок.** Компилятор не даст отправить в `<-chan T`.

### Пример

```go
func producer(ch chan<- int) {
    // ch — только для отправки
    for i := 0; i < 10; i++ {
        ch <- i
    }
    close(ch)
}

func consumer(ch <-chan int) {
    // ch — только для получения
    for v := range ch {
        fmt.Println(v)
    }
}

func main() {
    ch := make(chan int)  // двунаправленный
    go producer(ch)       // передаём как chan<- int
    consumer(ch)          // передаём как <-chan int
}
```

Двунаправленный канал **неявно преобразуется** в направленный при передаче в функцию. Обратно — нельзя.

### Внутреннее устройство

На уровне runtime направленные каналы — это **те же `hchan`**. Разница только на уровне типов. Компилятор проверяет, что нельзя отправить в `<-chan T`.

Это **zero-cost абстракция** — никаких накладных расходов.

### 💡 Практика: как использовать направленные каналы

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **В сигнатурах функций — направленные каналы:**
   ```go
   func producer(ch chan<- int)
   func consumer(ch <-chan int)
   ```

2. **Функции, возвращающие канал, — receive-only:**
   ```go
   func generate() <-chan int
   ```

**❌ НЕ ДЕЛАЙ:**

3. **Не пытайся преобразовать направленный канал обратно в двунаправленный.**

## 2.9 nil-канал

`nil`-канал — неинициализированный канал.

### Поведение

```go
var ch chan int  // ch == nil
```

| Операция | Поведение |
|:---|:---|
| Отправка `ch <- v` | **Блокируется навсегда** |
| Получение `<-ch` | **Блокируется навсегда** |
| `close(ch)` | **Паника** |
| `len(ch)`, `cap(ch)` | 0 |
| `select` с `case <-ch` | **Case игнорируется** |

### Зачем это нужно

`nil`-канал полезен в `select`: case с `nil`-каналом **никогда не выбирается**. Это позволяет **динамически отключать** case'ы.

Пример — чтение из двух каналов, один из которых может быть отключён:

```go
func merge(ch1, ch2 <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for ch1 != nil || ch2 != nil {
            select {
            case v, ok := <-ch1:
                if !ok {
                    ch1 = nil  // отключаем case
                    continue
                }
                out <- v
            case v, ok := <-ch2:
                if !ok {
                    ch2 = nil  // отключаем case
                    continue
                }
                out <- v
            }
        }
    }()
    return out
}
```

Когда `ch1` закрыт — `ch1 = nil`. Case `<-ch1` с `nil`-каналом **никогда не готов** — `select` его игнорирует. Цикл продолжается, пока хотя бы один канал не `nil`.

Это идиоматический паттерн для отключения case'ов.

### 💡 Практика: как использовать nil-канал

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: `nil`-канал блокируется навсегда вне `select`.**
2. **Используй `nil`-канал для отключения case'ов в `select`:**
   ```go
   case v, ok := <-ch:
       if !ok {
           ch = nil
           continue
       }
   ```

**❌ НЕ ДЕЛАЙ:**

3. **Не забывай инициализировать каналы.** `var ch chan int` без `make` — `nil`.
4. **Не закрывай `nil`-канал** — паника.

## 2.10 Практика Go: дедлок, утечки, диагностика

Разберём **три практических примера**: дедлок, утечка и диагностика.

### Пример 1: простой дедлок

Дедлок — ситуация, когда горутины ждут друг друга и никогда не завершатся. Даже простой код с каналами может привести к дедлоку.

```go
package main

import "fmt"

func main() {
    ch := make(chan int)
    ch <- 42  // ← блокируется: получателя нет
    
    fmt.Println(<-ch)  // никогда не выполнится
}
```

**Что происходит:**

1. `main` пытается отправить `42` в небуферизованный канал.
2. Получателя нет — `main` блокируется.
3. Строка `fmt.Println(<-ch)` не выполняется, потому что `main` уже заблокирован.
4. **Дедлок.**

**Runtime обнаруживает:**

```
fatal error: all goroutines are asleep - deadlock!
```

Runtime **обнаруживает** такой дедлок, потому что **все** горутины спят и **никто** не может их разбудить.

**Исправление:**

```go
ch := make(chan int, 1)  // буфер на 1
ch <- 42                 // не блокируется
fmt.Println(<-ch)        // 42
```

Или:

```go
ch := make(chan int)

go func() { ch <- 42 }()  // отправитель в горутине
fmt.Println(<-ch)         // 42
```

### Пример 2: утечка горутин через канал

Утечка горутин — родственная проблема. Горутина создаётся, но никогда не завершится.

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    fmt.Printf("goroutines before: %d\n", runtime.NumGoroutine())

    // Утечка: 1000 горутин пишут в небуферизованный канал без читателя
    for i := 0; i < 1000; i++ {
        ch := make(chan int)
        go func() {
            ch <- i  // блокируется навсегда
        }()
    }

    time.Sleep(100 * time.Millisecond)
    fmt.Printf("goroutines after: %d\n", runtime.NumGoroutine())

    // Дамп стеков
    buf := make([]byte, 1<<20)
    n := runtime.Stack(buf, true)
    fmt.Printf("goroutine dump (%d bytes):\n%s\n", n, buf[:n])
}
```

**Пример вывода:**

```
goroutines before: 1
goroutines after: 1001
goroutine dump (52345 bytes):
goroutine 1 [running]:
...
goroutine 18 [chan send]:
main.main.func1()
    /path/to/main.go:15 +0x...
created by main.main in goroutine 1
    /path/to/main.go:14 +0x...
... (повторяется 1000 раз)
```

**Что видно:** 1000 горутин в состоянии `chan send` на строке 15. Это утечка.

**Ключевое отличие от дедлока:** runtime **не обнаруживает** утечку как дедлок, потому что `main` **не спит** — он продолжает работу. Горутины висят в фоне.

### Пример 3: полная диагностика

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    // Мониторинг горутин в фоне
    go func() {
        for range time.Tick(500 * time.Millisecond) {
            fmt.Printf("[monitor] goroutines: %d\n", runtime.NumGoroutine())
        }
    }()

    // Утечка
    for i := 0; i < 100; i++ {
        ch := make(chan int)
        go func() {
            ch <- i
        }()
    }

    time.Sleep(2 * time.Second)
    fmt.Println("done")
}
```

**Пример вывода:**

```
[monitor] goroutines: 102
[monitor] goroutines: 102
[monitor] goroutines: 102
[monitor] goroutines: 102
done
```

**Что видно:** число горутин не падает — 102 и остаётся. Это утечка.

### Практика: демонстрация разных типов каналов

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    // Небуферизованный
    unbuffered := make(chan int)
    go func() { unbuffered <- 42 }()
    fmt.Println(<-unbuffered)  // 42

    // Буферизованный
    buffered := make(chan int, 3)
    buffered <- 1
    buffered <- 2
    buffered <- 3
    // buffered <- 4  // ← здесь заблокировалось бы
    fmt.Println(<-buffered)  // 1
    fmt.Println(<-buffered)  // 2
    fmt.Println(<-buffered)  // 3

    // Данные в буфере после close
    ch := make(chan int, 3)
    ch <- 1
    ch <- 2
    close(ch)

    for v := range ch {
        fmt.Println("from range:", v)  // 1, 2
    }

    v, ok := <-ch
    fmt.Printf("after close: v=%d, ok=%v\n", v, ok)  // v=0, ok=false

    // Сигнал через close
    done := make(chan struct{})
    for i := 0; i < 5; i++ {
        go func(id int) {
            <-done
            fmt.Printf("goroutine %d woke up\n", id)
        }(i)
    }
    time.Sleep(50 * time.Millisecond)
    close(done)
    time.Sleep(50 * time.Millisecond)
}
```

### 💡 Практика: как диагностировать проблемы с каналами

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Мониторь `runtime.NumGoroutine()`.**
2. **Дамп стеков при подозрении:**
   ```go
   buf := make([]byte, 1<<20)
   n := runtime.Stack(buf, true)
   log.Printf("goroutine dump: %s", buf[:n])
   ```

3. **Ищи горутины в `chan send`/`chan receive`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **pprof в production (localhost):**
   ```go
   import _ "net/http/pprof"
   go http.ListenAndServe("localhost:6060", nil)
   ```

**❌ НЕ ДЕЛАЙ:**

5. **Не игнорируй зависшие горутины.**
6. **Не используй `time.Sleep` для «ожидания» — используй каналы.**

## 2.11 Выводы и типичные ошибки

**Что мы узнали?**

Канал — это **точка синхронизации** между горутинами, а не очередь. Внутри — структура `hchan` с буфером и очередями `sendq`/`recvq`. Отправка и получение имеют три пути: быстрый (прямая передача), средний (буфер), медленный (блокировка). `close` — сигнал, не очистка; данные в буфере остаются доступны. Паттерн «сигнал через close» — для broadcast. Паттерн «отправка без блокировки» через `select` + `default`. Направленные каналы — zero-cost защита. `nil`-канал блокируется навсегда, но игнорируется в `select`.

**Типичные ошибки:**

- ❌ **Думать, что канал — очередь.** Канал — точка синхронизации.
- ❌ **Использовать буферизованный канал «на всякий случай».** Это маскирует проблемы синхронизации.
- ❌ **Отправлять в закрытый канал.** Паника.
- ❌ **Закрывать канал на читателе.** Паника при отправке.
- ❌ **Закрывать канал дважды.** Паника.
- ❌ **Думать, что `close` освобождает память или очищает буфер.**
- ❌ **Забывать про `nil`-канал.** Отправка/получение блокируются навсегда.
- ❌ **Не использовать направленные каналы в сигнатурах.**
- ❌ **Блокировать HTTP-хэндлер на отправке в канал.** Висящие соединения.
- ❌ **Игнорировать утечки горутин на каналах.**

## 2.12 Для быстрого повторения

- **Канал — не очередь.** Это точка синхронизации. Небуферизованный — рандеву. Буферизованный — развязка через буфер.
- **`hchan`** — структура канала (~96 байт): `qcount`, `dataqsiz`, `buf`, `sendq`, `recvq`, `lock`.
- **Три пути отправки/получения:** быстрый (прямая передача), средний (буфер), медленный (`gopark`).
- **`close(ch)`** — сигнал, не очистка. Разблокирует всех получателей. **Не стирает буфер** — данные остаются доступны.
- **Кто пишет — тот закрывает.** Писатель знает, когда закончил.
- **Паттерн «сигнал через close»** — для broadcast. Разбудит **всех**, а не одного.
- **Паттерн «отправка без блокировки»** — `select` + `default`. Для HTTP-хэндлеров.
- **Направленные каналы** — `chan<- T`, `<-chan T`. Zero-cost.
- **`nil`-канал** — блокируется навсегда вне `select`, игнорируется в `select`.
- **Для сигналов — `chan struct{}` + `close`.**
- **Для семафора — буферизованный канал с `struct{}`.**
- **Диагностика:** `runtime.NumGoroutine()`, pprof `debug/pprof/goroutine?debug=2`.

## 2.14 Ответы

### Ответ 1

Канал — **точка синхронизации**, а не очередь. В классической очереди producer кладёт элемент и идёт дальше. В канале producer **вступает в отношение** с consumer'ом. Для небуферизованного канала — рандеву: обе стороны ждут друг друга. Для буферизованного — развязка через буфер, но при переполнении producer блокируется.

### Ответ 2

**Небуферизованный:** `dataqsiz = 0`. Отправка блокируется, пока получатель не готов. Строгая синхронизация.

**Буферизованный:** `dataqsiz = N > 0`. Отправка блокируется, только если буфер полон. Ослабленная синхронизация.

### Ответ 3

Если получатель ждёт (в `recvq`), runtime:

1. Извлекает `sudog` получателя из `recvq`.
2. **Копирует данные напрямую** из стека отправителя в стек получателя.
3. Будит получателя.
4. Отправитель не блокируется.

### Ответ 4

`close(ch)`:

1. Устанавливает флаг `closed = 1`.
2. Разблокирует всех получателей — они получат `zero, false`.
3. Отправители получат панику.

**Что с данными в буфере:** они **остаются доступны**. `<-ch` вернёт их по одному, а когда буфер опустеет — вернёт `zero, false`.

### Ответ 5

**Писатель.** Он знает, когда закончил. Читатель не знает, будут ли ещё записи.

Если писателей несколько — `WaitGroup` + отдельная горутина для `close`.

### Ответ 6

**Broadcast через close:**

```go
done := make(chan struct{})

for i := 0; i < 100; i++ {
    go func() {
        <-done  // ждут все
    }()
}

close(done)  // разбудит всех сразу
```

`close` разблокирует **всех** получателей. Отправка `struct{}{}` разбудила бы только одного.

### Ответ 7

**Неблокирующая отправка:**

```go
select {
case ch <- v:
    // отправлено
default:
    // буфер полон — не блокируемся
}
```

**С таймаутом:**

```go
select {
case ch <- v:
case <-time.After(100 * time.Millisecond):
case <-ctx.Done():
}
```

### Ответ 8

**`nil`-канал** — неинициализированный. Вне `select`: отправка/получение блокируются навсегда. В `select`: case игнорируется — `nil`-канал никогда не готов. Используется для отключения case'ов.

### Ответ 9

**Направленные каналы:**

- **Документация.** Функция, принимающая `<-chan T`, не может отправить.
- **Защита от ошибок.** Компилятор проверяет.
- **Zero-cost.** На уровне runtime — те же `hchan`.

## 2.16 Чек-лист

| Компонент | Что это | Ключевые факты |
|:---|:---|:---|
| **Канал** | Точка синхронизации | Не очередь |
| **`hchan`** | Структура канала | ~96 байт: `qcount`, `buf`, `sendq`, `recvq`, `lock` |
| **Небуферизованный** | `make(chan T)` | `dataqsiz = 0`. Отправка блокируется, пока получатель не готов |
| **Буферизованный** | `make(chan T, N)` | `dataqsiz = N`. Отправка блокируется только если буфер полон |
| **Три пути отправки** | Быстрый / средний / медленный | Прямая передача / буфер / `gopark` |
| **Три пути получения** | Быстрый / средний / медленный | Прямая передача / буфер / `gopark` |
| **`close(ch)`** | Сигнал | Разблокирует всех получателей. **Не стирает буфер** |
| **Кто закрывает** | Писатель | Не читатель. Несколько писателей — `WaitGroup` |
| **Сигнал через close** | Broadcast | Разбудит всех. `chan struct{}` |
| **Отправка без блокировки** | `select` + `default` | Для HTTP-хэндлеров |
| **Направленные** | `chan<- T`, `<-chan T` | Zero-cost |
| **`nil`-канал** | Неинициализированный | Блокируется навсегда вне `select`, игнорируется в `select` |
| **Семафор** | Буферизованный `struct{}` | Размер буфера = число разрешений |

📡 **Ключевая идея:** Канал — это **не очередь**, а **точка синхронизации**. Внутри — структура `hchan` с буфером и очередями `sendq`/`recvq`. Отправка и получение имеют три пути: быстрый (прямая передача), средний (буфер), медленный (`gopark`). `close` — сигнал, не очистка; данные в буфере остаются доступны. Паттерн «сигнал через close» — для broadcast. Паттерн «отправка без блокировки» — `select` + `default` для HTTP-хэндлеров. Направленные каналы — zero-cost защита. `nil`-канал блокируется навсегда, но игнорируется в `select`. Главные проблемы: утечки горутин, отправка в закрытый канал, закрытие на читателе, блокировка хэндлера.
