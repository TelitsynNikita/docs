## 2.0 Пролог: очередь, которая ничего не помнит

Ты пишешь обработчик заказов. Логика простая: HTTP-хэндлер принимает заказ, кладёт его в «очередь», а фоновый воркер забирает и обрабатывает.

Ты пишешь:

```go
package main

import (
    "fmt"
    "net/http"
    "time"
)

var orders = make(chan Order, 100)

func main() {
    go worker()
    http.HandleFunc("/order", handleOrder)
    http.ListenAndServe(":8080", nil)
}

func handleOrder(w http.ResponseWriter, r *http.Request) {
    order := parseOrder(r)
    orders <- order  // кладём в «очередь»
    w.WriteHeader(http.StatusAccepted)
}

func worker() {
    for order := range orders {
        process(order)
    }
}
```

Всё работает. Пока не приходит **1001-й заказ за секунду**. Канал на 100 элементов переполняется, `orders <- order` **блокируется**, HTTP-хэндлер висит, клиент ждёт ответа. Через минуту сервер лежит.

Ты идёшь читать документацию и видишь: «канал — это труба, через которую горутины обмениваются данными». Но что это значит **на самом деле**?

❓ **Вопрос: если канал — это труба, почему он не может «принять» заказ и отпустить отправителя?**

💡 **Ответ:** потому что канал — это **не очередь**. Это **точка рандеву** (rendezvous point) между двумя горутинами. Отправитель и получатель **синхронизируются** в момент передачи. Если получатель не готов — отправитель ждёт. Если буфер полон — отправитель ждёт. Это не баг, это **свойство**.

Канал — это не «положил и забыл». Это «положил и жди, пока кто-то возьмёт» (для небуферизованного) или «положил, если есть место в буфере» (для буферизованного). Разница между этими двумя режимами — фундаментальна.

> **Важный мост к будущим главам:** Worker pool (Глава 7) строится на канале задач, куда producer'ы кладут работу. Fan-in/Fan-out (Глава 8) — на слиянии и разделении каналов. Pipeline (Глава 8) — на цепочке каналов. Context (Глава 5) — на канале `ctx.Done()`. Все эти паттерны работают **только если ты понимаешь, что канал — это не очередь**. Начнём с внутреннего устройства.

## 2.1 Канал — это не очередь: смена парадигмы

Прежде чем разбирать `hchan`, нужно снять главное заблуждение.

### Заблуждение: «канал — это очередь»

Многие приходят из мира, где «очередь» — это структура данных: `push` в конец, `pop` из начала. Очередь **буферизует** элементы и **развязывает** отправителя и получателя по времени.

```
Очередь (классическая):
  Producer ──push──▶ [1][2][3][4][5] ──pop──▶ Consumer
  Producer не ждёт Consumer. Он кладёт и идёт дальше.
```

**Канал в Go — не так.** Канал — это **точка синхронизации**. Когда горутина пишет в канал, она **вступает в отношение** с читателем (или с буфером). Это отношение может включать ожидание.

### Что такое канал на самом деле

**Канал** — это **синхронизированная типизированная труба**, через которую одна горутина передаёт значение другой. Ключевое слово — **синхронизированная**.

Формальное определение (из спецификации Go):

> Канал — это механизм, который позволяет одной горутине отправлять значения определённого типа другой горутине. Операции отправки и получения **синхронизируются**: если одна горутина отправляет значение в канал, а другая получает его, обе операции завершаются только когда обе стороны готовы.

### Два режима работы

**Небуферизованный канал** (`make(chan T)`):

```
Отправитель ──────┐
                  ├──► Рандеву (синхронизация)
Получатель ───────┘

Отправитель ЖДЁТ, пока получатель не будет готов.
Получатель ЖДЁТ, пока отправитель не будет готов.
```

**Это не передача данных — это обмен сигналами: «я готов отдать» ↔ «я готов взять».**

**Буферизованный канал** (`make(chan T, N)`):

```
Отправитель ──▶ [буфер N] ──▶ Получатель

Если в буфере есть место — отправитель кладёт и идёт дальше.
Если буфер пуст — получатель ждёт.
Если буфер полон — отправитель ждёт.
```

**Это уже ближе к очереди, но с ограничениями:** буфер фиксированного размера, при переполнении — блокировка.

### Аналогия: передача ключа из рук в руки

**Небуферизованный канал — это передача ключа из рук в руки.**

- Один человек держит ключ и **ждёт**, пока другой протянет руку.
- Только когда руки встречаются — ключ переходит.
- Если второй не протягивает руку — первый **стоит и ждёт** (не кладёт ключ на землю и не уходит).

**Буферизованный канал — это ящик для ключей.**

- Можно положить ключ в ящик и уйти (если в ящике есть место).
- Другой придёт и заберёт.
- Если ящик полон — придётся **стоять и ждать**, пока кто-то заберёт ключи.

**Ключевая разница:** в небуферизованном случае отправитель и получатель **встречаются**. В буферизованном — **развязываются по времени**, но не полностью (буфер ограничен).

### Почему это важно на практике

**Пример 1: HTTP-хэндлер и воркер (из пролога).**

```go
orders := make(chan Order, 100)

// В хэндлере:
orders <- order  // если буфер полон — БЛОКИРОВКА
```

Если хэндлер блокируется — HTTP-запрос висит. Клиент ждёт. Если таких запросов 1000 — 1000 висящих соединений.

**Решение:** использовать `select` с `default`:

```go
select {
case orders <- order:
    // приняли
    w.WriteHeader(http.StatusAccepted)
default:
    // буфер полон — отказываем
    w.WriteHeader(http.StatusServiceUnavailable)
}
```

Или увеличить буфер, или использовать worker pool (Глава 7), или backpressure через context.

**Пример 2: «сигнальный» канал.**

```go
done := make(chan struct{})

go func() {
    // ... работа ...
    close(done)  // сигнал: «готово»
}()

<-done  // ждём сигнала
```

Здесь канал используется **не для передачи данных**, а для **синхронизации**: «я закончил». `struct{}` — пустая структура, ноль байт. Это идиоматический способ передать сигнал.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Отправка в небуферизованный канал (есть получатель) | ~50-100 нс | 0 | Синхронизация |
| Отправка в небуферизованный канал (нет получателя) | ~∞ (gopark) | sudog (~48 байт) | Ожидание |
| Отправка в буферизованный канал (есть место) | ~30-70 нс | размер элемента | Асинхронная передача |
| Отправка в буферизованный канал (буфер полон) | ~∞ (gopark) | sudog | Backpressure |
| Получение из канала | ~50-100 нс | 0 | Синхронизация |

### 💡 Практика: как думать о канале

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Думай о канале как о точке синхронизации**, а не как об очереди. Отправка — это «я готов отдать», получение — «я готов взять».

2. **Для сигналов используй `chan struct{}`:**
   ```go
   done := make(chan struct{})
   close(done)  // сигнал всем читателям
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Небуферизованный канал — когда важна синхронизация.** Например, «дождись, пока воркер возьмёт задачу».

4. **Буферизованный канал — когда важна пропускная способность.** Например, «пусть producer'ы не ждут, пока буфер не полон».

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Очень большой буфер.** Если буфер на 10 000, producer'ы почти никогда не блокируются. Но это маскирует проблему: если consumer не успевает — данные копятся.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй канал как «очередь на всякий случай».** Если тебе нужна настоящая очередь — посмотри на Kafka, NATS, Redis Streams или `container/heap`.

7. **Не блокируй HTTP-хэндлер на отправке в канал без `select` + `default`.** Это приводит к висящим соединениям.

### Ключевые выводы подглавы 2.1

- **Канал — это не очередь.** Это точка синхронизации между горутинами.
- **Небуферизованный канал** — рандеву: отправитель и получатель ждут друг друга.
- **Буферизованный канал** — развязка по времени, но с ограниченным буфером.
- **Канал для сигналов** — `chan struct{}`, ноль байт, `close` как сигнал.
- **Блокировка на канале** — не баг, а свойство. Но её нужно обрабатывать (`select` + `default`, context, worker pool).

## 2.2 hchan: как устроен канал внутри

Теперь заглянем внутрь. Канал в runtime Go представлен структурой `hchan`. Разберём её.

### Структура hchan

```go
type hchan struct {
    qcount   uint           // число элементов в буфере сейчас
    dataqsiz uint           // размер буфера (capacity)
    buf      unsafe.Pointer // указатель на кольцевой буфер (если буферизованный)
    elemsize uint16         // размер элемента в байтах
    closed   uint32         // 1, если канал закрыт
    
    elemtype *_type         // тип элемента (для GC и копирования)
    
    sendx    uint           // индекс, куда писать следующий элемент (в buf)
    recvx    uint           // индекс, откуда читать следующий элемент (из buf)
    
    recvq    waitq          // очередь горутин, ждущих получения
    sendq    waitq          // очередь горутин, ждущих отправки
    
    lock     mutex          // мьютекс для защиты всех полей
}
```

**Размер `hchan`** — около **96 байт** (на 64-битной системе). Плюс буфер (если буферизованный).

### Разбор полей

**`qcount`** — сколько элементов в буфере **сейчас**. Для небуферизованного канала всегда 0.

**`dataqsiz`** — размер буфера (capacity). Для небуферизованного канала 0.

**`buf`** — указатель на **кольцевой буфер**. Для небуферизованного канала `nil`.

```
Кольцевой буфер (dataqsiz = 4):

  ┌─────┬─────┬─────┬─────┐
  │ [0] │ [1] │ [2] │ [3] │
  └─────┴─────┴─────┴─────┘
    ▲                 ▲
    │                 │
  recvx             sendx
  (читаем отсюда)   (пишем сюда)

Когда sendx доходит до конца — оборачивается в 0.
```

**`elemsize`** — размер одного элемента в байтах. Для `chan int` — 8 (на 64-битной), для `chan struct{}` — 0.

**`closed`** — флаг: 1, если канал закрыт. Защищён мьютексом.

**`elemtype`** — указатель на тип элемента. Нужен для GC: runtime должен знать, какие элементы в буфере являются указателями (для обхода при сборке мусора).

**`sendx` / `recvx`** — индексы в кольцевом буфере. `sendx` — куда писать следующий элемент, `recvx` — откуда читать.

**`recvq`** — очередь горутин, **ждущих получения**. Каждая горутина представлена структурой `sudog`.

**`sendq`** — очередь горутин, **ждущих отправки**. Тоже `sudog`.

**`lock`** — мьютекс. Защищает **все** поля `hchan`. Любая операция с каналом (отправка, получение, close) захватывает этот мьютекс.

### Структура sudog: горутина в очереди ожидания

Когда горутина блокируется на канале, она оборачивается в `sudog` и добавляется в `sendq` или `recvq`.

```go
type sudog struct {
    g          *g           // горутина, которая ждёт
    next       *sudog       // следующий в очереди
    prev       *sudog       // предыдущий в очереди
    elem       unsafe.Pointer // указатель на данные (куда писать/откуда читать)
    acquiretime int64       // для трейсинга
    releasetime int64       // для трейсинга
    isSelect   bool         // true, если горутина ждёт в select
    ...
}
```

**Размер `sudog`** — около **48-64 байт**.

**Зачем `elem`:** когда отправитель блокируется, он передаёт **указатель на свои данные**. Когда получатель появится, runtime скопирует данные **напрямую** из отправителя в получателя (без промежуточного буфера).

### Визуализация канала

```
Небуферизованный канал make(chan int):

  hchan:
    qcount:   0
    dataqsiz: 0
    buf:      nil
    elemsize: 8
    closed:   0
    sendx:    0
    recvx:    0
    recvq:    [G1, G2]     ← горутины, ждущие получения
    sendq:    [G3]         ← горутины, ждущие отправки
    lock:     unlocked

Буферизованный канал make(chan int, 4):

  hchan:
    qcount:   2             ← в буфере 2 элемента
    dataqsiz: 4             ← размер буфера 4
    buf:      ──────┐
    elemsize: 8     │
    closed:   0     │
    sendx:    2     │       ← следующая запись в индекс 2
    recvx:    0     │       ← следующее чтение из индекса 0
    recvq:    []    │
    sendq:    []    │
    lock:     unlocked
                    │
                    ▼
                  ┌─────┬─────┬─────┬─────┐
                  │ 42  │ 17  │     │     │
                  └─────┴─────┴─────┴─────┘
                    ▲                 ▲
                  recvx             sendx
                  (читаем 42)      (пишем в индекс 2)
```

### Ключевая идея: канал — это структура с мьютексом

Все операции с каналом (отправка, получение, close) захватывают **один и тот же мьютекс** `hchan.lock`. Это делает канал **потокобезопасным** — но также означает, что **операции с одним каналом сериализуются**.

**Важно:** разные каналы имеют **разные мьютексы**. Если у тебя 100 каналов, операции с ними могут выполняться параллельно.

### Кто владеет каналом

**Канал создаётся в куче.** `make(chan T, N)` выделяет `hchan` + буфер (если N > 0) через `mallocgc`. Возвращается **указатель** на `hchan`.

**Канал не освобождается при `close`.** Он освобождается **только сборщиком мусора**, когда на `hchan` не осталось ссылок. `close` только устанавливает флаг `closed = 1` — это не освобождение памяти.

**Это важно:** если у тебя есть ссылка на канал, но он закрыт — память всё ещё занята. GC освободит её, только когда все ссылки исчезнут.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `make(chan T)` | ~50-100 нс | ~96 байт (hchan) | Небуферизованный канал |
| `make(chan T, N)` | ~100-200 нс | 96 + N × elemsize | Буферизованный канал |
| Захват мьютекса канала | ~10-30 нс | 0 | Каждая операция |
| Создание sudog | ~50-100 нс | ~48-64 байт | При блокировке |

### 💡 Практика: что важно знать про hchan

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: канал имеет мьютекс.** Операции с одним каналом сериализуются. Если нужна параллельность — используй несколько каналов.

2. **Помни: `close` не освобождает память.** Канал освобождается GC, когда на него не осталось ссылок.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для сигналов — `chan struct{}`** (elemsize = 0, ноль байт на буфер).

4. **Для передачи мелких данных — `chan int`, `chan uint64`** (elemsize = 8).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать точный размер hchan.** Но полезно понимать, что каждый канал — это ~100 байт + буфер.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай канал на каждый чих.** 100 000 каналов = ~10 МБ только на hchan. Если можно переиспользовать — переиспользуй.

### Ключевые выводы подглавы 2.2

- **Канал — это структура `hchan`** (~96 байт) + буфер (если буферизованный).
- **Все поля защищены мьютексом `hchan.lock`.** Операции с одним каналом сериализуются.
- **`buf`** — кольцевой буфер для буферизованных каналов. **`sendx`/`recvx`** — индексы записи/чтения.
- **`sendq`/`recvq`** — очереди горутин, ждущих отправки/получения. Каждая — `sudog` (~48-64 байт).
- **`sudog` хранит указатель на данные** (`elem`), чтобы runtime мог скопировать напрямую из отправителя в получателя.
- **`close` не освобождает память** — только ставит флаг `closed`. Память освобождает GC.

## 2.3 Отправка в канал: путь от ch <- v до gopark

Теперь разберём, **что происходит**, когда горутина выполняет `ch <- v`. Это самая важная часть главы: понимание этого пути даёт понимание всех паттернов.

### Быстрый путь: получатель уже ждёт

**Ситуация:** в `recvq` есть горутина, которая ждёт получения.

```go
// Горутина A: ch <- 42
// Горутина B (в recvq): v := <-ch
```

**Что делает runtime:**

```
runtime.chansend(c, elem, block):

  1. Захватить lock канала.
  
  2. Проверить: closed == 1?
     → Если да: panic("send on closed channel").
  
  3. Проверить recvq: есть ли ждущий получатель?
     → Да! (горутина B в recvq)
  
  4. Взять sudog горутины B из recvq (dequeue).
  
  5. Скопировать данные НАПРЯМУЮ:
     Из elem (данные горутины A) → в sudog.elem (данные горутины B).
     
     ⚡ Это ключевой момент: нет промежуточного буфера!
     Данные идут из стека отправителя в стек получателя.
  
  6. Разбудить горутину B: goready(sudog.g).
     → B переходит из _Gwaiting в _Grunnable.
     → B ставится в очередь P.
  
  7. Отпустить lock канала.
  
  8. Вернуться из chansend.
  
  Горутина A продолжает работу.
```

**Это быстрый путь:** ни A, ни B не блокируются. A отправляет данные, будит B, и идёт дальше.

**Время:** ~50-100 нс. Одно копирование данных.

### Средний путь: буфер, есть место

**Ситуация:** буферизованный канал, в буфере есть место, `recvq` пуста.

```go
ch := make(chan int, 4)
ch <- 42  // буфер пуст, recvq пуста
```

**Что делает runtime:**

```
runtime.chansend:

  1. Захватить lock.
  2. closed? Нет.
  3. recvq пуста? Да.
  4. qcount < dataqsiz? Да (0 < 4).
  
  5. Скопировать данные в буфер:
     buf[sendx] = elem
     sendx = (sendx + 1) % dataqsiz
     qcount++
  
  6. Отпустить lock.
  7. Вернуться.
  
  Горутина A продолжает работу БЕЗ блокировки.
```

**Это средний путь:** A не блокируется, но данные скопированы в буфер.

**Время:** ~30-70 нс. Одно копирование данных.

### Медленный путь: буфер полон (или небуферизованный без получателя)

**Ситуация:** буфер полон (или канал небуферизованный, и получателя нет).

```go
// Буферизованный, полный:
ch := make(chan int, 4)
ch <- 1; ch <- 2; ch <- 3; ch <- 4
ch <- 5  // блокировка

// Или небуферизованный без получателя:
ch := make(chan int)
ch <- 42  // блокировка
```

**Что делает runtime:**

```
runtime.chansend:

  1. Захватить lock.
  2. closed? Нет.
  3. recvq пуста? Да.
  4. qcount < dataqsiz? НЕТ (буфер полон).
  
  5. Создать sudog для горутины A:
     sudog.g = A
     sudog.elem = &v  (указатель на данные A)
     sudog.c = c
  
  6. Добавить sudog в sendq (enqueue).
  
  7. Отпустить lock.
  
  8. Вызвать gopark:
     gopark(chanparkcommit, ..., waitReasonChanSend):
       - Установить g.atomicstatus = _Gwaiting.
       - Установить g.waitreason = waitReasonChanSend.
       - Вызвать schedule() — переключиться на другую горутину.
  
  Горутина A ЗАБЛОКИРОВАНА. Она не занимает M.
  M свободен для других горутин.
```

**Это медленный путь:** A блокируется. Её `sudog` ждёт в `sendq`. Когда появится получатель — он **напрямую** скопирует данные из `sudog.elem`.

**Время:** A блокируется на неопределённый срок. Стоимость `gopark` — ~100-200 нс + время ожидания.

### Полная схема: три пути отправки

```
ch <- v
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  runtime.chansend(c, elem, block)                        │
│                                                           │
│  1. lock(c.lock)                                         │
│  2. if c.closed: panic                                   │
│                                                           │
│  3. if recvq не пуста:                                   │
│     ├─ sudog := dequeue(recvq)                           │
│     ├─ copy(sudog.elem, elem)   ← ПРЯМАЯ ПЕРЕДАЧА        │
│     ├─ goready(sudog.g)         ← РАЗБУДИТЬ ПОЛУЧАТЕЛЯ   │
│     └─ unlock; return                                    │
│                                                           │
│  4. if qcount < dataqsiz:                                │
│     ├─ buf[sendx] = elem        ← КОПИРОВАНИЕ В БУФЕР    │
│     ├─ sendx = (sendx+1) % dataqsiz                      │
│     ├─ qcount++                                          │
│     └─ unlock; return                                    │
│                                                           │
│  5. // Буфер полон или небуферизованный без получателя   │
│     if !block:                                           │
│       └─ unlock; return false  ← НЕБЛОКИРУЮЩАЯ ОТПРАВКА  │
│                                                           │
│     ├─ sudog := acquireSudog()                           │
│     ├─ sudog.g = current_g                               │
│     ├─ sudog.elem = &elem                                │
│     ├─ enqueue(sendq, sudog)                             │
│     ├─ unlock                                            │
│     └─ gopark(...)              ← БЛОКИРОВКА             │
│                                                           │
└──────────────────────────────────────────────────────────┘
```

### Важно: прямая передача данных

**Ключевой момент быстрого пути:** данные копируются **напрямую** из стека отправителя в стек получателя. Нет промежуточного буфера.

```
Горутина A (отправитель):         Горутина B (получатель):
  v := 42                           var result int
  ch <- v                           result = <-ch
       │                                  ▲
       │                                  │
       │      copy(sudog.elem, &v)        │
       └──────────────────────────────────┘
       
  sudog.elem указывает на result в стеке B.
  Данные идут из стека A в стек B напрямую.
```

**Почему это важно:** для небуферизованного канала **нет буфера**. Данные передаются из рук в руки.

**Для больших структур:** копирование может быть дорогим. Поэтому для больших данных передают **указатели** (`chan *BigStruct`), а не значения.

### Что происходит с M при gopark

Когда горутина A вызывает `gopark`, runtime:

1. Сохраняет контекст A в `g.sched` (SP, PC, BP).
2. Устанавливает `g.atomicstatus = _Gwaiting`.
3. Вызывает `schedule()` — планировщик выбирает следующую горутину.
4. M (поток ОС) переключается на стек другой горутины.

**M не блокируется!** Он продолжает выполнять другие горутины. Это ключевое отличие от блокировки потока ОС.

**Когда A разбудят:** получатель вызовет `goready(A)`, A перейдёт в `_Grunnable` и попадёт в очередь P. При следующем переключении планировщик выберет A.

### Аннотация сложности

| Путь | Time | Space | Use case |
|:---|:---|:---|:---|
| Быстрый (получатель ждёт) | ~50-100 нс | 0 | Небуферизованный с получателем |
| Средний (буфер есть место) | ~30-70 нс | размер элемента | Буферизованный, не полный |
| Медленный (gopark) | ~100-200 нс + ожидание | sudog (~64 байт) | Буфер полон / нет получателя |

### 💡 Практика: что важно знать про отправку

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: отправка в небуферизованный канал блокируется, пока получатель не будет готов.** Это синхронизация, а не «положил и забыл».

2. **Для больших структур — передавай указатели:**
   ```go
   ch := make(chan *BigStruct)  // ✅
   // ch := make(chan BigStruct)  // ❌ копирование при каждой передаче
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Оценивай размер буфера.** Маленький буфер → частые блокировки. Большой буфер → накопление данных при медленном consumer'е.

4. **Используй `select` с `default` для неблокирующей отправки:**
   ```go
   select {
   case ch <- v:
       // отправили
   default:
       // канал полон — не блокируемся
   }
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Небуферизованный канал для синхронизации.** Часто лучше `chan struct{}` + `close` (сигнал всем).

**❌ НЕ ДЕЛАЙ:**

6. **Не отправляй в закрытый канал** — паника. Всегда проверяй или используй `select`.

7. **Не игнорируй блокировку в HTTP-хэндлере** — висящие соединения.

### Ключевые выводы подглавы 2.3

- **Три пути отправки:** быстрый (получатель ждёт), средний (буфер есть место), медленный (gopark).
- **Быстрый путь:** данные копируются **напрямую** из стека отправителя в стек получателя. Получатель разбужен.
- **Средний путь:** данные копируются в кольцевой буфер. Отправитель продолжает работу.
- **Медленный путь:** отправитель блокируется, его `sudog` ждёт в `sendq`. M освобождается для других горутин.
- **Прямая передача** — ключевая оптимизация небуферизованных каналов.
- **Для больших структур — указатели.**

## 2.4 Получение из канала: путь от <-ch до пробуждения отправителя

Получение — зеркальная операция. Разберём её.

### Быстрый путь: отправитель уже ждёт

**Ситуация:** в `sendq` есть горутина, которая ждёт отправки.

```go
// Горутина A (в sendq): ch <- 42
// Горутина B: v := <-ch
```

**Что делает runtime:**

```
runtime.chanrecv(c, elem, block):

  1. Захватить lock.
  
  2. Проверить: closed == 1 и qcount == 0?
     → Если да: 
        elem = zero_value
        return false  (получение из закрытого канала)
  
  3. Проверить sendq: есть ли ждущий отправитель?
     → Да! (горутина A в sendq)
  
  4. Взять sudog горутины A из sendq (dequeue).
  
  5. Скопировать данные:
     Из sudog.elem (данные A) → в elem (данные B).
     
     ⚡ Прямая передача.
  
  6. Если буфер был полон (dataqsiz > 0):
     → Взять следующий элемент из буфера и записать в sudog.elem.
     → Обновить recvx, sendx, qcount.
     
     Это нужно, чтобы сохранить порядок FIFO.
  
  7. Разбудить горутину A: goready(sudog.g).
  
  8. Отпустить lock.
  
  Горутина B продолжает работу с полученными данными.
```

**Время:** ~50-100 нс.

### Средний путь: буфер, есть данные

**Ситуация:** буферизованный канал, в буфере есть данные.

```go
ch := make(chan int, 4)
ch <- 42  // в буфере
v := <-ch  // читаем
```

**Что делает runtime:**

```
runtime.chanrecv:

  1. Захватить lock.
  2. closed? Нет.
  3. sendq пуста? Да.
  4. qcount > 0? Да.
  
  5. Скопировать из буфера:
     elem = buf[recvx]
     recvx = (recvx + 1) % dataqsiz
     qcount--
  
  6. Отпустить lock.
  7. Вернуться.
```

**Время:** ~30-70 нс.

### Медленный путь: буфер пуст (или небуферизованный без отправителя)

**Ситуация:** буфер пуст, `sendq` пуста.

**Что делает runtime:**

```
runtime.chanrecv:

  1. Захватить lock.
  2. closed? Нет.
  3. sendq пуста? Да.
  4. qcount > 0? Нет.
  
  5. Создать sudog для горутины B:
     sudog.g = B
     sudog.elem = &v
     sudog.c = c
  
  6. Добавить sudog в recvq.
  
  7. Отпустить lock.
  
  8. Вызвать gopark:
     - B переходит в _Gwaiting.
     - B.waitreason = waitReasonChanReceive.
     - M переключается на другую горутину.
  
  Горутина B ЗАБЛОКИРОВАНА.
```

**Время:** B блокируется на неопределённый срок.

### Полная схема: три пути получения

```
v := <-ch
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  runtime.chanrecv(c, elem, block)                        │
│                                                           │
│  1. lock(c.lock)                                         │
│                                                           │
│  2. if c.closed && qcount == 0:                          │
│     ├─ elem = zero                                       │
│     └─ unlock; return false  ← ЗАКРЫТЫЙ КАНАЛ            │
│                                                           │
│  3. if sendq не пуста:                                   │
│     ├─ sudog := dequeue(sendq)                           │
│     ├─ copy(elem, sudog.elem)   ← ПРЯМАЯ ПЕРЕДАЧА        │
│     ├─ if dataqsiz > 0:                                  │
│     │    buf-манипуляции для сохранения FIFO             │
│     ├─ goready(sudog.g)         ← РАЗБУДИТЬ ОТПРАВИТЕЛЯ  │
│     └─ unlock; return true                               │
│                                                           │
│  4. if qcount > 0:                                       │
│     ├─ elem = buf[recvx]        ← ЧТЕНИЕ ИЗ БУФЕРА       │
│     ├─ recvx = (recvx+1) % dataqsiz                      │
│     ├─ qcount--                                          │
│     └─ unlock; return true                               │
│                                                           │
│  5. // Буфер пуст или небуферизованный без отправителя   │
│     if !block:                                           │
│       └─ unlock; return false  ← НЕБЛОКИРУЮЩЕЕ ПОЛУЧЕНИЕ │
│                                                           │
│     ├─ sudog := acquireSudog()                           │
│     ├─ sudog.g = current_g                               │
│     ├─ sudog.elem = &elem                                │
│     ├─ enqueue(recvq, sudog)                             │
│     ├─ unlock                                            │
│     └─ gopark(...)              ← БЛОКИРОВКА             │
│                                                           │
└──────────────────────────────────────────────────────────┘
```

### Особый случай: получение из закрытого канала

```go
ch := make(chan int, 4)
ch <- 1
ch <- 2
close(ch)

v, ok := <-ch  // v = 1, ok = true
v, ok = <-ch   // v = 2, ok = true
v, ok = <-ch   // v = 0, ok = false
```

**Что делает runtime:**

```
runtime.chanrecv:

  1. Захватить lock.
  2. closed == 1 И qcount == 0? 
     → Да.
  3. elem = zero_value (нулевое значение типа).
  4. Вернуть false (второе значение ok).
  5. Отпустить lock.
```

**Ключевой момент:** закрытый канал с данными в буфере **сначала отдаёт данные**, и только потом возвращает `zero, false`.

```
Буферизованный канал, закрытый:
  ch <- 1; ch <- 2; close(ch)
  
  <-ch  → 1, true
  <-ch  → 2, true
  <-ch  → 0, false  ← буфер пуст, канал закрыт
  <-ch  → 0, false  ← то же самое, не блокируется
```

### Получение через range

```go
for v := range ch {
    process(v)
}
```

**Что делает runtime:**

```
for v := range ch:

  1. v, ok := <-ch
  2. if !ok: break
  3. process(v)
  4. goto 1
```

**Эквивалентно:**

```go
for {
    v, ok := <-ch
    if !ok {
        break
    }
    process(v)
}
```

**range завершается, когда канал закрыт И буфер пуст.** Это важно: если в буфере есть данные, range их отдаст, потом завершится.

### Аннотация сложности

| Путь | Time | Space | Use case |
|:---|:---|:---|:---|
| Быстрый (отправитель ждёт) | ~50-100 нс | 0 | Небуферизованный с отправителем |
| Средний (буфер есть данные) | ~30-70 нс | размер элемента | Буферизованный, не пустой |
| Медленный (gopark) | ~100-200 нс + ожидание | sudog (~64 байт) | Буфер пуст / нет отправителя |
| Из закрытого канала | ~50-100 нс | 0 | Сигнал завершения |

### 💡 Практика: что важно знать про получение

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Проверяй `ok` при получении, если важно отличить «ноль» от «закрыт»:**
   ```go
   v, ok := <-ch
   if !ok {
       // канал закрыт
   }
   ```

2. **Используй `range` для чтения всех значений до закрытия:**
   ```go
   for v := range ch {
       process(v)
   }
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для сигнала завершения — `chan struct{}`:**
   ```go
   done := make(chan struct{})
   <-done  // ждём сигнала
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Проверять `ok` всегда.** Если канал не закрывается — `ok` всегда `true`, проверка не нужна.

**❌ НЕ ДЕЛАЙ:**

5. **Не игнорируй закрытие канала в `range`** — цикл не завершится, если канал не закрыт.

6. **Не путай «закрытый канал» и «пустой канал»:**
   - Пустой, но не закрытый → `<-ch` **блокируется**.
   - Закрытый → `<-ch` возвращает `zero, false` **немедленно**.

### Ключевые выводы подглавы 2.4

- **Три пути получения:** быстрый (отправитель ждёт), средний (буфер есть данные), медленный (gopark).
- **Быстрый путь:** данные копируются напрямую из `sudog.elem` отправителя в переменную получателя.
- **Средний путь:** чтение из кольцевого буфера.
- **Медленный путь:** получатель блокируется, его `sudog` ждёт в `recvq`.
- **Закрытый канал:** возвращает `zero, false` немедленно, если буфер пуст. Сначала отдаёт данные из буфера.
- **`range` завершается**, когда канал закрыт И буфер пуст.

## 2.5 Буферизованный vs небуферизованный: разница на уровне рантайма

Теперь, когда мы разобрали `hchan` и пути отправки/получения, сформулируем **разницу** между буферизованным и небуферизованным каналом.

### Что общего

- Оба — структура `hchan`.
- Оба используют `sendq` и `recvq` для блокировки.
- Оба защищены мьютексом.
- Оба могут быть закрыты через `close`.
- Оба могут быть `nil` (блокируются навсегда).

### Что различается

| Аспект | Небуферизованный | Буферизованный |
|:---|:---|:---|
| `dataqsiz` | 0 | N > 0 |
| `buf` | `nil` | Указатель на кольцевой буфер |
| `qcount` | Всегда 0 | 0..N |
| Отправка без получателя | Блокируется | Блокируется, если буфер полон |
| Получение без отправителя | Блокируется | Блокируется, если буфер пуст |
| Синхронизация | **Строгая** (рандеву) | **Ослабленная** (через буфер) |
| Память | ~96 байт (только hchan) | ~96 + N × elemsize |
| Пропускная способность | Низкая (1 передача за раз) | Высокая (N в буфере) |
| Backpressure | Мгновенный | С задержкой (пока буфер не полон) |

### Ключевое различие: синхронизация

**Небуферизованный канал** обеспечивает **строгую синхронизацию**: отправитель и получатель **встречаются** в момент передачи.

```
Небуферизованный:
  A: ch <- 42  ──┐
                 ├──► рандеву
  B: <-ch      ──┘
  
  A и B синхронизированы. Передача происходит ТОЛЬКО когда обе готовы.
```

**Буферизованный канал** обеспечивает **ослабленную синхронизацию**: отправитель и получатель могут не встретиться.

```
Буферизованный (N=4):
  A: ch <- 42  ──▶ [буфер]  ──▶  B: <-ch
  
  A положил и ушёл. B взял и ушёл. Они не встретились.
  Но: если буфер полон, A блокируется.
```

### Когда что использовать

**Небуферизованный канал:**

- Когда нужна **гарантия**, что получатель получил данные (рандеву).
- Когда важна **синхронизация**, а не пропускная способность.
- Пример: передача результата от worker'а к collector'у.

**Буферизованный канал:**

- Когда нужна **пропускная способность**: producer'ы не ждут consumer'ов.
- Когда важен **backpressure** с задержкой: буфер сглаживает пики.
- Пример: очередь задач с ограниченным буфером.

### Паттерн: «сигнал через close»

```go
done := make(chan struct{})
go func() {
    // ... работа ...
    close(done)  // сигнал
}()

<-done  // ждём
```

**Почему `close`, а не отправка:**

- `close` работает **без получателя**: если никто не читает — не блокируется.
- `close` **разблокирует всех** читателей: `<-done` возвращается у всех.
- `close` — **идемпотентен**: повторный вызов — паника, но это защита от багов.

**Сравнение:**

| Способ | Блокировка | Разблокирует | Память |
|:---|:---|:---|:---|
| `ch <- struct{}{}` | Да, если нет читателя | Одного | 0 (struct{}) |
| `close(ch)` | Нет | Всех | 0 |

### Паттерн: «буфер как ограничитель»

```go
sem := make(chan struct{}, 10)  // семафор на 10

for _, task := range tasks {
    sem <- struct{}{}  // захватить слот (блокируется на 10)
    go func(t Task) {
        defer func() { <-sem }()  // освободить слот
        process(t)
    }(task)
}
```

**Что это даёт:** максимум 10 горутин одновременно. Буфер канала = число «разрешений».

Это **семафор** на каналах. Мы разберём его детально в Главе 9.

### Аннотация сложности

| Аспект | Небуферизованный | Буферизованный |
|:---|:---|:---|
| Отправка (есть получатель) | ~50-100 нс | ~30-70 нс |
| Отправка (нет получателя) | gopark | gopark (если полон) |
| Получение (есть отправитель) | ~50-100 нс | ~30-70 нс |
| Получение (нет отправителя) | gopark | gopark (если пуст) |
| Память | ~96 байт | ~96 + N × elemsize |

### 💡 Практика: как выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для синхронизации — небуферизованный канал.** Гарантия рандеву.
2. **Для пропускной способности — буферизованный канал.** Producer'ы не ждут.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для сигналов — `chan struct{}` + `close`.**
4. **Для семафора — буферизованный канал с `struct{}`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Очень большой буфер.** Если consumer не успевает — данные копятся, но проблема маскируется.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй буферизованный канал «на всякий случай».** Это скрывает проблемы синхронизации.

7. **Не ставь буфер 1 «для развязки».** Часто это ошибка: producer'ы всё равно блокируются.

### Ключевые выводы подглавы 2.5

- **Небуферизованный канал** — строгая синхронизация (рандеву). **Буферизованный** — ослабленная (через буфер).
- **`dataqsiz`** определяет размер буфера. Для небуферизованного — 0.
- **Буферизованный канал** даёт пропускную способность, но не гарантирует синхронизацию.
- **`close` для сигналов** — без получателя, разблокирует всех.
- **Буферизованный канал как семафор** — ограничивает параллелизм.

## 2.6 close(ch): сигнал, а не очистка

`close(ch)` — самая непонятая операция с каналами. Разберём её детально.

### Что делает close на уровне runtime

```
runtime.closechan(c):

  1. Захватить lock.
  2. if c.closed == 1: panic("close of closed channel").
  3. c.closed = 1.
  
  4. Разбудить ВСЕХ получателей из recvq:
     for sudog := range recvq:
        sudog.elem = zero_value
        goready(sudog.g)
  
  5. Разбудить ВСЕХ отправителей из sendq:
     for sudog := range sendq:
        panic("send on closed channel")  ← они получат панику
  
  6. Отпустить lock.
```

**Ключевые моменты:**

1. **`close` не освобождает память.** Он ставит флаг `closed = 1`. Память освободит GC.
2. **`close` не «закрывает трубу».** Данные в буфере остаются доступны.
3. **`close` разблокирует всех получателей.** Они получат `zero, false`.
4. **Отправители, ждущие в sendq, получат панику** при попытке отправки после close.

### Что происходит с получателями

```go
ch := make(chan int, 4)
ch <- 1
ch <- 2
close(ch)

// Все получатели разблокированы:
<-ch  // 1, true
<-ch  // 2, true
<-ch  // 0, false (буфер пуст, канал закрыт)
<-ch  // 0, false (канал закрыт, не блокируется)
```

**Данные в буфере остаются доступны.** `close` не «очищает» буфер.

### Что происходит с отправителями

```go
ch := make(chan int)
close(ch)
ch <- 42  // panic: send on closed channel
```

**Отправка в закрытый канал — паника.** Это не «игнорируется», не «блокируется» — именно паника.

**Почему:** если бы отправка после close блокировалась, горутина висела бы вечно. Если бы игнорировалась — терялись бы данные. Паника — единственный способ явно показать ошибку.

### Правило: кто закрывает канал

**Канал закрывает тот, кто пишет.** Не тот, кто читает.

```
❌ Плохо: читатель закрывает канал
   Читатель не знает, будут ли ещё записи.
   Если писатель попробует записать после close — паника.

✅ Хорошо: писатель закрывает канал
   Писатель знает, когда закончил.
   Читатели видят close и завершают range.
```

**Идиоматический паттерн:**

```go
func producer(ch chan<- int) {
    defer close(ch)  // писатель закрывает
    for i := 0; i < 10; i++ {
        ch <- i
    }
}

func consumer(ch <-chan int) {
    for v := range ch {  // читатель читает до close
        fmt.Println(v)
    }
}

func main() {
    ch := make(chan int)
    go producer(ch)
    consumer(ch)
}
```

### Что НЕ делает close

**`close` не «очищает» канал.** Данные в буфере остаются.

**`close` не освобождает память.** Память освободит GC, когда не останется ссылок.

**`close` не «отправляет сигнал» в смысле данных.** Это флаг, который проверяют все операции.

**`close` не идемпотентен.** Повторный вызов — паника.

### Паттерн: close как broadcast-сигнал

```go
done := make(chan struct{})

// 100 горутин ждут сигнала
for i := 0; i < 100; i++ {
    go func() {
        <-done  // ждём
        // ... работа ...
    }()
}

// Один close разбудит ВСЕ 100 горутин
close(done)
```

**Это ключевой паттерн:** `close` разблокирует **всех** получателей. Отправка `struct{}{}` разбудила бы только одного.

**Использование:** graceful shutdown, отмена через context, сигнал «готово».

### Паттерн: проверка закрытия без блокировки

```go
select {
case v, ok := <-ch:
    if !ok {
        // канал закрыт
    }
default:
    // канал не закрыт (или пуст)
}
```

**`select` с `default`** позволяет проверить канал без блокировки.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `close(ch)` | ~50-100 нс | 0 | Сигнал завершения |
| Получение из закрытого | ~50-100 нс | 0 | После close |
| Отправка в закрытый | panic | 0 | Баг |
| `close` разбудить 100 горутин | ~5-10 мкс | 0 | Broadcast |

### 💡 Практика: как использовать close

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Закрывай канал на писателе, не на читателе.**
2. **Используй `close` для broadcast-сигналов:**
   ```go
   done := make(chan struct{})
   close(done)  // разбудит всех
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **Проверяй `ok` при получении, если канал может быть закрыт:**
   ```go
   v, ok := <-ch
   if !ok {
       // канал закрыт
   }
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для одиночного сигнала — `ch <- struct{}{}`.** Но `close` лучше.

**❌ НЕ ДЕЛАЙ:**

5. **Не закрывай канал дважды** — паника.
6. **Не отправляй в закрытый канал** — паника.
7. **Не закрывай канал на читателе** — если писатель ещё пишет, паника.
8. **Не думай, что `close` освобождает память** — освобождает GC.

### Ключевые выводы подглавы 2.6

- **`close` — это сигнал**, а не очистка. Данные в буфере остаются.
- **`close` не освобождает память** — освобождает GC.
- **Получатели** разблокируются и получают `zero, false`.
- **Отправители** получают панику при попытке отправки.
- **Кто пишет — тот и закрывает.** Это правило.
- **`close` для broadcast** — разбудит всех получателей.
- **Повторный `close`** — паника.

## 2.7 select: мультиплексирование каналов

`select` — это **мультиплексор** каналов. Он позволяет горутине ждать **несколько** каналов одновременно.

### Синтаксис и базовое поведение

```go
select {
case v := <-ch1:
    // ch1 готов к получению
case ch2 <- 42:
    // ch2 готов к отправке
case <-ch3:
    // ch3 готов к получению (значение игнорируется)
default:
    // ни один канал не готов
}
```

**Что делает `select`:**

1. Проверяет **все** case'ы на готовность.
2. Если **несколько** готовы — выбирает **случайный**.
3. Если **один** готов — выполняет его.
4. Если **ни один** не готов:
   - Есть `default` → выполняет `default`.
   - Нет `default` → **блокируется**, пока один из case'ов не будет готов.

### Как select устроен внутри

`select` в runtime представлен структурой `scase` (select case):

```go
type scase struct {
    c    *hchan         // канал
    elem unsafe.Pointer // указатель на данные
    kind uint16         // caseRecv, caseSend, caseDefault
    ...
}
```

**Что делает runtime:**

```
runtime.selectgo(cases []scase):

  1. Сгенерировать случайный порядок обхода case'ов.
     (чтобы не было starvation — чтобы не всегда выбирался первый case)
  
  2. Для каждого case'а проверить готовность:
     - Для получения: sendq не пуста ИЛИ qcount > 0 ИЛИ closed?
     - Для отправки: recvq не пуста ИЛИ qcount < dataqsiz?
  
  3. Если найден готовый case:
     → Выполнить операцию (отправка/получение).
     → Вернуть.
  
  4. Если есть default:
     → Выполнить default.
     → Вернуть.
  
  5. Если ни один не готов и нет default:
     → Создать sudog для каждого case'а.
     → Добавить sudog в sendq/recvq соответствующего канала.
     → gopark.
     → При пробуждении — удалить sudog'и из остальных очередей.
     → Вернуть тот case, который сработал.
```

### Случайный выбор case

**Если несколько case'ов готовы, `select` выбирает случайный.** Это важно: это предотвращает **starvation** (голодание).

**Пример:**

```go
ch1 := make(chan int, 1)
ch2 := make(chan int, 1)
ch1 <- 1
ch2 <- 2

for i := 0; i < 10; i++ {
    select {
    case v := <-ch1:
        fmt.Println("ch1:", v)
    case v := <-ch2:
        fmt.Println("ch2:", v)
    }
}
// Вывод: ch1 и ch2 будут чередоваться в случайном порядке.
```

Если бы выбирался всегда первый готовый case — `ch1` всегда выигрывал бы, `ch2` голодал.

### select с default: неблокирующие операции

**`default`** позволяет **не блокироваться**, если ни один case не готов:

```go
select {
case v := <-ch:
    // получили
default:
    // не блокируемся — делаем что-то другое
}
```

**Использование:**

- **Проверка канала без блокировки.**
- **Неблокирующая отправка:**
  ```go
  select {
  case ch <- v:
      // отправили
  default:
      // канал полон
  }
  ```

- **Опрос нескольких каналов в цикле:**
  ```go
  for {
      select {
      case v := <-ch:
          process(v)
      default:
          // нет данных — делаем другую работу
      }
      doSomethingElse()
  }
  ```

### select с таймаутом

**Классический паттерн:**

```go
select {
case v := <-ch:
    // получили
case <-time.After(5 * time.Second):
    // таймаут
}
```

**`time.After`** возвращает канал, в который будет отправлено значение через 5 секунд. `select` ждёт либо данных из `ch`, либо сигнала от таймаута.

**Что происходит:**

1. `select` проверяет готовность `ch` и `time.After`.
2. Если `ch` готов — берём оттуда.
3. Если `ch` не готов, а таймаут сработал — берём из `time.After`.
4. Если ни то, ни другое — блокируемся.

**Важно:** `time.After` создаёт **новый таймер** каждый раз. Если в цикле — это утечка. Лучше использовать `time.NewTimer` или `context`:

```go
// ❌ Плохо: создаёт новый таймер каждый цикл
for {
    select {
    case v := <-ch:
        process(v)
    case <-time.After(5 * time.Second):
        return
    }
}

// ✅ Хорошо: один таймер
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()
for {
    select {
    case v := <-ch:
        process(v)
    case <-timer.C:
        return
    }
}
```

### select с context

**Самый частый паттерн в production:**

```go
select {
case v := <-ch:
    process(v)
case <-ctx.Done():
    return ctx.Err()
}
```

**`ctx.Done()`** — канал, который закрывается при отмене контекста. `select` ждёт либо данных, либо отмены.

Это идиоматический способ сделать операцию **отменяемой**. Мы разберём context детально в Главе 5.

### select внутри for: важный нюанс

```go
for {
    select {
    case v := <-ch:
        process(v)
    }
}
```

**Если `ch` не закрыт и не готов** — `select` блокируется. Цикл не выполняется до появления данных. Это нормально.

**Но:** если `ch` закрыт, `<-ch` возвращает `zero, false` **немедленно**. Цикл станет **busy loop**:

```go
// ❌ Плохо: busy loop после закрытия
for {
    select {
    case v := <-ch:
        process(v)  // если ch закрыт, v = 0, ok = false
    }
}
```

**Исправление:**

```go
// ✅ Хорошо: проверяем ok
for {
    select {
    case v, ok := <-ch:
        if !ok {
            return  // канал закрыт
        }
        process(v)
    case <-ctx.Done():
        return
    }
}
```

### Полная схема select

```
select {
case v := <-ch1:  ...
case ch2 <- 42:   ...
case <-ch3:       ...
default:          ...
}
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  runtime.selectgo(cases)                                 │
│                                                           │
│  1. Случайный порядок обхода cases.                      │
│                                                           │
│  2. Для каждого case:                                    │
│     ├─ caseRecv: if sendq не пуста || qcount > 0 ||      │
│     │            closed → ГОТОВ                          │
│     └─ caseSend: if recvq не пуста || qcount < dataqsiz  │
│                  → ГОТОВ                                 │
│                                                           │
│  3. Если есть готовые:                                   │
│     ├─ Выбрать случайный из готовых                      │
│     ├─ Выполнить операцию                                │
│     └─ Вернуть                                           │
│                                                           │
│  4. Если есть default:                                   │
│     ├─ Выполнить default                                 │
│     └─ Вернуть                                           │
│                                                           │
│  5. // Ни один не готов, default нет                     │
│     ├─ Создать sudog для каждого case                    │
│     ├─ Добавить sudog в sendq/recvq каналов              │
│     ├─ gopark                                            │
│     ├─ При пробуждении:                                  │
│     │   ├─ Удалить sudog'и из остальных очередей         │

│                                                           │
└──────────────────────────────────────────────────────────┘
```

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `select` с готовым case | ~100-200 нс | 0 | Мультиплексирование |
| `select` с `default` (не готов) | ~50-100 нс | 0 | Неблокирующая проверка |
| `select` с блокировкой | ~200-500 нс + ожидание | sudog на каждый case | Ожидание нескольких каналов |
| `time.After` в цикле | ~100 нс + память таймера | Таймер | Таймаут (осторожно с утечкой) |

### 💡 Практика: как использовать select

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для отмены — `select` с `ctx.Done()`:**
   ```go
   select {
   case v := <-ch:
       process(v)
   case <-ctx.Done():
       return ctx.Err()
   }
   ```

2. **Для таймаута — `time.NewTimer` в цикле, не `time.After`:**
   ```go
   timer := time.NewTimer(5 * time.Second)
   defer timer.Stop()
   select {
   case v := <-ch:
       process(v)
   case <-timer.C:
       return
   }
   ```

3. **Проверяй `ok` при получении в `select` внутри `for`:**
   ```go
   v, ok := <-ch
   if !ok { return }
   ```

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для неблокирующей отправки — `select` с `default`:**
   ```go
   select {
   case ch <- v:
   default:
       // канал полон
   }
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **`select` с одним case** — эквивалентно простой операции, но работает. Иногда используется для единообразия.

**❌ НЕ ДЕЛАЙ:**

6. **`select` без `default` в цикле на закрытом канале** — busy loop.
7. **`time.After` в цикле** — утечка таймеров.
8. **Несколько `case` с одинаковым каналом** — undefined behavior (паника или случайный выбор).

### Ключевые выводы подглавы 2.7

- **`select` — мультиплексор каналов.** Ждёт несколько каналов одновременно.
- **Случайный выбор** среди готовых case'ов — предотвращает starvation.
- **`default`** — неблокирующая операция. Если ни один case не готов — выполняется `default`.
- **`time.After`** в цикле — утечка таймеров. Используй `time.NewTimer`.
- **`select` с `ctx.Done()`** — идиоматический способ сделать операцию отменяемой.
- **`select` в `for`** требует проверки `ok` — иначе busy loop после закрытия.

## 2.8 nil-канал: канал, который всегда блокируется

**nil-канал** — это канал, который не был инициализирован:

```go
var ch chan int  // ch == nil
```

**Поведение nil-канала:**

| Операция | Поведение |
|:---|:---|
| Отправка `ch <- v` | **Блокируется навсегда** |
| Получение `<-ch` | **Блокируется навсегда** |
| `close(ch)` | **Паника** |
| `len(ch)` | 0 |
| `cap(ch)` | 0 |
| `select` с `case <-ch` | **Case игнорируется** (никогда не готов) |

### Почему nil-канал блокируется

**На уровне runtime:**

```
runtime.chansend(c, elem, block):
  1. if c == nil:
     if !block:
        return false  // неблокирующая отправка
     // Иначе:
     gopark(nil, nil, waitReasonChanSendNilChan, ...)
     // Горутина блокируется НАВСЕГДА.
```

**Почему так:** nil-канал — это «канал, которого нет». Отправка в него не может быть выполнена. Блокировка — единственный безопасный вариант (альтернатива — паника).

### Зачем это нужно

**nil-канал полезен в `select`:** case с nil-каналом **никогда не выбирается**. Это позволяет **динамически отключать** case'ы.

**Пример: чтение из двух каналов, один из которых может быть отключён:**

```go
func merge(ch1, ch2 <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for ch1 != nil || ch2 != nil {
            select {
            case v, ok := <-ch1:
                if !ok {
                    ch1 = nil  // отключаем ch1
                    continue
                }
                out <- v
            case v, ok := <-ch2:
                if !ok {
                    ch2 = nil  // отключаем ch2
                    continue
                }
                out <- v
            }
        }
    }()
    return out
}
```

**Что происходит:**

1. Пока `ch1` не закрыт — case `<-ch1` активен.
2. Когда `ch1` закрыт — `ch1 = nil`.
3. Case `<-ch1` с nil-каналом **никогда не готов** — `select` его игнорирует.
4. Цикл продолжается, пока хотя бы один канал не nil.

**Это идиоматический паттерн:** отключение case'ов через nil.

### Аналогия: «выключенный» канал

Представь пульт с двумя кнопками. Одна кнопка сломана (nil-канал) — сколько ни жми, ничего не произойдёт. `select` — это как «жду, пока нажмут любую кнопку». Сломанная кнопка просто игнорируется.

### Важно: nil-канал в select vs вне select

**Вне `select`:**

```go
var ch chan int
<-ch  // блокируется навсегда
```

**В `select`:**

```go
var ch chan int
select {
case <-ch:
    // НИКОГДА не выполнится
case <-otherCh:
    // выполнится, если otherCh готов
}
```

**Разница:** в `select` nil-канал **игнорируется**, вне `select` — **блокирует**.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Отправка в nil-канал | ∞ (gopark) | sudog | Баг (или намеренно) |
| Получение из nil-канала | ∞ (gopark) | sudog | Баг (или намеренно) |
| `close(nil)` | panic | 0 | Баг |
| nil-канал в `select` | 0 (игнорируется) | 0 | Отключение case'а |

### 💡 Практика: как использовать nil-канал

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: nil-канал блокируется навсегда.** Если горутина висит — проверь, не nil ли канал.

2. **Используй nil-канал для отключения case'ов в `select`:**
   ```go
   case v, ok := <-ch:
       if !ok {
           ch = nil  // отключаем case
           continue
       }
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **В `merge`-паттернах (fan-in) — nil для завершённых каналов.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Инициализировать каналы всегда.** Но nil-канал — легитимный инструмент.

**❌ НЕ ДЕЛАЙ:**

5. **Не забывай инициализировать каналы.** `var ch chan int` без `make` — nil.
6. **Не закрывай nil-канал** — паника.

### Ключевые выводы подглавы 2.8

- **nil-канал** — неинициализированный канал.
- **Отправка/получение** — блокируются навсегда. **`close`** — паника.
- **В `select`** — nil-канал игнорируется (case никогда не выбирается).
- **Использование:** отключение case'ов в `select`, merge-паттерны.
- **Правило:** если горутина висит — проверь, не nil ли канал.

## 2.9 Направленные каналы: типы как документация

**Направленные каналы** — это каналы с ограничением направления: только отправка или только получение.

### Синтаксис

```go
chan T      // двунаправленный (можно и отправлять, и получать)
chan<- T    // только для отправки (send-only)
<-chan T    // только для получения (receive-only)
```

**Стрелка показывает направление потока данных:**

```
chan<- T    // данные идут В канал (отправка)
<-chan T    // данные идут ИЗ канала (получение)
```

### Зачем нужны направленные каналы

**1. Документация.** Функция, которая принимает `<-chan T`, **не может** отправить в канал. Это видно из сигнатуры.

**2. Защита от ошибок.** Компилятор не даст отправить в `<-chan T` или получить из `chan<- T`.

**3. Ясность намерений.** `chan<- T` — «я только пишу». `<-chan T` — «я только читаю».

### Пример: producer и consumer

```go
func producer(ch chan<- int) {
    // ch — только для отправки
    for i := 0; i < 10; i++ {
        ch <- i
    }
    close(ch)  // можно закрывать
}

func consumer(ch <-chan int) {
    // ch — только для получения
    for v := range ch {
        fmt.Println(v)
    }
    // close(ch)  // ❌ НЕЛЬЗЯ — компилятор не даст
}

func main() {
    ch := make(chan int)  // двунаправленный
    go producer(ch)       // передаём как chan<- int
    consumer(ch)          // передаём как <-chan int
}
```

**Что происходит:** двунаправленный канал **неявно преобразуется** в направленный при передаче в функцию. Это безопасно: `producer` не может читать, `consumer` не может писать.

### Преобразование направлений

```
chan T  →  chan<- T   ✅ (двунаправленный → send-only)
chan T  →  <-chan T   ✅ (двунаправленный → receive-only)

chan<- T  →  chan T    ❌
<-chan T  →  chan T    ❌

chan<- T  →  <-chan T  ❌
<-chan T  →  chan<- T  ❌
```

**Только от двунаправленного к направленному.** Обратно — нельзя.

### Внутреннее устройство

**Направленные каналы — это те же `hchan`.** На уровне runtime нет разницы между `chan T`, `chan<- T` и `<-chan T`. Это **ограничение на уровне типов**, которое проверяет компилятор.

```
chan T      → *hchan
chan<- T    → *hchan (компилятор запрещает получение)
<-chan T    → *hchan (компилятор запрещает отправку)
```

**Это zero-cost абстракция:** никаких накладных расходов в runtime.

### Паттерн: функция возвращает receive-only канал

```go
func generate(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            out <- n
        }
    }()
    return out
}

func main() {
    ch := generate(1, 2, 3, 4, 5)
    // ch — receive-only. Отправить нельзя.
    for v := range ch {
        fmt.Println(v)
    }
}
```

**Что это даёт:** вызывающий код **не может** отправить в канал. Только читать. Это защищает от ошибок.

### Паттерн: pipeline с направленными каналами

```go
func stage1(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for v := range in {
            out <- v * 2
        }
    }()
    return out
}

func stage2(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for v := range in {
            out <- v + 1
        }
    }()
    return out
}

func main() {
    ch := generate(1, 2, 3, 4, 5)
    ch = stage1(ch)
    ch = stage2(ch)
    for v := range ch {
        fmt.Println(v)
    }
}
```

**Каждая стадия** принимает `<-chan int` и возвращает `<-chan int`. Типы говорят: «я читаю из входа, пишу в выход, не наоборот».

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Преобразование `chan T` → `<-chan T` | 0 | 0 | Передача в функцию |
| Использование направленного канала | То же, что обычного | 0 | Документация + защита |

### 💡 Практика: как использовать направленные каналы

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **В сигнатурах функций — направленные каналы:**
   ```go
   func producer(ch chan<- int)  // только пишет
   func consumer(ch <-chan int)  // только читает
   ```

2. **Функции, возвращающие канал, — receive-only:**
   ```go
   func generate() <-chan int
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **В pipeline — каждая стадия принимает `<-chan` и возвращает `<-chan`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **В локальных переменных — двунаправленный.** Направление важно в сигнатурах.

**❌ НЕ ДЕЛАЙ:**

5. **Не пытайся преобразовать направленный канал обратно в двунаправленный** — компилятор не даст.

### Ключевые выводы подглавы 2.9

- **Направленные каналы:** `chan<- T` (только отправка), `<-chan T` (только получение).
- **На уровне runtime** — те же `hchan`. Ограничение только на уровне типов.
- **Двунаправленный → направленный** — можно. **Обратно** — нельзя.
- **Использование:** документация, защита от ошибок, ясность намерений.
- **Zero-cost абстракция** — никаких накладных расходов.

## 2.10 Практика Go: диагностика каналов

Теперь напишем **утилиту на Go**, которая демонстрирует и диагностирует проблемы с каналами:

1. **Дедлок** — две горутины ждут друг друга.
2. **Утечка** — горутина навсегда в `_Gwaiting` на канале.
3. **Busy loop** — `select` в цикле на закрытом канале.
4. **Сравнение производительности** буферизованных и небуферизованных каналов.

### Утилита 1: демонстрация дедлока

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    ch1 := make(chan int)
    ch2 := make(chan int)

    // Горутина 1: пишет в ch1, читает из ch2
    go func() {
        ch1 <- 1        // ждёт читателя ch1
        fmt.Println(<-ch2)  // ждёт данные из ch2
    }()

    // Горутина 2: пишет в ch2, читает из ch1
    go func() {
        ch2 <- 2        // ждёт читателя ch2
        fmt.Println(<-ch1)  // ждёт данные из ch1
    }()

    time.Sleep(1 * time.Second)
    fmt.Println("main завершается")
}
```

**Что происходит:**

```
Горутина 1: ch1 <- 1  → блокируется (нет читателя ch1)
Горутина 2: ch2 <- 2  → блокируется (нет читателя ch2)
```

**Обе горутины ждут друг друга — дедлок.**

**Но:** Go runtime **не всегда** обнаруживает дедлок. В этом случае `main` завершается через 1 секунду, и программа выходит (горутины убиваются).

**Если бы `main` ждал:** `runtime` обнаружил бы deadlock:

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan send]:
main.main.func1()
    /path/to/main.go:12 +0x...

goroutine 2 [chan send]:
main.main.func2()
    /path/to/main.go:18 +0x...
```

### Утилита 2: демонстрация утечки

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    fmt.Printf("goroutines before: %d\n", runtime.NumGoroutine())

    // Утечка: 1000 горутин пишут в канал без читателя
    for i := 0; i < 1000; i++ {
        ch := make(chan int)
        go func() {
            ch <- i  // блокируется навсегда
        }()
        _ = ch  // канал не собран GC — ссылка есть только в горутине
    }

    time.Sleep(1 * time.Second)
    fmt.Printf("goroutines after: %d\n", runtime.NumGoroutine())

    // Дамп стеков
    buf := make([]byte, 1<<20)
    n := runtime.Stack(buf, true)
    fmt.Printf("goroutine dump (%d bytes):\n%s\n", n, buf[:n])
}
```

**Пример вывода:**

```
goroutines before: 1
goroutines after: 1001
goroutine dump (52345 bytes):
goroutine 1 [running]:
...
goroutine 18 [chan send]:
main.main.func1()
    /path/to/main.go:18 +0x...
created by main.main in goroutine 1
    /path/to/main.go:17 +0x...
... (повторяется 1000 раз)
```

**1000 горутин в состоянии `chan send`** — утечка.

### Утилита 3: busy loop на закрытом канале

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

func main() {
    ch := make(chan int)
    close(ch)

    // ❌ Плохо: busy loop
    go func() {
        count := 0
        for {
            select {
            case v := <-ch:
                count++
                _ = v
            }
        }
        _ = count
    }()

    time.Sleep(100 * time.Millisecond)
    fmt.Printf("goroutines: %d\n", runtime.NumGoroutine())
}
```

**Что происходит:** канал закрыт, `<-ch` возвращает `zero, false` **немедленно**. `select` всегда готов. Цикл крутится на 100% CPU.

**Исправление:**

```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            return  // канал закрыт — выходим
        }
        process(v)
    }
}
```

### Утилита 4: бенчмарк буферизованных vs небуферизованных

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

func main() {
    // Бенчмарк: 1 000 000 передач через канал
    for _, size := range []int{0, 1, 10, 100, 1000} {
        measureChannel(size)
    }
}

func measureChannel(bufferSize int) {
    ch := make(chan int, bufferSize)
    const N = 1_000_000

    var wg sync.WaitGroup
    wg.Add(2)

    start := time.Now()

    // Producer
    go func() {
        defer wg.Done()
        for i := 0; i < N; i++ {
            ch <- i
        }
        close(ch)
    }()

    // Consumer
    go func() {
        defer wg.Done()
        count := 0
        for range ch {
            count++
        }
    }()

    wg.Wait()
    elapsed := time.Since(start)

    fmt.Printf("buffer=%4d: %v (%v/op)\n", bufferSize, elapsed, elapsed/N)
}
```

**Пример вывода:**

```
buffer=   0: 250ms (250ns/op)
buffer=   1: 180ms (180ns/op)
buffer=  10: 150ms (150ns/op)
buffer= 100: 140ms (140ns/op)
buffer=1000: 135ms (135ns/op)
```

**Что видно:**

- Небуферизованный канал (buffer=0) — самый медленный (250 нс/op).
- Буферизованный на 1000 — самый быстрый (135 нс/op).
- **Разница — в 2 раза.** Но это **микрооптимизация**: в реальных задачах узкое место — не канал, а обработка.

### Утилита 5: select с таймаутом

```go
package main

import (
    "context"
    "fmt"
    "time"
)

func main() {
    ch := make(chan int)

    // Отправляем данные через 2 секунды
    go func() {
        time.Sleep(2 * time.Second)
        ch <- 42
    }()

    // Ждём с таймаутом 1 секунда
    select {
    case v := <-ch:
        fmt.Println("получили:", v)
    case <-time.After(1 * time.Second):
        fmt.Println("таймаут")
    }

    // Ждём с context
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()

    select {
    case v := <-ch:
        fmt.Println("получили:", v)
    case <-ctx.Done():
        fmt.Println("context done:", ctx.Err())
    }
}
```

**Вывод:**

```
таймаут
получили: 42
```

**Что видно:** `select` с таймаутом работает. `context.WithTimeout` — идиоматичный способ.

### Аннотация сложности

| Диагностика | Time | Space | Use case |
|:---|:---|:---|:---|
| `runtime.NumGoroutine()` | ~10-50 нс | 0 | Мониторинг |
| `runtime.Stack(buf, true)` | ~1-100 мс | Зависит | Дамп стеков |
| pprof `debug/pprof/goroutine?debug=2` | ~10-100 мс | Зависит | Диагностика |
| Бенчмарк канала | ~мс-сек | Зависит | Оптимизация |

### 💡 Практика: как диагностировать проблемы с каналами

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Мониторь `runtime.NumGoroutine()`.** Рост без падения — утечка.

2. **Дамп стеков при подозрении:**
   ```go
   buf := make([]byte, 1<<20)
   n := runtime.Stack(buf, true)
   log.Printf("goroutine dump: %s", buf[:n])
   ```

**👍 СТОИТ СДЕЛАТЬ:**

3. **pprof в production (localhost):**
   ```go
   import _ "net/http/pprof"
   go http.ListenAndServe("localhost:6060", nil)
   ```

4. **Проверяй `ok` при получении в `select` внутри `for`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Микробенчмарки каналов** — редко дают полезную информацию. Узкое место обычно не в канале.

**❌ НЕ ДЕЛАЙ:**

6. **Не игнорируй `fatal error: all goroutines are asleep - deadlock!`** — это всегда баг.
7. **Не используй `time.After` в цикле** — утечка таймеров.
8. **Не проверяй `ok` без необходимости** — если канал не закрывается, проверка не нужна.

### Ключевые выводы подглавы 2.10

- **Дедлок** — две горутины ждут друг друга. Runtime обнаруживает, если все горутины спят.
- **Утечка** — горутина навсегда в `_Gwaiting` на канале.
- **Busy loop** — `select` в `for` на закрытом канале без проверки `ok`.
- **Бенчмарк:** буферизованный канал быстрее небуферизованного в ~2 раза. Но это микрооптимизация.
- **Диагностика:** `runtime.NumGoroutine()`, `runtime.Stack`, pprof.

## 2.11 Выводы и типичные ошибки

**Что мы узнали?**

Канал — это **структура `hchan`** (~96 байт) + буфер (если буферизованный). Все операции защищены **мьютексом `hchan.lock`**. Отправка и получение имеют **три пути**: быстрый (получатель/отправитель ждёт — прямая передача данных), средний (буфер — копирование), медленный (`gopark` — блокировка). **Небуферизованный канал** — строгая синхронизация (рандеву). **Буферизованный** — ослабленная, через буфер. **`close`** — сигнал, разблокирует всех получателей, не освобождает память. **`select`** — мультиплексор, случайный выбор среди готовых case'ов. **nil-канал** — блокируется навсегда, но игнорируется в `select`. **Направленные каналы** — ограничение на уровне типов, zero-cost.

**Типичные ошибки:**

- ❌ **Думать, что канал — это очередь.** Канал — точка синхронизации. Отправка в небуферизованный канал блокируется, пока получатель не готов.
- ❌ **Использовать буферизованный канал «на всякий случай».** Это маскирует проблемы синхронизации. Если буфер полон — producer блокируется.
- ❌ **Отправлять в закрытый канал.** Паника. Всегда проверяй или используй `select`.
- ❌ **Закрывать канал на читателе.** Закрывает **писатель**. Иначе паника при отправке.
- ❌ **Закрывать канал дважды.** Паника. `close` не идемпотентен.
- ❌ **Думать, что `close` освобождает память.** Освобождает GC, когда не останется ссылок.
- ❌ **Использовать `time.After` в цикле.** Создаёт новый таймер каждый раз — утечка. Используй `time.NewTimer`.
- ❌ **`select` в `for` без проверки `ok` на закрытом канале.** Busy loop на 100% CPU.
- ❌ **Забывать про nil-канал.** `var ch chan int` без `make` — nil. Отправка/получение блокируются навсегда.
- ❌ **Не использовать направленные каналы в сигнатурах.** Теряешь документацию и защиту от ошибок.
- ❌ **Блокировать HTTP-хэндлер на отправке в канал.** Висящие соединения. Используй `select` + `default` или worker pool.
- ❌ **Игнорировать утечки горутин на каналах.** Мониторь `runtime.NumGoroutine()`, используй pprof.

## 2.12 Для быстрого повторения

- **Канал — не очередь.** Это точка синхронизации. Небуферизованный — рандеву. Буферизованный — развязка через буфер.
- **`hchan`** — структура канала (~96 байт): `qcount`, `dataqsiz`, `buf`, `sendq`, `recvq`, `lock`. Все поля защищены мьютексом.
- **Отправка `ch <- v`:** три пути — быстрый (получатель ждёт, прямая передача), средний (буфер), медленный (`gopark`).
- **Получение `<-ch`:** три пути — быстрый (отправитель ждёт), средний (буфер), медленный (`gopark`).
- **`close(ch)`** — сигнал, не очистка. Разблокирует всех получателей (`zero, false`). Не освобождает память. Кто пишет — тот закрывает.
- **`select`** — мультиплексор. Случайный выбор среди готовых. `default` — неблокирующая операция. `time.After` в цикле — утечка.
- **nil-канал** — блокируется навсегда вне `select`, игнорируется в `select`. Используется для отключения case'ов.
- **Направленные каналы** — `chan<- T`, `<-chan T`. Ограничение на уровне типов, zero-cost.
- **Для сигналов — `chan struct{}` + `close`.** Ноль байт, broadcast всем.
- **Для семафора — буферизованный канал с `struct{}`.** Размер буфера = число разрешений.
- **Для отмены — `select` с `ctx.Done()`.**
- **Диагностика:** `runtime.NumGoroutine()`, `runtime.Stack`, pprof `debug/pprof/goroutine?debug=2`.

## 2.14 Ответы

### Ответ 1

Канал — **точка синхронизации**, а не очередь. В классической очереди producer кладёт элемент и идёт дальше. В канале producer **вступает в отношение** с consumer'ом. Для небуферизованного канала — рандеву: обе стороны ждут друг друга. Для буферизованного — развязка через буфер, но при переполнении producer блокируется.

### Ответ 2

`hchan` — структура канала в runtime Go. Поля:
- `qcount` — число элементов в буфере.
- `dataqsiz` — размер буфера.
- `buf` — указатель на кольцевой буфер.
- `elemsize` — размер элемента.
- `closed` — флаг закрытия.
- `elemtype` — тип элемента (для GC).
- `sendx`/`recvx` — индексы записи/чтения.
- `recvq`/`sendq` — очереди горутин, ждущих получения/отправки.
- `lock` — мьютекс, защищающий все поля.

Размер ~96 байт. Плюс буфер, если буферизованный.

### Ответ 3

Если получатель уже ждёт (в `recvq`), runtime:
1. Захватывает lock.
2. Извлекает `sudog` получателя из `recvq`.
3. **Копирует данные напрямую** из стека отправителя в стек получателя (`copy(sudog.elem, elem)`).
4. Будит получателя (`goready`).
5. Отпускает lock.

**Прямая передача** — ключевая оптимизация: нет промежуточного буфера. Отправитель не блокируется. Время ~50-100 нс.

### Ответ 4

Если буфер полон (или небуферизованный без получателя), runtime:
1. Создаёт `sudog` для отправителя.
2. Добавляет `sudog` в `sendq`.
3. Вызывает `gopark` — горутина переходит в `_Gwaiting`.
4. M (поток ОС) освобождается для других горутин.

`gopark` — функция runtime, которая «усыпляет» горутину: сохраняет контекст в `g.sched`, устанавливает `_Gwaiting`, вызывает `schedule()`. M не блокируется — он переключается на другую горутину.

### Ответ 5

**На уровне `hchan`:**
- Небуферизованный: `dataqsiz = 0`, `buf = nil`, `qcount = 0` всегда.
- Буферизованный: `dataqsiz = N > 0`, `buf` указывает на кольцевой буфер, `qcount` от 0 до N.

**На уровне поведения:**
- Небуферизованный: отправка блокируется, пока получатель не готов. Строгая синхронизация.
- Буферизованный: отправка блокируется, только если буфер полон. Ослабленная синхронизация.

### Ответ 6

`close(ch)`:
1. Захватывает lock.
2. Проверяет `closed == 0` (иначе паника).
3. Устанавливает `closed = 1`.
4. **Разблокирует всех получателей** из `recvq` — они получат `zero, false`.
5. **Отправители из `sendq` получат панику** при попытке отправки.

**Получатели:** `<-ch` возвращает `zero, false` немедленно. Данные в буфере сначала отдаются, потом `zero, false`.

**Отправители:** `ch <- v` — паника `send on closed channel`.

### Ответ 7

**Канал закрывает писатель.** Писатель знает, когда закончил. Читатель не знает, будут ли ещё записи. Если читатель закроет канал, а писатель попробует записать — паника.

**Идиоматический паттерн:**
```go
func producer(ch chan<- int) {
    defer close(ch)  // писатель закрывает
    // ...
}
```

### Ответ 8

**Нет, `close` не освобождает память.** Он только ставит флаг `closed = 1`. Канал освобождается **сборщиком мусора**, когда на `hchan` не осталось ссылок.

**Когда освобождается:** когда все горутины, имеющие ссылку на канал, завершились или перестали ссылаться. GC обходит граф объектов и освобождает недостижимые.

### Ответ 9

`select` проверяет все case'ы на готовность. Если несколько готовы — выбирает **случайный**.

**Почему случайный:** чтобы предотвратить **starvation** (голодание). Если бы всегда выбирался первый готовый case, каналы дальше в списке никогда бы не обрабатывались. Случайный выбор обеспечивает справедливость.

### Ответ 10

`select` с `default`:
- Если **хотя бы один** case готов — выполняется он.
- Если **ни один** не готов — выполняется `default`.

**Когда использовать:**
- Неблокирующая отправка: `select { case ch <- v: default: }`.
- Неблокирующее получение: `select { case v := <-ch: default: }`.
- Опрос каналов в цикле без блокировки.

### Ответ 11

`time.After` создаёт **новый таймер** каждый раз. В цикле это означает: каждый цикл создаётся таймер, который не освобождается до срабатывания. Если цикл быстрый, а таймаут долгий — тысячи таймеров в памяти.

**Замена:** `time.NewTimer` + `defer timer.Stop()`:
```go
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()
for {
    select {
    case v := <-ch:
        process(v)
    case <-timer.C:
        return
    }
}
```

Или `context.WithTimeout` — идиоматичнее.

### Ответ 12

**nil-канал** — неинициализированный канал (`var ch chan int`).

**Вне `select`:**
- `ch <- v` — блокируется навсегда.
- `<-ch` — блокируется навсегда.
- `close(ch)` — паника.

**Внутри `select`:**
- `case <-ch` — case **никогда не готов** (игнорируется).
- Используется для **отключения case'ов**: `ch = nil` после закрытия.

### Ответ 13

**Направленные каналы** — ограничение на уровне типов:
- `chan<- T` — только отправка.
- `<-chan T` — только получение.

**Зачем:** документация, защита от ошибок, ясность намерений. На уровне runtime — те же `hchan`, zero-cost.

**Преобразования:**
- `chan T` → `chan<- T` ✅
- `chan T` → `<-chan T` ✅
- Обратные — ❌

### Ответ 14

`select` в `for` на закрытом канале без проверки `ok`:
- `<-ch` возвращает `zero, false` **немедленно**.
- `select` всегда готов.
- Цикл крутится на 100% CPU — **busy loop**.

**Исправление:** проверять `ok`:
```go
v, ok := <-ch
if !ok { return }
```

### Ответ 15

**Два способа:**
1. **`runtime.NumGoroutine()`** — мониторинг. Если число горутин растёт и не падает — утечка.
2. **pprof goroutine dump:** `curl http://localhost:6060/debug/pprof/goroutine?debug=2`. Показывает стеки всех горутин — видно, какие застряли на канале.

Плюс `goleak` в тестах.

### Ответ 16

Буферизованный канал быстрее, потому что:
1. **Быстрый путь для отправки:** если в буфере есть место, отправитель не блокируется (`gopark` не вызывается).
2. **Меньше переключений контекста:** producer и consumer не синхронизируются на каждой передаче.
3. **Прямая передача при быстром пути:** данные идут напрямую, без `gopark`.

**Насколько:** в ~2 раза для 1 000 000 передач (250 нс/op vs 135 нс/op). Но это **микрооптимизация** — в реальных задачах узкое место обычно не в канале.
