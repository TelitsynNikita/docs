## 3.0 Пролог: счётчик, который врёт

Ты пишешь сервис с метриками. Есть счётчик запросов, который увеличивается в каждом HTTP-хэндлере:

```go
package main

import (
    "fmt"
    "net/http"
    "sync"
)

var requestCount int

func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        requestCount++  // ← что здесь не так?
        fmt.Fprintf(w, "requests: %d\n", requestCount)
    })
    http.ListenAndServe(":8080", nil)
}
```

Запускаешь. Делаешь 1000 запросов. Ожидаешь увидеть 1000, но видишь 987. Или 963. Или 1000 — но не всегда.

❓ **Почему счётчик врёт?**

Потому что `requestCount++` — **не атомарная операция**. Это три действия:

```
1. Прочитать значение requestCount из памяти в регистр.
2. Увеличить значение в регистре на 1.
3. Записать значение из регистра обратно в память.
```

Если две горутины выполняют это одновременно:

```
Горутина A: читает requestCount = 42
Горутина B: читает requestCount = 42
Горутина A: увеличивает до 43
Горутина B: увеличивает до 43
Горутина A: записывает 43
Горутина B: записывает 43   ← ОБА записали 43, но должно быть 44!
```

Это **data race** — ситуация, когда две горутины обращаются к одной памяти, и хотя бы одна пишет, без синхронизации. В Go это **undefined behavior**: результат непредсказуем, программа может упасть или работать «почти правильно».

❓ **Как исправить?**

Три способа:

1. **`sync.Mutex`** — заблокировать критическую секцию.
2. **`sync/atomic`** — атомарный инкремент.
3. **Канал** — передать «право на изменение» через канал.

```go
// Способ 1: Mutex
var (
    mu           sync.Mutex
    requestCount int
)

func increment() {
    mu.Lock()
    requestCount++
    mu.Unlock()
}

// Способ 2: atomic
var requestCount atomic.Int64

func increment() {
    requestCount.Add(1)
}

// Способ 3: канал (не идиоматично для счётчика)
var countCh = make(chan int, 1)

func increment() {
    countCh <- 1
}
```

Каждый способ имеет свою нишу. Но чтобы **осознанно** выбирать, нужно понимать, **как они устроены** и **сколько стоят**.

> **Важный мост к будущим главам:** `sync.Mutex` — основа для `sync.RWMutex`, `sync.WaitGroup`, `sync.Once`. Понимание `Mutex` даёт понимание всей синхронизации в Go. Memory model и data race — Глава 4. Детально `atomic` — Глава 4. В этой главе — **инструменты** и **когда их использовать**.

## 3.1 Когда каналы не подходят

Прежде чем разбирать `Mutex`, нужно понять: **почему каналы — не всегда правильный инструмент**.

### Философия Go: «share memory by communicating»

Известная цитата из документации Go:

> Do not communicate by sharing memory; instead, share memory by communicating.

Перевод: «Не общайтесь через разделяемую память; вместо этого разделяйте память через общение».

**Что это значит:**

- **Плохо:** две горутины имеют доступ к одной переменной и меняют её через мьютекс.
- **Хорошо:** одна горутина владеет переменной, а другие передают ей данные через канал.

**Пример — счётчик через канал:**

```go
type Counter struct {
    ch chan int
}

func NewCounter() *Counter {
    c := &Counter{ch: make(chan int)}
    go c.run()
    return c
}

func (c *Counter) run() {
    count := 0
    for delta := range c.ch {
        count += delta
    }
}

func (c *Counter) Inc() {
    c.ch <- 1
}
```

**Что это даёт:** переменная `count` принадлежит **одной** горутине. Нет data race. Нет мьютекса.

**Но:** это **медленнее**, чем `atomic.Add`. И **сложнее**, чем `Mutex`.

### Терминология: сериализация доступа vs сериализация данных

Прежде чем идти дальше, важно разграничить два значения слова «сериализация», потому что в контексте синхронизации оно используется постоянно.

**Сериализация данных** (data serialization) — это преобразование структуры в байты для передачи или хранения:

```
struct User { Name string; Age int }
        │
        │ json.Marshal
        ▼
{"name": "Alice", "age": 30}
```

Это то, что делает `json.Marshal`, `protobuf.Marshal`, `gob.Encode`. К синхронизации отношения не имеет.

**Сериализация доступа** (access serialization) — это упорядочивание доступа к ресурсу: несколько горутин выстраиваются в **последовательность**, и каждая получает доступ **по очереди**, а не одновременно.

```
Сериализация доступа:
  Горутина A: ──Lock──▶ [критическая секция] ──Unlock──▶
  Горутина B: ──────────ЖДЁТ──────────────────Lock──▶ [секция] ──Unlock──▶
  Горутина C: ──────────ЖДЁТ──────────────────ЖДЁТ──────────Lock──▶ [секция] ──Unlock──▶
```

**Откуда путаница:** слово «сериализация» происходит от латинского **series** — «ряд, последовательность». В обоих случаях есть идея **последовательности**:

- **Сериализация данных:** данные выстраиваются в **последовательность байт**.
- **Сериализация доступа:** горутины выстраиваются в **последовательность доступа** (одна за другой).

**Дальше в главе**, когда мы говорим «операции сериализуются», мы имеем в виду именно **сериализацию доступа** — упорядочивание, превращение параллельного доступа в последовательный. Не преобразование в байты.

### Когда каналы не подходят

**1. Простые счётчики и флаги.**

Для `counter++` или `flag = true` использовать канал — overkill. `atomic` или `Mutex` проще и быстрее.

```go
// ❌ Плохо: канал для счётчика
ch := make(chan int)
go func() { count++ }()

// ✅ Хорошо: atomic
var count atomic.Int64
count.Add(1)
```

**2. Защита структуры данных.**

Если у тебя `map[string]int`, и несколько горутин читают/пишут — нужен `Mutex` или `sync.Map`. Канал не поможет (или поможет, но сложно).

```go
// ❌ Плохо: канал для map
type SafeMap struct {
    ch chan func(map[string]int)
}

// ✅ Хорошо: Mutex
type SafeMap struct {
    mu sync.Mutex
    m  map[string]int
}
```

**3. Ленивая инициализация.**

Для «инициализировать ровно один раз» есть `sync.Once`.

```go
// ❌ Плохо: канал для once
onceCh := make(chan struct{})

// ✅ Хорошо: sync.Once
var once sync.Once
once.Do(initFunc)
```

**4. Ожидание группы горутин.**

Для «дождаться, пока все завершатся» есть `sync.WaitGroup`.

```go
// ❌ Плохо: канал для WaitGroup
done := make(chan struct{})
go func() { /* ... */; done <- struct{}{} }()

// ✅ Хорошо: sync.WaitGroup
var wg sync.WaitGroup
wg.Add(1)
go func() { defer wg.Done(); /* ... */ }()
wg.Wait()
```

**5. Высокочастотные операции.**

Если операция выполняется миллионы раз в секунду, `atomic` или `Mutex` будут быстрее канала.

```go
// ❌ Плохо: канал для счётчика метрик
metricsCh <- 1

// ✅ Хорошо: atomic
metricsCounter.Add(1)
```

### Когда каналы подходят

**1. Передача владения данными.**

Одна горутина создаёт данные, другая обрабатывает. Канал — идеально.

```go
go func() {
    result := compute()
    resultCh <- result  // передали владение
}()
```

**2. Потоковая обработка.**

Pipeline, fan-in, fan-out — каналы.

**3. Синхронизация событий.**

«Дождись, пока произойдёт X» — канал с `close` или `struct{}{}`.

```go
done := make(chan struct{})
go func() { /* ... */; close(done) }()
<-done
```

**4. Отмена и таймауты.**

`context.Context` использует канал `Done()`.

### Сравнительная таблица

| Задача | Инструмент | Почему |
|:---|:---|:---|
| Счётчик, флаг | `atomic` | Атомарно, быстро |
| Защита структуры (map, slice) | `Mutex` | Проще, чем канал |
| Много читателей, мало писателей | `RWMutex` | Параллельные читатели |
| Ожидание группы горутин | `WaitGroup` | Идиоматично |
| Инициализация один раз | `Once` | Идиоматично |
| Передача владения данными | Канал | Семантика |
| Потоковая обработка | Канал | Естественно |
| Синхронизация событий | Канал | `close` — broadcast |
| Отмена | `context` (канал) | Стандарт |

### Аннотация сложности

| Инструмент | Time (uncontended) | Time (contended) | Space |
|:---|:---|:---|:---|
| `atomic.Add` | ~5-10 нс | ~10-20 нс | 8 байт |
| `Mutex.Lock/Unlock` | ~15-25 нс | ~мкс-мс (зависит) | 8 байт |
| `RWMutex.RLock/RUnlock` | ~20-30 нс | ~мкс-мс | 24 байта |
| Канал (отправка) | ~50-100 нс | ~мкс-мс | ~96 байт + буфер |
| `WaitGroup` | ~10-20 нс | ~мкс-мс | 12 байт |

### 💡 Практика: как выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков и флагов — `atomic`.** Быстрее и проще.
2. **Для защиты map/slice — `Mutex` или `RWMutex`.**
3. **Для передачи владения — канал.**
4. **Для ожидания — `WaitGroup`.**

**👍 СТОИТ СДЕЛАТЬ:**

5. **Не бойся использовать `Mutex`.** Это не «плохо». Каналы — не единственный инструмент.
6. **Для read-heavy — `RWMutex`.** Но проверь, что он реально быстрее в твоём случае.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

7. **`sync.Map` — только для специфичных сценариев.** Не для «map с конкурентностью».

**❌ НЕ ДЕЛАЙ:**

8. **Не используй канал для счётчика.** Это медленнее и сложнее.
9. **Не используй `Mutex` для ожидания горутин.** Для этого есть `WaitGroup`.
10. **Не используй `Mutex` для инициализации.** Для этого есть `Once`.

### Ключевые выводы подглавы 3.1

- **Каналы — не всегда правильный инструмент.** Для счётчиков, защиты структур, ожидания — есть специализированные примитивы.
- **Сериализация доступа** — упорядочивание доступа к ресурсу. Не путать с **сериализацией данных** (JSON, Protobuf).
- **`atomic`** — для простых атомарных операций (счётчики, флаги).
- **`Mutex`** — для защиты разделяемого состояния (map, slice, структуры).
- **`RWMutex`** — для read-heavy сценариев.
- **`WaitGroup`** — для ожидания группы горутин.
- **`Once`** — для инициализации один раз.
- **Каналы** — для передачи владения, потоковой обработки, синхронизации событий.

## 3.2 sync.Mutex: как устроен

`sync.Mutex` — самый базовый примитив синхронизации. Разберём его внутреннее устройство.

### Структура Mutex

```go
type Mutex struct {
    state int32   // состояние: locked, woken, starving
    sema  uint32  // семафор для блокировки горутин
}
```

**Размер `Mutex` — 8 байт.** Два 32-битных поля.

### Поле state: битовая маска

`state` — это **битовая маска**. Каждый бит означает что-то своё:

```
state (32 бита):
┌────────────────────────────────────────────────────┐
│ 31               3 2 1 0                            │
│ ┌─────────────┬───┬───┬───┐                        │
│ │  waiters    │ S │ W │ L │                        │
│ │  (29 бит)   │   │   │   │                        │
│ └─────────────┴───┴───┴───┘                        │
│                                                    │
│  L (bit 0) = mutexLocked    — мьютекс захвачен     │
│  W (bit 1) = mutexWoken     — горутина разбужена   │
│  S (bit 2) = mutexStarving  — режим голодания      │
│  waiters (bits 3-31)        — число ждущих горутин │
└────────────────────────────────────────────────────┘
```

**Расшифровка:**

- **`mutexLocked`** (bit 0): 1, если мьютекс захвачен.
- **`mutexWoken`** (bit 1): 1, если runtime разбудил одну из ждущих горутин (чтобы избежать лишних пробуждений).
- **`mutexStarving`** (bit 2): 1, если мьютекс в режиме голодания (starvation mode).
- **`waiters`** (bits 3-31): число горутин, ждущих в `Lock()`.

### Поле sema: ключ, а не счётчик

`sema` — это **не сам семафор**, а **номер** (адрес) семафора. По этому адресу runtime находит структуру `semaRoot` — дерево ждущих горутин.

**Почему так:** семафоров в программе может быть миллионы (каждый `Mutex`, `WaitGroup`, `Once`, канал). Держать для каждого полноценную структуру — расточительно. Вместо этого — глобальная таблица, индексированная по адресу.

**Подробно — в подглаве 3.4.**

### Схема Mutex

```
┌─────────────────────────────────────────────────────────┐
│                    sync.Mutex                            │
│                                                          │
│  state (int32):                                          │
│  ┌────────────────────────────────────────────────────┐ │
│  │ waiters (29) │ S │ W │ L │                        │ │
│  └────────────────────────────────────────────────────┘ │
│   waiters=0     │   │   │                              │
│                 │   │   └── L = 0 (не захвачен)         │
│                 │   └────── W = 0 (никого не разбудили) │
│                 └────────── S = 0 (не голодает)         │
│                                                          │
│  sema (uint32): 0  ← адрес семафора (ключ для semaRoot) │
│                                                          │
│  Размер: 8 байт                                          │
└─────────────────────────────────────────────────────────┘
```

### Почему 8 байт — это важно

`Mutex` занимает **8 байт**. Это означает:

- Можно встроить `Mutex` в структуру без больших накладных расходов.
- Можно иметь много мьютексов (например, по одному на элемент map) без раздувания памяти.

**Но:** нельзя **копировать** `Mutex`. Копирование создаёт **второй, независимый** мьютекс, и синхронизация ломается.

**Правило:** `Mutex` всегда должен передаваться **по указателю** или быть **полем структуры**, которая передаётся по указателю.

```go
// ❌ Плохо: копирование Mutex
type Counter struct {
    mu sync.Mutex
    n  int
}

func (c Counter) Inc() {  // ← c копируется!
    c.mu.Lock()
    c.n++
    c.mu.Unlock()
}

// ✅ Хорошо: указатель
func (c *Counter) Inc() {
    c.mu.Lock()
    c.n++
    c.mu.Unlock()
}
```

**`go vet`** обнаруживает копирование мьютексов. Всегда запускай `go vet ./...`.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Создание `Mutex` | 0 (zero value) | 8 байт | Поле структуры |
| `Lock()` uncontended | ~15-25 нс | 0 | Быстрый путь |
| `Lock()` contended | ~мкс-мс | 0 | Slow path |
| `Unlock()` | ~10-20 нс | 0 | Освобождение |

### 💡 Практика: что важно знать про Mutex

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Mutex` — поле структуры, не копируй:**
   ```go
   type SafeCounter struct {
       mu sync.Mutex
       n  int
   }
   
   func (c *SafeCounter) Inc() {  // указатель!
       c.mu.Lock()
       defer c.mu.Unlock()
       c.n++
   }
   ```

2. **Запускай `go vet ./...`** — он ловит копирование мьютексов.

**👍 СТОИТ СДЕЛАТЬ:**

3. **`defer mu.Unlock()`** — если критическая секция может паниковать или возвращаться.

4. **Короткие критические секции** — меньше contention (что это и откуда берётся — в подглаве 3.4).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **`defer` для очень коротких секций** — `defer` имеет небольшую стоимость (~5 нс). Для горячего кода можно явный `Unlock()`.

**❌ НЕ ДЕЛАЙ:**

6. **Не копируй `Mutex`.** Никогда.
7. **Не забывай `Unlock()`.** Deadlock.
8. **Не делай критическую секцию длинной.** Contention растёт (см. 3.4).

### Ключевые выводы подглавы 3.2

- **`Mutex` — 8 байт:** `state` (int32) + `sema` (uint32).
- **`state`** — битовая маска: `mutexLocked`, `mutexWoken`, `mutexStarving`, `waiters`.
- **`sema`** — не счётчик, а **ключ** для поиска в глобальной таблице `semaRoot`.
- **`Mutex` нельзя копировать.** Всегда по указателю или поле структуры с pointer-методами.
- **`go vet`** ловит копирование.

## 3.3 Быстрый путь и slow path: что происходит при Lock()

Разберём, что происходит при `mu.Lock()`. У `Mutex` есть два пути: **быстрый** (когда мьютекс свободен) и **медленный** (когда занят или есть ждущие).

### Быстрый путь: uncontended Lock

**Ситуация:** мьютекс свободен, нет ждущих горутин.

Горутина вызывает `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)` — атомарную операцию **CAS** (Compare-And-Swap). Если `state` был равен 0 (мьютекс свободен), то CAS записывает `mutexLocked` (1) в `state`. Это означает «мьютекс захвачен».

**Что происходит на уровне CPU:**

```
1. Загрузить state в регистр.
2. Проверить: state == 0?
3. Если да — записать mutexLocked (1) в state.
4. Это CAS — атомарная операция, блокирует шину памяти.
```

**Стоимость:** ~15-25 нс. **Самая быстрая операция.** Никаких блокировок, никаких системных вызовов.

### Slow path: contended Lock

**Ситуация:** мьютекс занят, или есть ждущие горутины.

Горутина вызывает `lockSlow(&m)` — функцию runtime, которая обрабатывает медленный путь.

**Что делает `lockSlow`:**

1. **Spin** (короткий цикл ожидания) — горутина крутится в цикле, несколько раз пытаясь захватить мьютекс через CAS. Это быстрее, чем сразу блокироваться, если мьютекс скоро освободится. Внутри цикла вызывается `runtime_procyield()` — инструкция `PAUSE` на x86, которая говорит CPU «я в цикле ожидания».

2. **Блокировка** — если spin не помог, горутина вызывает `runtime_SemacquireMutex(&m.sema)` — функцию runtime, которая **блокирует горутину** в семафоре. Горутина переходит в `_Gwaiting`. Где именно она ждёт — разберём в подглаве 3.4.

3. **Пробуждение** — при `Unlock` runtime разбудит одну из ждущих горутин. Разбуженная горутина **снова попытается захватить мьютекс** (через CAS). Если не удалось — снова в семафор.

### Unlock: что происходит

Горутина вызывает `atomic.AddInt32(&m.state, -mutexLocked)` — атомарно снимает флаг `mutexLocked`. Затем проверяет: были ли ждущие? Если `state != 0` (были `waiters` или `woken`) — вызывает `unlockSlow(&m)`.

**Что делает `unlockSlow`:**

1. Проверяет `mutexStarving` — если да, передаёт мьютекс напрямую ждущей горутине.
2. Проверяет `waiters > 0` — если да, вызывает `runtime_Semrelease(&m.sema)`, которая **будит одну ждущую горутину**.

**Ключевой момент:** `Unlock` **не передаёт мьютекс напрямую**. Он только **будит** одну горутину. Разбуженная горутина должна **сама** захватить мьютекс (через CAS). Если не удалось — снова в семафор.

### Полная схема Lock

```
mu.Lock()
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  1. Быстрый путь:                                        │
│     if atomic.CAS(&m.state, 0, mutexLocked):            │
│         return  ← захвачен!                              │
└─────────────────────────────────────────────────────────┘
    │ CAS не удался
    ▼
┌─────────────────────────────────────────────────────────┐
│  2. lockSlow:                                            │
│                                                          │
│     for {                                                │
│         old = state                                      │
│         if old & mutexLocked == 0:                       │
│             if CAS(&state, old, old|mutexLocked):        │
│                 return  ← захвачен!                      │
│                                                          │
│         if old & mutexStarving != 0:                     │
│             break  ← идём в очередь                      │
│                                                          │
│         if old & (mutexLocked|mutexWoken) != 0 ||        │
│            old>>mutexWaiterShift == 0:                   │
│             // spin не поможет                           │
│             break                                        │
│                                                          │
│         // Spin: попробовать ещё раз                     │
│         runtime_procyield()                              │
│     }                                                    │
│                                                          │
│     // Блокировка:                                       │
│     for {                                                │
│         old = state                                      │
│         if old & mutexLocked == 0 &&                     │
│            old & mutexStarving == 0:                     │
│             if CAS(&state, old, old|mutexLocked):        │
│                 return                                   │
│                                                          │
│         // Increment waiters                             │
│         new = old + (1 << mutexWaiterShift)              │
│         if old & mutexLocked == 0:                       │
│             new |= mutexLocked                            │
│                                                          │
│         if CAS(&state, old, new):                        │
│             if old & mutexLocked != 0:                   │
│                 // Идём спать                            │
│                 runtime_SemacquireMutex(&m.sema)         │
│             else:                                        │
│                 return  ← захватили в последний момент   │
│     }                                                    │
└─────────────────────────────────────────────────────────┘
```

**Соглашение об именах в этой главе:**

- **Имена функций и полей** (`lockSlow`, `unlockSlow`, `runtime_SemacquireMutex`, `runtime_Semrelease`, `runtime_procyield`, `state`, `sema`) — на английском, потому что это идентификаторы в исходном коде runtime.
- **Описания** («медленный путь», «короткий цикл ожидания», «блокирует горутину», «снимает флаг») — на русском.
- **Общепринятые термины** (`CAS`, `spin`, `contention`) — на английском, потому что перевод только запутает.

### Стоимость

| Ситуация | Time | Что происходит |
|:---|:---|:---|
| Uncontended Lock | ~15-25 нс | Один CAS |
| Contended (spin успешен) | ~50-100 нс | Несколько CAS + spin |
| Contended (блокировка) | ~мкс-мс | Spin + `runtime_SemacquireMutex` + пробуждение |
| Unlock (без waiters) | ~10-20 нс | Один `atomic.AddInt32` |
| Unlock (с waiters) | ~100-500 нс | `runtime_Semrelease` + пробуждение |

### 💡 Практика: как минимизировать contention

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Короткие критические секции.** Чем меньше времени держишь мьютекс — тем меньше contention (см. 3.4).
   ```go
   // ❌ Плохо: долгая секция
   mu.Lock()
   result := slowComputation()
   shared = result
   mu.Unlock()
   
   // ✅ Хорошо: вычисление вне секции
   result := slowComputation()
   mu.Lock()
   shared = result
   mu.Unlock()
   ```

2. **Не делай I/O под мьютексом.** Сетевые вызовы, чтение файлов — вне секции.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Разделяй мьютексы.** Один на структуру — плохо. Несколько — лучше.
   ```go
   // ❌ Плохо: один мьютекс на всё
   type Cache struct {
       mu sync.Mutex
       users map[string]User
       orders map[string]Order
   }
   
   // ✅ Хорошо: разные мьютексы
   type Cache struct {
       usersMu sync.Mutex
       users   map[string]User
       ordersMu sync.Mutex
       orders  map[string]Order
   }
   ```

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **`sync.Pool` для частых аллокаций** — если contention на аллокаторе.

**❌ НЕ ДЕЛАЙ:**

5. **Не делай длинные критические секции.** Contention растёт (см. 3.4).
6. **Не делай I/O под мьютексом.** Это блокирует всех.
7. **Не используй один мьютекс на всё.** Разделяй.

**О contention:** когда несколько горутин одновременно пытаются захватить один мьютекс, возникает **contention** — конкуренция. Одна захватывает, остальные уходят в slow path: spin, затем блокировка в семафоре. Где именно они ждут и что такое contention на уровне runtime — в подглаве 3.4.

### Ключевые выводы подглавы 3.3

- **Быстрый путь `Lock`:** `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)`. ~15-25 нс.
- **Slow path (`lockSlow`):** spin (`runtime_procyield`) + `runtime_SemacquireMutex`. ~мкс-мс.
- **`Unlock`:** `atomic.AddInt32(&m.state, -mutexLocked)` + (опционально) `runtime_Semrelease`.
- **`Unlock` не передаёт мьютекс напрямую** — только будит одну горутину.
- **Contention — главная проблема.** Короткие секции, разделение мьютексов. Детали — в 3.4.

## 3.4 Где ждут горутины: семафоры и semaRoot

В подглавах 3.2 и 3.3 мы несколько раз сказали: «горутина блокируется в семафоре», «runtime будит одну из ждущих», «`runtime_SemacquireMutex`». Но **не объяснили**, что это за семафор, где физически находятся ждущие горутины и как runtime их находит.

Этот пробел нужно закрыть сейчас. Без понимания `semaRoot` и `sudog` непонятно:

- Почему `Mutex` занимает всего **8 байт**, хотя за ним могут ждать сотни горутин.
- Как `Unlock` «будит одну из ждущих», если в `Mutex` нет списка ждущих.
- Почему starvation mode (подглава 3.5) вообще возможен.
- Что такое **contention** и откуда он берётся.

### 3.4.1 Что такое семафор в runtime Go

**Семафор** — это примитив синхронизации: счётчик с двумя операциями:

- **`acquire`** (захватить): уменьшить счётчик. Если счётчик == 0 — **блокироваться**, пока кто-то не сделает `release`.
- **`release`** (освободить): увеличить счётчик. Если есть ждущие — **разбудить одного**.

**Важно:** семафор в runtime Go — это **не то же самое**, что `sync.Mutex`. `sync.Mutex` — высокоуровневый примитив с состоянием (`state`), оптимизациями (spin, starvation mode). Семафор в runtime — низкоуровневый примитив, на котором `Mutex` **построен**.

**Где живёт семафор:**

В `sync.Mutex` есть поле `sema uint32`:

```go
type Mutex struct {
    state int32
    sema  uint32  // ← это НЕ сам семафор, это НОМЕР семафора
}
```

**`sema` — это не счётчик.** Это **идентификатор** (адрес), по которому runtime находит структуру `semaRoot` — дерево ждущих горутин.

Почему так: семафоров в программе может быть **миллионы** (по одному на каждый `Mutex`, `WaitGroup`, `Once`, канал). Держать для каждого полноценную структуру с деревом — расточительно. Вместо этого runtime использует **глобальную таблицу** `semaRoot`-деревьев, индексированную по **адресу** переменной `sema`.

```
┌──────────────────────────────────────────────────────────────┐
│                    sync.Mutex (8 байт)                        │
│                                                               │
│  ┌──────────────────┬──────────────────┐                     │
│  │ state (int32)    │ sema (uint32)    │                     │
│  │ locked/woken/... │ = адрес семафора │                     │
│  └──────────────────┴──────────────────┘                     │
│                            │                                  │
│                            │ runtime ищет по этому адресу    │
│                            ▼                                  │
│  ┌──────────────────────────────────────────────────────┐    │
│  │           Глобальная таблица semaRoot                 │    │
│  │                                                       │    │
│  │  semaRoot[addr1] → дерево ждущих горутин             │    │
│  │  semaRoot[addr2] → дерево ждущих горутин             │    │
│  │  ...                                                  │    │
│  │  semaRoot[&m.sema] → дерево для ЭТОГО мьютекса       │    │
│  └──────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

**Ключевая идея:** `sema` в `Mutex` — это **не данные**, а **ключ** для поиска в глобальной таблице runtime. Сами ждущие горутины хранятся **вне** `Mutex`.

### 3.4.2 Структура semaRoot: дерево ждущих горутин

Каждый семафор в runtime представлен структурой `semaRoot`:

```go
type semaRoot struct {
    lock  mutex      // защита дерева
    treap *sudog     // корень дерева ждущих горутин
    nwait atomic.Uint32  // число ждущих
}
```

**`treap`** — корень **дерева** `sudog`. Каждый узел — горутина, которая ждёт на этом семафоре.

**Почему дерево, а не очередь?**

Казалось бы, для «ждущих» логично использовать очередь (FIFO). Но runtime использует **treap** (tree + heap) — самобалансирующееся бинарное дерево поиска.

**Причина:** семафоры в runtime **адресуются по адресу переменной** `sema`. Когда горутина блокируется, она указывает: «я жду на семафоре по адресу `&m.sema`». Runtime должен **быстро найти** дерево для этого адреса.

- **Очередь** не позволяет искать по ключу — только перебор.
- **Хэш-таблица** — тоже вариант, но требует больше памяти и хуже работает с редкими семафорами.
- **Treap** — O(log N) поиск по адресу, O(log N) вставка, O(1) доступ к минимуму (для пробуждения по FIFO).

**Почему treap, а не красно-чёрное дерево или AVL:**

- Treap **проще** в реализации (нет сложной балансировки).
- Treap даёт **O(log N) в среднем** — достаточно для семафоров.
- Treap хранит **приоритет** (случайный) — обеспечивает балансировку без явных поворотов.

**Структура treap:**

Каждый узел `sudog` имеет:
- **Ключ** — адрес семафора (`sema`).
- **Приоритет** — случайное число (генерируется при вставке).
- **Потомки** — левый и правый.

Treap одновременно **дерево поиска** (по ключу) и **куча** (по приоритету). Это даёт балансировку.

**Но:** для одного семафора все узлы имеют **один и тот же ключ** (адрес). Тогда дерево вырождается в **список**, отсортированный по приоритету. Это **и есть очередь**, но реализованная через treap.

```
Дерево semaRoot для одного семафора:

              [sudog G1, prio=0.8]
                    /          \
        [G2, 0.5]                [G3, 0.9]
        /      \                /       \
    [G4, 0.1] [G5, 0.3]    [G6, 0.7]  [G7, 0.95]

  Приоритеты случайны, поэтому дерево сбалансировано.
  Обход в порядке приоритета — очередь FIFO.
```

**На практике:** для одного семафора дерево — это **список**, отсортированный по приоритету. `semaRoot` нужен, чтобы **разные семафоры** (разные адреса) хранились в **одной глобальной структуре**.

### 3.4.3 Структура sudog: горутина в очереди ожидания

Когда горутина блокируется на семафоре, она оборачивается в **`sudog`** — структуру, которая связывает горутину с ожиданием.

```go
type sudog struct {
    g          *g           // горутина, которая ждёт
    next       *sudog       // следующий в очереди (связный список)
    prev       *sudog       // предыдущий в очереди
    
    elem       unsafe.Pointer  // указатель на данные (что ждём)
    
    acquiretime int64       // время начала ожидания (для трейсинга)
    releasetime int64       // время окончания ожидания
    
    isSelect   bool         // true, если ждём в select
    success    bool         // для select: сработал ли case
    
    waiters    uint32       // для select: число case'ов
    parent     *sudog       // для select: родительский sudog
    waitlink   *sudog       // для select: связь между case'ами
    
    c          *hchan       // канал (если ждём на канале)
}
```

**Размер `sudog`** — около **48-64 байт** (зависит от платформы).

**Разбор полей:**

| Поле | Назначение | Где используется |
|:---|:---|:---|
| `g` | Горутина, которая ждёт | Везде |
| `next` / `prev` | Связный список (для treap — потомки) | Везде |
| `elem` | Указатель на данные, которые ждём | Каналы, select |
| `acquiretime` | Время начала ожидания | Трейсинг, starvation mode |
| `releasetime` | Время окончания ожидания | Трейсинг |
| `isSelect` | true, если ждём в `select` | `select` |
| `success` | Сработал ли case | `select` |
| `waiters` | Число case'ов в `select` | `select` |
| `parent` | Родительский sudog (для select) | `select` |
| `waitlink` | Связь между case'ами | `select` |
| `c` | Канал, на котором ждём | Каналы |

**Важно:** `sudog` используется **не только в семафорах**, но и в:
- **Каналах** (`sendq`/`recvq`) — Глава 2.
- **`select`** — Глава 2.
- **Семафорах** (`semaRoot`) — здесь.

**Разница в использовании:**

- **В каналах:** `sudog` лежит в `sendq`/`recvq` (очередь).
- **В `select`:** `sudog` связывает несколько case'ов (список).
- **В семафорах:** `sudog` лежит в treap `semaRoot`.

**Общее:** `sudog` всегда означает «горутина, которая чего-то ждёт». Поля `next`/`prev` используются по-разному в зависимости от контекста.

**Для одного семафора** `sudog` образует связный список, отсортированный по приоритету (treap с одинаковыми ключами — это список).

### 3.4.4 Путь горутины при блокировке

Теперь разберём полный путь: от `mu.Lock()` до `_Gwaiting` в `semaRoot`.

**Ситуация:** горутина `G1` вызывает `mu.Lock()`, но мьютекс занят, и CAS не удался.

```
ШАГ 1: mu.Lock()
       │
       │ CAS не удался
       ▼
ШАГ 2: lockSlow(&m)
       │
       │ Spin не помог
       ▼
ШАГ 3: runtime_SemacquireMutex(&m.sema, ...)
       │
       │ Вызов функции runtime
       ▼
ШАГ 4: semacquire1(addr = &m.sema, ...)
       │
       │ 1. Найти semaRoot для addr.
       │ 2. Захватить semaRoot.lock.
       │ 3. Создать sudog для G1.
       │ 4. Добавить sudog в treap.
       │ 5. semaRoot.nwait++.
       │ 6. Отпустить semaRoot.lock.
       ▼
ШАГ 5: gopark(...)
       │
       │ 1. Сохранить контекст G1 в g.sched.
       │ 2. Установить g.atomicstatus = _Gwaiting.
       │ 3. Установить g.waitreason = waitReasonSemacquire.
       │ 4. Вызвать schedule().
       ▼
ШАГ 6: schedule()
       │
       │ 1. Выбрать следующую горутину из очереди P.
       │ 2. Переключиться на неё.
       ▼
       G1 ЗАБЛОКИРОВАНА.
       M свободен для других горутин.
```

**Визуализация:**

```
ДО БЛОКИРОВКИ:

  G1 (выполняется на M)               sync.Mutex
       │                              ┌────────────────┐
       │ mu.Lock()                    │ state: locked  │
       │ (CAS не удался)              │ sema: 0x...    │
       │                              └────────────────┘
       │
       │ SemacquireMutex
       ▼
  semaRoot для &m.sema
  ┌─────────────────────────┐
  │ treap: nil              │
  │ nwait: 0                │
  └─────────────────────────┘

ПОСЛЕ БЛОКИРОВКИ:

  G1 (в _Gwaiting)                    sync.Mutex
       │                              ┌────────────────┐
       │                              │ state: locked  │
       │                              │ sema: 0x...    │
       │                              └────────────────┘
       │
       │ sudog G1 добавлен в treap
       ▼
  semaRoot для &m.sema
  ┌─────────────────────────┐
  │ treap: sudog G1         │
  │ nwait: 1                │
  └─────────────────────────┘
       │
       │ G1.g.atomicstatus = _Gwaiting
       │ G1.g.waitreason = waitReasonSemacquire
       ▼
  M переключился на другую горутину.
  G1 ждёт в semaRoot.
```

**Ключевое:** `Mutex` (8 байт) **не хранит** список ждущих. Список ждущих хранится **вне** мьютекса — в глобальной таблице `semaRoot`. `Mutex.sema` — это **ключ** для поиска.

### 3.4.5 Путь горутины при пробуждении

Теперь разберём, что происходит при `Unlock`.

**Ситуация:** горутина `G2` вызывает `mu.Unlock()`. В `semaRoot` для этого мьютекса есть ждущая `G1`.

```
ШАГ 1: mu.Unlock()
       │
       │ atomic.AddInt32(&state, -mutexLocked)
       │ Проверка: waiters > 0?
       ▼
ШАГ 2: unlockSlow(&m)
       │
       │ 1. Проверка: mutexStarving?
       │ 2. Проверка: waiters > 0?
       ▼
ШАГ 3: runtime_Semrelease(&m.sema, ...)
       │
       ▼
ШАГ 4: semrelease1(addr = &m.sema, ...)
       │
       │ 1. Найти semaRoot для addr.
       │ 2. Захватить semaRoot.lock.
       │ 3. Найти sudog в treap.
       │    (по ключу = addr, приоритет определяет порядок)
       │ 4. Удалить sudog из treap.
       │ 5. semaRoot.nwait--.
       │ 6. Отпустить semaRoot.lock.
       │ 7. goready(sudog.g)
       ▼
ШАГ 5: goready(G1.g)
       │
       │ 1. G1.g.atomicstatus = _Grunnable.
       │ 2. Поместить G1.g в очередь P.
       │    (локальная очередь P или глобальная)
       │ 3. Возможно, разбудить другой P (wakep).
       ▼
       G1 ГОТОВА К ВЫПОЛНЕНИЮ.
       Ждёт, когда планировщик её выберет.
```

**Визуализация:**

```
ДО UNLOCK:

  G2 (выполняется на M)               sync.Mutex
       │                              ┌────────────────┐
       │ mu.Unlock()                  │ state: locked  │
       │                              │ sema: 0x...    │
       │                              └────────────────┘
       │
       │ SemreleaseMutex
       ▼
  semaRoot для &m.sema
  ┌─────────────────────────┐
  │ treap: sudog G1         │
  │ nwait: 1                │
  └─────────────────────────┘

ПОСЛЕ UNLOCK:

  G2 (продолжает работу)              sync.Mutex
       │                              ┌────────────────┐
       │                              │ state: 0       │
       │                              │ sema: 0x...    │
       │                              └────────────────┘
       │
       │ semaRoot
       ▼
  semaRoot для &m.sema
  ┌─────────────────────────┐
  │ treap: nil              │
  │ nwait: 0                │
  └─────────────────────────┘
       │
       │ goready(G1.g)
       ▼
  Очередь P
  ┌─────────────────────────┐
  │ [G1]                    │
  └─────────────────────────┘
       │
       │ G1.g.atomicStatus = _Grunnable
       ▼
  G1 ждёт, когда планировщик её выберет.
```

**Ключевое:** `Unlock` **не передаёт мьютекс напрямую**. Он только **будит** одну горутину. Разбуженная `G1` должна **сама** захватить мьютекс (через CAS). Если не удалось — снова в `semaRoot`.

**Именно поэтому starvation mode возможен:** разбуженная горутина конкурирует с новыми горутинами. Без starvation mode новые могут «перехватывать» мьютекс, и разбуженная горутина снова уходит в `semaRoot`.

**Детали очередей P (локальная, глобальная, work stealing) — в Главе 6 (Планировщик Go).**

### 3.4.7 Что такое contention

Теперь, когда мы знаем, **где ждут горутины**, можем определить **contention**.

**Contention** (конкуренция за ресурс) — ситуация, когда **несколько горутин одновременно пытаются захватить один и тот же мьютекс**. Одна захватывает, остальные уходят в slow path: spin, затем блокировка в `semaRoot`.

**Что происходит при contention:**

```
Низкий contention:                    Высокий contention:
  G1: Lock → работа → Unlock            G1: Lock → работа → Unlock
  G2: Lock → работа → Unlock            G2: Lock → ЖДЁТ → Lock → Unlock
  G3: Lock → работа → Unlock            G3: Lock → ЖДЁТ → Lock → Unlock
                                        G4: Lock → ЖДЁТ → ЖДЁТ → Lock → Unlock
                                        G5: Lock → ЖДЁТ → ЖДЁТ → ЖДЁТ → Lock → Unlock
```

**В чём проблема:**

- **Spin** — горутина крутится в цикле, тратя CPU.
- **Блокировка в `semaRoot`** — горутина переходит в `_Gwaiting`, но потом её нужно **разбудить**, переключиться на неё — это накладные расходы.
- **Starvation mode** — при ожидании > 1 мс мьютекс переходит в режим передачи напрямую, что **снижает пропускную способность**.
- **Пропускная способность падает** — чем больше contention, тем меньше полезной работы.

**Формула:**

```
Время ожидания ≈ O(N × T_hold)

где N — число горутин, конкурирующих за мьютекс,
    T_hold — среднее время удержания мьютекса.
```

**Пример:**

- 100 горутин, каждая держит мьютекс 1 мс.
- Общее время: 100 × 1 мс = 100 мс.
- Последняя горутина ждёт 99 мс.

Если держать мьютекс 100 мкс — последняя ждёт 9.9 мс. **В 10 раз быстрее.**

**Как измерить contention:**

```go
runtime.SetMutexProfileFraction(1)

// ... нагрузка ...

f, _ := os.Create("mutex.prof")
pprof.Lookup("mutex").WriteTo(f, 0)
f.Close()
```

Затем:

```bash
go tool pprof mutex.prof
(pprof) top
(pprof) list main.main
```

**Подробнее о диагностике — в подглаве 3.12.**

**Что делать при высоком contention:**

1. **Короткие критические секции.** Уменьшить `T_hold`.
2. **Разделить мьютексы.** Один на структуру — плохо. Несколько — лучше.
3. **Использовать `atomic`** там, где можно. Атомики не создают contention (нет блокировки).
4. **Использовать `RWMutex`** для read-heavy сценариев. Читатели не конкурируют.
5. **Sharding** — разбить данные на N частей, каждая со своим мьютексом.

### 3.4.8 Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Поиск `semaRoot` по адресу | O(log N) | ~24 байта на семафор | Каждая блокировка |
| Вставка `sudog` в treap | O(log N) | ~48-64 байта | Блокировка |
| Удаление `sudog` из treap | O(log N) | 0 | Пробуждение |
| `gopark` (блокировка) | ~100-200 нс | 0 | Slow path |
| `goready` (пробуждение) | ~100-200 нс | 0 | Unlock |
| Contention (N горутин, T_hold) | O(N × T_hold) | — | Проблема производительности |

### 3.4.9 Ключевые выводы подглавы

- **`sema` в `Mutex` — не счётчик, а ключ** (адрес) для поиска в глобальной таблице `semaRoot`.
- **`semaRoot` — дерево (treap) ждущих горутин**, сгруппированных по адресу семафора. Позволяет быстро находить ждущих.
- **`sudog`** — структура, оборачивающая горутину в ожидании. ~48-64 байт. Используется в семафорах, каналах, select.
- **Путь блокировки:** `Mutex.Lock` → `SemacquireMutex` → `semacquire1` → `sudog` в `semaRoot` → `gopark` → `_Gwaiting`.
- **Путь пробуждения:** `Unlock` → `SemreleaseMutex` → `semrelease1` → удаление `sudog` из treap → `goready` → `_Grunnable` → очередь P.
- **`Unlock` не передаёт мьютекс напрямую** — только будит одну горутину. Разбуженная конкурирует с новыми.
- **Contention** — конкуренция за мьютекс. Время ожидания ≈ O(N × T_hold).
- **Как уменьшить contention:** короткие секции, разделение мьютексов, `atomic`, `RWMutex`, sharding.

## 3.5 Starvation mode: когда горутина голодает

Мы упомянули `mutexStarving` в `state`. Разберём, что это.

### Проблема: голодание

Представь: 100 горутин ждут мьютекс. Каждая делает `Lock()`. Когда мьютекс освобождается, **одна** из них захватывает его. Но кто?

**Проблема:** если мьютекс освобождается и сразу захватывается **новой** горутиной (которая только что пришла), а ждущие горутины остаются в очереди — они **голодают**.

**Пример:**

```
Горутина A: Lock() → блокируется (мьютекс занят B).
Горутина C: Lock() → блокируется (мьютекс занят B).

B: Unlock() → будит A.
Но: горутина D (новая) делает Lock() и захватывает мьютекс раньше A.
A: просыпается, но мьютекс занят D → снова блокируется.
D: Unlock() → будит A.
Но: горутина E захватывает раньше A.
...

A голодает бесконечно.
```

### Решение: starvation mode

В Go 1.9 добавлен **starvation mode**: если горутина ждёт мьютекс дольше **1 мс**, мьютекс переходит в режим голодания.

**Что это значит:**

- **Обычный режим (normal):** разбуженная горутина **конкурирует** с новыми за мьютекс. Новые могут выиграть.
- **Режим голодания (starving):** мьютекс **передаётся напрямую** ждущей горутине. Новые не могут захватить.

**Как работает:**

```
1. Горутина A ждёт мьютекс.
2. Если A ждёт > 1 мс → state |= mutexStarving.
3. Теперь при Unlock:
   → Мьютекс НЕ освобождается для конкуренции.
   → Передаётся напрямую A (или первой в очереди).
4. A захватывает мьютекс.
5. Когда A отпускает:
   → Если waiters > 0 ИЛИ A держал < 1 мс:
     → Продолжить starvation mode.
   → Иначе:
     → Выйти из starvation mode.
```

**Ключевое:** в starvation mode **новые горутины не могут захватить мьютекс**, даже если он свободен. Только ждущие.

### Визуализация

```
Нормальный режим:

  Мьютекс освобождён.
  ┌─────────────────────────────────────┐
  │ Ждущие: A, B, C                     │
  │ Новые: D, E                         │
  └─────────────────────────────────────┘
       │
       ▼
  Конкуренция. Может выиграть D (новая).
  A, B, C продолжают голодать.

Starvation mode:

  Мьютекс освобождён.
  ┌─────────────────────────────────────┐
  │ Ждущие: A, B, C                     │
  │ Новые: D, E                         │
  └─────────────────────────────────────┘
       │
       ▼
  Мьютекс передаётся НАПРЯМУЮ A.
  D, E не могут захватить.
  Справедливость восстановлена.
```

### Почему это важно

**Без starvation mode:** при высокой конкуренции некоторые горутины могут голодать **бесконечно**. Это приводит к непредсказуемым задержкам.

**С starvation mode:** задержка ограничена. Горутина, ждущая > 1 мс, получит мьютекс.

**Цена:** starvation mode **снижает пропускную способность**. Потому что мьютекс передаётся напрямую, без конкуренции. Это trade-off: **справедливость vs throughput**.

### Когда starvation mode активируется

- Горутина ждёт мьютекс > 1 мс.
- Мьютекс переходит в `mutexStarving`.
- Все новые `Lock()` видят `starving` и **не пытаются захватить** — идут в очередь.

**Пока starvation mode активен:** мьютекс передаётся по очереди. Справедливость.

**Когда выходит:** когда последняя ждущая горутина захватила и отпустила мьютекс, и новых ждущих нет (или они держат < 1 мс).

### Аннотация сложности

| Режим | Throughput | Latency | Use case |
|:---|:---|:---|:---|
| Normal | Высокий | Может быть высокий (голодание) | Низкая конкуренция |
| Starving | Ниже | Ограничен | Высокая конкуренция |

### 💡 Практика: что важно знать про starvation

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: starvation mode активируется автоматически** при ожидании > 1 мс. Тебе не нужно ничего настраивать.

2. **Короткие критические секции — лучшая защита.** Чем меньше держишь мьютекс, тем меньше ждут другие (см. 3.4 про contention).

**👍 СТОИТ СДЕЛАТЬ:**

3. **Мониторь contention.** `pprof` mutex profile покажет, где contention.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Знать точный порог (1 мс).** Но полезно понимать, что starvation mode существует.

**❌ НЕ ДЕЛАЙ:**

5. **Не пытайся «оптимизировать» starvation mode.** Он работает автоматически.
6. **Не держи мьютекс долго.** Это провоцирует starvation mode и снижает throughput.

### Ключевые выводы подглавы 3.5

- **Starvation mode** — режим, при котором мьютекс передаётся напрямую ждущей горутине.
- **Активируется** при ожидании > 1 мс.
- **Цель:** предотвратить бесконечное голодание.
- **Цена:** снижение пропускной способности.
- **Лучшая защита:** короткие критические секции.

## 3.6 Почему Mutex не рекурсивный

Один из самых частых вопросов: «Почему `Mutex` в Go не рекурсивный?» Разберём.

### Что такое рекурсивный мьютекс

**Рекурсивный мьютекс** (reentrant mutex) — мьютекс, который может быть захвачен **одной и той же горутиной** несколько раз.

```go
// Гипотетический рекурсивный мьютекс:
mu.Lock()
    // ...
    mu.Lock()  // ✅ работает в рекурсивном мьютексе
        // ...
    mu.Unlock()
mu.Unlock()
```

**В Go `sync.Mutex` — не рекурсивный:**

```go
mu.Lock()
    mu.Lock()  // ❌ DEADLOCK
mu.Unlock()
```

### Почему Go выбрал нерекурсивный Mutex

**1. Рекурсивный мьютекс — это «запах» плохого дизайна.**

Если функция `A` захватывает мьютекс, а потом вызывает функцию `B`, которая **тоже** захватывает тот же мьютекс — это означает, что **границы критической секции размыты**. Непонятно, кто владеет мьютексом.

**2. Рекурсивный мьютекс скрывает ошибки.**

Если ты случайно вызвал `Lock()` дважды, рекурсивный мьютекс не скажет об этом. Нерекурсивный — **сразу deadlock**, и ты видишь ошибку.

**3. Рекурсивный мьютекс требует знания «владельца».**

Чтобы знать, кто захватил мьютекс, нужно хранить `goroutine ID`. Но **goroutine ID не доступен** в Go (специально, чтобы не поощрять рекурсивные мьютексы). Это добавило бы накладные расходы.

**4. Go-философия: явное лучше неявного.**

Рекурсивный мьютекс — неявное поведение. Go предпочитает явные конструкции.

### Что делать вместо рекурсивного мьютекса

**1. Разделить критическую секцию.**

```go
// ❌ Плохо: вложенные Lock
func (s *Service) Process() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.processInternal()  // тоже Lock — deadlock
}

// ✅ Хорошо: разделить
func (s *Service) Process() {
    s.mu.Lock()
    data := s.getData()
    s.mu.Unlock()
    
    s.processData(data)  // без мьютекса
}

func (s *Service) getData() []Data {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.data
}
```

**2. Использовать приватные методы без Lock.**

```go
// Публичный метод — с Lock.
func (s *Service) Process() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.processLocked()  // приватный метод, БЕЗ Lock
}

// Приватный метод — предполагает, что Lock уже захвачен.
func (s *Service) processLocked() {
    // работа с s.data без Lock
}
```

**Соглашение:** методы с суффиксом `Locked` предполагают, что мьютекс уже захвачен.

**3. Использовать `sync.RWMutex` с аккуратностью.**

`RWMutex` **тоже не рекурсивный**. `RLock` можно вызывать несколько раз из разных горутин, но `Lock` и `RLock` из одной горутины — deadlock.

### Пример: как НЕ надо

```go
// ❌ Плохо: рекурсивный вызов
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.incInternal()  // тоже Lock
}

func (c *Counter) incInternal() {
    c.mu.Lock()  // DEADLOCK
    defer c.mu.Unlock()
    c.n++
}
```

### Пример: как надо

```go
// ✅ Хорошо: разделение
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.incLocked()
}

func (c *Counter) incLocked() {
    // предполагает, что Lock уже захвачен
    c.n++
}
```

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| Рекурсивный Lock (гипотетический) | ~30-50 нс | +8 байт (goroutine ID) | Не в Go |
| Нерекурсивный Lock | ~15-25 нс | 0 | Go |

### 💡 Практика: как избежать рекурсивного Lock

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Разделяй критические секции.** Публичный метод с `Lock`, приватный — без.
2. **Соглашение `Locked`:** `processLocked()` предполагает захваченный мьютекс.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Проверяй с `go vet`** — он не ловит рекурсивный Lock, но ловит копирование.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Комментарии** для методов, требующих захваченного мьютекса.

**❌ НЕ ДЕЛАЙ:**

5. **Не пытайся реализовать рекурсивный мьютекс.** Это плохой дизайн.
6. **Не вызывай `Lock()` дважды.** Deadlock.
7. **Не смешивай `Lock` и `RLock` из одной горутины.** Deadlock.

### Ключевые выводы подглавы 3.6

- **`sync.Mutex` не рекурсивный.** `Lock()` дважды из одной горутины — deadlock.
- **Почему:** рекурсивный мьютекс — плохой дизайн, скрывает ошибки, требует goroutine ID.
- **Что делать:** разделять критические секции, использовать `Locked`-соглашение.
- **`RWMutex` тоже не рекурсивный.**

## 3.7 sync.RWMutex: читатели и писатели

`sync.RWMutex` — мьютекс с разделением на читателей и писателей.

### Идея

**Проблема `Mutex`:** если 100 горутин только **читают** данные, они всё равно сериализуются — то есть выстраиваются в очередь, одна за другой. Хотя чтение не конфликтует с чтением.

**Решение `RWMutex`:** разрешить **нескольким читателям** одновременно, но писатель — только один.

```
Mutex:
  [R] [R] [R] [W] [R] [R]  — все по очереди

RWMutex:
  [R R R] [W] [R R R]       — читатели параллельно, писатель один
```

### API

```go
var rw sync.RWMutex

// Читатели:
rw.RLock()
// ... чтение ...
rw.RUnlock()

// Писатели:
rw.Lock()
// ... запись ...
rw.Unlock()
```

### Структура RWMutex

```go
type RWMutex struct {
    w           Mutex   // мьютекс для писателей
    writerSem   uint32  // семафор для ждущих писателей
    readerSem   uint32  // семафор для ждущих читателей
    readerCount atomic.Int32  // число активных читателей
    readerWait  atomic.Int32  // число читателей, которых ждёт писатель
}
```

**Размер `RWMutex` — 24 байта** (на 64-битной). Больше, чем `Mutex` (8 байт).

### Как это работает

**RLock (читатель):**

```
1. readerCount++ (атомарно).
2. Если readerCount < 0 → писатель ждёт или пишет:
   → readerCount-- (откат).
   → readerSem — блокироваться, пока писатель не закончит.
3. Читатель захватил.
```

**RUnlock (читатель):**

```
1. readerCount-- (атомарно).
2. Если readerCount < 0 → писатель ждёт:
   → readerWait--.
   → Если readerWait == 0 → разбудить писателя (writerSem).
```

**Lock (писатель):**

```
1. w.Lock() — захватить внутренний Mutex.
2. readerCount -= maxReaders (атомарно).
   → Теперь readerCount < 0 → новые читатели блокируются.
3. Если были активные читатели:
   → readerWait = -readerCount.
   → writerSem — ждать, пока все читатели закончат.
4. Писатель захватил.
```

**Unlock (писатель):**

```
1. readerCount += maxReaders.
2. w.Unlock() — освободить внутренний Mutex.
3. Разбудить всех ждущих читателей (readerSem).
```

### Пример: кэш пользователей

Разберём конкретный сценарий, чтобы понять, **на что именно влияет** `RWMutex`.

**Задача:** кэш пользователей. 100 горутин читают `GetUser(42)`, 1 горутина пишет `SetUser(42, ...)`. Чтение — быстрая операция (взятие из map).

```go
type User struct {
    ID   int
    Name string
}

type UserCache struct {
    mu    sync.Mutex   // или sync.RWMutex
    users map[int]User
}

func NewUserCache() *UserCache {
    return &UserCache{users: make(map[int]User)}
}

func (c *UserCache) GetUser(id int) (User, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    u, ok := c.users[id]
    return u, ok
}

func (c *UserCache) SetUser(u User) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.users[u.ID] = u
}
```

**Сценарий:** 100 горутин читают `GetUser(42)`, 1 горутина пишет `SetUser(42, ...)` в момент `t=0`.

### Пошаговый разбор с `Mutex`

```
t=0:   G1 (writer): Lock() → захватил → пишет
t=1:   G2 (reader): Lock() → ЖДЁТ
t=2:   G3 (reader): Lock() → ЖДЁТ
t=3:   G4 (reader): Lock() → ЖДЁТ
...
t=100: G1 (writer): Unlock()
t=101: G2 (reader): Lock() → захватил → читает → Unlock()
t=102: G3 (reader): Lock() → ЖДЁТ
t=103: G4 (reader): Lock() → ЖДЁТ
t=104: G5 (reader): Lock() → ЖДЁТ
...
```

**Что происходит:**

- Все читатели **выстраиваются в очередь** за мьютексом.
- Каждый читатель ждёт, пока предыдущий не отпустит мьютекс.
- Даже если чтение не изменяет данные — оно всё равно сериализуется.

**Время выполнения:** 100 читателей × T_read. Если T_read = 100 нс, то 10 мкс.

### Пошаговый разбор с `RWMutex`

```
t=0:   G1 (writer): Lock() → захватил → пишет
t=1:   G2 (reader): RLock() → ЖДЁТ (писатель активен)
t=2:   G3 (reader): RLock() → ЖДЁТ (писатель активен)
t=3:   G4 (reader): RLock() → ЖДЁТ (писатель активен)
...
t=100: G1 (writer): Unlock()
t=101: G2 (reader): RLock() → захватил (читатели параллельно)
t=101: G3 (reader): RLock() → захватил (читатели параллельно)
t=101: G4 (reader): RLock() → захватил (читатели параллельно)
t=101: G5 (reader): RLock() → захватил (читатели параллельно)
...
t=102: G2..G101: RUnlock()
```

**Что происходит:**

- Читатели **не выстраиваются в очередь** друг за другом — они захватывают `RLock` параллельно.
- Только писатель блокирует всех.
- Когда писатель отпускает — все читатели читают **одновременно**.

**Время выполнения:** 1 × T_read (все читатели параллельно). Если T_read = 100 нс, то 100 нс. **В 100 раз быстрее.**

### Визуализация различий

```
Mutex (100 читателей, 1 писатель):
  Writer:  [W]
  Readers:    [R] [R] [R] [R] [R] ... [R]  ← по очереди
  Общее:   ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~ 100 × T_read

RWMutex (100 читателей, 1 писатель):
  Writer:  [W]
  Readers:    [R R R R R ... R]  ← параллельно
  Общее:   ~~~~~~~~~~~~~~~~~~~~ 1 × T_read
```

### Ключевое различие

| Аспект | `Mutex` | `RWMutex` |
|:---|:---|:---|
| Читатели | По очереди (сериализация доступа) | Параллельно |
| Писатель | Блокирует всех | Блокирует всех |
| Читатель vs писатель | Блокируют друг друга | Блокируют друг друга |
| Пропускная способность (read-heavy) | Низкая | Высокая |
| Overhead (uncontended) | ~15-25 нс | ~20-30 нс |
| Размер | 8 байт | 24 байта |

### Когда `RWMutex` реально выигрывает

**Выигрывает, если:**

- **Чтение долгое** (обход большой map, парсинг JSON). Читатели параллельны → пропускная способность растёт.
- **Много читателей** (100+ горутин). Очередь на `Mutex` растёт → `RWMutex` пропускает параллельно.
- **Мало писателей** (10% и меньше).

**Не выигрывает, если:**

- **Чтение короткое** (получение поля из map — 50 нс). Overhead `RWMutex` (два `atomic.AddInt32`) выше → медленнее.
- **Мало горутин** (2-3). Нет конкуренции → `Mutex` проще и быстрее.
- **Много писателей** (50%+). `RWMutex` не даёт выигрыша, только overhead.

### Бенчмарк

```go
package main

import (
    "sync"
    "testing"
)

// Короткое чтение — RWMutex медленнее
func BenchmarkMutexShortRead(b *testing.B) {
    var mu sync.Mutex
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.Lock()
            _ = 42
            mu.Unlock()
        }
    })
}

func BenchmarkRWMutexShortRead(b *testing.B) {
    var mu sync.RWMutex
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.RLock()
            _ = 42
            mu.RUnlock()
        }
    })
}

// Долгое чтение — RWMutex быстрее
func BenchmarkMutexLongRead(b *testing.B) {
    var mu sync.Mutex
    data := make([]int, 10000)
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.Lock()
            sum := 0
            for _, v := range data {
                sum += v
            }
            _ = sum
            mu.Unlock()
        }
    })
}

func BenchmarkRWMutexLongRead(b *testing.B) {
    var mu sync.RWMutex
    data := make([]int, 10000)
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.RLock()
            sum := 0
            for _, v := range data {
                sum += v
            }
            _ = sum
            mu.RUnlock()
        }
    })
}
```

**Результат (примерный):**

```
Короткое чтение (получение поля):
BenchmarkMutexShortRead-8       50000000    25 ns/op
BenchmarkRWMutexShortRead-8     30000000    40 ns/op  ← RWMutex медленнее

Долгое чтение (обход 10000 элементов):
BenchmarkMutexLongRead-8         1000000  1500 ns/op
BenchmarkRWMutexLongRead-8       5000000   300 ns/op  ← RWMutex быстрее в 5 раз
```

**Что видно:**

- Для **короткого** чтения `RWMutex` **медленнее** — overhead `atomic.AddInt32` на `readerCount` не окупается.
- Для **долгого** чтения `RWMutex` **быстрее в 5 раз** — параллельное чтение даёт выигрыш.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `RLock/RUnlock` (нет писателя) | ~20-30 нс | 0 | Параллельное чтение |
| `RLock` (писатель ждёт) | ~мкс-мс | 0 | Блокировка |
| `Lock/Unlock` (нет читателей) | ~25-40 нс | 0 | Запись |
| `Lock` (читатели активны) | ~мкс-мс | 0 | Ожидание читателей |

### 💡 Практика: когда использовать RWMutex

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **RWMutex — когда чтение доминирует (90%+) и оно длительное.**
2. **Бенчмаркай перед заменой `Mutex` на `RWMutex`.** Часто `Mutex` быстрее.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для read-heavy кэшей с дорогим чтением** (парсинг, обход больших структур).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для коротких чтений `Mutex` может быть лучше.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `RWMutex` «на всякий случай».** Overhead выше.
6. **Не используй `RWMutex`, если писателей много.** Он не даст выигрыша.
7. **Не смешивай `Lock` и `RLock` из одной горутины.** Deadlock.

### Ключевые выводы подглавы 3.7

- **`RWMutex`** — читатели параллельно, писатель один.
- **Размер — 24 байта** (больше `Mutex`).
- **`RLock/RUnlock`** — `atomic.AddInt32` на `readerCount`.
- **`Lock/Unlock`** — блокирует читателей, ждёт активных.
- **С `Mutex`:** читатели выстраиваются в очередь (сериализация доступа).
- **С `RWMutex`:** читатели параллельны.
- **Не всегда быстрее `Mutex`.** Бенчмаркай.
- **Для read-heavy с длинным чтением — быстрее в разы.**

## 3.8 sync/atomic: атомарные операции

`sync/atomic` — пакет для **атомарных** операций над переменными.

### Что такое атомарная операция

**Атомарная операция** — операция, которая выполняется **целиком** или **не выполняется вообще**. Нет промежуточных состояний.

```
Не атомарно:
  counter++  →  read, add, write  (3 операции)

Атомарно:
  atomic.AddInt64(&counter, 1)  →  1 операция (CAS или LOCK XADD)
```

### API

```go
// Старый API (до Go 1.19):
var counter int64
atomic.AddInt64(&counter, 1)  // инкремент

// Новый API (Go 1.19+):
var counter atomic.Int64
counter.Add(1)  // инкремент
```

**Новый API — предпочтительнее:** безопаснее, читаемее, нельзя случайно скопировать.

### Основные операции

```go
var v atomic.Int64

// Add — добавить
v.Add(1)

// Load — прочитать
x := v.Load()

// Store — записать
v.Store(42)

// Swap — заменить и вернуть старое
old := v.Swap(100)

// CompareAndSwap — заменить, если равно ожидаемому
swapped := v.CompareAndSwap(100, 200)
```

### Как это работает на уровне CPU

**x86-64:**

- `LOCK XADD` — атомарное сложение.
- `LOCK CMPXCHG` — атомарное сравнение и замена (CAS).
- `MOV` с барьером памяти — для Load/Store.

**ARM64:**

- `LDADD` — атомарное сложение.
- `CAS` — атомарное сравнение и замена.

**Барьеры памяти:** атомарные операции включают **барьеры**, чтобы гарантировать видимость изменений между ядрами. Это делает их дороже обычных операций, но дешевле мьютексов.

### Стоимость

| Операция | Time | Use case |
|:---|:---|:---|
| `atomic.Add` | ~5-10 нс | Счётчики |
| `atomic.Load` | ~1-2 нс | Чтение флага |
| `atomic.Store` | ~1-2 нс | Запись флага |
| `atomic.CompareAndSwap` | ~5-15 нс | Lock-free структуры |
| `Mutex.Lock/Unlock` | ~15-25 нс | Защита секции |

**Атомики быстрее мьютексов** в 2-3 раза для простых операций.

### Когда использовать atomic

**✅ Подходит:**

- **Счётчики:** `atomic.AddInt64`.
- **Флаги:** `atomic.Bool`.
- **Указатели:** `atomic.Pointer[T]`.
- **Lock-free структуры:** очереди, стеки (сложно).

**❌ Не подходит:**

- **Защита нескольких переменных.** `atomic` работает с **одной** переменной.
- **Сложные операции.** «Прочитать, вычислить, записать» — не атомарно.
- **Защита структур.** `map`, `slice` — нужен `Mutex`.

### Пример: счётчик

```go
// ❌ Плохо: data race
var counter int
counter++

// ✅ Хорошо: atomic
var counter atomic.Int64
counter.Add(1)
```

### Пример: флаг

```go
// ❌ Плохо: data race
var ready bool
ready = true  // в одной горутине
if ready { }  // в другой

// ✅ Хорошо: atomic
var ready atomic.Bool
ready.Store(true)
if ready.Load() { }
```

### Пример: CompareAndSwap

**CAS** — основа lock-free структур. «Заменить, если текущее значение равно ожидаемому».

```go
var value atomic.Int64

// Попытаться заменить 10 на 20
if value.CompareAndSwap(10, 20) {
    // успех: было 10, стало 20
} else {
    // неудача: значение не 10
}
```

**Использование:** оптимистичные блокировки, lock-free алгоритмы.

### Опасность: atomic не заменяет Mutex

**❌ Плохо:**

```go
var a, b atomic.Int64

// Хотим атомарно увеличить оба
a.Add(1)
b.Add(1)  // ← не атомарно вместе!
```

**Между `a.Add` и `b.Add` может произойти что угодно.** Если нужна атомарность для нескольких переменных — используй `Mutex`.

**✅ Хорошо:**

```go
var mu sync.Mutex
var a, b int64

mu.Lock()
a++
b++
mu.Unlock()
```

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `atomic.Add` | ~5-10 нс | 8 байт | Счётчики |
| `atomic.Load` | ~1-2 нс | 8 байт | Флаги |
| `atomic.Store` | ~1-2 нс | 8 байт | Флаги |
| `atomic.CompareAndSwap` | ~5-15 нс | 8 байт | Lock-free |
| `Mutex.Lock/Unlock` | ~15-25 нс | 8 байт | Защита секции |

### 💡 Практика: когда использовать atomic

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков — `atomic.Int64`.**
2. **Для флагов — `atomic.Bool`.**
3. **Для указателей — `atomic.Pointer[T]`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Новый API (Go 1.19+):** `atomic.Int64`, `atomic.Bool`, а не `atomic.AddInt64(&v, 1)`.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **CAS для lock-free структур** — только если понимаешь, что делаешь.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `atomic` для нескольких переменных.** Только одна.
7. **Не используй `atomic` для сложных операций.** «Прочитать, вычислить, записать» — не атомарно.
8. **Не используй `atomic` для защиты map/slice.** Нужен `Mutex`.

### Ключевые выводы подглавы 3.8

- **`atomic`** — атомарные операции над одной переменной.
- **Быстрее `Mutex`** в 2-3 раза для простых операций.
- **Основные операции:** `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap`.
- **Использование:** счётчики, флаги, указатели, lock-free структуры.
- **Не заменяет `Mutex`** для нескольких переменных или сложных операций.
- **Новый API (Go 1.19+)** предпочтительнее.

## 3.9 sync.WaitGroup: ожидание группы горутин

`sync.WaitGroup` — примитив для ожидания завершения группы горутин.

### API

```go
var wg sync.WaitGroup

wg.Add(1)  // добавить 1 к счётчику
go func() {
    defer wg.Done()  // уменьшить счётчик на 1
    // работа
}()

wg.Wait()  // ждать, пока счётчик станет 0
```

### Структура WaitGroup

```go
type WaitGroup struct {
    noCopy noCopy      // защита от копирования
    state  atomic.Uint64  // счётчик + waiter count
    sema   uint32      // семафор для блокировки
}
```

**`state`** — 64-битное поле:
- **Старшие 32 бита** — счётчик (`counter`).
- **Младшие 32 бита** — число ждущих (`waiters`).

### Как это работает

**Add(delta):**

```
1. atomic.AddUint64(&state, uint64(delta)<<32)
   → Добавить delta к счётчику.
2. Если delta < 0 и counter == 0:
   → Разбудить всех ждущих (Semrelease).
```

**Done():**

```
1. Add(-1).
```

**Wait():**

```
1. Прочитать state.
2. Если counter == 0:
   → return (ничего не ждём).
3. Если counter > 0:
   → waiters++.
   → Semacquire(&sema) — блокироваться.
```

### Визуализация

```
WaitGroup:

  counter = 3
  waiters = 0

Горутина A: wg.Add(1) → counter = 4
Горутина B: wg.Done() → counter = 3
Горутина C: wg.Wait() → waiters = 1, блокируется
Горутина D: wg.Done() → counter = 2
Горутина E: wg.Done() → counter = 1
Горутина F: wg.Done() → counter = 0
  → Разбудить всех ждущих (C).

C: Wait() возвращается.
```

### Важно: Add должен быть до Wait

**❌ Плохо:**

```go
var wg sync.WaitGroup

go func() {
    wg.Add(1)  // ← может выполниться ПОСЛЕ Wait
    defer wg.Done()
    // работа
}()

wg.Wait()  // может вернуться сразу (counter = 0)
```

**✅ Хорошо:**

```go
var wg sync.WaitGroup

wg.Add(1)  // до запуска горутины
go func() {
    defer wg.Done()
    // работа
}()

wg.Wait()
```

**Правило:** `Add` вызывается **до** `Wait` (и до запуска горутин).

### Нельзя копировать WaitGroup

`WaitGroup` содержит `noCopy` — `go vet` поймает копирование. Но лучше помнить:

**❌ Плохо:**

```go
func process(wg sync.WaitGroup) {  // ← копия!
    defer wg.Done()
    // ...
}

// ✅ Хорошо:
func process(wg *sync.WaitGroup) {
    defer wg.Done()
    // ...
}
```

### Паттерн: worker pool с WaitGroup

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        // работа
    }(i)
}
wg.Wait()
```

### Паттерн: ожидание с таймаутом

`WaitGroup.Wait()` не поддерживает таймаут. Но можно обернуть:

```go
func waitWithTimeout(wg *sync.WaitGroup, timeout time.Duration) bool {
    done := make(chan struct{})
    go func() {
        wg.Wait()
        close(done)
    }()
    
    select {
    case <-done:
        return true  // завершилось
    case <-time.After(timeout):
        return false  // таймаут
    }
}
```

**Важно:** `WaitGroup` не отменяется. Горутины продолжат работу. Таймаут — только для **ожидания**, не для отмены.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `Add` | ~5-10 нс | 0 | Добавить счётчик |
| `Done` | ~5-10 нс | 0 | Уменьшить счётчик |
| `Wait` (counter > 0) | ~10-20 нс + ожидание | 0 | Ждать |
| `Wait` (counter == 0) | ~5-10 нс | 0 | Не ждать |

### 💡 Практика: как использовать WaitGroup

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Add` до `Wait`:**
   ```go
   wg.Add(1)
   go func() { defer wg.Done(); /* ... */ }()
   wg.Wait()
   ```

2. **`defer wg.Done()`** — гарантирует вызов даже при панике.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Передавай `*sync.WaitGroup`, не `sync.WaitGroup`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для таймаута — обёртка с каналом.**

**❌ НЕ ДЕЛАЙ:**

5. **Не копируй `WaitGroup`.**
6. **Не вызывай `Add` внутри горутины после `Wait`.**
7. **Не используй `WaitGroup` для отмены.** Только для ожидания.

### Ключевые выводы подглавы 3.9

- **`WaitGroup`** — счётчик + семафор. `state` — atomic.Uint64.
- **`Add`** — увеличить счётчик. **`Done`** — уменьшить. **`Wait`** — ждать нуля.
- **`Add` до `Wait`.** Иначе race.
- **Нельзя копировать.** `noCopy` + `go vet`.
- **Для таймаута — обёртка с каналом.** Но отмены нет.

## 3.10 sync.Once: инициализация ровно один раз

`sync.Once` — примитив для инициализации, которая должна выполниться **ровно один раз**.

### API

```go
var once sync.Once

once.Do(func() {
    // инициализация
})
```

**Что делает:** `once.Do(f)` вызывает `f` **ровно один раз**, даже если `Do` вызывается из нескольких горутин.

### Структура Once

```go
type Once struct {
    done atomic.Uint32  // 0 = не выполнено, 1 = выполнено
    m    Mutex          // для сериализации
}
```

### Как это работает

```
once.Do(f):

  1. if done.Load() == 1:
     → return (уже выполнено)
  
  2. m.Lock()
  
  3. if done.Load() == 1:  // double-check
     → m.Unlock()
     → return
  
  4. f()  // выполнить инициализацию
  
  5. done.Store(1)
  
  6. m.Unlock()
```

**Двойная проверка (double-check):** первый `done.Load()` — быстрый путь. Если `done == 1` — сразу return. Если 0 — захватить мьютекс и проверить снова.

### Паттерн: ленивая инициализация

```go
type Config struct {
    once sync.Once
    data map[string]string
}

func (c *Config) Get(key string) string {
    c.once.Do(func() {
        c.data = loadConfig()  // дорогая операция
    })
    return c.data[key]
}
```

**Что это даёт:** конфиг загружается **при первом обращении**, а не при создании. И **ровно один раз**, даже если 100 горутин вызывают `Get` одновременно.

### Паттерн: singleton

```go
var (
    instance *Service
    once     sync.Once
)

func GetInstance() *Service {
    once.Do(func() {
        instance = &Service{
            // инициализация
        }
    })
    return instance
}
```

### Важно: Once не сбрасывается

`sync.Once` **нельзя сбросить**. Если `Do` выполнился — он больше не выполнится. Даже если хочешь.

**Если нужно сбросить:** используй `sync.Mutex` или `atomic.Bool`:

```go
var (
    mu   sync.Mutex
    data map[string]string
)

func (c *Config) Get(key string) string {
    mu.Lock()
    if c.data == nil {
        c.data = loadConfig()
    }
    mu.Unlock()
    return c.data[key]
}
```

### Опасность: паника в Do

**Если `f` паникует** — `once.Do` считается **выполненным**. Повторный вызов не будет выполнять `f`.

```go
var once sync.Once

once.Do(func() {
    panic("oops")
})

once.Do(func() {
    fmt.Println("never printed")  // НЕ выполнится
})
```

**Правило:** не паникуй в `once.Do` или обрабатывай панику.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `once.Do` (первый раз) | ~20-50 нс + f | 0 | Инициализация |
| `once.Do` (повторно) | ~1-2 нс | 0 | Быстрый путь |

### 💡 Практика: как использовать Once

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для ленивой инициализации — `once.Do`:**
   ```go
   var once sync.Once
   once.Do(initFunc)
   ```

2. **Не паникуй в `once.Do`.** Или обрабатывай панику.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для singleton — `once.Do` + глобальная переменная.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для сбрасываемой инициализации — `Mutex` + флаг.**

**❌ НЕ ДЕЛАЙ:**

5. **Не пытайся сбросить `Once`.** Нельзя.
6. **Не используй `Once` для периодических задач.** Только один раз.

### Ключевые выводы подглавы 3.10

- **`Once`** — инициализация ровно один раз.
- **`done` + `Mutex`** — double-check.
- **Не сбрасывается.** Если нужно — `Mutex`.
- **Не паникуй в `Do`.** Иначе «выполнено».

## 3.11 sync.Map: когда он реально нужен

`sync.Map` — конкурентная map. Но **не замена** обычной map с `Mutex`.

### API

```go
var m sync.Map

m.Store("key", "value")  // записать
v, ok := m.Load("key")   // прочитать
m.Delete("key")          // удалить
m.Range(func(k, v any) bool {  // обход
    return true  // продолжить
})
```

### Структура sync.Map

```go
type Map struct {
    mu     Mutex
    read   atomic.Pointer[readOnly]  // read-only map (lock-free чтение)
    dirty  map[any]*entry            // dirty map (с мьютексом)
    misses int                        // число промахов read
}
```

**Идея:** `read` — read-only map, доступна **без блокировки**. `dirty` — с блокировкой.

### Как это работает

**Load:**

```
1. Прочитать read (атомарно).
2. Если ключ есть в read:
   → return (без блокировки!)
3. Иначе:
   → misses++
   → Захватить mu.
   → Проверить dirty.
   → Если есть — return.
   → Если misses > len(dirty):
      → read = dirty (промоут).
```

**Store:**

```
1. Прочитать read.
2. Если ключ есть в read:
   → Обновить значение (атомарно).
3. Иначе:
   → Захватить mu.
   → Обновить dirty.
```

**Ключевая идея:** чтение **часто lock-free**. Запись — с мьютексом.

### Когда sync.Map быстрее

**✅ `sync.Map` быстрее, если:**

- **Ключи стабильны** (пишутся редко, читаются часто).
- **Много горутин читают** одни и те же ключи.
- **Ключи не пересекаются** (каждая горутина работает со своими).

**❌ `sync.Map` медленнее, если:**

- **Много записей.** Каждая запись — `Mutex`.
- **Ключи постоянно меняются.** Промоут dirty → read дорогой.
- **Мало горутин.** `Mutex` + обычная map проще и быстрее.

### Бенчмарк

```go
func BenchmarkMutexMap(b *testing.B) {
    var mu sync.Mutex
    m := make(map[string]int)
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.Lock()
            _ = m["key"]
            mu.Unlock()
        }
    })
}

func BenchmarkSyncMap(b *testing.B) {
    var m sync.Map
    m.Store("key", 1)
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            m.Load("key")
        }
    })
}
```

**Результат (примерный, read-only):**

```
BenchmarkMutexMap-8     30000000    40 ns/op
BenchmarkSyncMap-8     100000000    15 ns/op  ← быстрее
```

**Результат (write-heavy):**

```
BenchmarkMutexMapWrite-8    20000000    60 ns/op
BenchmarkSyncMapWrite-8     10000000    120 ns/op  ← медленнее
```

### Когда использовать sync.Map

**✅ Подходит:**

- **Кэш с редкими записями и частыми чтениями.**
- **Реестр соединений** (каждая горутина работает со своим ключом).
- **Метрики** (ключи стабильны).

**❌ Не подходит:**

- **Обычная map с конкурентностью.** Используй `Mutex`.
- **Write-heavy сценарии.** `Mutex` быстрее.
- **Мало горутин.** Overhead `sync.Map` не окупается.

### Аннотация сложности

| Операция | Time | Space | Use case |
|:---|:---|:---|:---|
| `Load` (read hit) | ~10-15 нс | 0 | Lock-free чтение |
| `Load` (read miss) | ~50-100 нс | 0 | С мьютексом |
| `Store` (read hit) | ~15-25 нс | 0 | Атомарное обновление |
| `Store` (read miss) | ~50-100 нс | 0 | С мьютексом |

### 💡 Практика: когда использовать sync.Map

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для read-heavy кэшей — `sync.Map`.**
2. **Для реестров, где ключи стабильны.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Бенчмаркай перед заменой `Mutex` + map на `sync.Map`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Для write-heavy — `Mutex` + map.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `sync.Map` «на всякий случай».** Часто `Mutex` быстрее.
6. **Не используй `sync.Map` для счётчиков.** Для этого `atomic`.

### Ключевые выводы подглавы 3.11

- **`sync.Map`** — конкурентная map с lock-free чтением.
- **`read` + `dirty`** — две map. Чтение из `read` без блокировки.
- **Быстрее `Mutex` + map** для read-heavy.
- **Медленнее** для write-heavy.
- **Не замена** обычной map с `Mutex`.

## 3.12 Практика Go: диагностика contention

Теперь напишем **утилиту на Go**, которая демонстрирует и диагностирует contention:

1. **Mutex profile** — где contention на мьютексах.
2. **Block profile** — где горутины блокируются.
3. **Сравнение `Mutex` vs `RWMutex` vs `atomic`.**
4. **Демонстрация starvation mode.**

### Утилита 1: mutex profile

```go
package main

import (
    "fmt"
    "os"
    "runtime"
    "runtime/pprof"
    "sync"
    "time"
)

var (
    mu      sync.Mutex
    counter int
)

func main() {
    // Включаем mutex profiling
    runtime.SetMutexProfileFraction(1)

        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }

    // Ждём немного
    time.Sleep(100 * time.Millisecond)

    // Сохраняем профиль
    f, _ := os.Create("mutex.prof")
    pprof.Lookup("mutex").WriteTo(f, 0)
    f.Close()

    wg.Wait()
    fmt.Println("counter:", counter)
}
```

import (
    "fmt"
    "sync"
    "sync/atomic"

    var counter int

                _ = counter
                mu.RUnlock()
            }
        }()
    }

}

func benchAtomic() time.Duration {
    var counter atomic.Int64
    start := time.Now()

        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {

            }
        }()
    }

### Утилита 4: демонстрация starvation mode

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

var (
    mu        sync.Mutex
    starving  atomic.Bool
    waitTime  time.Duration
)

func main() {
    // Запускаем горутину, которая держит мьютекс долго
    go func() {
        mu.Lock()
        defer mu.Unlock()
        time.Sleep(10 * time.Millisecond)  // долгая операция
    }()

    time.Sleep(1 * time.Millisecond)

    // Запускаем 100 горутин, которые ждут мьютекс
    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            mu.Lock()
            mu.Unlock()
            if id == 0 {
                waitTime = time.Since(start)
            }
        }(i)
    }
    wg.Wait()

    fmt.Printf("Горутина 0 ждала: %v\n", waitTime)
    fmt.Println("(Если > 1ms — starvation mode активировался)")
}
```

**Вывод:**

```
Горутина 0 ждала: 12ms
(Если > 1ms — starvation mode активировался)
```

**Что видно:** горутина ждала 12 мс — starvation mode активировался. Без него горутина 0 могла бы голодать бесконечно.

## 3.13 Выводы и типичные ошибки

**Что мы узнали?**

`sync.Mutex` — 8 байт: `state` (битовая маска) + `sema` (ключ для поиска в `semaRoot`). Быстрый путь — один CAS (~15-25 нс). Slow path — spin + `runtime_SemacquireMutex`. Ждущие горутины хранятся **вне** мьютекса — в глобальной таблице `semaRoot` (treap `sudog`). Starvation mode активируется при ожидании > 1 мс. `Mutex` не рекурсивный. `RWMutex` — 24 байта, читатели параллельно, писатель один. Не всегда быстрее `Mutex`. `atomic` — атомарные операции над одной переменной, быстрее `Mutex` в 2-5 раз. `WaitGroup` — счётчик + семафор, `Add` до `Wait`, нельзя копировать. `Once` — инициализация один раз, не сбрасывается. `sync.Map` — lock-free чтение, для read-heavy. Contention — конкуренция за мьютекс, время ожидания ≈ O(N × T_hold). Каналы — не единственный инструмент.

**Типичные ошибки:**

- ❌ **Копировать `Mutex`.** Копия — независимый мьютекс, синхронизация ломается. `go vet` ловит.
- ❌ **Рекурсивный `Lock`.** `Mutex` не рекурсивный. `Lock` дважды — deadlock.
- ❌ **Смешивать `Lock` и `RLock` из одной горутины.** Deadlock.
- ❌ **Забывать `Unlock`.** Deadlock. Используй `defer`.
- ❌ **Длинные критические секции.** Contention (см. 3.4), starvation mode.
- ❌ **I/O под мьютексом.** Блокирует всех.
- ❌ **Один мьютекс на всё.** Разделяй.
- ❌ **`Add` внутри горутины после `Wait`.** Race. `Add` до `Wait`.
- ❌ **Копировать `WaitGroup`.** `noCopy` + `go vet`.
- ❌ **Паника в `once.Do`.** `Once` считается выполненным.
- ❌ **`sync.Map` «на всякий случай».** Часто `Mutex` быстрее.
- ❌ **`atomic` для нескольких переменных.** Только одна. Для нескольких — `Mutex`.
- ❌ **`atomic` для сложных операций.** «Прочитать, вычислить, записать» — не атомарно.
- ❌ **Игнорировать contention.** Mutex profile покажет.

## 3.14 Для быстрого повторения

- **`Mutex` — 8 байт:** `state` (locked, woken, starving, waiters) + `sema`. Быстрый путь — CAS (~15-25 нс). Slow path — spin + `runtime_SemacquireMutex`.
- **Ждущие горутины хранятся вне мьютекса** — в глобальной таблице `semaRoot` (treap). `sema` — ключ (адрес) для поиска.
- **`sudog`** — узел treap, оборачивает горутину в ожидании. ~48-64 байт. Используется в семафорах, каналах, select.
- **Starvation mode** активируется при ожидании > 1 мс. Мьютекс передаётся напрямую ждущей горутине. Trade-off: справедливость vs throughput.
- **Contention** — конкуренция за мьютекс. Время ожидания ≈ O(N × T_hold). Короткие секции, разделение мьютексов, `atomic`, `RWMutex`, sharding.
- **`Mutex` не рекурсивный.** `Lock` дважды — deadlock. Разделяй секции, используй `Locked`-соглашение.
- **`RWMutex` — 24 байта.** Читатели параллельно, писатель один. Не всегда быстрее `Mutex`. Бенчмаркай.
- **`atomic`** — атомарные операции над одной переменной. Быстрее `Mutex` в 2-5 раз. `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap`.
- **`WaitGroup`** — счётчик + семафор. `Add` до `Wait`. Нельзя копировать. Для таймаута — обёртка с каналом.
- **`Once`** — инициализация один раз. `done` + `Mutex` (double-check). Не сбрасывается. Не паникуй в `Do`.
- **`sync.Map`** — lock-free чтение (`read` + `dirty`). Для read-heavy. Для write-heavy — `Mutex` + map.
- **Сериализация доступа** — упорядочивание доступа к ресурсу (не путать с сериализацией данных).
- **Выбор инструмента:** счётчики → `atomic`, защита структуры → `Mutex`, read-heavy → `RWMutex`, ожидание → `WaitGroup`, инициализация → `Once`, передача владения → канал.
- **Диагностика:** `runtime.SetMutexProfileFraction`, `runtime.SetBlockProfileRate`, pprof.
- **Правило:** каналы — не единственный инструмент. `Mutex` — не «плохо».

## 3.16 Ответы

### Ответ 1

**Три случая, где каналы не подходят:**
1. **Счётчики и флаги.** `atomic` быстрее и проще.
2. **Защита структуры данных (map, slice).** `Mutex` или `RWMutex`.
3. **Ожидание группы горутин.** `WaitGroup`.
4. **Инициализация один раз.** `Once`.
5. **Высокочастотные операции.** `atomic` быстрее канала.

### Ответ 2

**Сериализация данных** — преобразование структуры в байты (JSON, Protobuf). К синхронизации отношения не имеет.

**Сериализация доступа** — упорядочивание доступа к ресурсу: горутины выстраиваются в последовательность, каждая получает доступ по очереди. В контексте синхронизации «сериализация» означает именно это.

### Ответ 3

`sync.Mutex` — 8 байт:
- `state int32` — битовая маска: `mutexLocked` (bit 0), `mutexWoken` (bit 1), `mutexStarving` (bit 2), `waiters` (bits 3-31).
- `sema uint32` — **ключ** (адрес) для поиска в глобальной таблице `semaRoot`. Не счётчик.

### Ответ 4

**Быстрый путь:** `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)`. Если state был 0 — мьютекс захвачен. ~15-25 нс.

**Slow path (`lockSlow`):** CAS не удался → spin (`runtime_procyield`), затем `runtime_SemacquireMutex(&m.sema)` — горутина блокируется в `semaRoot`. При пробуждении — попытка захватить снова. ~мкс-мс.

### Ответ 5

**Ждущие горутины хранятся в глобальной таблице `semaRoot`** — вне мьютекса. `Mutex.sema` — это **ключ** (адрес) для поиска в таблице.

**`semaRoot`** — структура:
```go
type semaRoot struct {
    lock  mutex
    treap *sudog      // дерево ждущих горутин
    nwait atomic.Uint32
}
```

**Почему дерево (treap), а не очередь:** семафоры адресуются по адресу переменной. Runtime должен быстро найти дерево для конкретного адреса. Treap даёт O(log N) поиск по ключу (адресу).

### Ответ 6

**`sudog`** — структура, оборачивающая горутину в ожидании. ~48-64 байт.

**Поля:**
- `g` — горутина.
- `next`/`prev` — связи (для treap — потомки, для каналов — очередь).
- `elem` — указатель на данные.
- `acquiretime`/`releasetime` — для трейсинга.
- `isSelect`/`success`/`waiters`/`parent`/`waitlink` — для select.
- `c` — канал (если ждём на канале).

**Где используется:** в семафорах (`semaRoot`), каналах (`sendq`/`recvq`), select.

### Ответ 7

**`sema` в `Mutex` — не счётчик, а ключ (адрес).** Потому что семафоров в программе может быть миллионы (каждый `Mutex`, `WaitGroup`, `Once`, канал). Держать для каждого полноценную структуру с деревом — расточительно.

**Глобальная таблица `semaRoot`** хранит деревья ждущих, индексированные по адресу семафора. `Mutex` (8 байт) содержит только `sema` — ключ для поиска.

### Ответ 8

**Contention** — конкуренция за мьютекс. Несколько горутин одновременно пытаются захватить один мьютекс. Одна захватывает, остальные уходят в slow path.

**Время ожидания** ≈ O(N × T_hold), где N — число горутин, T_hold — среднее время удержания.

**Как измерить:** `runtime.SetMutexProfileFraction(1)`, `pprof.Lookup("mutex")`, `go tool pprof mutex.prof`.

**Как уменьшить:**
1. Короткие критические секции (уменьшить T_hold).
2. Разделить мьютексы.
3. Использовать `atomic` где можно.
4. Использовать `RWMutex` для read-heavy.
5. Sharding.

### Ответ 9

**Starvation mode** — режим, при котором мьютекс передаётся напрямую ждущей горутине, а не конкурирует с новыми.

**Активируется:** когда горутина ждёт мьютекс > 1 мс.

**Зачем:** предотвратить бесконечное голодание. Без него новые горутины могут постоянно «перехватывать» мьютекс, а ждущие — голодать.

**Цена:** снижение пропускной способности (мьютекс передаётся без конкуренции).

### Ответ 10

**`Mutex` не рекурсивный, потому что:**
1. Рекурсивный мьютекс — «запах» плохого дизайна (размытые границы секции).
2. Скрывает ошибки (двойной Lock не виден).
3. Требует знания goroutine ID (недоступен в Go).
4. Go-философия: явное лучше неявного.

**Что делать:** разделять критические секции, использовать `Locked`-соглашение (публичный метод с Lock, приватный без).

### Ответ 11

**`RWMutex`:**
- Читатели (`RLock/RUnlock`) — параллельно.
- Писатель (`Lock/Unlock`) — один, блокирует читателей.
- Размер 24 байта.

**Пример:** кэш пользователей. С `Mutex` 100 читателей выстраиваются в очередь → 100 × T_read. С `RWMutex` читают параллельно → 1 × T_read. **В 100 раз быстрее** для read-heavy.

**Быстрее `Mutex`, когда:** много читателей, мало писателей, чтение длительное.

**Медленнее `Mutex`, когда:** короткие секции, мало горутин, write-heavy.

### Ответ 12

**`atomic`** — атомарные операции над одной переменной. `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap`.

**Отличие от `Mutex`:** работает с одной переменной, без блокировки, быстрее в 2-5 раз.

**Когда использовать:** счётчики, флаги, указатели, lock-free структуры.

**Когда не использовать:** несколько переменных, сложные операции, защита map/slice.

### Ответ 13

**`WaitGroup`:** `state atomic.Uint64` (counter + waiters) + `sema uint32`.

**`Add` до `Wait`:** если `Add` внутри горутины после `Wait`, `Wait` может вернуться сразу (counter = 0), не дождавшись горутины. Race.

### Ответ 14

**`sync.Once`:** `done atomic.Uint32` + `m Mutex`.

**Double-check:** первый `done.Load()` — быстрый путь (return, если done). Если 0 — `m.Lock()`, повторная проверка `done.Load()`, вызов `f()`, `done.Store(1)`, `m.Unlock()`.

### Ответ 15

**`sync.Map` быстрее:**
- Read-heavy (много чтений, мало записей).
- Ключи стабильны.
- Много горутин читают.

**`sync.Map` медленнее:**
- Write-heavy.
- Ключи часто меняются.
- Мало горутин.

### Ответ 16

**Два инструмента:**
1. **Mutex profile:** `runtime.SetMutexProfileFraction(1)`, `pprof.Lookup("mutex")`. Показывает contention на мьютексах.
2. **Block profile:** `runtime.SetBlockProfileRate(1)`, `pprof.Lookup("block")`. Показывает, где горутины блокируются.

### Ответ 17

**Копирование `Mutex`:** создаётся второй, независимый мьютекс. Синхронизация ломается. Data race.

**Копирование `WaitGroup`:** аналогично. `Add` в одной копии, `Done` в другой — счётчик не работает. `noCopy` + `go vet` ловят.

### Ответ 18

**`Lock()` дважды из одной горутины:** **deadlock**. Горутина ждёт саму себя. `Mutex` не рекурсивный.

### Ответ 19

**Паника в `once.Do`:** `Once` считается **выполненным**. Повторный вызов `Do` не выполнит `f`. Это опасно: если инициализация упала, она больше не выполнится.

### Ответ 20

**`atomic` не заменяет `Mutex` для нескольких переменных, потому что:**
- `atomic` работает с **одной** переменной.
- `a.Add(1); b.Add(1)` — не атомарно вместе. Между ними может произойти что угодно.
- Для атомарности нескольких переменных — `Mutex`.

### Ответ 21

**Разбуженная горутина после `Unlock`:**
1. `Unlock` вызывает `runtime_Semrelease(&m.sema)`.
2. `semrelease1` находит `sudog` в `semaRoot`, удаляет его.
3. `goready(sudog.g)` — горутина переходит в `_Grunnable`.
4. Горутина помещается в **очередь P** (локальная или глобальная).
5. Ждёт, когда планировщик её выберет.

**Важно:** `Unlock` **не передаёт мьютекс напрямую**. Разбуженная горутина должна **сама** захватить мьютекс (через CAS). Если не удалось — снова в `semaRoot`. Детали очередей P — в Главе 6.

🔐 **Ключевая идея:** Каналы — не единственный инструмент синхронизации. `sync.Mutex` (8 байт) — базовый примитив: `state` + `sema`. Ждущие горутины хранятся **вне** мьютекса — в глобальной таблице `semaRoot` (treap `sudog`). Быстрый путь — CAS. Slow path — spin + Semacquire. Starvation mode активируется при ожидании > 1 мс. `Mutex` не рекурсивный. `RWMutex` — для read-heavy, не всегда быстрее. `atomic` — быстрее `Mutex` в 2-5 раз, но только для одной переменной. `WaitGroup`, `Once`, `sync.Map` — специализированные примитивы. Contention — главная проблема: O(N × T_hold). Диагностика — mutex profile, block profile. `go vet` — всегда.
