## 3.0 Пролог: один обработчик, много событий

В предыдущих главах мы разобрали горутины и каналы. Мы умеем запускать горутины, знаем их стоимость, умеем передавать данные между ними.

Но есть задача, которую мы пока не умеем решать хорошо. Представим: у нас есть **один воркер**, который должен обрабатывать **несколько источников** событий одновременно. Например, воркер обрабатывает задачи из очереди, а ещё должен реагировать на сигнал остановки.

Наивное решение:

```go
func worker(tasksCh <-chan Task, stopCh <-chan struct{}) {
    for {
        // проверяем stopCh
        select {
        case <-stopCh:
            return
        default:
        }
        
        // проверяем tasksCh
        select {
        case task := <-tasksCh:
            process(task)
        default:
        }
    }
}
```

Это работает, но получается плохо. `worker` крутится в **busy loop** — постоянно проверяет оба канала, даже если ни один не готов. CPU сгорает на 100%, а пользы нет.

Хочется чего-то более простого: механизма, который **сам ждёт** готовности **любого** из нескольких каналов. Чтобы воркер заснул, пока не появится задача или сигнал остановки, и проснулся, когда что-то произойдёт.

Именно эту задачу решает **`select`**.

> **Мост к следующим главам:** `select` — основа мультиплексирования каналов. Worker pool (Глава 13), pipeline (Глава 11), graceful shutdown (Глава 26) — всё использует `select`. Понимание `select` критично для production-кода.

## 3.1 Что такое select

`select` — это **мультиплексор каналов**. Он позволяет горутине **ждать несколько каналов одновременно**.

### Синтаксис

```go
select {
case v := <-ch1:
    // ch1 готов к получению
case ch2 <- 42:
    // ch2 готов к отправке
case <-ch3:
    // ch3 готов к получению (значение игнорируется)
default:
    // ни один канал не готов
}
```

### Что делает select

`select` проверяет **все** case'ы на готовность:

- Если **несколько** готовы — выбирает **случайный**.
- Если **один** готов — выполняет его.
- Если **ни один** не готов:
  - Есть `default` — выполняет `default`.
  - Нет `default` — **блокируется**, пока один из case'ов не будет готов.

### Простой пример

```go
func worker(stopCh <-chan struct{}, tasksCh <-chan Task) {
    for {
        select {
        case <-stopCh:
            return
        case task := <-tasksCh:
            process(task)
        }
    }
}
```

**Что происходит:**

- `worker` спит, пока не готов один из каналов.
- Если получен `stopCh` — завершается.
- Если пришла задача — обрабатывает.
- **Нет busy loop.** CPU не жрётся.

### Схема

```
worker:
   │
   ▼
┌──────────────────────────────┐
│  select                      │
│  ├─ case <-stopCh            │
│  └─ case task := <-tasksCh   │
└──────────────────────────────┘
   │
   ├─ если stopCh готов → return
   │
   └─ если tasksCh готов → process(task)
   
   иначе — блокируется
```

### Когда использовать select

**1. Мультиплексирование каналов.**

Когда нужно ждать несколько каналов одновременно.

**2. Отмена операции.**

Добавить `ctx.Done()` к любому ожиданию.

**3. Таймауты.**

`select` с `time.After` или `context.WithTimeout`.

**4. Неблокирующие операции.**

`select` с `default`.

**5. Отключение case'ов.**

`nil`-канал в `select` — case игнорируется.

### 💡 Практика: как думать о select

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для мультиплексирования — `select`.**
2. **Для отмены — `select` с `ctx.Done()`.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Неблокирующая отправка — `select` + `default`.**
4. **Таймаут — `select` с `time.After` или `context`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `select` в busy loop без `default`.**
6. **Не путай `default` с «ничего не делать».**

## 3.2 Что происходит при select

Разберём, что физически происходит при `select`.

### Случайный выбор

Если **несколько** case'ов готовы — `select` выбирает **случайный**. Это не баг, а **намеренное** поведение.

**Почему случайный:**

- **Справедливость.** Если бы всегда выбирался первый готовый case, каналы «справа» голодали бы.
- **Нет приоритетов.** `select` не поддерживает приоритеты (об этом — в Главе 23).

**Пример:**

```go
ch1 := make(chan int, 1)
ch2 := make(chan int, 1)
ch1 <- 1
ch2 <- 2

for i := 0; i < 10; i++ {
    select {
    case v := <-ch1:
        fmt.Println("ch1:", v)
    case v := <-ch2:
        fmt.Println("ch2:", v)
    }
}
```

**Пример вывода:**

```
ch2: 2
ch1: 1
ch2: 2
ch1: 1
ch1: 1
ch2: 2
...
```

**Что видно:** порядок случайный. Оба канала обрабатываются.

### Как select устроен внутри

`select` в runtime представлен структурой `scase`:

```go
type scase struct {
    c    *hchan         // канал
    elem unsafe.Pointer // указатель на данные
    kind uint16         // caseRecv, caseSend, caseDefault
    // ...
}
```

Когда горутина вызывает `select`:

1. Runtime **перемешивает** порядок case'ов (для случайности).
2. Для каждого case'а проверяет готовность.
3. Если найден готовый — выполняет операцию.
4. Если есть `default` — выполняет его.
5. Если ни один не готов и `default` нет:
   - Создаёт `sudog` для каждого case'а.
   - Добавляет их в `sendq`/`recvq` соответствующих каналов.
   - Блокируется.
   - При пробуждении — удаляет `sudog`'и из остальных очередей.

### Схема

```
select {
case v := <-ch1: ...
case ch2 <- 42:  ...
default:         ...
}
   │
   ▼
┌──────────────────────────────────────┐
│  runtime.selectgo                    │
│                                      │
│  1. Случайный порядок case'ов        │
│                                      │
│  2. Для каждого case проверить:      │
│     caseRecv: sendq не пуста ||      │
│               qcount > 0 ||          │
│               closed → готов         │
│     caseSend: recvq не пуста ||      │
│               qcount < dataqsiz →    │
│               готов                  │
│                                      │
│  3. Если есть готовые:               │
│     → выбрать случайный              │
│     → выполнить операцию             │
│                                      │
│  4. Если есть default:               │
│     → выполнить default              │
│                                      │
│  5. Иначе:                           │
│     → создать sudog для каждого case │
│     → добавить в sendq/recvq         │
│     → gopark                         │
└──────────────────────────────────────┘
```

### Когда select блокируется

Если ни один case не готов и нет `default`, горутина переходит в `_Gwaiting`. Поток ОС **освобождается** для других горутин. При появлении готовности любого канала — горутина разблокируется.

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: `select` выбирает случайный case.**
2. **Помни: `select` без `default` блокируется.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Не полагайся на порядок case'ов.**

**❌ НЕ ДЕЛАЙ:**

4. **Не используй `select` для приоритетов** — он их не поддерживает.
5. **Не путай `select` с `switch`** — `select` работает только с каналами.

## 3.3 default: неблокирующие операции

`default` позволяет **не блокироваться**, если ни один case не готов.

### Синтаксис

```go
select {
case v := <-ch:
    // получили
default:
    // не блокируемся
}
```

### Неблокирующая отправка

```go
select {
case ch <- v:
    // отправили
default:
    // канал полон — не блокируемся
}
```

**Когда использовать:**

- **HTTP-хэндлеры.** Если буфер полон — вернуть 503, не висеть.
- **Логирование.** Если очередь переполнена — дропнуть сообщение.
- **Метрики.** Если буфер метрик полон — не блокировать приложение.

### Неблокирующее получение

```go
select {
case v := <-ch:
    process(v)
default:
    // нет данных — делаем что-то другое
}
```

**Когда использовать:**

- **Опрос канала в цикле.** Есть другая работа, а канал проверяем время от времени.
- **Отдача из кэша.** Если данные готовы — отдаём, иначе — обновляем кэш.

### Пример: HTTP-хэндлер с неблокирующей отправкой

```go
func handleOrder(w http.ResponseWriter, r *http.Request) {
    task := parseOrder(r)
    
    select {
    case tasksCh <- task:
        w.WriteHeader(http.StatusAccepted)
    default:
        http.Error(w, "server busy", http.StatusServiceUnavailable)
    }
}
```

**Что происходит:**

- Если в буфере есть место → 202 Accepted.
- Если буфер полон → 503 Service Unavailable.
- Хэндлер **никогда не блокируется**.

### Ловушка: потеря данных

`select` с `default` **дропает** операцию, если case не готов. Это **может быть проблемой**, если данные **нельзя терять**.

```go
// ❌ Плохо: заказ может потеряться
select {
case ordersCh <- order:
    // отправлен
default:
    log.Println("order dropped")
}
```

**Когда это приемлемо:** если заказ **некритичен** или можно переотправить.

**Когда это НЕ приемлемо:** если заказ **критичен** — нужна очередь с гарантией доставки (Kafka, NATS).

### 💡 Практика: как использовать default

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`select` + `default` для неблокирующих операций.**
2. **Для HTTP-хэндлеров — обязательно.**
3. **Помни: `default` дропает операцию.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для некритичных данных — drop.**
5. **Для критичных — очередь.**

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `default` для критичных данных.**
7. **Не путай `default` с «ничего не делать»** — это явное решение.

## 3.4 Таймауты через select

`select` — основной инструмент для таймаутов в Go.

### Таймаут через time.After

```go
select {
case v := <-ch:
    process(v)
case <-time.After(5 * time.Second):
    return errors.New("timeout")
}
```

**Что происходит:**

- `time.After` возвращает канал, в который отправляется значение через 5 секунд.
- `select` ждёт либо данных из `ch`, либо таймаута.
- Через 5 секунд сработает таймаут.

### Ловушка: time.After в цикле

**❌ Плохо:**

```go
for {
    select {
    case v := <-ch:
        process(v)
    case <-time.After(5 * time.Second):  // ← создаёт НОВЫЙ таймер каждый цикл
        return
    }
}
```

**Проблема:** `time.After` создаёт **новый таймер** на каждой итерации. Старые таймеры не освобождаются до срабатывания. Если цикл быстрый, а таймаут 5 секунд — тысячи таймеров в памяти.

**✅ Хорошо:**

```go
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()

for {
    select {
    case v := <-ch:
        process(v)
        timer.Reset(5 * time.Second)
    case <-timer.C:
        return
    }
}
```

**Что изменилось:** один таймер, `timer.Reset` перезапускает его.

### Таймаут через context

Более идиоматичный способ — `context.WithTimeout`:

```go
ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
defer cancel()

select {
case v := <-ch:
    process(v)
case <-ctx.Done():
    return ctx.Err()  // context.DeadlineExceeded
}
```

**Что происходит:**

- `ctx.Done()` — канал, который закрывается при отмене.
- Если таймаут истёк — `ctx.Err()` вернёт `DeadlineExceeded`.
- `cancel()` освобождает таймер.

**Преимущества:**

- Работает с отменой (если родительский `ctx` отменён — тоже сработает).
- `ctx.Err()` даёт **причину**.

### Что выбрать

| Способ | Когда |
|:---|:---|
| `time.After` | Простой таймаут, без отмены |
| `time.NewTimer` | Таймаут в цикле |
| `context.WithTimeout` | Таймаут + отмена |

**Рекомендация:** используй `context.WithTimeout` — он более гибкий.

### Пример: HTTP-запрос с таймаутом

```go
func fetchWithTimeout(ctx context.Context, url string) (*http.Response, error) {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    
    req, err := http.NewRequestWithContext(ctx, "GET", url, nil)
    if err != nil {
        return nil, err
    }
    return http.DefaultClient.Do(req)
}
```

**Что происходит:** HTTP-запрос отменяется через 5 секунд.

### 💡 Практика: как использовать таймауты

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для таймаута — `context.WithTimeout`.**
2. **`defer cancel()`** — обязательно.

**👍 СТОИТ СДЕЛАТЬ:**

3. **`time.NewTimer` для таймаута в цикле.**

**❌ НЕ ДЕЛАЙ:**

4. **Не используй `time.After` в цикле** — утечка таймеров.
5. **Не забывай `cancel()`** — утечка.

## 3.5 nil-канал: отключение case'ов

`nil`-канал в `select` — case **никогда не готов**. Это позволяет **динамически отключать** case'ы.

### Поведение

```go
var ch chan int  // ch == nil

select {
case <-ch:
    // НИКОГДА не выполнится
case <-otherCh:
    // выполнится, если otherCh готов
}
```

### Зачем это нужно

**Пример:** чтение из двух каналов, один из которых может быть закрыт.

```go
func merge(ch1, ch2 <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for ch1 != nil || ch2 != nil {
            select {
            case v, ok := <-ch1:
                if !ok {
                    ch1 = nil  // отключаем case
                    continue
                }
                out <- v
            case v, ok := <-ch2:
                if !ok {
                    ch2 = nil  // отключаем case
                    continue
                }
                out <- v
            }
        }
    }()
    return out
}
```

**Что происходит:**

- Пока `ch1` не закрыт — case `<-ch1` активен.
- Когда `ch1` закрыт — `ch1 = nil`.
- Case `<-ch1` с `nil`-каналом **никогда не готов** — `select` его игнорирует.
- Цикл продолжается, пока хотя бы один канал не `nil`.

### Схема

```
До закрытия ch1:
   select {
   case <-ch1:    ← активен
   case <-ch2:    ← активен
   }

После ch1 = nil:
   select {
   case <-nil:    ← НИКОГДА не готов
   case <-ch2:    ← активен
   }
```

### Ловушка: busy loop на закрытом канале

**❌ Плохо:**

```go
for {
    select {
    case v := <-ch:  // ← если ch закрыт, всегда готов, v = 0
        process(v)
    }
}
```

**Что происходит:** если `ch` закрыт, `<-ch` возвращает `zero` **немедленно**. `select` всегда готов. Цикл крутится на 100% CPU.

**✅ Хорошо:**

```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            return  // канал закрыт
        }
        process(v)
    }
}
```

**Что изменилось:** проверяем `ok` — выходим при закрытии.

### Практический пример: merge двух каналов

Именно так реализуется **fan-in** (см. Глава 9):

```go
func fanIn(ch1, ch2 <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for ch1 != nil || ch2 != nil {
            select {
            case v, ok := <-ch1:
                if !ok {
                    ch1 = nil
                    continue
                }
                out <- v
            case v, ok := <-ch2:
                if !ok {
                    ch2 = nil
                    continue
                }
                out <- v
            }
        }
    }()
    return out
}
```

### 💡 Практика: как использовать nil-канал

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`nil`-канал для отключения case'ов:**
   ```go
   case v, ok := <-ch:
       if !ok {
           ch = nil
           continue
       }
   ```

2. **Проверяй `ok` при получении в `select` внутри цикла.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Используй `for ch1 != nil || ch2 != nil`** для циклов с несколькими каналами.

**❌ НЕ ДЕЛАЙ:**

4. **Не `select` без `ok` на закрытом канале** — busy loop.
5. **Не закрывай `nil`-канал** — паника.

## 3.6 select и context

`select` и `context` — лучшие друзья. `ctx.Done()` — это канал, который отлично подходит для `select`.

### Паттерн: отменяемая операция

```go
func process(ctx context.Context, task Task) error {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case result := <-doWork(task):
        return handleResult(result)
    }
}
```

**Что происходит:**

- Если `ctx` отменён → возвращаем ошибку.
- Если задача завершилась → обрабатываем результат.
- **Отмена работает мгновенно.**

### Паттерн: отменяемый воркер

```go
func worker(ctx context.Context, tasksCh <-chan Task) {
    for {
        select {
        case <-ctx.Done():
            return
        case task := <-tasksCh:
            process(ctx, task)
        }
    }
}
```

**Что происходит:**

- Воркер ждёт задачу.
- Если `ctx` отменён → завершается.
- Иначе обрабатывает задачу.

### Паттерн: отменяемая отправка

```go
select {
case ch <- result:
    // отправлено
case <-ctx.Done():
    return ctx.Err()
}
```

**Что происходит:**

- Если канал готов → отправляем.
- Если `ctx` отменён → выходим.
- Не блокируемся навсегда.

### Паттерн: отменяемое получение

```go
select {
case v := <-ch:
    return v
case <-ctx.Done():
    return ctx.Err()
}
```

### Паттерн: комбинация таймаута и отмены

```go
ctx, cancel := context.WithTimeout(parentCtx, 5*time.Second)
defer cancel()

select {
case v := <-ch:
    process(v)
case <-ctx.Done():
    return ctx.Err()  // DeadlineExceeded или Canceled
}
```

**Что происходит:**

- Через 5 секунд — таймаут.
- Если родительский `ctx` отменён — тоже срабатывает.
- `ctx.Err()` показывает **причину**.

### Схема: полный воркер с отменой

```
worker(ctx, tasksCh):
   │
   ▼
┌──────────────────────────────┐
│  for {                       │
│    select {                  │
│    case <-ctx.Done():        │ ← отмена
│      return                  │
│    case task := <-tasksCh:   │ ← задача
│      process(ctx, task)      │
│    }                         │
│  }                           │
└──────────────────────────────┘
```

### 💡 Практика: как комбинировать select и context

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`ctx.Done()` в `select`** — для отмены.
2. **`ctx.Err()` для причины.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **`context.WithTimeout` для таймаута.**

**❌ НЕ ДЕЛАЙ:**

4. **Не игнорируй `ctx.Done()`.** Отмена не сработает.

## 3.7 Паттерн: worker с несколькими источниками

Классический паттерн — воркер, который слушает **несколько источников** и реагирует на любой.

### Идея

Воркер может получать задачи из **основной очереди** и из **очереди приоритета**. Или, например, слушать **сигнал остановки**.

```go
func worker(
    ctx context.Context,
    highPriorityCh <-chan Task,
    lowPriorityCh  <-chan Task,
) {
    for {
        select {
        case <-ctx.Done():
            return
        case task := <-highPriorityCh:
            process(task)
        case task := <-lowPriorityCh:
            process(task)
        }
    }
}
```

**Что происходит:**

- Воркер ждёт задачу из **любого** канала.
- `select` выбирает **случайный** из готовых.
- Отмена работает через `ctx.Done()`.

### Ловушка: приоритеты

`select` **не поддерживает приоритеты**. Если оба канала готовы — выбирается случайный. Если нужен приоритет, придётся его эмулировать.

**Эмуляция приоритета:**

```go
for {
    select {
    case <-ctx.Done():
        return
    case task := <-highPriorityCh:
        process(task)
    default:
        // high priority пуст, пробуем low
        select {
        case <-ctx.Done():
            return
        case task := <-highPriorityCh:
            process(task)
        case task := <-lowPriorityCh:
            process(task)
        }
    }
}
```

**Что происходит:**

- Сначала проверяем `highPriorityCh` без блокировки (`default`).
- Если есть — обрабатываем.
- Если нет — переходим к блокирующему `select` с обоими каналами.

**Минус:** если `highPriorityCh` всегда готов, `lowPriorityCh` **голодает**.

### Пример: воркер с rate limiter

```go
func worker(
    ctx context.Context,
    tasksCh <-chan Task,
    limiter *rate.Limiter,
) {
    for {
        select {
        case <-ctx.Done():
            return
        case task := <-tasksCh:
            if err := limiter.Wait(ctx); err != nil {
                return  // ctx отменён
            }
            process(task)
        }
    }
}
```

**Что происходит:**

- Воркер ждёт задачу.
- Перед обработкой ждёт разрешения rate limiter.
- Если `ctx` отменён — завершается.

### Пример: воркер с graceful shutdown

```go
func worker(
    ctx context.Context,
    tasksCh <-chan Task,
    resultsCh chan<- Result,
) {
    for {
        select {
        case <-ctx.Done():
            return
        case task, ok := <-tasksCh:
            if !ok {
                return  // канал закрыт
            }
            result := process(ctx, task)
            select {
            case resultsCh <- result:
            case <-ctx.Done():
                return
            }
        }
    }
}
```

**Что происходит:**

- Воркер слушает `ctx.Done()`, `tasksCh`.
- При получении задачи — обрабатывает.
- Результат отправляет в `resultsCh` тоже с отменой.

### Схема

```
worker:
   │
   ▼
┌──────────────────────────────────────┐
│  select                              │
│  ├─ <-ctx.Done()      → return       │
│  └─ task := <-tasksCh → process      │
│                          │           │
│                          ▼           │
│                     select           │
│                     ├─ resultsCh <- r│
│                     └─ <-ctx.Done()  │
└──────────────────────────────────────┘
```

### 💡 Практика: как строить воркер

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`ctx.Done()` в `select`** — обязательно.
2. **Проверяй `ok` при получении из канала.**
3. **Отмена при отправке результатов.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Эмуляция приоритетов через `select` + `default`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не полагайся на порядок case'ов.**
6. **Не забывай проверять `ctx.Err()`.**

## 3.8 Практика Go: диагностика select

Разберём **три примера**: таймаут, отмена, отключение case'ов.

### Пример 1: таймаут через select

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    ch := make(chan int)
    
    go func() {
        time.Sleep(2 * time.Second)
        ch <- 42
    }()
    
    start := time.Now()
    select {
    case v := <-ch:
        fmt.Printf("got %d after %v\n", v, time.Since(start))
    case <-time.After(1 * time.Second):
        fmt.Printf("timeout after %v\n", time.Since(start))
    }
}
```

**Пример вывода:**

```
timeout after 1.000123s
```

**Что видно:** через 1 секунду сработал таймаут, не 2 секунды.

### Пример 2: отмена через context

```go
package main

import (
    "context"
    "fmt"
    "time"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    
    // Отменяем через 500 мс
    go func() {
        time.Sleep(500 * time.Millisecond)
        cancel()
    }()
    
    ch := make(chan int)
    
    start := time.Now()
    select {
    case v := <-ch:
        fmt.Printf("got %d after %v\n", v, time.Since(start))
    case <-ctx.Done():
        fmt.Printf("canceled after %v: %v\n", time.Since(start), ctx.Err())
    }
}
```

**Пример вывода:**

```
canceled after 500ms: context canceled
```

**Что видно:** через 500 мс `ctx.Done()` сработал, `ctx.Err()` вернул `context canceled`.

### Пример 3: отключение case'ов через nil

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    ch1 := make(chan int, 1)
    ch2 := make(chan int, 1)
    
    ch1 <- 1
    ch2 <- 2
    close(ch1)
    
    total := 0
    for ch1 != nil || ch2 != nil {
        select {
        case v, ok := <-ch1:
            if !ok {
                fmt.Println("ch1 closed, disabling")
                ch1 = nil
                continue
            }
            fmt.Println("ch1:", v)
            total++
        case v, ok := <-ch2:
            if !ok {
                fmt.Println("ch2 closed, disabling")
                ch2 = nil
                continue
            }
            fmt.Println("ch2:", v)
            total++
        }
        time.Sleep(100 * time.Millisecond)
    }
    
    fmt.Println("total:", total)
}
```

**Пример вывода:**

```
ch2: 2
ch1: 1
ch1 closed, disabling
total: 2
```

**Что видно:**

- `ch2` прочитан.
- `ch1` прочитан из буфера (данные остались доступны после `close`).
- `ch1` отключён через `ch1 = nil`.
- Цикл завершается, когда оба канала `nil`.

### Пример 4: демонстрация случайного выбора

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    ch1 := make(chan int, 1)
    ch2 := make(chan int, 1)
    
    counts := map[string]int{}
    
    for i := 0; i < 100; i++ {
        ch1 <- 1
        ch2 <- 2
        
        select {
        case <-ch1:
            counts["ch1"]++
        case <-ch2:
            counts["ch2"]++
        }
        time.Sleep(time.Microsecond)
    }
    
    fmt.Printf("ch1: %d, ch2: %d\n", counts["ch1"], counts["ch2"])
}
```

**Пример вывода:**

```
ch1: 52, ch2: 48
```

**Что видно:** распределение примерно 50/50. `select` выбирает случайно.

### 💡 Практика: как диагностировать проблемы с select

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Проверяй `ok` при получении в `select`.**
2. **Не используй `time.After` в цикле.**
3. **Помни: `select` выбирает случайный case.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Дамп стеков при подозрении на busy loop.**
5. **pprof CPU при 100% загрузке.**

**❌ НЕ ДЕЛАЙ:**

6. **Не игнорируй закрытые каналы** — busy loop.
7. **Не полагайся на порядок case'ов.**

## 3.9 Выводы и типичные ошибки

**Что мы узнали?**

`select` — мультиплексор каналов. Он ждёт несколько каналов одновременно и выбирает **случайный** из готовых. `default` делает операцию неблокирующей. `time.After` и `context.WithTimeout` дают таймауты. `nil`-канал в `select` отключает case. `ctx.Done()` — основа отмены. Классический паттерн — воркер с несколькими источниками и `ctx.Done()`.

**Типичные ошибки:**

- ❌ **Думать, что `select` выбирает case в порядке.** Выбирает случайный.
- ❌ **`time.After` в цикле.** Утечка таймеров.
- ❌ **`select` без `ok` на закрытом канале.** Busy loop.
- ❌ **`select` с `default` для критичных данных.** Данные теряются.
- ❌ **Игнорировать `ctx.Done()`.** Отмена не сработает.
- ❌ **Забывать `defer cancel()`.** Утечка.
- ❌ **Полагать, что `select` поддерживает приоритеты.** Не поддерживает.
- ❌ **Не проверять `ctx.Err()`.** Теряешь причину отмены.
- ❌ **`select` с `nil`-каналом вне отключения case'ов.** Блокируется навсегда.
- ❌ **Не закрывать каналы владельцем.** `select` не завершится.

## 3.10 Для быстрого повторения

- **`select` — мультиплексор каналов.** Ждёт несколько каналов одновременно.
- **Случайный выбор.** Из готовых case'ов выбирается случайный.
- **`default` — неблокирующая операция.** Если никто не готов — выполняется `default`.
- **`time.After`** — простой таймаут. **`context.WithTimeout`** — с отменой.
- **`time.After` в цикле — утечка.** Используй `time.NewTimer`.
- **`nil`-канал в `select`** — case игнорируется. Для отключения case'ов.
- **`ch = nil` для отключения** закрытого канала.
- **Проверяй `ok` при получении** — иначе busy loop.
- **`ctx.Done()` в `select`** — для отмены.
- **`select` не поддерживает приоритеты.** Эмуляция через `default`.
- **Воркер:** `select` с `ctx.Done()`, `tasksCh`, `resultsCh`.
- **Отправка с отменой:** `select` с `ctx.Done()`.

## 3.12 Ответы

### Ответ 1

**`select`** — мультиплексор каналов. Он ждёт **несколько** каналов одновременно и выполняет case того, который готов. Если готовы несколько — выбирает случайный. Если ни один не готов — блокируется (или выполняет `default`).

### Ответ 2

**Случайный выбор** для **справедливости**. Если бы всегда выбирался первый готовый case, каналы «справа» голодали бы.

### Ответ 3

**`default`** — неблокирующая операция. Если ни один case не готов — выполняется `default`. Используется для:
- Неблокирующей отправки/получения.
- Опроса каналов в цикле.
- HTTP-хэндлеров (не висеть на отправке).

### Ответ 4

**`time.After` в цикле** создаёт **новый таймер** на каждой итерации. Старые таймеры не освобождаются до срабатывания. Если цикл быстрый, а таймаут долгий — тысячи таймеров в памяти.

**Решение:** `time.NewTimer` + `timer.Reset`.

### Ответ 5

**Отключение case через `nil`-канал:**

```go
case v, ok := <-ch:
    if !ok {
        ch = nil  // отключаем case
        continue
    }
```

`nil`-канал никогда не готов — `select` его игнорирует.

### Ответ 6

**`select` и `context`:**

```go
select {
case <-ctx.Done():
    return ctx.Err()
case v := <-ch:
    process(v)
}
```

`ctx.Done()` — канал, который закрывается при отмене. `select` реагирует на него как на любой другой канал.

### Ответ 7

**Избежать busy loop на закрытом канале:**

```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            return  // канал закрыт — выходим
        }
        process(v)
    }
}
```

Без `ok` — `<-ch` всегда готов при закрытом канале, цикл крутится.
