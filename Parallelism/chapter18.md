## 18.0 Пролог: паузы, которые убивают latency

Ты пишешь сервис с требованием **p99 < 10 мс**. Всё работает. Пока не начинается нагрузка.

**Метрики:**

- **p50:** 2 мс.
- **p95:** 5 мс.
- **p99:** 50 мс. ← **Проблема.**
- **p99.9:** 200 мс.

Ты смотришь в `gctrace`:

```
gc 100 @10.234s 0%: 0.1+5+0.2 ms clock, 0.8+2/10/0+1.6 ms cpu, 200->210->100 MB, 220 MB goal, 8 P
```

**Что видно:**

- **GC срабатывает часто** — 100 раз за 10 секунд.
- **Паузы 5 мс** — STW.
- **Heap 200 МБ** — растёт.

❓ **Что произошло?** GC **задерживает** горутины. Паузы 5 мс — это **p99**.

💡 **Решение:** уменьшить аллокации. Меньше мусора → реже GC → короче паузы.

**Это GC.** В этой главе — как он работает, почему паузы, и как его настраивать.

> **Важный мост:** GC работает **параллельно** с программой. Понимание GC критично для **низколатентных** сервисов. Глава 17 (Pool) — как уменьшить аллокации. Глава 19 (Паттерны) — как строить real-time системы.

## 18.1 Что такое GC и зачем он нужен

Прежде чем разбирать tri-color, поймём **что такое GC**.

### Проблема: ручное управление памятью

**В C/C++:**

```c
int* p = malloc(sizeof(int));
// используем p
free(p);  // ← нужно вручную освободить
```

**Проблемы:**

- **Забыть `free`** → утечка памяти.
- **Освободить дважды** → double free.
- **Использовать после `free`** → use-after-free.

### Решение: GC

**GC** — автоматическое освобождение памяти.

```go
p := new(int)
// используем p
// GC сам освободит, когда p больше не нужен
```

**Что делает GC:**

1. Находит объекты, которые **больше не используются**.
2. Освобождает их память.
3. Работает **параллельно** с программой.

### Что такое «мёртвый» объект

**Живой объект** — достижимый из **корней** (стек, глобальные переменные, регистры).

**Мёртвый объект** — недостижимый.

**Пример:**

```go
func process() {
    x := &Data{}  // x — корень (на стеке)
    _ = x
    // после return x уходит со стека → Data становится мёртвым
}
```

**Ключевое:** GC **не считает ссылки** (как в Python). Он обходит **граф объектов** от корней.

### Преимущества GC

1. **Нет утечек** от забытого `free`.
2. **Нет double free.**
3. **Нет use-after-free.**
4. **Проще код.**

### Недостатки GC

1. **CPU** — GC тратит CPU на обход.
2. **Паузы** — STW.
3. **Память** — GC нужен запас.
4. **Недетерминизм** — GC запускается, когда хочет.

### GC в Go

**Go GC:**

- **Concurrent** — работает параллельно.
- **Tri-color** — алгоритм маркировки.
- **Write barrier** — для корректности.
- **STW паузы** — короткие (микросекунды).
- **Pacing** — решает, когда запускаться.

### Альтернативы

**1. Ручное управление** (C/C++).

- Быстро, но опасно.

**2. Reference counting** (Python, Swift).

- Детерминированный, но медленный.
- Не справляется с циклами.

**3. Region-based** (Rust с borrow checker).

- Без GC, но сложно.

**4. GC** (Go, Java, C#).

- Просто, но паузы.

### Аннотация сложности

| Подход | CPU | Паузы | Безопасность |
|:---|:---|:---|:---|
| Ручное | Минимум | 0 | Опасно |
| Ref counting | Высокий | 0 | Безопасно (кроме циклов) |
| GC | Средний | Есть | Безопасно |

### 💡 Практика: что важно знать про GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: GC работает параллельно.** Он тратит CPU.
2. **Помни: GC нужен запас памяти.**
3. **Понимай, что аллокации нагружают GC.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь GC** — `gctrace`, `runtime/metrics`.
5. **Уменьшай аллокации** для low-latency.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Знать детали tri-color** — достаточно понимать идею.

**❌ НЕ ДЕЛАЙ:**

7. **Не игнорируй GC паузы** для p99.
8. **Не отключай GC** без понимания.

### Ключевые выводы подглавы 18.1

- **GC** — автоматическое освобождение памяти.
- **Мёртвый объект** — недостижимый от корней.
- **Go GC:** concurrent, tri-color, write barrier, STW.
- **GC тратит CPU** и **имеет паузы**.
- **Аллокации нагружают GC.**

## 18.2 Tri-color marking: как GC находит мёртвые объекты

**Tri-color marking** — алгоритм маркировки в Go GC.

### Идея

**Объекты делятся на три цвета:**

- **Белые** — не посещены (могут быть мёртвыми).
- **Серые** — посещены, но дети не обработаны.
- **Чёрные** — посещены, дети обработаны (живые).

### Алгоритм

```
1. Все объекты — белые.
2. Корни (стек, глобальные) — серые.
3. Пока есть серые:
   a. Взять серый объект.
   b. Пометить его чёрным.
   c. Всех его белых детей — серыми.
4. В конце: чёрные и серые — живые. Белые — мёртвые.
```

### Визуализация

```
Начало:
  [Root] ──▶ [A] ──▶ [B]
              │
              ▼
             [C]

  Все белые. Корни — серые.

Шаг 1:
  [Root] — чёрный
  [A] — серый (ребёнок Root)
  [B], [C] — белые

Шаг 2:
  [A] — чёрный
  [B], [C] — серые (дети A)

Шаг 3:
  [B] — чёрный (нет детей)
  [C] — чёрный (нет детей)

Конец:
  Все объекты — чёрные.
  Белых нет → ничего не освобождается.
```

### Пример с мёртвым объектом

```
Начало:
  [Root] ──▶ [A]
  [B] (недостижим)
  [C] (недостижим)

После три-цвета:
  [Root], [A] — чёрные.
  [B], [C] — белые.

Конец:
  [B], [C] — мёртвые → освобождаются.
```

### Три фазы GC

**1. Mark setup (STW).**

- Включить write barrier.
- Короткая пауза (~10-100 мкс).

**2. Marking (concurrent).**

- Обход графа.
- Работает параллельно с программой.
- Горутины могут помогать (GC assist).

**3. Mark termination (STW).**

- Выключить write barrier.
- Проверить, что все чёрные.
- Короткая пауза (~10-100 мкс).

**4. Sweeping (concurrent).**

- Освободить белые объекты.
- Работает в фоне.

### Проблема: мутатор меняет граф

**Мутатор** — программа, которая работает **во время** GC.

**Проблема:** мутатор может изменить граф **во время** маркировки.

**Пример:**

```
1. GC пометил [A] чёрным.
2. Мутатор добавил ссылку [A] → [B].
3. GC не увидит [B] → [B] останется белым → будет освобождён.
4. Но [B] живой!
```

**Решение:** **write barrier**.

### Аннотация сложности

| Фаза | Time |
|:---|:---|
| Mark setup (STW) | ~10-100 мкс |
| Marking (concurrent) | ~мс-сек |
| Mark termination (STW) | ~10-100 мкс |
| Sweeping (concurrent) | ~мс-сек |

### 💡 Практика: что важно знать про tri-color

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: маркировка concurrent.** Работает параллельно.
2. **Помни: две STW паузы** — короткие.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Понимай, что write barrier** замедляет запись.

**❌ НЕ ДЕЛАЙ:**

4. **Не игнорируй concurrent marking** — он тратит CPU.

### Ключевые выводы подглавы 18.2

- **Tri-color:** белые, серые, чёрные.
- **Алгоритм:** корни серые → обход → чёрные.
- **Белые в конце** — мёртвые.
- **Concurrent marking** — работает параллельно.
- **Write barrier** — для корректности.

## 18.3 Write barrier: почему запись замедляется

**Write barrier** — механизм для корректности concurrent GC.

### Проблема

**Мутатор** меняет граф **во время** маркировки.

**Пример:**

```
1. GC пометил [A] чёрным.
2. Мутатор добавил ссылку [A] → [B].
3. GC не увидит [B] → освободит.
4. Use-after-free.
```

### Решение: write barrier

**Write barrier** — код, который выполняется **при каждой записи** указателя.

**Что делает:**

- Записывает информацию о изменении.
- GC использует её для корректности.

### Dijkstra barrier

**Dijkstra barrier** (используется в Go):

**При записи `slot = ptr`:**

```
shade(ptr)  // пометить ptr серым
```

**Что делает:** когда мутатор записывает указатель в чёрный объект, **новый объект** помечается серым.

**Результат:** GC увидит новый объект.

### Yuasa barrier

**Yuasa barrier** (альтернатива):

**При записи `slot = ptr`:**

```
shade(*slot)  // пометить старый объект серым
```

**Что делает:** старый объект помечается серым.

### Hybrid barrier

**Go использует гибрид** — комбинацию Dijkstra и Yuasa.

**При записи `slot = ptr`:**

```
shade(*slot)  // старый
shade(ptr)    // новый
```

**Что делает:** оба объекта помечаются серыми.

### Стоимость

**Write barrier добавляет ~1-5 нс** к каждой записи указателя.

**Когда включён:** во время marking.

**Что это значит:**

- **Все записи указателей** замедляются на ~1-5 нс.
- **В hot path** это может быть заметно.

### Как избежать

**1. Меньше указателей.**

Массивы значений вместо массивов указателей.

```go
// ❌ Много указателей
type Data struct {
    Values []*int
}

// ✅ Меньше указателей
type Data struct {
    Values []int
}
```

**2. `sync.Pool` для больших объектов.**

Меньше аллокаций → меньше работы для GC.

**3. Меньше аллокаций.**

Меньше мусора → реже GC → реже write barrier.

### Аннотация сложности

| Операция | Без barrier | С barrier |
|:---|:---|:---|
| Запись указателя | ~1 нс | ~2-6 нс |
| Запись значения | ~1 нс | ~1 нс |

### 💡 Практика: как уменьшить write barrier

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Меньше указателей** — массивы значений.
2. **`sync.Pool`** для больших.
3. **Меньше аллокаций.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Профилируй** hot path.
5. **Бенчмаркай** с GC и без.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй указатели без необходимости.**
7. **Не игнорируй write barrier** в hot path.

### Ключевые выводы подглавы 18.3

- **Write barrier** — для корректности concurrent GC.
- **Dijkstra, Yuasa, hybrid.**
- **Go использует hybrid.**
- **Стоимость ~1-5 нс** на запись указателя.
- **Меньше указателей** — меньше barrier.

## 18.4 STW паузы: почему они короткие

**STW (Stop-The-World)** — пауза, когда **все** горутины остановлены.

### Две STW паузы

**1. Mark setup.**

- Включение write barrier.
- ~10-100 мкс.

**2. Mark termination.**

- Выключение write barrier.
- Проверка.
- ~10-100 мкс.

### Почему короткие

**Go GC оптимизирован** для коротких STW:

1. **Concurrent marking** — основная работа параллельно.
2. **Только две короткие паузы.**
3. **Планировщик помогает** — быстро останавливает горутины.

### Стоимость STW

**STW пауза:**

- **Все горутины** останавливаются.
- **Latency spikes** — p99.
- **CPU idle** — во время паузы.

**Для low-latency:**

- **p99** может быть **STW пауза**.
- Если STW = 100 мкс, p99 может быть 100 мкс.

### Как измерить

**`GODEBUG=gctrace=1`:**

```
gc 100 @10.234s 0%: 0.1+5+0.2 ms clock, ...
```

**Расшифровка:**

- **`0.1`** — STW mark setup.
- **`5`** — concurrent marking.
- **`0.2`** — STW mark termination.

**Всего STW = 0.1 + 0.2 = 0.3 мс.**

### Как уменьшить

**1. Меньше аллокаций.**

Меньше мусора → реже GC → меньше STW.

**2. `GOGC`.**

Больше `GOGC` → реже GC → меньше STW (но больше память).

**3. `GOMEMLIMIT`.**

Soft limit → GC агрессивнее при приближении.

**4. `GOGC=off` + `GOMEMLIMIT`.**

Минимум GC, но heap растёт до лимита.

### Аннотация сложности

| Фаза | Time |
|:---|:---|
| STW mark setup | ~10-100 мкс |
| Concurrent marking | ~мс-сек |
| STW mark termination | ~10-100 мкс |
| Concurrent sweeping | ~мс-сек |

### 💡 Практика: как уменьшить STW

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Меньше аллокаций.**
2. **Мониторь STW** — `gctrace`.
3. **`GOGC`/`GOMEMLIMIT`** — настройка.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`sync.Pool`** для больших.
5. **Бенчмаркай** p99.

**❌ НЕ ДЕЛАЙ:**

6. **Не игнорируй STW** для p99.
7. **Не отключай GC** без понимания.

### Ключевые выводы подглавы 18.4

- **STW** — пауза, когда все горутины остановлены.
- **Две паузы:** mark setup, mark termination.
- **Короткие:** ~10-100 мкс.
- **p99** может быть STW.
- **Меньше аллокаций** — меньше STW.

## 18.5 GC assist: как горутины помогают GC

**GC assist** — механизм, когда горутины **помогают** GC.

### Проблема

**GC работает concurrent.** Но если программа **аллоцирует быстрее**, чем GC успевает маркировать, heap растёт.

**Решение:** **GC assist**.

### Как работает

**При аллокации:**

1. Горутина проверяет, **должна ли** она помочь GC.
2. Если да — **выполняет часть маркировки**.
3. Потом продолжает работу.

**Что это значит:**

- **Аллокация** может быть **дороже**, если GC активен.
- **Горутина** тратит CPU на маркировку.

### Когда срабатывает

**GC assist срабатывает**, когда:

- Горутина аллоцирует **много**.
- GC **не успевает** маркировать.

**Пропорционально:**

- Чем больше аллокаций — тем больше assist.
- Цель: держать heap в балансе.

### Стоимость

**GC assist** может добавить **~10-100 нс** к аллокации.

**В hot path** это заметно.

### Как избежать

**1. Меньше аллокаций.**

Меньше мусора → меньше assist.

**2. `sync.Pool`.**

Переиспользование → меньше аллокаций.

**3. `GOGC` больше.**

Реже GC → меньше assist.

### Пример

```
Программа аллоцирует 1 ГБ/сек.
GC маркирует 500 МБ/сек.
Разница 500 МБ/сек → assist.

Каждая горутина помогает GC.
Аллокации замедляются.
```

### Аннотация сложности

| Операция | Time |
|:---|:---|
| Аллокация без assist | ~10-50 нс |
| Аллокация с assist | ~50-200 нс |

### 💡 Практика: как избежать GC assist

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Меньше аллокаций.**
2. **`sync.Pool`** для больших.
3. **Мониторь GC assist** — `gctrace`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`GOGC=200`** если память позволяет.
5. **Бенчмаркай** hot path.

**❌ НЕ ДЕЛАЙ:**

6. **Не игнорируй assist** в hot path.
7. **Не аллоцируй без необходимости.**

### Ключевые выводы подглавы 18.5

- **GC assist** — горутины помогают GC.
- **Срабатывает** при быстрых аллокациях.
- **Стоимость ~10-100 нс** на аллокацию.
- **Меньше аллокаций** — меньше assist.
- **`GOGC` больше** — меньше assist.

## 18.6 Pacing: как GC решает, когда запускаться

**Pacing** — алгоритм, который решает, **когда** запустить GC.

### Цель

**Pacing** держит **heap** в балансе:

- **Не слишком часто** — иначе CPU тратится.
- **Не слишком редко** — иначе heap растёт.

### Формула

**Целевой размер heap:**

```
target = live × (1 + GOGC/100)
```

**Где:**

- `live` — размер живых объектов.
- `GOGC` — процент (default 100).

**Пример:** live = 100 МБ, GOGC=100 → target = 200 МБ.

**GC запускается**, когда heap близок к target.

### Pacing algorithm

**Go pacing** учитывает:

1. **Скорость аллокаций.**
2. **Скорость маркировки.**
3. **Размер heap.**
4. **CPU доступно.**

**Что делает:**

- **Прогнозирует** время до следующего GC.
- **Решает**, когда запустить.
- **Регулирует** assist.

### Стоимость

**Pacing** — **бесплатный** для программы.

**Но:** неправильные настройки → частые GC или большой heap.

### Как влиять

**1. `GOGC`.**

- Больше → реже GC → больше heap.
- Меньше → чаще GC → меньше heap.

**2. `GOMEMLIMIT`.**

- Soft limit.
- GC агрессивнее при приближении.

**3. Меньше аллокаций.**

- Меньше мусора → реже GC.

### Аннотация сложности

| Настройка | GC частота | Heap |
|:---|:---|:---|
| GOGC=50 | Чаще | Меньше |
| GOGC=100 | Default | Default |
| GOGC=200 | Реже | Больше |
| GOMEMLIMIT=1GiB | При лимите | До лимита |

### 💡 Практика: как влиять на pacing

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`GOGC`** — для частоты.
2. **`GOMEMLIMIT`** — для лимита.
3. **Меньше аллокаций.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь heap** — `runtime/metrics`.
5. **Бенчмаркай** разные настройки.

**❌ НЕ ДЕЛАЙ:**

6. **Не ставь `GOGC=off` без `GOMEMLIMIT`.**
7. **Не игнорируй heap growth.**

### Ключевые выводы подглавы 18.6

- **Pacing** — когда запускать GC.
- **target = live × (1 + GOGC/100).**
- **Учитывает** аллокации, маркировку, heap, CPU.
- **`GOGC`, `GOMEMLIMIT`** — настройка.
- **Меньше аллокаций** — реже GC.

## 18.7 GOGC и GOMEMLIMIT

Разберём **настройку** GC.

### GOGC

**`GOGC`** — процент роста heap до следующего GC.

**Формула:**

```
target = live × (1 + GOGC/100)
```

**Значения:**

- **`GOGC=100`** — по умолчанию.
- **`GOGC=200`** — GC реже, память больше.
- **`GOGC=50`** — GC чаще, память меньше.
- **`GOGC=off`** — GC отключён.

**Настройка:**

```bash
GOGC=200 ./app
```

Или:

```go
debug.SetGCPercent(200)
```

### GOMEMLIMIT

**`GOMEMLIMIT`** (Go 1.19+) — soft limit на heap.

**Формула:**

```
GC агрессивнее, когда heap близок к GOMEMLIMIT.
```

**Пример:** `GOMEMLIMIT=1GiB`.

**Настройка:**

```bash
GOMEMLIMIT=1GiB ./app
```

Или:

```go
debug.SetMemoryLimit(1 * 1024 * 1024 * 1024)
```

### Комбинация

**Рекомендация:**

- **`GOMEMLIMIT`** — всегда в контейнерах.
- **`GOGC=200`** — если память позволяет.
- **`GOGC=off` + `GOMEMLIMIT`** — минимум GC, но heap растёт.

### В контейнерах

**Проблема:** Go **не знает** о лимитах контейнера.

**Решение:**

```bash
GOMEMLIMIT=<memory_limit> ./app
```

**Плюс:** `automaxprocs` для CPU.

```go
import _ "go.uber.org/automaxprocs"
```

### Пример

**Без настройки:**

```
GOGC=100, heap растёт до 2 ГБ.
GC каждые 100 мс.
```

**С `GOMEMLIMIT=1GiB`:**

```
GOGC=100, heap растёт до 1 ГБ.
GC агрессивнее при 900 МБ.
Heap не превышает 1 ГБ.
```

### Как выбрать

**1. Мало памяти.**

- `GOGC=50`.
- `GOMEMLIMIT=<limit>`.

**2. Много памяти.**

- `GOGC=200`.
- `GOMEMLIMIT=<limit>`.

**3. Real-time.**

- `GOGC=off` + `GOMEMLIMIT`.
- Минимум пауз.

**4. Default.**

- `GOGC=100` + `GOMEMLIMIT`.

### Аннотация сложности

| Настройка | GC частота | Память |
|:---|:---|:---|
| GOGC=50 | Чаще | Меньше |
| GOGC=100 | Default | Default |
| GOGC=200 | Реже | Больше |
| GOGC=off + limit | При лимите | До лимита |

### 💡 Практика: как настраивать GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`GOMEMLIMIT`** — всегда в контейнерах.
2. **`automaxprocs`** — для CPU.
3. **Мониторинг** — `runtime/metrics`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`GOGC=200`** — если память позволяет.
5. **Бенчмаркай** разные настройки.

**❌ НЕ ДЕЛАЙ:**

6. **Не отключай GC** без понимания.
7. **Не ставь `GOMEMLIMIT` больше реальной памяти.**

### Ключевые выводы подглавы 18.7

- **`GOGC`** — процент роста heap.
- **`GOMEMLIMIT`** — soft limit.
- **В контейнерах** — `GOMEMLIMIT` + `automaxprocs`.
- **`GOGC=200`** — GC реже.
- **`GOGC=off`** — только с `GOMEMLIMIT`.

## 18.8 GC и sync.Pool

Разберём **взаимодействие** GC и `sync.Pool`.

### Проблема: GC очищает Pool

**`sync.Pool`** — пул объектов (Глава 17).

**Ключевое:** GC **очищает** `Pool` при каждой сборке.

**Что происходит:**

- `Put` — объект в Pool.
- GC — объект удаляется.
- `Get` — создаёт новый.

**Почему:** GC не знает, **будут ли** объекты использованы.

### Victim cache

**Решение:** **victim cache** (Глава 17).

**Идея:** при GC объекты **не удаляются** сразу, а **перемещаются** в `victim`.

```
До GC:
  local: [объекты]
  victim: nil

После GC:
  local: nil
  victim: [старые объекты]

Через один GC:
  local: [новые объекты]
  victim: nil (старые удалены)
```

**Что это даёт:**

- Объекты **живут 2 GC** вместо одного.
- Больше шансов переиспользовать.
- Меньше аллокаций.

### Что это значит для практики

**1. Pool не гарантирует переиспользование.**

`Get` может вернуть **новый** объект.

**2. Pool полезен в hot path.**

Между GC много операций.

**3. Pool бесполезен для редких операций.**

GC успевает очистить.

### Пример

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}

func process() {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    // используем buf
}
```

**Что происходит:**

- **Hot path:** Pool работает, объекты переиспользуются.
- **Редкий вызов:** GC очищает Pool, `Get` создаёт новый.
- **Victim cache:** объекты живут 2 GC.

### Как увеличить переиспользование

**1. `GOGC` больше.**

Реже GC → дольше живут объекты.

**2. Меньше аллокаций.**

Меньше мусора → реже GC.

**3. Не использовать Pool для редких.**

Бесполезно.

### Аннотация сложности

| Сценарий | Pool работает? |
|:---|:---|
| Hot path | ✅ Да |
| Редкие вызовы | ❌ Нет |
| Между GC | ✅ Да |
| После GC | ⚠️ Victim |

### 💡 Практика: как использовать Pool с GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Pool для hot path.**
2. **Victim cache** — объекты живут 2 GC.
3. **`GOGC=200`** — если память позволяет.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмаркай** с GC и без.
5. **Мониторь аллокации.**

**❌ НЕ ДЕЛАЙ:**

6. **Не используй Pool для редких.**
7. **Не ожидай 100% переиспользования.**

### Ключевые выводы подглавы 18.8

- **GC очищает Pool.**
- **Victim cache** — 2 GC.
- **Pool полезен в hot path.**
- **Pool бесполезен для редких.**
- **`GOGC` больше** — дольше живут.

## 18.9 Диагностика GC

Разберём **диагностику** GC.

### gctrace

**`GODEBUG=gctrace=1`:**

```bash
GODEBUG=gctrace=1 ./app
```

**Вывод:**

```
gc 1 @0.001s 0%: 0.012+0.5+0.008 ms clock, 0.096+0.2/0.4/0.6+0.064 ms cpu, 4->4->2 MB, 5 MB goal, 8 P
gc 2 @0.005s 0%: 0.014+0.6+0.009 ms clock, 0.112+0.3/0.5/0.7+0.072 ms cpu, 5->6->3 MB, 6 MB goal, 8 P
```

**Расшифровка:**

- **`gc 1`** — номер GC.
- **`@0.001s`** — время от старта.
- **`0%`** — процент CPU на GC.
- **`0.012+0.5+0.008 ms clock`** — STW setup + concurrent + STW termination.
- **`4->4->2 MB`** — heap до → во время → после.
- **`5 MB goal`** — target.
- **`8 P`** — GOMAXPROCS.

### runtime/metrics

**`runtime/metrics`** (Go 1.16+) — API для метрик.

```go

samples := []metrics.Sample{
    {Name: "/gc/cycles/total:gc-cycles"},

for _, s := range samples {
    fmt.Printf("%s: %v\n", s.Name, s.Value)
}
```

**Что даёт:**

- **Точные метрики** без парсинга.
- **Все** метрики GC.

### pprof

**CPU profile:**

```bash
go test -cpuprofile=cpu.prof -bench=. ./...

```

**Что искать:** `runtime.gc*` в top.

**Memory profile:**

```bash

```

**Что искать:** top аллокаций.

### runtime.ReadMemStats


**Что даёт:**

## 18.10 Практика Go: измерение GC

Напишем **программу** для измерения GC.

### Код

```go

    "fmt"
    "runtime"
    "runtime/metrics"
    "sync"
    "time"
)

    // Программа с аллокациями
    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {

    go func() {

        }
    }()

    fmt.Println("done")
    printGCStats()
}

    var m runtime.MemStats
    runtime.ReadMemStats(&m)

        {Name: "/gc/cycles/total:gc-cycles"},
        {Name: "/gc/heap/allocs:bytes"},
        {Name: "/gc/pauses:seconds"},
    }
    metrics.Read(samples)

    for _, s := range samples {
        fmt.Printf("  %s: %v\n", s.Name, s.Value)
    }
}
```

## 18.11 Выводы и типичные ошибки

**Что мы узнали?**

GC — автоматическое освобождение памяти. Tri-color marking: белые, серые, чёрные. Write barrier — для корректности concurrent GC. STW паузы — короткие (~10-100 мкс). GC assist — горутины помогают GC. Pacing — когда запускать GC. `GOGC` и `GOMEMLIMIT` — настройка. GC очищает `sync.Pool`, victim cache — 2 GC. Диагностика: `gctrace`, `runtime/metrics`, pprof.

**Типичные ошибки:**

- ❌ **Игнорировать GC паузы.** p99 может быть STW.
- ❌ **Много аллокаций в hot path.** GC assist.
- ❌ **Не использовать `sync.Pool`.** Больше GC.
- ❌ **Отключать GC без `GOMEMLIMIT`.** OOM.
- ❌ **Не настраивать `GOMEMLIMIT` в контейнерах.** OOM.
- ❌ **Игнорировать `TotalAlloc`.** Растёт быстрее, чем кажется.
- ❌ **Не мониторить GC.** Не видно проблем.
- ❌ **Использовать `interface{}` в hot path.** Аллокации.
- ❌ **`fmt.Sprintf` в hot path.** Аллокации.
- ❌ **Не использовать `-benchmem`.** Не видно аллокаций.
- ❌ **Парсить `gctrace` в production.** Дорого.
- ❌ **Ожидать 100% переиспользования Pool.**

## 18.16 Чек-лист

| Компонент | Что это | Ключевые факты |
|:---|:---|:---|
| **GC** | Автоматическое освобождение | Concurrent, tri-color |
| **Tri-color** | Алгоритм маркировки | Белые, серые, чёрные |
| **Write barrier** | При записи указателя | ~1-5 нс |
| **STW паузы** | Stop-The-World | ~10-100 мкс |
| **GC assist** | Горутины помогают | ~10-100 нс |
| **Pacing** | Когда запускать | target = live × (1 + GOGC/100) |
| **`GOGC`** | Процент роста heap | Default 100 |
| **`GOMEMLIMIT`** | Soft limit | В контейнерах |
| **Victim cache** | 2 GC | Больше переиспользования |
| **`gctrace`** | Быстрая диагностика | `GODEBUG=gctrace=1` |
| **`runtime/metrics`** | Точные метрики | Go 1.16+ |
| **`ReadMemStats`** | Основные метрики | Alloc, NumGC, PauseTotal |
| **Pool** | Меньше GC | 20x меньше |

🗑️ **Ключевая идея:** GC — автоматическое освобождение памяти. **Tri-color marking:** белые, серые, чёрные. **Write barrier** — для корректности concurrent GC. **STW паузы** — ~10-100 мкс. **GC assist** — горутины помогают при быстрых аллокациях. **Pacing** — target = live × (1 + GOGC/100). **`GOGC`** — процент роста heap. **`GOMEMLIMIT`** — soft limit. **GC очищает `sync.Pool`**, victim cache — 2 GC. **`gctrace`, `runtime/metrics`, pprof** — диагностика. **Pool уменьшает GC** в 20 раз. **Меньше аллокаций** — меньше GC. В контейнерах — `GOMEMLIMIT` + `automaxprocs`.
