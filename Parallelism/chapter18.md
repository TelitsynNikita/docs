## 18.0 Пролог: GC, который съедает 30% CPU

Ты пишешь сервис на Go. Всё работает. Пока не начинаешь смотреть на CPU-профиль:

```
flat  flat%   sum%        cum   cum%
 2.5s 30.00% 30.00%      2.5s 30.00%  runtime.gcBgMarkWorker
 1.0s 12.00% 42.00%      1.0s 12.00%  runtime.scanobject
 0.5s  6.00% 48.00%      0.5s  6.00%  runtime.greyobject
 ...
```

❓ **30% CPU в GC?** Это же Go, у него «быстрый» GC!

💡 **Что происходит:**

- GC **mark-фаза** тратит много CPU.
- Каждый объект требует **случайного доступа к памяти**.
- **Cache miss** — главный враг.
- Чем больше heap, тем хуже.

**В Go 1.26 появился Green Tea GC** — новый алгоритм, который:

- Работает со **страницами**, а не объектами.
- Улучшает **cache locality**.
- Использует **векторные инструкции**.
- Снижает GC overhead на **10-40%**.

**Эта глава — о том, как работает GC, что такое Green Tea, и как уменьшить давление на GC.**

> **Важный мост:** GC — это **фоновая горутина**, которая конкурирует с твоим кодом за CPU. Понимание GC критично для конкурентного кода. `sync.Pool` (Глава 17) — инструмент для уменьшения давления на GC. Профилирование (Глава 12) — для диагностики.

## 18.1 Что такое tracing GC

Прежде чем разбирать Green Tea, поймём **основы**.

### Tracing GC vs reference counting

**Tracing GC** (Go, Java, C#):

- Периодически **сканирует** граф объектов.
- Находит **недостижимые** объекты.
- Освобождает их.

**Reference counting** (Python, Swift):

- Каждый объект знает, **сколько ссылок** на него.
- Когда счётчик = 0 — освобождается.

**Почему Go выбрал tracing GC:**

- **Циклы** — reference counting не справляется с циклами.
- **Производительность** — инкремент счётчика на каждую ссылку.
- **Concurrent** — tracing можно делать параллельно.

### Mark-sweep алгоритм

**Mark-sweep** — конкретная реализация tracing GC:

**Фаза 1: Mark.**

- Начинаем с **roots** (глобальные переменные, стек).
- Идём по **указателям**.
- **Помечаем** каждый достигнутый объект.
- Работает как **graph flood** (DFS/BFS).

**Фаза 2: Sweep.**

- Проходим по **всем** объектам.
- **Немаркированные** — недостижимы.
- Освобождаем их память.

### Пример heap

```
Roots:
  x → Object A
  y → Object B

Heap:
  Object A → Object C
  Object B → Object C
  Object C → Object D
  Object E (недостижим)
  Object F (недостижим)

Mark:
  x → A → C → D
  y → B → C (уже помечен)
  
  Помечены: A, B, C, D
  Не помечены: E, F

Sweep:
  E, F освобождаются
```

### Аннотация сложности

| Алгоритм | Time | Space |
|:---|:---|:---|
| Mark | O(live objects) | O(heap) |
| Sweep | O(heap) | 0 |
| Полный GC цикл | O(heap) | 0 |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: GC работает параллельно** с твоим кодом.
2. **Помни: mark — самая дорогая фаза** (~90% времени GC).

**👍 СТОИТ СДЕЛАТЬ:**

3. **Профилируй GC** — `GODEBUG=gctrace=1`.
4. **Уменьшай аллокации** — меньше heap, меньше GC.

**❌ НЕ ДЕЛАЙ:**

5. **Не думай, что GC бесплатный.** 10-30% CPU — норма.

### Ключевые выводы подглавы 18.1

- **Tracing GC** — сканирует граф объектов.
- **Mark-sweep** — mark (обход) + sweep (освобождение).
- **Mark — 90% времени GC.**
- **GC параллелен** с кодом.

## 18.2 Mark-фаза: roots, work list, tri-color

Разберём **mark-фазу** подробнее.

### Roots

**Roots** — точки входа для обхода:

- **Глобальные переменные.**
- **Локальные переменные** (на стеке).
- **Регистры** (на некоторых архитектурах).

**В Go:** roots — это **globals** и **stacks всех горутин**.

### Work list

**Work list** — список объектов для сканирования.

**Классический алгоритм:**

1. Добавить roots в work list.
2. Пока work list не пуст:
   - Взять объект.
   - **Пометить** его.
   - Для каждого указателя — добавить цель в work list.

**Проблема:** объекты **разного размера**. Иногда 2 указателя, иногда 1000. **Случайный доступ к памяти**.

### Tri-color маркировка

**Tri-color** — абстракция для описания состояний:

- **White** — не посещён (кандидат на удаление).
- **Grey** — посещён, но не все дети обработаны.
- **Black** — посещён, все дети обработаны.

**Инвариант:** чёрный объект **не может** указывать на белый.

**Зачем:** чтобы concurrent GC не терял объекты.

### Work list: stack vs queue

**Классический graph flood:**

- **LIFO** (stack) — depth-first.
- Обход **глубокий**, но **случайный**.

**Green Tea:**

- **FIFO** (queue) — breadth-first по страницам.
- Обход **широкий** и **последовательный**.

### Визуализация

```
Классический mark:

  Work list (stack): [A, B]
  Берём B (LIFO):
    B → C, D
    Work list: [A, C, D]
  Берём D:
    D → E
    Work list: [A, C, E]
  ...
  
  Прыгаем по heap.

Green Tea mark:

  Work list (queue страниц): [Page1, Page2]
  Берём Page1:
    Сканируем ВСЕ объекты на Page1.
    Находим ссылки на Page3.
    Work list: [Page2, Page3]
  Берём Page2:
    Сканируем ВСЕ объекты на Page2.
  ...
  
  Последовательно по страницам.
```

### Аннотация сложности

| Подход | Доступ к памяти |
|:---|:---|
| LIFO (stack) | Случайный |
| FIFO (queue) | Последовательный |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: roots — globals и stacks.**
2. **Помни: tri-color — инвариант для concurrent GC.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Понимай разницу LIFO vs FIFO** — это основа Green Tea.

**❌ НЕ ДЕЛАЙ:**

4. **Не думай, что mark — простой обход.** Это **random memory access**.

### Ключевые выводы подглавы 18.2

- **Roots** — globals и stacks.
- **Work list** — список для сканирования.
- **Tri-color:** white, grey, black.
- **LIFO (классика) vs FIFO (Green Tea).**

## 18.3 Write barrier: почему он нужен

**Write barrier** — механизм для **concurrent GC**.

### Проблема: concurrent mark

**Классический GC** — stop-the-world: всё останавливается, mark, sweep, продолжение.

**Concurrent GC** — mark идёт **параллельно** с кодом.

**Проблема:** код **меняет указатели** во время mark.

```
1. GC пометил A (black).
2. Код: A.next = B (B — white).
3. GC не видит B (не сканирует A снова).
4. B остаётся white → освобождается.
5. A.next указывает на освобождённую память.
```

**Это баг.** Write barrier предотвращает его.

### Как работает write barrier

**Идея:** при **записи указателя** в объект — уведомить GC.

**В Go:**

```go
// Компилятор вставляет write barrier при записи указателя
obj.field = newValue

// Превращается в:
wb(obj, &obj.field, newValue)
obj.field = newValue
```

**Что делает `wb`:**

- Если **mark идёт** и `obj` — black, а `newValue` — white:
- **Пометить** `newValue` (или добавить в work list).

**Результат:** инвариант tri-color сохраняется.

### Стоимость write barrier

**Write barrier** — **не бесплатный**:

- Каждая запись указателя → вызов `wb`.
- ~5-20% overhead на запись указателей.

**Оптимизация:** write barrier **только во время mark**. В остальное время — обычная запись.

### Hybrid write barrier

**Go использует hybrid write barrier** (с Go 1.8):

- **Dijkstra barrier:** при записи — пометить новый объект.
- **Yuasa barrier:** при записи — пометить старый объект.

**Комбинация** даёт лучшую производительность.

### Аннотация сложности

| Операция | Time |
|:---|:---|
| Обычная запись | ~1 нс |
| Write barrier | ~5-10 нс |
| Overhead | ~5-20% |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: write barrier — стоимость concurrent GC.**
2. **Помни: barrier только во время mark.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Понимай, почему запись указателей дороже**, чем запись чисел.

**❌ НЕ ДЕЛАЙ:**

4. **Не думай, что concurrent GC бесплатный.**

### Ключевые выводы подглавы 18.3

- **Write barrier** — для concurrent mark.
- **Помечает** новые/старые объекты при записи.
- **~5-20% overhead** на запись указателей.
- **Только во время mark.**

## 18.4 Stop-the-world и concurrent GC

**Stop-the-world (STW)** — фазы, когда **весь код останавливается**.

### STW фазы в Go

**Классический GC** (до Green Tea):

1. **STW: Mark Setup** — подготовка mark.
2. **Concurrent Mark** — mark идёт параллельно.
3. **STW: Mark Termination** — завершение mark.
4. **Concurrent Sweep** — sweep параллельно.

**STW фазы короткие** (~микросекунды), но **есть**.

### Почему STW нужен

**Mark Setup:**

- Нужно **остановить** все горутины.
- Включить **write barrier**.
- Зафиксировать **roots**.

**Mark Termination:**

- Убедиться, что **все** объекты помечены.
- Выключить write barrier.

### Стоимость STW

**STW** — **пауза** для всего приложения.

**В Go:**

- Обычно **< 1 мс**.
- Может быть **> 10 мс** при большом heap.

**Влияние на latency:** STW — **tail latency** spike.

### Concurrent фазы

**Concurrent Mark:**

- Идёт **параллельно** с кодом.
- Использует **25% CPU** (по умолчанию).
- **Write barrier** активен.

**Concurrent Sweep:**

- Освобождает память **параллельно**.
- **Не блокирует** код.

### Визуализация

```
Время →
─────────────────────────────────────────────────────────

STW: Mark Setup (µs)
  │
  ▼
Concurrent Mark (ms)
  ████████████████████████████
  ████████████████████████████
  ████████████████████████████
                              │
                              ▼
STW: Mark Termination (µs)
                              │
                              ▼
Concurrent Sweep (ms)
                              ████████████████████████
```

### Аннотация сложности

| Фаза | Time | STW? |
|:---|:---|:---|
| Mark Setup | µs | ✅ Да |
| Concurrent Mark | ms | ❌ Нет |
| Mark Termination | µs | ✅ Да |
| Concurrent Sweep | ms | ❌ Нет |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: STW короткие, но есть.**
2. **Помни: STW — tail latency spike.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Профилируй STW** — `GODEBUG=gctrace=1`.

**❌ НЕ ДЕЛАЙ:**

4. **Не думай, что GC полностью concurrent.**

### Ключевые выводы подглавы 18.4

- **STW** — Mark Setup и Mark Termination.
- **Concurrent** — Mark и Sweep.
- **STW < 1 мс** обычно.
- **STW влияет на tail latency.**

## 18.5 Green Tea GC: страницы вместо объектов

**Green Tea** — новый алгоритм mark-фазы, **по умолчанию в Go 1.26**.

### Ключевая идея

> **Work with pages, not objects.**

**Что это значит:**

- **Вместо** отдельных объектов в work list → **страницы (spans)**.
- **Вместо** сканирования объектов по одному → **сканирование всей страницы**.
- **Метаданные** (mark bits + scanned bits) → **локально для страницы**.

### Как работает

**1. Span-based work list.**

- GC находит указатель на объект.
- **Помечает** объект в mark bits.
- **Добавляет span** (8 KiB страницу) в work list.
- **Не** отдельный объект — **вся страница**.

**2. Scanned bits.**

- Каждая страница имеет **scanned bits**.
- Показывают, какие объекты **уже сканированы**.
- **Разница** между mark bits и scanned bits → объекты для сканирования.

**3. Последовательное сканирование.**

- Когда span достаётся из work list:
- **Сканирует все объекты** с mark bit, но без scanned bit.
- **Последовательно** по странице.

**4. Queue вместо stack.**

- **FIFO** (queue) вместо LIFO (stack).
- Позволяет **накопить** объекты на странице.

### Визуализация

```
Классический GC:

  Work list: [Obj1, Obj2, Obj3, ...]
  Берём Obj1 (LIFO):
    Сканируем Obj1.
    Добавляем его детей.
  Прыгаем по heap.

Green Tea:

  Work list: [Span1, Span2, ...]
  Берём Span1:
    Сканируем ВСЕ объекты на Span1.
    Находим ссылки на Span3.
    Добавляем Span3.
  Берём Span2:
    Сканируем ВСЕ объекты на Span2.
  Последовательно по страницам!
```

### Преимущества

**1. Cache locality.**

- Объекты на одной странице — **рядом** в памяти.
- Меньше **cache miss**.
- Лучше **prefetch**.

**2. Меньше work list.**

- Страниц **меньше**, чем объектов.
- Меньше **contention**.
- Меньше **CPU stall**.

**3. Векторные инструкции.**

- **AVX-512** для сканирования страницы.
- **10% дополнительного ускорения**.

### Недостатки

**1. Не для всех workloads.**

- Если на странице **мало объектов** → хуже.
- Программы с **крупными объектами** → может быть регрессия.

**2. Накопление.**

- Нужно **накопить** объекты на странице.
- Если этого не происходит → overhead.

### Метрики

**Официально:** **10-40% снижение GC overhead**.

**В бенчмарках:**

- **Tree workload:** ~10% снижение GC CPU.
- **Map workload:** **60% снижение** (по данным блога).

### Аннотация сложности

| Аспект | Classic GC | Green Tea |
|:---|:---|:---|
| Work unit | Object | Span (8 KiB) |
| Work list | Stack (LIFO) | Queue (FIFO) |
| Cache locality | Плохая | Хорошая |
| Work list size | Большой | Меньше |
| Векторные | ❌ | ✅ AVX-512 |

### 💡 Практика: как использовать Green Tea

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Обновись до Go 1.26** — Green Tea по умолчанию.
2. **Проверь свой workload** — не всем помогает.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Профилируй GC CPU** — `GODEBUG=gctrace=1`.
4. **Сравни до/после** — `GOEXPERIMENT=nogreenteagc`.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Отключай Green Tea** — только если есть регрессия.

**❌ НЕ ДЕЛАЙ:**

6. **Не думай, что Green Tea — панацея.** Он **не заменяет** оптимизацию аллокаций.

### Ключевые выводы подглавы 18.5

- **Green Tea** — работа со **страницами**, а не объектами.
- **Scanned bits** — для отслеживания сканированных объектов.
- **FIFO** (queue) вместо LIFO (stack).
- **10-40% снижение GC overhead.**
- **Не для всех workloads.**

## 18.6 Векторные инструкции: AVX-512

**Green Tea** использует **векторные инструкции** для ускорения.

### Что такое AVX-512

**AVX-512** — расширение x86 для **512-битных** векторных операций.

**Что даёт:**

- **512-битные регистры** — 64 байта.
- **Битовые операции** над всем регистром.
- **Векторные сравнения**.

### Как используется в Green Tea

**Идея:** метаданные страницы **помещаются** в векторные регистры.

**Шаги (AVX-512 kernel):**

**1. Загрузить seen и scanned bits.**

- Seen bits: 1 бит на объект.
- Scanned bits: 1 бит на объект.
- **Вся страница** — в **двух** регистрах.

**2. Вычислить active objects.**

```c
active_objects = seen & ~scanned
```

- Seen, но не scanned — нужно сканировать.

**3. Расширить до active words.**

```c
active_words = expand(active_objects)
```

- 1 бит на объект → 1 бит на слово (8 байт).
- Если объект 48 байт (6 слов) — 1 бит расширяется в 6 бит.

**4. Сканировать активные слова.**

- Использовать active_words для сканирования.

**5. Всё за несколько инструкций.**

- **Страница** обрабатывается **целиком**.
- **Векторные инструкции** — **десятки циклов** вместо тысяч.

### Почему это возможно только в Green Tea

**Классический GC:**

- Объекты **разного размера**.
- Иногда 2 бита метаданных, иногда 10 000.
- **Нет предсказуемости** для векторизации.

**Green Tea:**

- Объекты на странице **одного размера**.
- Метаданные **фиксированного размера**.
- **Идеально** для векторизации.

### Требования

**CPU:**

- **Intel Ice Lake** (2019+) или новее.
- **AMD Zen 4** (2022+) или новее.

**Без AVX-512:**

- Green Tea **работает**, но **без ускорения**.
- Использует **скалярный** код.

### Метрики

**Официально:** **~10% дополнительного ускорения** на современных CPU.

### Аннотация сложности

| Операция | Без AVX-512 | С AVX-512 |
|:---|:---|:---|
| Сканирование страницы | ~1000 циклов | ~100 циклов |
| Ускорение | Baseline | ~10x для scan |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: AVX-512 требует современный CPU.**
2. **Помни: Green Tea работает и без AVX-512.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Проверь CPU** — Ice Lake / Zen 4+.

**❌ НЕ ДЕЛАЙ:**

4. **Не думай, что AVX-512 обязателен.**

### Ключевые выводы подглавы 18.6

- **AVX-512** — 512-битные регистры.
- **Green Tea** использует для сканирования страниц.
- **~10% дополнительного ускорения.**
- **Требует Ice Lake / Zen 4+.**

## 18.7 GC assist: горутины помогают GC

**GC assist** — механизм, при котором горутины **помогают** GC.

### Проблема: аллокация быстрее mark

**Что если:**

- Программа **аллоцирует** быстрее, чем GC **маркирует**?
- Heap **растёт** быстрее, чем GC успевает.
- **OOM**.

### Решение: GC assist

**Идея:** если горутина **аллоцирует** во время mark — она **помогает** GC.

**Как работает:**

1. Горутина аллоцирует.
2. Если **mark не успевает** — горутина **помогает**.
3. Горутина **сканирует** часть объектов.
4. Только потом продолжает работу.

**Результат:** mark **успевает** за аллокациями.

### Стоимость

**GC assist** — **замедляет** горутину.

- ~10-50% замедление во время mark.
- **Непредсказуемо** — зависит от темпа аллокаций.

**Влияние на latency:** **spike** при высокой аллокации.

### Как избежать GC assist

**1. Меньше аллокаций.**

- `sync.Pool` (Глава 17).
- Stack allocation.
- Переиспользование буферов.

**2. Увеличить GOGC.**

- Реже GC, но больше heap.
- Trade-off.

**3. GOMEMLIMIT.**

- Ограничить heap.
- GC будет чаще.

### Аннотация сложности

| Операция | Time |
|:---|:---|
| Аллокация без assist | ~10-50 нс |
| Аллокация с assist | ~50-200 нс |

### 💡 Практика: как избежать GC assist

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Уменьшай аллокации** — меньше assist.
2. **`sync.Pool`** — для частых аллокаций.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Профилируй GC assist** — `runtime/trace`.

**❌ НЕ ДЕЛАЙ:**

4. **Не игнорируй assist.** Он влияет на latency.

### Ключевые выводы подглавы 18.7

- **GC assist** — горутины помогают GC.
- **Стоимость:** ~10-50% замедление.
- **Избежать:** меньше аллокаций, `sync.Pool`.

## 18.8 GOGC и GOMEMLIMIT

Разберём **настройки GC**.

### GOGC

**`GOGC`** — целевой процент heap после GC.

**Формула:**

```
next_gc = live_heap × (1 + GOGC/100)
```

**По умолчанию:** `GOGC=100`.

- После GC: `next_gc = live_heap × 2`.
- То есть heap **удваивается** перед следующим GC.

**Меньше GOGC:**

- **Чаще** GC.
- **Меньше** heap.
- **Больше** CPU на GC.

**Больше GOGC:**

- **Реже** GC.
- **Больше** heap.
- **Меньше** CPU на GC, но **риск OOM**.

### GOMEMLIMIT

**`GOMEMLIMIT`** — **мягкий** лимит памяти (Go 1.19+).

**Как работает:**

- Если heap **приближается** к лимиту — GC **ускоряется**.
- **Не жёсткий** — может превысить.

**Зачем:**

- **Защита от OOM** в контейнерах.
- **Предсказуемость** памяти.

### Пример

```bash
# GOGC=50: GC чаще, heap меньше
GOGC=50 ./app

# GOGC=200: GC реже, heap больше
GOGC=200 ./app

# GOMEMLIMIT=1GiB: мягкий лимит
GOMEMLIMIT=1GiB ./app

# Комбинация
GOGC=100 GOMEMLIMIT=1GiB ./app
```

### Как выбрать

**Для latency-критичных:**

- **Больше GOGC** (200-400) — реже GC.
- **GOMEMLIMIT** — защита от OOM.

**Для памяти-критичных:**

- **Меньше GOGC** (50-100).
- **GOMEMLIMIT** обязательно.

**Для CPU-критичных:**

- **Больше GOGC** — меньше CPU на GC.

### Аннотация сложности

| Настройка | Влияние |
|:---|:---|
| `GOGC=50` | GC чаще, heap меньше |
| `GOGC=200` | GC реже, heap больше |
| `GOMEMLIMIT` | Мягкий лимит |

### 💡 Практика: как настроить GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **GOMEMLIMIT** в контейнерах.
2. **GOGC=200-400** для latency.
3. **GOGC=50-100** для памяти.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Профилируй** перед настройкой.
5. **Мониторь heap**.

**❌ НЕ ДЕЛАЙ:**

6. **Не ставь GOMEMLIMIT без тестов.**
7. **Не игнорируй GOGC.**

### Ключевые выводы подглавы 18.8

- **`GOGC`** — целевой heap после GC.
- **`GOMEMLIMIT`** — мягкий лимит.
- **Больше GOGC** — реже GC, больше heap.
- **GOMEMLIMIT** — для защиты от OOM.

## 18.10 Как уменьшить давление на GC

Разберём **способы уменьшить GC**.

### 1. Меньше аллокаций

**❌ Плохо:**

```go
for i := 0; i < 1000; i++ {
    result = append(result, fmt.Sprintf("item-%d", i))
}
```

**✅ Хорошо:**

```go
result = make([]string, 0, 1000)  // preallocate
for i := 0; i < 1000; i++ {
    result = append(result, strconv.Itoa(i))  // без fmt.Sprintf
}
```

### 2. Stack allocation

**Go compiler** может аллоцировать **на стеке**, если объект **не убегает**.

**Пример:**

```go
// ❌ Heap
func newUser() *User {
    return &User{Name: "Alice"}  // escapes
}

// ✅ Stack (если не возвращается)
func process() {
    u := User{Name: "Alice"}  // на стеке
    _ = u
}
```

**Как проверить:**

```bash
go build -gcflags="-m" ./...
```

**Вывод:**

```
./main.go:10:6: u escapes to heap
```

### 3. sync.Pool

**`sync.Pool`** — пул объектов (Глава 17).

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

buf := bufPool.Get().([]byte)
defer bufPool.Put(buf)
```

**Что даёт:** переиспользование **без GC**.

### 4. Уменьшить размер объектов

**Меньше объект → меньше heap → реже GC.**

**Пример:**

```go
// ❌ Большая структура
type User struct {
    Data [1024]byte
    Name string
}

// ✅ Указатель на данные
type User struct {
    Data *[1024]byte
    Name string
}
```

### 5. Уменьшить указатели

**Меньше указателей → быстрее mark.**

**Пример:**

```go
// ❌ Указатели
type Node struct {
    Next *Node
    Data []int  // slice — указатель
}

// ✅ Без указателей
type Node struct {
    Next int  // индекс
    Data [10]int
}
```

### 6. Избегать интерфейсов в hot path

**Интерфейс → аллокация.**

**Пример:**

```go
// ❌ Интерфейс
func process(v interface{}) {
    _ = v
}

// ✅ Конкретный тип
func process(v int) {
    _ = v
}
```

### Аннотация сложности

| Техника | Эффект |
|:---|:---|
| Preallocate | -50% аллокаций |
| Stack | -100% (для этих объектов) |
| `sync.Pool` | -90% для частых |
| Меньше указателей | Быстрее mark |

### 💡 Практика: как уменьшить GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Preallocate слайсы.**
2. **`sync.Pool`** для частых аллокаций.
3. **Проверяй escape analysis** — `-gcflags="-m"`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Меньше указателей.**
5. **Конкретные типы** вместо интерфейсов.

**❌ НЕ ДЕЛАЙ:**

6. **Не оптимизируй преждевременно.**
7. **Не используй `fmt.Sprintf` в hot path.**

### Ключевые выводы подглавы 18.10

- **Меньше аллокаций** — меньше GC.
- **Stack allocation** — если не убегает.
- **`sync.Pool`** — для частых.
- **Меньше указателей** — быстрее mark.

## 18.11 GC и конкурентный код

Разберём **влияние GC на конкурентный код**.

### GC assist замедляет горутины

**Если горутина аллоцирует во время mark:**

- Она **помогает** GC.
- **Замедляется**.
- **Непредсказуемо**.

**Влияние:** latency spike.

### STW паузы

**STW** останавливает **все** горутины.

**Влияние:**

- Tail latency.
- Метрики: p99, p999.

### GC и worker pool

**Worker pool** с большим числом воркеров:

- **Больше аллокаций** → чаще GC.
- **Больше assist**.

**Решение:** `sync.Pool` для буферов.

### GC и каналы

**Каналы** аллоцируют:

- **`hchan`** — при создании.
- **`sudog`** — при блокировке.

**Влияние:** много каналов → много аллокаций.

### GC и context

**`context.WithValue`** аллоцирует:

- **`valueCtx`** — на каждый вызов.

**Влияние:** много `WithValue` → аллокации.

### GC и sync.Pool

**`sync.Pool`** — **специально** для уменьшения GC.

**Как работает:**

- Объекты в пуле **не собираются** GC.
- **Переиспользуются**.

**Детали — Глава 17.**

### Аннотация сложности

| Компонент | Аллокации |
|:---|:---|
| Канал | ~96 байт + буфер |
| `context.WithValue` | ~50 байт |
| `sudog` | ~64 байта |

### 💡 Практика: GC в конкурентном коде

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`sync.Pool`** для буферов.
2. **Preallocate** каналы с буфером.
3. **Меньше `context.WithValue`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь GC assist** — `runtime/trace`.

**❌ НЕ ДЕЛАЙ:**

5. **Не аллоцируй в hot path.**
6. **Не создавай каналы в цикле.**

### Ключевые выводы подглавы 18.11

- **GC assist** замедляет горутины.
- **STW** — tail latency.
- **`sync.Pool`** — для буферов.
- **Меньше аллокаций** — меньше GC.

## 18.12 Практика Go: измеряем GC

Напишем **программу для измерения GC**.

### Программа

```go
package main

import (
    "fmt"
    "runtime"
    "sync"
    "time"
)

func main() {
    // Замер до
    var before runtime.MemStats
    runtime.ReadMemStats(&before)
    fmt.Printf("Before: NumGC=%d, HeapAlloc=%d MB\n",
        before.NumGC, before.HeapAlloc/1024/1024)

    // Работа
    start := time.Now()
    work()
    elapsed := time.Since(start)

    // Замер после
    var after runtime.MemStats
    runtime.ReadMemStats(&after)

    fmt.Printf("After: NumGC=%d, HeapAlloc=%d MB\n",
        after.NumGC, after.HeapAlloc/1024/1024)
    fmt.Printf("GC cycles: %d\n", after.NumGC-before.NumGC)
    fmt.Printf("Total GC pause: %v\n",
        time.Duration(after.PauseTotalNs-before.PauseTotalNs))
    fmt.Printf("Elapsed: %v\n", elapsed)
}

func work() {
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                _ = make([]byte, 1024)  // аллокация
            }
        }()
    }
    wg.Wait()
}
```

### Запуск с gctrace

```bash
GODEBUG=gctrace=1 go run main.go
```

**Вывод:**

```
gc 1 @0.001s 0%: 0.010+0.50+0.005 ms clock, 0.080+0.40/0.60/0.20+0.040 ms cpu, 4->4->2 MB, 5 MB goal, 8 P
gc 2 @0.005s 0%: 0.008+0.40+0.004 ms clock, 0.064+0.32/0.48/0.16+0.032 ms cpu, 4->4->3 MB, 6 MB goal, 8 P
...
```

### Сравнение с sync.Pool

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 1024)
    },
}

func workWithPool() {
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                buf := bufPool.Get().([]byte)
                _ = buf
                bufPool.Put(buf)
            }
        }()
    }
    wg.Wait()
}
```

**Что изменится:**

- **Меньше GC cycles.**
- **Меньше GC pause.**

### Аннотация сложности

| Версия | GC cycles | Pause |
|:---|:---|:---|
| Без Pool | ~100 | ~10 мс |
| С Pool | ~10 | ~1 мс |

### 💡 Практика: как измерять GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`runtime.ReadMemStats`** — метрики.
2. **`GODEBUG=gctrace=1`** — детально.
3. **Сравнивай до/после.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **`runtime/trace`** — для сложных случаев.
5. **Мониторинг в production.**

**❌ НЕ ДЕЛАЙ:**

6. **Не оптимизируй без замеров.**

### Ключевые выводы подглавы 18.12

- **`runtime.ReadMemStats`** — метрики.
- **`GODEBUG=gctrace=1`** — детально.

## 18.13 Выводы и типичные ошибки

**Что мы узнали?**

GC — это **tracing mark-sweep**. Mark-фаза — 90% времени. Roots — globals и stacks. Tri-color: white, grey, black. Write barrier — для concurrent mark. STW — Mark Setup и Mark Termination. **Green Tea** — новый алгоритм (Go 1.26): **страницы вместо объектов**, FIFO вместо LIFO, AVX-512. **10-40% снижение GC overhead.** **GC assist** — горутины помогают GC. **`GOGC`** и **`GOMEMLIMIT`** — настройки. **Профилирование:** `gctrace`, `runtime/trace`, pprof. **Уменьшить GC:** меньше аллокаций, stack, `sync.Pool`, меньше указателей.

**Типичные ошибки:**

- ❌ **Не профилировать GC.** 30% CPU может уходить в GC.
- ❌ **Не обновиться до Go 1.26.** Green Tea даёт 10-40%.
- ❌ **Игнорировать GC assist.** Latency spikes.
- ❌ **Игнорировать STW.** Tail latency.
- ❌ **Не использовать `sync.Pool`.** Много аллокаций.
- ❌ **Не preallocate слайсы.** Лишние аллокации.
- ❌ **Не проверять escape analysis.** Heap вместо stack.
- ❌ **Много указателей.** Медленный mark.
- ❌ **Интерфейсы в hot path.** Аллокации.
- ❌ **`context.WithValue` в цикле.** Аллокации.
- ❌ **Каналы в цикле.** Аллокации.
- ❌ **Не настраивать GOGC/GOMEMLIMIT.**
- ❌ **Не мониторить GC в production.**
- ❌ **Не сравнивать до/после оптимизации.**

- **Меньше указателей** — быстрее mark.

🗑️ **Ключевая идея:** GC — tracing mark-sweep. Mark — 90% времени. Roots — globals и stacks. Tri-color: white, grey, black. Write barrier — для concurrent mark. Профилирование: `gctrace`, `runtime/trace`, pprof, `MemStats`. Уменьшить GC: меньше аллокаций, `sync.Pool`, stack allocation, меньше указателей.
