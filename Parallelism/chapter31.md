## 31.0 Пролог: миллион аллокаций в секунду

У нас есть сервис, который обрабатывает HTTP-запросы. В каждом хэндлере **создаём буфер** для чтения тела:

```go
func handler(w http.ResponseWriter, r *http.Request) {
    buf := make([]byte, 4096)  // ← аллокация на каждый запрос
    n, _ := r.Body.Read(buf)
    process(buf[:n])
    w.WriteHeader(http.StatusOK)
}
```

Работает. Но при **100 000 RPS** — это **100 000 аллокаций в секунду**. Каждая — 4 КБ. **400 МБ/сек** аллокаций.

**Что происходит:**

- GC запускается **очень часто**.
- GC тратит **30–50% CPU**.
- Latency растёт из-за GC пауз.

Хочется: **не создавать** буфер каждый раз. **Переиспользовать** его.

Простейшее решение: глобальный пул буферов.

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    n, _ := r.Body.Read(buf)
    process(buf[:n])
    w.WriteHeader(http.StatusOK)
}
```

**Что даёт:**

- **Нет аллокаций** на каждый запрос.
- GC **не запускается**.
- CPU **освобождается**.

Это и есть **`sync.Pool`** — пул переиспользуемых объектов.

> **Мост к следующим главам:** `sync.Pool` — важный инструмент для снижения давления на GC. Он часто используется вместе с worker pool (Глава 13), batch (Глава 21) и pipeline (Глава 11). Понимание `sync.Pool` даёт понимание, **как оптимизировать горячий код**.

## 31.1 Почему аллокации дорогие

Прежде чем разбирать `sync.Pool`, поймём, **почему** аллокации дорогие.

### Что происходит при `make([]byte, 4096)`

**1. Аллокатор ищет место в heap.**

- Проверяет `mcache` текущего P.
- Если нет — идёт в `mcentral`.
- Если нет — идёт в `mheap`.
- Если нет — запрашивает память у ОС.

**2. Возвращает указатель.**

- Объект помечается как живой.

**3. GC при следующем цикле.**

- Обходит все живые объекты.
- Освобождает мёртвые.
- Тратит CPU.

**4. Копирование.**

- Объект может переместиться (если GC компактирующий).
- Хотя в Go — не компактирующий.

### Стоимость

| Операция | Time |
|:---|:---|
| `make([]byte, 4096)` | ~50–200 нс |
| GC цикл (маленький heap) | ~1–10 мс |
| GC цикл (большой heap) | ~10–100 мс |
| GC обход 1 объекта | ~10–50 нс |

**Ключевое:** аллокация сама по себе **дешёвая**. **Дорого** — **давление на GC**.

### Проблема: GC overhead

**Пример:** 100 000 аллокаций/сек.

- Heap растёт.
- GC запускается каждые 100 мс.
- Каждый GC обходит **все** живые объекты.
- **CPU на GC:** 30–50%.
- **Latency:** растёт из-за GC пауз.

### Как уменьшить давление на GC

**1. Меньше аллокаций.**

- `sync.Pool` — переиспользование.
- Stack allocation — если объект не убегает.

**2. Меньше объектов.**

- Объединить в один большой.
- Preallocate.

**3. Меньше указателей.**

- Указатели усложняют mark.

### Аналогия: посуда в кафе

**Без `sync.Pool`** — как если бы **каждый раз** при заказе покупали **новую тарелку**, а после еды **выкидывали**. Магазин бы разорился.

**С `sync.Pool`** — как если бы тарелки **мыли** и **переиспользовали**. Устойчиво и дёшево.

### 💡 Практика: как уменьшить давление на GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`sync.Pool`** для частых аллокаций в hot path.
2. **Preallocate слайсы** — `make([]T, 0, cap)`.
3. **Stack allocation** — если объект не убегает.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Профилируй GC** — `GODEBUG=gctrace=1`.
5. **Мониторинг heap.**

**❌ НЕ ДЕЛАЙ:**

6. **Не аллоцируй в hot path без необходимости.**
7. **Не используй `fmt.Sprintf` в hot path.**

## 31.2 Что такое sync.Pool

**`sync.Pool`** — пул объектов для переиспользования.

### API

```go
var pool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

// Получить объект
buf := pool.Get().([]byte)

// Вернуть объект
pool.Put(buf)
```

**Что делает:**

- `Get` — возвращает объект из пула. Если пул пуст — вызывает `New`.
- `Put` — возвращает объект в пул.

### Ключевое: `sync.Pool` не гарантирует сохранение

**`sync.Pool`** может **очиститься** в любой момент:

- При следующем GC.
- При переключении между P.

**Что это значит:** не полагайся на `sync.Pool` для **сохранения состояния**. Только для **переиспользования**.

### Пример: буфер в HTTP-хэндлере

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    // Используем buf
    n, _ := r.Body.Read(buf)
    process(buf[:n])
}
```

**Что происходит:**

- Первый запрос: `Get` → `New` (создаём буфер).
- После обработки: `Put` возвращает буфер в пул.
- Второй запрос: `Get` → получаем **тот же** буфер.
- **Нет аллокации.**

### Когда использовать `sync.Pool`

**1. Частые аллокации в hot path.**

- Буферы для I/O.
- Временные объекты.
- Рабочие структуры.

**2. Однотипные объекты.**

- Одинаковый размер.
- Одинаковая структура.

**3. Объекты без состояния.**

- Не важно, какой объект получишь.
- Главное — переиспользовать.

### Когда НЕ использовать

**1. Редкие аллокации.**

- Если аллокаций мало — overhead больше выгоды.

**2. Объекты с состоянием.**

- `sync.Pool` может вернуть **любой** объект.
- Состояние должно быть **сброшено**.

**3. Большие объекты.**

- 1 МБ буферы — пул будет **дорогим**.

### Схема

```
sync.Pool:

  Producer ──Put──► [pool] ──Get──► Consumer
                      │
                      │ если пуст
                      ▼
                    New() → создать новый
  
  GC может очистить pool в любой момент.
```

### 💡 Практика: как думать о sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`sync.Pool` для буферов в hot path.**
2. **`defer Put`** — обязательно.
3. **Сбрасывай состояние** перед Put.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`New`** — функция создания.

**❌ НЕ ДЕЛАЙ:**

5. **Не полагайся на `sync.Pool` для сохранения.**
6. **Не используй для редких аллокаций.**

## 31.3 sync.Pool внутри

Разберём **внутреннее устройство** `sync.Pool`.

### Структура

```go
type Pool struct {
    noCopy noCopy
    
    local     unsafe.Pointer  // [P]poolLocal
    localSize uintptr
    
    victim     unsafe.Pointer  // предыдущий local
    victimSize uintptr
    
    New func() any
}

type poolLocal struct {
    private any       // private — только для этого P
    shared  poolChain // shared — для stealing
}
```

**Ключевые поля:**

- **`local`** — массив `poolLocal` по одному на каждый P.
- **`victim`** — «жертвенный» кэш для двухфазной очистки.
- **`New`** — функция создания.

### poolLocal

**Каждый P имеет `poolLocal`:**

- **`private`** — один объект, доступный **только** этому P.
- **`shared`** — очередь объектов, из которой могут **красть** другие P.

### Как работает Get

```
pool.Get():
  1. Получить poolLocal текущего P.
  2. Если private != nil:
       взять private, обнулить private, вернуть.
  3. Иначе — взять из shared (FIFO).
  4. Если shared пуст — попробовать steal у других P.
  5. Если ничего нет — проверить victim.
  6. Если и там нет — вызвать New.
```

**Ключевое:** `private` — быстрый путь. `shared` — для переиспользования. `victim` — для двухфазной очистки.

### Как работает Put

```
pool.Put(x):
  1. Получить poolLocal текущего P.
  2. Если private == nil:
       private = x.
  3. Иначе — положить в shared (LIFO).
```

### Victim cache

**`victim`** — механизм **двухфазной очистки**.

**Что происходит:**

**При GC:**

1. `local` → `victim` (объекты **не удаляются**).
2. Старый `victim` — **удаляется**.
3. `local` — очищается.

**Что это даёт:** объекты **живут** два GC цикла. Это **сглаживает** пики.

### Схема

```
sync.Pool на 4 P:

  P0:  private=A  shared=[B, C]
  P1:  private=D  shared=[E]
  P2:  private=F  shared=[]
  P3:  private=G  shared=[H, I]

Get:
  - Если на текущем P есть private → взять.
  - Иначе — из shared.
  - Иначе — steal у другого P.
  - Иначе — victim.
  - Иначе — New.

GC:
  - local → victim.
  - старый victim → удалить.
```

### Стоимость

| Операция | Time |
|:---|:---|
| `Get` (private) | ~20–50 нс |
| `Get` (shared) | ~50–100 нс |
| `Get` (steal) | ~100–200 нс |
| `Get` (victim) | ~100–200 нс |
| `Get` (New) | ~200–500 нс |
| `Put` (private) | ~20–50 нс |
| `Put` (shared) | ~50–100 нс |

### 💡 Практика: как понимать sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`private` — быстрый путь.** Один объект на P.
2. **`shared` — для stealing.**
3. **`victim` — двухфазная очистка.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Не полагайся на сохранение.**

**❌ НЕ ДЕЛАЙ:**

5. **Не думай, что `sync.Pool` — это «бесплатный» кэш.**

## 31.4 Как использовать sync.Pool

Разберём **правильное использование** `sync.Pool`.

### Паттерн 1: буфер для I/O

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 32*1024)
    },
}

func process(r io.Reader) error {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    _, err := io.CopyBuffer(io.Discard, r, buf)
    return err
}
```

**Что даёт:** нет аллокаций буфера на каждый вызов.

### Паттерн 2: сброс состояния

**❌ Плохо:**

```go
var pool = sync.Pool{
    New: func() interface{} {
        return &Buffer{}
    },
}

func process() {
    b := pool.Get().(*Buffer)
    defer pool.Put(b)
    // b содержит данные предыдущего запроса!
}
```

**✅ Хорошо:**

```go
func process() {
    b := pool.Get().(*Buffer)
    defer func() {
        b.Reset()  // ← сброс перед Put
        pool.Put(b)
    }()
    // ...
}

type Buffer struct {
    data []byte
}

func (b *Buffer) Reset() {
    b.data = b.data[:0]
}
```

**Что даёт:** следующий `Get` вернёт **чистый** объект.

### Паттерн 3: `New` возвращает правильный тип

```go
var pool = sync.Pool{
    New: func() interface{} {
        return &Buffer{  // ← указатель, не значение
            data: make([]byte, 0, 4096),
        }
    },
}
```

**Почему указатель:** иначе копирование.

### Паттерн 4: использование в hot path

```go
func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    n, _ := r.Body.Read(buf)
    process(buf[:n])
}
```

**Ключевое:** `Get` и `Put` — **быстрые** (~50 нс). В hot path — ок.

### Паттерн 5: pool + метрики

```go
type PoolMetrics struct {
    Gets   atomic.Int64
    Puts   atomic.Int64
    News   atomic.Int64
}

var bufPool = sync.Pool{
    New: func() interface{} {
        poolMetrics.News.Add(1)
        return make([]byte, 4096)
    },
}

func Get() []byte {
    poolMetrics.Gets.Add(1)
    return bufPool.Get().([]byte)
}

func Put(b []byte) {
    poolMetrics.Puts.Add(1)
    bufPool.Put(b)
}
```

**Что даёт:** видно, сколько раз `New` вызывается.

### 💡 Практика: как использовать sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`defer Put`** — обязательно.
2. **Сбрасывай состояние** перед Put.
3. **Указатели** в `New`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Метрики** — Gets, Puts, News.
5. **Профилируй** до/после.

**❌ НЕ ДЕЛАЙ:**

6. **Не забывай Put.**
7. **Не оставляй состояние.**

## 31.5 Когда sync.Pool помогает

Разберём **случаи**, когда `sync.Pool` реально помогает.

### Случай 1: HTTP-сервер с буферами

**Без пула:**

- 100 000 RPS × 4 КБ = 400 МБ/сек аллокаций.
- GC: 30–50% CPU.

**С пулом:**

- 100 аллокаций в секунду (по числу P).
- GC: 5% CPU.

**Выгода: 6–10x по CPU.**

### Случай 2: JSON-энкодер

```go
var encoderPool = sync.Pool{
    New: func() interface{} {
        return json.NewEncoder(nil)
    },
}

func encode(w io.Writer, v interface{}) error {
    enc := encoderPool.Get().(*json.Encoder)
    defer encoderPool.Put(enc)
    
    enc.SetWriter(w)
    return enc.Encode(v)
}
```

**Что даёт:** нет аллокации `Encoder` на каждый вызов.

### Случай 3: парсер

```go
var parserPool = sync.Pool{
    New: func() interface{} {
        return &Parser{}
    },
}

func parse(data []byte) (Result, error) {
    p := parserPool.Get().(*Parser)
    defer parserPool.Put(p)
    
    p.Reset(data)
    return p.Parse()
}
```

### Случай 4: gzip

```go
var writerPool = sync.Pool{
    New: func() interface{} {
        w, _ := gzip.NewWriterLevel(io.Discard, gzip.BestSpeed)
        return w
    },
}

func compress(data []byte, w io.Writer) error {
    gw := writerPool.Get().(*gzip.Writer)
    defer writerPool.Put(gw)
    
    gw.Reset(w)
    defer gw.Reset(io.Discard)  // сброс для следующего
    _, err := gw.Write(data)
    if err != nil {
        return err
    }
    return gw.Close()
}
```

### Когда НЕ помогает

**1. Редкие вызовы.**

- 100 аллокаций/сек — пул не даст выгоды.

**2. Большие объекты.**

- 1 МБ буферы — пул занимает много памяти.

**3. Объекты с большим состоянием.**

- Сложно сбросить.

### Схема

```
sync.Pool помогает:

  Аллокаций/сек:  10 000+  ──►  да
  Размер объекта: 1 КБ – 100 КБ  ──►  да
  Hot path:       да  ──►  да
  
sync.Pool НЕ помогает:

  Аллокаций/сек:  < 100  ──►  нет
  Размер объекта: > 1 МБ  ──►  нет
  Редкий вызов:   да  ──►  нет
```

### 💡 Практика: когда использовать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Hot path с 10 000+ аллокаций/сек.**
2. **Буферы 1 КБ – 100 КБ.**
3. **Объекты без состояния.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмарк** до/после.

**❌ НЕ ДЕЛАЙ:**

5. **Не используй для редких аллокаций.**
6. **Не используй для больших объектов.**

## 31.6 Когда sync.Pool вредит

Разберём **случаи**, когда `sync.Pool` **вредит**.

### Проблема 1: утечка памяти

**`sync.Pool` может удерживать объекты долго.** Если объекты **большие** — это утечка.

```go
var pool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 10*1024*1024)  // 10 МБ!
    },
}
```

**Что происходит:**

- Каждый P держит 10 МБ.
- 8 P → 80 МБ.
- GC не может их освободить.

**Решение:** не используй `sync.Pool` для больших объектов.

### Проблема 2: разделяемое состояние

**Если объект содержит указатель на что-то большое** — пул может удерживать это.

```go
type Result struct {
    data []byte
    meta *BigMeta  // ← утечка
}
```

**Решение:** сбрасывай все поля.

### Проблема 3: неправильный Reset

**Если `Reset` не сбрасывает всё** — данные утекают.

```go
func (b *Buffer) Reset() {
    b.data = b.data[:0]
    // ← meta не сброшен!
}
```

### Проблема 4: `sync.Pool` не гарантирует

**`sync.Pool` может вернуть `nil`, если `New` не задан:**

```go
var pool sync.Pool  // ← без New
x := pool.Get()  // nil
```

**Решение:** всегда задавай `New`.

### Проблема 5: пул не даёт выгоды

**Если аллокаций мало** — пул только **добавляет overhead**.

```go
var pool = sync.Pool{
    New: func() interface{} { return &Struct{} },
}

// Редкий вызов
func process() {
    s := pool.Get().(*Struct)
    defer pool.Put(s)
    // ...
}
```

**Overhead:** `Get` + `Put` ~100 нс. Аллокация ~50 нс. **Пул медленнее.**

### Схема

```
sync.Pool вредит:

  Объект > 1 МБ  ──►  утечка памяти
  Редкие вызовы  ──►  overhead
  Сложное состояние  ──►  утечка данных
  Нет Reset  ──►  утечка данных
  Нет New  ──►  nil
```

### 💡 Практика: как не навредить

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Небольшие объекты** (1 КБ – 100 КБ).
2. **Правильный Reset.**
3. **Всегда задавай New.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмарк** до/после.
5. **Метрики** на New.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй для больших объектов.**
7. **Не используй для редких аллокаций.**
8. **Не оставляй состояние.**

## 31.7 Аллокатор Go: mcache, mcentral, mheap

Разберём **аллокатор Go** — три уровня.

### Три уровня аллокации

**1. `mcache` — per-P кэш.**

- Один на каждый P.
- **Без блокировок.**
- Быстрый путь.

**2. `mcentral` — общий кэш по размеру.**

- Один на каждый размер класса (67 классов).
- **С блокировкой.**
- Средний путь.

**3. `mheap` — глобальный heap.**

- Один на процесс.
- **С блокировкой.**
- Медленный путь.

### Схема

```
┌─────────────────────────────────────────────────────────┐
│  P0                    P1                    P2         │
│  ┌──────────┐         ┌──────────┐         ┌──────────┐│
│  │ mcache   │         │ mcache   │         │ mcache   ││
│  │ (без lock)│        │ (без lock)│        │ (без lock)││
│  └────┬─────┘         └────┬─────┘         └────┬─────┘│
│       │                    │                    │      │
│       │ если нет           │                    │      │
│       ▼                    ▼                    ▼      │
│  ┌──────────────────────────────────────────────────┐  │
│  │  mcentral[class] (по размеру класса)             │  │
│  │  (с блокировкой)                                  │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │                              │
│                         │ если нет                     │
│                         ▼                              │
│  ┌──────────────────────────────────────────────────┐  │
│  │  mheap (глобальный)                              │  │
│  │  (с блокировкой)                                  │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │                              │
│                         │ если нет                     │
│                         ▼                              │
│  ┌──────────────────────────────────────────────────┐  │
│  │  OS (mmap)                                        │  │
│  └──────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

### Как работает аллокация

```
make([]byte, 4096):
  1. Определить размер класса (например, 4096 → 4096).
  2. Проверить mcache текущего P:
       - Если есть свободный span — выделить.
  3. Иначе — mcentral[class]:
       - Заблокировать.
       - Найти span.
       - Разблокировать.
  4. Иначе — mheap:
       - Заблокировать.
       - Найти свободную память.
       - Разблокировать.
  5. Иначе — OS (mmap).
```

### Стоимость

| Уровень | Time | Блокировка |
|:---|:---|:---|
| `mcache` | ~10–30 нс | Нет |
| `mcentral` | ~50–100 нс | Да |
| `mheap` | ~100–500 нс | Да |
| `mmap` | ~1–10 мкс | Да |

**Ключевое:** `mcache` — **быстрый**. Если попадаешь в `mheap` — **медленно**.

### Как это связано с `sync.Pool`

**`sync.Pool` — выше аллокатора.** Он **переиспользует** уже выделенные объекты. Это **обходит аллокатор** и **GC** полностью.

**Схема:**

```
make([]byte, 4096) → mcache → mcentral → mheap → OS

sync.Pool.Get() → private → shared → victim → New() → make()
```

**С `sync.Pool`:**

- 99% операций — `private` или `shared`. **~20–100 нс**.
- 1% — `New`. **~200–500 нс**.

**Без `sync.Pool`:**

- Каждый раз — `mcache`. **~10–30 нс** (но плюс GC).

### 💡 Практика: как понимать аллокатор

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`mcache` — быстрый.** Избегай `mheap`.
2. **`sync.Pool`** — обходит аллокатор.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Профилируй аллокации** — `-memprofile`.

**❌ НЕ ДЕЛАЙ:**

4. **Не думай, что аллокация бесплатна.**
5. **Не игнорируй давление на GC.**

## 31.8 В связке с другими паттернами

`sync.Pool` редко используется **в одиночку**. Разберём связки.

### sync.Pool + worker pool

**Воркеры переиспользуют буферы:**

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

func worker(tasksCh <-chan Task) {
    for task := range tasksCh {
        buf := bufPool.Get().([]byte)
        process(task, buf)
        bufPool.Put(buf)
    }
}
```

### sync.Pool + batch

**Batch переиспользует буфер для накопления:**

```go
var batchPool = sync.Pool{
    New: func() interface{} {
        return make([]Event, 0, 1000)
    },
}

func flush(events []Event) {
    batch := batchPool.Get().([]Event)
    defer batchPool.Put(batch[:0])
    
    batch = append(batch, events...)
    db.InsertBatch(batch)
}
```

### sync.Pool + pipeline

**Стадии pipeline переиспользуют объекты:**

```go
var msgPool = sync.Pool{
    New: func() interface{} {
        return &Message{}
    },
}

func parseStage(ctx context.Context, in <-chan []byte) <-chan *Message {
    out := make(chan *Message)
    go func() {
        defer close(out)
        for data := range in {
            msg := msgPool.Get().(*Message)
            msg.Reset(data)
            select {
            case out <- msg:
            case <-ctx.Done():
                msgPool.Put(msg)
                return
            }
        }
    }()
    return out
}
```

**Проблема:** следующий потребитель должен **вернуть** объект в пул.

### sync.Pool + HTTP-сервер

**HTTP-хэндлеры переиспользуют буферы:**

```go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 32*1024)
    },
}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    
    // ... чтение тела ...
}
```

### sync.Pool + rate limiter

**Rate limiter переиспользует токены:**

```go
var tokenPool = sync.Pool{
    New: func() interface{} {
        return &Token{}
    },
}
```

### Схема

```
HTTP-хэндлер ──Get──► [sync.Pool] ──Put──► HTTP-хэндлер
                          │
                          │ если пуст
                          ▼
                       New()
```

### 💡 Практика: как комбинировать sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **sync.Pool + HTTP** — для буферов.
2. **sync.Pool + worker pool** — для воркеров.

**👍 СТОИТ СДЕЛАТЬ:**

3. **sync.Pool + batch** — для батчей.
4. **sync.Pool + pipeline** — для сообщений.

**❌ НЕ ДЕЛАЙ:**

5. **Не забывай возвращать в пул.**

## 31.9 Практика Go: sync.Pool с метриками

Разберём **sync.Pool с метриками**.

### Полный код

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

type Metrics struct {
    Gets atomic.Int64
    Puts atomic.Int64
    News atomic.Int64
}

var (
    bufPool = sync.Pool{
        New: func() interface{} {
            poolMetrics.News.Add(1)
            return make([]byte, 4096)
        },
    }
    poolMetrics Metrics
)

func GetBuffer() []byte {
    poolMetrics.Gets.Add(1)
    return bufPool.Get().([]byte)
}

func PutBuffer(buf []byte) {
    poolMetrics.Puts.Add(1)
    bufPool.Put(buf)
}

func process(data []byte) {
    buf := GetBuffer()
    defer PutBuffer(buf)
    
    copy(buf, data)
    // ... обработка ...
}

func main() {
    start := time.Now()
    
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                process([]byte("hello"))
            }
        }()
    }
    wg.Wait()
    
    elapsed := time.Since(start)
    fmt.Printf("Elapsed: %v\n", elapsed)
    fmt.Printf("Gets:    %d\n", poolMetrics.Gets.Load())
    fmt.Printf("Puts:    %d\n", poolMetrics.Puts.Load())
    fmt.Printf("News:    %d\n", poolMetrics.News.Load())
    fmt.Printf("Reuse:   %.1f%%\n",
        100*float64(poolMetrics.Gets.Load()-poolMetrics.News.Load())/
            float64(poolMetrics.Gets.Load()))
}
```

**Пример вывода:**

```
Elapsed: 45ms
Gets:    1000000
Puts:    1000000
News:    8
Reuse:   99.9992%
```

**Что видно:**

- **1 000 000 Get** — все обращения к пулу.
- **8 New** — по числу P (8 ядер).
- **99.9992% reuse** — пул работает.

### Сравнение с без пула

```go
func processNoPool(data []byte) {

    // ... обработка ...
}
```

### Метрики

**Что мониторить:**

- **Gets** — сколько раз брали из пула.
- **Puts** — сколько раз вернули.
- **News** — сколько раз создали новый.

**Что означает:**

- **Reuse > 95%** — пул работает.

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

## 31.10 Выводы и типичные ошибки

**Что мы узнали?**

Аллокации **дорогие** из-за давления на GC, а не из-за самого выделения памяти. `sync.Pool` — пул переиспользуемых объектов. Внутри: `private`, `shared`, `victim`. Работает **быстро** — 20–100 нс. **Не гарантирует** сохранение — может очиститься при GC. **Когда помогает:** hot path с 10 000+ аллокаций/сек, объекты 1 КБ – 100 КБ, без состояния. **Когда вредит:** большие объекты, редкие аллокации, сложное состояние. **Аллокатор Go:** `mcache` (быстро), `mcentral`, `mheap` (медленно). `sync.Pool` обходит аллокатор и GC.

**Типичные ошибки:**

- ❌ **Не делать `Put`.** Утечка.
- ❌ **Не сбрасывать состояние.** Утечка данных.
- ❌ **Не задавать `New`.** `Get` вернёт `nil`.
- ❌ **Использовать для больших объектов.** Утечка памяти.
- ❌ **Использовать для редких аллокаций.** Overhead.
- ❌ **Забывать про `victim` cache.** Объекты живут 2 GC цикла.
- ❌ **Полагать, что `sync.Pool` сохраняет.** Не гарантирует.
- ❌ **Использовать в hot path без измерения.**
- ❌ **Не мониторить `News`.**
- ❌ **Не сбрасывать указатели на большие объекты.**

## 31.13 Ответы

### Ответ 1

**Аллокации дорогие** из-за **давления на GC**, а не из-за выделения памяти. Сама аллокация — 50–200 нс. Но GC обходит **все** живые объекты. При 100 000 аллокаций/сек — GC запускается часто, тратит 30–50% CPU.

### Ответ 2

**`sync.Pool`** — пул переиспользуемых объектов. Решает задачу: **снизить давление на GC** через переиспользование.

```go
var pool = sync.Pool{
    New: func() interface{} { return make([]byte, 4096) },
}

buf := pool.Get().([]byte)
defer pool.Put(buf)
```

### Ответ 3

**`sync.Pool` внутри:**

- **`local`** — массив `poolLocal` по одному на P.
- **`poolLocal`:** `private` (один объект) + `shared` (очередь).
- **`victim`** — «жертвенный» кэш для двухфазной очистки.
- **`New`** — функция создания.

### Ответ 4

**`victim` cache** — механизм **двухфазной очистки**.

**При GC:**

1. `local` → `victim` (объекты не удаляются).
2. Старый `victim` → удаляется.
3. `local` → очищается.

**Что даёт:** объекты живут **два GC цикла**. Сглаживает пики.

### Ответ 5

**Правильное использование:**

1. **`defer Put`** — обязательно.
2. **Сброс состояния** перед Put.
3. **Указатели** в `New`.
4. **Метрики** Gets, Puts, News.

```go
var pool = sync.Pool{
    New: func() interface{} {
        return &Buffer{data: make([]byte, 0, 4096)}
    },
}

func process() {
    b := pool.Get().(*Buffer)
    defer func() {
        b.Reset()
        pool.Put(b)
    }()
    // ...
}
```

### Ответ 6

**Когда помогает:**

1. **10 000+ аллокаций/сек** в hot path.
2. **Объекты 1 КБ – 100 КБ.**
3. **Объекты без состояния.**
4. **HTTP-серверы** с буферами.
5. **JSON, gzip, парсеры.**

**Выгода:** 2–10x по CPU.

### Ответ 7

**Когда вредит:**

1. **Большие объекты** (> 1 МБ) — утечка памяти.
2. **Редкие аллокации** — overhead больше выгоды.
3. **Сложное состояние** — легко забыть сбросить.
4. **`Get` без `Put`** — утечка.

### Ответ 8

**Аллокатор Go:**

- **`mcache`** — per-P кэш. Без блокировок. Быстро (10–30 нс).
- **`mcentral`** — общий кэш по размеру. С блокировкой. Средне (50–100 нс).
- **`mheap`** — глобальный heap. С блокировкой. Медленно (100–500 нс).
- **OS (mmap)** — медленно (1–10 мкс).

**`sync.Pool`** обходит аллокатор **полностью**.

### Ответ 9

**Измерение:**

1. **Метрики:** Gets, Puts, News.
2. **Reuse** — процент переиспользования.
3. **Бенчмарк** до/после.
4. **Профилирование heap** — `-memprofile`.

```go
Reuse = (Gets - News) / Gets × 100%
```

**Reuse > 95%** — пул работает.

### Ответ 10

**`sync.Pool` не гарантирует сохранение**, потому что может **очиститься** в любой момент:

- При следующем GC.
- При переключении между P.

**Что это значит:** не полагайся на `sync.Pool` для **сохранения состояния**. Только для **переиспользования**. Если нужен кэш — используй свой с TTL.
