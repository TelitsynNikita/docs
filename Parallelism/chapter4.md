## 4.0 Пролог: код, который работает на моём ноутбуке

Ты пишешь сервис. Есть флаг `ready`, который одна горутина устанавливает, а другая читает:

```go
package main

import (
    "fmt"
    "time"
)

var ready bool
var data string

func producer() {
    data = "hello"   // (1) пишем данные
    ready = true     // (2) поднимаем флаг
}

func consumer() {
    for !ready {     // (3) ждём флаг
        // busy loop
    }
    fmt.Println(data) // (4) читаем данные
}

func main() {
    go producer()
    go consumer()
    time.Sleep(1 * time.Second)
}
```

Запускаешь на своём ноутбуке (x86, Linux) — работает. Печатает `hello`. Всегда.

Ты деплоишь на прод-сервер (ARM64, AWS Graviton) — **иногда** печатает пустую строку. **Иногда** — `hello`. А иногда — падает с segmentation fault.

❓ **Что произошло?** Код же одинаковый!

💡 **Ответ:** в коде **data race**, и он **не определён спецификацией Go**. На x86 гонка «маскируется» строгой моделью памяти процессора. На ARM — проявляется в полной мере.

**Что может произойти:**

- **Компилятор** может переставить (1) и (2) местами: `ready = true` до `data = "hello"`. Тогда consumer увидит `ready == true`, но `data` ещё пустая.
- **Компилятор** может закешировать `ready` в регистре в цикле (3): `for !ready` превратится в бесконечный цикл, потому что компилятор «не знает», что `ready` меняется другой горутиной.
- **Процессор** может выполнить запись `ready = true` **раньше**, чем запись `data = "hello"` — из-за store buffer.
- **Процессор** может прочитать `data` **раньше**, чем `ready` — из-за out-of-order execution.

**Ключевое:** это **не баг компилятора или процессора**. Это **разрешённое поведение**, потому что в коде **нет синхронизации**. Спецификация Go говорит: если есть data race, поведение **не определено**.

> **Важный мост к будущим главам:** эта глава — **фундамент**. Без понимания happens-before непонятно, почему `Mutex` работает (Глава 3), почему `atomic` работает (Глава 3), почему каналы синхронизируют (Глава 2). Всё, что мы разбирали раньше, **опирается** на модель памяти. Здесь мы закроем этот пробел.

## 4.1 Data race: определение из спецификации

В подглаве 3.0 (Глава 3) мы сказали: «data race — это undefined behavior». Теперь дадим **точное** определение.

### Определение из спецификации Go

Спецификация Go (Go Memory Model) говорит:

> **Data race** — это ситуация, когда две горутины обращаются к одной и той же переменной **одновременно**, и хотя бы одна из них **пишет**, без синхронизации.

Формально:

- **Две горутины** — не одна. Гонка между горутинами, не внутри одной.
- **Одна и та же переменная** — один и тот же адрес памяти.
- **Хотя бы одна пишет** — read-read не гонка. Write-read и write-write — гонка.
- **Без синхронизации** — нет happens-before между операциями.

### Что НЕ является data race

**Read-read:**

```go
// Горутина A: x := data
// Горутина B: y := data
```

Обе читают. Никто не пишет. **Не гонка.**

**Доступ под мьютексом:**

```go
var mu sync.Mutex
var data int

// Горутина A:
mu.Lock()
data = 42
mu.Unlock()

// Горутина B:
mu.Lock()
x := data
mu.Unlock()
```

Обе под одним мьютексом. Мьютекс устанавливает happens-before. **Не гонка.**

**Доступ через atomic:**

```go
var data atomic.Int64

// Горутина A:
data.Store(42)

// Горутина B:
x := data.Load()
```

Atomic-операции не создают гонку. **Не гонка.**

### Что является data race

**Write-read без синхронизации:**

```go
var data int

// Горутина A:
data = 42

// Горутина B:
x := data
```

**Гонка.** Даже если на x86 «работает».

**Write-write без синхронизации:**

```go
var data int

// Горутина A:
data = 42

// Горутина B:
data = 100
```

**Гонка.** Результат непредсказуем.

**Read-write с «флагом» без синхронизации:**

```go
var ready bool
var data string

// Горутина A:
data = "hello"
ready = true

// Горутина B:
for !ready {}
fmt.Println(data)
```

**Гонка.** `ready` и `data` — обе без синхронизации.

### Почему это undefined behavior

**Ключевое:** спецификация Go **не даёт никаких гарантий** при data race. Программа может:

- Работать «правильно» (как на x86 в примере).
- Работать «неправильно» (как на ARM).
- Падать с segmentation fault.
- Зацикливаться.
- Печатать мусор.
- **Что угодно.**

**Это не «баг, который иногда проявляется».** Это **нарушение контракта** программы со спецификацией. Программа, в которой есть data race, **не является корректной Go-программой**.

### Аналогия: чтение книги, которую кто-то редактирует

Представь, что ты читаешь книгу, а редактор одновременно правит её.

- **Без синхронизации:** ты можешь прочитать половину старой версии, половину новой. Или строку, которой ещё нет. Или строку, которую уже удалили.
- **С мьютексом:** редактор говорит «я закончил правку», ты говоришь «я начинаю чтение». Никто не мешает друг другу.
- **С atomic:** редактор атомарно заменяет одну страницу. Ты читаешь либо старую, либо новую — но не смесь.

**Ключевое:** без синхронизации **никто не гарантирует**, что ты прочитаешь что-то осмысленное.

### Аннотация сложности

| Ситуация | Гонка? | Поведение |
|:---|:---|:---|
| Read-read | ❌ Нет | Определено |
| Read-write под мьютексом | ❌ Нет | Определено (happens-before) |
| Read-write через atomic | ❌ Нет | Определено (atomic) |
| Write-read без синхронизации | ✅ Да | **Undefined** |
| Write-write без синхронизации | ✅ Да | **Undefined** |

### 💡 Практика: как не допустить data race

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Любой доступ к разделяемой памяти — под синхронизацией.** `Mutex`, `RWMutex`, `atomic`, канал.
2. **Запускай `go test -race`** — race detector найдёт гонки (см. 4.7).
3. **Помни: read-read — не гонка.** Но write-read и write-write — гонка.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для флагов — `atomic.Bool`.** Не `bool` + busy loop.
5. **Для данных — `Mutex` или канал.** Не «голые» переменные.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Комментарии** о том, под какой синхронизацией находится переменная.

**❌ НЕ ДЕЛАЙ:**

7. **Не полагайся на «работает на моём ноутбуке».** x86 маскирует гонки.
8. **Не используй `bool` для флага «готовности»** без atomic. Компилятор может закешировать.
9. **Не игнорируй предупреждения race detector.** «Иногда» — это всегда «когда-нибудь в проде».

### Ключевые выводы подглавы 4.1

- **Data race** — две горутины, одна переменная, хотя бы одна пишет, без синхронизации.
- **Read-read — не гонка.** Write-read и write-write — гонка.
- **Последствия data race — undefined behavior.** Не «иногда врёт», а «что угодно».
- **Синхронизация** — `Mutex`, `RWMutex`, `atomic`, канал.
- **Race detector** находит гонки, но не все (см. 4.7).

## 4.2 Happens-before: фундамент памяти

Мы сказали: «синхронизация устанавливает happens-before». Теперь разберём, **что это такое**.

### Определение

**Happens-before** — это **отношение порядка** между операциями в программе. Если операция A **happens-before** операции B, то:

- Все эффекты A **видны** B.
- A **упорядочена** до B.

**Обозначение:** A → B.

### Пример

```go
var x int
var mu sync.Mutex

// Горутина A:
mu.Lock()
x = 42       // (1)
mu.Unlock()  // (2)

// Горутина B:
mu.Lock()    // (3)
y := x       // (4)
mu.Unlock()  // (5)
```

**Что гарантирует `Mutex`:**

- (1) → (2) — внутри горутины A порядок очевиден.
- (3) → (4) — внутри горутины B порядок очевиден.
- **(2) → (3)** — `Unlock` в A happens-before `Lock` в B (если B получил мьютекс после A).
- **Следовательно, (1) → (4)** — запись `x = 42` happens-before чтения `y := x`.
- **Гарантия:** B увидит `x == 42`.

**Ключевое:** `Mutex` не просто «блокирует». Он **устанавливает happens-before** между `Unlock` одной горутины и `Lock` другой.

### Happens-before внутри одной горутины

Внутри одной горутины **все** операции упорядочены **естественным порядком выполнения**:

```go
x = 1
y = 2
z = x + y
```

`x = 1` → `y = 2` → `z = x + y`. Внутри горутины это **всегда** так.

**Но:** компилятор может переставить операции, если **результат** не меняется. Например:

```go
a := 1
b := 2
c := a + b
```

Компилятор может выполнить `b := 2` до `a := 1`, потому что результат `c` одинаков. Это **внутреннее переупорядочивание**, и оно разрешено.

**Гарантия happens-before внутри горутины:** если операция A зависит от B (например, читает переменную, которую B пишет), то A → B **сохраняется**. Компилятор не может нарушить **зависимости по данным**.

### Happens-before между горутинами

**По умолчанию** — **нет никакого порядка** между операциями разных горутин. Они выполняются параллельно, и порядок непредсказуем.

**Синхронизация** — это способ **установить** happens-before между горутинами:

| Синхронизация | Happens-before |
|:---|:---|
| `mu.Unlock()` → `mu.Lock()` | Unlock happens-before следующего Lock |
| `ch <- v` → `<-ch` | Отправка happens-before получения |
| `close(ch)` → `<-ch` (возвращает zero) | Close happens-before получения |
| `atomic.Store` → `atomic.Load` | Store happens-before Load (если Load видит Store) |
| `wg.Done()` → `wg.Wait()` | Done happens-before Wait |
| `once.Do(f)` → `once.Do(g)` | f happens-before g |

**Без синхронизации** — **нет** happens-before. Операции могут выполняться в любом порядке, и результаты непредсказуемы.

### Визуализация

```
Без синхронизации:

  Горутина A: ──[write x]──[write ready]──
  Горутина B: ──[read ready]──[read x]──
  
  Нет порядка между write и read. 
  B может прочитать ready=true, но x — старую.

С синхронизацией через Mutex:

  Горутина A: ──Lock──[write x]──[write ready]──Unlock──
  Горутина B: ───────────────────────────────────Lock──[read ready]──[read x]──Unlock──
  
  Unlock A → Lock B. Всё, что было до Unlock, видно после Lock.
  B увидит x и ready в правильном порядке.
```

### Пример: почему `data = "hello"; ready = true` не работает

```go
var data string
var ready bool

// Горутина A:
data = "hello"   // (1)
ready = true     // (2)

// Горутина B:
for !ready {}    // (3)
fmt.Println(data) // (4)
```

**Проблема:** нет happens-before между (2) и (3).

- Компилятор может переставить (1) и (2): `ready = true` до `data = "hello"`.
- Компилятор может закешировать `ready` в регистре в (3).
- Процессор может выполнить (2) раньше (1) из-за store buffer.

**Результат:** B может увидеть `ready == true`, но `data == ""`.

**Как исправить:**

```go
var data string
var ready atomic.Bool

// Горутина A:
data = "hello"
ready.Store(true)  // atomic.Store устанавливает happens-before

// Горутина B:
for !ready.Load() {}  // atomic.Load
fmt.Println(data)     // гарантированно увидит "hello"
```

**Что изменилось:** `atomic.Store` и `atomic.Load` устанавливают happens-before. Если B видит `ready == true`, то все записи **до** `ready.Store(true)` видны после `ready.Load()`.

### Три свойства happens-before

1. **Транзитивность:** если A → B и B → C, то A → C.
2. **Внутри горутины:** операции упорядочены естественным порядком (с учётом зависимостей).
3. **Между горутинами:** только через синхронизацию.

### Аннотация сложности

| Операция | Happens-before |
|:---|:---|
| Внутри горутины | Естественный порядок (с учётом зависимостей) |
| `Mutex.Unlock` → `Mutex.Lock` | ✅ Да |
| Канал: send → recv | ✅ Да |
| Канал: close → recv (zero) | ✅ Да |
| `atomic.Store` → `atomic.Load` | ✅ Да |
| `wg.Done` → `wg.Wait` | ✅ Да |
| `once.Do(f)` → `once.Do(g)` | ✅ Да |
| Без синхронизации | ❌ Нет |

### 💡 Практика: как использовать happens-before

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: без синхронизации — нет happens-before.** Не полагайся на «порядок в коде».
2. **Для флагов — `atomic.Bool`.** `atomic.Store`/`Load` устанавливают happens-before.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для данных — `Mutex` или канал.** Они устанавливают happens-before.
4. **Читай Go Memory Model** (официальная документация) — там полный список.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать все детали happens-before** — достаточно понимать, что синхронизация его устанавливает.

**❌ НЕ ДЕЛАЙ:**

6. **Не полагайся на «порядок в коде» между горутинами.** Без синхронизации порядок не определён.
7. **Не используй `bool` для флага** без atomic.

### Ключевые выводы подглавы 4.2

- **Happens-before** — отношение порядка между операциями. Если A → B, эффекты A видны B.
- **Внутри горутины** — естественный порядок (с учётом зависимостей).
- **Между горутинами** — только через синхронизацию.
- **Синхронизация устанавливает happens-before:** `Mutex`, каналы, `atomic`, `WaitGroup`, `Once`.
- **Без синхронизации** — нет happens-before, результаты непредсказуемы.

## 4.3 Переупорядочивание: компилятор и процессор

Мы сказали: «компилятор и процессор могут переставить операции». Разберём, **как именно** и **почему**.

### Два уровня переупорядочивания

**1. Переупорядочивание компилятором (compile-time):**

Компилятор анализирует код и может **переставить** операции, если это не меняет **результат в рамках одной горутины**.

**2. Переупорядочивание процессором (run-time):**

Процессор может выполнять инструкции **не в том порядке**, в котором они записаны в коде, если это не меняет **результат в рамках одного ядра**.

### Почему компилятор переупорядочивает

**Оптимизации:**

- **Устранение мёртвого кода** — если переменная не используется, запись можно удалить.
- **Общие подвыражения** — если `a + b` вычисляется дважды, можно вычислить один раз.
- **Инлайнинг** — встроить функцию в место вызова.
- **Перестановка** — если операция не зависит от другой, можно поменять их местами.

**Пример:**

```go
a := 1
b := 2
c := a + b
```

Компилятор может выполнить `b := 2` до `a := 1`, потому что `c` от этого не меняется. Это **разрешено** спецификацией.

**Проблема:** если `a` — разделяемая переменная, а `b` — флаг, компилятор может переставить их так, что флаг будет установлен до записи данных.

### Почему процессор переупорядочивает

**Out-of-order execution:**

Современные процессоры выполняют инструкции **не в порядке программы**, а в порядке **готовности**. Если инструкция `A` ждёт данные из памяти, процессор может выполнить `B` (которая не зависит от `A`), а потом вернуться к `A`.

**Store buffer:**

Запись в память проходит через **store buffer** — буфер между ядром и кэшем. Ядро может записать значение в store buffer и продолжить выполнение, не дожидаясь, пока запись попадёт в кэш.

**Проблема:** две записи могут попасть в память **в разном порядке** на разных ядрах.

**Пример на x86:**

```asm
; Горутина A:
mov [data], "hello"   ; (1)
mov [ready], 1        ; (2)
```

На x86 запись (2) **не может** обогнать (1) — x86 имеет модель памяти **TSO** (Total Store Order), которая гарантирует порядок записей. **Но** чтения могут обгонять записи.

**Пример на ARM:**

```asm
; Горутина A:
str "hello", [data]   ; (1)
str 1, [ready]        ; (2)
```

На ARM запись (2) **может** обогнать (1) — ARM имеет **слабую** модель памяти (weak memory model).

### Типы переупорядочивания

**1. Store-store:**

```
Запись A → Запись B
Может ли B выполниться раньше A?
```

- **x86:** ❌ Нет (TSO).
- **ARM:** ✅ Да.

**2. Load-load:**

```
Чтение A → Чтение B
Может ли B выполниться раньше A?
```

- **x86:** ❌ Нет.
- **ARM:** ✅ Да.

**3. Load-store:**

```
Чтение A → Запись B
Может ли B выполниться раньше A?
```

- **x86:** ❌ Нет.
- **ARM:** ✅ Да.

**4. Store-load:**

```
Запись A → Чтение B
Может ли B выполниться раньше A?
```

- **x86:** ✅ Да (единственное переупорядочивание, разрешённое в TSO).
- **ARM:** ✅ Да.

### Визуализация

```
Исходный код:
  data = "hello"    // (1) store
  ready = true      // (2) store

x86 (TSO):
  [store data] → [store ready]  ← порядок сохраняется
  Но: load ready может обогнать load data

ARM (weak):
  [store ready] → [store data]  ← порядок МОЖЕТ быть нарушен
  И: load data может обогнать load ready
```

### Почему это не баг

**Компилятор и процессор** оптимизируют **в рамках одной горутины**. Они гарантируют:

- Результат вычислений **внутри горутины** не меняется.
- Зависимости по данным **сохраняются**.

**Но:** они **не знают** о других горутинах. Если две горутины обращаются к одной памяти без синхронизации — компилятор и процессор **не обязаны** сохранять порядок.

### Как синхронизация решает проблему

**Синхронизация** (Mutex, atomic, каналы) вставляет **барьеры памяти**, которые:

- Запрещают компилятору переставлять операции **через барьер**.
- Запрещают процессору переупорядочивать операции **через барьер**.

**Без барьера** — компилятор и процессор свободны. **С барьером** — порядок гарантирован.

### Аннотация сложности

| Архитектура | Store-store | Load-load | Load-store | Store-load |
|:---|:---|:---|:---|:---|
| x86 (TSO) | ❌ Нет | ❌ Нет | ❌ Нет | ✅ Да |
| ARM (weak) | ✅ Да | ✅ Да | ✅ Да | ✅ Да |
| RISC-V (weak) | ✅ Да | ✅ Да | ✅ Да | ✅ Да |

### 💡 Практика: как не попасть на переупорядочивание

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: компилятор и процессор могут переставлять операции.** Не полагайся на «порядок в коде».
2. **Для порядка — синхронизация.** `Mutex`, `atomic`, каналы вставляют барьеры.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Тестируй на ARM.** Если код работает на x86, но не на ARM — это гонка.
4. **Запускай `go test -race`** — race detector ловит переупорядочивание.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать точную модель памяти x86 и ARM** — достаточно понимать, что переупорядочивание возможно.

**❌ НЕ ДЕЛАЙ:**

6. **Не полагайся на x86-поведение.** Прод может быть на ARM.
7. **Не используй `bool` для флага «готовности»** без atomic.

### Ключевые выводы подглавы 4.3

- **Переупорядочивание** — компилятор и процессор могут переставлять операции.
- **Компилятор** — оптимизации, перестановка независимых операций.
- **Процессор** — out-of-order execution, store buffer.
- **x86 (TSO)** — сохраняет порядок store-store, но разрешает store-load.
- **ARM (weak)** — разрешает все типы переупорядочивания.
- **Синхронизация** вставляет барьеры, запрещающие переупорядочивание.
- **Без синхронизации** — порядок не гарантирован.

## 4.4 Барьеры памяти: зачем они нужны

Мы сказали: «синхронизация вставляет барьеры». Разберём, **что это такое**.

### Определение

**Барьер памяти** (memory barrier, fence) — это **инструкция процессора**, которая:

- **Запрещает** переупорядочивание операций **через барьер**.
- **Гарантирует** видимость операций **до барьера** для других ядер **после барьера**.

### Типы барьеров

**1. Full barrier (Sequential Consistency, `MFENCE` на x86):**

- Запрещает **все** переупорядочивания через барьер.
- Самый дорогой.

**2. Store barrier (`SFENCE` на x86):**

- Запрещает переупорядочивание **записей** через барьер.
- Гарантирует, что все записи **до барьера** видны **после барьера**.

**3. Load barrier (`LFENCE` на x86):**

- Запрещает переупорядочивание **чтений** через барьер.
- Гарантирует, что все чтения **до барьера** завершены **до барьера**.

**4. Acquire barrier:**

- Запрещает переупорядочивание **чтений и записей** после барьера с операциями **до** барьера.
- Используется при «захвате» ресурса (например, `Mutex.Lock`).

**5. Release barrier:**

- Запрещает переупорядочивание **записей** до барьера с операциями **после** барьера.
- Используется при «освобождении» ресурса (например, `Mutex.Unlock`).

### Пример: acquire и release

```go
// Горутина A:
data = "hello"      // (1) обычная запись
mu.Lock()           // (2) acquire barrier (не даёт (3) обогнать (2))
shared = data       // (3) запись под мьютексом
mu.Unlock()         // (4) release barrier (не даёт (4) обогнать (3))

// Горутина B:
mu.Lock()           // (5) acquire barrier (не даёт (6) обогнать (5))
local = shared      // (6) чтение под мьютексом
mu.Unlock()         // (7)
```

**Что гарантируют барьеры:**

- (4) release barrier: всё, что было **до** Unlock, видно **после** Lock.
- (5) acquire barrier: всё, что было **до** Lock, видно **после** Lock.

**Результат:** B увидит `shared == "hello"`.

### Барьеры в Go

**Go не даёт прямого доступа к барьерам.** Вместо этого используются:

- **`sync/atomic`** — операции с acquire/release семантикой.
- **`sync.Mutex`** — Lock = acquire, Unlock = release.
- **Каналы** — send/receive с acquire/release семантикой.

**Компилятор Go** генерирует нужные барьеры автоматически, когда видит эти операции.

### Пример: atomic с барьерами

```go
var ready atomic.Bool
var data string

// Горутина A:
data = "hello"       // (1)
ready.Store(true)    // (2) release barrier

// Горутина B:
for !ready.Load() {} // (3) acquire barrier
fmt.Println(data)    // (4)
```

**Что гарантирует atomic:**

- `ready.Store(true)` — release barrier: всё, что было **до** Store, видно **после** Load.
- `ready.Load()` — acquire barrier: всё, что было **до** Store, видно **после** Load.

**Результат:** B увидит `data == "hello"`.

### Стоимость барьеров

| Барьер | x86 | ARM | Стоимость |
|:---|:---|:---|:---|
| Full (`MFENCE`) | `MFENCE` | `DMB ISH` | ~20-50 нс |
| Store (`SFENCE`) | `SFENCE` | `DMB ISHST` | ~10-20 нс |
| Load (`LFENCE`) | `LFENCE` | `DMB ISHLD` | ~10-20 нс |
| Acquire | Неявный в `LOCK` | `LDAR` | ~5-10 нс |
| Release | Неявный в `LOCK` | `STLR` | ~5-10 нс |

**Ключевое:** барьеры **дорогие**. Поэтому `atomic` (5-10 нс) дороже обычной записи (1 нс), а `Mutex` (15-25 нс) дороже `atomic`.

### Почему x86 «дешевле»

На x86 модель памяти **TSO** (Total Store Order) — почти последовательная. Большинство переупорядочиваний **запрещены** аппаратно. Поэтому x86 нужны только **некоторые** барьеры (в основном для store-load).

На ARM модель памяти **слабая** — почти все переупорядочивания **разрешены**. Поэтому ARM нужны **все** барьеры.

**Результат:** код с data race на x86 может «работать», а на ARM — падать. **Без барьеров** порядок не гарантирован.

### Аннотация сложности

| Операция | x86 | ARM | Стоимость |
|:---|:---|:---|:---|
| Обычная запись | `MOV` | `STR` | ~1 нс |
| Обычное чтение | `MOV` | `LDR` | ~1 нс |
| `atomic.Store` (release) | `MOV` + `SFENCE` (иногда) | `STLR` | ~5-10 нс |
| `atomic.Load` (acquire) | `MOV` | `LDAR` | ~5-10 нс |
| `atomic.CAS` | `LOCK CMPXCHG` | `CAS` | ~10-20 нс |
| `Mutex.Lock/Unlock` | `LOCK CMPXCHG` | `CAS` + барьеры | ~15-25 нс |

### 💡 Практика: как использовать барьеры

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Используй `atomic` для acquire/release семантики.** Не пытайся вставить барьеры вручную.
2. **Помни: `Mutex` уже вставляет барьеры.** Не нужно дополнительно.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для «флага готовности» — `atomic.Bool`.** Он даёт acquire/release.
4. **Для данных — `Mutex`.** Он даёт полный барьер.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать точные инструкции барьеров** — компилятор Go сгенерирует нужные.

**❌ НЕ ДЕЛАЙ:**

6. **Не пытайся вставить барьеры через `unsafe` или ассемблер.** Это ошибка.
7. **Не полагайся на «x86 и так работает».** Прод может быть на ARM.

### Ключевые выводы подглавы 4.4

- **Барьер памяти** — инструкция, запрещающая переупорядочивание через барьер.
- **Типы:** full, store, load, acquire, release.
- **Acquire** — при захвате ресурса (Lock). **Release** — при освобождении (Unlock).
- **В Go** барьеры вставляются автоматически: `atomic`, `Mutex`, каналы.
- **Стоимость:** ~5-50 нс, зависит от типа и архитектуры.
- **x86** дешевле (TSO), **ARM** дороже (weak).
- **Без барьеров** порядок не гарантирован.

## 4.5 Что устанавливает happens-before в Go

Теперь соберём **полный список** операций, которые устанавливают happens-before в Go.

### Официальный список (из Go Memory Model)

**1. Инициализация пакета:**

- `init()` пакета A happens-before `init()` пакета B, если B импортирует A.

**2. Горутины:**

- `go f()` happens-before начала выполнения `f`.

**3. Каналы:**

- **Отправка** в канал happens-before **получения** из этого канала.
- **Close** канала happens-before **получения** zero-значения (из закрытого канала).
- **Получение** из небуферизованного канала happens-before **завершения отправки**.

**4. Мьютексы:**

- `mu.Unlock()` happens-before `mu.Lock()`, который получает мьютекс после.

**5. WaitGroup:**

- `wg.Done()` happens-before `wg.Wait()`, который возвращается после.

**6. Once:**

- `once.Do(f)` — `f` happens-before возврата из `once.Do`.
- `once.Do(f)` happens-before `once.Do(g)`, если `g` выполняется после.

**7. Atomic:**

- `atomic.Store` happens-before `atomic.Load`, если Load видит Store.
- `atomic.CompareAndSwap` и `atomic.Swap` — аналогично.

**8. Finalizers:**

- `runtime.SetFinalizer` — finalizer happens-before завершения программы.

### Таблица happens-before

| Операция A | Операция B | Happens-before? |
|:---|:---|:---|
| `go f()` | начало `f` | ✅ Да |
| `ch <- v` | `<-ch` (получение v) | ✅ Да |
| `close(ch)` | `<-ch` (zero) | ✅ Да |
| `mu.Unlock()` | `mu.Lock()` (следующий) | ✅ Да |
| `wg.Done()` | `wg.Wait()` (возврат) | ✅ Да |
| `once.Do(f)` | возврат `once.Do` | ✅ Да |
| `atomic.Store` | `atomic.Load` (видит) | ✅ Да |
| Обычная запись | Обычное чтение | ❌ Нет |
| Два обычных чтения | — | ❌ Нет (но и не гонка) |

### Пример: каналы устанавливают happens-before

```go
var data string

// Горутина A:
data = "hello"     // (1)
ch <- struct{}{}   // (2) отправка

// Горутина B:
<-ch               // (3) получение
fmt.Println(data)  // (4)
```

**Что гарантирует канал:**

- (2) happens-before (3) — отправка → получение.
- (1) happens-before (4) — транзитивно.
- **Результат:** B увидит `data == "hello"`.

### Пример: close устанавливает happens-before

```go
var data string

// Горутина A:
data = "hello"  // (1)
close(ch)       // (2) close

// Горутина B:
<-ch            // (3) получение zero (канал закрыт)
fmt.Println(data) // (4)
```

**Что гарантирует close:**

- (2) happens-before (3) — close → получение zero.
- (1) happens-before (4) — транзитивно.
- **Результат:** B увидит `data == "hello"`.

**Важно:** это работает **только** если B получает из **закрытого** канала. Если B получает из **открытого** канала — нет гарантии.

### Пример: atomic устанавливает happens-before

```go
var data string
var ready atomic.Bool

// Горутина A:
data = "hello"      // (1)
ready.Store(true)   // (2) atomic.Store

// Горутина B:
for !ready.Load() {} // (3) atomic.Load
fmt.Println(data)    // (4)
```

**Что гарантирует atomic:**

- (2) happens-before (3) — если Load видит значение Store.
- (1) happens-before (4) — транзитивно.
- **Результат:** B увидит `data == "hello"`.

### Что НЕ устанавливает happens-before

**1. `time.Sleep`:**

```go
// Горутина A:
data = "hello"

// Горутина B:
time.Sleep(1 * time.Second)
fmt.Println(data)  // ← нет гарантии!
```

`time.Sleep` **не** устанавливает happens-before. Даже если B «проспал» секунду, компилятор и процессор **не обязаны** видеть запись A.

**2. `runtime.Gosched`:**

```go
// Горутина A:
data = "hello"
runtime.Gosched()

// Горутина B:
fmt.Println(data)  // ← нет гарантии!
```

`Gosched` **не** устанавливает happens-before. Это только «намёк» планировщику.

**3. Обычная запись/чтение:**

```go
// Горутина A:
data = "hello"

// Горутина B:
fmt.Println(data)  // ← гонка, нет гарантии!
```

Обычные операции **не** устанавливают happens-before между горутинами.

### Аннотация сложности

| Синхронизация | Happens-before | Стоимость |
|:---|:---|:---|
| Канал (send → recv) | ✅ Да | ~50-100 нс |
| Канал (close → recv) | ✅ Да | ~50-100 нс |
| Mutex (Unlock → Lock) | ✅ Да | ~15-25 нс |
| WaitGroup (Done → Wait) | ✅ Да | ~5-10 нс |
| Once (Do → Do) | ✅ Да | ~1-50 нс |
| Atomic (Store → Load) | ✅ Да | ~5-10 нс |
| `time.Sleep` | ❌ Нет | — |
| `runtime.Gosched` | ❌ Нет | — |
| Обычная запись/чтение | ❌ Нет | — |

### 💡 Практика: как использовать happens-before

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для передачи данных — канал или Mutex.** Они устанавливают happens-before.
2. **Для флагов — `atomic.Bool`.** Store/Load устанавливают happens-before.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Помни: `time.Sleep` и `Gosched` не синхронизируют.** Не полагайся на них.
4. **Для «дождаться завершения» — `WaitGroup`.** Done → Wait.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать все детали** — достаточно понимать основные.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `time.Sleep` для «синхронизации».** Это race.
7. **Не полагайся на `Gosched`** для порядка.
8. **Не используй обычные переменные между горутинами** без синхронизации.

### Ключевые выводы подглавы 4.5

- **Happens-before устанавливают:** каналы, `Mutex`, `WaitGroup`, `Once`, `atomic`, `go`.
- **НЕ устанавливают:** `time.Sleep`, `runtime.Gosched`, обычные операции.
- **Канал:** send → recv, close → recv (zero).
- **Mutex:** Unlock → Lock.
- **Atomic:** Store → Load.
- **`time.Sleep` не синхронизирует** — это race.

## 4.6 Atomic: видимость, упорядочивание, CAS

Мы несколько раз упомянули `atomic`. Теперь разберём **что именно** он гарантирует.

### Что гарантирует atomic

**1. Атомарность:**

Операция выполняется **целиком** или **не выполняется вообще**. Нет промежуточных состояний.

```go
var v atomic.Int64
v.Add(1)  // read-modify-write, атомарно
```

**2. Видимость:**

Запись через `atomic.Store` **видна** всем горутинам после `atomic.Load`.

```go
// Горутина A:
v.Store(42)

// Горутина B:
x := v.Load()  // увидит 42 (если Load после Store)
```

**3. Упорядочивание (happens-before):**

`atomic.Store` happens-before `atomic.Load`, если Load видит Store.

```go
// Горутина A:
data = "hello"
v.Store(true)

// Горутина B:
for !v.Load() {}
fmt.Println(data)  // увидит "hello"
```

**4. Acquire/release семантика:**

- `atomic.Store` — **release** барьер: всё, что было **до** Store, видно **после** Load.
- `atomic.Load` — **acquire** барьер: всё, что было **до** Store, видно **после** Load.

### Что НЕ гарантирует atomic

**1. Атомарность нескольких переменных:**

```go
// ❌ Не атомарно вместе:
a.Add(1)
b.Add(1)
```

Между `a.Add` и `b.Add` может произойти что угодно.

**2. Защита структур:**

`atomic` работает с **одной** переменной. Для `map`, `slice` — `Mutex`.

**3. «Быстрый мьютекс»:**

`atomic` не заменяет `Mutex` для сложных операций. «Прочитать, вычислить, записать» — не атомарно.

### CAS: Compare-And-Swap

**CAS** — атомарная операция: «заменить, если текущее значение равно ожидаемому».

```go
var v atomic.Int64
v.Store(10)

swapped := v.CompareAndSwap(10, 20)  // true, если было 10
// v == 20
```

**Алгоритм CAS:**

```
CAS(addr, old, new):
  1. Прочитать *addr.
  2. Если *addr == old:
       *addr = new
       return true
  3. Иначе:
       return false
```

**Всё атомарно** — одна инструкция процессора (`LOCK CMPXCHG` на x86, `CAS` на ARM).

### CAS: паттерн retry loop

CAS используется для **lock-free** алгоритмов. Паттерн:

```go
var v atomic.Int64

func increment() {
    for {
        old := v.Load()
        new := old + 1
        if v.CompareAndSwap(old, new) {
            return  // успех
        }
        // неудача: кто-то изменил v между Load и CAS
        // повторяем
    }
}
```

**Что происходит:**

1. Читаем текущее значение.
2. Вычисляем новое.
3. Пытаемся заменить через CAS.
4. Если не удалось (кто-то изменил) — повторяем.

**Проблема:** при высокой конкуренции CAS может «проваливаться» много раз. Это **дороже**, чем `Mutex`.

### Atomic vs Mutex: когда что

| Аспект | `atomic` | `Mutex` |
|:---|:---|:---|
| Атомарность | Одна переменная | Любая секция |
| Видимость | Да | Да |
| Happens-before | Да (Store → Load) | Да (Unlock → Lock) |
| Стоимость (uncontended) | ~5-10 нс | ~15-25 нс |
| Стоимость (contended) | Растёт (CAS retry) | Растёт (блокировка) |
| Использование | Счётчики, флаги, указатели | Защита структур, сложные операции |

**Правило:** `atomic` — для простых операций. `Mutex` — для сложных.

### Аннотация сложности

| Операция | Атомарность | Видимость | Happens-before | Стоимость |
|:---|:---|:---|:---|:---|
| `atomic.Add` | ✅ | ✅ | ✅ | ~5-10 нс |
| `atomic.Load` | ✅ | ✅ | ✅ | ~1-2 нс |
| `atomic.Store` | ✅ | ✅ | ✅ | ~1-2 нс |
| `atomic.CAS` | ✅ | ✅ | ✅ | ~5-15 нс |
| `Mutex.Lock/Unlock` | ✅ | ✅ | ✅ | ~15-25 нс |

### 💡 Практика: как использовать atomic

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков — `atomic.Int64`.** Быстрее `Mutex`.
2. **Для флагов — `atomic.Bool`.** Даёт acquire/release.
3. **Для указателей — `atomic.Pointer[T]`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Новый API (Go 1.19+):** `atomic.Int64`, а не `atomic.AddInt64(&v, 1)`.
5. **CAS retry loop** — только для lock-free структур, и если понимаешь.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **`atomic.Value`** — для произвольных типов (устарел, используй `atomic.Pointer[T]`).

**❌ НЕ ДЕЛАЙ:**

7. **Не используй `atomic` для нескольких переменных.** Только одна.
8. **Не используй `atomic` для сложных операций.** «Прочитать, вычислить, записать» — не атомарно.
9. **Не используй `atomic` для защиты map/slice.** Нужен `Mutex`.

### Ключевые выводы подглавы 4.6

- **`atomic` гарантирует:** атомарность, видимость, happens-before, acquire/release.
- **CAS** — атомарная «замена, если равно». Основа lock-free.
- **CAS retry loop** — при конкуренции может быть дороже `Mutex`.
- **`atomic` — для одной переменной.** `Mutex` — для секции.
- **`atomic` быстрее `Mutex`** в 2-3 раза для простых операций.

## 4.7 Race detector: как он работает

**Race detector** — инструмент, который находит data race во время выполнения.

### Как запустить

```bash
# Тесты:
go test -race ./...

# Программа:
go run -race main.go

# Бинарник:
go build -race -o myapp
./myapp
```

### Как работает

**Race detector** использует **алгоритм Vector Clock** (векторные часы) из **ThreadSanitizer** (TSan).

**Идея:**

- Для каждой переменной хранится **история доступов**.
- Для каждой горутины хранится **вектор часов** — какие операции других горутин она «видела».
- При каждом доступе проверяется: есть ли **параллельный** доступ без синхронизации?

**Упрощённо:**

```
Для каждой переменной v:
  last_write: (goroutine_id, clock)
  last_read: список (goroutine_id, clock)

При записи в v из горутины G:
  Если last_write или last_read содержит другую горутину,
  чьи часы НЕ предшествуют часам G:
    → RACE!
  Обновить last_write = (G, clock)

При чтении из v из горутины G:
  Если last_write содержит другую горутину,
  чьи часы НЕ предшествуют часам G:
    → RACE!
  Добавить (G, clock) в last_read
```

### Пример вывода

```go
package main

import "time"

var counter int

func main() {
    go func() {
        for i := 0; i < 1000; i++ {
            counter++
        }
    }()
    go func() {
        for i := 0; i < 1000; i++ {
            counter++
        }
    }()
    time.Sleep(1 * time.Second)
}
```

**Запуск:**

```bash
go run -race main.go
```

**Вывод:**

```
==================
WARNING: DATA RACE
Write at 0x0000005f8a50 by goroutine 7:
  main.main.func1()
      /path/to/main.go:9 +0x...

Previous write at 0x0000005f8a50 by goroutine 6:
  main.main.func2()
      /path/to/main.go:14 +0x...

Goroutine 7 (running) created at:
  main.main()
      /path/to/main.go:8 +0x...

Goroutine 6 (running) created at:
  main.main()
      /path/to/main.go:13 +0x...
==================
Found 1 data race(s)
```

**Что видно:**

- **Адрес** (`0x0000005f8a50`) — где находится переменная.
- **Две горутины** (`goroutine 7`, `goroutine 6`) — обе пишут.
- **Строки** (`main.go:9`, `main.go:14`) — где именно.
- **Создание горутин** — где они запущены.

### Ограничения race detector

**1. Не находит все гонки.**

Race detector находит гонки, которые **произошли** во время выполнения. Если гонка не «выстрелила» — detector её не увидит.

**2. Замедляет выполнение.**

Программа с `-race` работает **в 5-20 раз медленнее** и потребляет **в 5-10 раз больше памяти**.

**3. Не работает в production.**

Из-за замедления race detector используется **только в тестах** и **при отладке**.

**4. Ложные срабатывания.**

Иногда detector сообщает о гонке, которой нет (например, при использовании `unsafe` или ассемблера).

### Как race detector связан с happens-before

Race detector **отслеживает happens-before**. Если две операции **не связаны** happens-before — это гонка.

**Пример:**

```go
var data int
var mu sync.Mutex

// Горутина A:
mu.Lock()
data = 42
mu.Unlock()

// Горутина B:
mu.Lock()
x := data
mu.Unlock()
```

**Race detector:** не найдёт гонку. Потому что `Unlock` → `Lock` устанавливает happens-before.

**Без Mutex:**

```go
var data int

// Горутина A:
data = 42

// Горутина B:
x := data
```

**Race detector:** найдёт гонку. Потому что нет happens-before.

### Аннотация сложности

| Аспект | Значение |
|:---|:---|
| Замедление | 5-20x |
| Потребление памяти | 5-10x |
| Находит все гонки? | ❌ Нет |
| Работает в production? | ❌ Нет |
| Ложные срабатывания? | Иногда |

### 💡 Практика: как использовать race detector

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Запускай `go test -race ./...` в CI.** Это ловит гонки на ранней стадии.
2. **Запускай `go run -race` при отладке** странных багов.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Пиши тесты, которые создают конкуренцию.** Race detector найдёт гонки только в выполненных сценариях.
4. **Используй `-race` в stress-тестах.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Запускать `-race` постоянно** — замедление слишком велико.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `-race` в production.** Замедление 5-20x.
7. **Не полагайся только на race detector.** Он не находит все гонки.
8. **Не игнорируй предупреждения.** «Иногда» — это всегда «когда-нибудь в проде».

### Ключевые выводы подглавы 4.7

- **Race detector** — инструмент для поиска data race.
- **Запуск:** `go test -race`, `go run -race`.
- **Алгоритм:** Vector Clock (ThreadSanitizer).
- **Находит гонки, которые произошли.** Не все.
- **Замедляет в 5-20 раз.** Только для тестов.
- **Не работает в production.**

## 4.8 x86 vs ARM: почему гонка «не проявляется» на одном и «падает» на другом

Это ключевая подглава, которая объясняет, **почему** data race опасен, даже если «работает».

### Модели памяти

**x86 (TSO — Total Store Order):**

- **Порядок store-store сохраняется.** Запись A → Запись B: B не может обогнать A.
- **Порядок load-load сохраняется.**
- **Порядок load-store сохраняется.**
- **Store-load может быть переупорядочен.** Запись A → Чтение B: B может обогнать A.

**ARM (weak memory model):**

- **Все типы переупорядочивания разрешены.** Store-store, load-load, load-store, store-load.

### Почему x86 «маскирует» гонки

**Пример:**

```go
var data string
var ready bool

// Горутина A:
data = "hello"
ready = true

// Горутина B:
for !ready {}
fmt.Println(data)
```

**На x86:**

- `data = "hello"` → `ready = true`: порядок **сохраняется** (TSO).
- B видит `ready == true` **только после** того, как `data = "hello"` попало в кэш.
- **Результат:** B видит `data == "hello"`. **Работает.**

**На ARM:**

- `data = "hello"` → `ready = true`: порядок **может быть нарушен** (weak).
- B может увидеть `ready == true` **до** того, как `data = "hello"` попало в кэш.
- **Результат:** B видит `data == ""`. **Падает.**

### Почему компилятор тоже важен

**Даже на x86** компилятор может переставить операции:

```go
data = "hello"
ready = true
```

Компилятор может решить: `ready = true` не зависит от `data`, можно переставить. **Тогда даже на x86** B увидит `ready == true`, но `data == ""`.

**Что спасает:** компилятор Go **не переставляет** записи в глобальные переменные **без причины**. Но если переменная локальная или есть оптимизация — может.

### Пример: busy loop на x86 vs ARM

```go
var ready bool

// Горутина A:
ready = true

// Горутина B:
for !ready {}
```

**На x86:**

- Компилятор может закешировать `ready` в регистре: `for !ready` → бесконечный цикл.
- **Даже на x86** это **может** зациклиться.

**На ARM:**

- Та же проблема + переупорядочивание.
- **Почти всегда** зацикливается.

**Решение:** `atomic.Bool`:

```go
var ready atomic.Bool

// Горутина A:
ready.Store(true)

// Горутина B:
for !ready.Load() {}
```

**Почему работает:** `atomic.Load` — acquire барьер, компилятор **не может** закешировать значение. Каждая итерация — реальное чтение из памяти.

### Почему разработчики попадают в ловушку

**1. Разработка на x86.**

Большинство разработчиков работают на x86 (Intel, AMD). Гонки «не проявляются».

**2. Прод на ARM.**

AWS Graviton, Apple M1/M2, мобильные устройства — ARM. Гонки **проявляются**.

**3. «Работает у меня» — не аргумент.**

Код с data race **не является корректной Go-программой**. То, что он «работает» на x86 — случайность.

### Как проверить

**1. Запускай на ARM.**

Если есть доступ к ARM-машине (Graviton, M1) — запусти там.

**2. Используй `-race`.**

Race detector найдёт гонку, даже если она «не проявляется».

**3. Используй `GOARCH=arm64`.**

Кросс-компиляция не поможет найти гонку, но покажет, что код компилируется.

**4. Читай код.**

Если есть разделяемая переменная без синхронизации — это гонка.

### Аннотация сложности

| Архитектура | Store-store | Load-load | Load-store | Store-load | Гонка проявляется? |
|:---|:---|:---|:---|:---|:---|
| x86 (TSO) | ❌ Нет | ❌ Нет | ❌ Нет | ✅ Да | Реже |
| ARM (weak) | ✅ Да | ✅ Да | ✅ Да | ✅ Да | Чаще |
| RISC-V (weak) | ✅ Да | ✅ Да | ✅ Да | ✅ Да | Чаще |

### 💡 Практика: как не попасть на x86 vs ARM

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: x86 маскирует гонки.** Не полагайся на «работает у меня».
2. **Тестируй на ARM** (Graviton, M1) или используй `-race`.

**👍 СТОИТ СДЕЛАТЬ:**

3. **CI на ARM** — если прод на ARM.
4. **`go test -race`** — обязательно в CI.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Знать точные модели памяти** — достаточно понимать, что ARM слабее.

**❌ НЕ ДЕЛАЙ:**

6. **Не полагайся на x86-поведение.** Прод может быть на ARM.
7. **Не игнорируй race detector.** «Не проявляется» — не значит «нет гонки».

### Ключевые выводы подглавы 4.8

- **x86 (TSO)** — сохраняет порядок store-store, load-load, load-store.
- **ARM (weak)** — разрешает все переупорядочивания.
- **x86 маскирует гонки** — код «работает», но не корректен.
- **ARM проявляет гонки** — код падает.
- **Компилятор тоже переставляет** — даже на x86.
- **Race detector** находит гонки, даже если они «не проявляются».
- **Тестируй на ARM** или используй `-race`.

## 4.9 Модель памяти Go vs C++ vs Java

Go — не первый язык с моделью памяти. Сравним с C++ и Java.

### C++ Memory Model (C++11)

**C++11** ввёл формальную модель памяти. Ключевые концепции:

- **Happens-before** — аналогично Go.
- **Data race** — undefined behavior.
- **`std::atomic`** — атомарные операции с настраиваемой семантикой:
  - `memory_order_relaxed` — без барьеров.
  - `memory_order_acquire` — acquire.
  - `memory_order_release` — release.
  - `memory_order_acq_rel` — acquire + release.
  - `memory_order_seq_cst` — полный барьер (по умолчанию).

**Отличие от Go:** C++ даёт **больше контроля** (memory_order), но **больше ответственности**.

### Java Memory Model (JMM)

**Java** имеет модель памяти с **happens-before** (JSR-133, 2004).

- **`volatile`** — acquire/release семантика.
- **`synchronized`** — полный барьер.
- **`java.util.concurrent.atomic`** — атомарные операции.

**Отличие от Go:**

- Java `volatile` похож на Go `atomic`.
- Java `synchronized` похож на Go `Mutex`.
- Java НЕ даёт выбора memory_order — только acquire/release.

### Go Memory Model

**Go** имеет модель памяти, **похожую на C++ и Java**, но **проще**:

- **Happens-before** — аналогично.
- **Data race** — undefined behavior.
- **`sync/atomic`** — acquire/release семантика (без выбора memory_order).
- **`sync.Mutex`, каналы** — полный барьер.

**Отличие от C++:** Go **не даёт** выбора memory_order. Все atomic-операции — acquire/release.

**Отличие от Java:** Go `atomic` — аналог Java `volatile` + `AtomicInteger`.

### Сравнительная таблица

| Аспект | Go | C++ | Java |
|:---|:---|:---|:---|
| Happens-before | ✅ | ✅ | ✅ |
| Data race = UB | ✅ | ✅ | ✅ |
| Atomic | ✅ `sync/atomic` | ✅ `std::atomic` | ✅ `java.util.concurrent.atomic` |
| Выбор memory_order | ❌ | ✅ | ❌ |
| Мьютекс | `sync.Mutex` | `std::mutex` | `synchronized` |
| Acquire/release | ✅ | ✅ | ✅ |
| Полный барьер | ✅ | ✅ | ✅ |

### Почему Go проще

**Go не даёт выбора memory_order.** Все atomic-операции — acquire/release.

**Почему:**

- **Простота.** Меньше шансов ошибиться.
- **Достаточно для 99% задач.** Acquire/release покрывает почти все случаи.
- **Relaxed** — редко нужен, и его легко сделать неправильно.
- **Seq_cst** — избыточен для большинства задач.

**Результат:** Go-программист **не думает** о memory_order. Он использует `atomic` и получает acquire/release.

### Аннотация сложности

| Аспект | Go | C++ | Java |
|:---|:---|:---|:---|
| Сложность модели | Средняя | Высокая | Средняя |
| Контроль | Средний | Высокий | Средний |
| Шанс ошибки | Низкий | Высокий | Средний |

### 💡 Практика: что важно знать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Используй `sync/atomic` для acquire/release.** Не пытайся контролировать memory_order.
2. **Помни: Go проще C++.** Меньше шансов ошибиться.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Читай Go Memory Model** — там полный список happens-before.
4. **Если пришёл из C++** — забудь про `memory_order`. В Go его нет.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Сравнивать с Java** — если знаешь Java, аналогии помогут.

**❌ НЕ ДЕЛАЙ:**

6. **Не пытайся эмулировать `memory_order_relaxed`.** В Go его нет.
7. **Не полагайся на C++-паттерны** без адаптации.

### Ключевые выводы подглавы 4.9

- **Go Memory Model** — похожа на C++ и Java, но **проще**.
- **Happens-before, data race = UB** — как в C++ и Java.
- **`sync/atomic`** — acquire/release, без выбора memory_order.
- **Простота Go** — меньше шансов ошибиться.
- **Из C++:** забудь про `memory_order`.
- **Из Java:** `atomic` ≈ `volatile` + `AtomicInteger`.

## 4.10 Практика Go: ловим гонки и переупорядочивание

Теперь напишем **утилиту на Go**, которая:

1. **Демонстрирует data race** — и как его находит race detector.
2. **Демонстрирует переупорядочивание** — как компилятор и процессор могут переставить операции.
3. **Показывает разницу x86 vs ARM** — насколько возможно.
4. **Показывает, как atomic решает проблему.**

### Утилита 1: data race

```go
package main

import (
    "fmt"
    "sync"
)

var counter int

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++  // data race
        }()
    }
    wg.Wait()
    fmt.Println("counter:", counter)
}
```

**Запуск без `-race`:**

```bash
go run main.go
# counter: 987 (или другое число, не 1000)
```

**Запуск с `-race`:**

```bash
go run -race main.go
# WARNING: DATA RACE
# ...
# Found 1 data race(s)
```

**Что видно:** race detector находит гонку, которую без него не видно.

### Утилита 2: переупорядочивание через atomic

```go
package main

import (
    "fmt"
    "sync/atomic"
    "time"
)

var data string
var ready atomic.Bool

func producer() {
    data = "hello"
    ready.Store(true)  // release barrier
}

func consumer() {
    for !ready.Load() {  // acquire barrier
        // spin
    }
    fmt.Println("data:", data)
}

func main() {
    go producer()
    go consumer()
    time.Sleep(100 * time.Millisecond)
}
```

**Что демонстрирует:** `atomic.Store`/`Load` устанавливают happens-before. `data` видна после `ready.Load()`.

**Без atomic:**

```go
var ready bool

func producer() {
    data = "hello"
    ready = true
}

func consumer() {
    for !ready {}
    fmt.Println("data:", data)  // может быть пусто
}
```

**На x86** — часто работает. **На ARM** — часто падает. **С `-race`** — гонка найдена.

### Утилита 3: compare-and-swap retry loop

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

var counter atomic.Int64

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                old := counter.Load()
                new := old + 1
                if counter.CompareAndSwap(old, new) {
                    return
                }
            }
        }()
    }
    wg.Wait()
    fmt.Println("counter:", counter.Load())
}
```

**Что демонстрирует:** CAS retry loop. Без гонки, счётчик корректен.

### Утилита 4: сравнение atomic vs Mutex

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

const N = 10_000_000

func benchAtomic() time.Duration {
    var counter atomic.Int64
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                counter.Add(1)
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}

func benchMutex() time.Duration {
    var mu sync.Mutex
    var counter int
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}

func main() {
    fmt.Printf("atomic: %v\n", benchAtomic())
    fmt.Printf("Mutex:  %v\n", benchMutex())
}
```

**Пример вывода:**

```
atomic: 85ms
Mutex:  450ms
```

**Что видно:** `atomic` в 5 раз быстрее `Mutex` для счётчика.

### Утилита 5: демонстрация гонки через `go test -race`

```go
// race_test.go
package main

import (
    "sync"
    "testing"
)

func TestRace(t *testing.T) {
    var counter int
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++  // data race
        }()
    }
    wg.Wait()
    if counter != 100 {
        t.Errorf("expected 100, got %d", counter)
    }
}
```

**Запуск:**

```bash
go test -race ./...
```

**Вывод:**

```
==================
WARNING: DATA RACE
...
==================
--- FAIL: TestRace (0.00s)
```

**Что видно:** тест падает с `-race`, даже если без `-race` проходит.

| `go test -race` | 5-20x медленнее | 5-10x больше | CI |

### 💡 Практика: как использовать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`go test -race ./...` в CI.** Это ловит гонки на ранней стадии.
2. **`go run -race` при отладке** странных багов.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Тесты, которые создают конкуренцию.** Race detector найдёт гонки только в выполненных сценариях.
4. **Stress-тесты с `-race`.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Бенчмарки `atomic` vs `Mutex`** — полезно для выбора.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй `-race` в production.** Замедление 5-20x.
7. **Не игнорируй предупреждения race detector.**
8. **Не полагайся только на `-race`.** Он не находит все гонки.

### Ключевые выводы подглавы 4.10

## 4.11 Выводы и типичные ошибки

**Что мы узнали?**

Data race — это ситуация, когда две горутины обращаются к одной переменной, хотя бы одна пишет, без синхронизации. Это **undefined behavior** по спецификации Go. Happens-before — фундамент: если A → B, эффекты A видны B. Внутри горутины — естественный порядок. Между горутинами — только через синхронизацию. Компилятор и процессор могут переупорядочивать операции: x86 (TSO) сохраняет порядок store-store, ARM (weak) — нет. Барьеры памяти запрещают переупорядочивание. Синхронизация (`Mutex`, каналы, `atomic`, `WaitGroup`, `Once`) устанавливает happens-before. `atomic` гарантирует атомарность, видимость, acquire/release. Race detector находит гонки, но не все; замедляет в 5-20 раз. x86 маскирует гонки, ARM проявляет. Модель памяти Go похожа на C++ и Java, но проще (нет выбора memory_order).

**Типичные ошибки:**

- ❌ **Полагать, что «работает на моём ноутбуке» = «корректно».** x86 маскирует гонки. ARM проявляет.
- ❌ **Использовать `bool` для флага «готовности».** Компилятор может закешировать в регистре.
- ❌ **Использовать `time.Sleep` для «синхронизации».** `time.Sleep` не устанавливает happens-before.
- ❌ **Использовать `runtime.Gosched` для порядка.** `Gosched` не устанавливает happens-before.
- ❌ **Полагать, что «порядок в коде» сохранится между горутинами.** Компилятор и процессор могут переставить.
- ❌ **Игнорировать race detector.** «Не проявляется» — не значит «нет гонки».
- ❌ **Использовать `-race` в production.** Замедление 5-20x.
- ❌ **Пытаться эмулировать `memory_order_relaxed`.** В Go его нет.
- ❌ **Использовать `atomic` для нескольких переменных.** Только одна.
- ❌ **Полагать, что `atomic` — «быстрый мьютекс».** Атомарность одной переменной ≠ защита секции.
- ❌ **Не запускать `go test -race` в CI.** Гонки попадут в прод.
- ❌ **Использовать `sync.Mutex` для флага.** Для флага — `atomic.Bool`.

## 4.12 Для быстрого повторения

- **Data race** — две горутины, одна переменная, хотя бы одна пишет, без синхронизации. **Undefined behavior.**
- **Read-read — не гонка.** Write-read и write-write — гонка.
- **Happens-before** — отношение порядка. Если A → B, эффекты A видны B.
- **Внутри горутины** — естественный порядок. **Между горутинами** — только через синхронизацию.
- **Happens-before устанавливают:** `go`, каналы (send → recv, close → recv), `Mutex` (Unlock → Lock), `WaitGroup` (Done → Wait), `Once` (Do → Do), `atomic` (Store → Load).
- **НЕ устанавливают:** `time.Sleep`, `runtime.Gosched`, обычные операции.
- **Переупорядочивание** — компилятор и процессор могут переставлять операции.
- **x86 (TSO)** — сохраняет порядок store-store, load-load, load-store. **ARM (weak)** — разрешает все.
- **Барьеры памяти** — запрещают переупорядочивание. **Acquire** — при захвате, **release** — при освобождении.
- **`atomic`** гарантирует: атомарность, видимость, happens-before, acquire/release.
- **CAS** — атомарная «замена, если равно». Основа lock-free.
- **Race detector** — `go test -race`, `go run -race`. Замедляет в 5-20 раз. Не находит все гонки.
- **x86 маскирует гонки**, ARM проявляет. Тестируй на ARM или используй `-race`.
- **Go Memory Model** — похожа на C++ и Java, но проще (нет выбора memory_order).
- **Правило:** любая разделяемая память — под синхронизацией. `atomic` для флагов, `Mutex` для секций, каналы для передачи.

## 4.14 Ответы

### Ответ 1

**Data race** — две горутины, одна переменная, хотя бы одна пишет, без синхронизации.

**Гонка есть:**
1. `data = 42` в одной горутине, `x := data` в другой (write-read).
2. `data = 42` в одной, `data = 100` в другой (write-write).
3. `data = "hello"; ready = true` в одной, `for !ready {}; fmt.Println(data)` в другой (два race).

**Гонки нет:**
1. `x := data` в одной, `y := data` в другой (read-read).
2. `mu.Lock(); data = 42; mu.Unlock()` в одной, `mu.Lock(); x := data; mu.Unlock()` в другой (под мьютексом).
3. `atomic.Store(42)` в одной, `atomic.Load()` в другой (atomic).

### Ответ 2

**Happens-before** — отношение порядка. Если A → B, эффекты A видны B.

**Устанавливают:**
1. `go f()` → начало `f`.
2. `ch <- v` → `<-ch` (получение v).
3. `mu.Unlock()` → `mu.Lock()` (следующий).

**НЕ устанавливают:**
1. `time.Sleep`.
2. `runtime.Gosched`.
3. Обычная запись → обычное чтение.

### Ответ 3

**`time.Sleep` не синхронизирует**, потому что не устанавливает happens-before. Даже если B «проспал» секунду, компилятор и процессор не обязаны видеть запись A.

**Что использовать:** `atomic.Bool`, `Mutex`, канал.

### Ответ 4

**Компилятор может переупорядочить** `data = "hello"` и `ready = true`, потому что они не зависят друг от друга **в рамках одной горутины**. Компилятор оптимизирует **локально** и не знает о других горутинах.

**Разрешено:** спецификация Go не требует сохранения порядка между независимыми операциями, если нет синхронизации.

### Ответ 5

**x86 (TSO):**
- Store-store: ❌ Нет (порядок сохраняется).
- Load-load: ❌ Нет.
- Load-store: ❌ Нет.
- Store-load: ✅ Да (может переупорядочиться).

**ARM (weak):**
- Все типы: ✅ Да.

### Ответ 6

**Барьер памяти** — инструкция процессора, запрещающая переупорядочивание операций через барьер.

**Acquire** — при захвате ресурса. Запрещает переупорядочивание операций **после** барьера с операциями **до** барьера. Используется в `Lock`.

**Release** — при освобождении. Запрещает переупорядочивание операций **до** барьера с операциями **после** барьера. Используется в `Unlock`.

### Ответ 7

**`atomic.Store`** — release барьер: всё, что было **до** Store, видно **после** Load.

**`atomic.Load`** — acquire барьер: всё, что было **до** Store, видно **после** Load.

**Связь с happens-before:** Store → Load, если Load видит Store. Транзитивно: всё до Store видно после Load.

### Ответ 8

**Race detector** использует Vector Clock. Для каждой переменной хранится история доступов; для каждой горутины — вектор часов. При доступе проверяется, есть ли параллельный доступ без синхронизации.

**Не находит все гонки**, потому что находит только те, которые **произошли** во время выполнения. Если гонка не «выстрелила» — detector её не увидит.

### Ответ 9

**x86 (TSO)** сохраняет порядок store-store. Поэтому `data = "hello"; ready = true` выполняется в порядке. B видит `ready == true` после того, как `data` попала в кэш.

**ARM (weak)** разрешает переупорядочивание store-store. B может увидеть `ready == true` до того, как `data` попала в кэш. Результат: `data == ""`.

### Ответ 10

**Отличие от C++:** Go **не даёт** выбора memory_order. Все atomic-операции — acquire/release.

**Отличие от Java:** Go `atomic` ≈ Java `volatile` + `AtomicInteger`. Java `synchronized` ≈ Go `Mutex`.

**Общее:** happens-before, data race = UB.

### Ответ 11

**`for !ready {}`** может зациклиться, потому что **компилятор** может закешировать `ready` в регистре. Компилятор не знает, что `ready` меняется другой горутиной, и оптимизирует цикл в `for !cached_ready`.

**Даже на x86** это возможно. **Решение:** `atomic.Bool` — `atomic.Load` запрещает кеширование.

### Ответ 12

**CAS (Compare-And-Swap)** — атомарная «замена, если равно».

**Lock-free инкремент:**

```go
for {
    old := counter.Load()
    new := old + 1
    if counter.CompareAndSwap(old, new) {
        return
    }
}
```

Читаем, вычисляем, пытаемся заменить. Если не удалось — повторяем.

### Ответ 13

**`atomic` не заменяет `Mutex` для нескольких переменных**, потому что:
- `atomic` работает с **одной** переменной.
- `a.Add(1); b.Add(1)` — не атомарно вместе.
- Между ними может произойти что угодно.

**Для нескольких переменных — `Mutex`.**

### Ответ 14

**`bool` для флага между горутинами** — data race. Компилятор может закешировать, процессор может переупорядочить. Результат: consumer может никогда не увидеть `ready == true`, или увидеть, но не увидеть данные.

**Решение:** `atomic.Bool`.

### Ответ 15

**Проверить:**
1. `go test -race ./...` — race detector.
2. `go run -race main.go` — для программы.
3. Читать код: любая разделяемая память без синхронизации — гонка.
4. Тестировать на ARM.

### Ответ 16

**Race detector не используется в production**, потому что:
- Замедляет в 5-20 раз.
- Потребляет в 5-10 раз больше памяти.
- Не находит все гонки.
- Ложные срабатывания.

**Используется:** в тестах и при отладке.

### Ответ 17

**Acquire/release семантика:**

- **Acquire** — при захвате ресурса. Запрещает переупорядочивание операций после барьера с операциями до.
- **Release** — при освобождении. Запрещает переупорядочивание операций до барьера с операциями после.

**Пример:** `atomic.Store` — release, `atomic.Load` — acquire. `Mutex.Lock` — acquire, `Mutex.Unlock` — release.

### Ответ 18

**Go не даёт выбора memory_order**, потому что:
- **Простота.** Меньше шансов ошибиться.
- **Достаточно для 99% задач.** Acquire/release покрывает почти все.
- **Relaxed** редко нужен, легко сделать неправильно.
- **Seq_cst** избыточен.

**Результат:** Go-программист не думает о memory_order.

🔐 **Ключевая идея:** Data race — это **undefined behavior** по спецификации Go. Happens-before — фундамент синхронизации: если A → B, эффекты A видны B. Компилятор и процессор переупорядочивают операции; x86 (TSO) сохраняет порядок store-store, ARM (weak) — нет. Барьеры памяти запрещают переупорядочивание; acquire при захвате, release при освобождении. Синхронизация (`Mutex`, каналы, `atomic`, `WaitGroup`, `Once`) устанавливает happens-before. `atomic` гарантирует атомарность, видимость, acquire/release. Race detector находит гонки, но не все; замедляет в 5-20 раз. x86 маскирует гонки, ARM проявляет. Код с data race не является корректной Go-программой — даже если «работает». `time.Sleep` и `Gosched` не синхронизируют. `bool` для флага — гонка; используй `atomic.Bool`.
