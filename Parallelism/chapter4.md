## 4.0 Пролог: счётчик, который врёт

Ты пишешь сервис с метриками. Есть счётчик запросов, который увеличивается в каждом HTTP-хэндлере:

```go
var requestCount int

func handler(w http.ResponseWriter, r *http.Request) {
    requestCount++  // ← что здесь не так?
    fmt.Fprintf(w, "requests: %d\n", requestCount)
}
```

Запускаешь. Делаешь 1000 запросов. Ожидаешь увидеть 1000, но видишь 987. Или 963. Или 1000 — но не всегда.

❓ **Почему счётчик врёт?** Потому что `requestCount++` — **не атомарная операция**. Это три действия:

1. Прочитать значение из памяти в регистр.
2. Увеличить значение на 1.
3. Записать обратно в память.

Если две горутины выполняют это одновременно:

```
Горутина A: читает requestCount = 42
Горутина B: читает requestCount = 42
Горутина A: увеличивает до 43
Горутина B: увеличивает до 43
Горутина A: записывает 43
Горутина B: записывает 43   ← ОБА записали 43, но должно быть 44!
```

Это **data race** — undefined behavior. Результат непредсказуем.

💡 **Три способа исправить:**

```go
// 1. Mutex
var (
    mu           sync.Mutex
    requestCount int
)
func increment() {
    mu.Lock()
    requestCount++
    mu.Unlock()
}

// 2. atomic
var requestCount atomic.Int64
func increment() {
    requestCount.Add(1)
}

// 3. Канал (не идиоматично для счётчика)
var countCh = make(chan int, 1)
func increment() {
    countCh <- 1
}
```

Каждый способ имеет свою нишу. Чтобы **осознанно** выбирать, нужно понимать, **как они устроены** и **сколько стоят**.

> **Мост к следующим главам:** `Mutex` — основа для `RWMutex`, `WaitGroup`, `Once`. Понимание `Mutex` даёт понимание всей синхронизации в Go.

## 4.1 Когда каналы не подходят

Прежде чем разбирать `Mutex`, поймём: **почему каналы — не всегда правильный инструмент**.

### Философия Go

Известная цитата:

> Do not communicate by sharing memory; instead, share memory by communicating.

Перевод: «Не общайтесь через разделяемую память; вместо этого разделяйте память через общение».

**Что это значит:**

- **Плохо:** две горутины имеют доступ к одной переменной и меняют её через мьютекс.
- **Хорошо:** одна горутина владеет переменной, а другие передают ей данные через канал.

Но это **не догма**. Каналы — не всегда лучший выбор.

### Когда каналы не подходят

**1. Счётчики и флаги.**

```go
// ❌ Плохо: канал для счётчика
ch := make(chan int)
go func() { count++ }()

// ✅ Хорошо: atomic
var count atomic.Int64
count.Add(1)
```

**2. Защита структуры данных.**

```go
// ❌ Плохо: канал для map
type SafeMap struct {
    ch chan func(map[string]int)
}

// ✅ Хорошо: Mutex
type SafeMap struct {
    mu sync.Mutex
    m  map[string]int
}
```

**3. Ленивая инициализация.**

```go
// ✅ sync.Once
var once sync.Once
once.Do(initFunc)
```

**4. Ожидание группы горутин.**

```go
// ✅ sync.WaitGroup
var wg sync.WaitGroup
wg.Add(1)
go func() { defer wg.Done(); ... }()
wg.Wait()
```

**5. Высокочастотные операции.**

```go
// ✅ atomic
metricsCounter.Add(1)
```

### Сравнительная таблица

| Задача | Инструмент |
|:---|:---|
| Счётчик, флаг | `atomic` |
| Защита map/slice | `Mutex` или `RWMutex` |
| Много читателей, мало писателей | `RWMutex` |
| Ожидание группы горутин | `WaitGroup` |
| Инициализация один раз | `Once` |
| Передача владения | Канал |
| Потоковая обработка | Канал |

### 💡 Практика: как выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков — `atomic`.**
2. **Для защиты map/slice — `Mutex` или `RWMutex`.**
3. **Для передачи владения — канал.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для read-heavy — `RWMutex`.** Но бенчмаркай.

**❌ НЕ ДЕЛАЙ:**

5. **Не используй канал для счётчика.** Медленнее и сложнее.
6. **Не используй `Mutex` для ожидания горутин** — есть `WaitGroup`.

## 4.2 sync.Mutex: как устроен

Разберём внутреннее устройство `Mutex`.

### Структура Mutex

```go
type Mutex struct {
    state int32   // состояние: locked, woken, starving
    sema  uint32  // ключ для поиска в semaRoot
}
```

**Размер — 8 байт.** Два 32-битных поля.

### Поле state

`state` — это **битовая маска**:

```
state (32 бита):
┌────────────────────────────────────────────────────┐
│ 31               3 2 1 0                            │
│ ┌─────────────┬───┬───┬───┐                        │
│ │  waiters    │ S │ W │ L │                        │
│ │  (29 бит)   │   │   │   │                        │
│ └─────────────┴───┴───┴───┘                        │
│                                                    │
│  L (bit 0) = mutexLocked    — мьютекс захвачен     │
│  W (bit 1) = mutexWoken     — горутина разбужена   │
│  S (bit 2) = mutexStarving  — режим голодания      │
│  waiters (bits 3-31)        — число ждущих горутин │
└────────────────────────────────────────────────────┘
```

**`mutexLocked`** — 1, если мьютекс захвачен.
**`mutexWoken`** — 1, если runtime разбудил одну из ждущих горутин.
**`mutexStarving`** — 1, если мьютекс в режиме голодания.
**`waiters`** — число горутин, ждущих в `Lock()`.

### Поле sema

`sema` — это **не счётчик**, а **ключ** (адрес) для поиска в глобальной таблице `semaRoot`. Ждущие горутины хранятся **вне** мьютекса.

**Почему:** семафоров в программе может быть миллионы (каждый `Mutex`, `WaitGroup`, канал). Держать для каждого полноценную структуру — расточительно. Вместо этого — глобальная таблица, индексированная по адресу.

Подробно — в 4.4.

### Почему 8 байт важно

`Mutex` занимает **8 байт**. Можно встроить в структуру без накладных расходов. Но **нельзя копировать** — копия создаёт второй, независимый мьютекс.

```go
// ❌ Плохо: копирование
func (c Counter) Inc() {  // ← c копируется!
    c.mu.Lock()
    c.n++
    c.mu.Unlock()
}

// ✅ Хорошо: указатель
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
```

**`go vet`** обнаруживает копирование мьютексов. Запускай `go vet ./...`.

### Схема Mutex

```
┌─────────────────────────────────────────────────────────┐
│                    sync.Mutex                            │
│                                                          │
│  state (int32):                                          │
│  ┌────────────────────────────────────────────────────┐ │
│  │ waiters (29) │ S │ W │ L │                        │ │
│  └────────────────────────────────────────────────────┘ │
│   waiters=0     │   │   │                              │
│                 │   │   └── L = 0 (не захвачен)         │
│                 │   └────── W = 0 (никого не разбудили) │
│                 └────────── S = 0 (не голодает)         │
│                                                          │
│  sema (uint32): 0  ← ключ для поиска в semaRoot         │
│                                                          │
│  Размер: 8 байт                                          │
└─────────────────────────────────────────────────────────┘
```

### 💡 Практика: как использовать Mutex

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Mutex` — поле структуры, не копируй:**
   ```go
   type SafeCounter struct {
       mu sync.Mutex
       n  int
   }
   
   func (c *SafeCounter) Inc() {  // указатель!
       c.mu.Lock()
       defer c.mu.Unlock()
       c.n++
   }
   ```

2. **Запускай `go vet ./...`** — он ловит копирование.

**👍 СТОИТ СДЕЛАТЬ:**

3. **`defer mu.Unlock()`** — гарантирует вызов даже при панике.

**❌ НЕ ДЕЛАЙ:**

4. **Не копируй `Mutex`.**
5. **Не забывай `Unlock()`.**

## 4.3 Быстрый путь и slow path

Разберём, что происходит при `mu.Lock()`.

### Быстрый путь

**Ситуация:** мьютекс свободен, нет ждущих горутин.

Горутина вызывает `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)` — атомарную операцию **CAS**. Если `state` был равен 0 (мьютекс свободен), CAS записывает `mutexLocked` (1). Это означает «мьютекс захвачен».

**Что происходит на уровне CPU:**

1. Загрузить `state` в регистр.
2. Проверить: `state == 0`?
3. Если да — записать `mutexLocked` в `state`.

Это одна атомарная операция, ~15–25 нс. **Самая быстрая операция.** Никаких блокировок.

### Slow path

**Ситуация:** мьютекс занят или есть ждущие горутины.

Горутина вызывает `lockSlow(&m)` — функцию runtime, которая обрабатывает медленный путь.

**Что делает `lockSlow`:**

1. **Spin** — горутина крутится в цикле, несколько раз пытаясь захватить мьютекс через CAS. Это быстрее, чем сразу блокироваться, если мьютекс скоро освободится.

2. **Блокировка** — если spin не помог, горутина вызывает `runtime_SemacquireMutex(&m.sema)` — функцию runtime, которая блокирует горутину в семафоре. Горутина переходит в `_Gwaiting`.

3. **Пробуждение** — при `Unlock` runtime разбудит одну из ждущих горутин. Разбуженная горутина **снова попытается захватить мьютекс** (через CAS). Если не удалось — снова в семафор.

### Unlock

Горутина вызывает `atomic.AddInt32(&m.state, -mutexLocked)` — атомарно снимает флаг `mutexLocked`. Затем проверяет: были ли ждущие? Если `state != 0` — вызывает `unlockSlow(&m)`.

**Что делает `unlockSlow`:**

1. Проверяет `mutexStarving` — если да, передаёт мьютекс напрямую ждущей горутине.
2. Проверяет `waiters > 0` — если да, вызывает `runtime_Semrelease(&m.sema)`, которая будит одну ждущую горутину.

**Ключевое:** `Unlock` **не передаёт мьютекс напрямую**. Он только **будит** одну горутину. Разбуженная горутина должна **сама** захватить мьютекс (через CAS). Если не удалось — снова в семафор.

### Полная схема

```
mu.Lock()
    │
    ▼
┌─────────────────────────────────────────────┐
│  1. Быстрый путь:                            │
│     if atomic.CAS(&state, 0, mutexLocked):  │
│         return  ← захвачен!                  │
└─────────────────────────────────────────────┘
    │ CAS не удался
    ▼
┌─────────────────────────────────────────────┐
│  2. lockSlow:                                │
│                                              │
│     for {                                    │
│         old = state                          │
│         if old & mutexLocked == 0:           │
│             if CAS(&state, old, old|        │
│                    mutexLocked):             │
│                 return  ← захвачен!          │
│                                              │
│         if old & mutexStarving != 0:        │
│             break  ← идём в очередь          │
│                                              │
│         if spin не поможет: break            │
│                                              │
│         // Spin: попробовать ещё раз        │
│         runtime_procyield()                  │
│     }                                        │
│                                              │
│     // Блокировка:                          │
│     runtime_SemacquireMutex(&m.sema)         │
│     // Горутина в _Gwaiting                 │
└─────────────────────────────────────────────┘
```

### Стоимость

| Ситуация | Time |
|:---|:---|
| Uncontended Lock | ~15–25 нс |
| Contended (spin успешен) | ~50–100 нс |
| Contended (блокировка) | ~мкс–мс |
| Unlock (без waiters) | ~10–20 нс |
| Unlock (с waiters) | ~100–500 нс |

### 💡 Практика: как минимизировать contention

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Короткие критические секции:**
   ```go
   // ❌ Плохо: долгая секция
   mu.Lock()
   result := slowComputation()
   shared = result
   mu.Unlock()
   
   // ✅ Хорошо: вычисление вне секции
   result := slowComputation()
   mu.Lock()
   shared = result
   mu.Unlock()
   ```

2. **Не делай I/O под мьютексом.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Разделяй мьютексы:** один на структуру — плохо, несколько — лучше.

**❌ НЕ ДЕЛАЙ:**

4. **Не делай длинные критические секции.**
5. **Не делай I/O под мьютексом.**

**О contention:** когда несколько горутин одновременно пытаются захватить один мьютекс — возникает **contention**. Одна захватывает, остальные уходят в slow path. Где именно они ждут — в 4.4.

## 4.4 Где ждут горутины: semaRoot

В 4.3 мы сказали: «горутина блокируется в семафоре». Разберём, где именно.

### Что такое семафор в runtime

**Семафор** — примитив синхронизации: счётчик с двумя операциями:

- **`acquire`** — уменьшить счётчик, блокироваться, если 0.
- **`release`** — увеличить счётчик, разбудить одного ждущего.

**Важно:** семафор в runtime — это **не то же самое**, что `sync.Mutex`. `Mutex` **построен** на семафоре.

### Где живёт семафор

В `sync.Mutex` есть поле `sema uint32`:

```go
type Mutex struct {
    state int32
    sema  uint32  // ← это НЕ сам семафор, это НОМЕР семафора
}
```

**`sema` — это не счётчик.** Это **идентификатор** (адрес), по которому runtime находит структуру `semaRoot` — дерево ждущих горутин.

**Почему так:** семафоров в программе может быть **миллионы**. Держать для каждого полноценную структуру — расточительно. Вместо этого runtime использует **глобальную таблицу** `semaRoot`, индексированную по адресу `sema`.

```
┌──────────────────────────────────────────────┐
│           Глобальная таблица semaRoot        │
│                                              │
│  semaRoot[addr1] → дерево ждущих горутин     │
│  semaRoot[addr2] → дерево ждущих горутин     │
│  ...                                         │
│  semaRoot[&m.sema] → дерево для ЭТОГО        │
│                      мьютекса                │
└──────────────────────────────────────────────┘
```

**Ключевая идея:** `sema` в `Mutex` — это **не данные**, а **ключ** для поиска. Сами ждущие горутины хранятся **вне** `Mutex`.

### Структура semaRoot

```go
type semaRoot struct {
    lock  mutex      // защита дерева
    treap *sudog     // корень дерева ждущих горутин
    nwait atomic.Uint32  // число ждущих
}
```

**`treap`** — корень **дерева** `sudog`. Каждый узел — горутина, которая ждёт на этом семафоре.

### Почему дерево, а не очередь

Семафоры **адресуются по адресу** переменной `sema`. Когда горутина блокируется, она говорит: «я жду на семафоре по адресу `&m.sema`». Runtime должен **быстро найти** дерево для этого адреса.

- **Очередь** не позволяет искать по ключу.
- **Хэш-таблица** — вариант, но больше памяти.
- **Treap** — O(log N) поиск по адресу.

Для одного семафора дерево — это **список**, отсортированный по приоритету. `semaRoot` нужен, чтобы **разные семафоры** хранились в **одной глобальной структуре**.

### Структура sudog

Когда горутина блокируется, она оборачивается в **`sudog`**:

```go
type sudog struct {
    g          *g           // горутина
    next       *sudog       // следующий
    prev       *sudog       // предыдущий
    elem       unsafe.Pointer  // указатель на данные
    acquiretime int64       // время начала ожидания
    releasetime int64       // время окончания
    // ... поля для select
    c          *hchan       // канал (если ждём на канале)
}
```

**Размер** — ~48–64 байт.

**`sudog` используется:**

- **В семафорах** — узел дерева `semaRoot`.
- **В каналах** — в `sendq`/`recvq`.
- **В `select`** — связывает несколько case'ов.

**Общее:** `sudog` означает «горутина, которая чего-то ждёт».

### Путь блокировки

```
G1 вызывает mu.Lock(), но CAS не удался
   │
   ▼
lockSlow → runtime_SemacquireMutex(&m.sema)
   │
   ▼
semacquire1(addr = &m.sema):
   1. Найти semaRoot для addr
   2. Захватить semaRoot.lock
   3. Создать sudog для G1
   4. Добавить sudog в treap
   5. semaRoot.nwait++
   6. Отпустить lock
   │
   ▼
gopark:
   1. G1.atomicstatus = _Gwaiting
   2. G1.waitreason = waitReasonSemacquire
   3. Вызвать schedule()
   │
   ▼
G1 заблокирована, M свободен
```

### Путь пробуждения

```
G2 вызывает mu.Unlock()
   │
   ▼
unlockSlow → runtime_Semrelease(&m.sema)
   │
   ▼
semrelease1(addr = &m.sema):
   1. Найти semaRoot для addr
   2. Захватить semaRoot.lock
   3. Найти sudog в treap
   4. Удалить sudog
   5. nwait--
   6. Отпустить lock
   7. goready(sudog.g)
   │
   ▼
G1 помещена в очередь P
```

### Визуализация

```

│                    sync.Mutex (8 байт)                   │

│  │  │ semaRoot для &m.sema                        │   │ │
│  │  │  treap: sudog G1 → sudog G2 → sudog G3     │   │ │
│  │  │  nwait: 3                                   │   │ │

```

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: `sema` — это ключ, а не данные.**
2. **Помни: ждущие горутины хранятся вне мьютекса.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Знай: `sudog` используется в семафорах, каналах, `select`.**

**❌ НЕ ДЕЛАЙ:**

4. **Не пытайся «оптимизировать» очередь ждущих.**

## 4.5 Contention и starvation mode

Разберём **contention** и **starvation mode**.

### Что такое contention

**Contention** — ситуация, когда несколько горутин одновременно пытаются захватить один мьютекс. Одна захватывает, остальные уходят в slow path.

```
Низкий contention:              Высокий contention:
  G1: Lock → работа → Unlock     G1: Lock → работа → Unlock
  G2: Lock → работа → Unlock     G2: Lock → ЖДЁТ → Lock → Unlock
  G3: Lock → работа → Unlock     G3: Lock → ЖДЁТ → Lock → Unlock
                                 G4: Lock → ЖДЁТ → ЖДЁТ → Lock → Unlock
```

**Формула:**

```
Время ожидания ≈ O(N × T_hold)

N — число горутин
T_hold — среднее время удержания мьютекса
```

**Пример:** 100 горутин, каждая держит мьютекс 1 мс. Последняя ждёт 99 мс. Если держать 100 мкс — последняя ждёт 9.9 мс. **В 10 раз быстрее.**

### Starvation mode

**Проблема:** если мьютекс освобождается и сразу захватывается **новой** горутиной (которая только что пришла), а ждущие остаются в очереди — они **голодают**.

**Пример:**

```
Горутина A: Lock() → блокируется.
Горутина C: Lock() → блокируется.
B: Unlock() → будит A.
Но: горутина D (новая) захватывает раньше A.
A: просыпается, но мьютекс занят D → снова блокируется.
D: Unlock() → будит A.
Но: горутина E захватывает раньше A.
...

A голодает бесконечно.
```

**Решение:** **starvation mode** (Go 1.9+). Если горутина ждёт мьютекс дольше **1 мс** — мьютекс переходит в режим голодания:

- **Обычный режим:** разбуженная горутина **конкурирует** с новыми.
- **Starvation mode:** мьютекс **передаётся напрямую** ждущей горутине. Новые не могут захватить.

**Что это даёт:** справедливость. Горутина, ждущая > 1 мс, получит мьютекс.

**Цена:** starvation mode **снижает пропускную способность** — мьютекс передаётся без конкуренции. Это trade-off: **справедливость vs throughput**.

### Как диагностировать contention

**1. Mutex profile:**

```go
runtime.SetMutexProfileFraction(1)
```

**2. pprof:**

```bash
go tool pprof mutex.prof
(pprof) top
```

**Что искать:** функции с высоким contention.

**3. Метрики:**

- Latency под нагрузкой.
- CPU с высоким contention.

### Как уменьшить contention

**1. Короткие критические секции.**

**2. Разделение мьютексов.**

```go
// ❌ Плохо: один мьютекс на всё
type Cache struct {
    mu     sync.Mutex
    users  map[string]User
    orders map[string]Order
}

// ✅ Хорошо: разные мьютексы
type Cache struct {
    usersMu sync.Mutex
    users   map[string]User
    ordersMu sync.Mutex
    orders  map[string]Order
}
```

**3. `atomic` где можно.**

**4. Sharding** — разбить данные на N частей с отдельными мьютексами (Глава 29).

### 💡 Практика: как бороться с contention

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Короткие критические секции.**
2. **Разделение мьютексов.**
3. **`atomic` где можно.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь contention** через mutex profile.

**❌ НЕ ДЕЛАЙ:**

5. **Не держи мьютекс долго** — провоцирует starvation mode.

## 4.6 Почему Mutex не рекурсивный

Один из самых частых вопросов: **почему `Mutex` в Go не рекурсивный?**

### Что такое рекурсивный мьютекс

**Рекурсивный мьютекс** может быть захвачен **одной и той же горутиной** несколько раз:

```go
mu.Lock()
    mu.Lock()  // ✅ работает в рекурсивном мьютексе
    mu.Unlock()
mu.Unlock()
```

**В Go `sync.Mutex` — не рекурсивный:**

```go
mu.Lock()
    mu.Lock()  // ❌ DEADLOCK
mu.Unlock()
```

### Почему Go выбрал нерекурсивный

**1. Рекурсивный мьютекс — «запах» плохого дизайна.**

Если функция `A` захватывает мьютекс, потом вызывает `B`, которая **тоже** захватывает — границы критической секции размыты.

**2. Рекурсивный мьютекс скрывает ошибки.**

Случайный двойной `Lock` → **сразу deadlock** в нерекурсивном. В рекурсивном — не видно.

**3. Требует знания «владельца».**

Нужно хранить `goroutine ID`. Но **goroutine ID не доступен** в Go (специально, чтобы не поощрять рекурсивные мьютексы).

**4. Go-философия: явное лучше неявного.**

### Что делать вместо рекурсивного мьютекса

**1. Разделить критическую секцию.**

```go
// ❌ Плохо: вложенные Lock
func (s *Service) Process() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.processInternal()  // тоже Lock — deadlock
}

// ✅ Хорошо: разделить
func (s *Service) Process() {
    s.mu.Lock()
    data := s.getData()
    s.mu.Unlock()
    
    s.processData(data)  // без мьютекса
}
```

**2. Использовать приватные методы без Lock.**

```go
// Публичный метод — с Lock
func (s *Service) Process() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.processLocked()  // приватный метод, БЕЗ Lock
}

// Приватный метод — предполагает захваченный мьютекс
func (s *Service) processLocked() {
    // работа с s.data без Lock
}
```

**Соглашение:** методы с суффиксом `Locked` предполагают, что мьютекс уже захвачен.

### 💡 Практика: как избежать рекурсивного Lock

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Разделяй критические секции.**
2. **Соглашение `Locked`** для приватных методов.

**❌ НЕ ДЕЛАЙ:**

3. **Не вызывай `Lock()` дважды.** Deadlock.
4. **Не смешивай `Lock` и `RLock` из одной горутины.**

## 4.7 sync.RWMutex: читатели и писатели

`sync.RWMutex` — мьютекс с разделением на читателей и писателей.

### Идея

**Проблема `Mutex`:** если 100 горутин только **читают** данные, они всё равно сериализуются. Хотя чтение не конфликтует с чтением.

**Решение `RWMutex`:** разрешить **нескольким читателям** одновременно, но писатель — только один.

```
Mutex:
  [R] [R] [R] [W] [R] [R]  — все по очереди

RWMutex:
  [R R R] [W] [R R R]       — читатели параллельно, писатель один
```

### API

```go
var rw sync.RWMutex

rw.RLock()    // читатель
rw.RUnlock()

rw.Lock()     // писатель
rw.Unlock()
```

### Пример: кэш пользователей

**Задача:** 100 горутин читают `GetUser(42)`, 1 горутина пишет `SetUser(42, ...)`.

```go
type UserCache struct {
    mu    sync.Mutex   // или sync.RWMutex
    users map[int]User
}

func (c *UserCache) GetUser(id int) (User, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    u, ok := c.users[id]
    return u, ok
}

func (c *UserCache) SetUser(u User) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.users[u.ID] = u
}
```

**Что происходит с `Mutex`:**

- Все читатели выстраиваются в очередь.
- Каждый читатель ждёт предыдущего.
- Даже если чтение не изменяет данные — оно сериализуется.

**Что происходит с `RWMutex`:**

- Читатели захватывают `RLock` параллельно.
- Только писатель блокирует всех.
- Когда писатель отпускает — все читатели читают одновременно.

### Когда RWMutex быстрее

**Быстрее, если:**

- **Много читателей, мало писателей** (90%+).
- **Чтение длительное** (парсинг, обход больших структур).
- **Много горутин** (100+).

**Медленнее, если:**

- **Чтение короткое** (получение поля из map, 50 нс).
- **Мало горутин** (2–3).
- **Много писателей** (50%+).

### Бенчмарк

```go
func BenchmarkMutexShortRead(b *testing.B) {
    var mu sync.Mutex
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.Lock()
            _ = 42
            mu.Unlock()
        }
    })
}

func BenchmarkRWMutexShortRead(b *testing.B) {
    var mu sync.RWMutex
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() {
            mu.RLock()
            _ = 42
            mu.RUnlock()
        }
    })
}
```

**Результат (примерный):**

```
Короткое чтение:
BenchmarkMutexShortRead-8       50000000    25 ns/op
BenchmarkRWMutexShortRead-8     30000000    40 ns/op  ← медленнее!

Долгое чтение:
BenchmarkMutexLongRead-8         1000000  1500 ns/op
BenchmarkRWMutexLongRead-8       5000000   300 ns/op  ← быстрее в 5 раз
```

**Что видно:**

- Для **короткого** чтения `RWMutex` **медленнее** — overhead `atomic.AddInt32`.
- Для **долгого** чтения `RWMutex` **быстрее в 5 раз** — параллельное чтение.

### 💡 Практика: как использовать RWMutex

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **RWMutex — когда чтение доминирует (90%+) и оно длительное.**
2. **Бенчмаркай перед заменой `Mutex` на `RWMutex`.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для read-heavy кэшей с дорогим чтением.**

**❌ НЕ ДЕЛАЙ:**

4. **Не используй `RWMutex` «на всякий случай».**
5. **Не смешивай `Lock` и `RLock` из одной горутины.**

## 4.8 sync/atomic: атомарные операции

`sync/atomic` — пакет для **атомарных** операций.

### Что такое атомарная операция

**Атомарная операция** выполняется **целиком** или **не выполняется вообще**. Нет промежуточных состояний.

```
Не атомарно:
  counter++  →  read, add, write  (3 операции)

Атомарно:
  atomic.AddInt64(&counter, 1)  →  1 операция
```

### API

```go
// Новый API (Go 1.19+):
var counter atomic.Int64
counter.Add(1)
x := counter.Load()
counter.Store(42)
old := counter.Swap(100)
swapped := counter.CompareAndSwap(100, 200)
```

**Новый API — предпочтительнее:** безопаснее, читаемее, нельзя скопировать.

### Основные операции

**Add** — добавить.
**Load** — прочитать.
**Store** — записать.
**Swap** — заменить и вернуть старое.
**CompareAndSwap** — заменить, если равно ожидаемому.

### Как это работает на уровне CPU

- **x86-64:** `LOCK XADD` (сложение), `LOCK CMPXCHG` (CAS).
- **ARM64:** `LDADD`, `CAS`.

**Барьеры памяти:** атомарные операции включают **барьеры** для видимости между ядрами. Это дороже обычных операций, но дешевле мьютексов.

### Стоимость

| Операция | Time |
|:---|:---|
| `atomic.Add` | ~5–10 нс |
| `atomic.Load` | ~1–2 нс |
| `atomic.Store` | ~1–2 нс |
| `atomic.CompareAndSwap` | ~5–15 нс |
| `Mutex.Lock/Unlock` | ~15–25 нс |

**Атомики быстрее мьютексов** в 2–3 раза для простых операций.

### Когда использовать atomic

**✅ Подходит:**

- **Счётчики:** `atomic.AddInt64`.
- **Флаги:** `atomic.Bool`.
- **Указатели:** `atomic.Pointer[T]`.
- **Lock-free структуры:** сложно.

**❌ Не подходит:**

- **Защита нескольких переменных.** `atomic` работает с **одной**.
- **Сложные операции.** «Прочитать, вычислить, записать» — не атомарно.
- **Защита структур.** `map`, `slice` — нужен `Mutex`.

### Опасность: atomic не заменяет Mutex

**❌ Плохо:**

```go
var a, b atomic.Int64

a.Add(1)
b.Add(1)  // ← не атомарно вместе!
```

**Между `a.Add` и `b.Add` может произойти что угодно.** Если нужна атомарность для нескольких переменных — используй `Mutex`.

**✅ Хорошо:**

```go
var mu sync.Mutex
var a, b int64

mu.Lock()
a++
b++
mu.Unlock()
```

### 💡 Практика: как использовать atomic

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков — `atomic.Int64`.**
2. **Для флагов — `atomic.Bool`.**
3. **Новый API (Go 1.19+).**

**👍 СТОИТ СДЕЛАТЬ:**

4. **`atomic.Pointer[T]` для указателей.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `atomic` для нескольких переменных.**
6. **Не используй `atomic` для защиты map/slice.**

## 4.9 sync.WaitGroup изнутри

Разберём `WaitGroup` подробнее.

### Структура

```go
type WaitGroup struct {
    noCopy noCopy      // защита от копирования
    state  atomic.Uint64  // счётчик + waiter count
    sema   uint32      // семафор
}
```

**`state`** — 64-битное поле:
- **Старшие 32 бита** — счётчик.
- **Младшие 32 бита** — число ждущих.

### Как работает

**Add(delta):**

1. `atomic.AddUint64(&state, uint64(delta)<<32)` — добавить к счётчику.
2. Если `delta < 0` и счётчик == 0 — разбудить всех ждущих.

**Done():** `Add(-1)`.

**Wait():**

1. Прочитать state.
2. Если счётчик == 0 — return.
3. Если счётчик > 0 — `waiters++`, `Semacquire(&sema)` — блокироваться.

### Важно: Add до Wait

**❌ Плохо:**

```go
var wg sync.WaitGroup

go func() {
    wg.Add(1)  // может выполниться ПОСЛЕ Wait
    defer wg.Done()
}()

wg.Wait()  // может вернуться сразу
```

**✅ Хорошо:**

```go
var wg sync.WaitGroup

wg.Add(1)  // до запуска горутины
go func() {
    defer wg.Done()
}()

wg.Wait()
```

### Нельзя копировать

`WaitGroup` содержит `noCopy` — `go vet` ловит копирование. Но лучше помнить:

```go
// ❌ Плохо
func process(wg sync.WaitGroup) {  // копия!
    defer wg.Done()
}

// ✅ Хорошо
func process(wg *sync.WaitGroup) {
    defer wg.Done()
}
```

### Паттерн: worker pool с WaitGroup

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        // работа
    }(i)
}
wg.Wait()
```

### Паттерн: ожидание с таймаутом

`WaitGroup.Wait()` не поддерживает таймаут. Но можно обернуть:

```go
func waitWithTimeout(wg *sync.WaitGroup, timeout time.Duration) bool {
    done := make(chan struct{})
    go func() {
        wg.Wait()
        close(done)
    }()
    
    select {
    case <-done:
        return true
    case <-time.After(timeout):
        return false
    }
}
```

**Важно:** `WaitGroup` **не отменяется**. Горутины продолжат работу.

### 💡 Практика: как использовать WaitGroup

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Add` до `Wait`** (и до запуска горутин).
2. **`defer wg.Done()`** — гарантирует вызов.
3. **Передавай `*sync.WaitGroup`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для таймаута — обёртка с каналом.**

**❌ НЕ ДЕЛАЙ:**

5. **Не копируй `WaitGroup`.**
6. **Не вызывай `Add` внутри горутины после `Wait`.**

## 4.10 Практика Go: диагностика contention

Напишем **утилиту**, которая демонстрирует contention.

### Mutex profile

```go
package main

import (
    "os"
    "runtime"
    "runtime/pprof"
    "sync"
    "time"
)

var (
    mu      sync.Mutex
    counter int
)

func main() {
    runtime.SetMutexProfileFraction(1)

    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 10000; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }

    time.Sleep(100 * time.Millisecond)

    f, _ := os.Create("mutex.prof")
    pprof.Lookup("mutex").WriteTo(f, 0)
    f.Close()

    wg.Wait()
}
```

**Анализ:**

```bash
go tool pprof mutex.prof
(pprof) top
```

**Что искать:** `sync.(*Mutex).Lock` в top.

### Сравнение Mutex vs RWMutex vs atomic

```go
const N = 10_000_000

func benchMutex() time.Duration {
    var mu sync.Mutex
    var counter int
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}

func benchAtomic() time.Duration {
    var counter atomic.Int64
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                counter.Add(1)
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}
```

**Пример вывода:**

```
Mutex:   450ms
atomic:  85ms   ← быстрее в 5 раз
```

**Что видно:** `atomic` в 5 раз быстрее `Mutex` для счётчиков.

### Демонстрация starvation mode

```go
func main() {
    go func() {
        mu.Lock()
        defer mu.Unlock()
        time.Sleep(10 * time.Millisecond)  // долгая операция
    }()

    time.Sleep(1 * time.Millisecond)

    var wg sync.WaitGroup
    start := time.Now()
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            mu.Lock()
            mu.Unlock()
            if id == 0 {
                fmt.Printf("Waited: %v\n", time.Since(start))
            }
        }(i)
    }
    wg.Wait()
}
```

**Пример вывода:**

```
Waited: 12ms  ← больше 1 мс — starvation mode активировался
```

## 4.11 Выводы и типичные ошибки

**Что мы узнали?**

`sync.Mutex` — 8 байт: `state` (битовая маска) + `sema` (ключ для поиска в `semaRoot`). Быстрый путь — один CAS (~15–25 нс). Slow path — spin + `runtime_SemacquireMutex`. Ждущие горутины хранятся **вне** мьютекса — в глобальной таблице `semaRoot` (treap `sudog`). Contention — конкуренция за мьютекс. Starvation mode активируется при ожидании > 1 мс. `Mutex` не рекурсивный. `RWMutex` — 24 байта, читатели параллельно, писатель один; не всегда быстрее. `atomic` — атомарные операции над одной переменной, быстрее `Mutex` в 2–5 раз. `WaitGroup` — счётчик + семафор, `Add` до `Wait`, нельзя копировать.

**Типичные ошибки:**

- ❌ **Копировать `Mutex`.** `go vet` ловит.
- ❌ **Рекурсивный `Lock`.** Deadlock.
- ❌ **Смешивать `Lock` и `RLock`.** Deadlock.
- ❌ **Забывать `Unlock`.** Deadlock.
- ❌ **Длинные критические секции.** Contention.
- ❌ **I/O под мьютексом.**
- ❌ **Один мьютекс на всё.**
- ❌ **`Add` внутри горутины после `Wait`.**
- ❌ **Копировать `WaitGroup`.**
- ❌ **`atomic` для нескольких переменных.**
- ❌ **`atomic` для сложных операций.**
- ❌ **`RWMutex` «на всякий случай».**
- ❌ **Игнорировать contention.**

## 4.12 Для быстрого повторения

- **`Mutex` — 8 байт.** `state` + `sema`. Быстрый путь — CAS. Slow path — spin + `Semacquire`.
- **Ждущие горутины хранятся вне мьютекса** — в глобальной таблице `semaRoot` (treap).
- **`sudog`** — узел treap. Используется в семафорах, каналах, `select`.
- **Contention** — конкуренция за мьютекс. O(N × T_hold). Короткие секции, разделение мьютексов, `atomic`.
- **Starvation mode** активируется при ожидании > 1 мс.
- **`Mutex` не рекурсивный.** `Lock` дважды — deadlock. Разделяй секции, `Locked`-соглашение.
- **`RWMutex` — 24 байта.** Читатели параллельно, писатель один. Не всегда быстрее `Mutex`. Бенчмаркай.
- **`atomic`** — быстрее `Mutex` в 2–5 раз. Одна переменная. `Add`, `Load`, `Store`, `Swap`, `CAS`.
- **`WaitGroup`** — счётчик + семафор. `Add` до `Wait`. Не копировать.
- **Диагностика:** `SetMutexProfileFraction`, pprof mutex profile.

## 4.14 Ответы

### Ответ 1

**Три случая:**
1. **Счётчики и флаги** — `atomic` быстрее.
2. **Защита map/slice** — `Mutex` или `RWMutex`.
3. **Ожидание группы горутин** — `WaitGroup`.
4. **Инициализация один раз** — `Once`.

### Ответ 2

**`state`** — битовая маска: `mutexLocked`, `mutexWoken`, `mutexStarving`, `waiters`.

**`sema`** — **ключ** (адрес) для поиска в глобальной таблице `semaRoot`. Не счётчик.

### Ответ 3

**Быстрый путь:** `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)`. Если `state` был 0 — мьютекс захвачен. ~15–25 нс.

### Ответ 4

**В глобальной таблице `semaRoot`** — вне мьютекса. `Mutex.sema` — ключ для поиска. Ждущие горутины — в treap `semaRoot`.

### Ответ 5

**Contention** — конкуренция за мьютекс. Время ожидания ≈ O(N × T_hold).

**Уменьшить:**
1. Короткие критические секции.
2. Разделение мьютексов.
3. `atomic` где можно.
4. Sharding.

### Ответ 6

**`Mutex` не рекурсивный, потому что:**
1. Рекурсивный — «запах» плохого дизайна.
2. Скрывает ошибки.
3. Требует `goroutine ID` (недоступен в Go).
4. Go-философия: явное лучше неявного.

**Что делать:** разделять секции, `Locked`-соглашение.

### Ответ 7

**`RWMutex`:**
- Читатели (`RLock/RUnlock`) — параллельно.
- Писатель (`Lock/Unlock`) — один.

**Быстрее `Mutex`, когда:** много читателей, мало писателей, чтение длительное.

**Медленнее, когда:** короткие секции, мало горутин.

### Ответ 8

**`atomic`** — атомарные операции над одной переменной. Быстрее `Mutex` в 2–5 раз.

**Когда использовать:** счётчики, флаги, указатели, lock-free.

**Когда не использовать:** несколько переменных, сложные операции, `map`/`slice`.

### Ответ 9

**`WaitGroup` нельзя копировать**, потому что копия получает **свой** счётчик. `Add` в одной копии, `Done` в другой — счётчик не работает. `noCopy` + `go vet` ловят.
