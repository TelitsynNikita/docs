## 7.0 Пролог: код, который работает на моём ноутбуке

Ты пишешь сервис. Есть флаг `ready`, который одна горутина устанавливает, а другая читает:

```go
var ready bool
var data string

func producer() {
    data = "hello"   // (1) пишем данные
    ready = true     // (2) поднимаем флаг
}

func consumer() {
    for !ready {     // (3) ждём флаг
    }
    fmt.Println(data) // (4) читаем данные
}

func main() {
    go producer()
    go consumer()
    time.Sleep(1 * time.Second)
}
```

Запускаешь на своём ноутбуке (x86, Linux) — работает. Печатает `hello`. Всегда.

Ты деплоишь на прод-сервер (ARM64, AWS Graviton) — **иногда** печатает пустую строку. **Иногда** — `hello`. А иногда — падает с segmentation fault.

❓ **Что произошло?** Код же одинаковый!

💡 **Ответ:** в коде **data race**, и он **не определён спецификацией Go**. На x86 гонка «маскируется» строгой моделью памяти процессора. На ARM — проявляется в полной мере.

**Что может произойти:**

- **Компилятор** может переставить (1) и (2) местами: `ready = true` до `data = "hello"`. Тогда consumer увидит `ready == true`, но `data` ещё пустая.
- **Компилятор** может закешировать `ready` в регистре в цикле (3): `for !ready` превратится в бесконечный цикл.
- **Процессор** может выполнить запись `ready = true` **раньше**, чем запись `data = "hello"` — из-за store buffer.

**Ключевое:** это **не баг компилятора или процессора**. Это **разрешённое поведение**, потому что в коде **нет синхронизации**. Спецификация Go говорит: если есть data race, поведение **не определено**.

> **Мост к следующим главам:** эта глава — **фундамент**. Без понимания happens-before непонятно, почему `Mutex` работает, почему `atomic` работает, почему каналы синхронизируют. Всё, что мы разбирали раньше, **опирается** на модель памяти.

## 7.1 Data race: определение из спецификации

В предыдущих главах мы несколько раз сказали: «data race — это undefined behavior». Теперь дадим **точное** определение.

### Определение

**Data race** — это ситуация, когда две горутины обращаются к одной и той же переменной **одновременно**, и хотя бы одна из них **пишет**, без синхронизации.

Формально:

- **Две горутины** — не одна.
- **Одна и та же переменная** — один и тот же адрес памяти.
- **Хотя бы одна пишет** — read-read не гонка. Write-read и write-write — гонка.
- **Без синхронизации** — нет happens-before между операциями.

### Что НЕ является data race

**Read-read:**

```go
// Горутина A: x := data
// Горутина B: y := data
```

Обе читают. Никто не пишет. **Не гонка.**

**Доступ под мьютексом:**

```go
var mu sync.Mutex
var data int

// Горутина A:
mu.Lock()
data = 42
mu.Unlock()

// Горутина B:
mu.Lock()
x := data
mu.Unlock()
```

Мьютекс устанавливает happens-before. **Не гонка.**

**Доступ через atomic:**

```go
var data atomic.Int64

// Горутина A:
data.Store(42)

// Горутина B:
x := data.Load()
```

Atomic-операции не создают гонку. **Не гонка.**

### Что является data race

**Write-read без синхронизации:**

```go
var data int

// Горутина A:
data = 42

// Горутина B:
x := data
```

**Гонка.** Даже если на x86 «работает».

**Write-write без синхронизации:**

```go
var data int

// Горутина A:
data = 42

// Горутина B:
data = 100
```

**Гонка.** Результат непредсказуем.

### Почему это undefined behavior

Спецификация Go **не даёт никаких гарантий** при data race. Программа может:

- Работать «правильно».
- Работать «неправильно».
- Падать с segmentation fault.
- Зацикливаться.
- Печатать мусор.
- **Что угодно.**

**Это не «баг, который иногда проявляется».** Это **нарушение контракта** программы со спецификацией.

### Аналогия: чтение книги, которую кто-то редактирует

Представь, что ты читаешь книгу, а редактор одновременно правит её.

- **Без синхронизации:** ты можешь прочитать половину старой версии, половину новой. Или строку, которой ещё нет.
- **С мьютексом:** редактор говорит «я закончил правку», ты говоришь «я начинаю чтение».
- **С atomic:** редактор атомарно заменяет одну страницу. Ты читаешь либо старую, либо новую — но не смесь.

### 💡 Практика: как не допустить data race

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Любой доступ к разделяемой памяти — под синхронизацией.**
2. **Запускай `go test -race`.**
3. **Помни: read-read — не гонка.** Write-read и write-write — гонка.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для флагов — `atomic.Bool`.**
5. **Для данных — `Mutex` или канал.**

**❌ НЕ ДЕЛАЙ:**

6. **Не полагайся на «работает на моём ноутбуке».**
7. **Не используй `bool` для флага «готовности»** без atomic.

## 7.2 Happens-before: фундамент памяти

Мы сказали: «синхронизация устанавливает happens-before». Теперь разберём, **что это такое**.

### Определение

**Happens-before** — это **отношение порядка** между операциями. Если операция A **happens-before** операции B, то:

- Все эффекты A **видны** B.
- A **упорядочена** до B.

**Обозначение:** A → B.

### Пример

```go
var x int
var mu sync.Mutex

// Горутина A:
mu.Lock()
x = 42       // (1)
mu.Unlock()  // (2)

// Горутина B:
mu.Lock()    // (3)
y := x       // (4)
mu.Unlock()  // (5)
```

**Что гарантирует `Mutex`:**

- (1) → (2) — внутри горутины A порядок очевиден.
- (3) → (4) — внутри горутины B порядок очевиден.
- **(2) → (3)** — `Unlock` в A happens-before `Lock` в B.
- **Следовательно, (1) → (4)** — запись `x = 42` happens-before чтения `y := x`.
- **Гарантия:** B увидит `x == 42`.

**Ключевое:** `Mutex` не просто «блокирует». Он **устанавливает happens-before** между `Unlock` одной горутины и `Lock` другой.

### Happens-before внутри одной горутины

Внутри одной горутины **все** операции упорядочены **естественным порядком выполнения**:

```go
x = 1
y = 2
z = x + y
```

`x = 1` → `y = 2` → `z = x + y`. Внутри горутины это **всегда** так.

**Но:** компилятор может переставить операции, если **результат** не меняется. Например, `b := 2` до `a := 1` — если `c := a + b` от этого не меняется.

**Гарантия happens-before внутри горутины:** если операция A зависит от B (читает переменную, которую B пишет), то A → B **сохраняется**.

### Happens-before между горутинами

**По умолчанию** — **нет никакого порядка** между операциями разных горутин.

**Синхронизация** — это способ **установить** happens-before между горутинами:

| Синхронизация | Happens-before |
|:---|:---|
| `mu.Unlock()` → `mu.Lock()` | ✅ Да |
| `ch <- v` → `<-ch` | ✅ Да |
| `close(ch)` → `<-ch` (zero) | ✅ Да |
| `atomic.Store` → `atomic.Load` | ✅ Да (если Load видит Store) |
| `wg.Done()` → `wg.Wait()` | ✅ Да |
| `once.Do(f)` → `once.Do(g)` | ✅ Да |
| `cancel()` → `<-ctx.Done()` | ✅ Да |

**Без синхронизации** — **нет** happens-before. Операции могут выполняться в любом порядке.

### Пример: почему `data = "hello"; ready = true` не работает

```go
var data string
var ready bool

// Горутина A:
data = "hello"   // (1)
ready = true     // (2)

// Горутина B:
for !ready {}    // (3)
fmt.Println(data) // (4)
```

**Проблема:** нет happens-before между (2) и (3).

- Компилятор может переставить (1) и (2).
- Компилятор может закешировать `ready` в регистре в (3).
- Процессор может выполнить (2) раньше (1).

**Результат:** B может увидеть `ready == true`, но `data == ""`.

**Как исправить:**

```go
var data string
var ready atomic.Bool

// Горутина A:
data = "hello"
ready.Store(true)  // atomic.Store устанавливает happens-before

// Горутина B:
for !ready.Load() {}  // atomic.Load
fmt.Println(data)     // гарантированно увидит "hello"
```

### Три свойства happens-before

1. **Транзитивность:** если A → B и B → C, то A → C.
2. **Внутри горутины:** операции упорядочены естественным порядком.
3. **Между горутинами:** только через синхронизацию.

### 💡 Практика: как использовать happens-before

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: без синхронизации — нет happens-before.**
2. **Для флагов — `atomic.Bool`.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Для данных — `Mutex` или канал.**

**❌ НЕ ДЕЛАЙ:**

4. **Не полагайся на «порядок в коде» между горутинами.**
5. **Не используй `bool` для флага** без atomic.

## 7.3 Переупорядочивание: компилятор и процессор

Мы сказали: «компилятор и процессор могут переставить операции». Разберём, **как именно**.

### Два уровня переупорядочивания

**1. Компилятор** анализирует код и может **переставить** операции, если это не меняет **результат в рамках одной горутины**.

**2. Процессор** может выполнять инструкции **не в том порядке**, в котором они записаны, если это не меняет **результат в рамках одного ядра**.

### Почему компилятор переупорядочивает

**Оптимизации:**

- **Устранение мёртвого кода.**
- **Общие подвыражения.**
- **Инлайнинг.**
- **Перестановка** — если операция не зависит от другой.

**Пример:**

```go
a := 1
b := 2
c := a + b
```

Компилятор может выполнить `b := 2` до `a := 1`. Это **разрешено** спецификацией.

**Проблема:** если `a` — разделяемая переменная, а `b` — флаг, компилятор может переставить их так, что флаг будет установлен до записи данных.

### Почему процессор переупорядочивает

**Out-of-order execution:**

Современные процессоры выполняют инструкции **не в порядке программы**, а в порядке **готовности**.

**Store buffer:**

Запись в память проходит через **store buffer** — буфер между ядром и кэшем. Ядро может записать значение в store buffer и продолжить выполнение, не дожидаясь, пока запись попадёт в кэш.

**Проблема:** две записи могут попасть в память **в разном порядке** на разных ядрах.

### Типы переупорядочивания

**1. Store-store:**

```
Запись A → Запись B
Может ли B выполниться раньше A?
```

- **x86:** ❌ Нет.
- **ARM:** ✅ Да.

**2. Load-load:**

- **x86:** ❌ Нет.
- **ARM:** ✅ Да.

**3. Load-store:**

- **x86:** ❌ Нет.
- **ARM:** ✅ Да.

**4. Store-load:**

- **x86:** ✅ Да (единственное, разрешённое в TSO).
- **ARM:** ✅ Да.

### Визуализация

```
Исходный код:
  data = "hello"    // (1) store
  ready = true      // (2) store

x86 (TSO):
  [store data] → [store ready]  ← порядок сохраняется
  Но: load ready может обогнать load data

ARM (weak):
  [store ready] → [store data]  ← порядок МОЖЕТ быть нарушен
  И: load data может обогнать load ready
```

### Как синхронизация решает проблему

**Синхронизация** вставляет **барьеры памяти**, которые:

- Запрещают компилятору переставлять операции **через барьер**.
- Запрещают процессору переупорядочивать операции **через барьер**.

**Без барьера** — компилятор и процессор свободны. **С барьером** — порядок гарантирован.

### 💡 Практика: как не попасть на переупорядочивание

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: компилятор и процессор могут переставлять операции.**
2. **Для порядка — синхронизация.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Тестируй на ARM.**
4. **Запускай `go test -race`.**

**❌ НЕ ДЕЛАЙ:**

5. **Не полагайся на x86-поведение.**
6. **Не используй `bool` для флага «готовности»** без atomic.

## 7.4 Барьеры памяти

Мы сказали: «синхронизация вставляет барьеры». Разберём, **что это такое**.

### Определение

**Барьер памяти** (memory barrier, fence) — это **инструкция процессора**, которая:

- **Запрещает** переупорядочивание операций **через барьер**.
- **Гарантирует** видимость операций **до барьера** для других ядер **после барьера**.

### Типы барьеров

**1. Full barrier** (`MFENCE` на x86):

- Запрещает **все** переупорядочивания через барьер.
- Самый дорогой.

**2. Store barrier** (`SFENCE` на x86):

- Запрещает переупорядочивание **записей** через барьер.

**3. Load barrier** (`LFENCE` на x86):

- Запрещает переупорядочивание **чтений** через барьер.

**4. Acquire barrier:**

- Запрещает переупорядочивание операций **после** барьера с операциями **до** барьера.
- Используется при «захвате» ресурса (например, `Mutex.Lock`).

**5. Release barrier:**

- Запрещает переупорядочивание операций **до** барьера с операциями **после** барьера.
- Используется при «освобождении» ресурса (например, `Mutex.Unlock`).

### Пример: acquire и release

```go
// Горутина A:
data = "hello"      // (1) обычная запись
mu.Lock()           // (2) acquire
shared = data       // (3) под мьютексом
mu.Unlock()         // (4) release

// Горутина B:
mu.Lock()           // (5) acquire
local = shared      // (6) под мьютексом
mu.Unlock()         // (7)
```

**Что гарантируют барьеры:**

- (4) release: всё, что было **до** Unlock, видно **после** Lock.
- (5) acquire: всё, что было **до** Lock, видно **после** Lock.

**Результат:** B увидит `shared == "hello"`.

### Барьеры в Go

**Go не даёт прямого доступа к барьерам.** Вместо этого используются:

- **`sync/atomic`** — acquire/release семантика.
- **`sync.Mutex`** — Lock = acquire, Unlock = release.
- **Каналы** — send/receive с acquire/release.

**Компилятор Go** генерирует нужные барьеры автоматически.

### Стоимость барьеров

| Барьер | x86 | ARM | Стоимость |
|:---|:---|:---|:---|
| Full (`MFENCE`) | `MFENCE` | `DMB ISH` | ~20–50 нс |
| Store (`SFENCE`) | `SFENCE` | `DMB ISHST` | ~10–20 нс |
| Load (`LFENCE`) | `LFENCE` | `DMB ISHLD` | ~10–20 нс |
| Acquire | Неявный | `LDAR` | ~5–10 нс |
| Release | Неявный | `STLR` | ~5–10 нс |

**Ключевое:** барьеры **дорогие**. Поэтому `atomic` (5–10 нс) дороже обычной записи (1 нс), а `Mutex` (15–25 нс) дороже `atomic`.

### 💡 Практика: как использовать барьеры

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Используй `atomic` для acquire/release семантики.**
2. **Помни: `Mutex` уже вставляет барьеры.**

**❌ НЕ ДЕЛАЙ:**

3. **Не пытайся вставить барьеры через `unsafe` или ассемблер.**
4. **Не полагайся на «x86 и так работает».**

## 7.5 Что устанавливает happens-before в Go

Соберём **полный список** операций, которые устанавливают happens-before в Go.

### Официальный список

**1. Инициализация пакета.**

`init()` пакета A happens-before `init()` пакета B, если B импортирует A.

**2. Горутины.**

`go f()` happens-before начала выполнения `f`.

**3. Каналы.**

- **Отправка** в канал happens-before **получения** из этого канала.
- **Close** канала happens-before **получения** zero-значения.
- **Получение** из небуферизованного канала happens-before **завершения отправки**.

**4. Мьютексы.**

`mu.Unlock()` happens-before `mu.Lock()`, который получает мьютекс после.

**5. WaitGroup.**

`wg.Done()` happens-before `wg.Wait()`, который возвращается после.

**6. Once.**

`once.Do(f)` — `f` happens-before возврата из `once.Do`.

**7. Atomic.**

`atomic.Store` happens-before `atomic.Load`, если Load видит Store.

**8. Context.**

`cancel()` → `<-ctx.Done()`.

### Таблица happens-before

| Операция A | Операция B | Happens-before? |
|:---|:---|:---|
| `go f()` | начало `f` | ✅ Да |
| `ch <- v` | `<-ch` (получение v) | ✅ Да |
| `close(ch)` | `<-ch` (zero) | ✅ Да |
| `mu.Unlock()` | `mu.Lock()` (следующий) | ✅ Да |
| `wg.Done()` | `wg.Wait()` (возврат) | ✅ Да |
| `once.Do(f)` | возврат `once.Do` | ✅ Да |
| `atomic.Store` | `atomic.Load` (видит) | ✅ Да |
| `cancel()` | `<-ctx.Done()` | ✅ Да |
| `time.Sleep` | — | ❌ Нет |
| `runtime.Gosched` | — | ❌ Нет |
| Обычная запись | Обычное чтение | ❌ Нет |

### Пример: каналы устанавливают happens-before

```go
var data string

// Горутина A:
data = "hello"     // (1)
ch <- struct{}{}   // (2) отправка

// Горутина B:
<-ch               // (3) получение
fmt.Println(data)  // (4)
```

**Что гарантирует канал:**

- (2) happens-before (3).
- (1) happens-before (4) — транзитивно.
- **Результат:** B увидит `data == "hello"`.

### Пример: close устанавливает happens-before

```go
var data string

// Горутина A:
data = "hello"  // (1)
close(ch)       // (2)

// Горутина B:
<-ch            // (3) получение zero
fmt.Println(data) // (4)
```

**Что гарантирует close:**

- (2) happens-before (3).
- (1) happens-before (4).
- **Результат:** B увидит `data == "hello"`.

**Важно:** это работает **только** если B получает из **закрытого** канала.

### Что НЕ устанавливает happens-before

**`time.Sleep`:**

```go
// Горутина A:
data = "hello"

// Горутина B:
time.Sleep(1 * time.Second)
fmt.Println(data)  // ← нет гарантии!
```

**`runtime.Gosched`:**

```go
// Горутина A:
data = "hello"
runtime.Gosched()

// Горутина B:
fmt.Println(data)  // ← нет гарантии!
```

### 💡 Практика: как использовать happens-before

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для передачи данных — канал или `Mutex`.**
2. **Для флагов — `atomic.Bool`.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Помни: `time.Sleep` и `Gosched` не синхронизируют.**

**❌ НЕ ДЕЛАЙ:**

4. **Не используй `time.Sleep` для «синхронизации».**
5. **Не полагайся на `Gosched`** для порядка.

## 7.6 Atomic: видимость, упорядочивание, CAS

Разберём, **что именно** гарантирует `atomic`.

### Что гарантирует atomic

**1. Атомарность.**

Операция выполняется **целиком** или **не выполняется вообще**. Нет промежуточных состояний.

**2. Видимость.**

Запись через `atomic.Store` **видна** всем горутинам после `atomic.Load`.

**3. Упорядочивание (happens-before).**

`atomic.Store` happens-before `atomic.Load`, если Load видит Store.

**4. Acquire/release семантика.**

- `atomic.Store` — **release** барьер.
- `atomic.Load` — **acquire** барьер.

### Что НЕ гарантирует atomic

**1. Атомарность нескольких переменных.**

```go
// ❌ Не атомарно вместе:
a.Add(1)
b.Add(1)
```

Между `a.Add` и `b.Add` может произойти что угодно.

**2. Защита структур.**

`atomic` работает с **одной** переменной. Для `map`, `slice` — `Mutex`.

**3. «Быстрый мьютекс».**

`atomic` не заменяет `Mutex` для сложных операций.

### CAS: Compare-And-Swap

**CAS** — атомарная операция: «заменить, если текущее значение равно ожидаемому».

```go
var v atomic.Int64
v.Store(10)

swapped := v.CompareAndSwap(10, 20)  // true, если было 10
// v == 20
```

**Алгоритм CAS:**

```
CAS(addr, old, new):
   1. Прочитать *addr
   2. Если *addr == old:
        *addr = new
        return true
   3. Иначе:
        return false
```

**Всё атомарно** — одна инструкция процессора.

### CAS: паттерн retry loop

CAS используется для **lock-free** алгоритмов. Паттерн:

```go
var v atomic.Int64

func increment() {
    for {
        old := v.Load()
        new := old + 1
        if v.CompareAndSwap(old, new) {
            return  // успех
        }
        // неудача: кто-то изменил v между Load и CAS
        // повторяем
    }
}
```

**Проблема:** при высокой конкуренции CAS может «проваливаться» много раз. Это **дороже**, чем `Mutex`.

### Atomic vs Mutex: когда что

| Аспект | `atomic` | `Mutex` |
|:---|:---|:---|
| Атомарность | Одна переменная | Любая секция |
| Видимость | Да | Да |
| Happens-before | Да (Store → Load) | Да (Unlock → Lock) |
| Стоимость (uncontended) | ~5–10 нс | ~15–25 нс |
| Стоимость (contended) | Растёт (CAS retry) | Растёт (блокировка) |
| Использование | Счётчики, флаги | Защита структур |

**Правило:** `atomic` — для простых операций. `Mutex` — для сложных.

### 💡 Практика: как использовать atomic

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для счётчиков — `atomic.Int64`.**
2. **Для флагов — `atomic.Bool`.**
3. **Для указателей — `atomic.Pointer[T]`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Новый API (Go 1.19+).**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `atomic` для нескольких переменных.**
6. **Не используй `atomic` для сложных операций.**
7. **Не используй `atomic` для защиты map/slice.**

## 7.7 Race detector: как он работает

**Race detector** — инструмент для поиска data race.

### Запуск

```bash
go test -race ./...
go run -race main.go
go build -race -o myapp
```

### Как работает

**Race detector** использует **Vector Clock** из ThreadSanitizer.

Для каждой переменной хранится **история доступов**. Для каждой горутины — **вектор часов**.

При каждом доступе проверяется: есть ли **параллельный** доступ без синхронизации? Если да — **race**.

### Пример

```go
func main() {
    var counter int
    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++  // ← data race
        }()
    }
    wg.Wait()
}
```

**Запуск:** `go run -race main.go`

**Вывод:**

```
==================
WARNING: DATA RACE
Write at 0x00c00001e0b8 by goroutine 7:
  main.main.func1()
      /path/to/main.go:12 +0x...

Previous write at 0x00c00001e0b8 by goroutine 6:
  main.main.func1()
      /path/to/main.go:12 +0x...
==================
Found 1 data race(s)
```

**Что видно:**

- **Адрес** — где переменная.
- **Две горутины** — обе пишут.
- **Строки** — где именно.

### Что находит race detector

**Находит:**

- Write-write без синхронизации.
- Write-read без синхронизации.
- Игнорирует доступ через `Mutex`, каналы, `atomic`.

**Не находит:**

- Read-read (не гонка).
- Логические ошибки.
- Гонки, которые не произошли.

### Ограничения

**1. Замедление.** Программа с `-race` работает **в 5–20 раз медленнее**.

**2. Не находит все гонки.** Только те, которые **произошли**.

**3. Не работает в production.** Замедление слишком велико.

### Race detector в CI

```yaml
- name: Test with race detector
  run: go test -race ./...
```

**Почему:** ловит гонки на ранней стадии.

### 💡 Практика: как использовать race detector

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`go test -race ./...` в CI.**
2. **`go run -race` при отладке.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **Stress-тесты с `-race`.**
4. **Тесты на ARM.**

**❌ НЕ ДЕЛАЙ:**

5. **Не используй `-race` в production.**
6. **Не полагайся только на race detector.**

## 7.8 x86 vs ARM

Разберём разницу между архитектурами.

### Модели памяти

**x86 (TSO — Total Store Order):**

- Порядок **store-store** сохраняется.
- Порядок **load-load** сохраняется.
- Порядок **load-store** сохраняется.
- **Store-load** может быть переупорядочен.

**ARM (weak memory model):**

- **Все типы** переупорядочивания разрешены.

### Почему x86 «маскирует» гонки

**Пример:**

```go
var data string
var ready bool

// Горутина A:
data = "hello"
ready = true

// Горутина B:
for !ready {}
fmt.Println(data)
```

**На x86:**

- `data = "hello"` → `ready = true`: порядок **сохраняется**.
- B видит `ready == true` **только после** того, как `data` попало в кэш.
- **Результат:** B видит `data == "hello"`. **Работает.**

**На ARM:**

- `data = "hello"` → `ready = true`: порядок **может быть нарушен**.
- B может увидеть `ready == true` **до** того, как `data` попало в кэш.
- **Результат:** B видит `data == ""`. **Падает.**

### Почему это ловушка

**1. Разработка на x86.**

Большинство разработчиков работают на x86 (Intel, AMD). Гонки «не проявляются».

**2. Прод на ARM.**

AWS Graviton, Apple M1/M2, мобильные устройства — ARM. Гонки **проявляются**.

**3. «Работает у меня» — не аргумент.**

Код с data race **не является корректной Go-программой**.

### Как проверить

**1. Запускай на ARM.**

**2. Используй `-race`.**

**3. Читай код.**

Если есть разделяемая переменная без синхронизации — это гонка.

### 💡 Практика: как не попасть на x86 vs ARM

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: x86 маскирует гонки.**
2. **Тестируй на ARM или используй `-race`.**

**👍 СТОИТ СДЕЛАТЬ:**

3. **CI на ARM** — если прод на ARM.

**❌ НЕ ДЕЛАЙ:**

4. **Не полагайся на x86-поведение.**
5. **Не игнорируй race detector.**

## 7.9 Практика Go: ловим гонки

Разберём **три примера**.

### Пример 1: data race

```go
package main

import (
    "fmt"
    "sync"
)

var counter int

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++  // data race
        }()
    }
    wg.Wait()
    fmt.Println("counter:", counter)
}
```

**Запуск без `-race`:**

```bash
go run main.go
# counter: 987 (или другое число, не 1000)
```

**Запуск с `-race`:**

```bash
go run -race main.go
# WARNING: DATA RACE
# ...
# Found 1 data race(s)
```

**Что видно:** race detector находит гонку, которую без него не видно.

### Пример 2: атомарный счётчик

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

var counter atomic.Int64

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter.Add(1)
        }()
    }
    wg.Wait()
    fmt.Println("counter:", counter.Load())
}
```

**Пример вывода:**

```
counter: 1000
```

**Что видно:** `atomic` не создаёт гонку. Счётчик правильный.

### Пример 3: сравнение atomic vs Mutex

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

const N = 10_000_000

func benchAtomic() time.Duration {
    var counter atomic.Int64
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                counter.Add(1)
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}

func benchMutex() time.Duration {
    var mu sync.Mutex
    var counter int
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < N/100; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }
    wg.Wait()
    return time.Since(start)
}

func main() {
    fmt.Printf("atomic: %v\n", benchAtomic())
    fmt.Printf("Mutex:  %v\n", benchMutex())
}
```

**Пример вывода:**

```
atomic: 85ms
Mutex:  450ms
```

**Что видно:** `atomic` в 5 раз быстрее `Mutex` для счётчика.

### Пример 4: race detector в тестах

```go
// race_test.go
package main

import (
    "sync"
    "testing"
)

func TestRace(t *testing.T) {
    var counter int

        }()
    }
    wg.Wait()
    if counter != 100 {
        t.Errorf("expected 100, got %d", counter)
    }
}
```

**Запуск:**

```bash
go test -race ./...
```

**Вывод:**

```
==================
WARNING: DATA RACE
...
==================
--- FAIL: TestRace (0.00s)
```

**Что видно:** тест падает с `-race`, даже если без `-race` проходит.

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`go test -race ./...` в CI.**
2. **`go run -race` при отладке.**
3. **Тесты на ARM.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **Stress-тесты с `-race`.**

**❌ НЕ ДЕЛАЙ:**

## 7.10 Выводы и типичные ошибки

**Что мы узнали?**

Data race — это ситуация, когда две горутины обращаются к одной переменной, хотя бы одна пишет, без синхронизации. Это **undefined behavior**. Happens-before — фундамент: если A → B, эффекты A видны B. Внутри горутины — естественный порядок. Между горутинами — только через синхронизацию. Компилятор и процессор могут переупорядочивать операции: x86 (TSO) сохраняет порядок store-store, ARM (weak) — нет. Барьеры памяти запрещают переупорядочивание. Синхронизация (`Mutex`, каналы, `atomic`, `WaitGroup`, `Once`, `Context`) устанавливает happens-before. `atomic` гарантирует атомарность, видимость, acquire/release. Race detector находит гонки, но не все; замедляет в 5–20 раз. x86 маскирует гонки, ARM проявляет.

**Типичные ошибки:**

- ❌ **Полагать, что «работает на моём ноутбуке» = «корректно».**
- ❌ **Использовать `bool` для флага «готовности».**
- ❌ **Использовать `time.Sleep` для «синхронизации».**
- ❌ **Использовать `runtime.Gosched` для порядка.**
- ❌ **Полагать, что «порядок в коде» сохранится между горутинами.**
- ❌ **Игнорировать race detector.**
- ❌ **Использовать `-race` в production.**
- ❌ **Использовать `atomic` для нескольких переменных.**
- ❌ **Полагать, что `atomic` — «быстрый мьютекс».**
- ❌ **Не запускать `go test -race` в CI.**
- ❌ **Использовать `sync.Mutex` для флага.** Для флага — `atomic.Bool`.

## 7.11 Для быстрого повторения

- **Data race** — две горутины, одна переменная, хотя бы одна пишет, без синхронизации. **Undefined behavior.**
- **Read-read — не гонка.** Write-read и write-write — гонка.
- **Happens-before** — отношение порядка. Если A → B, эффекты A видны B.
- **Внутри горутины** — естественный порядок. **Между горутинами** — только через синхронизацию.
- **Happens-before устанавливают:** `go`, каналы, `Mutex`, `WaitGroup`, `Once`, `atomic`, `Context`.
- **НЕ устанавливают:** `time.Sleep`, `runtime.Gosched`, обычные операции.
- **Переупорядочивание** — компилятор и процессор могут переставлять.
- **x86 (TSO)** — сохраняет порядок store-store, load-load, load-store.
- **ARM (weak)** — разрешает все.
- **Барьеры памяти** — запрещают переупорядочивание. **Acquire** — при захвате, **release** — при освобождении.
- **`atomic`** гарантирует: атомарность, видимость, happens-before, acquire/release.
- **CAS** — атомарная «замена, если равно».
- **Race detector** — `go test -race`, `go run -race`. Замедляет в 5–20 раз.
- **x86 маскирует гонки**, ARM проявляет.

## 7.13 Ответы

### Ответ 1

**Data race** — две горутины, одна переменная, хотя бы одна пишет, без синхронизации.

**Гонка есть:** `data = 42` в одной горутине, `x := data` в другой.

**Гонки нет:** `mu.Lock(); data = 42; mu.Unlock()` в одной, `mu.Lock(); x := data; mu.Unlock()` в другой.

### Ответ 2

**Happens-before** — отношение порядка. Если A → B, эффекты A видны B.

**Устанавливают:** `go`, каналы, `Mutex`, `WaitGroup`, `Once`, `atomic`, `Context`.

**НЕ устанавливают:** `time.Sleep`, `Gosched`, обычные операции.

### Ответ 3

**`time.Sleep` не синхронизирует**, потому что не устанавливает happens-before. Даже если B «проспал» секунду, компилятор и процессор не обязаны видеть запись A.

**Что использовать:** `atomic.Bool`, `Mutex`, канал.

### Ответ 4

**Компилятор может переупорядочить** `data = "hello"` и `ready = true`, потому что они не зависят друг от друга **в рамках одной горутины**. Компилятор оптимизирует **локально** и не знает о других горутинах.

### Ответ 5

**x86 (TSO):** сохраняет порядок store-store, load-load, load-store. Разрешает только store-load.

**ARM (weak):** разрешает все типы.

### Ответ 6

**Барьер памяти** — инструкция, запрещающая переупорядочивание через барьер.

**Acquire** — при захвате. **Release** — при освобождении.

### Ответ 7

**`atomic` гарантирует:**
- Атомарность.
- Видимость.
- Happens-before (Store → Load).
- Acquire/release семантику.

### Ответ 8

**Race detector** использует Vector Clock. Для каждой переменной хранится история доступов; для каждой горутины — вектор часов. При доступе проверяется: есть ли параллельный доступ без синхронизации?

### Ответ 9

**x86 (TSO)** сохраняет порядок store-store. Поэтому `data = "hello"; ready = true` выполняется в порядке. B видит `ready == true` после того, как `data` попала в кэш.

**ARM (weak)** разрешает переупорядочивание store-store. B может увидеть `ready == true` до того, как `data` попала в кэш.

## 7.15 Чек-лист

| Концепция | Что это | Ключевые факты |
|:---|:---|:---|
| **Data race** | Две горутины, одна переменная, хотя бы одна пишет | Undefined behavior. Read-read — не гонка |
| **Happens-before** | Отношение порядка | Если A → B, эффекты A видны B |
| **Внутри горутины** | Естественный порядок | С учётом зависимостей |
| **Между горутинами** | Только через синхронизацию | `go`, каналы, `Mutex`, `WaitGroup`, `Once`, `atomic`, `Context` |
| **Переупорядочивание** | Компилятор и процессор | Разрешено, если результат в одной горутине не меняется |
| **x86 (TSO)** | Store-store, load-load, load-store сохраняются | Store-load может переупорядочиться |
| **ARM (weak)** | Все переупорядочивания разрешены | Гонки проявляются чаще |
| **Барьер памяти** | Инструкция, запрещающая переупорядочивание | Acquire, release, full |
| **Acquire** | При захвате | `Mutex.Lock`, `atomic.Load` |
| **Release** | При освобождении | `Mutex.Unlock`, `atomic.Store` |
| **`atomic`** | Атомарные операции над одной переменной | Атомарность, видимость, happens-before |
| **CAS** | Compare-And-Swap | «Заменить, если равно». Основа lock-free |
| **Race detector** | `go test -race`, `go run -race` | Замедляет 5–20x. Не находит все гонки |
| **x86 vs ARM** | x86 маскирует, ARM проявляет | Тестируй на ARM или используй `-race` |

🧠 **Ключевая идея:** Data race — это **undefined behavior** по спецификации Go. Happens-before — фундамент синхронизации: если A → B, эффекты A видны B. Компилятор и процессор переупорядочивают операции; x86 (TSO) сохраняет порядок store-store, ARM (weak) — нет. Барьеры памяти запрещают переупорядочивание; acquire при захвате, release при освобождении. Синхронизация (`Mutex`, каналы, `atomic`, `WaitGroup`, `Once`, `Context`) устанавливает happens-before. `atomic` гарантирует атомарность, видимость, acquire/release. Race detector находит гонки, но не все; замедляет в 5–20 раз. x86 маскирует гонки, ARM проявляет. Код с data race не является корректной Go-программой — даже если «работает». `time.Sleep` и `Gosched` не синхронизируют. `bool` для флага — гонка; используй `atomic.Bool`.
