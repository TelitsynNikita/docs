## 7.0 Пролог: 10 000 URL, которые положили сервер

Вернёмся к примеру из пролога Главы 1. Ты пишешь сервис, который качает 10 000 URL:

```go
func main() {
    urls := loadURLs()  // 10 000 URL
    
    var wg sync.WaitGroup
    for _, url := range urls {
        wg.Add(1)
        go func(u string) {
            defer wg.Done()
            resp, err := http.Get(u)
            if err != nil {
                return
            }
            defer resp.Body.Close()
        }(url)
    }
    wg.Wait()
}
```

В Главе 1 мы разобрали, что **10 000 горутин — это нормально**, но каждая делает HTTP-запрос, и это создаёт:

- 10 000 открытых TCP-соединений.
- 10 000 файловых дескрипторов (лимит ОС обычно 1024 на процесс).
- 10 000 буферов чтения/записи.
- Давление на GC.

На сервере с 8 ядрами и 16 ГБ RAM программа падает с OOM или исчерпанием file descriptors.

❓ **Что произошло?** 10 000 горутин — не проблема сама по себе. Проблема в том, что **все они работают одновременно**.

💡 **Решение:** ограничить параллелизм. Не 10 000 одновременных запросов, а, скажем, 20. Остальные ждут в очереди.

**Worker pool** — это паттерн, который это делает:

- **N воркеров** (горутин) обрабатывают задачи.
- **Канал задач** — очередь, из которой воркеры берут работу.
- **Канал результатов** — куда воркеры пишут результаты.

**Результат:** параллелизм ограничен N. Память, file descriptors, сетевые соединения — под контролем.

> **Важный мост к будущим главам:** worker pool — базовый паттерн. Fan-out/Fan-in (Глава 8) — его обобщение. Pipeline (Глава 8) — цепочка worker pool'ов. Rate limiter (Глава 9) — ограничение скорости. Graceful shutdown (Глава 11) — завершение worker pool'а.

## 7.1 Проблема: неограниченный параллелизм

Прежде чем строить worker pool, нужно понять, **почему** неограниченный параллелизм — проблема.

### Что происходит при 10 000 горутин

**1. Память.**

- Каждая горутина: ~2.3 КБ (стек + структура g).
- 10 000 × 2.3 КБ = **23 МБ** только на горутины.
- Плюс буферы HTTP-запросов, TCP-соединения, `sudog` при блокировках.

**2. File descriptors.**

- Каждое TCP-соединение — 1 fd.
- Лимит ОС: обычно 1024 на процесс (`ulimit -n`).
- **10 000 > 1024** → `too many open files`.

**3. Сетевые соединения.**

- 10 000 одновременных запросов к одному серверу — это DDoS с точки зрения сервера.
- Сервер может ответить 429 (Too Many Requests) или заблокировать.

**4. CPU.**

- Все горутины конкурируют за 8 ядер.
- Планировщик тратит время на переключение.
- Контекстные переключения в HTTP-стеке — overhead.

**5. GC.**

- 10 000 горутин — 10 000 `g`-структур, 10 000 стеков.
- GC обходит их при каждой сборке.
- Давление на GC → частые сборки → паузы.

### Пример: что видно в мониторинге

```
Горутины:    10 000+ (растёт)
File desc:   1024 (лимит достигнут)
Память:      500 МБ → 2 ГБ → OOM
CPU:         100% (но не полезная работа)
GC паузы:    частые, длинные
```

### Почему нельзя просто «подождать»

**Наивное решение:** добавить `time.Sleep` между запусками горутин.

```go
for _, url := range urls {
    go fetch(url)
    time.Sleep(1 * time.Millisecond)  // «размазать» запуск
}
```

**Проблема:**

- **Не контролирует параллелизм.** Если запрос длится 100 мс, всё равно накопится 100 одновременных.
- **Замедляет запуск.** 10 000 × 1 мс = 10 секунд только на запуск.
- **Нет backpressure.** Если внешний API тормозит — горутины копятся.

**Правильное решение:** worker pool с ограниченным числом воркеров.

### Аннотация сложности

| Подход | Горутин | File desc | Память | Контроль |
|:---|:---|:---|:---|:---|
| `go func()` на каждую | 10 000 | 10 000 | ~23 МБ | ❌ Нет |
| `time.Sleep` между | 10 000 | 10 000 | ~23 МБ | ⚠️ Частичный |
| Worker pool N=20 | 20 | 20 | ~50 КБ | ✅ Полный |

### 💡 Практика: как не допустить неограниченного параллелизма

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для внешних вызовов (HTTP, БД, API) — worker pool.** Ограничивай параллелизм.
2. **Мониторь `runtime.NumGoroutine()`.** Рост без падения = утечка или неограниченный параллелизм.
3. **Мониторь file descriptors.** `lsof -p <pid> | wc -l`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Для CPU-bound задач — worker pool с N = `GOMAXPROCS`.**
5. **Для I/O-bound задач — worker pool с N = 10-100.**

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Для лёгких задач (быстрее 1 мкс) — pool может быть overhead.**

**❌ НЕ ДЕЛАЙ:**

7. **Не создавай горутину на каждую задачу без ограничения.** OOM или исчерпание fd.
8. **Не используй `time.Sleep` для «размазывания».** Это не контроль.
9. **Не игнорируй file descriptors.** Лимит ОС — 1024.

### Ключевые выводы подглавы 7.1

- **Неограниченный параллелизм** → OOM, исчерпание fd, давление на GC.
- **`time.Sleep` не решает проблему** — не контролирует параллелизм.
- **Worker pool** ограничивает число одновременно работающих горутин.
- **Мониторь** `NumGoroutine()` и file descriptors.

## 7.2 Идея: worker pool

Разберём **идею worker pool**.

### Что такое worker pool

**Worker pool** — паттерн, при котором:

1. Есть **N воркеров** (горутин), которые обрабатывают задачи.
2. Есть **канал задач** — очередь, из которой воркеры берут работу.
3. Есть **канал результатов** (опционально) — куда воркеры пишут результаты.

**Параллелизм ограничен N.** Даже если задач 10 000, одновременно обрабатывается N.

### Схема

```
┌─────────────────────────────────────────────────────────────┐
│                    Producer (главная горутина)               │
│                                                              │
│  for _, task := range tasks {                               │
│      tasksCh <- task                                        │
│  }                                                           │
│  close(tasksCh)                                             │
└──────────────────────┬──────────────────────────────────────┘
                       │
                       │ tasksCh (канал задач)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    Worker Pool (N воркеров)                  │
│                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      ┌──────────┐ │
│  │ Worker 1 │  │ Worker 2 │  │ Worker 3 │ ...  │ Worker N │ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘      └────┬─────┘ │
│       │             │             │                  │       │
│       └─────────────┴─────────────┴──────────────────┘       │
│                              │                                │
│                              │ resultsCh (канал результатов)  │
│                              ▼                                │
└─────────────────────────────────────────────────────────────┘
                       │
                       │ resultsCh
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    Collector (главная горутина)              │
│                                                              │
│  for result := range resultsCh {                            │
│      process(result)                                        │
│  }                                                           │
└─────────────────────────────────────────────────────────────┘
```

### Ключевые свойства

1. **Ограниченный параллелизм:** N воркеров.
2. **Backpressure:** если канал задач буферизован и полон, producer ждёт.
3. **Переиспользование:** воркеры не создаются на каждую задачу.
4. **Контроль ресурсов:** N TCP-соединений, N буферов, N fd.

### Сколько воркеров

**Зависит от задачи:**

| Тип задачи | N воркеров | Почему |
|:---|:---|:---|
| CPU-bound | `GOMAXPROCS` | Больше — конкуренция за CPU |
| I/O-bound (HTTP, БД) | 10-100 | Зависит от latency внешнего сервиса |
| Смешанная | `GOMAXPROCS` × 2-4 | Компромисс |

**Эмпирическое правило:**

```
N = GOMAXPROCS × (1 + wait_time / compute_time)
```

Где:

- `wait_time` — время ожидания I/O.
- `compute_time` — время вычислений.

**Пример:** HTTP-запрос: 1 мс CPU + 100 мс ожидания сети.

```
N = 8 × (1 + 100/1) = 8 × 101 = 808
```

**Но:** это теоретический максимум. На практике — 20-100, потому что внешний сервис может не выдержать 800 одновременных запросов.

### Аннотация сложности

| Аспект | Значение |
|:---|:---|
| Горутин | N (воркеры) + 2 (producer, collector) |
| Память | N × ~2.3 КБ + буферы |
| File descriptors | N |
| Параллелизм | N |
| Пропускная способность | min(N, задач/время) |

### 💡 Практика: как выбирать N

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для CPU-bound — `N = GOMAXPROCS`.**
2. **Для I/O-bound — 10-100** (зависит от latency).

**👍 СТОИТ СДЕЛАТЬ:**

3. **Бенчмаркай разные N.** Оптимум зависит от задачи.
4. **Мониторь latency и throughput.** N должен балансировать.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Формула `N = GOMAXPROCS × (1 + wait/compute)`** — теоретический ориентир.

**❌ НЕ ДЕЛАЙ:**

6. **Не ставь N больше, чем выдержит внешний сервис.** Rate limit — твой друг (Глава 9).
7. **Не ставь N = 1**, если задача I/O-bound.

### Ключевые выводы подглавы 7.2

- **Worker pool** — N воркеров + канал задач + канал результатов.
- **Ограничивает параллелизм** до N.
- **Backpressure** через буферизованный канал.
- **N** зависит от задачи: CPU-bound → `GOMAXPROCS`, I/O-bound → 10-100.

## 7.3 Worker pool с нуля: пошагово

Построим worker pool **с нуля**, шаг за шагом.

### Шаг 1: канал задач

```go
type Task struct {
    ID  int
    URL string
}

tasksCh := make(chan Task, 100)  // буфер на 100
```

**Зачем буфер:**

- **Producer не блокируется**, пока в буфере есть место.
- **Backpressure:** если буфер полон, producer ждёт.
- **Размер буфера:** эмпирически 10-1000. Больше — producer быстрее, но память.

### Шаг 2: канал результатов

```go
type Result struct {
    TaskID int
    Status int
    Err    error
}

resultsCh := make(chan Result, 100)
```

**Зачем канал результатов:**

- **Воркеры не пишут в общий слайс** (это была бы гонка).
- **Collector читает результаты** и обрабатывает их.

### Шаг 3: запуск воркеров

```go
const numWorkers = 20

var wg sync.WaitGroup
for i := 0; i < numWorkers; i++ {
    wg.Add(1)
    go func(workerID int) {
        defer wg.Done()
        for task := range tasksCh {
            result := process(task)
            resultsCh <- result
        }
    }(i)
}
```

**Что происходит:**

1. **N воркеров** запускаются.
2. Каждый читает из `tasksCh` в цикле `for task := range tasksCh`.
3. Когда `tasksCh` закрыт, цикл завершается.
4. Результат пишется в `resultsCh`.

**Ключевое:** воркеры **переиспользуются**. Один воркер обрабатывает много задач.

### Шаг 4: producer

```go
go func() {
    defer close(tasksCh)
    for _, url := range urls {
        tasksCh <- Task{URL: url}
    }
}()
```

**Что происходит:**

1. Producer пишет задачи в `tasksCh`.
2. Когда все задачи отправлены — `close(tasksCh)`.
3. Воркеры видят закрытие и завершают цикл.

**Важно:** `close` делает **producer** (тот, кто пишет), а не воркеры.

### Шаг 5: collector

```go
go func() {
    wg.Wait()
    close(resultsCh)
}()

for result := range resultsCh {
    processResult(result)
}
```

**Что происходит:**

1. Отдельная горутина ждёт завершения всех воркеров (`wg.Wait()`).
2. Когда все воркеры завершились — `close(resultsCh)`.
3. Главная горутина читает результаты из `resultsCh`.
4. Когда `resultsCh` закрыт — цикл завершается.

**Почему отдельная горутина:**

- Если `wg.Wait()` и `for range resultsCh` в одной горутине — deadlock: `Wait` ждёт воркеров, воркеры ждут, пока collector читает, collector ждёт `Wait`.

### Полный код

```go
package main

import (
    "fmt"
    "net/http"
    "sync"
    "time"
)

type Task struct {
    ID  int
    URL string
}

type Result struct {
    TaskID int
    Status int
    Err    error
}

func main() {
    urls := []string{
        "https://example.com",
        // ... 10 000 URL
    }

    const numWorkers = 20
    const taskBuffer = 100
    const resultBuffer = 100

    tasksCh := make(chan Task, taskBuffer)
    resultsCh := make(chan Result, resultBuffer)

    // Запуск воркеров
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go worker(i, tasksCh, resultsCh, &wg)
    }

    // Producer
    go func() {
        defer close(tasksCh)
        for i, url := range urls {
            tasksCh <- Task{ID: i, URL: url}
        }
    }()

    // Закрытие resultsCh после завершения воркеров
    go func() {
        wg.Wait()
        close(resultsCh)
    }()

    // Collector
    var success, failed int
    for result := range resultsCh {
        if result.Err != nil {
            failed++
        } else {
            success++
        }
    }

    fmt.Printf("success: %d, failed: %d\n", success, failed)
}

func worker(id int, tasksCh <-chan Task, resultsCh chan<- Result, wg *sync.WaitGroup) {
    defer wg.Done()
    for task := range tasksCh {
        result := process(task)
        resultsCh <- result
    }
}

func process(task Task) Result {
    start := time.Now()
    resp, err := http.Get(task.URL)
    if err != nil {
        return Result{TaskID: task.ID, Err: err}
    }
    defer resp.Body.Close()
    _ = time.Since(start)
    return Result{TaskID: task.ID, Status: resp.StatusCode}
}
```

### Пошаговый разбор выполнения

```
t=0:    20 воркеров запущены, ждут в tasksCh
        Producer запущен, пишет в tasksCh
        Collector ждёт resultsCh

t=1:    Producer пишет Task{0} → воркер 0 берёт
        Producer пишет Task{1} → воркер 1 берёт
        ...
        Producer пишет Task{19} → воркер 19 берёт
        Producer пишет Task{20} → воркер 0 (освободился)

t=100ms: Воркеры пишут результаты в resultsCh
        Collector читает результаты

t=...:  Все задачи отправлены, close(tasksCh)
        Воркеры видят закрытие, завершают цикл
        wg.Wait() возвращается
        close(resultsCh)
        Collector видит закрытие, завершает цикл
        main выходит
```

### Аннотация сложности

| Операция | Time | Space |
|:---|:---|:---|
| Запуск воркера | ~100-300 нс | ~2.3 КБ |
| Отправка задачи в канал | ~50-100 нс | 0 |
| Получение задачи из канала | ~50-100 нс | 0 |
| Обработка задачи | зависит от задачи | зависит |
| Отправка результата | ~50-100 нс | 0 |
| Чтение результата | ~50-100 нс | 0 |

### 💡 Практика: как строить worker pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Буферизованные каналы** для задач и результатов:
   ```go
   tasksCh := make(chan Task, 100)
   resultsCh := make(chan Result, 100)
   ```

2. **`close(tasksCh)` в producer**, не в воркерах.

3. **`close(resultsCh)` после `wg.Wait()`** — в отдельной горутине.

4. **`for task := range tasksCh`** — автоматическое завершение по close.

**👍 СТОИТ СДЕЛАТЬ:**

5. **Передавай каналы как направленные:**
   ```go
   func worker(id int, tasksCh <-chan Task, resultsCh chan<- Result)
   ```

6. **Используй `context.Context`** для отмены (см. 7.9).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

7. **Метрики** — сколько задач обработано, latency (см. 7.10).

**❌ НЕ ДЕЛАЙ:**

8. **Не закрывай `tasksCh` в воркерах.** Только producer.
9. **Не пиши в `resultsCh` после `close`.** Паника.
10. **Не забывай `wg.Done()`.** Deadlock.

### Ключевые выводы подглавы 7.3

- **Канал задач** с буфером — очередь.
- **N воркеров** читают из `tasksCh` в `for range`.
- **Producer** пишет задачи и закрывает `tasksCh`.
- **Collector** читает результаты.
- **`wg.Wait()` + `close(resultsCh)`** в отдельной горутине.
- **Каналы передавай как направленные.**

## 7.4 Закрытие каналов и завершение воркеров

Разберём **правильное закрытие** каналов.

### Кто закрывает канал

**Правило:** канал закрывает **тот, кто пишет**.

```
tasksCh:    producer пишет → producer закрывает
resultsCh:  воркеры пишут → ??? закрывает
```

**Проблема с `resultsCh`:** писателей **несколько** (N воркеров). Кто закроет?

**Решение:** отдельная горутина, которая ждёт завершения всех воркеров:

```go
go func() {
    wg.Wait()      // ждём всех воркеров
    close(resultsCh)  // закрываем
}()
```

**Почему это работает:**

- `wg.Wait()` возвращается, когда **все** воркеры вызвали `wg.Done()`.
- Значит, никто больше не пишет в `resultsCh`.
- `close(resultsCh)` безопасен.

### Что происходит при close

**Воркер:**

```go
for task := range tasksCh {
    // ...
}
// Когда tasksCh закрыт — цикл завершается.
```

**`range` по каналу:**

- Читает, пока канал открыт.
- Когда канал **закрыт** и **буфер пуст** — цикл завершается.

**Коллектор:**

```go
for result := range resultsCh {
    // ...
}
// Когда resultsCh закрыт — цикл завершается.
```

### Deadlock: неправильное закрытие

**❌ Плохо: `close(resultsCh)` в main**

```go
for result := range resultsCh {  // блокируется, ждёт результатов
    process(result)
}
close(resultsCh)  // никогда не выполнится
```

**Что происходит:** `for range resultsCh` блокируется, ждёт результатов. Но воркеры не могут завершиться, пока `tasksCh` не закрыт. `close(resultsCh)` не выполняется, потому что цикл не завершился. **Deadlock.**

**✅ Хорошо: `close(resultsCh)` в отдельной горутине**

```go
go func() {
    wg.Wait()
    close(resultsCh)
}()

for result := range resultsCh {  // читаем, пока не закрыт
    process(result)
}
```

**Что происходит:** отдельная горутина ждёт воркеров и закрывает `resultsCh`. Главная горутина читает, пока не закрыт.

### Паттерн: `errgroup` для закрытия

`golang.org/x/sync/errgroup` автоматически управляет закрытием:

```go
g, ctx := errgroup.WithContext(context.Background())

for i := 0; i < numWorkers; i++ {
    g.Go(func() error {
        for task := range tasksCh {
            if err := process(ctx, task); err != nil {
                return err
            }
        }
        return nil
    })
}

go func() {
    defer close(tasksCh)
    for _, task := range tasks {
        select {
        case tasksCh <- task:
        case <-ctx.Done():
            return
        }
    }
}()

if err := g.Wait(); err != nil {
    // ошибка
}
```

**Что делает `errgroup`:**

- Запускает N горутин.
- Ждёт их завершения.
- Возвращает первую ошибку (или `nil`).
- Отменяет контекст при ошибке.

**Детали — в 7.9 и Главе 10.**

### Схема закрытия

```
t=0:    20 воркеров запущены, читают tasksCh
        Producer пишет задачи

t=T:    Producer закончил, close(tasksCh)
        Воркеры дочитывают остатки
        Каждый воркер завершает for range, вызывает wg.Done()

t=T+ε:  Все воркеры завершены, wg.Wait() вернулся
        close(resultsCh)
        Collector дочитывает результаты
        Collector завершает for range
        main выходит
```

### Аннотация сложности

| Операция | Time | Space |
|:---|:---|:---|
| `close(ch)` | ~50-100 нс | 0 |
| `range ch` после close | ~50-100 нс на элемент | 0 |
| `wg.Wait()` | ~10-20 нс + ожидание | 0 |

### 💡 Практика: как правильно закрывать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Producer закрывает `tasksCh`.**
2. **Отдельная горутина с `wg.Wait()` закрывает `resultsCh`.**
3. **`for range` в воркерах и коллекторе** — автоматическое завершение.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`errgroup`** — если нужна обработка ошибок и отмена.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Метрики** — сколько задач обработано.

**❌ НЕ ДЕЛАЙ:**

6. **Не закрывай `resultsCh` в main** до чтения. Deadlock.
7. **Не закрывай канал дважды.** Паника.
8. **Не пиши в закрытый канал.** Паника.
9. **Не забывай `wg.Done()`.** `wg.Wait()` не вернётся.

### Ключевые выводы подглавы 7.4

- **Producer закрывает `tasksCh`.**
- **Отдельная горутина с `wg.Wait()` закрывает `resultsCh`.**
- **`for range`** — автоматическое завершение по close.
- **`close(resultsCh)` в main** → deadlock.
- **`errgroup`** — для обработки ошибок.

## 7.5 Сбор результатов: три подхода

Разберём **три подхода** к сбору результатов.

### Подход 1: канал результатов (рекомендуемый)

```go
resultsCh := make(chan Result, 100)

// Воркеры пишут в resultsCh
go func() {
    wg.Wait()
    close(resultsCh)
}()

// Collector читает
for result := range resultsCh {
    process(result)
}
```

**Плюсы:**

- **Нет гонок.** Канал синхронизирует.
- **Backpressure.** Если collector медленный — воркеры ждут.
- **Естественное завершение.** `close` + `range`.

**Минусы:**

- **Один collector.** Если обработка результатов медленная — bottleneck.
- **Порядок не гарантирован.** Результаты приходят в порядке завершения.

### Подход 2: `Mutex` + слайс

```go
var (
    mu      sync.Mutex
    results []Result
)

// Воркеры:
result := process(task)
mu.Lock()
results = append(results, result)
mu.Unlock()
```

**Плюсы:**

- **Просто.** Нет канала.
- **Все результаты в одном слайсе.** Легко обработать после.

**Минусы:**

- **Mutex contention.** При N воркерах — конкуренция.
- **Память.** Все результаты в памяти.
- **Нет backpressure.** Воркеры не ждут.

### Подход 3: `atomic` счётчик + слайс с предварительным выделением

```go
results := make([]Result, len(tasks))  // предварительно выделен
var idx atomic.Int64

// Воркеры:
result := process(task)
i := idx.Add(1) - 1
results[i] = result  // разные индексы, нет гонки
```

**Плюсы:**

- **Нет блокировок.** `atomic.Add` быстрее `Mutex`.
- **Нет аллокаций.** Слайс выделен заранее.

**Минусы:**

- **Нужно знать число задач заранее.**
- **Порядок не гарантирован** (если важен — нужна сортировка).

### Сравнение

| Подход | Гонки | Backpressure | Память | Порядок |
|:---|:---|:---|:---|:---|
| Канал результатов | Нет | Да | O(1) в буфере | Не гарантирован |
| Mutex + слайс | Нет (Mutex) | Нет | O(N) | Не гарантирован |
| Atomic + слайс | Нет | Нет | O(N) | Не гарантирован |

**Рекомендация:** **канал результатов** — для большинства случаев. `Mutex` — если нужно собрать все результаты и обработать после. `Atomic` — если важна производительность и порядок не важен.

### Пример: канал результатов с обработкой

```go
type Result struct {
    TaskID int
    Status int
    Err    error
}

func main() {
    tasksCh := make(chan Task, 100)
    resultsCh := make(chan Result, 100)

    var wg sync.WaitGroup
    for i := 0; i < 20; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for task := range tasksCh {
                resultsCh <- process(task)
            }
        }()
    }

    go func() {
        defer close(tasksCh)
        for _, url := range urls {
            tasksCh <- Task{URL: url}
        }
    }()

    go func() {
        wg.Wait()
        close(resultsCh)
    }()

    // Сбор результатов
    var success, failed int
    for result := range resultsCh {
        if result.Err != nil {
            failed++
        } else {
            success++
        }
    }

    fmt.Printf("success: %d, failed: %d\n", success, failed)
}
```

### Аннотация сложности

| Подход | Отправка | Чтение | Память |
|:---|:---|:---|:---|
| Канал | ~50-100 нс | ~50-100 нс | O(буфер) |
| Mutex | ~15-25 нс | — | O(N) |
| Atomic | ~5-10 нс | — | O(N) |

### 💡 Практика: как выбирать подход

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Для большинства случаев — канал результатов.** Просто и безопасно.
2. **Backpressure** — канал результатов даёт его бесплатно.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Mutex + слайс** — если нужно обработать все результаты после.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Atomic** — только для горячего кода.

**❌ НЕ ДЕЛАЙ:**

5. **Не пиши в общий слайс без синхронизации.** Гонка.
6. **Не используй `append` без `Mutex`.** Гонка.

### Ключевые выводы подглавы 7.5

- **Канал результатов** — рекомендуемый подход.
- **Mutex + слайс** — если нужны все результаты.
- **Atomic + слайс** — для горячего кода.
- **Backpressure** — только у канала.

## 7.6 Backpressure: что это и зачем

Разберём **backpressure** — механизм контроля нагрузки.

### Определение

**Backpressure** — это механизм, при котором **замедление потребителя замедляет производителя**.

**Пример:** если collector не успевает обрабатывать результаты, воркеры начинают ждать при отправке в `resultsCh`. Это замедляет воркеров. Воркеры перестают брать новые задачи из `tasksCh`. Producer начинает ждать при отправке в `tasksCh`.

**Результат:** вся система замедляется до скорости самого медленного звена.

### Без backpressure

```
Producer (быстро) → tasksCh → Воркеры (быстро) → resultsCh (небуферизованный) → Collector (медленно)
```

**Что происходит:**

- Воркеры пишут в `resultsCh`, но collector не успевает.
- Воркеры блокируются на `resultsCh <- result`.
- Воркеры не берут новые задачи.
- `tasksCh` заполняется.
- Producer блокируется на `tasksCh <- task`.

**Backpressure работает.** Но только если `resultsCh` **небуферизованный** или **маленький**.

### С большим буфером

```
Producer (быстро) → tasksCh (1000) → Воркеры (быстро) → resultsCh (1000) → Collector (медленно)
```

**Что происходит:**

- Воркеры пишут в `resultsCh`, буфер заполняется (1000).
- Пока буфер не полон, воркеры не блокируются.
- Воркеры берут новые задачи.
- `tasksCh` заполняется (1000).
- Пока буфер не полон, producer не блокируется.

**Backpressure откладывается.** Проблема маскируется: буферы скрывают несоответствие скоростей. Но если producer быстрее collector **надолго** — буферы переполнятся, и система всё равно замедлится.

### Как обеспечить backpressure

**1. Буферизованный канал задач с разумным размером:**

```go
tasksCh := make(chan Task, 100)
```

**2. Небуферизованный или маленький канал результатов:**

```go
resultsCh := make(chan Result, 10)
```

**3. `select` с `ctx.Done()`:**

```go
select {
case resultsCh <- result:
case <-ctx.Done():
    return
}
```

**4. Rate limiter** (Глава 9) — если внешний сервис имеет лимит.

### Визуализация

```
Без backpressure:

  Producer: ████████████████████ (быстро)
  Воркеры:  ████████████████████ (быстро)
  Collector: ██░░░░░░░░░░░░░░░░░░ (медленно)
  Результат: буферы переполняются, память растёт

С backpressure:

  Producer: ████████████████████
  Воркеры:  ████████████████████
  Collector: ██░░░░░░░░░░░░░░░░░░
  → Producer ждёт (backpressure)
  → Воркеры ждут (backpressure)
  → Скорость = скорость collector
```

### Аннотация сложности

| Аспект | Без backpressure | С backpressure |
|:---|:---|:---|
| Память | Растёт | Ограничена |
| Скорость | Скорость producer | Скорость collector |
| Стабильность | Может упасть | Стабильна |

### 💡 Практика: как обеспечить backpressure

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Буферизованный канал задач** с разумным размером.
2. **Маленький буфер результатов** (или небуферизованный).
3. **`select` с `ctx.Done()`** для отмены.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Мониторь длину очередей.** Если растёт — backpressure не работает.
5. **Rate limiter** (Глава 9) для внешних сервисов.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Динамический размер буфера** — редко нужно.

**❌ НЕ ДЕЛАЙ:**

7. **Не ставь огромные буферы** — маскируют проблему.
8. **Не игнорируй растущие очереди** — это сигнал.

### Ключевые выводы подглавы 7.6

- **Backpressure** — замедление потребителя замедляет производителя.
- **Буферизованный канал задач** + **маленький буфер результатов** — backpressure.
- **Большие буферы маскируют проблему.**
- **Мониторь длину очередей.**

## 7.7 Динамическое число воркеров

Разберём **динамическое изменение** числа воркеров.

### Зачем

**Фиксированное N** — не всегда оптимально:

- **Днём** — высокая нагрузка, нужно 100 воркеров.
- **Ночью** — низкая нагрузка, достаточно 10.
- **Всплески** — нужно быстро добавить воркеров.

**Динамическое N** позволяет адаптироваться.

### Подход 1: масштабирование через `context`

```go
type Pool struct {
    tasksCh  chan Task
    resultsCh chan Result
    ctx      context.Context
    cancel   context.CancelFunc
    wg       sync.WaitGroup
    mu       sync.Mutex
    workers  int
}

func NewPool(ctx context.Context, numWorkers int) *Pool {
    ctx, cancel := context.WithCancel(ctx)
    p := &Pool{
        tasksCh:  make(chan Task, 100),
        resultsCh: make(chan Result, 100),
        ctx:      ctx,
        cancel:   cancel,
    }
    p.Scale(numWorkers)
    return p
}

func (p *Pool) Scale(n int) {
    p.mu.Lock()
    defer p.mu.Unlock()
    
    delta := n - p.workers
    if delta > 0 {
        // Добавить воркеров
        for i := 0; i < delta; i++ {
            p.wg.Add(1)
            go p.worker()
        }
    } else {
        // Уменьшить — отправить сигнал отмены
        // (сложнее, требует отдельного механизма)
    }
    p.workers = n
}

func (p *Pool) worker() {
    defer p.wg.Done()
    for {
        select {
        case <-p.ctx.Done():
            return
        case task, ok := <-p.tasksCh:
            if !ok {
                return
            }
            p.resultsCh <- process(task)
        }
    }
}
```

**Проблема:** уменьшение воркеров **сложнее**. Нужен механизм «скажи воркеру завершиться».

### Подход 2: отдельный канал отмены для воркеров

```go
type Pool struct {
    tasksCh   chan Task
    resultsCh chan Result
    stopCh    chan struct{}  // сигнал остановки воркера
    wg        sync.WaitGroup
    mu        sync.Mutex
    workers   int
}

func (p *Pool) AddWorker() {
    p.mu.Lock()
    defer p.mu.Unlock()
    p.wg.Add(1)
    go p.worker()
    p.workers++
}

func (p *Pool) RemoveWorker() {
    p.mu.Lock()
    defer p.mu.Unlock()
    if p.workers > 0 {
        p.stopCh <- struct{}{}  // сигнал одному воркеру
        p.workers--
    }
}

func (p *Pool) worker() {
    defer p.wg.Done()
    for {
        select {
        case <-p.stopCh:
            return  // завершиться по сигналу
        case task, ok := <-p.tasksCh:
            if !ok {
                return
            }
            p.resultsCh <- process(task)
        }
    }
}
```

**Что происходит:**

- `AddWorker` — запускает нового воркера.
- `RemoveWorker` — отправляет сигнал в `stopCh`, один воркер завершается.
- Воркеры **сами решают**, когда завершиться.

### Подход 3: `errgroup` + динамическое добавление

```go
g, ctx := errgroup.WithContext(context.Background())

addWorker := func() {
    g.Go(func() error {
        for {
            select {
            case <-ctx.Done():
                return ctx.Err()
            case task, ok := <-tasksCh:
                if !ok {
                    return nil
                }
                if err := process(ctx, task); err != nil {
                    return err
                }
            }
        }
    })
}

// Начальные воркеры
for i := 0; i < 10; i++ {
    addWorker()
}

// Динамически добавляем
go func() {
    for {
        time.Sleep(1 * time.Second)
        if load() > threshold {
            addWorker()
        }
    }
}()
```

**Проблема:** `errgroup` **не поддерживает** удаление воркеров. Только добавление.

### Когда динамическое N оправдано

**Оправдано:**

- **Нагрузка сильно варьируется** (день/ночь, всплески).
- **Внешний сервис имеет rate limit** — нужно адаптироваться.
- **CPU/память ограничены** — нужно экономить.

**Не оправдано:**

- **Стабильная нагрузка.** Фиксированное N проще.
- **Малая система.** Overhead не окупается.

### Аннотация сложности

| Операция | Time | Space |
|:---|:---|:---|
| Добавление воркера | ~100-300 нс | ~2.3 КБ |
| Удаление воркера | ~100-300 нс | 0 |
| Проверка нагрузки | ~мкс | 0 |

### 💡 Практика: когда использовать динамическое N

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Динамическое N** — если нагрузка сильно варьируется.
2. **`stopCh` для уменьшения** — отдельный канал.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Метрики нагрузки** — CPU, длина очереди.
4. **Пороги** — когда добавлять/удалять воркеров.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

4. **Динамическое N для стабильной нагрузки** — overhead не нужен.

**❌ НЕ ДЕЛАЙ:**

5. **Не меняй N слишком часто** — overhead на создание/удаление.
6. **Не забывай про backpressure** — динамическое N не заменяет его.

### Ключевые выводы подглавы 7.7

- **Динамическое N** — для переменной нагрузки.
- **`stopCh`** — для уменьшения.
- **`errgroup`** — только для добавления.
- **Пороги** — CPU, длина очереди.
- **Не меняй N слишком часто.**

## 7.8 Worker pool vs семафор

Разберём **разницу** между worker pool и семафором.

### Семафор

**Семафор** — примитив, ограничивающий доступ к ресурсу. Реализуется через **буферизованный канал**:

```go
sem := make(chan struct{}, 10)  // семафор на 10

for _, task := range tasks {
    sem <- struct{}{}  // захватить слот
    go func(t Task) {
        defer func() { <-sem }()  // освободить
        process(t)
    }(task)
}
```

**Что происходит:**

- 10 слотов.
- Каждая задача **захватывает** слот.
- Когда все 10 заняты — новая задача **ждёт**.
- После завершения — слот **освобождается**.

### Worker pool

```go
tasksCh := make(chan Task, 100)

for i := 0; i < 10; i++ {
    go func() {
        for task := range tasksCh {
            process(task)
        }
    }()
}
```

**Что происходит:**

- 10 воркеров.
- Воркеры **читают** задачи из канала.
- Один воркер обрабатывает много задач.

### Ключевые различия

| Аспект | Worker pool | Семафор |
|:---|:---|:---|
| Горутин | N (фиксировано) | N + 1 на задачу (создаются и завершаются) |
| Создание горутин | N раз | На каждую задачу |
| Память | N × 2.3 КБ | N × 2.3 КБ + переиспользование |
| Overhead | Низкий | Средний (создание/завершение G) |
| Backpressure | Через канал | Через канал |
| Отмена | Через `context` | Через `context` |

### Пример: когда что использовать

**Worker pool:**

- **Много задач** (10 000).
- **Задачи однотипные.**
- **Важна производительность.**
- **Воркеры переиспользуются.**

**Семафор:**

- **Мало задач** (100).
- **Задачи разные.**
- **Простота важнее производительности.**
- **Нужно ограничить доступ к ресурсу** (например, БД-соединения).

### Пример: семафор для БД

```go
var dbSem = make(chan struct{}, 10)  // 10 одновременных запросов

func queryDB(ctx context.Context, query string) (Result, error) {
    select {
    case dbSem <- struct{}{}:
        defer func() { <-dbSem }()
    case <-ctx.Done():
        return Result{}, ctx.Err()
    }
    return db.Query(ctx, query)
}
```

**Что происходит:** не более 10 одновременных БД-запросов. Остальные ждут.

### Пример: worker pool для HTTP

```go
tasksCh := make(chan Task, 100)
for i := 0; i < 20; i++ {
    go func() {
        for task := range tasksCh {
            resp, _ := http.Get(task.URL)
            _ = resp
        }
    }()
}
```

**Что происходит:** 20 воркеров, каждый обрабатывает много URL.

### Аннотация сложности

| Аспект | Worker pool | Семафор |
|:---|:---|:---|
| Горутин | N | N + задачи |
| Создание G | N | N + задачи |
| Память | N × 2.3 КБ | (N + задачи) × 2.3 КБ |
| Overhead | ~100-300 нс на N | ~100-300 нс на задачу |

### 💡 Практика: как выбирать

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Worker pool** — для многих однотипных задач.
2. **Семафор** — для ограничения доступа к ресурсу.

**👍 СТОИТ СДЕЛАТЬ:**

3. **Семафор для БД-соединений** — ограничить pool.
4. **Worker pool для HTTP-запросов** — переиспользование воркеров.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

5. **Комбинация:** worker pool + семафор внутри воркера.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай горутину на каждую задачу**, если задач много. Используй worker pool.
7. **Не используй worker pool для ограничения ресурса** — семафор лучше.

### Ключевые выводы подглавы 7.8

- **Worker pool:** N воркеров, переиспользование.
- **Семафор:** N + задачи горутин, создание на каждую.
- **Worker pool** — для многих задач.
- **Семафор** — для ограничения ресурса.

## 7.9 Обработка ошибок и отмена

Разберём **обработку ошибок** и **отмену** в worker pool.

### Проблема: ошибки в воркерах

```go
for task := range tasksCh {
    result := process(task)  // если ошибка?
    resultsCh <- result
}
```

**Варианты:**

1. **Игнорировать.** Плохо — ошибки теряются.
2. **Логировать.** Лучше, но не отменяет работу.
3. **Отменить всё.** Хорошо для критичных ошибок.

### `context.Context` для отмены

```go
func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    
    tasksCh := make(chan Task, 100)
    resultsCh := make(chan Result, 100)
    
    var wg sync.WaitGroup
    for i := 0; i < 20; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for task := range tasksCh {
                select {
                case <-ctx.Done():
                    return
                case resultsCh <- process(ctx, task):
                }
            }
        }()
    }
    
    // Producer с отменой
    go func() {
        defer close(tasksCh)
        for _, url := range urls {
            select {
            case tasksCh <- Task{URL: url}:
            case <-ctx.Done():
                return
            }
        }
    }()
    
    // Collector
    go func() {
        wg.Wait()
        close(resultsCh)
    }()
    
    for result := range resultsCh {
        if result.Err != nil {
            cancel()  // отменяем всё при ошибке
        }
    }
}
```

**Что происходит:**

1. `ctx` создан с `cancel`.
2. Воркеры проверяют `ctx.Done()` в `select`.
3. Producer проверяет `ctx.Done()` при отправке.
4. Collector вызывает `cancel()` при ошибке.
5. Все воркеры и producer завершаются.

### `errgroup` для обработки ошибок

```go
import "golang.org/x/sync/errgroup"

func main() {
    g, ctx := errgroup.WithContext(context.Background())
    
    tasksCh := make(chan Task, 100)
    
    // Воркеры
    for i := 0; i < 20; i++ {
        g.Go(func() error {
            for task := range tasksCh {
                select {
                case <-ctx.Done():
                    return ctx.Err()
                default:
                }
                if err := process(ctx, task); err != nil {
                    return err  // отменяет всё
                }
            }
            return nil
        })
    }
    
    // Producer
    go func() {
        defer close(tasksCh)
        for _, url := range urls {
            select {
            case tasksCh <- Task{URL: url}:
            case <-ctx.Done():
                return
            }
        }
    }()
    
    if err := g.Wait(); err != nil {
        log.Fatal(err)
    }
}
```

**Что делает `errgroup`:**

1. Запускает N горутин.
2. При **первой** ошибке — отменяет `ctx`.
3. `g.Wait()` возвращает первую ошибку (или `nil`).

### Сбор нескольких ошибок

**`errors.Join` (Go 1.20+):**

```go
var errs []error

for result := range resultsCh {
    if result.Err != nil {
        errs = append(errs, result.Err)
    }
}

if len(errs) > 0 {
    return errors.Join(errs...)
}
```

**`multierror` (HashiCorp):**

```go
import "github.com/hashicorp/go-multierror"

var result *multierror.Error
for r := range resultsCh {
    if r.Err != nil {
        result = multierror.Append(result, r.Err)
    }
}
return result.ErrorOrNil()
```

### Паттерн: ошибка не отменяет всё

```go
for task := range tasksCh {
    result := process(ctx, task)
    if result.Err != nil {
        // Логируем, но не отменяем
        log.Printf("task %d failed: %v", task.ID, result.Err)
    }
    resultsCh <- result
}
```

**Когда использовать:** если ошибки **не критичны** (например, один URL из 10 000 недоступен).

### Аннотация сложности

| Подход | Отмена | Ошибок | Сложность |
|:---|:---|:---|:---|
| Игнорировать | ❌ | 0 | Низкая |
| Логировать | ❌ | Все | Низкая |
| `context` + `cancel` | ✅ | Первая | Средняя |
| `errgroup` | ✅ | Первая | Низкая |
| `errors.Join` | ❌ | Все | Средняя |

### 💡 Практика: как обрабатывать ошибки

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`context.Context`** для отмены.
2. **`errgroup`** для критичных ошибок.
3. **`select` с `ctx.Done()`** в воркерах и producer.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`errors.Join`** — если нужно собрать все ошибки.
5. **Логирование** — для некритичных ошибок.

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **`multierror`** — если Go < 1.20.

**❌ НЕ ДЕЛАЙ:**

7. **Не игнорируй ошибки.** Логируй или отменяй.
8. **Не забывай `ctx.Done()` в `select`.** Иначе отмена не сработает.

### Ключевые выводы подглавы 7.9

- **`context.Context`** — для отмены.
- **`errgroup`** — для критичных ошибок (отменяет всё).
- **`errors.Join`** — для сбора всех ошибок.
- **`select` с `ctx.Done()`** — в воркерах и producer.
- **Логирование** — для некритичных.

## 7.10 Практика Go: worker pool с метриками

Напишем **worker pool с метриками**.

### Полный код

```go
package main

import (
    "context"
    "fmt"
    "net/http"
    "sync"
    "sync/atomic"
    "time"
)

type Task struct {
    ID  int
    URL string
}

type Result struct {
    TaskID   int
    Status   int
    Err      error
    Duration time.Duration
}

type Metrics struct {
    TasksProcessed atomic.Int64
    TasksFailed    atomic.Int64
    TotalDuration  atomic.Int64  // в наносекундах
    ActiveWorkers  atomic.Int64
}

func main() {
    urls := make([]string, 1000)
    for i := range urls {
        urls[i] = "https://example.com"
    }

    const numWorkers = 20

    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    tasksCh := make(chan Task, 100)
    resultsCh := make(chan Result, 100)

    var metrics Metrics

    // Запуск воркеров
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go worker(ctx, i, tasksCh, resultsCh, &metrics, &wg)
    }

    // Producer
    go func() {
        defer close(tasksCh)
        for i, url := range urls {
            select {
            case tasksCh <- Task{ID: i, URL: url}:
            case <-ctx.Done():
                return
            }
        }
    }()

    // Закрытие resultsCh
    go func() {
        wg.Wait()
        close(resultsCh)
    }()

    // Мониторинг метрик
    go func() {
        ticker := time.NewTicker(1 * time.Second)
        defer ticker.Stop()
        for range ticker.C {
            fmt.Printf("processed: %d, failed: %d, active: %d\n",
                metrics.TasksProcessed.Load(),
                metrics.TasksFailed.Load(),
                metrics.ActiveWorkers.Load())
        }
    }()

    // Collector
    start := time.Now()
    for result := range resultsCh {
        if result.Err != nil {
            metrics.TasksFailed.Add(1)
        }
    }

    fmt.Printf("\nTotal time: %v\n", time.Since(start))
    fmt.Printf("Processed: %d\n", metrics.TasksProcessed.Load())
    fmt.Printf("Failed: %d\n", metrics.TasksFailed.Load())
    if metrics.TasksProcessed.Load() > 0 {
        avg := time.Duration(metrics.TotalDuration.Load() / metrics.TasksProcessed.Load())
        fmt.Printf("Avg duration: %v\n", avg)
    }
}

func worker(ctx context.Context, id int, tasksCh <-chan Task, resultsCh chan<- Result,
    metrics *Metrics, wg *sync.WaitGroup) {
    defer wg.Done()
    
    for {
        select {
        case <-ctx.Done():
            return
        case task, ok := <-tasksCh:
            if !ok {
                return
            }
            
            metrics.ActiveWorkers.Add(1)
            start := time.Now()
            result := process(ctx, task)
            result.Duration = time.Since(start)
            metrics.ActiveWorkers.Add(-1)
            
            metrics.TasksProcessed.Add(1)
            metrics.TotalDuration.Add(int64(result.Duration))
            
            select {
            case resultsCh <- result:
            case <-ctx.Done():
                return
            }
        }
    }
}

func process(ctx context.Context, task Task) Result {
    req, err := http.NewRequestWithContext(ctx, "GET", task.URL, nil)
    if err != nil {
        return Result{TaskID: task.ID, Err: err}
    }
    
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return Result{TaskID: task.ID, Err: err}
    }
    defer resp.Body.Close()
    
    return Result{TaskID: task.ID, Status: resp.StatusCode}
}
```

### Что демонстрирует

1. **Worker pool** с 20 воркерами.
2. **Метрики:** processed, failed, active, total duration.
3. **Отмена через `context.WithTimeout`.**
4. **Backpressure** через буферизованные каналы.
5. **Мониторинг** в реальном времени.

### Пример вывода

```
processed: 234, failed: 0, active: 20
processed: 512, failed: 2, active: 20
processed: 789, failed: 3, active: 20
...

Total time: 3.456s
Processed: 1000
Failed: 3
Avg duration: 65ms
```

### Аннотация сложности

| Метрика | Как измеряется |
|:---|:---|
| Processed | `atomic.Int64` |
| Failed | `atomic.Int64` |
| Active | `atomic.Int64` |
| Duration | `time.Since` + `atomic.Int64` |

### 💡 Практика: как измерять worker pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Метрики:** processed, failed, active.
2. **Latency:** среднее время обработки.
3. **Мониторинг** в реальном времени.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`atomic.Int64`** для метрик — быстрее `Mutex`.
5. **Экспорт в Prometheus** (если production).

**🤔 НЕ ОБЯЗАТЕЛЬНО:**

6. **Percentile latency** (p50, p95, p99) — сложнее, но полезно.

**❌ НЕ ДЕЛАЙ:**

7. **Не используй `Mutex` для метрик** — `atomic` быстрее.
8. **Не игнорируй метрики.** Они показывают, работает ли pool.

### Ключевые выводы подглавы 7.10

- **Метрики:** processed, failed, active, duration.
- **`atomic.Int64`** — для счётчиков.
- **Мониторинг** в реальном времени.
- **Экспорт в Prometheus** — для production.

## 7.11 Выводы и типичные ошибки

**Что мы узнали?**

Worker pool — паттерн для ограничения параллелизма. N воркеров читают задачи из канала, пишут результаты в канал. Producer закрывает `tasksCh`. Отдельная горутина с `wg.Wait()` закрывает `resultsCh`. Backpressure — замедление потребителя замедляет производителя. Динамическое N — для переменной нагрузки. Worker pool vs семафор: pool переиспользует воркеров, семафор создаёт горутину на задачу. Обработка ошибок: `context.Context` для отмены, `errgroup` для критичных ошибок, `errors.Join` для сбора всех. Метрики: `atomic.Int64` для счётчиков.

**Типичные ошибки:**

- ❌ **Создавать горутину на каждую задачу без ограничения.** OOM, исчерпание fd.
- ❌ **Не буферизовать каналы.** Producer блокируется слишком часто.
- ❌ **Огромные буферы.** Маскируют проблему, память растёт.
- ❌ **Закрывать `tasksCh` в воркерах.** Только producer.
- ❌ **Закрывать `resultsCh` в main до чтения.** Deadlock.
- ❌ **Забывать `wg.Done()`.** `wg.Wait()` не вернётся.
- ❌ **Писать в общий слайс без синхронизации.** Гонка.
- ❌ **Игнорировать `ctx.Done()`.** Отмена не сработает.
- ❌ **Не обрабатывать ошибки.** Теряются.
- ❌ **Не мониторить метрики.** Не видно проблем.
- ❌ **Слишком много воркеров.** Конкуренция за CPU, rate limit.
- ❌ **Слишком мало воркеров.** Недоиспользование ресурсов.
- ❌ **Менять N слишком часто.** Overhead.

## 7.12 Для быстрого повторения

- **Worker pool:** N воркеров + канал задач + канал результатов.
- **N:** CPU-bound → `GOMAXPROCS`, I/O-bound → 10-100.
- **Каналы:** буферизованные (100-1000).
- **Producer закрывает `tasksCh`.** Отдельная горутина с `wg.Wait()` закрывает `resultsCh`.
- **`for range`** в воркерах и коллекторе — автоматическое завершение.
- **Backpressure:** маленький буфер результатов, разумный буфер задач.
- **Сбор результатов:** канал (рекомендуется), Mutex + слайс, atomic + слайс.
- **Динамическое N:** `stopCh` для уменьшения, `errgroup` для добавления.
- **Worker pool vs семафор:** pool переиспользует, семафор создаёт на задачу.
- **Обработка ошибок:** `context`, `errgroup`, `errors.Join`.
- **Метрики:** `atomic.Int64` для processed, failed, active.
- **Формула:** `N = GOMAXPROCS × (1 + wait/compute)`.
- **Мониторь:** `NumGoroutine`, file descriptors, длина очередей.

## 7.14 Ответы

### Ответ 1

**Три причины:**
1. **Память:** 10 000 горутин × 2.3 КБ = 23 МБ.
2. **File descriptors:** 10 000 TCP-соединений, лимит 1024.
3. **Давление на GC:** 10 000 `g`-структур, частые сборки.

### Ответ 2

**Worker pool** — N воркеров обрабатывают задачи из канала. Ограничивает параллелизм до N, переиспользует воркеров, контролирует ресурсы (fd, память).

### Ответ 3

**CPU-bound:** N = `GOMAXPROCS` (число ядер).

**I/O-bound:** N = 10-100 (зависит от latency внешнего сервиса).

### Ответ 4

**Шаги:**
1. Канал задач (буферизованный).
2. Канал результатов.
3. Запуск N воркеров.
4. Producer пишет задачи, закрывает `tasksCh`.
5. Отдельная горутина с `wg.Wait()` закрывает `resultsCh`.
6. Collector читает результаты.

### Ответ 5

**Producer закрывает `tasksCh`**, потому что он **пишет** в канал. Воркеры **читают**. Закрытие на читателе → паника при отправке.

### Ответ 6

**`close(resultsCh)` в main → deadlock**, потому что `for range resultsCh` блокируется, ждёт результатов. Воркеры не могут завершиться, пока `tasksCh` не закрыт. `close` не выполняется.

**Решение:** отдельная горутина с `wg.Wait()`.

### Ответ 7

**Три подхода:**
1. **Канал результатов** (рекомендуется) — нет гонок, backpressure.
2. **Mutex + слайс** — просто, все результаты в памяти.
3. **Atomic + слайс** — быстро, но нужен размер заранее.

### Ответ 8

**Backpressure** — замедление потребителя замедляет производителя.

**Обеспечить:** маленький буфер результатов, разумный буфер задач, `select` с `ctx.Done()`.

### Ответ 9

**Большие буферы маскируют проблему**, потому что producer и воркеры не блокируются, пока буфер не полон. Но если producer быстрее collector надолго — буферы переполнятся.

### Ответ 10

**Динамическое N:**
- **Добавление:** запуск новых воркеров.
- **Уменьшение:** `stopCh` — сигнал воркеру завершиться.
- **`errgroup`** — только добавление.

### Ответ 11

**Worker pool:** N воркеров, переиспользование. **Семафор:** N + задачи горутин, создание на каждую.

**Worker pool** — для многих однотипных задач. **Семафор** — для ограничения доступа к ресурсу.

### Ответ 12

**Обработка ошибок:**
- **Логирование** — для некритичных.
- **`context` + `cancel`** — для критичных.
- **`errgroup`** — для первой ошибки.

### Ответ 13

**`errgroup`:**
1. Запускает N горутин.
2. При первой ошибке — отменяет `ctx`.
3. `g.Wait()` возвращает первую ошибку (или `nil`).

### Ответ 14

**`errors.Join` (Go 1.20+):**
```go
return errors.Join(errs...)
```

**`multierror` (HashiCorp):** для Go < 1.20.

### Ответ 15

**Метрики:**
- **Processed:** `atomic.Int64`.
- **Failed:** `atomic.Int64`.
- **Active:** `atomic.Int64`.
- **Duration:** `time.Since` + `atomic.Int64`.
- **Мониторинг:** ticker + вывод.

### Ответ 16

**`atomic.Int64` лучше `Mutex`**, потому что:
- **Быстрее** в 2-5 раз.
- **Нет contention** — нет блокировки.
- **Проще** — одна операция.

### Ответ 17

**Без `wg.Done()`:** `wg.Wait()` не вернётся. `close(resultsCh)` не выполнится. Deadlock.

### Ответ 18

**Писать в общий слайс без синхронизации — гонка.** `append` — не атомарная операция. Нужен `Mutex` или `atomic`.

## 7.16 Чек-лист

| Компонент | Что это | Ключевые факты |
|:---|:---|:---|
| **Worker pool** | N воркеров + каналы | Ограничивает параллелизм до N |
| **N** | Число воркеров | CPU-bound → `GOMAXPROCS`, I/O-bound → 10-100 |
| **`tasksCh`** | Канал задач | Буферизованный (100-1000). Producer закрывает |
| **`resultsCh`** | Канал результатов | Маленький буфер (или небуферизованный) |
| **Producer** | Пишет задачи | Закрывает `tasksCh` через `defer close` |
| **Воркеры** | Читают задачи | `for range tasksCh`, `wg.Done()` |
| **Collector** | Читает результаты | `for range resultsCh` |
| **`close(resultsCh)`** | Закрытие | Отдельная горутина с `wg.Wait()` |
| **Backpressure** | Замедление производителя | Через маленький буфер результатов |
| **Динамическое N** | Переменное число воркеров | `stopCh` для уменьшения |
| **Worker pool vs семафор** | Переиспользование vs ограничение | Pool для многих задач, семафор для ресурса |
| **`errgroup`** | Обработка ошибок | Отменяет при первой ошибке |
| **`errors.Join`** | Сбор ошибок | Go 1.20+ |
| **Метрики** | `atomic.Int64` | Processed, failed, active, duration |
| **`NumGoroutine`** | Мониторинг | Рост без падения = утечка |
| **File descriptors** | Мониторинг | `lsof -p <pid> \| wc -l` |

🏊 **Ключевая идея:** Worker pool ограничивает параллелизм до N воркеров. Producer пишет задачи в `tasksCh` и закрывает его. Отдельная горутина с `wg.Wait()` закрывает `resultsCh`. Backpressure — замедление потребителя замедляет производителя. Сбор результатов: канал (рекомендуется), Mutex + слайс, atomic + слайс. Обработка ошибок: `context`, `errgroup`, `errors.Join`. Метрики: `atomic.Int64`. N для CPU-bound — `GOMAXPROCS`, для I/O-bound — 10-100. Мониторь `NumGoroutine`, file descriptors, длину очередей.
