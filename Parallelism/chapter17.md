## 17.0 Пролог: сервис, который тонет в аллокациях

Ты пишешь высоконагруженный HTTP-сервис. 100 000 запросов в секунду. Каждый запрос создаёт `[]byte` буфер на 4 КБ.

```go
func handler(w http.ResponseWriter, r *http.Request) {
    buf := make([]byte, 4096)  // ← 100 000 аллокаций в секунду
    n, _ := r.Body.Read(buf)
    process(buf[:n])
}
```

Профилирование показывает: **40% CPU в GC**. Память растёт, паузы GC — 5-10 мс.

❓ **Что произошло?** Ты создаёшь **400 МБ в секунду** мусора. GC не успевает.

💡 **Решение:** **`sync.Pool`**. Переиспользовать буферы вместо создания новых.

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    n, _ := r.Body.Read(buf)
    process(buf[:n])
}
```

**Что изменилось:** аллокаций почти нет. GC нагрузка упала в разы. Паузы — микросекунды.

**Это `sync.Pool`.** В этой главе — как он работает, когда помогает, когда вредит, и как устроен аллокатор Go.

> **Важный мост:** `sync.Pool` работает **вместе с GC**. Глава 18 (GC) — как GC взаимодействует с `Pool`. Глава 16 (Lock-free) — почему `Pool` использует `atomic`. Глава 12 (Профилирование) — как измерить аллокации.

## 17.1 Аллокации — главный источник нагрузки на GC

Прежде чем разбирать `sync.Pool`, поймём **почему аллокации дороги**.

### Как работает GC

**GC (Garbage Collector)** в Go:

1. Находит объекты, которые **больше не используются**.
2. Освобождает их память.
3. Работает **параллельно** с программой (concurrent).
4. Имеет **STW** (Stop-The-World) паузы — короткие, но есть.

**Что нагружает GC:**

- **Количество аллокаций** — сколько объектов создано.
- **Размер живых объектов** — сколько памяти занято.
- **Скорость аллокаций** — сколько байт/сек.

**Формула:**

```
GC частота = скорость аллокаций / (GOGC% × размер живых объектов)
```

**Пример:** 400 МБ/сек аллокаций, 100 МБ живых, GOGC=100.

```
GC частота = 400 / (1.0 × 100) = 4 раза в секунду
```

**Каждый GC:**

- Сканирует heap.
- Тратит CPU.
- Может вызвать STW паузу.

### Почему аллокации дороги

**1. Стоимость аллокации.**

- **`mallocgc`** — функция аллокатора.
- **Size class lookup** — поиск подходящего класса.
- **mcache** — локальный кэш.
- **Стоимость:** ~10-50 нс.

**2. Стоимость GC.**

- **Marking** — обход живых объектов.
- **Sweeping** — освобождение мёртвых.
- **Стоимость:** ~1-5% CPU на каждый GC.

**3. Стоимость памяти.**

- **Фрагментация** — свободные блоки разного размера.
- **Overhead** — заголовки объектов.
- **Стоимость:** ~10-30% памяти.

### Как уменьшить аллокации

**1. Escape analysis.**

Компилятор может разместить объект **на стеке** вместо кучи.

**2. `sync.Pool`.**

Переиспользовать объекты.

**3. Предварительное выделение.**

`make([]T, 0, capacity)` вместо `append`.

**4. Избегать интерфейсов.**

`interface{}` вызывает аллокацию.

**5. Избегать замыканий в hot path.**

Замыкания могут аллоцировать.

### Как измерить

**1. `-benchmem`:**

```bash
go test -bench=. -benchmem ./...
```

**Вывод:**

```
BenchmarkHandler-8    1000000    1500 ns/op    4096 B/op    1 allocs/op
```

**Что видно:** 4096 байт на операцию, 1 аллокация.

**2. pprof memory:**

```bash
go test -bench=. -memprofile=mem.prof ./...
go tool pprof mem.prof
```

**Что искать:** top аллокаций.

**3. `runtime.ReadMemStats`:**

```go
var m runtime.MemStats
runtime.ReadMemStats(&m)
fmt.Printf("Alloc: %d MB\n", m.Alloc/1024/1024)
fmt.Printf("TotalAlloc: %d MB\n", m.TotalAlloc/1024/1024)
fmt.Printf("NumGC: %d\n", m.NumGC)
```

### Аннотация сложности

| Операция | Time |
|:---|:---|
| Аллокация на стеке | ~1 нс |
| Аллокация в куче (маленькая) | ~10-50 нс |
| Аллокация в куче (большая) | ~100-1000 нс |
| GC (mark + sweep) | ~1-5% CPU |

### 💡 Практика: как уменьшить аллокации

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`-benchmem`** — измеряй аллокации.
2. **Escape analysis** — компилятор решает.
3. **`sync.Pool`** — для hot path.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Предварительное выделение** — `make([]T, 0, N)`.
5. **Избегай `interface{}`** в hot path.

**❌ НЕ ДЕЛАЙ:**

6. **Не оптимизируй аллокации преждевременно.**
7. **Не игнорируй pprof memory.**

### Ключевые выводы подглавы 17.1

- **Аллокации** нагружают GC.
- **GC частота** = скорость аллокаций / (GOGC% × живые).
- **Уменьшить:** escape analysis, `Pool`, предварительное выделение.
- **Измерить:** `-benchmem`, pprof memory.

## 17.2 Escape analysis: стек vs куча

**Escape analysis** — анализ компилятора, определяющий, где аллоцировать объект.

### Идея

**Стек** — быстрая память, освобождается автоматически.

**Куча** — медленнее, требует GC.

**Escape analysis** решает: объект **«убегает»** из функции?

- **Не убегает** → стек.
- **Убегает** → куча.

### Что значит «убегает»

**Объект убегает, если:**

1. **Возвращается** из функции.
2. **Сохраняется** в глобальной переменной.
3. **Передаётся** в другую горутину.
4. **Сохраняется** в интерфейсе.
5. **Адрес** сохраняется где-то.

### Пример: не убегает

```go
func sum() int {
    s := 0  // s на стеке
    for i := 0; i < 100; i++ {
        s += i
    }
    return s  // возвращаем значение, не указатель
}
```

**Что происходит:** `s` не убегает — на стеке.

### Пример: убегает

```go
func newInt() *int {
    x := 42
    return &x  // x убегает — возвращаем указатель
}
```

**Что происходит:** `x` убегает — в куче.

### Пример: интерфейс

```go
func process() {
    var x any = 42  // x убегает в интерфейс
    _ = x
}
```

**Что происходит:** `x` упакован в интерфейс — в куче.

### Как проверить

**`go build -gcflags=-m`:**

```bash
go build -gcflags=-m main.go
```

**Вывод:**

```
./main.go:5:6: can inline sum
./main.go:6:2: moved to heap: x
./main.go:12:2: x escapes to heap
```

**Что видно:** какие переменные убегают.

### Как избежать escape

**1. Не возвращать указатели на локальные переменные.**

```go
// ❌ Плохо
func newSlice() *[]int {
    s := make([]int, 10)
    return &s
}

// ✅ Хорошо
func newSlice() []int {
    return make([]int, 10)
}
```

**2. Не использовать `interface{}` в hot path.**

```go
// ❌ Плохо
func process(v any) {
    // ...
}

// ✅ Хорошо
func process[T any](v T) {
    // ...
}
```

**3. Не сохранять в замыканиях без необходимости.**

```go
// ❌ Плохо
func process() func() int {
    x := 42
    return func() int { return x }  // x убегает
}

// ✅ Хорошо
func process() int {
    x := 42
    return x
}
```

**4. `sync.Pool` для больших объектов.**

Если объект большой и не убегает — на стеке. Если убегает — `Pool`.

### Escape analysis и конкурентность

**Горутины** — escape analysis **не помогает** для данных, разделяемых между горутинами.

```go
func process() {
    data := make([]byte, 4096)
    go func() {
        // data убегает — в куче
        _ = data
    }()
}
```

**Что происходит:** `data` используется в другой горутине — в куче.

**Решение:** `sync.Pool`.

### Аннотация сложности

| Аллокация | Time |
|:---|:---|
| Стек | ~1 нс |
| Куча (маленькая) | ~10-50 нс |
| Куча (большая) | ~100-1000 нс |

### 💡 Практика: как использовать escape analysis

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`go build -gcflags=-m`** — проверяй escape.
2. **Не возвращай указатели** на локальные.
3. **Generic вместо `interface{}`.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **`sync.Pool`** для больших объектов.
5. **Профилирование** для hot path.

**❌ НЕ ДЕЛАЙ:**

6. **Не оптимизируй без профиля.**
7. **Не полагайся на escape analysis для горутин.**

### Ключевые выводы подглавы 17.2

- **Escape analysis** решает: стек или куча.
- **Убегает** → куча. **Не убегает** → стек.
- **Проверка:** `go build -gcflags=-m`.
- **Горутины** → данные в куче.
- **`sync.Pool`** для больших объектов.

## 17.3 Аллокатор Go: mcache, mcentral, mheap

Разберём **аллокатор** Go.

### Три уровня

**1. `mcache`** — локальный кэш для **каждого P**.

**2. `mcentral`** — общий для **всех P** кэш для каждого size class.

**3. `mheap`** — глобальный heap.

### Схема

```
┌─────────────────────────────────────────────────────────────┐
│                         mheap                               │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  spans (страницы по 8 КБ)                           │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
        │                                          │
        │ пополнение                               │ пополнение
        ▼                                          ▼
┌──────────────────┐                    ┌──────────────────┐
│  mcentral[8]     │                    │  mcentral[16]    │
│  (size class 8)  │                    │  (size class 16) │
└──────────────────┘                    └──────────────────┘
        │                                          │
        │ пополнение                               │ пополнение
        ▼                                          ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  mcache P0   │  │  mcache P1   │  │  mcache P2   │
│  [8][16][32] │  │  [8][16][32] │  │  [8][16][32] │
└──────────────┘  └──────────────┘  └──────────────┘
```

### mcache

**`mcache`** — локальный кэш для **каждого P**.

**Что хранит:** свободные объекты по size classes.

**Плюсы:**

- **Без блокировок** — каждый P имеет свой mcache.
- **Быстро** — объект берётся из mcache.

**Минусы:**

- **Ограничен** размером.
- **Периодически пополняется** из mcentral.

### mcentral

**`mcentral`** — общий кэш для каждого size class.

**Что хранит:** списки свободных span'ов.

**Использование:**

- Когда mcache пуст — берёт из mcentral.
- **С блокировкой** — mcentral защищён.

### mheap

**`mheap`** — глобальный heap.

**Что хранит:** все страницы памяти.

**Использование:**

- Когда mcentral пуст — берёт из mheap.
- **С блокировкой** — mheap защищён.

### Путь аллокации

```
mallocgc(size):
  1. Если size > 32 КБ:
       → large alloc из mheap
  2. Иначе:
       a. Найти size class для size.
       b. Взять объект из mcache.
       c. Если mcache пуст — пополнить из mcentral.
       d. Если mcentral пуст — пополнить из mheap.
```

**Ключевое:** **большинство аллокаций** — из mcache, **без блокировок**.

### Почему это быстро

**1. Локальность.**

Каждый P имеет свой mcache. Нет contention.

**2. Size classes.**

Объекты одного размера. Нет фрагментации.

**3. Переиспользование.**

Освобождённые объекты возвращаются в mcache.

### Аннотация сложности

| Операция | Time |
|:---|:---|
| Аллокация из mcache | ~10-50 нс |
| Пополнение mcache из mcentral | ~100-500 нс |
| Пополнение mcentral из mheap | ~1-10 мкс |

### 💡 Практика: как использовать аллокатор эффективно

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Маленькие объекты** — из mcache, быстро.
2. **Одинаковые размеры** — size classes.
3. **`sync.Pool`** для больших.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Предварительное выделение** — `make([]T, 0, N)`.
5. **Избегай больших аллокаций** в hot path.

**❌ НЕ ДЕЛАЙ:**

6. **Не аллоцируй большие объекты** (> 32 КБ) часто.
7. **Не создавай объекты разного размера** в hot path.

### Ключевые выводы подглавы 17.3

- **Три уровня:** mcache (per P), mcentral (shared), mheap (global).
- **mcache** — без блокировок.
- **Большинство аллокаций** — из mcache.
- **Size classes** — одинаковые размеры.
- **`sync.Pool`** для больших.

## 17.4 Size classes: почему размер имеет значение

**Size classes** — классы размеров объектов.

### Что это

**Go аллокатор** имеет **фиксированный набор** размеров (size classes).

**Примеры:**

```
8, 16, 24, 32, 48, 64, 80, 96, 112, 128, ...
```

**Что происходит:**

- Объект размера 50 байт → класс 64 байта.
- Объект размера 100 байт → класс 112 байт.
- Объект размера 200 байт → класс 224 байта.

### Overhead

**Overhead** — разница между запрошенным и фактическим размером.

**Пример:**

- Запросили 50 байт.
- Получили 64 байта.
- **Overhead = 14 байт (28%).**

**Для маленьких объектов overhead больше.**

### Почему size classes

**1. Быстро.**

Каждый класс имеет свой mcache. Не нужно искать подходящий размер.

**2. Без фрагментации.**

Объекты одного размера. Нет «дырок».

**3. Переиспользование.**

Освобождённый объект размера 64 возвращается в пул 64.

### Как использовать

**1. Выбирай размеры, близкие к size classes.**

```go
// ❌ Плохо: 50 → 64 (overhead 28%)
buf := make([]byte, 50)

// ✅ Хорошо: 64 → 64 (overhead 0%)
buf := make([]byte, 64)
```

**2. Не создавай объекты разного размера.**

```go
// ❌ Плохо: разные размеры
for _, size := range []int{10, 50, 100, 200} {
    buf := make([]byte, size)
    // ...
}
```

**3. `sync.Pool` для повторяющихся размеров.**

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)  // фиксированный размер
    },
}
```

### Список size classes

**Маленькие (< 32 КБ):**

```
8, 16, 24, 32, 48, 64, 80, 96, 112, 128,
144, 160, 176, 192, 208, 224, 240, 256,
288, 320, 352, 384, 416, 448, 480, 512,
...
```

**Большие (> 32 КБ):**

Не имеют size class. Аллоцируются напрямую из mheap.

### Аннотация сложности

| Размер | Класс | Overhead |
|:---|:---|:---|
| 8 | 8 | 0% |
| 50 | 64 | 28% |
| 100 | 112 | 12% |
| 1000 | 1024 | 2.4% |
| 10000 | 10240 | 2.4% |

### 💡 Практика: как выбирать размеры

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Размеры, близкие к size classes** — 64, 128, 256, 512, 1024.
2. **Фиксированные размеры** в hot path.
3. **`sync.Pool`** для повторяющихся.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Избегай 50, 100, 200** — overhead.
5. **Профилируй** для hot path.

**❌ НЕ ДЕЛАЙ:**

6. **Не создавай объекты разного размера** в цикле.
7. **Не игнорируй overhead** для маленьких.

### Ключевые выводы подглавы 17.4

- **Size classes** — фиксированные размеры.
- **Overhead** для маленьких объектов.
- **Выбирай 64, 128, 256, 512, 1024.**
- **Фиксированные размеры** в hot path.
- **`sync.Pool`** для повторяющихся.

## 17.5 sync.Pool: идея и API

**`sync.Pool`** — пул переиспользуемых объектов.

### API

```go
type Pool struct {
    New func() any
}

func (p *Pool) Get() any
func (p *Pool) Put(x any)
```

**Три метода:**

- **`New`** — функция для создания новых объектов.
- **`Get`** — получить объект из пула.
- **`Put`** — вернуть объект в пул.

### Пример

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}

func process() {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)

    // используем buf
    _ = buf
}
```

**Что делает:**

1. `Get` — берёт буфер из пула.
2. `defer Put` — возвращает в пул.
3. Буфер переиспользуется.

### Важно: Pool не гарантирует

**Ключевое:** `sync.Pool` **не гарантирует**, что `Get` вернёт объект из `Put`.

**Причины:**

1. **GC очищает Pool.** Объекты могут быть удалены при GC.
2. **Per-P пулы.** `Get` может не найти объект в **своём** P.
3. **Lock-free.** Конкурентные `Get`/`Put`.

**Что это значит:**

- `Get` может вернуть **новый** объект.
- `Put` может **не сохранить** объект.
- **Pool — оптимизация, не гарантия.**

### Паттерн: правильное использование

```go
func process(data []byte) ([]byte, error) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)

    // Используем buf
    n := copy(buf, data)
    return buf[:n], nil
}
```

**Важно:** `defer Put` — обязательно. Иначе утечка.

### Паттерн: с типом

```go
type Buffer struct {
    data []byte
}

var bufPool = sync.Pool{
    New: func() any {
        return &Buffer{data: make([]byte, 4096)}
    },
}

func getBuffer() *Buffer {
    return bufPool.Get().(*Buffer)
}

func putBuffer(b *Buffer) {
    b.data = b.data[:0]  // сброс
    bufPool.Put(b)
}
```

**Что делает:** типизированный пул с сбросом.

### Аннотация сложности

| Операция | Time |
|:---|:---|
| `Get` (есть объект) | ~10-20 нс |
| `Get` (нет объекта) | ~50-100 нс + `New` |
| `Put` | ~10-20 нс |

### 💡 Практика: как использовать sync.Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`defer Put`** — обязательно.
2. **Сброс состояния** перед `Put`.
3. **Фиксированный размер** объектов.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Типизированный пул** — с обёрткой.
5. **Бенчмаркай** с `Pool` и без.

**❌ НЕ ДЕЛАЙ:**

6. **Не полагайся на `Pool`** для критичных данных.
7. **Не забывай `Put`.**
8. **Не используй для маленьких объектов** (< 64 байт).

### Ключевые выводы подглавы 17.5

- **`sync.Pool`** — пул объектов.
- **`Get`, `Put`, `New`.**
- **Не гарантирует** переиспользование.
- **`defer Put`** — обязательно.
- **Для больших объектов.**

## 17.6 sync.Pool внутри: poolLocal и victim cache

Разберём **устройство** `sync.Pool`.

### Структура

```go
type Pool struct {
    noCopy noCopy

    local     unsafe.Pointer  // []poolLocal
    localSize uintptr

    victim     unsafe.Pointer  // []poolLocal (victim)
    victimSize uintptr

    New func() any
}

type poolLocal struct {
    poolLocalInternal

    // Padding для false sharing
    pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
}

type poolLocalInternal struct {
    private any       // приватный объект
    shared  poolChain  // shared (lock-free)
}
```

### Два уровня: private и shared

**private:**

- **Приватный** объект для каждого P.
- **Без блокировок.**
- **Только один** объект.

**shared:**

- **Lock-free** очередь.
- **Много** объектов.
- **Может** быть доступен другим P.

### Get

```go
func (p *Pool) Get() any {
    l, pid := p.pin()
    x := l.private
    l.private = nil

    if x == nil {
        x, _ = l.shared.popHead()
        if x == nil {
            x = p.getSlow(pid)
        }
    }

    runtime_procUnpin()
    if x == nil && p.New != nil {
        x = p.New()
    }
    return x
}
```

**Что делает:**

1. **Private** — берёт приватный объект (быстро).
2. **Shared** — берёт из shared очереди.
3. **getSlow** — пробует украсть у других P.
4. **New** — создаёт новый.

### Put

```go
func (p *Pool) Put(x any) {
    if x == nil {
        return
    }
    l, _ := p.pin()
    if l.private == nil {
        l.private = x
        x = nil
    }
    if x != nil {
        l.shared.pushHead(x)
    }
    runtime_procUnpin()
}
```

**Что делает:**

1. **Private** — если пусто, кладёт в private.
2. **Shared** — иначе в shared.

### Victim cache

**Ключевая идея:** при GC **не удалять** объекты сразу, а **перемещать** в `victim`.

```
До GC:
  local: [объекты]
  victim: nil

После GC:
  local: nil
  victim: [старые объекты]

Через один GC:
  local: [новые объекты]
  victim: nil (старые удалены)
```

**Что это даёт:**

- Объекты **живут два GC** вместо одного.
- Больше шансов переиспользовать.
- Меньше аллокаций.

### False sharing

```go
pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
```

**Что делает:** padding до 128 байт (2 кэш-линии).

**Зачем:** избежать **false sharing** (Глава 16).

### Аннотация сложности

| Операция | Time |
|:---|:---|
| `Get` из private | ~10-20 нс |
| `Get` из shared | ~50-100 нс |
| `Get` из victim | ~50-100 нс |
| `Get` с New | ~100-500 нс |
| `Put` в private | ~10-20 нс |
| `Put` в shared | ~50-100 нс |

### 💡 Практика: как понять поведение Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Помни: Pool очищается при GC.**
2. **Victim cache** — объекты живут 2 GC.
3. **Private** — быстрее всего.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Не полагайся на Pool** для долгоживущих объектов.
5. **Бенчмаркай** с GC и без.

**❌ НЕ ДЕЛАЙ:**

6. **Не ожидай 100% переиспользования.**
7. **Не используй Pool для маленьких объектов.**

### Ключевые выводы подглавы 17.6

- **`Pool`** — `poolLocal` для каждого P.
- **Private** — быстро. **Shared** — lock-free.
- **Victim cache** — объекты живут 2 GC.
- **Padding** — против false sharing.
- **GC очищает Pool.**

## 17.7 Когда sync.Pool помогает

Разберём **когда Pool помогает**.

### 1. Hot-path аллокации

**Проблема:** функция вызывается **миллионы раз** в секунду.

```go
func handleRequest(data []byte) {
    buf := make([]byte, 4096)  // ← миллионы аллокаций
    // ...
}
```

**Решение:** `sync.Pool`.

**Выигрыш:** аллокаций почти нет.

### 2. Большие объекты

**Проблема:** объект > 1 КБ.

```go
buf := make([]byte, 64*1024)  // 64 КБ
```

**Решение:** `Pool`.

**Выигрыш:** GC нагрузка падает в разы.

### 3. Одинаковые размеры

**Проблема:** много объектов **одного** размера.

```go
for i := 0; i < 100000; i++ {
    buf := make([]byte, 4096)  // все одного размера
}
```

**Решение:** `Pool` с фиксированным размером.

### 4. JSON/Protobuf буферы

**Проблема:** сериализация создаёт много `[]byte`.

```go
data, _ := json.Marshal(v)  // аллокация
```

**Решение:** `Pool` для буферов + `json.Encoder`.

### 5. HTTP body

**Проблема:** чтение body создаёт буфер.

```go
body, _ := io.ReadAll(r.Body)  // аллокация
```

**Решение:** `Pool` для буферов + `io.CopyBuffer`.

### Пример: HTTP handler с Pool

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 32*1024)
    },
}

func handler(w http.ResponseWriter, r *http.Request) {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)

    body := buf[:0]
    for {
        n, err := r.Body.Read(buf)
        body = append(body, buf[:n]...)
        if err != nil {
            break
        }
    }
    process(body)
}
```

### Аннотация сложности

| Сценарий | Без Pool | С Pool |
|:---|:---|:---|
| 1M аллокаций 4 КБ | ~4 ГБ мусора | ~0 |
| GC нагрузка | 40% CPU | 5% CPU |
| Паузы GC | 5-10 мс | < 1 мс |

### 💡 Практика: когда использовать Pool

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **Hot-path аллокации.**
2. **Большие объекты** (> 1 КБ).
3. **Одинаковые размеры.**

**👍 СТОИТ СДЕЛАТЬ:**

4. **JSON/Protobuf буферы.**
5. **HTTP body.**

**❌ НЕ ДЕЛАЙ:**

6. **Не используй для маленьких объектов.**
7. **Не используй для долгоживущих.**

### Ключевые выводы подглавы 17.7

- **Pool помогает** для hot-path, больших объектов, одинаковых размеров.
- **JSON/Protobuf буферы** — идеальный случай.
- **HTTP body** — тоже.
- **GC нагрузка падает в разы.**

## 17.8 Когда sync.Pool вредит

Разберём **когда Pool вредит**.

### 1. Маленькие объекты

**Проблема:** объект < 64 байт.

```go
var intPool = sync.Pool{
    New: func() any { return new(int) },
}
```

**Что происходит:**

- Аллокация из mcache — ~10-50 нс.
- `Pool.Get` — ~10-20 нс.
- **Выигрыш минимален.**

**Хуже:** Pool добавляет overhead.

### 2. Редкие аллокации

**Проблема:** функция вызывается **раз в секунду**.

```go
func rare() {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
}
```

**Что происходит:**

- GC очищает Pool между вызовами.
- `Get` всегда создаёт новый объект.
- **Pool бесполезен.**

### 3. Долгоживущие объекты

**Проблема:** объект живёт **часы**.

```go
conn := connPool.Get().(*Conn)
// используем часы
```

**Что происходит:**

- Объект не возвращается в Pool.
- Pool пуст.
- **Другие горутины создают новые.**

### 4. Разные размеры

**Проблема:** объекты разного размера.

```go
for _, size := range []int{10, 100, 1000, 10000} {
    buf := make([]byte, size)
}
```

**Что происходит:**

- Pool не может переиспользовать.
- **Разные size classes.**

### 5. Не забывать Put

**Проблема:** забыли `Put`.

```go
func bad() {
    buf := bufPool.Get().([]byte)
    // забыли Put
    _ = buf
}
```

**Что происходит:**

- Объект не возвращается.
- **Утечка.**

### 6. Состояние между использованиями

**Проблема:** объект сохраняет состояние.

```go
buf := bufPool.Get().([]byte)
// buf содержит старые данные
```

**Решение:** сброс перед использованием или после Put.

```go
func getBuffer() []byte {
    buf := bufPool.Get().([]byte)
    return buf[:0]  // сброс длины
}

func putBuffer(buf []byte) {
    if cap(buf) > 64*1024 {
        return  // не храним слишком большие
    }
    bufPool.Put(buf)
}
```

### 7. GC pressure

**Проблема:** Pool хранит объекты, GC их сканирует.

**Что происходит:**

- Если объектов много — GC тратит время.
- Victim cache — объекты живут 2 GC.

**Решение:** ограничить размер Pool.

### Аннотация сложности

| Сценарий | Pool помогает? |
|:---|:---|
| Hot path, большие | ✅ Да |
| Маленькие (< 64) | ❌ Нет |
| Редкие | ❌ Нет |
| Долгоживущие | ❌ Нет |
| Разные размеры | ❌ Нет |
| Забыли Put | ❌ Утечка |

### 💡 Практика: когда Pool вредит

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`Put`** — обязательно.
2. **Сброс состояния** перед использованием.
3. **Ограничить размер** объектов.

**👍 СТОИТ СДЕЛАТЬ:**

4. **Бенчмаркай** с Pool и без.
5. **Профилируй** GC.

**❌ НЕ ДЕЛАЙ:**

6. **Не используй Pool для маленьких.**
7. **Не используй для долгоживущих.**
8. **Не забывай Put.**

### Ключевые выводы подглавы 17.8

- **Pool вредит** для маленьких, редких, долгоживущих, разных размеров.
- **Не забывай Put.**
- **Сброс состояния** обязателен.
- **Бенчмаркай** перед использованием.

## 17.9 Практика Go: измерение аллокаций

Напишем **бенчмарки** для измерения аллокаций.

### Код

```go
package benchmarks

import (
    "bytes"
    "sync"
    "testing"
)

// Без Pool
func processNoPool(data []byte) []byte {
    buf := make([]byte, 4096)
    n := copy(buf, data)
    return buf[:n]
}

// С Pool
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 4096)
    },
}

func processWithPool(data []byte) []byte {
    buf := bufPool.Get().([]byte)
    defer bufPool.Put(buf)
    n := copy(buf, data)
    return buf[:n]
}

// Без предварительного выделения
func concatNoPrealloc(parts [][]byte) []byte {
    var result []byte
    for _, p := range parts {
        result = append(result, p...)
    }
    return result
}

// С предварительным выделением
func concatPrealloc(parts [][]byte) []byte {
    total := 0
    for _, p := range parts {
        total += len(p)
    }
    result := make([]byte, 0, total)
    for _, p := range parts {
        result = append(result, p...)
    }
    return result
}

// bytes.Buffer без Pool
func concatBuffer(parts [][]byte) []byte {
    var buf bytes.Buffer
    for _, p := range parts {
        buf.Write(p)
    }
    return buf.Bytes()
}

// bytes.Buffer с Pool
var bufferPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func concatBufferPool(parts [][]byte) []byte {
    buf := bufferPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()
        bufferPool.Put(buf)
    }()
    for _, p := range parts {
        buf.Write(p)
    }
    return buf.Bytes()
}
```

## 17.10 Настройка GOGC и GOMEMLIMIT

Разберём **настройку GC**.

### GOGC

**`GOGC`** — процент роста heap до следующего GC.

**Формула:**

```
Следующий GC, когда heap вырастет на GOGC% от живых объектов.
```

**Пример:** GOGC=100, живых 100 МБ → GC при 200 МБ.

**Значения:**

- **`GOGC=100`** — по умолчанию.
- **`GOGC=200`** — GC реже, память больше.
- **`GOGC=50`** — GC чаще, память меньше.
- **`GOGC=off`** — GC отключён.

**Настройка:**

```bash
GOGC=200 ./app
```

Или:

```go
import "runtime/debug"

debug.SetGCPercent(200)
```

### GOMEMLIMIT

**`GOMEMLIMIT`** (Go 1.19+) — soft limit на heap.

**Формула:**

```
GC агрессивнее, когда heap близок к GOMEMLIMIT.
```

**Пример:** `GOMEMLIMIT=1GiB`.

**Настройка:**

```bash
GOMEMLIMIT=1GiB ./app
```

Или:

```go
debug.SetMemoryLimit(1 * 1024 * 1024 * 1024)
```

### Комбинация GOGC и GOMEMLIMIT

**Рекомендация:**

- **`GOMEMLIMIT`** — soft limit.
- **`GOGC=off`** + **`GOMEMLIMIT`** — максимальная память, но GC только при лимите.
- **`GOGC=100`** + **`GOMEMLIMIT`** — компромисс.

**Пример:**

```bash
GOMEMLIMIT=1GiB GOGC=100 ./app
```

**Что происходит:**

- GC при 200 МБ (GOGC).
- Если heap близок к 1 ГБ — GC агрессивнее.

### В контейнерах

**Проблема:** `NumCPU()` возвращает **число ядер хоста**, а не контейнера.

**Решение:** `automaxprocs` + `GOMEMLIMIT`.

```go
import _ "go.uber.org/automaxprocs"

func main() {
    // GOMAXPROCS автоматически = CPU quota контейнера
}
```

**Для памяти:**

```bash
GOMEMLIMIT=<limit> ./app
```

Или через `debug.SetMemoryLimit`.

### Как выбрать

**1. Мало памяти.**

- `GOGC=50` — GC чаще.
- `GOMEMLIMIT=<limit>`.

**2. Много памяти.**

- `GOGC=200` — GC реже.
- `GOMEMLIMIT=<limit>`.

**3. Real-time.**

- `GOGC=off` + `GOMEMLIMIT` — минимум пауз.
- Но: heap растёт до лимита.

**4. Default.**

- `GOGC=100` + `GOMEMLIMIT` — компромисс.

### Аннотация сложности

| Настройка | GC частота | Память |
|:---|:---|:---|
| GOGC=50 | Чаще | Меньше |
| GOGC=100 | Default | Default |
| GOGC=200 | Реже | Больше |
| GOGC=off + limit | При лимите | До лимита |

### 💡 Практика: как настраивать GC

**✅ ОБЯЗАТЕЛЬНО ДЕЛАЙ:**

1. **`GOMEMLIMIT`** — всегда в контейнерах.
2. **`automaxprocs`** — для CPU.
3. **Мониторинг** — `runtime.ReadMemStats`.

**👍 СТОИТ СДЕЛАТЬ:**

4. **`GOGC=200`** — если память позволяет.
5. **Бенчмаркай** разные настройки.

**❌ НЕ ДЕЛАЙ:**

6. **Не отключай GC** без понимания.
7. **Не ставь `GOMEMLIMIT` больше реальной памяти.**

### Ключевые выводы подглавы 17.10

- **`GOGC`** — процент роста heap.
- **`GOMEMLIMIT`** — soft limit.
- **В контейнерах** — `GOMEMLIMIT` + `automaxprocs`.

## 17.11 Выводы и типичные ошибки

**Что мы узнали?**

Аллокации — главный источник нагрузки на GC. Escape analysis решает: стек или куча. Аллокатор Go: mcache (per P), mcentral (shared), mheap (global). Size classes — фиксированные размеры. `sync.Pool` — пул объектов. `poolLocal` для каждого P. Private + shared. Victim cache — объекты живут 2 GC. Pool помогает для hot-path, больших, одинаковых. Pool вредит для маленьких, редких, долгоживущих. `GOGC` и `GOMEMLIMIT` — настройка GC.

**Типичные ошибки:**

- ❌ **Не использовать `-benchmem`.** Не видно аллокаций.
- ❌ **Игнорировать escape analysis.** Объекты в куче.
- ❌ **Использовать `Pool` для маленьких.** Overhead.
- ❌ **Забыть `Put`.** Утечка.
- ❌ **Использовать `Pool` для долгоживущих.**
- ❌ **Не сбрасывать состояние.** Старые данные.
- ❌ **Разные размеры.** Size classes не помогают.
- ❌ **`interface{}` в hot path.** Аллокации.
- ❌ **`fmt.Sprintf` в hot path.** Аллокации.
- ❌ **Не использовать `GOMEMLIMIT` в контейнерах.**
- ❌ **Отключать GC без понимания.**
- ❌ **Не мониторить GC.**

## 17.14 Ответы

### Ответ 1

**Аллокации нагружают GC**, потому что GC должен сканировать heap, находить мёртвые объекты, освобождать. Чем больше аллокаций — тем чаще GC.

### Ответ 2

**Escape analysis** — анализ компилятора, определяющий, где аллоцировать объект: на стеке или в куче.

### Ответ 3

**Проверка:**

```bash
go build -gcflags=-m main.go
```

### Ответ 4

- **mcache** — локальный кэш для каждого P.
- **mcentral** — общий кэш для каждого size class.
- **mheap** — глобальный heap.

### Ответ 5

**mcache быстрый**, потому что **без блокировок**. Каждый P имеет свой mcache.

### Ответ 6

**Size classes** — фиксированные размеры объектов (8, 16, 24, 32, ...).

### Ответ 7

**Объект 50 байт** → класс 64 байта. Overhead = 14 байт (28%).

### Ответ 8

**`sync.Pool`** — пул переиспользуемых объектов.

### Ответ 9

```go
var bufPool = sync.Pool{
    New: func() any { return make([]byte, 4096) },
}

buf := bufPool.Get().([]byte)
defer bufPool.Put(buf)
```

### Ответ 10

**`poolLocal`** — структура для каждого P. Содержит `private` и `shared`.

### Ответ 11

**Victim cache** — при GC объекты не удаляются сразу, а перемещаются в victim. Живут 2 GC.

### Ответ 12

**Pool помогает:** hot-path, большие объекты, одинаковые размеры.

### Ответ 13

**Pool вредит:** маленькие объекты, редкие аллокации, долгоживущие.

### Ответ 14

**`GOGC`** — процент роста heap до следующего GC. Default = 100.

### Ответ 15

**`GOMEMLIMIT`** — soft limit на heap. GC агрессивнее при приближении.

### Ответ 16

```bash
GOMEMLIMIT=<limit> GOGC=100 ./app
```

Плюс `automaxprocs`.

### Ответ 17

**Измерить:**

```bash
go test -bench=. -benchmem ./...
go tool pprof mem.prof
```

### Ответ 18

**`-benchmem`** — флаг для показа аллокаций в бенчмарках.
