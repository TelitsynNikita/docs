# 🛡️ Глава 7: Уязвимости десериализации — Когда данные оживают

## Часть 1: Десериализация — что это и почему это опасно

### 🎯 Конкретный инцидент

Твой микросервис на Go общается с другим внутренним сервисом через бинарный протокол. Ты используешь `encoding/gob` для сериализации объектов перед отправкой и десериализации при получении. Код выглядит примерно так:

```go
// Принимаем gob-данные от другого сервиса
func handleMessage(w http.ResponseWriter, r *http.Request) {
    var msg Message
    decoder := gob.NewDecoder(r.Body)
    err := decoder.Decode(&msg)
    if err != nil {
        http.Error(w, "Bad request", http.StatusBadRequest)
        return
    }
    // Обрабатываем сообщение...
}
```

Внутренний сервис скомпрометирован, или хакер нашёл SSRF и может отправлять запросы к этому эндпоинту. Вместо обычного `Message` он отправляет специально подготовленный gob-объект, который при десериализации вызывает произвольный метод или аллоцирует столько памяти, что сервер падает с OOM.

Это уязвимость десериализации — выполнение кода или DoS через «злые» данные.

*(Deserialization Vulnerability — уязвимость, при которой злоумышленник передаёт приложению вредоносные сериализованные данные. При десериализации эти данные могут вызвать выполнение произвольного кода, отказ в обслуживании, повышение привилегий или обход бизнес-логики. Входит в OWASP Top 10 A08:2021 — Software and Data Integrity Failures. Особенно опасна в языках с развитой рефлексией и динамической загрузкой классов (Java, .NET, Python), но возможна и в Go при использовании определённых форматов и библиотек.)*

---

### 🧠 Как работает уязвимость десериализации: цепочка рассуждений

**Вопрос 1: Почему десериализация вообще может быть опасной? Это же просто восстановление объекта из байтов?**

Обычная десериализация простых структур в JSON действительно безопасна. Проблемы начинаются, когда формат поддерживает:

1. **Полиморфизм:** возможность указать тип объекта внутри данных. Хакер говорит: «Создай объект типа `Exploit`, а не `Message`».
2. **Выполнение кода при создании объекта:** конструкторы, деструкторы, методы `UnmarshalJSON` / `Decode`, которые вызываются автоматически.
3. **Ссылки на объекты и циклы:** возможность создать объект, который ссылается сам на себя или на другие объекты, вызывая бесконечную рекурсию.

В Go стандартный `encoding/json` относительно безопасен: он не поддерживает полиморфизм «из коробки» и не вызывает пользовательские методы, кроме `UnmarshalJSON` (который ты сам написал). Но `encoding/gob`, некоторые сторонние библиотеки и особенно CGO-биндинги к нативным библиотекам могут быть уязвимы.

**Вопрос 2: JSON безопасен? Мне можно не беспокоиться?**

Не совсем. Даже с JSON есть несколько векторов:

1. **DoS через глубину вложенности:** JSON с 10 000 уровней вложенности `{"a":{"a":{"a":...` может вызвать stack overflow в рекурсивном парсере.

2. **DoS через огромные числа:** `{"amount": 1e9999999}` может положить парсер, пытающийся конвертировать это в число.

3. **Неожиданные типы:** если ты ожидаешь `string`, а приходит `null`, `[]` или `{"key": "value"}`, и твой код не проверяет тип после десериализации — паника.

4. **Custom UnmarshalJSON с побочными эффектами:** если ты написал `UnmarshalJSON`, который ходит в БД, отправляет HTTP-запросы или выполняет системные вызовы — хакер может эксплуатировать это через SSRF или инъекции.

**Вопрос 3: А что насчёт Go-specific форматов? gob? protobuf?**

`encoding/gob` — это Go-специфичный бинарный формат. Он разработан для доверенных коммуникаций между Go-сервисами. Но если ты принимаешь gob от недоверенного источника (например, из внешнего API), возможны проблемы:

- gob поддерживает регистрацию произвольных типов через `gob.Register()`. Если в твоём приложении зарегистрированы типы с опасными методами, хакер может инстанциировать их.
- gob может передавать интерфейсы (через `gob.Register` конкретных реализаций). Хакер может подсунуть неожиданную реализацию интерфейса.

Protobuf от gRPC более безопасен, потому что схема строго определена в `.proto`-файлах. Парсер protobuf не вызывает произвольные конструкторы — он мапит поля на структуру по номерам. Но и здесь есть нюанс: если ты используешь `google.protobuf.Any` (полиморфное поле), хакер может подсунуть неожиданный тип сообщения.

## Часть 2: DoS через десериализацию

### 🎯 JSON Bomb — маленький запрос, огромная память

Хакер отправляет POST-запрос с телом в 200 байт:

```json
{"data": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"}
```

Ничего страшного, обычная строка. Но он использует тот факт, что твой парсер читает весь JSON в память. Если он отправит 100 000 таких запросов одновременно, каждый из которых весит 1 МБ после парсинга, сервер упадёт.

Более изощрённый вариант — бомба сжатия (zip bomb, но для JSON). JSON с глубокой вложенностью:

```json
{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":{"a":"boom"}}}}}}}}}}}}}}}}}}}}
```

200 байт на диске, но при парсинге создаются десятки вложенных map'ов, каждый со своим аллокатором.

### 🛡️ Защита от DoS при десериализации

**1. Ограничение размера тела запроса:**

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MB
```

**2. Ограничение глубины вложенности в JSON:**

```go
import "encoding/json"

func decodeJSON(r io.Reader, v interface{}) error {
    decoder := json.NewDecoder(r)
    // Ограничиваем максимальную глубину (через кастомный токенизатор)
    // Стандартный encoding/json не поддерживает ограничение глубины,
    // используй github.com/buger/jsonparser или ручную проверку
    return decoder.Decode(v)
}
```

Для ограничения глубины можно использовать библиотеки вроде `github.com/buger/jsonparser` или написать wrapper над `json.Decoder`, который считает вложенность.

**3. Ограничение размера отдельных полей:**

```go
type Request struct {
    Data string `json:"data" validate:"max=10000"`
}
```

**4. Таймаут на десериализацию:**

```go
ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
defer cancel()

decoder := json.NewDecoder(r.Body)
err := decoder.Decode(&v)
// Если десериализация зависла (бесконечная рекурсия?), контекст отменится
```

## Часть 3: Полиморфная десериализация и выполнение кода

### 🎯 Когда gob может быть опасен

Представь, что у тебя есть интерфейс `Action` и несколько его реализаций, зарегистрированных в gob:

```go
type Action interface {
    Execute() error
}

type SendEmail struct {
    To      string
    Subject string
    Body    string
}

type RunCommand struct {
    Cmd string
    Args []string
}

func (r *RunCommand) Execute() error {
    return exec.Command(r.Cmd, r.Args...).Run()
}

func init() {
    gob.Register(&SendEmail{})
    gob.Register(&RunCommand{})
}
```

И ты десериализуешь `Action` из ненадёжного источника:

```go
var action Action
decoder := gob.NewDecoder(r.Body)
decoder.Decode(&action)
action.Execute() // Выполнит ВСЁ, что прислал хакер!
```

Хакер может отправить сериализованный `RunCommand{Cmd: "rm", Args: ["-rf", "/"]}`. При десериализации gob создаст `RunCommand`, вызовет `Execute()` — и сервер выполнит команду.

**Это не ошибка в gob.** Это ошибка в архитектуре: ты регистрируешь опасные типы для десериализации из ненадёжного источника и автоматически вызываешь методы на них.

### 🛡️ Защита от полиморфной десериализации

**1. Не десериализуй полиморфные объекты из ненадёжных источников.**

Если тебе нужно принимать разные типы сообщений, используй дискриминированное объединение (discriminated union) с явным switch по типу:

```go
type Message struct {
    Type    string          `json:"type"`
    Payload json.RawMessage `json:"payload"`
}

func handleMessage(msg Message) error {
    switch msg.Type {
    case "send_email":
        var email SendEmail
        json.Unmarshal(msg.Payload, &email)
        return email.Execute()
    case "log":
        var log LogEntry
        json.Unmarshal(msg.Payload, &log)
        return log.Execute()
    default:
        return fmt.Errorf("unknown message type: %s", msg.Type)
    }
}
```

Белый список разрешённых типов. Всё остальное — ошибка.

**2. Не регистрируй опасные типы в gob.**

Если тип может выполнить команду, открыть файл или сделать HTTP-запрос, он не должен быть зарегистрирован для десериализации из внешнего источника.

**3. Используй protobuf вместо gob для внешних API.**

Protobuf не поддерживает выполнение произвольного кода при десериализации (если не использовать `Any` с непроверенными типами).

## Часть 4: YAML и XML — скрытые угрозы

### 🎯 YAML: больше, чем JSON

Многие Go-разработчики используют YAML для конфигов (через `gopkg.in/yaml.v3`). YAML гораздо мощнее JSON: он поддерживает теги, якоря, а в некоторых парсерах — даже вызов конструкторов.

Классический пример — YAML bomb:

```yaml
a: &a ["a", "a", "a", "a", "a", "a", "a", "a", "a"]
b: &b [*a, *a, *a, *a, *a, *a, *a, *a, *a]
c: &c [*b, *b, *b, *b, *b, *b, *b, *b, *b]
d: &d [*c, *c, *c, *c, *c, *c, *c, *c, *c]
```

100 байт YAML разворачиваются в гигабайты данных через алиасы.

**Защита:** при десериализации YAML из ненадёжного источника использовать `yaml.Decoder` с ограничениями или вообще не принимать YAML извне — JSON для API, YAML только для внутренних конфигов.

### 🎯 XML: Billion Laughs и XXE

XML-парсеры уязвимы к двум классическим атакам:

**Billion Laughs (XML Bomb):**

```xml
<?xml version="1.0"?>
<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
  ...
  <!ENTITY lol9 "&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;">
]>
<lolz>&lol9;</lolz>
```

10 ENTITY-определений разворачиваются в миллиард «lol». Парсер вешает сервер.

**XXE (XML External Entity):**

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>&xxe;</root>
```

Парсер читает `/etc/passwd` и вставляет содержимое в XML. Хакер получает системные файлы.

**Защита:**
- Не принимать XML от ненадёжных источников. Если принимаешь — отключить DTD и внешние сущности.
- В Go стандартный `encoding/xml` **не поддерживает** DTD и внешние сущности, поэтому XXE не работает «из коробки». Но осторожно с CGO-биндингами к libxml2 — там XXE работает.

### 📝 Что мы узнали?
- Десериализация опасна, когда формат поддерживает полиморфизм или автоматический вызов методов
- Даже JSON может быть использован для DoS через глубину вложенности и огромные числа
- gob безопасен только между доверенными сервисами; регистрировать опасные типы для десериализации — ошибка
- YAML и XML имеют дополнительные векторы атак (алиасы, DTD, внешние сущности)
- **Главное правило:** валидируй тип и содержимое ПОСЛЕ десериализации, ограничивай размер и глубину ДО

### 💥 Типичные ошибки
- **Ошибка:** «Я использую JSON, десериализация безопасна»
    - **Правда:** JSON безопаснее gob, но DoS через бомбы и проблемы с неожиданными типами всё ещё актуальны.
- **Ошибка:** Регистрировать опасные типы в gob и принимать gob извне
    - **Правда:** gob создаст любой зарегистрированный тип по требованию хакера. Не регистрируй типы с опасными методами.
- **Ошибка:** Не проверять тип поля после `json.Unmarshal`
    - **Правда:** Если ожидал `string`, а пришёл `null`, `int`, `[]`, дальнейший код может запаниковать.

### 🔁 Для быстрого повторения
- **Десериализация:** восстановление объекта из байтов; опасна при полиморфизме
- **JSON DoS:** глубина вложенности, огромные числа, zip-бомбы
- **gob:** только между доверенными сервисами; не регистрировать опасные типы
- **Защита:** `MaxBytesReader`, валидация после десериализации, белый список типов, таймауты
- **YAML:** алиасы могут раздуть память; не принимать YAML извне
- **XML:** DTD, Billion Laughs, XXE; `encoding/xml` в Go безопасен по умолчанию

### ❓ Вопросы для самопроверки

1.  Почему десериализация полиморфных объектов опаснее, чем десериализация простых структур?
2.  Хакер отправляет JSON `{"amount": 1e9999999}`. Что может произойти на сервере? Как защититься?
3.  Ты используешь gob для обмена сообщениями с другим микросервисом. При каких условиях это безопасно, а при каких — нет?
4.  Что такое Billion Laughs attack? Работает ли она против стандартного `encoding/xml` в Go?
5.  Чем опасен YAML по сравнению с JSON при десериализации из ненадёжного источника?
6.  Ты написал `UnmarshalJSON` для своего типа, который ходит в БД при десериализации. Почему это плохая идея?
7.  Как защититься от DoS через JSON с глубиной вложенности 10 000?
8.  Protobuf безопаснее gob для внешних API? Почему?

---

### ✅ Ответы на вопросы для самопроверки

1.  Полиморфная десериализация позволяет хакеру указать тип создаваемого объекта. Если в системе зарегистрированы типы с опасными методами (выполнение команд, чтение файлов, HTTP-запросы), хакер может инстанциировать их и вызвать эти методы. Простые структуры с фиксированными полями не дают такого контроля — хакер может только заполнить поля значениями.

2.  Парсер попытается конвертировать `1e9999999` в `float64` или `int64`. Это число выходит за пределы допустимых значений, что может вызвать: (1) панику в рантайме, (2) бесконечный цикл в парсере, (3) `+Inf` и дальнейшие проблемы в бизнес-логике. Защита: валидация после десериализации (`if math.IsInf(amount, 0) { ... }`), использование `json.Decoder` с `UseNumber()` для отсрочки конвертации, ограничение размера чисел на уровне валидации.

3.  **Безопасно:** gob между доверенными сервисами в одной сети, где оба сервиса контролируются тобой, и зарегистрированы только безопасные типы (без методов, выполняющих системные вызовы). **Небезопасно:** gob от внешних клиентов, gob с зарегистрированными типами вроде `RunCommand`, gob в открытых API — потому что хакер может инстанциировать любой зарегистрированный тип.

4.  Billion Laughs — это XML-бомба: через вложенные ENTITY-определения маленький XML-файл разворачивается в гигабайты данных, истощая память. Стандартный `encoding/xml` в Go **не поддерживает** DTD и ENTITY, поэтому Billion Laughs не работает. Но если ты используешь CGO-биндинг к libxml2, атака работает — нужно отключать DTD в настройках парсера.

5.  YAML поддерживает: (1) алиасы и якоря, позволяющие маленькому YAML-файлу развернуться в огромные структуры (YAML bomb), (2) теги, которые в некоторых парсерах могут вызывать конструкторы произвольных типов, (3) в старых версиях PyYAML — выполнение Python-кода через `!!python/object`. В Go `gopkg.in/yaml.v3` не вызывает конструкторы, но YAML bomb всё ещё работает.

6.  `UnmarshalJSON` вызывается автоматически при десериализации. Если он ходит в БД, хакер может: (1) вызвать множество обращений к БД через множество полей в JSON (DoS на БД), (2) через SSRF заставить сервер десериализовать JSON и получить доступ к БД, (3) инжектировать SQL через значения полей, если `UnmarshalJSON` строит SQL-запросы. Побочные эффекты в `UnmarshalJSON` — антипаттерн.

7.  Защита: (1) `http.MaxBytesReader` для ограничения размера тела, (2) использование `json.Decoder` с ручным подсчётом глубины (считать открывающие/закрывающие скобки при вызове `decoder.Token()`), (3) библиотеки вроде `github.com/buger/jsonparser` с встроенным ограничением глубины, (4) таймаут через `context.Context` на случай, если парсер завис.

8.  **Да.** Protobuf: (1) схема строго определена в `.proto`-файлах, типы известны на этапе компиляции, (2) парсер не вызывает конструкторы и пользовательские методы (кроме well-defined `Unmarshal`), (3) нет полиморфизма без явного использования `google.protobuf.Any` (который требует ручной проверки типа). gob: полиморфизм встроен через `Register()`, типы могут быть зарегистрированы динамически, что даёт хакеру больше контроля.

### 🚀 Мост к Главе 8

Хакер больше не может атаковать твой парсер — ты ограничил размер, глубину и не десериализуешь опасные типы. Теперь он ищет другой вектор: он заметил, что твой сервис сам делает HTTP-запросы к другим серверам. В Главе 8 мы разберём **SSRF (Server-Side Request Forgery)** — как заставить твой сервер сделать запрос к внутренней AWS metadata, украсть ключи доступа и получить полный контроль над облачной инфраструктурой.
