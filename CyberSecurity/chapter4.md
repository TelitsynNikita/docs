# 🛡️ Глава 4: Подделка межсайтовых запросов (CSRF) — Когда браузер выполняет чужую волю

## Часть 1: Классическая CSRF-атака — перевод денег по ссылке

### 🎯 Конкретный инцидент

Твой финтех-стартап внедрил функцию перевода денег между пользователями. Эндпоинт на бэкенде предельно прост:

```
POST /api/transfer
Content-Type: application/x-www-form-urlencoded

to_user=alice&amount=1000
```

Пользователь заходит в приложение, логинится, получает session cookie. Браузер хранит эту куку и автоматически прикрепляет её к каждому запросу на `your-app.com`. Пользователь заполняет форму перевода, нажимает «Отправить». Браузер делает POST-запрос, прикрепляет куку, бэкенд проверяет сессию и выполняет перевод. Всё работает.

Я — хакер. Я знаю, что этот эндпоинт существует (я просто залогинился в свой аккаунт и посмотрел вкладку Network в DevTools). Я создаю HTML-страницу на своём домене `evil.com`:

```html
<html>
<body>
    <h1>Поздравляем! Вы выиграли iPhone!</h1>
    <p>Нажмите кнопку, чтобы получить приз:</p>
    <form action="https://your-app.com/api/transfer" method="POST" id="steal">
        <input type="hidden" name="to_user" value="hacker">
        <input type="hidden" name="amount" value="9999">
    </form>
    <button onclick="document.getElementById('steal').submit()">Получить приз!</button>
</body>
</html>
```

Я отправляю ссылку на `evil.com/win-iphone` твоему пользователю через email: «Вы выиграли приз, заберите его здесь!». Пользователь кликает. Открывается моя страница. Он видит кнопку «Получить приз!», нажимает. Браузер отправляет POST-запрос на `https://your-app.com/api/transfer` с кукой этого пользователя. Бэкенд видит: кука валидная, сессия активна, пользователь авторизован. Запрос выполняется. 9999 рублей уходят на счёт хакера.

Это CSRF — атака, которая заставляет браузер жертвы выполнить нежелательное действие на сайте, где жертва авторизована. Никакого XSS, никакого внедрения скриптов на твой сайт. Просто HTML-форма на чужом домене.

*(Cross-Site Request Forgery (CSRF) — атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательный запрос к сайту, на котором жертва авторизована. Эксплуатирует автоматическую отправку браузером кук и других credentials для целевого домена. Входит в OWASP Top 10 A01:2021 — Broken Access Control. Защита: CSRF-токены (синхронизация токена между фронтендом и бэкендом), SameSite cookies, проверка заголовков Origin/Referer.)*

---

### 🧠 Как работает CSRF: цепочка рассуждений

**Вопрос 1: Почему браузер отправляет куки на чужой запрос?**

По умолчанию браузер прикрепляет куки к любому запросу, который соответствует домену, пути и протоколу. Если кука была установлена для `your-app.com` с `Path=/`, она будет отправлена с ЛЮБЫМ запросом к `your-app.com` — независимо от того, с какой страницы этот запрос был инициирован. Это фундаментальное свойство HTTP-кук, которое существовало задолго до появления SameSite.

Когда пользователь нажимает кнопку на `evil.com`, браузер формирует POST-запрос к `your-app.com`. Браузер проверяет: «У меня есть куки для `your-app.com`? Да. Прикрепляю их к запросу». Бэкенд `your-app.com` получает запрос с валидной сессионной кукой и не может отличить легитимный запрос от поддельного.

**Вопрос 2: Почему нельзя просто проверять заголовок Origin/Referer?**

Заголовок `Origin` (и более старый `Referer`) сообщает серверу, с какого домена был отправлен запрос. Браузер автоматически добавляет `Origin: https://evil.com` к cross-origin POST-запросам. Казалось бы, бэкенд может просто отклонить запрос, если `Origin` не совпадает с `https://your-app.com`. Но есть нюансы:

1. **Не все браузеры отправляют Origin для всех типов запросов.** Старые браузеры могут не отправлять его вовсе. Same-origin запросы (с того же домена) могут не иметь Origin.

2. **Origin можно подделать в некоторых сценариях.** Если на твоём сайте есть открытый редирект (Open Redirect), хакер может использовать его для обхода проверки Origin.

3. **Referer можно отключить через Referrer-Policy.** Некоторые corporate proxy и браузерные расширения удаляют Referer.

Поэтому проверка Origin/Referer — это дополнительная защита, а не основная. Основная защита — CSRF-токены.

**Вопрос 3: CSRF работает только с POST-запросами? А GET?**

CSRF может работать и с GET-запросами, если они меняют состояние. Классический пример — старые версии WordPress, где `GET /wp-admin/options.php?action=delete&id=1` удалял запись. Хакер просто вставлял `<img src="https://target.com/wp-admin/options.php?action=delete&id=1">` на свою страницу, браузер загружал «картинку» — и запись удалялась. Никакого клика не требовалось.

Современная передовая практика: **никогда не менять состояние в GET-запросах**. GET должен быть идемпотентным и безопасным (только чтение). Все мутации — через POST, PUT, PATCH, DELETE. Это не защищает от CSRF напрямую, но уменьшает поверхность атаки.

### 🛡️ Защита: CSRF-токены (синхронизация токена)

*(CSRF Token (Synchronizer Token Pattern) — криптографически случайный токен, который сервер генерирует для каждой сессии и встраивает в HTML-формы (скрытое поле) и/или в куки. Клиент должен отправить этот токен вместе с запросом (в теле POST или в заголовке). Сервер сверяет токен из запроса с токеном сессии. Поскольку чужой сайт не может прочитать токен с целевого домена (same-origin policy), он не может создать валидный запрос.)*

Идея проста: сервер генерирует случайный токен, связанный с сессией пользователя. Этот токен передаётся на фронтенд (через куку, кастомный заголовок или встроенным в HTML). При отправке формы токен должен быть включён в запрос. Сервер проверяет: совпадает ли токен из запроса с токеном, связанным с сессией? Если нет — запрос отклоняется.

Почему хакер не может просто прочитать токен? Из-за Same-Origin Policy (SOP). JavaScript с `evil.com` не может прочитать куки или DOM `your-app.com`. Хакер не может извлечь CSRF-токен и вставить его в свою форму.

**Реализация в Go с использованием библиотеки `gorilla/csrf`:**

```go
package main

import (
    "net/http"
    "github.com/gorilla/csrf"
    "github.com/gorilla/mux"
)

func main() {
    r := mux.NewRouter()

    // Ключ для шифрования CSRF-токенов (32 байта)
    csrfKey := []byte("32-byte-long-secret-key-here!!")

    // Middleware CSRF
    csrfMiddleware := csrf.Protect(
        csrfKey,
        csrf.Secure(true),       // Только HTTPS
        csrf.HttpOnly(true),     // Кука токена недоступна из JS
        csrf.SameSite(csrf.SameSiteStrictMode),
    )

    r.HandleFunc("/api/transfer", transferHandler).Methods("POST")

    http.ListenAndServe(":8080", csrfMiddleware(r))
}

func transferHandler(w http.ResponseWriter, r *http.Request) {
    // CSRF-токен автоматически проверяется middleware.
    // Если токен неверный — запрос не дойдёт до обработчика.
    // Здесь уже безопасно выполнять операцию.
    toUser := r.FormValue("to_user")
    amount := r.FormValue("amount")
    // ... выполняем перевод ...
}
```

**Как фронтенд получает и отправляет токен:**

Библиотека `gorilla/csrf` автоматически устанавливает куку `_gorilla_csrf` с токеном. Фронтенд должен прочитать эту куку и отправить её значение либо в HTTP-заголовке `X-CSRF-Token`, либо в поле формы `gorilla.csrf.Token`.

Для SPA на React/Angular бэкенд должен также отдавать токен через кастомный заголовок или endpoint, потому что JavaScript может не иметь доступа к HttpOnly-куке. Конфигурация:

```go
csrf.Protect(csrfKey,
    csrf.CookieName("csrf_token"),
    csrf.HttpOnly(false),  // Разрешаем JS читать куку токена
    csrf.Secure(true),
)
```

Теперь фронтенд может прочитать `csrf_token` из `document.cookie` и отправить его в заголовке `X-CSRF-Token`.

### 🖥️ Фронтенд: отправка CSRF-токена в React и Angular

**React с axios:**

```javascript
import axios from 'axios';

// Читаем CSRF-токен из куки
function getCSRFToken() {
    const match = document.cookie.match(/csrf_token=([^;]+)/);
    return match ? match[1] : '';
}

// Настраиваем axios interceptor для автоматической отправки токена
axios.defaults.withCredentials = true; // Отправлять куки с cross-origin запросами
axios.interceptors.request.use(config => {
    // Для мутирующих методов добавляем CSRF-токен
    if (['post', 'put', 'patch', 'delete'].includes(config.method)) {
        config.headers['X-CSRF-Token'] = getCSRFToken();
    }
    return config;
});

// Использование
async function transfer(toUser, amount) {
    const formData = new URLSearchParams();
    formData.append('to_user', toUser);
    formData.append('amount', amount);

    await axios.post('/api/transfer', formData, {
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    });
}
```

**Angular с HttpClient:**

Angular имеет встроенную поддержку CSRF: если кука называется `XSRF-TOKEN`, Angular автоматически читает её и отправляет в заголовке `X-XSRF-TOKEN` для всех мутирующих запросов. Достаточно настроить бэкенд на использование этого имени:

```go
csrf.Protect(csrfKey,
    csrf.CookieName("XSRF-TOKEN"),
    csrf.HttpOnly(false),
    csrf.Secure(true),
)
```

Angular-код (работает из коробки, без дополнительных интерсепторов):

```typescript
import { HttpClient } from '@angular/common/http';

@Injectable()
export class TransferService {
    constructor(private http: HttpClient) {}

    transfer(toUser: string, amount: number) {
        const body = new URLSearchParams();
        body.set('to_user', toUser);
        body.set('amount', amount.toString());

        return this.http.post('/api/transfer', body.toString(), {
            headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
            withCredentials: true,
        });
    }
}
```

Angular автоматически прочитает куку `XSRF-TOKEN` и добавит заголовок `X-XSRF-TOKEN`.

### 🛡️ Защита: Double Submit Cookie (альтернативный паттерн)

Не всегда хочется хранить CSRF-токены на сервере (особенно в stateless API). Паттерн Double Submit Cookie не требует серверного хранения.

Идея:
1. Сервер генерирует случайный токен и устанавливает его в куке `csrf_token`.
2. Фронтенд читает куку и отправляет токен в заголовке `X-CSRF-Token`.
3. Сервер просто сравнивает: `cookie.csrf_token == header['X-CSRF-Token']`.

Хакер с `evil.com` не может прочитать куку `your-app.com` (SOP), поэтому не может установить правильный заголовок. Сервер видит: кука есть, а заголовка нет или он не совпадает — запрос отклонён.

**Реализация в Go (без внешних библиотек):**

```go
package main

import (
    "crypto/rand"
    "encoding/base64"
    "net/http"
)

func CSRFMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Пропускаем безопасные методы
        if r.Method == "GET" || r.Method == "HEAD" || r.Method == "OPTIONS" {
            next.ServeHTTP(w, r)
            return
        }

        // Получаем токен из куки
        cookie, err := r.Cookie("csrf_token")
        if err != nil {
            http.Error(w, "CSRF token missing", http.StatusForbidden)
            return
        }

        // Получаем токен из заголовка
        headerToken := r.Header.Get("X-CSRF-Token")
        if headerToken == "" {
            http.Error(w, "CSRF header missing", http.StatusForbidden)
            return
        }

        // Сравниваем
        if cookie.Value != headerToken {
            http.Error(w, "CSRF token mismatch", http.StatusForbidden)
            return
        }

        next.ServeHTTP(w, r)
    })
}

func generateCSRFToken() string {
    b := make([]byte, 32)
    rand.Read(b)
    return base64.StdEncoding.EncodeToString(b)
}
```

### 🛡️ Защита: SameSite cookies

*(SameSite — атрибут куки, который контролирует, отправлять ли куку с cross-origin запросами. SameSite=Strict: кука не отправляется никогда с cross-origin запросов. SameSite=Lax: кука отправляется с cross-origin GET-навигации (переход по ссылке), но не с POST/изображений/iframes. SameSite=None: кука отправляется всегда (требует Secure). SameSite=Lax — безопасный дефолт в современных браузерах, предотвращает CSRF для POST-запросов.)*

SameSite решает проблему CSRF на уровне браузера, не требуя токенов. Ты просто говоришь браузеру: «Никогда не отправляй эту куку, если запрос инициирован с другого домена».

Три режима SameSite:

**SameSite=Strict**
Кука не отправляется с ЛЮБЫХ cross-origin запросов. Если пользователь кликает по ссылке на `your-app.com` из email или с другого сайта, кука не отправляется — пользователь будет неавторизован. Максимальная защита, но плохой UX: переходы по ссылкам ломаются.

**SameSite=Lax (рекомендуемый дефолт)**
Кука отправляется с cross-origin GET-навигации (переход по ссылке), но НЕ отправляется с cross-origin POST, загрузки изображений, iframe, AJAX. Защищает от CSRF на мутирующие операции, но не ломает навигацию.

**SameSite=None**
Кука отправляется всегда, как в старые времена. Требует `Secure` (только HTTPS). Нужен для кросс-доменных сценариев (например, когда API и фронтенд на разных origin).

Настройка в Go:

```go
http.SetCookie(w, &http.Cookie{
    Name:     "session_id",
    Value:    sessionToken,
    Path:     "/",
    HttpOnly: true,
    Secure:   true,
    SameSite: http.SameSiteLaxMode, // Защита от CSRF без токенов
})
```

**Важно:** SameSite защищает от CSRF, но не заменяет CSRF-токены в сценариях, где SameSite=None (кросс-доменные запросы с `withCredentials: true`). Если твой фронтенд на `app.example.com`, а API на `api.example.com`, SameSite=Lax не защитит POST-запросы — они будут считаться same-site (поддомены одного сайта). Same-site ≠ same-origin. Домен `app.example.com` и `api.example.com` — это один site (`example.com`), поэтому SameSite=Lax разрешает cross-origin запросы между ними.

### 📝 Что мы узнали?
- CSRF заставляет браузер жертвы выполнить нежелательное действие на сайте, где жертва авторизована
- Атака использует автоматическую отправку кук браузером
- Главная защита: CSRF-токены (синхронизация токена между фронтендом и бэкендом)
- Double Submit Cookie — альтернатива для stateless API
- SameSite cookies решают проблему на уровне браузера, но не для всех сценариев
- **Фронтенд:** axios interceptor для автоматической отправки токена, Angular HttpClient делает это из коробки

### 💥 Типичные ошибки
- **Ошибка:** «У меня REST API, я не использую формы — CSRF мне не страшен»
    - **Правда:** Если бэкенд проверяет сессию по кукам, CSRF работает независимо от того, форма это или AJAX. SPA на React точно так же уязвимы.
- **Ошибка:** «Я использую JWT в localStorage, мне не нужна защита от CSRF»
    - **Правда:** Если JWT хранится в localStorage, JavaScript должен вручную прикреплять его к запросам через `Authorization: Bearer`. Злоумышленник с `evil.com` не может прочитать localStorage чужого домена (SOP), поэтому не может прикрепить токен. Это правда защищает от CSRF. Но JWT в localStorage уязвим к XSS: любой XSS на твоём сайте может прочитать токен из localStorage и украсть его. HttpOnly-кука не видна через XSS, но требует CSRF-защиты. Выбор между куками и localStorage — это компромисс между CSRF и XSS.
- **Ошибка:** «SameSite=Lax защищает от всего»
    - **Правда:** SameSite=Lax не защищает same-site запросы (между поддоменами). Если API и фронтенд на одном сайте, SameSite=Lax пропускает POST-запросы между ними. Плюс старые браузеры не поддерживают SameSite.

### 🔁 Для быстрого повторения
- **CSRF:** заставляет жертву выполнить действие на целевом сайте через браузер
- **Механизм:** автоматическая отправка кук браузером с cross-origin запросов
- **CSRF-токен:** случайный токен, известный серверу и клиенту, передаётся в заголовке или теле запроса
- **Double Submit Cookie:** токен в куке = токен в заголовке, без серверного хранения
- **SameSite=Lax:** кука не отправляется с cross-origin POST, защита без токенов
- **Фронтенд:** axios interceptor для `X-CSRF-Token`, Angular XSRF из коробки

## Часть 2: CSRF через GET — когда «просто посмотреть» уже опасно

### 🎯 Конкретный инцидент

Твой бэкенд следует передовым практикам: все мутации через POST, CSRF-токены проверяются. Но есть старый эндпоинт, доставшийся от MVP:

```
GET /api/delete-account
```

Он удаляет аккаунт текущего пользователя. Работает без токена, потому что «это же временный эндпоинт для отладки».

Я, хакер, вставляю на свою страницу:

```html
<img src="https://your-app.com/api/delete-account" width="0" height="0">
```

Или отправляю жертве email с «письмом», которое содержит:

```html
<img src="https://your-app.com/api/delete-account">
```

Как только жертва открывает письмо (если почтовый клиент загружает изображения) или заходит на мою страницу, браузер пытается загрузить «картинку» с `your-app.com`. Он отправляет GET-запрос, прикрепляет сессионную куку. Бэкенд видит валидную сессию и удаляет аккаунт. Жертва просто открыла письмо.

Это CSRF через GET. Никаких кнопок, никаких форм. Просто загрузка «изображения».

---

### 🛡️ Защита: никогда не менять состояние в GET

Железное правило REST и HTTP: GET-запросы должны быть безопасными и идемпотентными. Они не должны менять состояние сервера. Все мутации — только POST, PUT, PATCH, DELETE.

Просто переписать эндпоинт на POST и добавить CSRF-токен — проблема решена. Даже если где-то остался GET с мутацией и на него нет CSRF-защиты, SameSite=Lax защитит: GET из `<img>` с чужого домена — это cross-origin без навигации, кука с SameSite=Lax не отправится.

Но старые почтовые клиенты и некоторые браузерные конфигурации могут игнорировать SameSite. Поэтому основная защита — не иметь мутирующих GET-эндпоинтов.

---

### 📝 Что мы узнали?
- CSRF через GET не требует взаимодействия пользователя — достаточно загрузить «изображение» или открыть письмо
- SameSite=Lax защищает от CSRF через GET из `<img>`, `<iframe>`, `<script>`
- Железное правило: GET только для чтения, мутации только через POST/PUT/DELETE с токеном

### 🔁 Для быстрого повторения
- **CSRF через GET:** `<img src="...">` автоматически отправляет GET с куками
- **Защита:** не делать мутаций в GET, SameSite=Lax для кук

## Часть 3: Обход CSRF-защиты и продвинутые сценарии

### 🎯 CSRF + XSS = полный обход

Если на сайте есть XSS, любая CSRF-защита бесполезна. XSS позволяет хакеру выполнить JavaScript в контексте твоего домена, прочитать CSRF-токен из DOM или куки и отправить полностью валидный запрос.

Вывод: CSRF-защита и XSS-защита работают в тандеме. XSS без CSRF — хакер может украсть данные, но не может делать мутации? Нет, может: он может просто отправить fetch с правильным токеном, потому что он в контексте твоего домена.

### 🎯 CSRF с подделкой заголовков через Flash (устаревший, но показательный)

Раньше Flash мог отправлять cross-origin запросы с кастомными заголовками. Хакер создавал Flash-ролик, который отправлял POST с поддельным `X-CSRF-Token` (любым) и `Content-Type: application/json`. Браузер прикреплял куки. Бэкенд, проверяющий только наличие заголовка, пропускал запрос. Flash умер в 2020 году, но принцип остался: недостаточно просто проверить, что заголовок существует. Нужно проверять его значение.

### 🎯 Same-site bypass: когда поддомен атакует поддомен

Если у тебя `app.example.com` и `api.example.com`, SameSite=Lax разрешает запросы между ними (они one site). Если хакер найдёт XSS на любом поддомене `*.example.com`, он сможет делать CSRF-атаки на API, потому что браузер отправит SameSite=Lax куки.

Защита: всегда использовать CSRF-токены даже внутри одного сайта. Не полагаться только на SameSite.

### ✅ Ответы на вопросы для самопроверки

1.  **CSRF** заставляет браузер жертвы отправить запрос к целевому сайту, используя автоматическую отправку кук. XSS не требуется — форма на чужом сайте работает без JavaScript. **XSS** выполняет вредоносный скрипт в контексте целевого сайта. CSRF может работать без XSS. XSS полностью обходит CSRF-защиту: хакер в контексте домена может прочитать CSRF-токен из DOM или куки и отправить валидный запрос.

2.  SOP запрещает JavaScript с `evil.com` читать ответ от `bank.com`. Но CSRF не требует чтения ответа. Браузер отправляет запрос с куками, сервер выполняет действие, но ответ получает страница `evil.com`, которая не может его прочитать из-за SOP. Хакеру не нужен ответ — ему нужно, чтобы действие выполнилось.

3.  Сервер генерирует случайный токен для сессии и передаёт его клиенту (в куке или встроенным в HTML). Клиент отправляет токен с каждым мутирующим запросом. Сервер сверяет токен из запроса с токеном сессии. Хакер с `evil.com` не может получить токен, потому что SOP запрещает JavaScript с чужого домена читать куки или DOM `your-app.com`. Он не может вставить правильный токен в форму.

4.  **SameSite=Strict:** кука не отправляется ни с какими cross-origin запросами, включая переход по ссылке из email. Если пользователь кликает по ссылке `your-app.com/dashboard` из письма, он будет неавторизован — плохой UX. **SameSite=Lax:** кука отправляется с cross-origin GET-навигации (клик по ссылке), но не отправляется с cross-origin POST, загрузки изображений, iframe. Это сохраняет UX и защищает от CSRF на мутации.

5.  **Нет, не защищает.** `app.example.com` и `api.example.com` имеют один registrable domain (`example.com`), поэтому они являются same-site. SameSite=Lax разрешает cross-origin запросы между ними (включая POST). Нужна дополнительная защита: CSRF-токены, проверка Origin, CORS с ограничением origins.

6.  **Да, нужна.** HttpOnly защищает от кражи JWT через XSS (`document.cookie` не видит HttpOnly-куку). Но CSRF заставляет браузер отправить эту куку автоматически с запросом. Браузер не спрашивает JavaScript, он просто прикрепляет куки, соответствующие домену. Бэкенд получает валидный JWT из куки и выполняет действие. HttpOnly не защищает от CSRF.

7.  **Формально нет, но есть нюанс.** JWT в localStorage не отправляется браузером автоматически. JavaScript должен вручную прочитать токен из localStorage и добавить в заголовок `Authorization`. Хакер с `evil.com` не может прочитать localStorage `your-app.com` (SOP), поэтому не может прикрепить токен. Это защищает от CSRF. Но: (1) JWT в localStorage уязвим к XSS — любой XSS на твоём сайте крадёт токен, (2) если в коде есть баг и JWT кладётся в куки «на всякий случай», CSRF снова работает. HttpOnly-кука + CSRF-токен — более сбалансированный подход.

8.  Angular ожидает куку с именем `XSRF-TOKEN` и автоматически отправляет заголовок `X-XSRF-TOKEN` для мутирующих запросов. Бэкенд должен: (1) установить куку с именем `XSRF-TOKEN` (не HttpOnly, чтобы Angular мог прочитать), (2) проверять заголовок `X-XSRF-TOKEN` и сверять со значением куки. С `gorilla/csrf`: `csrf.CookieName("XSRF-TOKEN")`, `csrf.HttpOnly(false)`.

9.  **Нет.** GET-запрос на `/api/delete-account` уязвим к CSRF через `<img src="...">` или просто ссылку. SameSite=Lax частично защищает (не отправит куку для `<img>`), но не для ссылки (навигация). Решение: переписать на POST и добавить CSRF-токен. Или как минимум переименовать в POST-эндпоинт и удалить GET-версию.

10. **Double Submit Cookie** не требует хранения токена на сервере: сервер сверяет токен из куки с токеном из заголовка. Если они совпадают — запрос валиден (хакер не может прочитать куку, чтобы установить заголовок). **Synchronizer Token Pattern** хранит токен на сервере (в сессии) и сверяет присланный токен с сохранённым. Double Submit Cookie проще для stateless API, но уязвим к подделке куки через man-in-the-middle на поддоменах (cookie tossing). Выбирай Double Submit Cookie для stateless сервисов; Synchronizer Token для приложений с серверной сессией.
