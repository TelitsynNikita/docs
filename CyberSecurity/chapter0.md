## 0.0 Пролог: три инцидента за одно утро

Ты — Go-разработчик в финтех-стартапе. Понедельник, 9:00 утра.

Ты открываешь почту и видишь письмо. Служба безопасности банка-партнёра просит срочно обновить сертификат по ссылке `bank-partner.ru`. Настоящий домен — `bank-partner.com`. Разница не в одной букве, а в доменной зоне: `.ru` вместо `.com`. Это целевой фишинг.

Пока ты читаешь письмо, приходит алерт из Grafana: микросервис, обрабатывающий платежи, лежит. В логах за последние 20 минут — **15 миллионов запросов с разных IP**. Это DDoS.

Ты начинаешь разбираться с DDoS, и в этот момент приходит третье сообщение. Кто-то получил доступ к админке и изменил расчётный счёт для выплат на подставной.

Три разных инцидента. Но у них есть кое-что общее.

Каждый бьёт в одну из трёх целей безопасности. Понимание этих целей — твоя система координат для всего, что будет дальше.

## 0.1 CIA Triad — три кита безопасности

В прологе мы увидели три атаки: DDoS, фишинг, подмена счёта.

Каждая из них нарушает одно из трёх фундаментальных свойств информации. Эти свойства называются **CIA Triad**:

- **Confidentiality** — конфиденциальность;
- **Integrity** — целостность;
- **Availability** — доступность.

Разберём каждое.

---

### 🔒 Конфиденциальность

**Конфиденциальность** — это свойство, при котором данные доступны только тем, кто имеет на них право.

Проще говоря: **может ли кто-то прочитать то, что не должен?**

Когда говорят «хакер украл данные», почти всегда речь о конфиденциальности.

Но это не только кража паролей. Вот реальные примеры:

- злоумышленник перехватывает трафик между бэкендом и базой данных;
- S3-бакет оказался публичным, и оттуда скачали внутренние документы;
- API возвращает лишние поля: вместе с профилем пользователя отдаётся его внутренний ID, роль и email;
- секреты попали в логи;
- сервер вернул трассировку стека, и в ней видны пути к файлам;
- резервная копия лежит в открытом доступе.

Заметь: в большинстве случаев хакер ничего не «взламывает». Он находит то, что плохо лежит.

Поэтому конфиденциальность — это не только защита от внешнего взлома. Это ещё и дисциплина внутри команды.

---

#### 💻 Пример на Go

❌ Очень частая ошибка:

```go
func getUser(w http.ResponseWriter, r *http.Request) {
    user, err := service.GetUser(r.Context(), id)
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(user)
}
```

Если `err` содержит строку подключения к БД, путь к файлу или имя таблицы, клиент это увидит.

✅ Правильный подход:

```go
func getUser(w http.ResponseWriter, r *http.Request) {
    user, err := service.GetUser(r.Context(), id)
    if err != nil {
        log.Printf("get user: %v", err)
        http.Error(w, `{"error": "Internal Server Error"}`, http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(user)
}
```

Здесь детали ошибки остаются внутри сервера, клиенту возвращается нейтральное сообщение, а разработчик видит проблему в логах.

---

### 🛡️ Целостность

**Целостность** — это свойство, при котором данные не могут быть изменены без разрешения.

Здесь речь не о краже, а о **подмене**.

Примеры:

- хакер меняет сумму транзакции с `100` на `10000`;
- кто-то модифицирует JavaScript-файл на CDN;
- пользователь меняет роль в JWT с `user` на `admin`;
- кто-то подменяет запись в базе данных;
- вредоносный пакет попадает в цепочку поставки.

Целостность нарушается часто незаметно.

Кражу видно. А подмену можно не замечать годами.

---

#### 💻 Пример на Go

У тебя есть структура:

```go
type TransferRequest struct {
    FromUserID int `json:"from_user_id"`
    ToUserID   int `json:"to_user_id"`
    Amount     int `json:"amount"`
}
```

Если бэкенд просто доверяет `FromUserID`, хакер может подставить чужой ID и перевести деньги с чужого счёта.

✅ Как исправить?

Не брать `FromUserID` из запроса. Брать его из сессии или из токена аутентификации:

```go
func transferHandler(w http.ResponseWriter, r *http.Request) {
    userID := getUserIDFromContext(r.Context())

    var req TransferRequest
    json.NewDecoder(r.Body).Decode(&req)

    err := service.Transfer(r.Context(), userID, req.ToUserID, req.Amount)
    // ...
}
```

Теперь хакер может сколько угодно подставлять `FromUserID` в JSON — сервер его проигнорирует.

---

### ⚡ Доступность

**Доступность** — это свойство, при котором легитимные пользователи могут получить сервис, когда им нужно.

Самая очевидная атака — DDoS.

Но доступность нарушается и другими способами:

- ransomware шифрует файлы, и пользователь теряет данные;
- path traversal позволяет удалить файлы;
- сложный SQL-запрос вызывает deadlock в базе;
- приложение исчерпало файловые дескрипторы и перестало принимать соединения.

Доступность — это не только «сервер лежит».

Это ещё и «сервер отвечает, но очень медленно».

---

### 🏦 Метафора

Представь банковскую ячейку.

- 🔒 **Конфиденциальность** — это стены хранилища. Никто не должен видеть, что внутри.
- 🛡️ **Целостность** — гарантия, что ночью твои золотые слитки не подменили на вольфрамовые.
- ⚡ **Доступность** — уверенность, что дверь откроется, когда ты придёшь за своими ценностями.

Если хотя бы одно свойство нарушено, ячейка бесполезна.

---

### 💡 Как это связано с разработкой

Каждый раз, когда ты пишешь код, спрашивай себя:

- Может ли кто-то прочитать то, что не должен?
- Может ли кто-то изменить то, что не должен?
- Может ли кто-то сделать сервис недоступным?

Это и есть мышление безопасника.

---

### 🧭 Где мы сейчас

Мы разобрали три цели, в которые бьют атаки.

Дальше — как хакер доводит атаку до реализации. Потому что атака — это не одно действие. Это процесс.

---

> **CIA Triad** — три фундаментальных свойства информации: конфиденциальность, целостность, доступность.

## 0.2 Cyber Kill Chain — как мыслит атакующий

В 0.1 мы разобрали три цели атаки. Но как атака достигает своей цели?

Если смотреть только на конечную точку, кажется, что «взломали за секунду».

На самом деле атака — это цепочка.

**Cyber Kill Chain** — модель, разработанная Lockheed Martin. Она описывает семь последовательных этапов атаки:

> разведка → вооружение → доставка → эксплуатация → закрепление → управление → действия.

Ценность модели в том, что её можно разорвать на любом этапе.

---

### 1️⃣ Reconnaissance — разведка

Хакер изучает цель:

- на чём работает сервер;
- какие порты открыты;
- какие технологии используются;
- кто работает в компании;
- есть ли утечки в открытом виде.

Инструменты мы разберём в 0.6. Пока просто пример:

```bash
curl -I https://target.com
nmap -sV target.com
whois target.com
dig target.com ANY
```

🛡️ **Задача защитника на этом этапе** — дать как можно меньше информации.

---

### 2️⃣ Weaponization — вооружение

Хакер готовит инструмент атаки:

- эксплойт под найденную уязвимость;
- вредоносный макрос для Word;
- фальшивый пакет в репозитории;
- фишинговая страница.

На этом этапе хакер ещё не взаимодействует с целью. Он просто готовится.

---

### 3️⃣ Delivery — доставка

Хакер передаёт полезную нагрузку:

- фишинговое письмо;
- ссылка в мессенджере;
- вредоносный JSON;
- пакет в публичном реестре;
- поддельный сайт.

---

### 4️⃣ Exploitation — эксплуатация

Срабатывает уязвимость:

- SQL-инъекция;
- XSS;
- переполнение буфера;
- SSRF.

Именно здесь уязвимость превращается в реальный взлом.

---

### 5️⃣ Installation — закрепление

Хакер остаётся в системе:

- ставит бэкдор;
- добавляет SSH-ключ;
- загружает веб-шелл;
- создаёт нового пользователя.

Цель — сохранить доступ даже после перезагрузки или смены пароля.

---

### 6️⃣ Command & Control — управление

Хакер устанавливает связь с сервером управления:

- HTTPS;
- DNS-туннель;
- WebSocket.

Через этот канал он будет отдавать команды скомпрометированной системе.

---

### 7️⃣ Actions on Objectives — действия

Финальная цель:

- кража данных;
- шифрование файлов;
- майнинг;
- атака на соседние системы;
- уничтожение инфраструктуры.

---

### 🗺️ Как разработчик рвёт цепочку

Ты не обязан останавливать хакера на последнем этапе.

Можно разорвать цепочку раньше:

| Этап | Защита |
|---|---|
| Разведка | OPSEC: прячем стек, заголовки, ошибки |
| Доставка и эксплуатация | Валидация ввода |
| Закрепление | Минимальные привилегии |
| Управление | Ограничение исходящего трафика |
| Действия | Бэкапы, шифрование, аудит |

Чем раньше ты рвёшь цепочку, тем дешевле защита.

---

### 🧭 Где мы сейчас

Мы увидели, что атака — это процесс из семи этапов, и каждый можно разорвать.

Но Kill Chain линейная. Реальные атаки не всегда идут строго по шагам. Дальше — более гибкая модель.

---

> **Cyber Kill Chain** — модель атаки из семи этапов: разведка → вооружение → доставка → эксплуатация → закрепление → управление → действия.

## 0.3 MITRE ATT&CK — карта техник реальных атак

Kill Chain предполагает, что атака идёт строго по шагам.

В реальности атакующий может пропускать этапы, возвращаться назад, использовать несколько техник одновременно.

Поэтому появился **MITRE ATT&CK** — база знаний о тактиках, техниках и процедурах атакующих.

---

### 🧠 Тактика, техника, процедура

- **тактика** — это цель этапа;
- **техника** — способ достижения цели;
- **процедура** — конкретная реализация техники.

---

### 📊 Пример

Kill Chain говорит: «закрепление».

MITRE ATT&CK уточняет:

- **тактика:** закрепление (Persistence);
- **техника:** манипуляция учётными записями (Account Manipulation);
- **подтехника:** добавление SSH-ключа (SSH Authorized Keys).

Это уже можно проверить на сервере:

```bash
cat ~/.ssh/authorized_keys
```

---

### 📋 Ещё несколько примеров техник

| Тактика | Техника | Что делает хакер |
|---|---|---|
| Разведка | Active Scanning | Сканирует порты через nmap |
| Доставка | Spearphishing Attachment | Отправляет письмо с вредоносным вложением |
| Эксплуатация | SQL Injection | Внедряет SQL-код через поля ввода |
| Закрепление | Cron Job | Добавляет задачу в crontab для автозапуска |
| Управление | DNS Tunneling | Передаёт команды через DNS-запросы |
| Действия | Data Exfiltration | Выводит данные через HTTPS |

---

### 💡 Почему это важно разработчику

Ты не обязан знать все 600+ техник.

Но ты должен понимать:

- атака — это связка «тактика → техника»;
- каждая техника оставляет след;
- защита строится от техник, а не от абстрактных «хакеров».

---

### 🧭 Где мы сейчас

Kill Chain даёт этапы. MITRE ATT&CK — техники внутри этапов.

Дальше — что именно ищет защитник, когда атака уже произошла.

---

> **MITRE ATT&CK** — база знаний о тактиках, техниках и процедурах атакующих.

## 0.4 IOC и TTP — что ищет Blue Team

Атака произошла. Твой SOC получил алерт: с одного IP идёт подозрительная активность.

Аналитик видит:

- **IOC:** IP `203.0.113.7`, хеш файла, домен `evil.com`.

Но завтра хакер сменит IP и домен.

IOC — это конкретные артефакты атаки. Они быстро устаревают.

TTP — это тактики, техники и процедуры. Они меняются редко.

---

### 🧠 IOC vs TTP

**IOC (Indicators of Compromise)** — индикаторы компрометации.

Это конкретные артефакты:

- IP-адрес атакующего;
- домен C2-сервера;
- хеш вредоносного файла;
- имя файла;
- строка в логах.

**TTP (Tactics, Techniques, Procedures)** — тактики, техники и процедуры.

Это поведение атакующего:

- как он закрепляется;
- как двигается внутри сети;
- как выводит данные.

---

### 🔍 Почему TTP важнее IOC

- **IOC** — это улики конкретного преступления.
- **TTP** — это почерк преступника.

Если защищаться только по IOC, ты всегда догоняешь.

Если понимать TTP, ты ломаешь атаку на уровне техники.

---

### 💡 Что такое SOC

**SOC (Security Operations Center)** — это команда или подразделение, которое занимается мониторингом и реагированием на инциденты безопасности.

SOC-аналитик смотрит на алерты, расследует подозрительную активность и принимает меры.

В больших компаниях SOC — это отдельный отдел. В малых — один человек, который «смотрит за безопасностью».

В нашем учебнике мы часто будем говорить про SOC, потому что именно туда попадают алерты и оттуда начинается реагирование.

---

### 🧭 Где мы сейчас

Мы разобрали, как атакуют и как защитник обнаруживает атаку.

Дальше — как устроена сама команда защиты.

---

> **IOC** — конкретные артефакты атаки: IP, домен, хеш файла.

> **TTP** — поведенческие паттерны атакующего.

> **SOC** — команда, отвечающая за мониторинг и реагирование на инциденты.

## 0.5 Red Team, Blue Team, Purple Team — три взгляда на безопасность

Мы разобрали, как атакуют и как обнаруживают атаки.

Но кто именно атакует? И кто защищает?

В безопасности есть три роли.

---

### 🔴 Red Team

**Red Team** — атакующая сторона.

Это люди, которые ищут способы прорваться в систему.

Они используют все техники из MITRE ATT&CK: разведку, эксплуатацию, закрепление, lateral movement.

Их цель — **найти слабые места до того, как их найдёт настоящий хакер**.

---

### 🔵 Blue Team

**Blue Team** — защищающаяся сторона.

Это люди, которые строят защиту:

- настраивают мониторинг;
- пишут правила алертов;
- расследуют инциденты;
- восстанавливают систему после атаки.

Их цель — **обнаружить атаку и остановить её**.

---

### 🟣 Purple Team

**Purple Team** — связка между Red и Blue.

Это процесс, в котором Red Team и Blue Team работают вместе.

Red Team показывает, как они обошли защиту. Blue Team улучшает защиту на основе этих знаний.

## 0.6 Инструментарий разведки — что видит хакер

В 0.2 мы сказали, что атака начинается с разведки.

Теперь посмотрим, как именно хакер собирает информацию. Это не магия — это четыре команды, которые может выполнить любой.

---

### whois — информация о домене

```bash
whois example.com
```

Пример реального вывода:

```
Domain Name: EXAMPLE.COM
Registry Domain ID: 2336799_DOMAIN_COM-VRSN
Registrar WHOIS Server: whois.iana.org
Registrar URL: http://www.iana.org
Updated Date: 2024-08-14T00:00:00Z
Creation Date: 1995-08-14T04:00:00Z
Registry Expiry Date: 2025-08-13T04:00:00Z
Registrar: IANA
Name Server: A.IANA-SERVERS.NET
Name Server: B.IANA-SERVERS.NET
DNSSEC: signedDelegation
```

Разберём, что здесь важно:

- **Domain Name** — сам домен.
- **Creation Date** — когда домен был зарегистрирован.
- **Registry Expiry Date** — когда истекает регистрация. Если домен скоро истекает, хакер может попытаться перехватить его.
- **Registrar** — регистратор, у которого зарегистрирован домен.
- **Name Server** — DNS-серверы домена.
- **DNSSEC** — подписан ли домен. Отсутствие DNSSEC означает, что DNS-ответы можно подделать.

Для «живых» доменов вывод будет больше: там будет ещё **Registrant Email**, **Registrant Phone**, **Registrant Organization** — контактные данные владельца.

---

### dig — DNS-запросы

```bash
dig example.com ANY
```

Пример реального вывода:

```
;; ANSWER SECTION:
example.com.		3600	IN	A	93.184.216.34
example.com.		3600	IN	MX	0 .
example.com.		3600	IN	NS	a.iana-servers.net.
example.com.		3600	IN	NS	b.iana-servers.net.
example.com.		3600	IN	TXT	"v=spf1 -all"
```

Разберём:

- **A** — IPv4-адрес сервера, на котором хостится домен.
- **MX** — почтовый сервер домена.
- **NS** — DNS-серверы.
- **TXT** — текстовая запись. В ней может лежать что угодно, но чаще всего — SPF.

---

### ✉️ Что такое SPF и DKIM

Когда хакер отправляет письмо, он может указать в поле «От кого» любой адрес. Например, `security@bank-partner.com`.

Почтовый сервер получателя видит это письмо и думает: «А точно ли его отправил bank-partner.com? Или кто-то притворяется?»

Чтобы это проверить, существуют два механизма:

**SPF (Sender Policy Framework)** — это TXT-запись в DNS, которая говорит: «Почту от имени этого домена имеют право отправлять только вот эти серверы».

Пример рабочей SPF-записи:

```
"v=spf1 include:_spf.google.com ~all"
```

Это означает: «Почту от имени домена могут отправлять только серверы Google».

Если хакер попытается отправить письмо с адресом `security@bank-partner.com` со своего сервера, почтовый сервер получателя проверит SPF, увидит, что сервер хакера не в списке, и отправит письмо в спам или отбросит.

**DKIM (DomainKeys Identified Mail)** — это цифровая подпись, которая добавляется к каждому письму. Получатель проверяет подпись по публичному ключу из DNS.

Если письмо подписано ключом домена — значит, оно действительно отправлено с сервера, которому домен доверяет.

Если SPF/DKIM не настроены, хакер может подделывать письма от имени твоего домена — это один из векторов фишинга.

---

### curl -I — заголовки ответа

```bash
curl -I https://example.com
```

Пример реального вывода:

```
HTTP/1.1 200 OK
Server: nginx/1.18.0 (Ubuntu)
Date: Wed, 14 Aug 2026 12:00:00 GMT
Content-Type: text/html; charset=utf-8
X-Powered-By: Express/4.17.1
```

Разберём:

- **Server** — веб-сервер и его версия. Хакер видит `nginx/1.18.0` и ОС `Ubuntu`.
- **X-Powered-By** — фреймворк и его версия. Хакер видит `Express/4.17.1`.
- **Content-Type** — тип контента. Обычно не критично.

Дальше хакер берёт `nginx 1.18.0` и `Express 4.17.1`, идёт в базу CVE и ищет эксплойты под эту связку.

---

### nmap — сканирование портов

```bash
nmap -sV example.com
```

Пример реального вывода:

```
PORT     STATE SERVICE  VERSION
22/tcp   open  ssh      OpenSSH 7.2p2 Ubuntu
80/tcp   open  http     nginx 1.18.0
5432/tcp open  postgres PostgreSQL 12.2
```

Разберём:

- **22/tcp — ssh** — SSH-сервер. Если он открыт в интернет, хакер может пытаться подобрать пароль.
- **80/tcp — http** — веб-сервер. Основная точка входа.
- **5432/tcp — postgres** — база данных, открытая в интернет. Это критично: база данных никогда не должна торчать наружу.

Каждый открытый порт — это потенциальная точка входа.

---

### 🧰 Сводная таблица

| Команда | Что показывает | Что ищет хакер |
|---|---|---|
| `whois example.com` | владелец, DNS, даты | контактные данные |
| `dig example.com ANY` | A, MX, NS, TXT | IP, почтовые серверы, SPF |
| `curl -I https://example.com` | заголовки ответа | версии сервера и фреймворка |
| `nmap -sV example.com` | порты и сервисы | открытые сервисы и их версии |

## 0.7 Валидация всего внешнего — первый рубеж обороны

В 0.2 мы сказали, что на этапах доставки и эксплуатации защита — это валидация.

Теперь разберём, что это значит на практике.

---

### 🎯 Конкретный инцидент

Ты написал на Go endpoint регистрации:

```go
func registerHandler(w http.ResponseWriter, r *http.Request) {
    username := r.FormValue("username")
    age := r.FormValue("age")
    // ... сохранение в БД ...
}
```

Я — хакер. Я вижу форму и задаю три вопроса:

1. Что будет, если `username` длиной в 1 мегабайт?
2. Что будет, если `age = -500`?
3. Что будет, если `username = "<script>alert(1)</script>"`?

Если у тебя нет защиты от этого, я прошёл дальше по Kill Chain.

---

### 🧠 Почему валидация — это не скучная рутина

Многие разработчики думают:

- «Валидация — это просто проверить, что поле не пустое».
- «Фронтенд уже валидирует».
- «Пользователь не будет ломать свой же интерфейс».

Это опасные заблуждения.

Хакер не пользуется твоим интерфейсом.

Он отправляет запросы напрямую через `curl` или свой скрипт.

Вся валидация на фронтенде для него не существует.

---

### 📚 Четыре уровня валидации

Валидация должна быть многоуровневой.

Нужно проверять:

1. **размер;**
2. **тип;**
3. **формат;**
4. **бизнес-логику.**

---

#### 1️⃣ Размер

Хакер может отправить JSON на 100 мегабайт.

✅ Решение — ограничивать размер тела запроса:

```go
r.Body = http.MaxBytesReader(w, r.Body, 1048576) // 1 MB
```

Если запрос больше — сервер оборвёт чтение.

---

#### 2️⃣ Длина строк

Имя пользователя на 1 000 000 символов:

```go
if len(username) < 3 || len(username) > 50 {
    http.Error(w, "Invalid username length", http.StatusBadRequest)
    return
}
```

---

#### 3️⃣ Количество элементов в массиве

Массив из 1 000 000 ID на удаление:

```go
if len(ids) > 100 {
    http.Error(w, "Too many items", http.StatusBadRequest)
    return
}
```

---

#### 4️⃣ Тип данных

Ожидаешь число — проверь, что это число:

```go
age, err := strconv.Atoi(r.FormValue("age"))
if err != nil || age < 0 || age > 150 {
    http.Error(w, "Invalid age", http.StatusBadRequest)
    return
}
```

---

#### 5️⃣ Перечисления

Если поле может принимать только ограниченный набор значений, проверяй по белому списку:

```go
validRoles := map[string]bool{"user": true, "admin": true}
if !validRoles[role] {
    http.Error(w, "Invalid role", http.StatusBadRequest)
    return
}
```

---

### 🛡️ Whitelist вместо blacklist

Допустим, ты хочешь защитить поле `username` от опасных символов.

**Blacklist-подход** — это когда ты составляешь список «запрещённых» значений:

```go
// ❌ Так делать не стоит
blacklist := []string{"<script>", "' OR 1=1", "admin", "root", "\\"}
```

Что здесь не так?

Хакер всегда найдёт обход. Ты запретил `<script>`, он напишет `<scr<script>ipt>`. Ты запретил `admin`, он напишет `admın` (с турецкой `ı`). Ты запретил кавычку, он использует другую кодировку.

Это бесконечная гонка: ты добавляешь новые запреты, хакер ищет новые обходы.

**Whitelist-подход** — это когда ты разрешаешь только то, что явно допустимо:

```go
// ✅ Правильный подход
if len(username) < 3 || len(username) > 50 {
    http.Error(w, "Invalid username length", http.StatusBadRequest)
    return
}

// Разрешены только буквы, цифры и подчёркивание
for _, r := range username {
    if !unicode.IsLetter(r) && !unicode.IsDigit(r) && r != '_' {
        http.Error(w, "Invalid username characters", http.StatusBadRequest)
        return
    }
}
```

Ты не пытаешься угадать, что может придумать хакер.

Ты говоришь: «Вот что разрешено. Всё остальное — отклоняется».

Это жёстче, но надёжнее.

---

### 🧭 Где мы сейчас

Мы разобрали валидацию — первый рубеж обороны на этапах доставки и эксплуатации.

Дальше — как не дать хакеру информацию на этапе разведки. Это называется OPSEC.

---

> **Валидация** — проверка всех данных, поступающих извне, на соответствие ожидаемому формату, типу, размеру и бизнес-правилам.

> **Whitelist** — подход, при котором разрешены только явно допустимые значения.

## 0.8 OPSEC — не свети свой стек

В 0.6 мы увидели, как хакер собирает информацию через заголовки, DNS и nmap.

Теперь — как дать ему как можно меньше.

---

### 🎯 Конкретный инцидент

Я — злоумышленник.

Я получил IP твоего сервера.

Прежде чем атаковать, я провожу разведку:

```bash
curl -I https://target.com
```

Ответ:

```http
Server: nginx/1.18.0 (Ubuntu)
X-Powered-By: Express/4.17.1
```

Из трёх строк я уже знаю:

- веб-сервер — `nginx`;
- его версию — `1.18.0`;
- ОС — `Ubuntu`;
- фреймворк — `Express`;
- версию Express — `4.17.1`.

Дальше я иду в базу CVE и ищу эксплойты под эту связку.

---

### 🧠 Что такое OPSEC

**OPSEC** — это operational security.

Если коротко: **не давай противнику информацию, которая ему не нужна**.

Каждый лишний заголовок, каждая стандартная страница ошибки — это подсказка.

---

### 📚 Что прятать

- заголовок `Server`;
- заголовок `X-Powered-By`;
- стандартные страницы ошибок;
- source maps;
- комментарии в HTML и JS;
- баннеры SSH и БД;
- версии в глобальных JS-переменных;
- `robots.txt` с секретными путями;
- лишние порты.

---

### 🔧 Заголовки HTTP

Самые частые утечки:

- `Server: nginx/1.18.0`;
- `X-Powered-By: Express/4.17.1`;
- `X-AspNet-Version`;
- `X-Generator`;
- `Via`.

В Go стандартный `net/http` не добавляет их сам.

Но если ты используешь фреймворк или прокси, проверь.

---

### 💻 Пример для Nginx

```nginx
server_tokens off;
```

Можно вообще заменить заголовок:

```nginx
more_set_headers "Server: warpdrive";
```

Хакер увидит бессмысленное слово вместо версии.

---

### 💻 Стандартные страницы ошибок

Стандартная 500-я ошибка Go может раскрыть трассировку стека.

Хакер увидит:

- пути к файлам;
- номера строк;
- иногда — переменные окружения.

✅ Решение — middleware:

```go
func RecoveryMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Printf("PANIC: %v", err)
                http.Error(w, `{"error": "Internal Server Error"}`, http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

Логируем внутри. Клиенту — нейтрально.

---

### 🖥️ Source maps и фронтенд

Если React или Angular собирается с source maps, хакер видит исходники.

В DevTools → Sources он читает твои комментарии и структуру.

✅ Отключай:

```bash
GENERATE_SOURCEMAP=false react-scripts build
```

Или в конфиге:

```javascript
devtool: false
```

---

### 🐳 Docker и Kubernetes

Твой `Dockerfile` может раскрыть пути и версии.

`docker inspect` показывает переменные окружения.

Не храни секреты в `ENV`.

Не давай доступ к `docker.sock`.

Мы разобрали, как не давать хакеру информацию на этапе разведки.

Дальше — последний рубеж: как ограничить ущерб, если хакер всё-таки проник.

> **OPSEC (Operational Security)** — практика сокрытия информации, которая может помочь противнику.

## 0.9 Least Privilege и Zero Trust — не доверяй даже себе

Мы разобрали, как не пустить хакера.

Но что, если он всё-таки проник?

Тогда важно, чтобы у него было как можно меньше прав.

---

### 🛡️ Least Privilege

**Least Privilege** — принцип минимальных привилегий.

Процесс получает только те права, которые нужны для работы.

Примеры:

- контейнер с `readOnlyRootFilesystem`;
- запрет `privileged`;
- отдельный пользователь БД с минимумом прав;
- запрет доступа к Docker socket;
- egress только к нужным сервисам.

Если хакер взломал приложение, он упирается в эти же ограничения.

---

### 💻 Пример

Контейнер с Go-сервисом:

```yaml
securityContext:
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  runAsNonRoot: true
```

БД-пользователь:

```sql
GRANT SELECT, INSERT, UPDATE ON myapp.public.users TO app_user;
```

Хакер не сможет удалить таблицы.

---

### 🔒 Zero Trust

**Zero Trust** — принцип: не доверять никому по умолчанию.

Раньше думали: «внутри сети — свои, можно доверять».

Теперь так нельзя.

- каждый запрос проверяется;
- каждый сервис аутентифицируется;
- каждый доступ авторизуется;
- даже внутри кластера.

---

### 🧭 Где мы сейчас

Мы разобрали три рубежа обороны:

- валидация — не пустить;
- OPSEC — не дать информацию;
- Least Privilege — ограничить ущерб.

В следующей подглаве — итог всей главы.

---

> **Least Privilege** — принцип минимальных привилегий.

> **Zero Trust** — не доверять никому по умолчанию, даже внутри периметра.

## Что мы узнали?

- Безопасность — это защита трёх свойств: конфиденциальности, целостности, доступности.
- Атака — это процесс. Мы рвём его на ранних этапах.
- MITRE ATT&CK даёт общий язык для описания атак.
- TTP важнее IOC, потому что поведение меняется реже артефактов.
- Валидация, OPSEC и Least Privilege — три первых рубежа защиты.
- Безопасность нельзя добавить в конце. Она закладывается в мышление.

## Типичные ошибки

- ❌ Думать, что безопасность можно добавить в конце.
- ❌ Думать, что фреймворк всё делает сам.
- ❌ Доверять данным от клиента.
- ❌ Оставлять сырые ошибки в ответе.
- ❌ Держать секреты в `ENV`.
- ❌ Игнорировать OPSEC.
- ❌ Не валидировать размер и тип данных.
- ❌ Защищать только периметр.
- ❌ Не ограничивать права приложения.
- ❌ Забывать про исходящий трафик.

## Для быстрого повторения

- **CIA Triad:** C — раскрытие, I — изменение, A — отказ в доступе.
- **Kill Chain:** Recon → Weaponize → Deliver → Exploit → Install → C2 → Act.
- **ATT&CK:** тактика → техника → процедура.
- **Защита:** валидация, OPSEC, Least Privilege.
- **Инструменты разведки:** whois, dig, curl -I, nmap -sV.

## Ответы

**1.** CIA Triad — это три фундаментальных свойства информации:

- **Конфиденциальность** — данные доступны только тем, кто имеет на них право.
- **Целостность** — данные не могут быть изменены без разрешения.
- **Доступность** — легитимные пользователи могут получить сервис, когда им нужно.

**2.** DDoS нарушает **доступность**. Сервис становится недоступным для легитимных пользователей.

**3.** Cyber Kill Chain — модель атаки из семи этапов: разведка, вооружение, доставка, эксплуатация, закрепление, управление, действия.

**4.** Kill Chain линейная: атака идёт по шагам. MITRE ATT&CK — база знаний о тактиках и техниках. Kill Chain говорит «закрепление», ATT&CK уточняет, как именно: например, через SSH-ключ.

**5.** IOC — конкретные артефакты: IP, домен, хеш. TTP — поведение: тактики, техники, процедуры. Пример IOC: IP `203.0.113.7`. Пример TTP: закрепление через SSH-ключ.

**6.** IOC быстро устаревают: хакер сменит IP, домен, файл. TTP меняются редко: почерк атакующего остаётся стабильным. Защита по TTP ломает атаку на уровне техники.

**7.** OPSEC — это сокрытие информации о системе. Раскрывают стек: `Server`, `X-Powered-By`, `X-AspNet-Version`, `X-Generator`, `Via`.

**8.** Потому что хакер не пользуется фронтендом. Он отправляет запросы напрямую через `curl` или свой скрипт. Фронтенд — это UX. Бэкенд — это безопасность.

**9.** Whitelist — разрешены только явно допустимые значения. Это надёжнее, чем blacklist, потому что хакер не найдёт неожиданный обход.

**10.** Red Team атакует и ищет способы прорваться. Blue Team защищает и обнаруживает атаки. Purple Team связывает их и улучшает обе стороны.

**11.** Да, достаточно. Хакер узнаёт фреймворк и его версию из `X-Powered-By`, идёт в базу CVE и ищет эксплойты. OPSEC работает только когда закрыты **все** утечки.

**12.** Least Privilege ограничивает ущерб. Если приложение взломано, но работает в контейнере с `readOnlyRootFilesystem` и без `privileged`, хакер не сможет установить бэкдор. Если egress ограничен, не сможет связаться с C2.

**13.** XSS выполняется в браузере жертвы. Он может украсть cookies (конфиденциальность), подменить контент страницы (целостность), сделать сайт недоступным через дефейс (доступность).

**14.** Нет. Это только OPSEC и частично защита от XSS. Нужны ещё: валидация ввода, защита от SQLi, CSRF, IDOR, аутентификация, least privilege, мониторинг.

**15.** Zero Trust требует проверять каждый запрос, даже внутри сети. Для микросервисов: каждый сервис аутентифицируется, каждый вызов авторизуется, сеть сегментирована NetworkPolicy. Если один сервис взломан, хакер не может свободно ходить по внутренней сети.
