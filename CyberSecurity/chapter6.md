# 🛡️ Глава 6: Атаки на аутентификацию — Брутфорс, Password Spraying и JWT

## Часть 1: Брутфорс и Password Spraying — подбор пароля

### 🎯 Конкретный инцидент

Твой финтех-стартап запустился. У тебя endpoint логина:

```
POST /api/login
Content-Type: application/json

{"username": "alice", "password": "qwerty123"}
```

Бэкенд проверяет пароль через bcrypt, всё красиво. Но ты забыл одну вещь: у тебя нет rate limiting на этом эндпоинте. Вообще.

Я — хакер. Я скачал базу из 10 миллионов самых популярных паролей (rockyou.txt) и написал простой скрипт на Go, который перебирает пароли для пользователя `admin`:

```go
package main

import (
    "bytes"
    "encoding/json"
    "fmt"
    "net/http"
    "os"
    "strings"
)

func main() {
    passwords, _ := os.ReadFile("rockyou.txt")
    for _, password := range strings.Split(string(passwords), "\n") {
        body, _ := json.Marshal(map[string]string{
            "username": "admin",
            "password": strings.TrimSpace(password),
        })
        resp, _ := http.Post(
            "https://target.com/api/login",
            "application/json",
            bytes.NewReader(body),
        )
        if resp.StatusCode == 200 {
            fmt.Printf("Password found: %s\n", password)
            break
        }
        resp.Body.Close()
    }
}
```

На сервере нет rate limiting. Мой скрипт делает 100 запросов в секунду. Через 5 часов у меня пароль администратора.

Это брутфорс — перебор паролей для одного пользователя.

*(Brute Force Attack — атака на аутентификацию, при которой злоумышленник перебирает множество паролей для одного аккаунта. Отличается от Password Spraying, где один пароль пробуется против множества аккаунтов. Защита: rate limiting на эндпоинте логина, account lockout после N неудачных попыток, bcrypt/scrypt/argon2 для замедления хеширования, мониторинг аномального количества попыток входа.)*

Password Spraying — это обратная тактика. Вместо миллиона паролей на одного пользователя, я беру ОДИН пароль («Password123!») и пробую его против ВСЕХ пользователей. Между попытками я жду 30 минут, чтобы не триггерить account lockout. Рано или поздно кто-то с этим паролем находится.

---

### 🧠 Как работает брутфорс: цепочка рассуждений

**Вопрос 1: Почему нельзя просто блокировать аккаунт после 5 неудачных попыток?**

Можно, но это создаёт вектор для DoS. Если я, хакер, знаю email твоего пользователя, я могу намеренно ввести неверный пароль 5 раз и заблокировать его аккаунт. Пользователь не сможет залогиниться, пока не сбросит пароль или не пройдёт дополнительную верификацию. Это называется lockout attack — атака на доступность через механизм защиты от брутфорса.

Баланс: временная блокировка (увеличивающаяся задержка) вместо перманентной. После первой неверной попытки — подожди 1 секунду. После второй — 2 секунды. После пятой — 30 секунд. После десятой — 15 минут. Это не блокирует аккаунт навсегда, но делает брутфорс непрактично медленным.

**Вопрос 2: Почему bcrypt, а не SHA-256?**

SHA-256 спроектирован для скорости. Он должен быстро считать хеши файлов, сообщений, блоков в блокчейне. Одна видеокарта может посчитать миллиарды SHA-256-хешей в секунду. Если база паролей утекла, хакер восстановит большинство паролей за часы.

bcrypt спроектирован для медленности. У него есть параметр cost (количество раундов), который определяет, сколько раз алгоритм будет итеративно хешировать пароль. Cost=12 означает 2^12 = 4096 итераций. Один bcrypt-хеш считается ~300 мс. Миллион паролей — это 83 часа на одном ядре. Хакер не может эффективно брутфорсить bcrypt даже с утекшей базой.

*(bcrypt — адаптивная хеш-функция для паролей, основанная на Blowfish. Ключевая особенность: настраиваемый cost factor, который определяет количество итераций. При cost=12 вычисление одного хеша занимает ~300 мс, что делает массовый брутфорс непрактичным. В отличие от SHA-256, bcrypt автоматически включает соль в хеш (формат $2a$12$salt+hash). Другие безопасные альтернативы: scrypt (memory-hard, устойчив к GPU-атакам), argon2id (победитель Password Hashing Competition 2015, устойчив и к GPU, и к side-channel атакам).)*

**Вопрос 3: Что такое соль и зачем она нужна?**

Без соли два пользователя с одинаковым паролем «qwerty123» будут иметь одинаковый хеш. Хакер, получив базу, может посчитать хеш для «qwerty123» один раз и найти всех пользователей с этим паролем. Это называется rainbow table attack: заранее посчитанная таблица «пароль → хеш» для миллионов популярных паролей.

Соль — это случайная строка, уникальная для каждого пользователя. Она добавляется к паролю перед хешированием. Даже если у двух пользователей пароль «qwerty123», их хеши будут разными, потому что соли разные. bcrypt автоматически генерирует соль и включает её в итоговый хеш — тебе не нужно управлять солью отдельно.

### 🛡️ Защита: bcrypt + rate limiting в Go

**Хеширование пароля через bcrypt:**

```go
import "golang.org/x/crypto/bcrypt"

func hashPassword(password string) (string, error) {
    // cost=12 — хороший баланс безопасности и производительности для 2024
    bytes, err := bcrypt.GenerateFromPassword([]byte(password), 12)
    return string(bytes), err
}

func checkPassword(password, hash string) bool {
    err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
    return err == nil
}
```

**Cost factor: как выбрать правильное значение**

Правило: cost должен быть таким, чтобы хеширование на твоём продакшен-железе занимало 250-500 мс. Это делает брутфорс неприемлемо медленным, но пользователь при логине не замечает задержки в полсекунды.

Как подобрать: написать бенчмарк на своём сервере, замерить время для cost=10, 11, 12, 13, выбрать ближайший к 300 мс. Не бери cost из интернета без тестирования — на разных CPU время отличается в разы.

```go
func benchmarkCost(password string, cost int) time.Duration {
    start := time.Now()
    bcrypt.GenerateFromPassword([]byte(password), cost)
    return time.Since(start)
}
```

**Rate limiting на эндпоинте логина (из Главы 1):**

Тот же Token Bucket, который мы разбирали для HTTP-флуда, применяется и для логина, но с более строгими лимитами:

```go
// Для логина: 5 попыток в минуту, burst до 3
loginLimiter := NewPerIPRateLimiter(5.0/60.0, 3)
// Для сброса пароля: 1 попытка в 5 минут
resetLimiter := NewPerIPRateLimiter(1.0/300.0, 1)
```

Важно лимитировать по IP (для неаутентифицированных запросов) и по username (чтобы один IP не мог перебирать пароли для разных пользователей). Комбинированный подход: лимит на IP + лимит на username.

**Прогрессивная задержка (progressive delay):**

Вместо жёсткого отказа после N попыток, увеличивай задержку ответа:

```go
func loginHandler(w http.ResponseWriter, r *http.Request) {
    username := r.FormValue("username")
    attempts := getFailedAttempts(username)

    // Прогрессивная задержка: 1s, 2s, 4s, 8s, 16s...
    delay := time.Duration(math.Pow(2, float64(attempts))) * time.Second
    if delay > 30*time.Second {
        delay = 30 * time.Second // Максимум 30 секунд
    }
    time.Sleep(delay)

    // Проверяем пароль
    if !checkPassword(password, hash) {
        incrementFailedAttempts(username)
        http.Error(w, "Invalid credentials", http.StatusUnauthorized)
        return
    }
    resetFailedAttempts(username)
    // Создаём сессию...
}
```

Такой подход не блокирует аккаунт (нет DoS-вектора), но делает брутфорс экспоненциально медленным.

## Часть 2: Credential Stuffing — когда пароли уже утекли

### 🎯 Конкретный инцидент

Ты защитился rate limiting: 5 попыток в минуту с одного IP. Я, хакер, не могу брутфорсить. Но у меня есть база из 100 миллионов пар email+пароль, утекших из взломанного соцсетевого сервиса. Люди часто используют один пароль везде.

Я беру эту базу и пробую каждую пару email+пароль против твоего API. У меня ботнет из 10 000 IP — я делаю по 3 запроса с каждого IP, распределяя нагрузку. Rate limiting по IP не спасает. Из 100 000 твоих пользователей 2 000 использовали тот же пароль, что и в утекшем сервисе. Я захожу в их аккаунты.

Это credential stuffing — атака, использующая утекшие базы паролей.

*(Credential Stuffing — атака, при которой злоумышленник использует базы утекших логинов и паролей для автоматизированных попыток входа на другие сервисы. Эксплуатирует повторное использование паролей пользователями. Отличается от брутфорса тем, что не перебирает пароли, а использует уже известные пары. Защита: MFA (многофакторная аутентификация), проверка паролей по базам утекших паролей (Have I Been Pwned API), мониторинг аномальных паттернов входа (новый IP, новое устройство, необычное время).)*

---

### 🛡️ Защита от Credential Stuffing

1. **Многофакторная аутентификация (MFA).** Даже если пароль утек, хакер не сможет залогиниться без второго фактора (TOTP, SMS, hardware token). Это самая эффективная защита.

2. **Проверка пароля при регистрации и смене.** При создании нового пароля проверять его по API Have I Been Pwned (k-anonymity, безопасно — пароль не покидает сервер):

```go
import (
    "crypto/sha1"
    "fmt"
    "net/http"
    "strings"
)

func isPasswordPwned(password string) (bool, error) {
    // SHA-1 хеш пароля
    h := sha1.Sum([]byte(password))
    hash := strings.ToUpper(fmt.Sprintf("%x", h[:]))
    prefix := hash[:5]
    suffix := hash[5:]

    // k-anonymity: отправляем только первые 5 символов хеша
    resp, err := http.Get("https://api.pwnedpasswords.com/range/" + prefix)
    if err != nil {
        return false, err
    }
    defer resp.Body.Close()

    body, _ := io.ReadAll(resp.Body)
    // Ищем suffix в ответе
    return strings.Contains(string(body), suffix), nil
}
```

Если пароль найден в базе утекших — предложить пользователю выбрать другой.

3. **Мониторинг аномалий:** отслеживать попытки входа с новых устройств, новых IP, из новых геолокаций. Отправлять уведомление пользователю: «В ваш аккаунт зашли из Берлина. Это вы?».

## Часть 3: Атаки на JWT — когда токен рассказывает лишнее

### 🎯 Конкретный инцидент

Твой микросервис использует JWT для аутентификации. Бэкенд генерирует токен при логине:

```go
func generateToken(userID int, role string) (string, error) {
    token := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
        "user_id": userID,
        "role":    role,
        "exp":     time.Now().Add(24 * time.Hour).Unix(),
    })
    return token.SignedString([]byte("my-secret-key"))
}
```

Я, хакер, получил этот токен (через XSS, через открытый роутер, через лог сервера). Я иду на jwt.io, вставляю токен, и вижу:

```json
{
  "user_id": 42,
  "role": "user",
  "exp": 1700000000
}
```

Токен не зашифрован — он только подписан. Любой может прочитать его содержимое. Это нормально для JWT (он не для конфиденциальности, а для целостности). Но что, если я попробую изменить `role` на `admin` и подделать подпись?

---

### 🧠 Атаки на JWT: цепочка рассуждений

**Атака 1: Алгоритм none**

JWT поддерживает алгоритм `none` — без подписи вообще. Если бэкенд использует библиотеку, которая не проверяет алгоритм строго, я могу создать токен:

```json
{
  "alg": "none",
  "typ": "JWT"
}
{
  "user_id": 1,
  "role": "admin"
}
```

И отправить его. Некоторые библиотеки принимают `alg: none` как валидный токен без проверки подписи.

**Защита:** всегда явно указывать ожидаемый алгоритм при верификации:

```go
token, err := jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
    // Явно проверяем алгоритм
    if _, ok := token.Method.(*jwt.SigningMethodHMAC); !ok {
        return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
    }
    return secretKey, nil
})
```

**Атака 2: Подмена алгоритма RS256 на HS256**

Если бэкенд использует RS256 (асимметричный, приватный ключ на сервере, публичный — для проверки), но публичный ключ доступен (например, через `/.well-known/jwks.json`), я могу:

1. Взять публичный ключ
2. Создать JWT с `alg: HS256`, подписанный публичным ключом как HMAC-секретом
3. Библиотека на бэкенде видит `HS256`, использует публичный ключ как секрет для HMAC, проверяет подпись — подходит!

**Защита:** при верификации проверять, что алгоритм в токене совпадает с ожидаемым типом ключа:

```go
token, err := jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
    if token.Method.Alg() != "RS256" {
        return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
    }
    return publicKey, nil
})
```

**Атака 3: Утечка секрета**

Если секрет `my-secret-key` зашит в коде (как в примере выше), и код утёк (через source maps, через `.git`, через уволенного разработчика), я могу подписывать любые токены. Всегда храни секреты в переменных окружения, Vault, AWS Secrets Manager — не в коде.

**Атака 4: JWT без срока действия**

Если токен не имеет `exp` (expiration), он валиден вечно. Если я украл такой токен, я могу использовать его годами. Всегда устанавливай `exp` и `iat` (issued at).

### 🛡️ Защита JWT в Go (best practices)

```go
import (
    "time"
    "github.com/golang-jwt/jwt/v5"
)

// Секрет из переменной окружения, не из кода
var jwtSecret = []byte(os.Getenv("JWT_SECRET"))

type Claims struct {
    UserID int    `json:"user_id"`
    Role   string `json:"role"`
    jwt.RegisteredClaims
}

func generateToken(userID int, role string) (string, error) {
    claims := Claims{
        UserID: userID,
        Role:   role,
        RegisteredClaims: jwt.RegisteredClaims{
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(15 * time.Minute)), // Короткий срок
            IssuedAt:  jwt.NewNumericDate(time.Now()),
            NotBefore: jwt.NewNumericDate(time.Now()),
            Issuer:    "my-app",
            Subject:   fmt.Sprintf("%d", userID),
        },
    }

    token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return token.SignedString(jwtSecret)
}

func validateToken(tokenString string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenString, &Claims{}, func(token *jwt.Token) (interface{}, error) {
        // Явно проверяем алгоритм
        if _, ok := token.Method.(*jwt.SigningMethodHMAC); !ok {
            return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
        }
        return jwtSecret, nil
    })
    if err != nil {
        return nil, err
    }

    claims, ok := token.Claims.(*Claims)
    if !ok || !token.Valid {
        return nil, fmt.Errorf("invalid token")
    }

    return claims, nil
}
```

### 🖥️ Фронтенд: хранение JWT — localStorage vs HttpOnly cookie vs sessionStorage

Как middle/middle+ фронтендер, ты знаешь, что хранение токена — это компромисс. Вот полная картина с точки зрения безопасности:

**localStorage**

```javascript
// После логина
localStorage.setItem('access_token', response.data.token);

// При запросах
axios.defaults.headers.common['Authorization'] = `Bearer ${localStorage.getItem('access_token')}`;
```

Плюсы: простота, не требует CSRF-защиты (токен не отправляется автоматически), survives page reloads и закрытые вкладки.

Минусы: **уязвим к XSS.** Любой XSS на твоём домене может прочитать `localStorage.getItem('access_token')` и отправить токен хакеру. Защита через CSP и отсутствие XSS — но XSS бывают даже в хороших проектах. Если у тебя SPA с user-generated content (комментарии, сообщения), localStorage — опасный выбор.

**HttpOnly cookie**

```go
// Бэкенд устанавливает куку при логине
http.SetCookie(w, &http.Cookie{
    Name:     "access_token",
    Value:    token,
    HttpOnly: true,  // JS не может прочитать
    Secure:   true,  // Только HTTPS
    SameSite: http.SameSiteStrictMode,
    Path:     "/",
    MaxAge:   900,   // 15 минут
})
```

Плюсы: защищён от XSS (JS не видит HttpOnly-куку), автоматически отправляется браузером.

Минусы: **требует CSRF-защиты** (кука отправляется автоматически с любым запросом к домену). Невозможно использовать для кросс-доменных API (другой origin).

**sessionStorage**

```javascript
sessionStorage.setItem('access_token', response.data.token);
```

Плюсы: автоматически очищается при закрытии вкладки, не survives page reloads в новой вкладке (хорошо для чувствительных операций).

Минусы: те же проблемы с XSS, что и localStorage. Не survives закрытие вкладки (может быть и плюсом, и минусом).

**Рекомендация для SPA + API (один origin):**
- Access token (короткий срок, 15 мин) — в HttpOnly cookie (защита от XSS) + CSRF-токен (защита от CSRF)
- Refresh token (долгий срок, 7-30 дней) — в отдельной HttpOnly cookie с `Path=/api/auth/refresh` (не отправляется с обычными запросами)

**Рекомендация для SPA + API (разные origins, например app.example.com + api.example.com):**
- Access token — в памяти JavaScript (переменная, не localStorage), обновляется через refresh token
- Refresh token — в HttpOnly cookie на API-домене с `SameSite=None; Secure`
- Это сложнее, но безопаснее для cross-origin сценариев

**Refresh Token Flow на фронтенде (React с axios):**

```javascript
// Перехватываем 401 и пытаемся обновить токен
axios.interceptors.response.use(
    response => response,
    async error => {
        const originalRequest = error.config;

        if (error.response?.status === 401 && !originalRequest._retry) {
            originalRequest._retry = true;

            try {
                // Пытаемся обновить токен через refresh_token (HttpOnly кука)
                await axios.post('/api/auth/refresh', {}, { withCredentials: true });
                // Повторяем оригинальный запрос
                return axios(originalRequest);
            } catch (refreshError) {
                // Refresh token тоже протух — редиректим на логин
                window.location.href = '/login';
                return Promise.reject(refreshError);
            }
        }

        return Promise.reject(error);
    }
);
```

### 🔧 DevOps: управление секретами и мониторинг попыток входа

**Управление JWT-секретами**

JWT-секрет не должен лежать в коде, в `.env`-файле в репозитории или в Docker-образе. Правильные способы хранения:

1. **Vault (HashiCorp):** секреты инжектируются в контейнер при запуске, никогда не записываются на диск.
2. **AWS Secrets Manager / GCP Secret Manager:** секреты получаются через API при старте приложения.
3. **Kubernetes Secrets:** лучше, чем `.env` в репозитории, но всё ещё не идеально (base64 — не шифрование). Использовать вместе с etcd encryption at rest.

Ротация секретов: JWT-секрет должен периодически меняться. При ротации старый секрет ещё некоторое время принимается для валидации существующих токенов, а новые токены выпускаются с новым секретом. Это позволяет бесшовно перейти на новый ключ без инвалидации всех активных сессий.

**Мониторинг попыток входа через SIEM**

Настрой экспорт логов аутентификации в SIEM (ELK, Splunk, Grafana Loki) и создай алерты на:

- N неудачных попыток входа с одного IP за короткий промежуток времени (брутфорс)
- N неудачных попыток входа на разные аккаунты с одного IP (password spraying)
- Успешный вход с нового IP/устройства для пользователя (возможно, credential stuffing)
- Использование `alg: none` в JWT (атака на JWT)

### 📝 Что мы узнали?
- Брутфорс перебирает пароли для одного аккаунта, password spraying — один пароль для многих аккаунтов
- bcrypt с cost=12+ делает массовый перебор непрактичным
- Credential stuffing использует утекшие базы паролей; главная защита — MFA
- JWT не шифрует данные, только подписывает; секреты нельзя хранить в коде
- Атаки на JWT: alg=none, подмена алгоритма, утечка секрета, отсутствие срока действия
- **Фронтенд:** HttpOnly cookie + CSRF — безопаснее, чем localStorage + XSS-уязвимость
- **DevOps:** секреты в Vault/KMS, ротация ключей, SIEM-алерты на аномалии входа

### 💥 Типичные ошибки
- **Ошибка:** Хранить JWT в localStorage, потому что «так проще»
    - **Правда:** Любой XSS украдёт токен. HttpOnly cookie + CSRF-защита безопаснее для одного origin.
- **Ошибка:** Использовать SHA-256 для хеширования паролей
    - **Правда:** SHA-256 быстрый, брутфорс по утекшей базе восстановит большинство паролей. bcrypt/scrypt/argon2.
- **Ошибка:** Не проверять алгоритм при верификации JWT
    - **Правда:** Атака с подменой алгоритма (RS256→HS256) работает, если библиотека не проверяет `alg`.
- **Ошибка:** Жёсткая блокировка аккаунта после N неудачных попыток
    - **Правда:** Создаёт DoS-вектор. Используй прогрессивную задержку.

### 🔁 Для быстрого повторения
- **Брутфорс:** много паролей → один аккаунт. Защита: rate limiting + bcrypt
- **Password Spraying:** один пароль → много аккаунтов. Защита: rate limiting по IP + username
- **Credential Stuffing:** утекшие пары email+пароль. Защита: MFA
- **bcrypt:** cost=12, ~300 мс на хеш, автоматическая соль
- **JWT:** проверять `alg` явно, `exp` всегда, секрет не в коде, short-lived токены
- **Фронтенд:** HttpOnly cookie + refresh token flow, перехват 401 в axios
- **DevOps:** Vault для секретов, fail2ban на логин, SIEM-алерты

### ✅ Ответы на вопросы для самопроверки

1.  **Брутфорс:** много паролей для одного аккаунта. Account lockout эффективен: после N неудач аккаунт блокируется. **Password Spraying:** один пароль для тысяч аккаунтов, по 1-2 попытки на аккаунт с большими интервалами. Account lockout не срабатывает, потому что на каждый аккаунт приходится 1 попытка, и она ниже порога блокировки. Защита: rate limiting по IP (один IP не может перебирать сотни аккаунтов), мониторинг аномалий (всплеск 401-х ответов).

2.  SHA-256 спроектирован для скорости (миллиарды хешей в секунду на GPU), bcrypt — для медлительности (~300 мс на хеш при cost=12). Cost factor определяет количество итераций (2^cost). Правильный cost: такой, при котором хеширование на продакшен-железе занимает 250-500 мс. Слишком низкий — быстрый брутфорс. Слишком высокий — пользователи ждут логина по 2 секунды.

3.  Rainbow table — это заранее посчитанная таблица «пароль → хеш» для популярных паролей. Без соли два пользователя с паролем «qwerty123» имеют одинаковый хеш — хакер находит всех одним поиском по таблице. Соль — уникальная случайная строка для каждого пользователя — делает каждый хеш уникальным даже для одинаковых паролей. Хакеру нужно строить новую rainbow table для каждого пользователя, что делает атаку непрактичной.

4.  Это **credential stuffing.** Брутфорс не дал бы 100% успешных попыток (пароли подбираются, а не известны заранее). 10 000 уникальных IP обходят rate limiting по IP. Защита: MFA (даже с правильным паролем хакер не пройдёт второй фактор), мониторинг аномалий (10 000 входов с новых устройств/IP за час — триггер), проверка паролей на утечку при регистрации.

5.  **Атака с подменой алгоритма (RS256 → HS256).** Хакер берёт публичный ключ, создаёт JWT с `alg: HS256` и подписывает его публичным ключом как HMAC-секретом. Если серверная библиотека не проверяет алгоритм строго, она использует публичный ключ как секрет для HMAC, проверяет подпись — и она совпадает. Защита: явно проверять `alg` при верификации (`token.Method.Alg() != "RS256"`).

6.  **localStorage:** уязвим к XSS (любой скрипт читает токен), не уязвим к CSRF (токен не отправляется автоматически). **HttpOnly cookie:** защищён от XSS (JS не видит куку), уязвим к CSRF (кука отправляется автоматически) — нужна CSRF-защита. **sessionStorage:** как localStorage, но очищается при закрытии вкладки. **Рекомендация для одного origin:** HttpOnly cookie для access токена + CSRF-токен. **Для разных origin:** access токен в памяти JS + refresh токен в HttpOnly cookie на API-домене.

7.  **Нет.** Rate limiting по IP блокирует каждый IP индивидуально. Ботнет с 10 000 IP делает по 3 запроса с каждого — лимит в 5 не превышен. Нужен дополнительный лимит по username: не более N попыток на конкретный аккаунт за период, независимо от IP. И прогрессивная задержка вместо отказа.

8.  Если JWT-секрет утёк, хакер может подписывать любые токены — он становится любым пользователем, включая администратора. Нужна немедленная ротация. Для бесшовной ротации: ввести новый секрет, но валидировать токены и старым секретом тоже. Новые токены выпускать с новым секретом. Когда все старые токены истекут (по `exp`), убрать старый секрет. Альтернатива: инвалидировать все сессии принудительно (пользователи перелогинятся).

9.  **Да, безопасно.** Have I Been Pwned API использует k-anonymity: клиент отправляет только первые 5 символов SHA-1-хеша пароля. Сервер возвращает список хвостов хешей с таким префиксом. Клиент проверяет, есть ли хвост его хеша в ответе. Полный хеш (и тем более пароль) никогда не покидает твой сервер.

10. **Refresh token flow:** access token живёт 15 минут, refresh token — 7 дней. Когда access token истекает (401), фронтенд шлёт refresh token на `/api/auth/refresh`, получает новый access token и повторяет оригинальный запрос. Преимущества: (1) короткоживущий access token ограничивает окно атаки при краже, (2) refresh token используется редко и только на одном эндпоинте (меньше шансов утечки через логи), (3) сервер может инвалидировать refresh token (отозвать сессию) без влияния на других пользователей. Недостаточно одного долгоживущего токена: если его украдут, хакер будет иметь доступ месяцами.
